# Spec: 조회·완료 입력의 주변 ASCII 공백만 허용
Upstream: intent.md@ac0963b. Status: draft.
작성 조건: root가 허용한 합성 예시 작성이며 실제 제품 수락 기록이 아니다. 입력은 intent.md와 context.md다.
Skills applied: none — 합성 입력만 사용했으며 조직 정책 스킬 적용을 실행한 예시는 아니다.

복사한 ID는 허용된 주변 공백만 떼어 비교한다. 저장 ID, 내부 공백, 대소문자와 다른 유니코드
공백의 의미는 바꾸지 않는다. 같은 규칙을 조회와 완료에 적용한다.

## Requirements
- R1. show/complete는 입력 양끝의 ASCII space, tab, CR, LF를 제외한 ID로 정확히 조회한다.
  내부 공백·대소문자·다른 유니코드 공백은 변환하지 않는다.
- R2. 정상 show와 실패 입력은 데이터 파일을 바꾸지 않는다. 정상 complete는 대상 status만
  done으로 바꾸고, 이미 완료된 대상의 반복 처리는 파일을 다시 쓰지 않는다. 저장 ID는 항상 보존한다.
- R3. 빈 입력이나 허용된 공백뿐인 입력, 존재하지 않는 ID는 기존 없는 요청의 rc=1·오류 형식을
  유지한다. list와 다른 파일 읽기/쓰기 오류 처리도 유지한다.

## Acceptance criteria
각 사례는 [context.md](context.md)의 새 데이터에서 시작한다. 아래 결과는 실행 기록이 아닌 검증 기준이다.
- AC1 → R1,R2: `show`에 문자열 ` \tR-202\r\n`을 주면 R-202를 조회하고 파일은 바뀌지 않는다.
  `\t`, `\r`, `\n`은 이 예시에서 실제 ASCII 제어 문자를 뜻한다.
- AC2 → R1,R2,R3: `R-20 2`, `r-202`, 공백·탭·LF뿐인 입력, U+00A0으로 감싼 R-202,
  빈 문자열과 R-999는 show/complete 모두 rc=1이고 파일은 같다. 새 데이터 복사본마다 확인한다.
- AC3 → R1,R2: `complete`에 ` R-202\n`을 주면 그 행의 status만 done이 된다. 재실행은 성공하고
  파일 바이트가 그대로다. ID·다른 필드·다른 행을 정규화하지 않는다.
- AC4 → R2,R3: 정확한 ID의 기존 조회·완료, 목록 순서와 출력, 원래 오류 동작을 유지한다.
  재현/회귀 시험을 먼저 추가하고 기존 시험은 수정·삭제하지 않는다. 구체적인 시험 경로·명령은 plan의 몫이다.

## Design
코드 읽기에서 원본 입력과 저장 ID를 바로 비교하는 공유 조회를 확인했다. 원본 문자열은 유지하고
비교할 입력 사본에만 허용 문자 집합을 적용한 뒤 기존 조회·완료 흐름을 재사용한다.
오류 메시지의 입력 표현도 원본을 사용해 기존 오류 계약을 유지한다.

Python의 인자 없는 strip은 허용한 네 문자보다 넓게 처리하므로 이 결정과 맞지 않는다.
`value.strip(" \t\r\n")`은 의도를 설명하는 구현 예시이며 helper 이름·함수 분리는 계약이 아니다.
저장 데이터를 일괄 보정하거나 각 명령에서 따로 정규화하면 데이터 의미나 두 명령의 일관성을
깨뜨릴 수 있어 선택하지 않는다. 원인 관측은 코드에서 얻은 것이며 요청자가 처음부터 알았다고 쓰지 않는다.

## Constraints and scope
입력 보정을 위해 저장 ID나 행을 재작성하지 않으며 complete의 기존 상태 변경만 허용한다(R2).
기존 시험을 유지하고 새 재현/회귀 시험을 먼저 작성한다. Python 표준 라이브러리와 2~4 업무
파일 범위를 유지한다. ID 재발급, 전체 데이터 정리, 유니코드·대소문자 정규화, list 변경은 범위 밖이다.

## Open questions
- Q1 answered: 네 ASCII 문자만 허용한다. 합성 요청자의 후속 답변을 R1에 반영했다.
- Q2 answered: 내부 공백·대소문자·그 밖의 공백은 그대로 비교하며, 빈 ID는 기존 실패다. R1,R3에 반영했다.
- Q3 answered: show/complete에 함께 적용하고 list는 유지한다. R1,R3에 반영했다.
설계 중 추가된 중요한 미결 질문은 현재 없다.

## Flagged concerns
없음 — 주어진 입력 범위에서 저장 형식이나 새로운 권한·외부 의존을 바꾸지 않는다. 지나치게 넓은
정규화로 다른 입력을 같은 ID에 연결하는 회귀 위험은 R1과 AC2에 반영했다. 정책 적용 실행 결과는 아니다.
