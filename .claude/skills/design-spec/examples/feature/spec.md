# Spec: 담당자 조건으로 요청 목록 좁히기
Upstream: intent.md@ac0963b. Status: draft.
작성 조건: root가 허용한 합성 예시 작성이며 실제 제품 수락 기록이 아니다. 입력은 intent.md와 context.md다.
Skills applied: none — 합성 입력만 사용했으며 조직 정책 스킬 적용을 실행한 예시는 아니다.

기존 목록 사용법을 유지하면서 `list --owner <ID>`로 담당자의 완료·미완료 요청을 함께 조회한다.
기존 목록 흐름에서 조건을 적용하면 충분하다. 현재 입력에서 별도 사람 결정이 필요한 우려는 없다.

## Requirements
- R1. `list --owner <ID>`는 담당자가 문자열 ID와 정확히 일치하는 행을 기존 순서로 출력한다.
  완료 건도 포함하며 null 담당자는 어떤 문자열과도 일치하지 않는다.
- R2. 옵션 없는 list, show/complete의 동작과 출력 열·JSON 필드를 유지한다.
- R3. 조회는 파일을 바꾸지 않는다. 일치하는 행이 없으면 stdout이 비고 rc=0이다.

## Acceptance criteria
각 사례는 [context.md](context.md)의 새 데이터 복사본을 사용한다. 예시 ID는 입력 데이터다.
- AC1 → R1,R3: `list --owner hana`는 R-101, R-103만 그 순서로 출력하고 파일 바이트는 같다.
- AC2 → R1,R3: nobody, HANA, `-`로 각각 조회하면 출력이 없고 rc=0이며 파일은 같다.
  마지막 사례는 화면상의 미배정 표시를 실제 담당자 문자열로 오인하지 않는지 확인한다.
- AC3 → R2,R3: 옵션 없는 list는 네 행을 원래 순서·열로 출력한다. 기존 show/complete와 I/O
  오류 처리의 회귀는 기존 검증으로 확인한다. 새 시험의 파일명과 실행 명령은 plan에서 정한다.

## Design
argparse의 list 하위 명령에 선택 인자를 추가하고, 현재 JSON 읽기 뒤 순서를 유지하는 필터를
적용한다. 출력은 기존 display를 사용한다. 비교는 대소문자 변환이나 부분 일치를 하지 않는다.
show/complete의 ID 조회 흐름에 조건을 끼워 넣지 않는다.

별도 인덱스·DB·캐시는 도입하지 않는다. 이 기능은 이미 읽는 배열을 한 번 걸러내는 선택이며,
입력에는 기존 순회를 대체할 규모나 성능 문제가 없다. 내부 함수 이름은 구현자가 정할 수 있다.

## Constraints and scope
기존 명령·필드와 조회의 읽기 전용 성격을 보존한다(R2,R3). 업무 코드는 2~4파일 이내의 작은
변경이고 시험·문서는 별도다. 미배정 전용 조회, 복수 담당자, 부분 일치·정렬·새 저장소는 범위 밖이다.

## Open questions
- Q1 answered: 완료 건 포함·원래 순서 유지. 합성 요청자의 후속 답변이며 R1에 반영했다.
- Q2 answered: 정확 일치, null 제외, 없는 담당자는 빈 결과. R1,R3과 AC2에 반영했다.
- Q3 answered: `list --owner <ID>`, 기존 list 유지. R1,R2에 반영했다.
설계 중 추가된 중요한 미결 질문은 현재 없다.

## Flagged concerns
없음 — 알려진 입력 범위에서는 외부 연동·권한·저장 형식을 바꾸지 않는다. 이는 실제 팀 정책을
모두 검토했다는 뜻이 아니며, 채택 팀이 별도 제약을 제공하면 관련 요구와 설계를 다시 검토한다.
