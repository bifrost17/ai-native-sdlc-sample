# M01 합성 입력: 공유 저장소 이행과 뒤늦은 소비자 발견

root가 이 양식 설계를 위해 만든 가상 서비스다. 실제 저장소·운영·고객 지표를 관측한 사례가 아니다.
아래 구성·정책·답변은 이 사례에만 주어진 사실이며 우리 회사의 정책으로 추정하지 않는다.

## 현재 구조와 확인된 조건

- 단일 호스트의 사내 Python 서비스다. API와 웹 화면, 저장소 어댑터가 구분돼 있다.
  기존 사내 로그인과 권한 검사를 API가 처리한다. SQLite를 사용할 수 있고 운영 담당이 관리한다.
- GET /requests는 저장 순서대로 id, title, owner, status를 반환한다. POST /requests/{id}/complete는
  대상의 status만 done으로 바꾸고 같은 완료의 반복은 같은 결과다. 이 API에는 기존 오류 응답 계약이 있다.
  이 합성 입력의 GET 성공 형식은 HTTP 200의 `{ "requests": [...] }`, 완료 성공은 HTTP 200의
  해당 행 객체다. 미인증 401, 완료 권한 부족 403, 없는 ID 404, 일시 저장 오류 503을 사용한다.
  503 본문은 `{ "error": "temporarily_unavailable" }`이고 내부 DB 오류를 노출하지 않는다.
- 담당자 본인과 운영자만 완료 처리할 수 있다. 권한 없는 요청이 저장소를 바꾸면 안 된다.
  이는 주어진 기존 계약이며 신규 보안 정책을 만들어 정한 값이 아니다.
- 이행은 서비스를 멈춘 동안 할 수 있다. 롤링 배포·무중단 이행은 필요하지 않다.
  기존 JSON에는 schema_version=1, requests 배열이 있고 각 행의 id는 유일하다.
  id/title은 문자열, owner는 문자열 또는 null, status는 open 또는 done이다. 별도 사용자 정의
  필드는 없는 것으로 확인했다. 알 수 없는 필드나 형식 버전은 버리며 이행하지 않고 거부한다.
- 처리 결과 보존은 필수다. 신규 프로세스가 쓰기를 시작한 뒤 옛 백업 JSON으로 단순 복귀하면
  이후 처리 결과가 사라지므로 허용하지 않는다. 운영 담당은 별도 복구용 내보내기를 원한다.
- 정량 성능 목표·측정치는 주어지지 않았다. 임의의 rps·지연 목표를 만들지 않는다.
  기존 저장 오류 대기 상한 설정은 5초이며, 새 저장소도 이 상한을 사용한다. 이는 성능 측정치가
  아닌 합성 입력의 기존 동작이다. 영속성 설정을 끄지 않는 SQLite 지원 로컬 파일시스템을 사용한다.

## 첫 설계 시점의 답변

- Q2: 이행 실패 시 원본 JSON을 보존하고 새 저장소를 사용하지 않는다. 검증 후 전환한다.
  전환 후 쓰기까지 했다면 그 결과를 포함하는 복구가 필요하다. 이행·복구는 중지 상태에서 실행한다.
- Q3: 위 단일 호스트와 SQLite 가능 여부, 운영 담당의 책임이 확인됐다.
- Q1: 업무 오너는 API 밖 소비자를 아직 확인하지 못했다. 확인 전 “없음”으로 적지 않는다.

## 설계 검토 중 발견과 후속 결정

운영 담당이 야간 보고서가 JSON을 직접 읽는다고 알렸다. 최초 설계는 읽기 소비자를 미확인으로
표시한 초안이며 아직 plan으로 인계하지 않았다. 새 저장소만 갱신하면 보고서가 옛 데이터를 읽는다.

업무 오너·운영 담당은 보고서를 기존 GET /requests로 전환하는 안을 선택했다. 이미 있는 읽기 전용
서비스 계정과 호출 경로를 재사용할 수 있으며 새 자격증명을 만들지 않는다. 저장소 전환 전에 이
호환성을 확인하고 같은 전달 범위에 포함한다. 영구 JSON 미러·이중 쓰기는 원하지 않는다.
읽기 소비자는 이 보고서 하나이고 다른 직접 쓰기 소비자는 없다고 운영 담당이 확인했다.

문구 개선 같은 질문은 뒤로 미룰 수 있어도, 이 소비자 결정은 설계와 수용 기준을 바꾸므로
담당자 이름만 붙여 두고 엔지니어링에 넘길 수 없는 질문이라는 예시다.
