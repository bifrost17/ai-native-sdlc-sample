# 필요한 경우에만 늘리는 실행 상세

이 문서는 선택한 상세를 어디에 남길지 돕는다. 기본 양식에 모든 표·항목을 추가하지 않는다.
프로젝트의 docs/GIT-WORKFLOW.md와 docs/PR-SIZE.md가 기준이며, 계획은 이 변경의 구체적인 답을 기록한다.

## 여러 PR
Order of work 안에 PR별 짧은 블록을 둔다. 목적·포함 작업·선행 관계·통합 후 main의 동작·남은
범위·Proof 참조면 충분하다. 사용자에게 새 기능이 노출되지 않는 호환 준비도 기존 동작을 보존하고
독립 검증할 수 있으면 합리적이다. 단순 DB/API/UI 층별 제목만으로 분할을 끝내지 않는다.
기능·시험·필요한 설명을 응집되게 묶으며 줄 수를 맞추려 쪼개거나 큰 계획 전체를 한 PR로 고정하지 않는다.
큰 묶음이 더 낫다면 함께 둔 이유, 읽을 순서, 위험·복구를 적는다.

종속 작업은 선행 PR을 main에 통합한 뒤 최신 main에서 시작하는 것이 기본이다. 대기 비용 때문에
stacked 작업을 선택하면 실제 base·의존성을 표시하고 선행 merge 뒤 남은 diff와 대상 main을
다시 맞춘다. 장기 기능 통합 브랜치를 만들지 않는다. 단계 문서 커밋·사람 수락과 PR 통합은 별개다.

## 통합과 공개가 다를 때
docs/RELEASE-CONTROL.md를 읽고 spec의 공개 계약을 실행 순서로 옮긴다. 관련 PR별 main의 동작과
일반 OFF/테스트 ON 상태, 남은 공개 단위와 증거를 적는다. 같은 제어·설정 위치를 PR 사이에 재사용하며
소스의 숨김 코드를 매번 고치지 않는다. 담당자의 공개 판단, 설정 반영/중단 방법(재시작이 필요하면 포함),
최종 전체 확인과 제거 조건을 기존 Order/Proof에 둔다. OFF도 빌드·기존 동작·호환성을 유지해야 한다.
부분 ON 시험을 전체 완료로 쓰지 않고, 제어 제거 전 구버전/복구 경로와 설정 정리 순서를 고려한다.
작은 완결 변경에 플래그나 별도 공개 문서를 추가하지 않는다.

## 병렬 인계
독립 세션은 branch/worktree별로 나눈다. 각 작업의 파일·결과·필요한 입력과 읽을 공유 계약의 위치/판을
남긴다. 같은 파일을 수정하는 작업은 순차 실행한다. 파일이 달라도 계약·순서 의존이 있으면 먼저
합의하거나 선행 작업을 기다린다. 한정된 조사·검증 subagent가 필요하다고 PR을 따로 만들지는 않는다.

통합 책임과 공유 plan 조정 책임을 정한다. 병렬 담당의 변경은 관련 구현 커밋에 반영할 수 있도록
조정하며, 공유 문서 편집은 순차로 처리한다. 다른 branch의 계획 변경을 덮어쓰거나 마지막에 한꺼번에
갱신하지 않는다. 개별 PASS 뒤에도 최신 main과 합친 계약·데이터·사용 흐름을 함께 확인한다.
사람이 검토할 수 있는 범위 안에서만 병렬도를 늘린다.

## 전환·복구 또는 큰 불확실성
Git merge는 배포·데이터 전환의 원자성을 보장하지 않는다. 실제로 운영 영향이 있을 때 중지/호환
조건, 전환 전 확인, 실패 후 데이터와 기존 사용자 흐름의 처리, 재개 판단을 적는다. 없는 호스트 명령이나
무중단 요구를 만들지 않는다. 미확인 사항은 영향과 해결할 단계/담당을 적고 그 결정에 의존하는 작업은
해결 전 진행하지 않는다. 이미 합의한 구현을 막지 않는 질문까지 일괄 중지 조건으로 만들지는 않는다.

기존 테스트로 확인하지 못하는 중요한 동작은 실제 시험이나 관측 방법을 정한다. 시험 코드 전체와
사소한 함수 선택까지 plan에 복제하지 않는다. 모델의 실수 가능성을 없애려는 체크리스트보다
변경 영향에 맞는 모델·추론, 반복 검증과 사람 판단을 사용한다.
