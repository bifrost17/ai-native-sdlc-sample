# intent.md 딥 리서치 — 「Capture as intent.md」 · The AI-Native SDLC Playbook (Claude Academy)

조사일 2026-09-08 · 부모(Fable) + 조사 레인 5개(sonnet · medium · 읽기 전용) · 원문 raw 215파일(L1 24 · L2 33 · L3 48 · L4 61 · L5 49) · 인용은 부모가 raw 를 열어 축자 대조한 것만 실었다. 라벨: **확정**(원문 직접 확인) · **추정** · **확인 못 함** · **부모 판독**(해석).

## 0. 한 장 요약

1. **정의.** intent.md 는 Stage 1 Plan 의 산출물 — *"a proto-spec in the originator's own terms. The artifact contains what is wanted, why, and under which constraints."* 필드는 `# Intent:` 제목 · `Author/Status` 머리 · Problem · Proposed outcome · Affected users and systems · Constraints · Open questions 의 7개. 비엔지니어 originator 가 Claude 와 써서 제품 레포 `intent/` 폴더에 커밋하고, product owner 의 accept/reject 가 merge 또는 closing review 로 기록된다. 사슬(intent.md → spec.md → plan.md → diff → review findings → incident record)의 시작이자, Stage 6 이 같은 형식으로 되돌려 쓰는 끝이다.
2. **공식 문서 대조(사용자 지시 「공식이 제일 정확」).** `intent.md` 라는 문자열은 Academy 코스와 같은 날(2026-08-21) 블로그 밖 어디에도 없다 — Claude Code 문서(code.claude.com) · docs.claude.com · support.claude.com · `anthropics/*` 레포 전부 0건. 레슨이 전제하는 인프라 5개 중 「비엔지니어의 Claude 접근(Cowork)」만 온전히 뒷받침되고, 「커넥터가 대신 커밋」(내장 GitHub 통합은 읽기 전용 · GitHub MCP 커넥터는 Read & write 배지만) · 「템플릿을 skill 로 + 리드 사인오프」(번들·조직 배포는 있으나 사인오프 장치 없음) · 「plan.md 커밋」(제품 기능이 아니라 관행)은 부분, 「알림 → intent.md 초안 자동화」는 인접 패턴만 있다.
3. **선행 기법 대비.** 필드는 Shape Up(Problem) · PRD/RFC(Open questions) · ADR(Status) 의 합류이고, 「git 옆에 산다」「승인 = merge」는 Doorstop(2013)·RFC PR 이 이미 확립한 관행이다. 진짜 차별점은 ① 비엔지니어 원저자를 진입 조건으로 명시 ② 산문 intent 와 형식 spec 을 파일 층으로 분리 ③ 단계 경계의 손실률 지표(survival rate · 첫 spec.md 이후 intent 변경 수). 파일명 자체는 2026 상반기에 무관한 3곳(02-18 gist · 04-18 `intent-verify` · 06-26 `intent-md`)에서 먼저 쓰였다 — 최초 명명은 아니다.
4. **외부 논평의 수렴점(발행 후 2주 · 오독 0건 · 도입 보고 0건).** ⓐ hop 사이에 기계적 검사가 없다 — git 은 순서만 기록하고 파생을 증명하지 않는다(menuagentic) ⓑ 첫 아티팩트에 「준비도 바닥」이 없다(Pathmode) ⓒ 요구공학이 프롬프트 하나로 축소됐다(Martinelli) ⓓ 극장화 신호는 「수용률 ~100% · 파일당 1분 미만」(Kotadia) ⓔ 신호 → 레포 매핑 기전이 없다(Port.io).
5. **이 레포와의 대응.** 플레이가 노리는 「핸드오프 제거」는 1인 소유자 구조로 이미 얻고 있다. 없는 것은 「왜」 한 장이 상설로 사는 자리(지시는 작업 문서 §1 축자 · 브리프는 레포 밖 · 착지 시 아카이브)와 아이디어 accept/reject 의 계량뿐. `docs/spec/REQUIREMENTS.md` 는 플레이북 어휘로 spec 층이고, `FINDINGS.md` 의 「승격 조건」은 플레이북의 closed intent 보다 한 걸음 앞선 장치다.

## 1. 레슨 정독 (공식 페이지 curl 2026-09-08 04:43Z · L1 raw `off-11` · 부모 직접 대조)

### 1.1 위치 · 골격
- Lesson 2 of 14 · Stage 1 Plan. 앞은 Introduction, 뒤는 Stage 2 「Requirements and design」.
- 플레이 공통 골격(Introduction 이 정의): **What changes → Getting started(Prerequisites · Infrastructure) → How to execute it → What it looks like → Governance considerations → How to measure it.** 「Prerequisites」가 의존 그래프를 만든다. 이 플레이는 **Prerequisites: None** — 다른 플레이와 독립 도입 가능한 유일한 출발점 중 하나.

### 1.2 정의 문장(축자)
- *"The intent.md, which kicks off the software development process, can enter through different routes. A person has an idea, a ticket is filed, or an incident is surfaced via an alert (see Stage 6: Maintain)."*
- *"The proto-spec generated by Claude is human readable, version controlled, and immediately consumable by the next stage. The proto-spec is saved as an intent.md."*
- *"Regardless of whether the intent originates from an event trigger or a person, the same steps apply: the product owner reviews and corrects the agent-written intent.md before it is committed."*
- What changes — Traditional: *"An idea passes through backlog entries, user stories, story points, and refinement meetings before anyone can act on it. Ownership transfers at each handoff, so what reaches engineering is several steps removed from what the originator meant."* / AI-native: *"The originator brainstorms with Claude and writes the result down as intent.md, a proto-spec in the originator's own terms. The artifact contains what is wanted, why, and under which constraints. Repeat processes are encoded via skills."*

### 1.3 역할 · 인프라 · 실행
- **역할 5**: originator(원저자 · 비엔지니어 가능) · product owner(리뷰 · 정정 · accept/reject) · technical team member / platform or engineering team(intent home 설치 · 쓰기 권한 결정 · 템플릿 skill) · lead(템플릿 사인오프) · Claude(*"asks the questions an analyst would ask: scope, users, constraints, and what success looks like"*).
- **인프라 3**: *"Claude access for people who are not engineers (claude.ai or Cowork); an agreed intent.md template; a shared, version-controlled home for intent that the product owner watches."*
- **홈 선택 규칙**: *"For a single product the simplest home is an intent/ folder in the product repo. This setup keeps the artifact chain next to the code derived from it. A dedicated intent repo is only worth the overhead when intent spans many repositories, and in a monorepo it is a directory."* Jira 관계는 Stage 3 의 Legacy systems 절로 위임.
- **비Git 기여자**: *"a connector to the version-control system (e.g., GitHub) lets Claude commit Markdown files on their behalf from claude.ai or Cowork."*
- **실행 5단계**: ① originator 가 자기 말로 서술(*"what they cannot do today, who is affected by the idea, what better looks like, or what is out of scope. No formal language is required."*) ② 구체화까지 브레인스토밍 ③ *"Ask Claude to write the result as intent.md using the organization's template, which can be encoded as a skill set up by a technical team member and signed off by a lead. This can cover the problem, proposed outcome, affected users and systems, constraints, and open questions."* ④ originator 정정 ⑤ 공유 홈에 커밋 — *"Author and timestamp join the record, and the product owner picks the idea up from there."*

### 1.4 예시 파일(축자)
```markdown
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.
## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.
## Proposed outcome
Customers see claim status, next step and expected date in the portal.
## Affected users and systems
Claims handlers, portal team, claims-core API.
## Constraints
No new PII in the portal session. Existing authentication only.
## Open questions
Do third-party loss adjusters need access too?
```
본문이 여섯 줄 남짓 — 「proto-spec」의 크기 감각이 이것이다.

### 1.5 거버넌스 · 메트릭(축자)
- *"The evidence is the committed intent.md, which lists the author, the timestamp, and the full revision history. It's logged in the Git history of the intent home. The product owner approves, and the accept or reject decision that sends the intent into Stage 2: Design is recorded as the merge or the closing review."*
- Leading: *"Time from first conversation to a committed intent.md, read from Git history on the intent home, which records author and timestamp. The expectation is for this to fall from a multi-week elicitation and refinement cycle to hours."*
- Lagging: *"The survival rate, or the share of intent.md files that the product owner accepts into Stage 2: Design rather than closes. … Additionally, count the changes to intent.md made after the first spec.md commit for the same change."*

### 1.6 부모 판독
- **P1** 리뷰 지점이 둘 — 「커밋 전 PO 정정」과 「accept/reject = merge 또는 closing review」. 브랜치/PR 흐름(초안 커밋 → PO 리뷰 → merge = accept · close = reject)으로 읽는 것이 자연스럽지만 문면은 둘을 구분해 정의하지 않는다.
- **P2** `Status: draft` 는 있으나 상태 전이(draft → ?)는 정의되지 않았다 — merge/close 라는 git 행위가 곧 상태다.
- **P3** lagging 두 번째 지표(첫 spec.md 이후 intent 변경 수)는 「의도 불안정성」 계기 — 브레인스토밍 부족 또는 설계 단계에서 드러난 구멍을 잰다.
- **P4** leading 의 「첫 대화 시각」은 git 에 없다 — 문면은 "read from Git history" 라 하지만 git 은 커밋 시각만 안다(§6.4).
- **P5** 유일한 인프라 결정은 「홈을 어디에 둘 것인가」 — 나머지는 조직 정책(누가 쓰는가 · 템플릿).
- **P6** 파일명 · ID · 중복 · 폐기 후 처리 · Jira 이중 기록은 이 레슨에 없다(§8.2).

## 2. 플레이북 안의 위치 (공식 레슨 14개 · L1 raw + 부모 직접 확인)

### 2.1 사슬
Introduction 축자: *"A stage ends by committing an artifact with the commit initiating the next stage. An accepted intent.md triggers the requirements and design pass, an approved spec.md triggers plan mode, a merged PR triggers the pipeline, and a breached control band in production writes the next intent.md, and so the loop continues."* · *"Each stage ends by writing one to version control (including intent.md, spec.md, plan.md, the diff and its tests, the PR with its review findings, and the incident record), and the next stage begins by reading it. For the early stages, .md files are the predominant artifact because a product owner and an agent can both read and act on the same file."* · *"The chain of commits is also the audit trail: who asked for what, what the agent produced, and who approved it."*

| 아티팩트 | 생산 | 소비 |
|---|---|---|
| `intent.md` | Stage 1(Claude 초안 · PO 정정) **또는** Stage 6(에이전트가 "in the Stage 1: Plan format" 으로) | Stage 2(승인된 intent.md → spec) · Stage 3(*"The intent artifact (intent.md or spec.md) if one exists"*) |
| `spec.md` | Stage 2 | Stage 3(plan mode 입력) · Stage 5(PR 리뷰가 *"compliance against the spec (spec.md from the requirements play)"*) |
| `plan.md` | Stage 3 | Stage 5(PR 리뷰가 diff 를 plan.md 와 대조) |
| diff · tests · PR · review findings | Stage 3~5 | Stage 5~6 |
| incident record | Stage 6 | → 새 `intent.md` |

「artifact chain」이라는 낱말은 플레이북 전체에서 capture-intent 레슨에 1회뿐(L1 grep · 부모 확인). Introduction 은 "the committed artifact".

### 2.2 Stage 2 — spec.md 가 intent.md 를 소비하는 방식
- 입력: 승인된 intent.md + 조직 skills(brand · security · compliance · UX). *"The product owner reviews that spec, but doesn't write it."*
- 자동화 문면: *"make the acceptance of intent.md in the intent home the trigger, with a non-interactive job that fires on the merge, runs the pass with the organization's skills loaded, and commits spec.md as a pull request"* — 즉 intent 의 merge 가 spec 생성 job 의 트리거.
- 리뷰 물음: *"Does the spec solve the stated problem, and are the open questions from intent.md answered or carried forward?"* · *"Commit spec.md alongside intent.md. The file pair records what was asked for and what was decided."* · 승인은 PO, 고위험은 technical lead 자문. 프런트엔드는 intent.md → Claude Design(beta) 목업 → Claude Code.
- 메트릭: intent.md 커밋 → spec.md 커밋 시간(두 git 타임스탬프) / 첫 plan.md 커밋 이후 spec.md 커밋 수. **spec.md 에는 필드 템플릿이 없다** — 프롬프트 예시(*"Read the attached intent.md and produce a requirements and design spec … Document the spec fully as spec.md"*)만 있다.

### 2.3 Stage 3 — plan mode · 예시가 spec 을 건너뜀 · Legacy systems
- *"Prerequisites: The intent artifact (intent.md or spec.md) if one exists, and the CLAUDE.md file helps."* 엔지니어가 intent.md 와 spec.md 를 주고 계획을 요청 → *"Iterate until an engineer who has never seen the conversation could implement the change from the plan alone."* → plan.md 커밋 → PR 리뷰가 diff 를 plan.md 와 대조 → *"When implementation departs from the plan, update plan.md in the same commit."*
- 플레이북이 실은 유일한 plan.md 예시의 머리는 `# Plan: claims status self-service (from intent.md 2026-06-02)` — **spec.md 를 건너뛰고 intent.md 를 직접 인용**한다. 모순은 아니지만(전제조건이 「or」) 사슬은 문면상 3단, 예시는 2단이다.
- 「Legacy systems and the source of truth」절(capture-intent 레슨이 「Stage 3」이라고만 가리킨 곳 — plan-mode 레슨 끝): 구성 3 — ① *"The repo as the source of truth."* ② *"The legacy system is the truth. Jira, ServiceNow, or the requirements tool holds the authoritative record, and the Markdown artifacts are working copies. Claude reads the record at the start of the session and writes the outcome back through a Model Context Protocol (MCP) connector in the same session that produced the spec or the plan."* ③ *"Linkage as the minimum bar. All artifacts note the record ID, and all legacy records contain the commit SHA of the Markdown file."* — ③이 *"a good place to start when transitioning"*.

### 2.4 Stage 6 — 루프 폐쇄
- 트리거: *"a control-band breach, a ticket, a channel message, or a schedule invokes Claude without a person in the path."* · *"Prerequisites: intent.md, which gives the loop a structured output to restart."*
- `bands.yaml` 3단(1σ log · 2σ diagnose read-only · 3σ propose = PR 또는 사전 승인 runbook). *"The agent writes its diagnosis as intent.md in the Stage 1: Plan format, covering the anomaly and its evidence, a proposed outcome, the affected systems, and any open questions."* 사람은 triage(*"Fix now, schedule, or dismiss"*). Leading: *"Time from band breach to an intent.md in the triage queue"*.
- Claude Tag(Slack): *"A small, well-bounded fix arrives as a PR through the review gate, and anything larger is written up as intent.md for Stage 1: Plan, at which point the loop starts feeding itself."*

### 2.5 Skills 레슨 — 템플릿 skill 은 1회 언급
*"Skills are how an organization makes its institutional knowledge operational."* · `.claude/skills/<name>/SKILL.md` · *"A skill is a control, though an advisory one."* · *"a hook is the deterministic layer behind it"* · 정책 변경 시 policy owner 사인오프. **intent 템플릿을 skill 로 인코딩한다는 문장은 capture-intent 레슨 1회뿐이고 Skills 레슨은 다른 예(`secure-api-review`)만 든다.**

### 2.6 코스 vs 블로그 · 독자 · 리소스

### 4.1 필드 대조 요약

### 4.2 intent.md 에 없는 것(다른 기법엔 있음)
측정 가능 성공 기준(Spec Kit *"Success Criteria (mandatory)"* SC-001…) · 비목표(Shape Up *"No-gos"* · PRD *"Out of Scope"*) · appetite · 대안 검토(ADR *"Considered Options"* · RFC *"Rationale and alternatives"*) · drawbacks(RFC) · 수용 기준(Spec Kit Given/When/Then · Kiro EARS *"WHEN … THE SYSTEM SHALL"* · Gherkin) · 항목 ID/추적성(Spec Kit FR-XXX · ADR nnnn · StrictDoc UID · Doorstop) · Prior art(RFC). *"No formal language is required"* 원칙과 일관된 의도적 생략으로 읽힌다(추정).

### 4.3 신규성 판정
- **반증** — 「git 옆에 산다」: Doorstop README *"facilitates the storage of textual requirements alongside source code in version control"*(레포 생성 2013-04-01) · RFC PR · Spec Kit · OpenSpec · Gherkin 전부 같은 원칙. 「승인 = merge」도 Rust RFC 의 "RFC PR" 관행과 동일.
- **지지** — 「비엔지니어 원저자」: 비교 15개 중 어느 1차 문서도 이를 진입 조건으로 못 박지 않는다. 오히려 Böckeler(martinfowler.com, 2025-10-15, SDD 도구 3종 비평)가 이 공백을 지적했다: *"None of this is made explicit though, it's presented as a given that a developer would do all this analysis."* Thoughtworks Radar(2025-11, Spec-driven development = Assess): *"when they produce PRDs or user stories, it's sometimes unclear who their intended user is."* 정신적으로 가장 가까운 선언은 Sean Grove 「The New Code」: *"whoever writes the spec, be it a PM, a lawmaker, an engineer, a marketer, is now the programmer."*
- **부분** — 「템플릿을 skill 로」: 발상은 Spec Kit Bundles · BMAD 스킬 설치에도 있다. 고유한 건 Claude 의 1급 프리미티브라는 점뿐.
- **부재 확인(반증 아님)** — 「생존율 · spec 이후 변경 수」 같은 단계 경계 손실률 지표는 Spec Kit · Kiro · OpenSpec 문서 어디에도 없다.

### 4.4 Spec Kit · Kiro · OpenSpec 은 어느 층인가
- Kiro `requirements.md`(EARS · 요구 단위 추적성 · IDE 종속) → **spec.md 층**.
- Spec Kit `spec.md` — 정의는 *"Focus on the what and why, not the tech stack"* 로 intent 와 동형이나 템플릿이 FR-XXX · Success Criteria · Given/When/Then 을 첫 파일부터 요구 → **경계~spec 층**. 플레이북의 Stage 1 에 해당하는 산문 단계가 없다.
- OpenSpec `proposal.md`(동기) + `specs/`(SHALL + Scenario) — **파일 층에서 intent/spec 을 분리**하는 유일한 도구 → 플레이북 2단 구조에 가장 가깝다.

## 6. 구현 재료 (L4 · 공식 문서 + 실측)

### 6.1 템플릿 — 레슨 필드만
```markdown
# Intent: <변경의 이름 — 해법이 아니라 대상>
Author: <이름 (역할/팀)>. Status: draft.
## Problem
<오늘 무엇이 안 되는가 · 누가 겪는가>
## Proposed outcome
<끝났을 때 무엇이 달라지는가 — 발의자의 말로>
## Affected users and systems
## Constraints
<지켜야 하는 것 · 범위 밖>
## Open questions
<아직 답이 없는 것>
```
레슨에 없어 추가 여부를 판단해야 하는 것: `Date/Created` · Status enum(커뮤니티 `draft/accepted/superseded`) · 성공 지표 · 비목표 · 변형 템플릿(feature/defect/incident) · 「한 장 제한」 · 「미결이 남아 있으면 착수 금지」.

### 6.2 SKILL.md 초안(공식 frontmatter 필드만 — `name` + `description`)
```markdown
---
name: capture-intent
description: Brainstorms a problem with the originator and drafts it as intent.md — problem, proposed outcome, affected users and systems, constraints, open questions. Use when starting a change from an idea, a ticket, or an incident, before design work begins.
---
# Capture as intent.md
1. 발의자가 자기 말로 문제를 설명하게 한다(무엇을 못 하는가 · 누가 영향받는가 · 무엇이 나아지는가 · 범위 밖).
2. 구체화까지 브레인스토밍: scope, users, constraints, and what success looks like.
3. 위 템플릿으로 intent.md 를 쓴다. 4. 발의자가 정정한다. 5. intent 홈에 커밋하도록 안내한다.
(spec.md · plan.md 는 쓰지 않는다 — 다음 단계의 일)
```
「리드 사인오프」는 frontmatter 에 자리가 없다 → 이 skill 이 사는 레포의 CODEOWNERS 가 곧 사인오프.

### 6.3 거버넌스 배선(공식 docs.github.com · claude.com/docs)
`intent/` 폴더 → CODEOWNERS 에 `intent/** @product-owner` → branch protection / rulesets 「Require review from Code Owners」(제약: *"The people you choose as code owners must have write permissions for the repository."*) → merge = accept · close = reject. 에이전트가 초안 PR 을 열면 「Require two approving reviews」 또는 `agent-approval-check.yml`(`required_approvals: 2`)로 봇 PR 2차 승인.

### 6.4 메트릭 레시피(격리 레포 실측 · git 2.39.5)
1. 파일 최초 커밋 시각: `git log --diff-filter=A --format=%aI -- intent/<x>.md` → 1줄.
2. 첫 spec 커밋 이후 intent 변경 수: `git log --since="$(git log --diff-filter=A --format=%aI -- spec/<x>.md)" --format=%h -- intent/<x>.md | wc -l` — 경계 같은 초 커밋 **포함**(inclusive, 실측 3). 시계 대신 위상: `git rev-list <spec첫커밋>..HEAD -- intent/<x>.md | wc -l`.
3. survival rate = merged / (merged + closed) — `gh pr list --state merged --json number,files --jq '.[] | select(.files[].path | startswith("intent/"))'`(문법만 확인 · 라이브 미실행).
4. **간극**: leading 의 「첫 대화 시각」은 git 에 없다 — 레슨 문면은 단일 세션(브레인스토밍 직후 커밋)을 암묵 전제(추정). 대안: 머리글 `Created:` · 커밋 트레일러 · 대화 export 조인(미검증).

관찰(부모 판단):
- 플레이의 「핸드오프 제거」 효과는 이미 구조적으로 얻고 있다(1인 소유자). 남는 것은 (a) 「왜」가 축자 지시·브리프에 흩어져 착지 시 아카이브로 내려가는 것 (b) 아이디어의 accept/reject 이력이 계량되지 않는 것.
- `REQUIREMENTS.md` 는 플레이북 어휘로는 spec/requirements 층(Stage 2)이다 — 항목마다 「요구 → 수용 기준 → 장치」이고 소유자 결정이 §5 에 붙는다. intent 층은 없다.
- `FINDINGS.md` 의 「승격 조건」은 플레이북의 closed intent 에 가장 가까운 것이고, reject 된 의도가 어떤 조건에서 되살아나는지를 적는다는 점에서 플레이북(reject 뒤 처리 미정의)보다 한 걸음 앞서 있다.
- 2026-06-03 글(JIT planning)과 08-21 플레이북 사이에서 이 레포는 이미 「작업 문서 §1 축자 + 브리프」라는 중간 지점에 있다 — intent.md 를 들이느냐는 사용자 판단 자리(§8.3).

## 8. 종합 판정

### 8.1 새로운 것
1. 비엔지니어 원저자를 **진입 조건**으로 명시 — 선행 SDD 도구들이 비워 둔 자리(Böckeler · Thoughtworks 가 지적한 공백).
2. 산문 intent 와 형식 spec 을 **파일 층으로 분리**(OpenSpec 만 유사).
3. 단계 경계의 **손실률 지표**(survival rate · 첫 spec.md 이후 intent 변경 수) — 선례 문서에 없음.
4. Stage 6 이 **같은 형식**으로 되돌려 써 루프를 닫는다(*"in the Stage 1: Plan format"*).

### 8.2 약한 것 · 말하지 않는 것
1. intent → spec 파생을 검증하는 장치가 없다 — git 은 순서만 기록한다(menuagentic). 플레이북 자신도 plan.md 동기화엔 hook 을 권하면서 intent/spec 방향엔 없다.
2. 첫 아티팩트에 준비도 바닥이 없다(Pathmode) — 그리고 결정론 검사는 만들기 어렵다(Pathmode 의 1차 실패).
3. 스키마 · ID · 상태 전이 · 폐기 후 처리 · 여러 intent 의 충돌/우선순위 · 변경 관리 · 비엔지니어 PO 의 merge UX · intent home 접근 제어가 정의되지 않았다(L1 grep 0건).
4. 「커넥터가 대신 커밋」은 공식 문서에서 **부분 지원** — 내장 GitHub 통합은 읽기 전용, 쓰기는 GitHub MCP 커넥터 또는 Claude Tag/Claude Code 의 GitHub App.
5. leading 지표의 「첫 대화 시각」은 git 에 없다.
6. 유일한 plan.md 예시가 spec.md 를 건너뛴다 · 코스/블로그 문면 불일치 1건(person ↔ agent).
7. 도입 보고가 아직 0건 — 발행 18일째의 문서다.

### 8.3 열린 물음(사용자 판단 자리 · 이 보고서는 답하지 않는다)
- 이 레포에 intent 층(한 장 「왜」)을 둘 것인가, 둔다면 `docs/work/` 앞인가 `REQUIREMENTS.md` 위인가.
- 두면 승인 = merge 로 계량할 것인가(현재는 대화 결정 `D<n>`).
- 「첫 대화 시각」을 어디에 남길 것인가(머리글 · 커밋 트레일러 · 없음).
