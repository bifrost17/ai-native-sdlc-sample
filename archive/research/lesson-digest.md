# 부모 메모 — 레슨 정독(부모 직접 · WebFetch 원문) + 레포 대응 초안

## 1. 레슨 정독 — Capture as intent.md (Lesson 2 of 14 · 24 min · Stage 1 Plan)

출처: https://academy.claude.com/courses/ai-native-sdlc-playbook/capture-intent (부모 WebFetch 2026-09-08). 앞 레슨 Introduction, 뒤 레슨 Requirements and design.

### 1.1 정의 문장(축자)
- "The `intent.md`, which kicks off the software development process, can enter through different routes. A person has an idea, a ticket is filed, or an incident is surfaced via an alert (see Stage 6: Maintain)."
- "The proto-spec generated by Claude is human readable, version controlled, and immediately consumable by the next stage. The proto-spec is saved as an `intent.md`."
- "Regardless of whether the intent originates from an event trigger or a person, the same steps apply: the product owner reviews and corrects the agent-written `intent.md` before it is committed."
- What changes(AI-native 열): "The originator brainstorms with Claude and writes the result down as `intent.md`, a proto-spec in the originator's own terms. The artifact contains what is wanted, why, and under which constraints. Repeat processes are encoded via skills."
- What changes(Traditional 열): "An idea passes through backlog entries, user stories, story points, and refinement meetings before anyone can act on it. Ownership transfers at each handoff, so what reaches engineering is several steps removed from what the originator meant."

### 1.2 절 구조(플레이 공통 골격으로 보임 — L1 이 다른 레슨과 대조)
What changes(표) → Getting started(Prerequisites · Infrastructure) → How to execute it(5단계) → What it looks like(예시 파일) → Governance considerations → How to measure it(leading/lagging)

### 1.3 역할 어휘
originator(아이디어 원저자 · 비엔지니어 가능) · product owner(리뷰·정정·accept/reject) · technical team member / platform or engineering team(intent home 설치 · 쓰기 권한 · 템플릿 skill 설정) · lead(템플릿 사인오프) · Claude(analyst 역할 — "Claude asks the questions an analyst would ask: scope, users, constraints, and what success looks like.")

### 1.4 인프라 3 + 홈 선택 규칙
- "Claude access for people who are not engineers (claude.ai or Cowork); an agreed `intent.md` template; a shared, version-controlled home for intent that the product owner watches."
- 홈: "For a single product the simplest home is an `intent/` folder in the product repo. This setup keeps the artifact chain next to the code derived from it. A dedicated intent repo is only worth the overhead when intent spans many repositories, and in a monorepo it is a directory."
- Jira 관계: "The Legacy systems section in Stage 3: Build covers how this home relates to a Jira or requirements tool that already holds the record."
- 비Git 기여자: "a connector to the version-control system (e.g., GitHub) lets Claude commit Markdown files on their behalf from claude.ai or Cowork."

### 1.5 실행 5단계
1 originator 가 자기 말로 문제 서술("what they cannot do today, who is affected by the idea, what better looks like, or what is out of scope. No formal language is required.") → 2 구체화까지 브레인스토밍 → 3 "Ask Claude to write the result as `intent.md` using the organization's template, which can be encoded as a skill set up by a technical team member and signed off by a lead. This can cover the problem, proposed outcome, affected users and systems, constraints, and open questions." → 4 originator 정정 → 5 "Commit `intent.md` to the shared home. Author and timestamp join the record, and the product owner picks the idea up from there."

### 1.6 예시 파일(축자)
```markdown
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.
## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.
## Proposed outcome
Customers see claim status, next step and expected date in the portal.
## Affected users and systems
Claims handlers, portal team, claims-core API.
## Constraints
No new PII in the portal session. Existing authentication only.
## Open questions
Do third-party loss adjusters need access too?
```
필드 7: 제목(`# Intent:`) · Author(이름+소속) · Status(draft) · Problem · Proposed outcome · Affected users and systems · Constraints · Open questions. 본문 6줄 남짓 — 「proto-spec」의 크기 감각.

### 1.7 거버넌스 · 메트릭(축자)
- "The evidence is the committed `intent.md`, which lists the author, the timestamp, and the full revision history. It's logged in the Git history of the intent home. The product owner approves, and the accept or reject decision that sends the intent into Stage 2: Design is recorded as the merge or the closing review."
- Leading: "Time from first conversation to a committed `intent.md`, read from Git history on the intent home, which records author and timestamp. The expectation is for this to fall from a multi-week elicitation and refinement cycle to hours."
- Lagging: "The survival rate, or the share of `intent.md` files that the product owner accepts into Stage 2: Design rather than closes. The accept or reject decision is recorded as the merge of the artifact or the closed review. Additionally, count the changes to `intent.md` made after the first `spec.md` commit for the same change."

### 1.8 부모 판독(해석 — 라벨 「부모 판독」)
- P1 리뷰 지점이 둘이다: 「커밋 전 PO 가 정정」 + 「accept/reject = merge 또는 closing review」 → 브랜치/PR 흐름(초안 커밋 → PO 리뷰 → merge=accept · close=reject)으로 읽는 것이 자연스럽다. 문면은 두 지점을 구분해 정의하지 않는다.
- P2 `Status: draft` 가 있으나 상태 전이(draft→accepted/closed?)는 정의되지 않았다 — merge/close 가 곧 상태다.
- P3 lagging 두 번째 지표(첫 spec.md 커밋 이후 intent 변경 횟수)는 「의도 불안정성」 계기 — 브레인스토밍 부족 또는 설계 단계에서 발견된 구멍을 잰다.
- P4 leading 지표의 「첫 대화 시각」은 git 에 없다 — 문면은 "read from Git history" 라 하지만 git 은 커밋 시각만 안다(L4 가 간극 확인).
- P5 Prerequisites: None — 다른 플레이와 독립 도입 가능. 유일한 인프라 결정은 「홈을 어디에 둘 것인가」.
- P6 파일명·ID·중복 처리·폐기 뒤 처리·Jira 이중 기록은 이 레슨에 없다(Legacy systems 절로 위임 — L1 확인).

## 6. 이 레포(openwebagent)와의 대응 — 초안(부모 · 정책 문서 기준 · 코드 미확인)

| 역할 분리 | originator ≠ PO ≠ 기술 팀원 ≠ lead | 전부 사용자 1인(소유자) + 부모 세션 | 해당없음에 가까움 — 핸드오프 제거 효과는 이미 0 에 수렴 |

관찰(부모 판단 · 추가 제안 아님):
- 이 레포에서 플레이의 「핸드오프 제거」 효과는 이미 구조적으로 얻고 있다(1인 소유자). 남는 것은 (a) 「왜」가 축자 지시·브리프에 흩어져 착지 시 아카이브로 내려가는 점 (b) 아이디어의 accept/reject 이력이 계량되지 않는 점.
- REQUIREMENTS.md 는 플레이북 어휘로는 spec/requirements 층(Stage 2)이지 intent 층이 아니다 — 항목마다 「요구 → 수용 기준 → 장치」이고 소유자 결정이 §5 에 붙는다.
- FINDINGS.md 의 「승격 조건」은 플레이북의 「closed intent」에 가장 가까운 것 — reject 된 의도가 어떤 조건에서 되살아나는지를 적는다는 점에서 플레이북보다 한 걸음 더 나가 있다.

## 2. 플레이북 안의 위치 — 부모가 공식 원문(L1 raw/extracted, curl 2026-09-08 04:43Z)으로 확정한 것

- 사슬(Introduction 축자): "A stage ends by committing an artifact with the commit initiating the next stage. An accepted intent.md triggers the requirements and design pass, an approved spec.md triggers plan mode, a merged PR triggers the pipeline, and a breached control band in production writes the next intent.md, and so the loop continues."
- 아티팩트 목록(Introduction): "Each stage ends by writing one to version control (including intent.md, spec.md, plan.md, the diff and its tests, the PR with its review findings, and the incident record), and the next stage begins by reading it. For the early stages, .md files are the predominant artifact because a product owner and an agent can both read and act on the same file."
- 「The shifts」 표 Plan 행: "Claude synthesizes pain points straight from the sources and captures them within intent.md, which is human readable and machine actionable" · Maintain 행: "Any breached control band is diagnosed and written back into the loop as a new intent.md".
- 「artifact chain」 축자는 플레이북 전체에서 capture-intent 레슨 1회뿐(L1 grep · 부모 확인). Introduction 은 "the committed artifact".
- 플레이 공통 골격(Introduction): What changes · Getting started · Concrete steps · Governance considerations · How you measure — 「Prerequisites」로 의존 그래프.
- Stage 2(Requirements and design, 34 min): 입력 = 승인된 intent.md + 조직 skills(brand, security, compliance, UX). "The product owner reviews that spec, but doesn't write it." 자동화 문면: "make the acceptance of intent.md in the intent home the trigger, with a non-interactive job that fires on the merge, runs the pass with the organization's skills loaded, and commits spec.md as a pull request". 리뷰 물음: "Does the spec solve the stated problem, and are the open questions from intent.md answered or carried forward?" "Commit spec.md alongside intent.md. - Stage 3 plan-mode(45 min): "Prerequisites: The intent artifact (intent.md or spec.md) if one exists, and the CLAUDE.md file helps." 엔지니어가 intent.md 와 spec.md 를 주고 계획 요청 → plan.md 커밋 → PR 리뷰가 diff 를 plan.md 와 대조. 예시 plan.md 머리: "# Plan: claims status self-service (from intent.md 2026-06-02)" — spec.md 를 건너뛰고 intent.md 를 직접 인용(L1 발견 · 부모 확인). 「Legacy systems and the source of truth」절이 여기 있다(capture-intent 레슨은 "Stage 3: Build" 라고만 가리킨다): 구성 3 — ① "The repo as the source of truth." ② "The legacy system is the truth. Jira, ServiceNow, or the requirements tool holds the authoritative record, and the Markdown artifacts are working copies. Claude reads the record at the start of the session and writes the outcome back through a Model Context Protocol (MCP) connector in the same session that produced the spec or the plan." ③ "Linkage as the minimum bar. All artifacts note the record ID, and all legacy records contain the commit SHA of the Markdown file." — "a good place to start when transitioning".
- Stage 6(Closing the loop on metrics, 136 min): 트리거 = "a control-band breach, a ticket, a channel message, or a schedule"; "Prerequisites: intent.md, which gives the loop a structured output to restart." bands.yaml 1σ log / 2σ diagnose(read-only) / 3σ propose(PR 또는 사전 승인 runbook). "The agent writes its diagnosis as intent.md in the Stage 1: Plan format, covering the anomaly and its evidence, a proposed outcome, the affected systems, and any open questions." 사람은 triage("Fix now, schedule, or dismiss"). - 필드 대조(intent.md 7필드 ↔ 15개 기법): 「Problem」은 Shape Up 피치의 "Ingredient 1. Problem" 과 낱말 일치(단 Shape Up 은 "Solution"·"Appetite"·"Rabbit Holes"·"No-gos" 를 요구 — intent.md 는 해법을 빼고 outcome 만) · 「Open questions」는 Rust RFC "Unresolved questions" · Atlassian PRD "Assumptions and Open Questions" 계열 · 「Status」는 Spec Kit "Status: Draft" · MADR `status: proposed|rejected|accepted|deprecated|superseded` · 「Author」 단일 필드는 MADR 의 decision-makers/consulted/informed(RACI) 보다 얇다.
