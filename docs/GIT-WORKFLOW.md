# GitHub Flow 브랜치 정책

이 템플릿은 GitHub Flow를 기본 브랜치 전략으로 사용한다. 제품의 통합 기준은 `main`이다.
`main`은 프로젝트가 정한 기존 동작과 검증 기준을 만족하도록 유지한다. 큰 개발건도 장기
`develop`이나 기능 통합 브랜치에 전부 모으는 대신 검토 가능한 변경부터 이어서 통합한다.

## 시작과 계획

제품 저장소를 처음 만들 때 사용 템플릿의 판을 기록한다. 이후 작업 브랜치는 고정 템플릿 판이
아닌 최신 제품 `main`에서 만든다. 브랜치 이름은 짧게 목적을 드러내며 Codex 작업은 기본적으로
`codex/<작업명>`을 쓴다. 긴급 수정도 같은 흐름에서 필요한 검증을 거쳐 통합한다.

범위나 실현 가능성이 불명확하면 필요한 조사를 먼저 하고, 사람과 이번 결과와 완료 기준을 정한다.
큰 요구는 `plan.md`의 작업 순서에 선행 관계, 함께 검토할 PR 범위와 통합 순서, 각 통합에서 확인할
동작을 적는다. [PR 크기 가이드](PR-SIZE.md)에 따라 하나의 계획을 여러 PR로 실행할 수 있다.
작업·세션·서브에이전트마다 PR 하나를 만들 필요는 없다.

intent, spec, plan은 단계별로 커밋하고 다음 단계에서 사용할 판을 담당 사람이 수락한다.
대상 문서·커밋 SHA, 결정자, 결정과 이유를 같은 Draft PR이나 보존하는 대화·결정 기록에 남긴다.
문서마다 별도 PR을 만들 필요는 없다. 공유 계획을 먼저 문서 PR로 통합하는 방법도 가능하다.
단계 수락은 다음 작업의 근거를 정하는 결정이며, 최종 구현 PR의 통합 승인과 구분한다.
`Status: draft.`는 유지하고, 중요한 내용이 달라졌을 때 영향받는 결정만 다시 확인한다.

## 작업과 PR

독립 작업을 동시에 진행할 이점이 있으면 별도 세션마다 브랜치와 worktree를 둔다.
같은 파일을 바꾸는 작업은 순차 진행하고, 파일이 달라도 공유 계약이나 실행 순서에 의존하면
독립적이라고 보지 않는다. 조사·검증 등 한정된 도움은 세션 안의 서브에이전트에 맡길 수 있다.
사람이 검토할 수 있는 범위 안에서 병렬화한다. 특정 스킬·서브에이전트 도구는 필수가 아니다.

일찍 피드백이 필요하면 Draft PR을 연다. PR 설명에는 계획의 해당 범위, 의존하는 PR,
변경과 검증 근거·미확인 사항을 적는다. 일부 작업의 PR이 머지돼도 전체 요구를 완료로 표시하지 않는다.
같은 목적의 리뷰 수정은 같은 브랜치와 PR에 이어간다.

의존하는 작업은 선행 PR을 표시한다. 기본은 선행 변경을 `main`에 머지한 뒤 그 판에서 진행한다.
기다리는 비용이 크면 선행 작업 브랜치에서 갈라 미리 개발·검토할 수 있다. 이때 PR의 기준 브랜치와
의존성을 명시하고, 선행 PR 머지 후 대상과 남은 diff를 최신 `main`에 맞춰 다시 확인한다.
의존 브랜치를 장기 통합 브랜치로 유지하지 않는다.

## 검토와 통합

담당 에이전트는 `REVIEW.md`에 따라 동작·정책·범위를 검토하고 발견을 수정·재검증한다.
지정된 사람은 의도·위험·검증 근거를 보고 통합을 수락한다. AI 리뷰나 검사 통과만으로 승인하지 않는다.
PR이 만들어졌다는 사실도 승인이 아니다. 기록을 남기는 위치와 책임자는 `PROJECT-POLICY.md`에 적는다.

머지 전에는 최신 `main`과 합쳐진 결과에서 관련 검사와 인접 동작을 확인한다. `main`이나 변경이
그 뒤 달라져 검증 결과에 영향을 줄 수 있으면 해당 검증을 갱신한다. 충돌 해결이 끝났다는 사실만으로
통합 동작이 검증됐다고 보지 않는다. 필요한 검사가 아직 없거나 실행되지 않았으면 사람에게 그 범위를 남긴다.

기본 머지 방식은 merge commit이다. 승인된 문서의 Upstream SHA를 이력에 보존하기 쉽기 때문이다.
프로젝트가 squash/rebase를 선택하면 승인 원본을 조회 가능하게 보존하거나, PR·결정 기록에
원본과 통합 후 커밋의 대응 및 문서 내용이 같은지 확인한 근거를 남긴다. 내용이 바뀌었다면 승인을
자동 승계하지 않는다. 공유된 브랜치의 이력 재작성은 협의하고, `main`을 force push하지 않는다.

머지 후 통합 결과를 확인하고 완료된 작업 브랜치와 worktree를 정리한다. PR·커밋·결정 기록은 남긴다.
문제가 발견되면 영향과 의존성을 보고 수정 PR 또는 revert PR로 대응하며, 데이터·외부 효과는 별도로
복구한다. 머지는 배포나 기능 공개와 같지 않다. 배포·노출·되돌리기는 프로젝트의 실제 운영 방식에
따르며 필요한 경우에만 호환 단계나 기능 노출 제어를 사용한다.

[플레이북의 계획 분할과 병렬 실행](https://academy.claude.com/courses/ai-native-sdlc-playbook/parallel-sessions-and-subagents).
구체적인 PR 단위·merge commit·단계 수락 기록 방식은 이 템플릿이 선택한 팀 정책이다.
