# 제품 변경의 절차

한 변경은 `intent/<NNNN>-<slug>/`에서 의도, 요구·설계, 구현 계획을 이어 간다. 문서는 각 단계의
책임자가 읽고 결정할 수 있도록 작성한다. 문서 형식과 승인 상태를 판정하는 자동 검사는 이 템플릿에
포함하지 않는다. 실제 코드와 동작의 검증 방법은 프로젝트가 정한다.

## 역할과 승인

의도를 제시한 사람은 문제와 기대 결과를 확인한다. 제품 책임자는 의도와 요구·설계를 검토한다.
엔지니어는 계획을 검토하고 구현·검증을 수행한다. 정책 충돌과 운영 결정은 해당 책임자가 판단한다.
역할을 맡은 사람과 통합 대상 브랜치는 [PROJECT-POLICY.md](../PROJECT-POLICY.md)에 적는다.

문서는 단계별 변경으로 커밋하고 PR에서 검토한다. 정해진 통합 브랜치로의 머지는 승인,
머지하지 않고 닫는 검토는 거절의 기록이다. 파일의 `Status: draft.`는 그대로 둔다.
초안에서 다음 단계를 시작하라는 명시적 지시가 있으면 지시자·범위·이유를 문서와 PR에 남긴다.
상위 저장소의 기본 브랜치 이름이나 파일의 상태 문자열만 보고 승인됐다고 추정하지 않는다.

## 단계별 인계

| 단계 | 입력과 할 일 | 산출·검토 |
|---|---|---|
| 의도 | 제안자와 문제, 사용자, 범위, 제약, 성공의 의미를 확인한다. 관측과 추정을 구분한다. | [intent 양식](../templates/intent.md). 제안자가 사실을 확인하고 제품 책임자가 검토한다. |
| 요구·설계 | 승인된 의도에서 관측 가능한 요구와 설계를 만든다. 적용할 정책을 읽고 제약과 미결 질문을 이어받는다. | [spec 양식](../templates/spec.md). 우려와 결정자를 드러내어 제품 책임자에게 넘긴다. |
| 구현 계획 | 승인된 요구·설계에서 변경 파일, 작업 순서, 위험, 검증 근거를 정한다. | [plan 양식](../templates/plan.md). 엔지니어가 읽고 실행할 수 있는지 확인한다. |
| 구현·검증 | 계획에 따라 구현한다. 결함은 먼저 재현하고, 해당 동작과 인접 동작을 검증한다. 계획 변경은 이유와 함께 반영한다. | 코드 변경과 실행 근거. [리뷰 지침](../REVIEW.md)에 따라 검토한다. |
| 통합·운영 | 검토 결과를 처리하고 정해진 권한과 절차로 통합·배포한다. 운영 중 발견한 문제는 근거와 함께 다시 의도로 넘긴다. | 사람의 결정, 실행 결과, 미결 사항과 인계 대상. |

각 인계에서 확인할 내용은 “무엇이 달라졌는가, 어떤 근거가 있는가, 무엇이 미결이며 누가 결정하는가”다.
정책이 충돌하면 양쪽 출처와 내용을 기록하고 임의로 한쪽을 승인하지 않는다. 적용할 자료를 확인할 수
없다면 확인하지 못한 범위와 이유를 적는다. 팀이 보유한 스킬과 도구는 필요한 작업에 선택해서 활용할 수 있다.

## 검증 근거

검증은 실제 프로젝트에서 정한 명령과 관측 방법으로 한다. 실행한 명령·대상 판·결과·관측한 동작을
기록하고, 실행하지 못한 항목은 이유와 함께 분리한다. 테스트 실패를 숨기려고 기준을 완화하지 않는다.
독립 검토를 맡겼다면 검토 범위와 결과도 남긴다. 사람이 문서를 승인한 사실은 제품 동작을 검증한
사실을 대신하지 않으며, 검사 통과도 사람의 승인을 대신하지 않는다.

필요한 도구·자동화·CI·배포 환경이 없으면 필요한 자리와 담당자를 프로젝트 정책에 기록한다.
실행되지 않은 단계는 완료됐다고 보고하지 않는다.

## 전체 절차 실험에서 볼 것

사람이 실행 기록과 산출물을 함께 보고, 팀이 제공한 스킬의 기능이 해당 단계에 맞게 쓰였는지 확인한다.
예를 들어 의도 구체화, 설계의 정책 적용, 구현 계획의 위험·검증 정리가 각 단계에 맞는 역할이다.
이름을 나열한 것만으로 적용됐다고 보지 않는다. 본문을 실제로 읽거나 호출한 기록과 그 내용이
산출물의 판단에 반영된 근거를 연결한다. 불필요한 기능을 생략한 이유와 제공되지 않은 기능의 부재도
구분해 남긴다. 제공되지 않은 스킬을 사용했다고 꾸미지 않는다. 이 관측은 사람의 검토이며,
특정 스킬 이름의 사용이나 자동 판정기를 요구하지 않는다.

프로세스 실험에서 사람이 맡는 제안자·제품 책임자·엔지니어 역할을 대행할 수 있다. 이 역할과 개발
에이전트를 구분하고, 같은 작업 맥락을 이어 가며 질문·답변·검토·수정·수락·인계를 여러 차례 주고받는다.
한 번의 지시와 완성본만으로 상호작용 절차가 검증됐다고 보지 않는다. 각 대화와 결정 이유를 기록하고,
역할 대행자의 수락은 실험 안의 결정임을 밝힌다. 이를 실제 조직이나 사람의 승인으로 주장하지 않는다.
