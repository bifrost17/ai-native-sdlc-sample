# 정책 오너에게 묻는다 — 레인 8개의 질문 종합 (2026-09-10)

각 레인의 `docs/research/<skill>/README.md` 「정책 오너에게 묻는다」 절을 그대로 모았다. 답은 `policies/*.md` 개정 PR(오너 서명 = 머지) 또는 이 파일의 「답」 열에 적는다. 출처 절이 정본이다.
합계 51건.

## S8 · plugin (6) — `docs/research/plugin/README.md`

1. **라이선스** — 이 레포에 LICENSE 가 없다(GitHub API `license: null`). plugin.json 의 `license` 를 비워 두었다. 어떤 라이선스로 배포하나.
2. **플러그인 범위** — 레포 전체가 캐시에 복사된다. 그대로 두나, 아니면 플러그인을 `plugin/` 하위로 옮기고 `source: "./plugin"` 로 바꾸나(그러면 모든 세션의 `skills/`·`commands/` 경로가 바뀐다).
3. **명령 이름 공간** — 플러그인의 spec 명령은 `/intent-sdlc-skills:spec` 이 된다. 템플릿 `.claude/commands/spec.md`(`/spec`)를 남기고 플러그인은 스킬만 실을지, 명령도 실을지.
4. **관리 설정 배포** — `strictKnownMarketplaces: [{source: github, repo: bifrost17/intent-sdlc-skills}]` + `disableSideloadFlags: true` 를 누가 어떤 경로(MDM·관리 콘솔)로 배포하나. 브리프 근거 절이지만 이 세션은 검증 못 했다.
5. **판 범프 규칙** — `version: 0.1.0` 이 갱신 캐시 키다. 정책 변경 → 스킬 변경 → 오너 서명 때 누가 version 을 올리나(안 올리면 팀에 갱신이 안 간다).
6. **등록 ref** — 마켓플레이스 등록을 기본 브랜치로 할지 태그(`@v0.1.0`)로 고정할지.

## S1 · intent-template (5) — `docs/research/intent-template/README.md`

이 레인은 정책 파일이 없고(`{POLICY} = 없음`) intent 템플릿은 **리드 서명 사항**이다(L2 202 "encoded as a skill … signed off by a lead", ADOPTING "a technical team member writes it, a lead signs off"). 아래는 결정하지 않고 남긴다.

1. **묻는 넷 ↔ 쓰는 다섯의 어긋남을 맞출 것인가?** 기준선 "What to ask" 를 `Problem`(관측된 사실)·`Open questions` 를 포함한 다섯으로 고칠지, 지금처럼 본문이 받치게 둘지. **템플릿 변경이라 오너 서명이 필요하다 — 이 레인은 손대지 않았다.**
2. **동시 체인의 번호 배정**을 사람의 조정에 계속 맡길 것인가, `intent/` 에 번호 예약 규약을 둘 것인가?
3. **`to-questionnaire` 산출물의 자리.** `intent/<NNNN>-<slug>/` 안에 둘 것인가, PR 에 첨부할 것인가, 아니면 지금처럼 세션 작업 디렉터리에 둘 것인가? 지금 답은 「원문을 고치지 않으므로 현재 디렉터리」다.
4. **`grilling` 을 모델이 스스로 부르게 둘 것인가?** 지금은 그렇다. 「사람이 요청할 때만」으로 좁히려면 `disable-model-invocation: true` 를 더해야 하는데, 그것은 원문 수정이라 PROVENANCE 에 기록될 변경이 된다.
5. **spec-kit `assess.define` 의 두 항목**(`## Cost of Inaction`, `## Non-Goals`)을 다섯 절에 들일 것인가? 기각한 후보 중 유일하게 다섯 절과 같은 층에서 값을 더하는 항목이었다. **템플릿 변경이라 역시 오너 서명 사항.**

## S5 · secure-api-review (6) — `docs/research/secure-api-review/README.md`

1. **S5·S6·S7 뒤에 결정적 통제를 둘 것인가?** 스킬만으로는 「위반이 드물어질」 뿐이다(L6 503-504). 훅으로 막을지, PR 리뷰 패스로 다시 볼지, 아니면 권고로 둘지는 정책의 결정이다. 이 레인은 훅을 만들지 않았다.
2. **S6 의 「같은 지연」을 어디까지 요구하는가?** 「같은 코드 경로를 타라」(설계 가능·검토 가능)까지인가, 상수 시간 보장(측정과 시험이 필요)까지인가. 스킬은 앞쪽으로 적었다 — `skills/claims-api-security/SKILL.md` S6.
3. **채택분 `secrets-scan` 의 play 89–92행** 「Is it active? … Check if the key format is currently valid for the service」는 발견한 자격증명을 실제 서비스에 대 보라는 뜻으로 읽힌다. spec 을 쓰는 세션이 할 일이 아니라고 보지만, 원문을 고치지 않는 원칙 때문에 그대로 두었다. 잘라낼지, 조직 주석을 덧댈지 결정이 필요하다.
4. **OWASP 원문을 정책의 근거로 달 것인가?** OWASP API Security Top 10 2023 과 CheatSheetSeries 는 CC-BY-SA-4.0 이다. 문장을 옮기면 같은 라이선스와 저작자 표시가 정책·스킬에 따라붙는다. 지금은 착상만 가져오고 옮기지 않았다.
5. **S7 의 세션 키 이름 세 개**(customer · adjuster · agent)가 실제로 무엇인지 이 레포에는 없다. 스킬은 「자기 역할의 키만 읽는다」는 규칙만 적는다. 키 이름을 정책에 박을지, 세션 계약 문서로 뺄지.
6. **S5 의 50 rps 는 서비스 전체 합인가, 경로별인가?** 스킬은 「모든 경로가 나눠 쓰는 예산」으로 읽고 적었다. 다르면 고쳐야 한다.

## S7 · pr-loop (6) — `docs/research/pr-loop/README.md`

1. **이 루프에 정책 파일이 필요한가.** 지금은 `policies/*.md` 가 없어 `coverage.md` 의 행이 레슨
   문장이다. MAX_ROUNDS·resolve 주체·필수 체크 범위를 조직 정책으로 세우면 `policies/pr-review.md`
   가 생기고 스킬은 그것을 옮기게 된다. 세울 것인가, `SKILL.md` 의 「Team settings」 블록으로 둘 것인가.
2. **`RESOLVE_THREADS` 기본값.** 지금 기본은 `yes` — 고친 뒤 스킬이 스레드를 닫는다. 리뷰어가
   직접 닫아야 한다는 조직도 있다(후보 중 gabrielshanahan 은 명시적으로 금지). 어느 쪽인가.
3. **`claude-code-action` 과의 역할 분담.** 둘 다 켜면 같은 지적을 두 번 고칠 수 있다.
   리뷰어의 `@claude` 멘션은 action 에, PR 전체 훑기는 이 명령에 — 이 나눔이 맞는가.
4. **필수 체크만인가 전부인가.** `REQUIRED_ONLY` 기본은 `no`(전부 그린). advisory 봇 체크가 많은
   레포에서는 `yes`(branch protection 필수 체크만)가 맞을 수 있다.
5. **`LOCAL_CHECK` 에 무엇을 넣나.** 조직의 실제 사전 검사 명령(`make check` 등). 지금은 비어 있다.
6. **임시 레포를 남길 것인가.** `bifrost17/s7-pr-loop-test` — 시험 원문의 링크 대상.

## S4 · ux (10) — `docs/research/ux/README.md`

1. **다섯 어휘로 표현 못 하는 상태**를 어떻게 적는가. 시험 중 실제로 걸렸다 — 「청구 철회」의 결과를
   `종결`에 흡수시킬지, 여섯 번째 어휘를 만들지(U2·B4 는 다섯으로 못박는다). raw/23 의 답은 임의로
   `종결`을 골랐다.
2. **접근성의 정본 기준**: WCAG 2.2 인가 **KWCAG 2.2**(KS X OT0003:2022)인가. 후자라면 채택분과 조항
   번호가 다르고, 그것을 덮는 스킬은 라이선스가 없어 채택하지 못했다.
3. **스킬 뒤의 결정적 통제**를 둘 것인가(훅·리뷰 게이트). 스킬은 권고적 통제다.
4. **접근성 도구**(axe · Lighthouse · Playwright · Chrome DevTools MCP)를 도입할 것인가. 채택분 본문이
   그것을 전제로 쓰였고, 없으면 수동 검사로 물러선다.
5. **채택분 원문의 깨진 상대 경로를 고쳐도 되는가.** `ux-copy` 9행의 `../../CONNECTORS.md` 와
   `accessibility` 462행의 `../web-quality-audit/SKILL.md` 가 이 레포에서는 가리키는 곳이 없다.
   원문 유지 원칙과 부딪히는 자리다(지금은 고치지 않고 사본·기록으로 처리했다).
6. **일반 마이크로카피 스킬을 하나로 정리할 것인가.** 채택한 `ux-copy`(Apache-2.0, 공식) 말고
   `content-designer/ux-writing-skill`(MIT, 별 164)도 U1 을 같은 구조로 덮는다. 둘 다 두면 같은 자리에서
   경쟁한다 — 지금은 후자를 보류로 두었다.
7. **되돌리는 경로가 업무상 없을 때** U4 를 어떻게 만족시키는가. 재신청 절차·상담사 조작·고객센터 경로
   가운데 무엇을 「되돌리는 경로」로 인정하는지 정해 주어야 spec 이 닫힌다(raw/23 이 이 질문에서 멈췄다).
8. **U3 수치의 정본.** 「예상 시간·확인 시점」에 쓸 값(심사 소요, 조회 지연 SLA)을 어디서 가져오는가.
   근거가 없으면 스킬은 수치를 지어내지 말라고 하므로, 값이 없으면 문구를 못 쓴다.
9. **U6 의 「모든 아이콘·이미지에 대체 텍스트」에 장식용 예외를 둘 것인가.** WCAG 의 표준 답은 빈 alt 이지만
   정책 문면에는 예외가 없다. 지금 스킬은 예외를 적용하지 않고 이 질문을 남긴다.
10. **B7(이모지·느낌표 미사용)의 사정거리**가 고객 문구만인가, 스킬 문서까지인가. 채택분 `accessibility`
    본문은 `❌`/`✅` 기호를 쓴다(고객 문구가 아니라 예시 표시다). 지금은 고객 문구 조항으로 읽었다.

## S6 · spec-command (4) — `docs/research/spec-command/README.md`

1. **정책 4종이 모두 `Status: draft v0 — 오너 서명 대기`다.** 서명 전 조항(B1·C4·U2·S5 …)을 spec 이
   확정 제약으로 인용해도 되는가, 아니면 spec 의 우려 표에 「미서명」으로 함께 적어야 하는가.
   이 레인은 정하지 않고 조항 ID 를 그대로 인용하게 두었다.
2. **적용한 정책의 판을 무엇으로 적을 것인가.** `name@sha`(기준선, git 커밋)인가
   `name@last-reviewed`(정책 파일 머리의 검토일, 비엔지니어 오너에게 더 현실적)인가. 둘 다 L3 279 의
   "the skill versions in force" 를 만족하지만 감사 대상이 다르다.
3. **`templates/spec.md` 에 요구 ID 를 넣을 것인가.** 지금은 절만 있고 번호가 없어 다른 문서가 특정
   요구를 인용할 수 없다. 넣는다면 템플릿 소유자(템플릿 저장소)의 결정이다.
4. **수락된 intent 가 본문에 영원히 `Status: draft` 로 남는 문제.** `capture-intent` 는 "Approval is
   the merge" 라 손대지 말라 하고, `design-spec` 은 "must be accepted — merged to main. If it is still
   a draft … stop" 이라 한다. 시험에서 두 실행이 이 때문에 과제를 시작조차 하지 않았다
   (`trigger-tests.md` 2절). 둘 중 하나가 바뀌어야 한다 — 어느 쪽인가는 이 레인이 정할 일이 아니다.

## S2 · brand (6) — `docs/research/brand/README.md`

1. **공식 표기 목록은 어디에 두고 누가 관리하나(B5).** 회사·상품·기관 이름의 정본 목록이 없으면 이 조항은
   사람도 기계도 판정할 수 없다. 목록이 생기면 스킬에 표로 옮긴다.
2. **B2 의 「근거 조항」은 무엇을 인용하는 것인가.** 약관 조 번호 · 법령 · 사내 규정 중 어디까지 인정하는지,
   그리고 문구 안에 조 번호를 노출하는 것이 맞는지(고객 문구에 「(약관 제12조)」를 넣는 꼴).
3. **청구 시스템의 실제 상태값과 다섯 어휘의 대응은 누가 정하나(B4).** 특히 지급 없이 끝난 건과 지급이 끝난 건이
   화면에서 하나로 합쳐져 있을 때(실측 사례: 배지 3종 `처리중`·`완료`·`서류미비`). 다섯으로 표현되지 않는
   상태가 필요하면 어휘를 늘리는 개정인지, 화면을 고치는 일인지.
4. **정책의 대상이 마케팅 문구까지인가(B1·B7).** 정책은 대상을 「청구 상태 조회 서비스와 그 고객 통지」로 적었는데,
   스킬은 마케팅 블로그 문구에도 물린다(음성 대조 P5). 물리게 둘지, 대상 밖이라고 못박을지.
5. **「시각은 24시간제 · KST 표기」의 꼴을 정해 달라(B6).** `14:30 (KST)` 인지 `14:30 KST` 인지 정책이 정하지
   않아 스킬 예시에서 전자를 골랐다. 정책이 정하면 그대로 바꾼다.
6. **성명을 모르는 고객의 호칭(B7).** 「○○○ 고객님」 꼴인데 대리 청구인·법정대리인처럼 성명이 없거나 다른 사람일 때.

## S3 · compliance (8) — `docs/research/compliance/README.md`

스킬이 답을 지어내지 않고 **정본에 없어서 비워 둔** 자리들이다. 답이 오면 해당 조항과 두 스킬을 함께 고친다.

1. **C1 — 마스킹 자릿수를 식별자별로 고정하는가?** 정본은 "마스킹(뒤 4자리 등)"이라 예시만 든다.
   주민등록번호는 뒤 4자리를 남기면 생년월일·성별이 이미 앞자리에 있어 사실상 식별되는데,
   앞자리도 가려야 하는가? 계좌번호·연락처는 각각 몇 자리인가?
2. **C1 × C4 — 발송에 쓰는 연락처는 어디까지 「싣는 것」인가?** 통지를 보내려면 이메일·전화번호가
   발송 봉투에 쓰인다. 이 spec 은 「봉투에만 쓰고 본문·이력·로그에는 마스킹본조차 넣지 않는다」로
   기본값을 잡았는데(집합 시험 산출물 참조), 포털 화면에 "어디로 보냈는지"를 마스킹해 보여 주는 것은
   허용인가 금지인가?
3. **C5 — 지급 예정 「금액 자체」는 실을 수 있는가?** 정본은 "금액 산정 **근거**"를 뺐지만 금액 자체는
   말하지 않는다. 두 스킬의 기본값은 「애매하면 덜 싣는 쪽」이라 **미포함**이다.
   (시험용 intent 0011 의 열린 질문과 같은 것이고, 실제 과제에서 모델이 그대로 오너에게 넘겼다.)
4. **C5 — 보류·부지급 사유를 「화면」에는 보여도 되는가?** C5 는 통지에만 걸린다. 상담 콜의 큰 몫이
   보류 문의라면 사유 없는 "보류" 한 줄은 다시 전화를 부른다. 포털 화면의 기준이 필요하다.
5. **C6 — 3년의 기산점은 언제인가?** 이벤트 발생 시점인가, 청구 종결 시점인가.
   (후보 스킬들의 "3년"은 관계 종료 후 기산이라 우리와 다르다 — `coverage.md` 「가짜 친구」 참조.)
6. **C6 × 파기 요구 — 어느 쪽이 이기는가?** 고객이 개인정보 파기를 요구했을 때 3년 보존 의무가
   우선하는가? 정본에 예외 문장이 없다. **이 질문에 답이 없으면 스킬은 3년 보존을 그대로 지시하고,
   외부 GDPR 계열 스킬이 함께 로드되면 삭제와 보존이 부딪힌다**(후보 4건이 실제로 삭제를 지시한다).
7. **C7 — 「본인확인 기록」은 무엇이 자격을 갖추며 누가 발급하는가?** ARS·콜백·신분증 중 무엇인지,
   기록 ID 를 어느 시스템이 내주는지가 정해지지 않았다. 계약(기록이 있을 때만 조회, ID 병기)은
   C7 이 이미 고정하므로 구현은 이 답을 기다리지 않는다 — 발급처 하나만 열려 있다.
8. **C2 — 「근거 조항」은 무엇을 가리키는가?** 이 정책의 조항 ID(C1~C7)인가, 법령 조문인가,
   아니면 요구사항 번호인가. 외부 스킬을 함께 쓰면 GDPR 조문으로 오도될 여지가 있다.
