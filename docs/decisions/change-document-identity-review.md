# 개발건 문서 식별 규칙 검토

검토 기준판은 `182deba`이고, `codex/change-document-naming` 작업 트리의 문서 10개 변경을 읽었다.
이는 양 배포판의 지침으로 요청 시나리오를 판정한 문서 검토이며, 실제 제품 개발이나 에이전트 실행 실험이 아니다.

## 판정

중요한 흐름은 통과한다. `intent/README.md`가 대화 메시지·개발건·브랜치·PR을 구분하고,
`CLAUDE.md`, `docs/PROCESS.md`, `docs/GIT-WORKFLOW.md`, `capture-intent` 예시가 그 규칙으로
진입한다. 진행 중인 같은 목표는 기존 문서를 현재화하고, 완료 뒤 독립된 후속은 새 기록에서 이전
계약을 참조한다. 공통 설계 정본도 복제하지 않고 영향받는 한 정본을 갱신하게 했다.

양 배포판의 변경 기록 규칙과 Git 흐름은 같은 문면이다. 기존 차이는 보존됐다. 기본형은 새·변경
동작의 test-first 순서와 결함 재현을 유지하고, 선택형은 작업별 검증 방식 선택과 다음 의존 주기 전
문서 현재화를 유지한다. 이번 변경은 새 승인 단계, 프로그램, 검사기, 필수 스킬을 추가하지 않는다.

## 검토 중 발견과 반영

첫 검토에서는 두 문구를 보완 대상으로 보았다. 한 요청의 독립 목표를 여러 건으로 “나눌 수 있다”는
표현은 바로 아래 새 번호 규칙보다 약했고, README에 새 폴더 링크를 등록하라는 요구에는 별도 목록 자리가
없었다. 최종판은 전자를 `서로 독립적으로 수락·완료할 목표라면 같은 요청이어도 개발건을 나눈다`로
고쳤다. 후자는 등록 의무를 없애고 실제 `intent/` 디렉터리의 폴더를 목록으로 확인하게 했다. 빈 제품의
현재 상태를 적던 문장도 제거해 첫 변경 뒤 낡은 설명이 남지 않는다.

최종 문서에서 중요한 의미 누락은 찾지 못했다. 목표가 실제로 독립인지 판단하는 새 승인이나 자동
검사는 필요 없다.

번호는 정렬용 저장소 식별자이고 승인·시간·이슈·PR 번호가 아니라는 경계, slug 최소 문자 규칙,
완료 판정, 경로 변경 시 참조 갱신은 충분하다. 기능·버그·유지보수별 접두사, 번호 할당 프로그램,
상태 검사기나 추가 승인 절차를 더할 필요는 없다.

## 북극성 범위

북극성 L2는 아이디어·티켓·사고에서 intent를 만들고 수락 기록을 다음 단계에 넘기며, L3는 같은 변경의
요구·설계를 spec으로 기록하고, L4는 대화 없이 실행 가능한 plan과 여러 PR의 구현·검토 연결을 둔다.
이번 번호·slug·후속 기록 규칙은 그 artifact 인계를 채택 제품에서 일관되게 쓰기 위한 팀 규칙으로
표현돼 있다. 이를 플레이북의 보편적 형식으로 주장하지 않았고, 작은 변경에 불필요한 문서·검사를
늘리지 말라는 기존 `docs/PROCESS.md` 원칙도 유지했다.

## 확인 범위

두 배포판의 `intent/README.md`, `docs/GIT-WORKFLOW.md`, `capture-intent/SKILL.md`가 각각 같은지
대조했고, `CLAUDE.md`와 `docs/PROCESS.md`에서는 기존 TDD 필수형·선택형 차이만 남는지 확인했다.
`git diff --check`도 통과했다. 제품 코드·동작은 실행하지 않았고 `make check` 결과를 이 리뷰의
근거로 사용하지 않았다.
