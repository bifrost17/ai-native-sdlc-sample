## 목표와 선택

문서가 서로 일치하는지에 더해, **합의된 범위의 중요한 계약을 구현자가 새로 결정하지 않고 이어받을 수 있는지**를
검토에서 확인한다. 전체 코드나 모든 내부 선택이 같은 결과로 고정될 것을 요구하지 않는다.
판정은 다음 네 가지를 구분한다: 문서 정합성, 설계 계약의 충분성, 실제 실행 검증, 사람의 수락.

| 방법 | 판단 |
|---|---|
| “상세히 작성하라”는 문구만 강화 | 이미 있는 요구와 겹치며 검토 시점·미검출 판단을 바꾸기 어려움 |
| 별도 spec 검토 스킬·항상 두 리뷰어·필수 UML 패키지 | 역할과 설치 지점을 늘리고 작은 변경까지 무거워질 위험 |
| **기존 spec 인계 검토와 feedback/verifier에 범위·판별 질문을 보완** | **권고.** 기존 사람 검토를 유지하고 중요한 계약을 확인할 방법과 최소 근거를 구체화 |

목표는 이 종류의 중요한 공백을 더 잘 발견하는 것이다. 무결함 설계, 모든 에이전트 실수 차단,
전수 상태 조합, 새 승인 장부·자동 검사기·독립 에이전트 상시 호출을 목표로 하지 않는다.

## 언제 적용할지

| 사건 | 적용 |
|---|---|
| spec을 계획 수립에 인계하거나 “설계 완료”라고 보고하기 전 | 작성자가 intent와 전체 설계 정본을 기준으로 정합성·충분성을 검토해 기존 사람 검토에 근거를 제공 |
| 리뷰·구현 중 공유 입력/결과·권한·데이터/실행 수명·실패/복구 계약이 변경 | 영향받는 경계·분기와 인접 계약을 재검토하고 실제 spec/연관 plan을 갱신 |
| 골격 후보·한 설계 조각의 중간 검토 | 현재 질문·다음 단계에 필요한 결정만 검토. 미정 상세를 전체 최종 설계 완료로 보고하지 않음 |
| 질문·상태 보고·의미가 바뀌지 않는 표현 수정 | 새 독립 검토를 반복하지 않음 |

작은 변경은 짧은 작성자 확인과 기존 담당자 검토로 충분할 수 있다. 여러 구현자가 공유하는 새 계약,
독립 수명·권한·복구처럼 오판 영향이 큰 설계는 **새 문맥의 역량 높은 검토자를 우선 활용**한다.
복잡도·불확실성에 따라 관점을 나눌 수 있지만 사람 수나 모델명을 제품 정책의 고정 의무로 만들지 않는다.
기존 구현 완료 때 채택 스킬이 요구하는 fresh verifier 절차는 그대로 유지한다.

## 검토 방법

### 1. 판·범위·필수 입력을 확인한다

검토가 골격 후보, 계획에 인계할 spec, 구현 diff 중 무엇인지 먼저 밝힌다. 현재 intent/허용된 작업과
spec 진입점, 선언된 설계 정본, 필요한 기존 계약, 적용할 검토 기준을 읽는다. 정본과 과거 참고안을 구분한다.
이 입력은 기존 PR/대화·실행 기록에 남기면 된다. 매번 새 manifest나 전용 패킷을 만들 의무는 없다.

격리된 리뷰 패킷을 만들 경우 실제로 필요한 하위 지침·정본 참조까지 접근 가능하게 전달한다.
현재 스킬의 이름·버전만으로 그 본문을 읽었다고 하지 않는다. 읽지 못하거나 출력이 잘린 중요 부분은
범위를 나눠 다시 읽거나 미확인으로 남긴다. 상위 문서 링크와 파일 해시를 계약 충분성의 증거로 세지 않는다.

설계만 검토할 때 아직 없는 plan·구현 diff·시험 실행·배포 값을 필수 입력으로 요구하지 않는다.
기존 코드는 보존 계약과 실현 가능성의 근거로 필요할 때 읽되 새 설계의 정답으로 자동 채택하지 않는다.

### 2. 공유 계약을 양쪽 입장에서 따라간다

새로 만들거나 바꾸는 중요한 경계에서 호출자는 무엇을 보내고 수신자는 무엇을 허용·거부하며
어떤 결과/상태를 돌려주는지 정본으로 재구성한다. 필요한 입력의 의미·필수/선택·허용값, 결과·오류,
권한·호환과 결과를 바꾸는 순서·중복·취소 조건을 해당할 때 확인한다.

핵심 질문은 **“이 문서를 모두 지키면서도 양쪽 구현자가 서로 호환되지 않는 중요한 동작을 만들 수 있는가?”**다.
불일치 가능성을 지적할 때는 문서 위치와 서로 달라질 동작을 제시한다. 독자가 새 계약을 발명해 빈 곳을
메우거나, 특정 문서 형식이 없다는 이유로 반려하지 않는다. 이미 지정한 정확한 외부 계약을 재사용해도 된다.

작은 예: “중복 요청은 안전하게 처리한다”만 있으면 호출자는 재시도하고 수신자는 두 번 실행할 수 있다.
동일 ID의 같은 입력은 기존 결과를 돌려주고 다른 입력은 어떤 오류로 거절하는지 정해졌다면 공유 의미는
닫힌다. 그 내부 Map/DB 구현이나 private method까지 같은 문서에서 강제할 필요는 없다.
이 예시는 모든 제품에 멱등성이나 재시도를 추가하라는 정책이 아니다.

### 3. 중요한 분기는 출발 상태부터 결과까지 연결한다

하나의 AC가 여러 장애 주체·상태를 묶고 있으면 결과나 책임이 달라지는 분기를 구분한다.
전제/살아 있는 주체 → 사건 → 허용된 처리 주체 → 상태·영속 기록/효과 → 실패·불명 처리 →
사용자 결과와 재개/인계 조건을 필요한 깊이로 따라간다. 원자성·동시성이 중요하지 않은 변경에
모든 칸을 요구하지 않는다.

공통 불변식은 각 분기의 전이를 자동으로 완성하지 않는다. 다른 복구 절을 재사용한다면 그 절의 진입
조건과 처리 결과가 이 분기에도 적용되는지 확인한다. “문제 생기면 차단”만으로 복구 가능성을 약속하지 않는다.
지원하지 않는 복구 경로도 범위와 관찰 결과·수동 인계를 명시하면 정당한 결정일 수 있다.

상태표·시퀀스·구성 그림이 관계나 실패 분기를 더 잘 드러내면 선택한다. 실제로 추가한 그림은 정본의
이름·화살표·효과 시점과 맞추고 렌더링해 읽을 수 있는지 확인한다. UML 종류·그림 개수는 합격 기준이 아니다.

### 4. 이월할 수 있는 것을 구분한다

| 항목 | 판단 기준 |
|---|---|
| 공유 입력·의미·결과/오류·권한·중요 복구 선택 | 다음 의존 작업에 필요하면 spec에서 결정하거나 명시적 미결로 남겨 그 인계를 제한 |
| 내부 함수·파일 분해·알고리즘 구현, 생성 manifest 파일 | 공유 의미와 제약이 정해져 있으면 plan/구현에서 선택 가능 |
| 실제 배포 UID·인증 값·image digest | 선택 방법·권한 조건·필요 시점이 정해져 있고 설계 성립을 무효화하지 않으면 준비 단계에서 구체화 가능 |
| 성능·격리·복구의 실제 성공 | 실행으로 확인. 미실행은 설계 공백과 구분하되 설계 선택을 좌우하는 불확실성이면 먼저 작은 탐색 필요 |

“나중에 결정”이라는 이름보다 **지금 다른 구현자나 다음 단계가 그 답에 의존하는가**로 판단한다.
기존 Open questions/Flagged concerns 또는 리뷰 기록에 영향·해결 주체·필요 시점을 남긴다.
plan이 구체화 중 중요한 계약을 발견·수정하는 정상적인 반복은 허용하며 영향 spec을 함께 갱신한다.

### 5. 발견과 완료 근거를 종합한다

보고는 기존 리뷰/PR/실행 기록에 남긴다. 필요한 내용은 검토한 판·범위, 실제로 따라간 중요 계약·분기의
정본 위치, 발견과 영향, 정당한 이월·미확인, 다음 단계에 넘길 수 있는 범위다. 간단한 건은 몇 문장이면 된다.

작성자는 검토자의 PASS 개수를 합산해 완료를 정하지 않는다. 중요한 발견이 무엇으로 해결됐는지,
이월이 왜 다음 의존 작업을 막지 않는지, 검토 범위 밖에 무엇이 남았는지 확인해 종합한다.
중간 범위만 검토했다면 그 범위만 보고한다. 새 근거가 기존 PASS를 뒤집으면 과거 판정은 보존하고
현재 spec/인계 요약을 정정한다. 두 번의 PASS를 얻을 때까지 반복하는 방식은 사용하지 않는다.

설계 준비 판단·실제 AC 통과·사람 수락은 별개다. 새로운 상태 문자열이나 승인 단계를 추가하지 않는다.
이미 받은 사람의 허가를 재사용하고 중요한 미결 결정만 해당 담당자에게 연결한다.
설계와 구현이 섞인 작업은 명칭보다 실제 변경·완료 주장으로 검토 범위를 정한다. 구현을 바꿨거나
구현 완료를 주장하는 부분에 설계 검토의 실행 증거 예외를 적용하지 않는다.

## 반영할 자산과 경계

아래 경로는 두 배포판의 같은 상대 경로에 공통 의미로 반영한다. 기본형 test-first와 선택형 방식 선택은 보존한다.

| 경로 | 예정 보완 |
|---|---|
| `project/REVIEW.md` | 설계만 검토할 때의 입력과 정합성/충분성 기준을 짧게 명시. 기존 구현 리뷰와 구분 |
| `project/docs/PROCESS.md` | 기존 spec 인계 검토에서 REVIEW 기준을 적용하도록 연결. 새 단계 신설 없음 |
| `project/examples/skills/design-spec/SKILL.md` | 인계 전 기존 검토 기준·필요한 상세 참조를 적용하도록 연결. 전체 검토표 중복 없음 |
| `project/examples/skills/design-spec/references/design-depth.md` | 공유 의미/구현 선택, 복합 AC 분기, 충분한 작은 표현의 대비 예시 보완 |
| `org-skills/skills/sdlc-feedback/SKILL.md` | spec 인계 준비·중요 설계 개정도 적용 사건에 포함하고 설계만의 검토 범위 전달·결과 종합을 명확히 함 |
| `org-skills/agents/sdlc-verifier.md` | 설계 검토에서는 필요한 intent/spec/정본/기준을 받고, 구현 검토에서는 기존 plan/diff/실행 근거도 확인. 충분성 질문 추가 |

spec 양식의 여섯 절, plan 양식과 spec-policy-pass의 정책 검토 역할은 유지한다. 새 spec 검토 스킬을
만들지 않는다. 제품 REVIEW는 스킬 미설치 상태에서도 의미가 통하고 특정 도구의 필수 호출을 요구하지 않는다.
상세 질문은 기존 design-depth와 verifier 각 역할에 필요한 만큼만 둔다. 새 규칙의 별도 복제 목록은 만들지 않는다.

기존 OpenCode verifier 및 feedback patch, 선택형 Codex verifier TOML 및 feedback patch에서 같은 범위와
기준을 반영·검증한다. 기본형에는 현재 Codex adapter가 없으므로 있다고 가정하거나 이번 범위에서 새로 만들지 않는다.
구현 시 실제 diff에 따라 영향을 받는 adapter만 고치되 모든 제공 adapter의 적용·기준 일치를 확인한다.
작성 스킬도 양판 OpenCode `authoring-native.patch`와 선택형 Codex `explicit-only.patch`의 적용,
실제 설치본 design-spec 본문과 동반 `references/design-depth.md` 복사를 확인한다.
팀 패키지는 구현 시 최신 판을 확인해 patch version을 올리고 카탈로그·설치 안내를 맞춘다.
현재 판 기준 후보는 기본형 0.1.10/선택형 0.1.6이다. 이 설계 단계에서는 버전을 올리지 않는다.

## 구현·검토·부분 평가 순서

1. root가 공통 기준·작성 예시·검토 이벤트를 먼저 보완한다. 설계 의미는 Astra/high, 배포판 차이와
   adapter 경로는 Sol/medium이 검토한다. 변경이 작으면 역할을 합쳐 불필요한 중복을 줄인다.
2. 별도 부분 실험 기록을 만들고 번호는 그때의 사용 목록에서 정한다. 실험마다 새 브랜치/작업 공간을
   두고 원본 판·선별/추가 참조·설치판·실제 요청문·후속 메시지·응답·판정을 보존한다.
3. root가 HUMAN/평가자를 맡는다. **행동 평가는 선택형의 Codex 설치 한 조합에서만** 진행하며,
   기준/개선 비교 리뷰어는 Astra/high로 모델·추론을 고정한다. 마지막 사용 흐름의 parent도 Astra/high를 쓰고
   child는 채택한 adapter의 권장 설정을 사용해 실제 모델·추론을 별도 기록한다. 그 결과를 앞의 모델 비교에 합치지 않는다.
   F1/F2 원인 보고서·정답표·별도 PASS 보고서는 리뷰어 입력에서 분리한다. 원본 설계에 이미 포함된
   과거 리뷰 언급은 보존하되 판단 근거로 쓰지 않게 하고, 완전한 판정 미노출 실험이라고 주장하지 않는다.
   알려진 사례를 아는 root의 최종 채점과 리뷰어의 새 문맥 실행을 구분한다. 문서 검토이며 제품 코드나 실제 서비스는 실행하지 않는다.
4. 기준 실행과 개선 실행은 동일한 완전한 설계 입력·참조와 과제 범위를 사용하고 검토 지침만 바꾼다.
   과거 패킷의 누락을 복구한 현재 기준 실행은 역사적 B/C의 정확 재현이 아니다. 그 차이를 기록한다.
5. 아래 네 요청을 각 새 문맥으로 기본 1회씩 실행한다. 마지막 요청의 parent와 child를 별도 호출로 세어
   기본 총 5호출을 예상한다. 개선이 필요한 중요 누락이 있으면 최소 수정 후 영향 사례의 검토만 새 브랜치에서
   1회 추가한다. **모든 실험 참가 agent를 합해 최대 6호출·총 30분**을 시작 예산으로 두며 다른 판·플랫폼마다
   반복하지 않는다. 예산에 도달하면 새 호출을 시작하지 않고 진행 중 응답의 완료·중단·미확인을 그대로 기록한다.
   시간 자체를 충분성 판정으로 쓰지 않는다.

| 평가 입력 | 확인할 것 |
|---|---|
| 원본 r1 + 현행 기준 | 알려진 두 결함에 대한 현재 검토 결과를 다시 관측. 과거 미검출을 그대로 가정하지 않음 |
| 동일 r1 + 개선 기준 | F1의 공유 의미/생성 파일 구분, F2의 독립 장애 분기 누락을 정확한 근거로 발견하는지 |
| 작은 충분한 spec + 개선 기준 | 기존 F01/B01 수준의 문서를 그림·전체 schema·추가 승인 때문에 과도하게 반려하지 않는지 |
| 별도 합성 경계 사례 + 개선판의 사용 흐름 | 공유 계약·복구는 충분하고 내부/배포 값만 정당하게 이월된 사례. parent에게 스킬 이름 없이 “다른 검토자에게 검토받고 계획에 넘길 준비가 됐는지 정리해 달라”고 요청하여 적용 스킬·설계만의 입력 전달·결과 대기·종합을 관측 |

원본 r1은 선언된 전체 설계 정본과 필요한 기존 계약/지침을 제공한다. 이 폴더의 5개 발췌용 사본만으로
원본 전체 설계 리뷰를 했다고 하지 않는다. 합성 사례는 실제 제품의 미해결 설계를 대신 고친 것이 아니며
그 판의 허용·불허와 근거를 평가 전에 고정한다. 근거 수집과 새 지침의 자연 선택·읽기·실제 적용은
서로 구분한다. 명시적으로 스킬을 지정한 시험은 자연 선택의 증거가 아니다.
마지막 요청은 독립 검토 자체는 사람이 요청한 조건이다. 스킬 이름을 지정하지 않은 선택·범위 전달을
관측하되, 에이전트가 설계 완료 시점을 스스로 인지해 독립 검토를 시작했다는 증거로 확대하지 않는다.

개선 기준이 알려진 두 공백을 찾고, 작은 충분한 문서와 정당한 이월을 과도하게 반려하지 않으며,
설계 검토에서 제품 실행·존재하지 않는 plan을 요구하지 않으면 부분 적용을 통과시킬 수 있다.
정확한 문구·표 개수·finding 개수는 기준이 아니다. 기준 실행도 결함을 찾으면 우월성이 입증됐다고 하지 않는다.
이 작은 비교는 모델 실패율·일반 탐지율·전체 SDLC 통과를 입증하지 않는다.

정적 확인은 `make check`, 기존 패키지 strict 검증, 제공 adapter patch 적용·설치본 기준/해시 일치,
작은 예시의 참조, TDD 판별 차이를 대상으로 한다. 테스트로 의미 완결성을 판정하는 새 검사기는 만들지 않는다.
판별 차이·adapter 검토에서는 설계만의 입력을 받는지, 작은 설계 편집에 독립 검토를 일괄 요구하지 않는지,
구현 완료 때의 기존 fresh 검토 의무를 유지하는지 확인한다. 앞선 설계 PASS를 구현 완료 검토로 재사용하지 않는다.
앞의 세 요청은 기준의 직접 적용 시험, 마지막은 사용자 요청에 따른 스킬 선택·위임 흐름 시험이다.
설계 완료의 자율적 감지, 실제 구현 완료 호출과 다른 판·플랫폼의 자연 작동은 미검증으로 남긴다.
부분 평가가 통과한 뒤 제작 변경을 main에 반영하고, 북극성 주석은 실제로 확인한 범위만 갱신한다.
원본 제품의 F1/F2 수정·승인·구현과 이전 실험의 판정은 이 작업 범위에 포함하지 않는다.

## 이번 설계 단계의 산출물

원인분석·대화 발췌·원본 사본과 SHA, 현행 지침 대조, 위 보완안과 부분 평가 계획을 보존한다.
독립 검토의 의견·수정도 같은 폴더에 남긴다. 이 설계의 문서 검토가 끝나도 보완된 절차의 실제 효력은
아직 미검증이다. 활성 템플릿 반영·패키지 배포·설치·부분 실험은 후속 구현 범위다.

## 설계 검토와 현재 확인

[Astra/high 검토](review-astra.md)는 이벤트 연결이 적절하다고 판단했고, 후속 정적·adapter 검토에서
설계 검토의 선택 활용과 구현 완료 fresh 검토 의무의 구분을 명시할 필요를 지적했다.
root는 위 평가 절에 그 확인 항목, 설계 PASS로 구현 완료 검토를 대체하지 않는 조건과 자연 이벤트
자율 감지의 미검증을 반영했다. 혼합 작업은 실제 변경과 완료 주장으로 범위를 정하는 조건도 추가했다.
검토 원문은 보존하며 이 해소 기록과 구별한다. 보조 설계 분석에 참여한 에이전트의 재검토이므로
설계에 관여하지 않은 독립 최종 심사라고 표현하지 않는다.

[Sol/medium 검토](review-sol.md)는 총 호출 예산·대표 설치판과 작성 스킬 변환의 확인 범위를 명시하도록
권고했다. root는 선택형 Codex 한 조합·parent/child 합산 최대 6호출로 한정하고, 마지막 합성 사례에서
스킬 이름을 지정하지 않은 사용자형 위임 요청을 관측하도록 보완했다. 이 조건부 관측과 자율 완료 감지는 구분한다.
작성 스킬 patch와 동반 상세 지침의 설치본 확인도 추가했다. 검토자가 제안한 추가 조건을 보편적 제품 의무로 만들지 않았다.

[정적 확인](validation.json)은 원본 사본 9개 SHA/bytes·현재 원본 무변경, 설계 문서 참조,
현행 템플릿 입력 22개 지문을 기록한다. `make check`는 unittest 102개(1개 건너뜀), hooks 28개,
eval fixture 8개와 managed settings 확인을 통과했다. 활성 지침이 그대로인 상태의 회귀·증거 보존 확인이며
이 제안의 실험 통과를 뜻하지 않는다.
