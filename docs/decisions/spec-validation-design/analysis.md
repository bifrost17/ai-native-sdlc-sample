## 확인되는 원인과 확인되지 않는 원인

**F1: 공유 계약의 미완결을 구현 상세로 이월했다.** B의 마지막 이월 항목과 C의 요구·AC 표에는
opcode의 실제 완성을 구현 범위로 분류한 문장이 있다. 고정 protocol은 공통 header·메시지 종류와
일부 필수 필드를 정했지만 메시지별 입력·오류·상태 의미의 정본을 완결하지 않고 type별 schema와
build artifact를 참조한다. 숫자 배정/생성 파일과 양쪽 구현이 공유해야 할 의미를 구분해야 한다.

**F2: 공통 안전 조건과 특정 장애 분기의 복구 완결성을 혼동했다.** spec AC8은 engine·container·gateway를
각각 재시작한다. lifecycle의 cold recovery는 B/X process 또는 M 연속성 상실에 진입하며,
integration 장애 표에 engine-only 행은 없다. B/X/M이 살아 있는 engine 종료에서 다음 engine의 기동
주체·연결 세대 전환·별도 PTY·업무 재개 조건을 공통 차단 규칙만으로 결정할 수 없다.
이는 새로운 기능을 발명하라는 지적이 아니라 이미 약속한 분기를 끝까지 연결하라는 지적이다.

**root의 완료 종합도 미검출의 일부다.** 두 보고서는 실제로 많은 권한·저장·경합을 검토했고 제품 미실행을
명시했다. 그러나 두 PASS와 동일 해시를 설계 전체의 충분성 근거로 확대했다. 검토 횟수와 문서 일치보다
어떤 중요한 계약·분기가 닫혔는지를 근거로 종합해야 한다.

**지침 패킷의 완결성은 보완점이지만 단독 원인으로 확정할 수 없다.** 실제 동결 폴더에 design-depth와
Codex verifier TOML이 없음을 확인했다. 반면 고정 design-spec은 현행 선택형 작성 스킬에서 Codex
frontmatter 변환만 적용한 내용과 정확히 같고, 상위 지침만으로도 구체 계약·실패·전체 정본을 요구한다.
하위 참조가 있었으면 반드시 검출됐을 것이라는 인과는 입증되지 않았다.

선행 리뷰 요청문의 원문은 확인하지 못했다. 최근 대화는 평문이지만 해당 구간 spawn/followup 15개
message는 평문으로 해석할 수 없는 형태다. 도구 인자의 모델·추론·대상 metadata만 기록했고 본문을
복호화하거나 추정하지 않았다. 프롬프트가 잘못 지시했다고 단정하지 않는다. 숨은 추론은 조사하지 않았다.

시간 부족·토큰 부족·모델 자체의 일반 성능·동료 PASS 노출·관련 문서 전부 미열람을 원인으로 확정할 근거도 없다.
원인 보고의 210개 SHA 일치는 원 보고자의 관측이다. 이번에는 직접 대조한 5개 문서 범위로 한정한다.

## 현재 템플릿과의 차이

| 자산 | 이미 있는 요구 | 보완할 지점 |
|---|---|---|
| spec 양식·design-spec | 정확 계약, 중요한 실패 AC, 정본 집합, 미결 영향, 상위 의도와 연결 | 새 필수 양식보다 실제 검토 질문과 시점 연결 |
| design-depth | 입력/반환/오류·권한·호환, 상태·실패·복구, 필요한 도식 | 공유 의미/내부 선택 구분과 다른 장애 근거를 재사용할 때의 조건을 작은 예시로 설명 |
| spec-policy-pass | 관련 정책을 읽고 충돌·우려를 해당 정본에 반영 | 정책 PASS를 전체 설계 충분성의 판정으로 쓰지 않음. 이 스킬을 일반 설계 검토기로 키우지 않음 |
| PROCESS·REVIEW | spec 단계 사람 검토, intent/spec/plan/diff 대조 | spec만 검토할 때의 입력·충분성 질문을 명시. 아직 없는 plan·제품 실행 결과를 요구하지 않음 |
| feedback·verifier | 전체 설계 정본/관련 실패 대조, 강한 모델·새 문맥·PASS 한계, 영향 문서 갱신 | 구현 완료 중심의 이벤트/입력을 설계만의 검토 범위에서도 정확히 적용하도록 구분 |

따라서 이 사건은 원래 템플릿이 정확한 설계를 요구하지 않았다는 증거가 아니다. 기존 요구를 적용하는
검토 질문·인계 문맥·판정 근거가 충분히 구체적이지 않았다는 보완 근거로 삼는다.
하나의 복잡한 제품 사건을 전체 모델의 실패율이나 모든 사용자의 절차 위반으로 확대하지 않는다.

## 북극성 해석

[L3](../../verification/north-star-playbook.html#요구사항과-design)는 intent의 문제와 질문·우려를 처리한 요구·설계를
계획의 기준으로 넘기고 사람이 판단하게 한다. [L4](../../verification/north-star-playbook.html#기본-출발점으로서의-claude-code-plan-mode)는
실제 파일·순서·증명할 시험, 위험·대안 질문과 대화 없이 이어받을 수 있는 계획을 요구한다.
이 두 문서를 합친 인계에서 중요한 설계 결정을 구현자의 추측으로 남겨 두면 안 된다.
그러나 모든 내부 메서드·수치·클래스를 사전에 고정하라는 뜻도 아니다.

[L8](../../verification/north-star-playbook.html#claude에게-feedback-loop-주기)은 작업 중 피드백과 마지막 새 문맥 검토를
구분한다. 그 취지를 설계 검토에 적용하되 매 문서 편집마다 새 에이전트나 승인 단계를 의무화하지 않는다.
구체적인 충분성 질문과 위험에 따른 검토 선택은 팀의 적용 방법이다. UML 개수·리뷰어 둘·대안 셋을
북극성의 의무로 추가하지 않는다.
