# 003 선행 독립 설계 리뷰의 미검출 원인 분석 보고서

작성: Codex(root). 일자: 2026-09-14 KST.
Status: analysis recorded; design findings remain open; prevention measures proposed.

요청: “선행 리뷰어 2명이 왜 이 점을 놓쳤는지 분석한 상세 Report 작성해서 저장해.”
대상은 `final-design-r1`의 최종 독립 리뷰 B/C와 이를 종합한 root의 완료 판정이다.
기존 003 설계 작업의 검토 기록으로 작성한다. 002, 제품 구현, 운영 전환은 이번 범위에 포함하지 않는다.

## 1. 결론

**가장 강하게 확인되는 원인은 설계와 구현의 경계 판단 오류다.** 두 리뷰는 새 내부 프로토콜의
공유 계약 중 미완결 부분을 후속 구현 대상으로 분류했다. 또한 owner 상실 후 복구와 공통 안전 규칙을
확인했지만, engine만 종료되는 별도 경로까지 완결되었다는 근거를 제시하지 못했다.
root도 이 두 PASS를 종합하면서 계약의 완결성을 별도로 확인하지 않은 채 “최종 설계 완성”으로 보고했다.

현재 기록이 지지하는 설명은 다음과 같다.

1. **F1의 직접적인 분류 오류:** B는 opcode manifest를 후속 준비·구현으로, C는 opcode 완성을 구현 범위로
   명시했다. 구현 코드를 나중에 작성하는 것과, 양쪽 구현이 공유할 의미·입력·오류를 나중에 결정하는 것을
   충분히 구분하지 못했다.
2. **F2의 근거 적용 범위 오류:** owner 장애·전체 cold recovery의 근거와 공통 불변식이 AC8의
   engine-only 재시작 분기까지 설명하지는 않는다. 보고된 검토 근거는 그 분기를 닫지 못했다.
3. **리뷰 방법의 공통 취약점:** 두 보고서는 이미 서술된 보호 규칙의 정합성을 자세히 검토했지만,
   문서만 보고 서로 다른 중요한 동작을 구현할 여지가 남는지에 대한 확인 결과가 부족했다.
   이는 보고서 구성에서 도출한 해석이며 리뷰어의 내부 사고 과정을 확인한 주장이 아니다.
4. **입력 준비의 보완점:** 고정 패킷은 상위 스킬을 포함했지만 그 스킬이 연결한 상세 지침·verifier를
   포함하지 않았다. 지침 적용의 추적성이 약해졌을 가능성이 있다. 상위 스킬에도 구체 계약 요구가
   있었으므로 이 누락 하나를 충분한 원인으로 보지는 않는다.
5. **완료 판정의 책임:** 독립성·해시·두 PASS는 유효한 절차 증거지만 설계의 의미적 완결성을 보증하지 않는다.
   root가 보고 범위를 넓힌 것도 이번 실패의 일부다.

**문서 변경 때문에 새로 생긴 결함은 아니다.** 이번에도 210개 고정 사본의 bytes/SHA와 현재 15개 입력을
대조했고 불일치는 0개였다. 앞선 판정에 존재하던 공백을 후속 검증에서 발견했다.
시간 압박, 토큰 부족, 문서 미열람, 두 리뷰어 간 판정 공유, 특정 모델의 일반적 성능 부족은 확인된 원인이 아니다.

### 3.1 실제 요청문을 확인할 수 있었는가

당시 parent/B/C의 로컬 세션 메타데이터와 spawn의 모델·추론·새 문맥 인자는 확인했다.
다만 로컬 기록의 message 본문은 평문으로 해석할 수 없는 형태였고, 지원되는 `read_thread` 조회도
B/C의 최초 과제 요청문을 반환하지 않았다. parent의 최근 기록과 이전 페이지에서도 해당 요청문은 확보하지 못했다.
그 본문을 복호화하거나 추정으로 복원하지 않았다.

따라서 **“요청문에 완전성 검사가 없었다”, “리뷰어에게 engine-only를 제외하라고 했다” 같은
프롬프트 원인 주장은 하지 않는다.** 이번 분석은 읽을 수 있는 리뷰 보고서, 실제 command 기록,
고정 입력과 결과를 근거로 한다. 과제 요청문 보존을 개선안에 포함하는 이유도 이 사후 추적 한계 때문이다.

### 3.2 파일 접근 기록이 말해 주는 것

E10에는 B/C가 `runtime-lifecycle`, `protocol-and-resources`, `integration-and-verification`을 출력한
성공 command가 있다. B는 세 상위 스킬을, C는 sdlc-feedback을 읽는 command도 확인된다.
이는 관련 문서가 접근 불가였다는 설명에 반하는 증거다.

그러나 command 성공은 모든 출력이 잘림 없이 모델에 전달되었거나 모든 의미를 이해했다는 증거가 아니다.
C는 일부 source 출력이 잘렸다고 스스로 기록했다. 이 사실을 정본 전체 미열람의 증거로 확대하지 않는다.
이번 `read_thread` 조회는 command와 상태를 확인하는 데 사용했으며, 당시 모든 반환 출력의 완전성을
재검증한 것은 아니다. 모델의 숨은 추론은 조사·기록의 근거로 사용하지 않았다.

## 4. 판정이 만들어진 경과와 독립성

| 시점·기록 | 확인한 사실 | 의미 |
|---|---|---|
| 2026-09-14 15:41:52 KST | E3 packet 생성 시각 06:41:52 UTC | 최종 검토 대상이 고정됨 |
| B 보고 15:46:38 KST 재대조 | E1 19행의 manifest/210개 사본·현재 15개 대조 | 입력 동일성을 확인한 기록 |
| A의 독립성 한계 발견 | E9: parent가 자기 최초 보고 고정 전에 child PASS를 자동 수신 | A는 독립 최종 2명에서 제외되고 추가 리뷰로 보존됨 |
| C 새 문맥 생성 | 세션/spawn 기록 15:52:22 KST, Astra/high/fork_turns=none | A 대신 별도 C를 배정함 |
| C 최초 보고 | E2 및 최초 보고 전달 command 기록 | 같은 packet에 P0/P1/P2 발견 없음 |
| 16:01:37 KST | E9 closure의 07:01:37 UTC, status=design-complete | root가 B/C PASS를 최종 설계 완료로 종합함 |
| 후속 충실도 감사 | E4: 동일 15개 입력에서 F1/F2 확인 | 문서 drift가 아닌 앞선 판정의 미검출 |
| 현재 | execution 상단은 design revision required | 과거 PASS/closure를 유지하면서 현행 판정을 정정함 |

B의 세션은 동결 이전에 만들어져 대기 시간을 포함한다. C의 전체 turn 시간은 약 6분 51초로 기록된다.
세션 시간과 command 수로 실제 검토 집중 시간이나 충분성을 산정하지 않는다. 기한·토큰 상한 때문에
중요 검토를 생략했다는 증거는 확보하지 못했다.

**독립성 통제는 일부 정상 작동했다.** A의 자동 판정 노출을 발견해 최종 쌍에서 제외하고 B/C로 교체했다.
B/C는 peer 판정에 노출되지 않은 최초 보고라고 기록했다. 이를 뒤집을 증거는 이번 조사에서 발견하지 못했다.
따라서 A의 문제를 B/C의 누락 원인으로 전가하지 않는다. 독립성의 모든 메시지 경로를 이번에 재입증한 것도 아니다.

## 5. F1 분석 — 공통 계약을 구현 상세로 분류

### 5.1 직접 근거

- B 55행: “opcode별 구현 manifest”를 실제 image/credential/resource profile 값 및 parser/race 집행과
  함께 후속 준비·구현 입력/검증 대상으로 분류한다.
- C 43행: B/X의 기능 목적지를 대조한 뒤 “opcode의 실제 완성 여부는 구현 범위다”라고 명시한다.
- B 38–40행, C 47/52행: pair/CAS/fence, 단조 소비 번호, replay/credit 규칙은 검토했다.
- 고정 S8 34–48행은 type별 schema를 언급하지만 완결된 type별 계약이 없고, 143–144행은 정확한
  opcode 목록을 build artifact로 지정한다. coverage 23–25행도 앞으로 연결해야 할 대응을 요구한다.

따라서 관련 프로토콜을 전혀 살피지 않았다는 설명보다 **검토한 항목의 설계 책임을 너무 좁게 잡았다**는
설명이 기록에 더 잘 부합한다. 단, manifest 이월 문장은 모든 누락된 field schema를 의식적으로 이월했다는
증거까지 제공하지는 않는다. 그 부분의 내부 판단은 미확인이다.

### 5.2 무엇이 허용 가능한 이월이고 무엇이 아닌가

| 항목 | 설계와 후속 작업의 구분 |
|---|---|
| 실제 image digest, 설치 시 UID 숫자, credential 배포 값 | 의미·선택 방법·검증 조건이 이미 정해졌다면 준비 단계에서 채울 수 있음 |
| 파일 분해, private method, parser 구현, schema에서의 코드 생성 | 중요한 외부 계약이 정해졌다면 구현 단계의 선택 |
| 숫자 opcode 배정·생성 manifest의 실제 파일 | 유한 operation과 의미·매핑의 정본이 있으면 생성/구현 산출물로 둘 수 있음 |
| B가 보내고 X가 받아야 할 필수 입력, 의미, 결과·오류, 상태별 허용·권한 | 양쪽이 독립 구현해도 같아야 하는 공유 설계 계약 |
| handshake·재연결·조회·credit의 순서와 실패 후 처리 | 동작·권한·자원에 영향을 주는 설계 계약 |
| 실제 성능·namespace/UID 격리·race 집행 성공 | 후속 실행 증거. 문서만으로 PASS할 수 없음 |

문제는 생성 manifest 파일이 없다는 사실만이 아니다. 그것이 구현해야 할 공통 의미와 유한 지원 범위도
완결되지 않은 상태인데 같은 이월 설명으로 처리한 데 있다.

### 5.3 구체적인 반례와 영향

B 담당자는 HELLO 뒤 BIND에 engine generation과 continuity 증명을 어떤 필드로 담을지 결정해야 한다.
X 담당자는 허용할 상태, 누락·중복·오래된 세대 입력의 오류와 연결 종료 여부를 결정해야 한다.
두 담당자가 현재의 pair 원칙을 지키면서도 호환되지 않는 입력/응답과 재접속 절차를 만들 수 있다.
비슷한 공백이 결과 조회·credit 반환·watch/PTY event 식별에도 있다.

예상 영향은 통합 실패, 구현 중 재설계, 권한/중복 전달/자원 회수 의미의 불일치다.
현재 제품에서 그런 사고가 실제 발생했다는 증거는 아니다. 이번 건은 문서 결함이며 제품 실행은 하지 않았다.

## 6. F2 분석 — 안전 규칙과 복구 전이의 완결성을 혼동

### 6.1 직접 근거

- spec AC8은 engine·컨테이너·gateway를 **각각** 재시작하는 경우를 요구한다.
- C 45행은 AC6/7/8을 한 행에 묶어 전달·수신·writer·native 결과·unknown 규칙을 근거로 제시한다.
- B 32–33행과 C 52–54행은 새 B의 선점 방지, M/CLI 상실, 지연 start, old scope 종료와 cold recovery를 설명한다.
- S9 73–83행 장애표에는 engine-only 행이 없다. S6 105–108행의 cold recovery 진입 조건은
  B/X process 또는 M 연속성 상실이다. S8은 engine identity를 연결 pair/handshake에 묶는다.

이 사실로부터 “리뷰어가 engine-only를 전혀 생각하지 않았다”는 결론까지는 얻을 수 없다.
확인되는 것은 **두 보고서의 근거가 engine-only 분기의 완결성을 지지하지 못한다**는 점이다.

### 6.2 기존 안전 원칙만으로 결정되지 않는 것

다음 상황을 문서만으로 따라간다: B(gateway), X(컨테이너 실행 담당), M(수명 관리자)은 생존하고,
별도 PTY는 실행 중인데 Codex app-server만 종료된다.

| 질문 | 이미 있는 근거 | 여전히 필요한 결정 |
|---|---|---|
| 예전 실행권·승인은 유효한가 | 종료·세대 확인, 예전 승인 무효화 | 각 레지스트리의 전이 및 관찰 결과와 연결 |
| 새 engine을 누가 기동하는가 | 새 권위 전에 옛 실행 종료가 필요 | 명시적 기동 요청, 권한 주체, 허용 상태 |
| 기존 연결을 계속 쓸 수 있는가 | pair에 engine identity가 결합됨 | 새 engine generation과 pair/family/cursor 전환 절차 |
| 기존 PTY와 자원은 어떻게 되는가 | 수명·자원 소유권을 구분한다는 원칙 | PTY 유지/종료, credit·pending 요청의 처리 범위 |
| 언제 새 작업을 받는가 | 종료 미확인은 readiness/새 mutation 차단 | 확인 성공 뒤 admission을 다시 여는 구체 조건 |

이전 실행의 종료를 확인하기 전 새 실행권을 주지 않는다는 안전 규칙은 새 정상 상태로 돌아가는 절차 전체를 정의하지 않는다.
계속 차단된 상태에 머무르는 구현도 안전 규칙은 지킬 수 있다. reliability에는 잘못된 실행의 방지와 함께
허용된 복구의 정의도 필요하다.

한 구현자는 engine만 재기동하고 PTY를 보존할 수 있고, 다른 구현자는 전체 container cold recovery를
선택할 수 있다. 둘 중 하나를 지금 보고서에서 선택하지 않는다. 이것은 후속 설계에서 세 대안 비교와 함께
명시해야 할 결정이다. 현재 문서만으로 하나가 필연적으로 도출되지 않는다는 점이 지적의 핵심이다.

## 7. 두 리뷰에 공통으로 나타난 검출·종합의 한계

### 7.1 정합성 확인과 완전성 확인이 충분히 분리되지 않음

B는 반례별 통합 대조표, C는 R/AC 대응표를 작성했다. old-owner 배제, unknown 비재전송,
no-late-spawn, durable writer, TOML crash gap, 승인 본문 사본 등 많은 중요한 문제를 실제로 다뤘다.
그 검토가 무의미했다고 평가하지 않는다.

그러나 보고서에서 연결된 근거는 주로 “서술된 보호 규칙이 해당 위험을 막는가”를 답한다.
F1/F2를 검출하려면 다음 질문도 필요했다: **“문서의 규칙을 모두 지키면서도 두 구현자가 서로 다른
중요한 동작을 선택할 수 있는가?”** 불변식의 정합성, 경계 계약의 완전성, 실제 집행 증거는 서로 다른 검토다.

이 설명은 두 보고서의 선택·이월·근거 구성을 해석한 것으로 확신 수준은 중간이다.
개별 리뷰어의 주의 배분·동기·내부 추론을 관측한 결과로 표현하지 않는다.

### 7.2 새 문맥 두 개의 한계

같은 입력을 서로 판정 미노출 상태로 읽는 것은 독립 리뷰에 유용하다. 하지만 두 검토가 같은 수준의
정합성 질문에 집중한다면 같은 종류의 공백을 놓칠 수 있다. 이번 B/C는 표 형식은 다르지만 F1을
후속 구현으로 처리한 점과 F2의 분기별 근거가 빠진 점이 겹친다.

이를 통계적 실패 상관계수나 모델 전체의 신뢰도로 환산할 수 없다. 후속 감사도 Astra/high 도구 인자로
진행되어 같은 문서에서 두 지적을 찾았다. 이 한 사건은 “모델을 바꾸면 해결된다” 또는 “모델이 무능하다”는
결론을 지지하지 않는다. 우선 바꿀 것은 과제·기대 근거·검토 산출물의 구성이다.

### 7.3 정책 참조의 고정·접근 추적성이 불완전했음

E3에는 세 상위 스킬이 있지만 `.agents/skills/design-spec/references/design-depth.md`와
`.codex/agents/sdlc-verifier.toml`이 포함되어 있지 않다. design-spec은 상세 지침을, sdlc-feedback은
verifier 기준을 참조한다. B는 verifier가 패킷에 없음을 보고서 22행에 정확히 밝혔다.
C가 명시한 정책 읽기 목록은 sdlc-feedback을 포함한다. 다른 스킬의 미열람을 목록 부재만으로 단정하지 않는다.

이는 **동일 문서 해시 확보와 동일 판단 지침 적용의 증거가 다르다**는 문제다. 패킷 준비자는 관련 참조를
함께 고정하거나 별도 기준의 적용 범위를 명시했어야 했다. 다만 B가 읽은 spec-policy-pass 35–36행에도
인터페이스·상태·실패를 구체화하고 중요한 계약을 미루지 말라는 내용이 있다.
그러므로 하위 지침 부재는 가능한 기여 조건이며 F1/F2 미검출을 단독으로 설명하거나 면책하지 않는다.

패킷의 `authoritativePaths` 15개에는 spec이 참고 역할로 분류한 architecture/current-code-assessment도 있다.
현행 정본과 참고의 역할을 메타데이터에서 더 명확히 나눌 수 있다. 다만 이 명칭 혼재가 이번 두 누락을
일으켰다는 증거는 없으므로 별도의 추적성 개선으로만 둔다.

### 7.4 root의 작성·검토 요청·완료 판정 책임

원래 설계 공백을 남긴 작성 책임은 root에게 있다. 리뷰어에게 그 책임을 모두 이전할 수 없다.
또한 E9의 역사적 execution은 “완료는 003의 최종 아키텍처 설계”라고 선언했고,
closure는 `design-complete`를 기록했다. B/C의 의미 검토 결과를 종합해 이 표현을 선택한 책임도 root에게 있다.

두 보고서가 원본 판·독립성·제품 미실행의 한계를 정직하게 기록한 것은 유지할 장점이다.
하지만 P2 발견 없음 두 건으로, 아직 직접 제시하지 않은 공유 계약과 장애별 전이까지 닫혔다고
판정할 수는 없었다. **최종 보고에는 어떤 계약을 완결 근거로 확인했는지가 필요했다.**

현재 execution 상단의 정정과 E4는 이 문제를 드러낸다. 과거 기록을 삭제하거나 내용이 바뀌지 않았다는
이유로 옛 PASS를 되살리지 않는다. 보고서 작성 완료와 설계 결함 해결도 별개다.

### 9.1 다음 리뷰의 역할 분배

두 명 모두 동일 고정 설계 전체와 전체 범위를 읽는다. 한 명은 **프로토콜·원본 호환·권한·자원**을,
다른 한 명은 **수명·장애·복구·저장 원자성**을 주검토 축으로 맡는다. 이는 반씩 읽게 하는 분업이 아니다.
공통 경계는 양쪽에서 확인하되 서로 다른 질문과 구체 산출물로 검토한다.

최초 보고는 peer 판정 전 고정한다. 설계 작성자·조언자를 독립 최종 2명으로 세지 않는 현재 원칙은 유지한다.
일부 좁은 목록 대조는 Terra/medium으로 맡길 수 있지만, 의미·소유권·완료 판정은 Astra/high가 책임진다.
리뷰어 수를 무조건 늘리거나 같은 질문을 PASS가 나올 때까지 반복하는 방식을 해결책으로 삼지 않는다.

### 9.2 engine-only를 빠뜨리지 않는 장애 분해표

아래는 **검토 질문 목록**이다. 003의 새 복구 동작을 이 보고서에서 확정한 표가 아니다.

| 입력 사건 | 살아 있는 주체를 명시 | 반드시 설명할 결과 |
|---|---|---|
| engine만 종료 | B/X/M, 별도 PTY | 새 engine의 기동 권위·요청, old scope 확인, pair/generation, PTY/credit, readiness |
| X만 종료 | B/M, engine·PTY 상태 별도 확인 | 실제 자식 수명과 정리, 권위 차단, 다음 세대 허용 조건 |
| B만 종료 | X/M/store 및 작업 상태 | 기존 writer와 실행 처리, 새 B의 권위, 불명 결과와 복구 경계 |
| M 연속성 상실 | B/X와 container 상태 | 이전 lifecycle operation 정리, durable 기록, cold recovery 조건 |
| container/init 종료 | VM B/store/M | 종료 확인, 데이터 보존, 새 generation과 접속 준비 |
| transport 한쪽만 단절 | B/X/M/engine 생존 | pair 전체 전환, continuity, replay/credit와 중복 금지 |

행별로 정본의 전제→허용 주체→입력→영속 기록→실제 효과→실패/불명→회복 조건을 연결한다.
정확한 참조 없이 여러 행에 동일한 “cold recovery” 링크만 넣는 것으로 끝내지 않는다.
미지원 경로는 그 사실과 사용자에게 관찰되는 결과·후속 조치를 명시한다.

### 9.3 사후 설명에 그치지 않게 확인하는 방법

1. **고정 r1을 알려진 결함 사례로 보존한다.** 후속 검토 양식을 r1에 적용하면 F1/F2에 필요한 칸이
   비어 있거나 서로 다른 구현 선택을 허용한다는 점을 드러내야 한다. 이것은 알려진 사례의 민감도 확인이며
   새로운 결함 탐지 능력이나 선행 리뷰 당시의 준수를 입증하지 않는다.
2. **새 설계에서 같은 질문을 답한다.** F1의 양방향 계약과 F2의 engine-only 전이를 실제 정본 위치로
   채운다. “구현 때 결정”이라는 답으로 닫지 않는다. 적절히 이월할 내부 선택/실행 증거는 남겨 둔다.
3. **인접 반례도 확인한다.** 예를 들어 B 생존·engine 종료 직전에 승인 응답 결과가 유실된 경우,
   pair 전환 중 오래된 CREDIT/ACK가 도착한 경우, 엔진 종료에도 별도 PTY가 생존한 경우를 확인한다.
   전부 새 요구로 추가하는 것이 아니라 기존 세대·단발 효과·자원 계약의 적용을 대조한다.
4. **발견 수보다 근거를 평가한다.** 문제가 없는 새 설계에서 억지 finding을 만들 필요는 없다.
   오류가 있는 r1에서의 검출과 수정판에서의 계약 설명을 구분해 기록한다. 이 절차의 성능 수치는 아직 없다.

## 10. 다음 리뷰에 전달할 요청문 초안

아래는 앞으로 사용할 수 있는 초안이며 선행 요청문의 복원본이 아니다.

> 같은 고정 spec/설계 전체를 읽고 의미의 정합성과 계약의 완전성을 구분해 검토한다.
> 설계 밖 실행 증거가 없다는 사실과, 중요한 공유 계약이 아직 정해지지 않은 사실을 구분한다.
> 다른 검토자의 발견·판정을 받기 전에 최초 보고를 고정한다. 과거 PASS는 판단 근거로 쓰지 않는다.
>
> 공통 계약은 송신자와 수신자의 입력/결과/오류/허용 상태를 문서만으로 대조한다.
> 순서·권한·복구를 새로 결정해야 하면, 정확한 문서 공백과 서로 다른 두 해석의 결과를 보고한다.
> AC8은 engine-only, X-only, B-only, M 연속성 상실, container/init 상실, transport-only로 나누어
> 각 사건에서 살아 있는 주체·새 기동 권위·실제 종료 증거·generation/pair/cursor·PTY/credit·readiness를 확인한다.
>
> 공유 계약/권한 결정, 배치에서 채울 값, 내부 구현 선택, 실행으로 입증할 성질을 구분해 이월한다.
> 필요한 계약은 문장·표·도식 중 적절한 표현이면 된다. UML 종류·내부 클래스 전수 목록은 요구하지 않는다.
> 발견 없음은 읽은 범위와 실제 대조한 시나리오를 한정해 표현한다. 문서만으로 검증하지 못한 부분을 적는다.
> 본인의 주검토 축과 공통 전체 범위, 실제 읽은 지침, 접근/출력 한계를 기록한다.

## 11. 이번 작업의 결과·한계·남은 일

이번 작업은 원인 분석 보고서와 조사 증거를 저장하고 기존 execution에 포인터를 추가하는 문서 작업이다.
F1/F2 설계 수정, UML 추가, 예방 정책 변경·설치, 제품 구현·실행은 하지 않았다.
선행 B/C 보고서, frozen packet, 역사적 closure를 보존했다.

root는 보고서 작성·기록 대조를 수행했다. 별도 새 원인 분석 에이전트 생성은 thread limit으로 실패하여,
앞서 F1/F2를 발견한 `/root/design_completeness_audit`에 후속 보조 분석을 요청했다.
그 에이전트는 B/C 보고서 전체를 읽고 원인·반증·예방안을 반환했다. **새 독립 최종 리뷰로 세지 않는다.**
이번 분석은 해당 리뷰어들의 자기 해명이나 숨은 추론을 수집한 결과도 아니다.
같은 에이전트의 초안 사실 대조에서 engine 재기동 금지로 오해될 표현 1개를 지적받아,
실제 규칙인 “종료 확인 전 새 실행권 금지”로 바로잡았다. 나머지는 해당 사실 대조 범위에서 추가 지적이 없었다.

보존·링크·입력 대조의 최종 결과는 E10에 기록한다. 운영 checkout과 기존 WIP를 수정하거나
일괄 stage/commit하지 않는다. 파일 접근과 Git diff 확인은 문서 무결성의 근거이며 설계 수정 완료의 근거가 아니다.

남은 일은 F1/F2의 설계 보완, 필요한 도식의 계약 연결, 제안한 검토 방식의 실제 적용 및 수정판 재리뷰다.
그 결과가 나오기 전 현재 설계의 상태는 **design revision required**를 유지한다.

이 사건에서 배울 핵심은 **같은 판을 두 명이 독립적으로 읽었다는 절차와, 그 판으로 중요한 동작을
추측 없이 구현할 수 있다는 품질 판정을 따로 입증해야 한다**는 것이다.
