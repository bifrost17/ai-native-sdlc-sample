# 보완 설계 제안 검토

2026-09-14. 검토 대상은 이 폴더의 `README.md`와 `analysis.md` 현재 초안이다.
이 검토자는 앞서 기존 지침의 충분성 요구와 보완 위치 분석에 참여했다. 따라서 설계에 관여하지 않은
독립 최종 리뷰가 아니라, 별도 에이전트 문맥에서 수행한 제안 검토다. 활성 템플릿·제품·inputs 원문은 수정하지 않았다.

## 검토 범위와 결론

설계/구현 검토의 분리, 절차 부담, 조건부 검토, 후속 평가 계획을 읽었다. 현재 선택형의 PROCESS,
REVIEW, design-spec/design-depth, feedback, 공통 verifier 및 OpenCode/Codex verifier의 입력 전제와 대조했다.
외부 제품의 선행 리뷰·감사 원문을 이번 검토에서 다시 검증하지 않았다. 사건 사실의 최종 검증은 root의 분석 범위다.

기존 spec 인계에서 REVIEW 기준을 적용하고 feedback/verifier를 명시적인 설계 검토 범위에서도
사용할 수 있게 하는 연결은 적절하다. 현재 `tdd-optional/project/docs/PROCESS.md`의 spec 행(31행)은
작성·사람 검토를 연결하지만, REVIEW 링크는 구현·검증 행(33행)에 있다. 따라서 충분성 기준을
verifier에만 추가하는 것보다 제안의 PROCESS/design-spec 연결이 적용 시점을 명확히 한다.

README 28–36, 50–51, 105–106행은 작은 설계의 기존 작성·사람 검토, 중요한 계약의 새 문맥 검토
우선 활용, 설계 범위의 입력, 실제 실행 및 사람 수락을 구분한다. 여섯 자산의 변경도 상세 기준의
전면 복제가 아니라 역할별 연결로 제한한다면 별도 단계나 상시 독립 게이트를 만드는 과잉은 아니다.

## 발견 1 — 후속 평가에 두 검토 범위의 의무 구분을 명시할 필요

- 근거: README 36행은 기존 구현 완료 fresh verifier 의무를 유지한다고 정한다. 118–119행은
  feedback/verifier의 적용 사건과 입력 범위를 확장한다. 그러나 140–161행의 네 평가 요청은 모두
  직접 요청한 설계 검토이며, 163–164행의 정적 확인에는 이 의무 구분을 판정할 항목이 명시되어 있지 않다.
- 영향: 네 설계 리뷰가 통과해도 실제 구현 완료에 design-only 예외를 잘못 적용하거나, 앞선 설계
  PASS로 구현 완료 fresh 검토를 갈음하는 변경까지 검증됐다고 볼 수 없다. 이는 제안된 원칙의 모순이
  아니라 그 원칙이 배포판·adapter에 보존됐는지 확인하는 평가 범위의 공백이다.
- 권고: 기존 정적/adapter 검토에 다음 의미 확인을 명시한다. 설계만의 검토는 존재하지 않는
  plan/diff/시험을 요구하지 않으며 상시 새 에이전트 호출 의무가 아니다. 구현 완료 범위에서는 기존
  fresh 검토와 결과 대기 의무가 유지되며 설계 PASS가 이를 대신하지 않는다. 혼합 작업의 범위는
  작성자가 붙인 이름보다 실제 완료 주장과 변경 내용으로 판단한다.
- 비용 경계: 새 검사기·모델 호출·제품 실행을 추가할 필요는 없다. 기존 두 배포판과 제공 adapter의
  변경 대조에 포함하면 된다. 네 호출은 직접 요청한 설계 리뷰의 적용 관측이며, 자연 선택·자동 진입의
  실행 근거가 아니라는 현재 155–161행의 제한을 유지한다.

## 남는 한계

이 문서 검토는 보완 절차를 실제로 실행하거나 효과를 입증한 것이 아니다. 설치·adapter 적용,
부분 평가·제품 실행은 수행하지 않았다. 초기 제안에 기여한 검토자의 재검토라는 한계를 유지하며,
외부 제품 F1/F2의 수정·수락 또는 활성 지침 반영을 승인하지 않는다. 그 밖에 검토한 범위에서
설계/구현 분리를 깨거나 새로운 보편적 인원·도식·승인 의무를 만드는 중요한 추가 문제는 발견하지 못했다.
