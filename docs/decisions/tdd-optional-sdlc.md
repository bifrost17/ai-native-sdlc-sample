# TDD 선택형 SDLC 설계

설계일: 2026-09-12. 출발판: `e6b16db`. 대상: `tdd-optional/`.
사용자의 요청은 플레이북을 북극성으로 유지하며 조사에 근거해 TDD를 필수로 강제하지 않는 SDLC를 설계하는 것이다.
기본형은 보존하고, 선택형 초판에 있던 방식 선택을 실제 판단·작성·검토에 사용할 수 있게 구체화한다.

**핵심 결정은 원하는 동작과 판단 근거를 먼저 정하되, 테스트 코드의 작성 시점은 작업별로 선택하는 것이다.**
완료 판단은 선택한 방법의 이름이 아니라 요구 충족·회귀 보호·실제 실행과 사람의 검토에 둔다.

## 근거를 읽고 내린 판단

주보고서뿐 아니라 방법론, 에이전트 논문 11건의 카드, 사람 연구 5건, 공개 실험·커뮤니티 자료,
정책·실행 기록을 구분한 프로젝트 조사, 기존 비판 검토를 읽었다. 설계에 중요한 플레이북 문단과
A5의 실제 비교 조건은 보관한 원문으로 다시 대조했다. 새 비교 실험이나 최신 자료 전수조사를 한 것은 아니다.

| 근거 | 이 설계에 사용하는 의미 | 적용하지 않는 해석 |
|---|---|---|
| [TENET 등 선행 정보 연구](../research/tdd-vs-test-after/working/agent-studies.md#a1-tenet--가장-유용한-테스트-사용-시점-비교) | 기존 계약과 테스트에서 배울 수 있는 정보를 구현 전에 읽는다. | 기존 인간 테스트의 정보 효과를 새 테스트의 엄격한 작성 순서 효과로 바꾸지 않음 |
| [A5 구현 노출 연구](../research/tdd-vs-test-after/working/agent-studies.md#a5-구현을-본-테스트의-오류-전파), [원문 추출](../research/tdd-vs-test-after/originals/studies-agent/2607.05139.pdf.txt) | 정답의 출처·구현 노출·검토 문맥을 구별한다. 구현 뒤에도 요구사항만 주는 별도 시험 생성은 가능하다. | 새 에이전트·다른 모델·최종 리뷰만으로 오류가 제거된다고 보장하지 않음 |

| [TDAD·새 테스트 생성 연구](../research/tdd-vs-test-after/working/agent-studies.md) | 관련 기존 시험의 범위를 확인하고 빈 곳을 보강한다. 새 테스트의 개수 자체를 목표로 삼지 않는다. | 새 테스트는 쓸모없다거나 기존 시험 통과만으로 새 요구가 충족됐다고 하지 않음 |
| [사람 연구](../research/tdd-vs-test-after/human-studies.md) | 순서·주기 크기·테스트 노력·숙련도 차이를 고려하는 배경 근거로 쓴다. | 사람의 시간·결함 수치를 에이전트의 효과로 외삽하지 않음 |
| [프로젝트 정책과 공개 이력](../research/tdd-vs-test-after/README.md#유명-프로젝트의-정책과-관찰-사례) | 회귀 시험의 판별력, 재현 기록과 작성 순서를 별도로 다룬다. | 72건에서 TDD 사용률을 추정하거나 같은 커밋을 구현 후 테스트의 증거로 세지 않음 |

이 자료는 조건부 선택제를 설계하기에 충분하다. 추가 검색으로 보안·이행의 최적 순서, 전략 전환의
고정 횟수, 전체 개발비용 절감률이 이미 입증된 것처럼 보충하지 않는다. 그러한 강한 주장을 하려면
해당 조건의 별도 근거가 필요하다. 지금은 위험에 근거한 설계 판단과 남은 불확실성으로 표시한다.

정독 중 A5 카드의 한 문장을 정밀화했다. 원문 599–618행은 코드 생성 대화를 유지한 시험 생성과
요구사항만 제공하는 새 대화를 실제 비교한다. 따라서 ‘직접 검증되지 않았다’는 한계는 후자의
존재가 아니라 전체 제품 개발·최종 독립 리뷰의 효과로 일반화하는 데 붙여야 한다. 원문은 수정하지 않았다.

## 플레이북을 유지하는 부분과 조정하는 부분

주석은 당시 소스와 실행의 평가다. 아래 설계 근거가 과거의 ‘충실’ 판정이나 새 선택형의 실행 성공을
자동으로 승계하지는 않는다. 링크의 V 번호는 제작본의 주석 식별자이며 원문의 절차 이름과 구별한다.

| 북극성의 요구·처방 | 선택형의 적용 |
|---|---|
| [V2-02·V2-11](../verification/north-star-playbook.html#V2-11): 제안자가 의도를 확인·교정 | 사람의 문제·범위·성공 의미를 intent에서 확인한다. 테스트 방식으로 업무 결정을 대신하지 않는다. |
| [V3-09~12](../verification/north-star-playbook.html#V3-09): spec 대조, 질문·정책 우려, 사람 판단 | 관측 가능한 요구·설계·AC를 spec에 둔다. 중요한 미결 계약은 의존 구현에 앞서 해결한다. |
| [V4-06~09](../verification/north-star-playbook.html#V4-06): 파일·순서·증명, 위험·대안, 대화 없이 실행할 수 있는 plan | 기존 네 절에 방식·이유·독립 기대·구체 순서를 담고 사람이 계획을 검토한다. |
| [V4-11](../verification/north-star-playbook.html#V4-11): 이탈한 plan은 관련 구현과 같은 commit에서 갱신 | 방식 변경도 이유·검증 영향과 함께 plan에 반영한다. 별도 상태 장부는 만들지 않는다. |
| [V8-01·02·06](../verification/north-star-playbook.html#V8-01): 작업 중 피드백·새 문맥의 최종 확인·명확한 목표 | 구현 후 테스트도 동작별로 확인한다. 작업 중 실행과 최종 리뷰를 구분한다. |
| [V8-07](../verification/north-star-playbook.html#V8-07): 버그의 실패 시험 선작성·실패 확인·시험 commit·시험을 바꾸지 않는 수정 | **의도적 조정.** 버그에도 TDD 선택을 허용한다. 재현을 권장하고 실제 순서·회귀 근거·한계를 남긴다. 별도 시험 commit을 보편 의무로 추가하지 않는다. |
| [V8-10·12](../verification/north-star-playbook.html#V8-10): 수정 중 시험 편집 보호 | **의도적 조정.** 새 시험 추가·근거 있는 정정은 허용하되 실패를 숨기는 완화는 금지한다. 프로젝트가 채택한 실제 보호 경계는 그대로 따른다. |
| [V8-09·13](../verification/north-star-playbook.html#V8-13): 완료 전 검사·toolchain 원문 근거 | 실행한 코드판·명령·결과를 남긴다. 통과·실패·미실행·검토 진행 중을 구분한다. |
| [V10-04](../verification/north-star-playbook.html#V10-04): 팀의 관리형 리뷰·CI 선택; [V10-05](../verification/north-star-playbook.html#V10-05): Bugs/Security/spec·plan 대조; [V10-06](../verification/north-star-playbook.html#V10-06): 사람의 승인 | 방식 자체에 감점하지 않고 계약·회귀·정책·기록의 실제 불일치를 검토한다. 자동 검토는 사람의 승인이 아니다. |
| [V12-08·09](../verification/north-star-playbook.html#V12-08), [V13-09·10](../verification/north-star-playbook.html#V13-09): 공개 권한·복구·운영 진단 환류 | 통합·배포·일반 공개를 구분하고 운영 증거를 다음 의도로 넘긴다. |

플레이북에서 모든 새 기능·순수 리팩터링에 엄격한 RGR을 의무화한 것은 확인되지 않았다.
현재 제작본의 618행 주석도 일반 TDD를 팀의 선택으로 구분한다. 반면 버그 수정의 구체적 처방은
원문에 명시돼 있으므로, 선택형을 그 부분까지 문자적으로 동일한 구현이라고 부르지 않는다.
사용자가 요청한 선택 정책으로 조정하며, 그 조정의 효과가 원문 절차와 동등하다는 실험적 주장도 하지 않는다.

## 전체 SDLC에서의 책임과 인계

| 단계 | 정할 것·실행할 것 | 다음 단계에 남기는 것 |
|---|---|---|
| Intent | 누구의 어떤 문제인지, 범위·제약·성공의 의미를 사람과 확인 | 문제와 확인 근거, 미결 질문·결정자 |
| Spec / design | 요구·보존 계약·중요한 실패·정책·AC를 정의. 구현 출력을 정답으로 사용하지 않음 | 관측할 기대와 출처, 설계 선택·대안·의존 문서, 사람의 수락 판 |
| Plan | 현재 코드·시험·도구를 읽고 작업 순서와 방식·이유·검증을 정함 | 실제 변경 경로, 선행 계약, PR·통합 관계, 위험과 Proof |
| 구현·피드백 | 선택한 단위마다 구현과 검증을 진행. 발견에 따라 근거·문서를 갱신 | 코드·필요한 시험·영향 문서와 실제 결과 |
| 최종 확인·리뷰 | 독립 기준과 최신 spec·plan·diff·검증 근거를 대조 | 발견·보완·재검증, 미실행과 남은 판단 |
| 통합·공개 | 최신 결합 결과를 확인하고 지정된 사람이 통합·공개 결정 | 실제 통합 판, 노출 상태, 중단·복구와 남은 범위 |
| 운영·학습 | 제품 이상과 에이전트의 반복 오해를 구별해 대응 | 제품 회귀 또는 지침·예시·에이전트 평가의 개선 근거 |

단계별 승인·초안 작업의 기존 허용·GitHub Flow·공개 제어 정책을 유지한다. 검사 통과나 방식 선택이
수락 권한을 만들지 않는다. 이미 허용된 기술 선택은 자율적으로 진행하고 중요한 업무·정책 결정만
기존 담당자에게 돌린다. 새 질문지·상태 전이·의무 문서나 작업당 PR을 추가하지 않는다.

## 구현 순서를 선택하는 설계

선택은 테스트 작성 순서 하나로 모든 활동을 분류하는 규칙이 아니다. TDD와 구현 후 테스트는 새
시험의 시점을 다루고, 기존 시험 활용은 회귀 근거의 재사용을 다룬다. 혼합은 이들을 동작별로 결합한다.
각 선택에는 관련 AC·독립 기대·검증 방법이 따라야 한다.

명확한 버그·계산 경계에는 TDD가 자연스러운 후보다. 안정된 기능은 TDD와 동작별 구현 후 테스트
모두 가능하다. 동작 보존 리팩터링은 기존 시험의 범위를 먼저 읽고 충분한 부분을 재사용한다.
인증·이행에는 권한 행렬·원자성·실패/복구 같은 위험의 검증을 강화하되 특정 작성 순서를 자동 지정하지 않는다.
이 조건별 권고는 위험에 근거한 적용 판단이며 해당 작업 유형의 비교효과 연구 결과가 아니다.

새 가이드 [TESTING-STRATEGY](../../tdd-optional/project/docs/TESTING-STRATEGY.md)는 선택 기준의 정본이다.
policy는 적용 원칙, plan은 이번 작업의 구체 결정, 실행 기록은 관측 결과, REVIEW는 대조 기준을 맡는다.
같은 상세 판단표를 각 스킬·양식에 반복하지 않는다.

## 탐색과 제품 완료의 경계

불확실성이 큰 UI·기술 가능성은 질문·제약·관찰 방법을 정해 조사하거나 허용된 작은 prototype으로
확인한다. 탐색은 고정된 AC를 발명하거나 모든 테스트를 먼저 쓰는 단계가 아니다. 무엇을 배웠는지,
무엇을 버릴지, 무엇이 아직 결정되지 않았는지를 남긴다. 코드를 시도한다면 그 실험 범위가 허용돼 있어야 한다.
초기 계획 작성 중 제품 코드를 바꾸는 행위와, 별도로 허용된 탐색 작업을 구분한다.

제품에 편입할 동작은 안정된 spec·plan과 필요한 제품 검증으로 연결한다. “화면을 봤다”는 관찰과
상태 전환·권한·데이터 변경의 검증은 다르다. 탐색 질문에 답했다는 성공을 제품 기능 완료로 바꾸지 않는다.
그 반대로 폐기할 조사에 출시용 CI·영구 테스트 세트·전체 배포 절차를 일괄 요구하지도 않는다.

## 독립 기준·검토·시험 정정

기대값은 구현과 다른 근거에서 나온다. 그래도 요구 해석·기준 데이터가 틀릴 수 있으므로 근거와
중요한 가정을 검토한다. 구현·시험을 같은 모델이 만들었는지보다 무엇을 기준으로 검증했는지 본다.
독립 계산·외부 적합성 사례·실제 부정 사례·신뢰할 수 있는 기준과의 대조 중 위험에 맞는 방법을 쓴다.
모든 변경에 여러 모델·전체 mutation testing·새 테스트 작성을 강제하지 않는다.

새 문맥의 리뷰는 구현자의 설명을 그대로 믿지 않고 기준 문서·현재 diff·시험·결과를 읽는 역할이다.
이는 A5의 구현 비노출 시험 생성과 다르다. 둘 중 하나를 수행했다고 다른 하나의 실증 효과를
승계하지 않는다. 선택 설치 팀 스킬의 fresh verifier 규칙은 유지하며 제품 전체의 특정 도구 의무로 확대하지 않는다.

시험이 잘못됐다는 주장은 구현과 불일치한다는 사실만으로 성립하지 않는다. 요구·독립 근거·오류를
제시하고 필요한 독립 검토와 기존 사람 결정을 따른다. 정당한 계약 변경·fixture 정정·종료된 공개
단계의 시험 정리와, 실패를 가리는 삭제·완화를 구분한다. 남아 있는 회귀는 보존한다.

사후 시험의 안전한 기준판 재생은 원래 결함을 잡는지 확인하는 선택지다. 운영 부수 효과나 사용자
작업을 손상시키며 재현하지 않는다. 재생 불가·환경 차이·비결정성이 있으면 다른 근거와 한계를 남긴다.
이 결과를 과거 RED 실행·TDD 준수로 소급하지 않는다.

## 전략과 문서를 바꾸는 시점

계약의 변경, 재현·자동화의 제약, 새로 드러난 회귀 공백, 반복 실패의 원인과 검사 비용을 알게 되면
선택을 다시 검토한다. 이유와 새 검증을 plan에 넣고 다음 의존 작업 전에 필요한 설계를 갱신한다.
선택 변경만으로 재승인을 요구하지 않으며 계약·권한 변경은 기존 절차를 따른다.
횟수·시간·LOC에 따른 자동 전환 규칙이나 실패를 무시하는 종료 규칙을 만들지 않는다.

효율을 논할 때는 최초 구현 시간과 검증·수리·사람 검토까지 끝난 시간을 구분한다. 알려진 API 비용,
재시도·중단·미측정 비용을 구별한다. 이 설계는 비용 측정 체계를 제품마다 새로 설치하도록 요구하지 않는다.

## 문서에 반영하는 범위

| 위치 | 역할 |
|---|---|
| `tdd-optional/project/docs/TESTING-STRATEGY.md` | 실무 선택·독립 기대·탐색·실행·완료의 판단 가이드 |
| 선택형 PROJECT-POLICY·CLAUDE·PROCESS·REVIEW | 가이드와 연결하고 단계별 판단·기존 책임 구조 유지 |
| 선택형 plan 양식·계획 작성 스킬·참조 | 작업별 방식·이유·기대 출처·검증과 선행 탐색을 표현 |
| 선택형 spec 작성 스킬 | 기존 AC 작성에 기대의 출처·모호한 계약 해결을 연결. 공통 intent/spec 양식은 유지 |
| 짧은 리팩터링·탐색 계획 예시 | 기존 시험 활용과 학습/제품 편입의 구분을 구체화 |
| 선택형 feedback·두 verifier·provenance | 실제 관찰·탐색 경계·기준 독립성의 검토와 역사적 TDD 문구의 범위 명확화 |
| 선택형·루트 README | 설계·가이드·검증으로 안내. 기본형 본문과 설치는 유지 |

제품 가이드는 선택한 `project/` 안에서 읽힌다. 팀 스킬은 형제 제품 폴더를 필수로 요구하지 않으며,
자기 동봉 검증자와 기준으로 완결한다. 연구·이 설계서·검증 기록은 제작 저장소에 남긴다.
활성 스킬·훅·CI를 제품에 자동 설치하지 않는다.

## 설계 검증과 남는 범위

다음 사례에서 지침·계획·검증자가 같은 판단을 하는지 독립 검토한다. 이는 문서에 따른 판단 검토이며
실제 모델의 자연 호출·개발 성능·모든 프로젝트 성공을 입증하는 비교 실험이 아니다.

| 사례 | 설계가 허용·요구해야 할 판단 |
|---|---|
| 안정된 새 기능을 구현 후 테스트로 진행 | 별도 TDD 예외 승인 없이 독립 기대와 동작별 실행·회귀 근거를 계획 |
| 현재 시험으로 보호되는 순수 리팩터링 | 관련 계약의 검증 범위를 확인하고, 필요 없는 새 시험·RED를 강제하지 않음 |
| UI 탐색 중 요구가 바뀜 | 학습 결과와 제품 완료를 구분하고, 채택할 계약·계획·검증을 갱신 |
| 인증 실패를 정상 처리하도록 시험이 변경됨 | 구현과 일치해 통과하더라도 독립된 권한 계약에 위배되면 발견으로 보고 |
| 뒤늦게 회귀 시험을 추가한 버그 수정 | 현재 효과와 가능한 기준판 판별력 확인. 과거 TDD를 했다고 표시하지 않음 |
| TDD를 선택했지만 시험을 먼저 실행하지 않음 | 이탈을 정직하게 기록하고 필요한 증거·계획 보완. 무의미한 재구현을 요구하지 않음 |
| 실행 환경이나 verifier가 없음 | 미실행·자체 검토의 한계를 남기고 그 결과를 통과·독립 검토로 만들지 않음 |

링크·독립 채택·manifest/adapter와 기존 회귀는 로컬 도구로 확인하고, 문서의 의미와 과잉 의무는
별도 검토자가 확인한다. 구체 결과와 미검증 범위는 [이번 설계 검토 기록](../verification/variants/optional-sdlc-design.md)에 남긴다.
