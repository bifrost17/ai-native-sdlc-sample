# 0017 — 중요한 spec/plan 누락과 후속 요구 재검증

**이전 문서 갱신 누락은 중요한 실패다.** 코드·시험·README가 맞아도 합의한 요구·설계와 계획이
뒤처지면 다음 작업의 근거가 깨진다. [0016 후속 실행](0016-flow-pilot.md)의 HUMAN 리뷰 후 복구를
자발적 갱신 통과로 계산하지 않는다. 이전 실행과 복구 커밋 34c351b는 그대로 보존한다.

새 후보의 두 작은 사례에서는 문서 갱신을 따로 상기하지 않은 업무 대화에서 spec/plan을 갱신했다.
HUMAN(Codex root)은 **이번 조건의 문서 개정·인계를 통과**로 판단한다. 파일 출력 사례의 제품
결함은 별도로 발견·수정·회귀 검증했으며 처음부터 제품도 통과했던 것으로 바꾸지 않는다.

## 필요한 만큼만 바꾼 지침

북극성 V4-11은 구현이 계획에서 벗어나면 같은 commit에 plan.md를 갱신하도록 한다.
동기화 hook은 선택 사항이다. 이번에는 기존 네 문서의 안내만 보완했다.

| 문서 | 연결한 행동 |
|---|---|
| 사용판 CLAUDE.md | 후속 요청·리뷰·구현 중 합의가 바뀌면 해당 spec/plan을 읽고 필요한 갱신을 포함한다. 완료 전 합의·문서·diff·근거를 대조하며 누락이 있으면 미완료다. |
| 사용판 REVIEW.md | 시험이 통과해도 중요한 요구·수용 기준·계획 누락은 해결되지 않은 발견으로 남긴다. |
| 사용판 docs/PROCESS.md | 구현 단계의 산출물에 필요한 설계·계획 개정을 포함한다. |
| [Git 정책](../GIT-WORKFLOW.md) | 동작·설계·수용 기준은 spec, 구현 파일·순서·PR 경계·검증은 plan에 반영한다. 새 수락 판을 먼저 고정하고 하위 참조를 잇는다. 개정 plan과 이유는 구현과 같은 커밋에 담는다. |

후보는 `codex/use-template-0017@add296d3875fb5555b583fdb5fce9ca4696b424c`다.
80e9001 대비 **4파일, 14줄 추가/4줄 삭제**, 총 18개 사용 파일을 유지했다. Git 정책은 제작판과
사용판에서 바이트가 같다. 새 검사기·hook·CI·필수 스킬을 추가하지 않았다. 영향 없는 문서를
형식적으로 고치거나 이미 허용된 사소한 구현 판단을 다시 승인받도록 요구하지 않는다.

## 지침 전달도 확인했다

원래 실패 당시 지침 파일은 있었지만 자동 주입 원문이 모델에 전달됐는지는 보존 기록으로
확정할 수 없었다. 별도 명시적 읽기가 없다는 사실만으로 미전달이나 위반을 단정하지 않는다.
CLI의 `--restricted`가 CLAUDE.md를 끈다는 결론도 근거가 없었다. JSON 설정과 memory의 구분은
[공식 settings 설명](https://code.claude.com/docs/en/settings), 프로젝트 문서 로딩 계약은
[공식 SDK 설명](https://code.claude.com/docs/en/agent-sdk/claude-code-features)을 확인했다.

새 두 실행은 첫 온보딩에서 CLAUDE.md를 실제 읽도록 요청했고 **Bash cat의 성공 결과가 지침
파일 전문과 같음**을 확인했다. 이후 업무 요구·리뷰에서는 문서 갱신을 상기하지 않았다.
온보딩도 바뀌었으므로 결과를 개선 문구만의 인과 효과로 주장하지 않는다. 초기 감사의 Read 도구
전용 검사는 Bash 읽기를 놓쳤고, 실제 성공한 도구 결과와 파일을 대조하여 바로잡았다.

## 입력·고정 판·실제 대화

## 제품 결함을 숨기지 않고 확인한 회귀

R02의 최초 설계는 출력 파일 존재를 확인한 뒤 쓰므로 그 사이 생성된 동료 파일을 덮어쓸 수 있었다.
독립 재현에서도 rc0과 파일 유실이 관측됐다. HUMAN이 파일 보존 동작의 결함을 전달하자 AGENT는
배타적 생성으로 고치고 spec R9/Design과 plan도 함께 수정했다. 새 spec 수락 후 참조를 갱신했다.

HUMAN은 기존 시험이 놓친 결함의 회귀 시험도 요청했다. AGENT는 저장 직전 다른 작성자의 파일을
만드는 결정론적 시험을 추가했다. 실제 결함 변이에서는 `AssertionError: 0 != 2`로 실패했고,
복원 후 전체 시험은 통과했다. 이 마지막 시험 추가는 이미 합의한 R9와 계획의 검증을 구체화한
것이므로 spec/plan을 또 편집하지 않은 것을 중요한 누락으로 보지 않았다. 독립 verifier도 동의했다.
