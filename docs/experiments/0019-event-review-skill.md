# 0019 — 이벤트에 맞춰 사용하는 팀 스킬과 네이티브 검증자

별도 CLI를 기본 실행 경로로 삼는 대신, 설치 가능한 `sdlc-feedback` 스킬과 Claude Code의
`sdlc-verifier` 서브에이전트를 구성했다. 업무 대화는 주 개발 세션에 남긴다. 요구·설계 변경과
수락 시에는 영향받는 문서를 갱신하고, 관련 커밋에는 바뀐 계획과 구현을 함께 담는다. 완료나
중요한 변경 검토에는 새 문맥의 검증자를 사용한다. 사람의 결정·수락·병합 권한은 유지한다.

최종 설치 후보는 **`893b79e`, 플러그인 0.1.4**다. [설치/갱신 안내](../../org-skills/README.md),
[스킬](../../org-skills/skills/sdlc-feedback/SKILL.md),
[기본 검증자와 공통 기준](../../org-skills/agents/sdlc-verifier.md)을 함께 배포한다.
사용 템플릿 `codex/use-template-0017@add296d`에는 필수 스킬·실행 프로그램을 추가하지 않았다.
0018 CLI와 그 전용 검토 프롬프트는 별도 실험 경로로 보존하며 이 스킬에서 호출하지 않는다.

## 환경과 비교 조건

[v5 데이터](datasets/v5/manifest.json)는 F02 PR1 제품 `28b8fa8`과 기존 사용판을 합친
**`codex/experiment-base-0019@8dbf319f19fd8be2e006151867363b7867665bfb`**를 고정했다.
새 얕은 clone에서 작업 브랜치를 만들었다. 제작 이력·자료·oracle은 개발 저장소에 복사하지 않았다.
Codex가 [HUMAN 페르소나](PERSONA.md)를 맡고 실제 응답을 읽어 업무 결정과 수락을 전달했다.
Claude Code가 개발 AGENT를 맡았다. 고정된 대화 대본이나 답안 파일을 개발 세션에 넣지 않았다.

이 실험은 이미 수락된 PR1 이후의 **부분 실험**이다. 처음부터 intent/spec/plan을 작성한 전체
SDLC 재실행이나 호스티드 PR 실험이 아니다. E02의 문서 누락은 통제된 결함이며 자연 누락과 구분한다.

일반 구현은 medium, 중요한 합의 대조는 high, 단순 제목 정정은 low로 요청했다. 기본 검증자는
Opus/high다. 난도·영향·불확실성에 맞춰 선택했으며 높은 모델의 무오류를 가정하지 않았다.

사용자 범위 플러그인을 영구 설치·갱신하고 새 세션 init에서 판·Skill/Agent 목록을 확인했다.

확인했지만, 캐시의 독립 복사본으로 실행됐다고 주장하지 않는다. 실행 중 플러그인 원문은 바꾸지 않았다.

일반 `claude -p`와 `--resume`을 사용했다. 기록 도우미는 HUMAN 프롬프트를 stdin으로 전달하고
출력을 보존할 뿐, 검토 호출·자동 보완·채점을 하지 않는다. safe-mode나 제한 프로필은 쓰지 않았다.
기존 개인 스킬/agent 목록이 함께 노출됐으며 관련 없는 플러그인 두 개와 MCP·브라우저는 껐다.
셸 허용 목록 때문에 일부 조회가 거부된 기록도 남긴다. 이를 별도 보안 격리나 무제한 기본 환경으로
표현하지 않는다. 초기 거부를 보고 T4부터 필요한 해시·출력·Git 조회 명령을 허용했다.

0.1.3에는 프로젝트 정책을 직접 읽는 문장과 검토 결과를 기다린 뒤 완료를 보고하는 문장을 보완했다.

E02a는 같은 기준의 새 clone에 E01 T3의 코드·시험·README만 복사했다. spec/plan은 이전 판으로
남겨 JSON 계약이 빠진 상태에서 자연어로 커밋 준비와 브랜치 리뷰를 요청했다. 0.1.3의 주 세션은
Skill과 native Agent를 호출했고 양쪽 모두 현재 문서 누락을 발견했다. 그러나 호출자가 공통 기준
파일 경로를 전달하지 않았다. 검증자는 광범위한 파일 검색이 거부된 뒤 프로젝트 정책으로 검토했다.
**누락 발견은 성공, 공통 기준 전달은 실패**다. 읽기 전용 요청은 지켰다.

0.1.4는 이 실패에 새 규칙을 붙이지 않고 별도 기준 파일을 없앴다. 공통 기준을 native agent
본문에 넣고 주 스킬도 같은 부분을 읽는다. 검증자 전용 권한은 개발자에게 적용하지 않는다.
다른 프로젝트 검증자를 선택할 때에는 동등한 기준을 확인·인계한다. 두 실행에서 과거 객체 부재를
단정적으로 squash라고 표현한 것은 근거가 부족했다. 실제로는 얕은 복제이며, 새 실험에는 HUMAN이
기존 수락을 확인하여 승계했다는 사실을 전달했다.

E02b는 0.1.4와 같은 누락 상태를 또 다른 새 clone·세션
`421b4a77-c5f7-4228-8725-d399fc08c89a`에서 재검증했다. T1은 Skill을 먼저 읽지 않고 native
검증자를 직접 선택했다. 따라서 주 스킬 로드로 계산하지 않는다. 검증자는 정의에 포함된 기준으로
현재 문서·코드·정책·시험을 대조하고 JSON 요구 누락을 발견했다. 별도 기준 파일 검색은 없었다.

HUMAN은 그 발견을 보완하도록 응답했고, T2에서 주 개발 세션이 spec의 R5/R8·설계·AC9와 plan의
절차·위험·Proof·변경 이유를 갱신했다. 없는 새 SHA를 만들지 않고 수락을 기다렸다. HUMAN이 실제
개정 spec **`8b4395f0fcb17a48a64d93ed79dca1f18831d1e5`**를 읽고 커밋하여 수락한 뒤,
T3에서 **`f14c81133246c228a9fcf16e51a4f306e1f48912`**에 plan·구현·시험·README를 함께 담았다.
plan의 Upstream은 그 수락 SHA와 일치한다. T2/T3에 추가 Skill/Agent 호출은 없었고 주 세션이
갱신·자체 확인을 수행했다. 마지막 커밋에 대한 새 native 승인으로 쓰지 않는다. 최종 제품·문서는
별도 HUMAN/독립 verifier가 확인한다. 초기 plan의 실행 전 설명과 현재 실행 근거도 구분한다.

**HUMAN은 이벤트 기반 팀 구성의 관측 범위를 통과로 판정한다.** 자연 업무의 문서 개정,
별도 검증자의 현재 누락 발견, 주 세션의 복구·수락 인계·관련 커밋, 정상 질문/작은 정정에서
불필요한 작업을 피하는 흐름을 확인했다. 0.1.4의 주 Skill 자연 로드를 새로 관측한 것은 아니다.
동일한 description을 쓴 0.1.2/0.1.3의 Skill 호출과 0.1.4의 native Agent 선택을 각각 근거로 쓴다.
모든 이벤트의 매번 호출이나 검증 정확도를 입증한 것은 아니며, 중간 실패를 소급해 통과시키지 않는다.

## 최종 확인과 보존

E01/E02b 각각 제품 unittest 12개, 독립 CLI 16건, 원래 시험 5개/helper 2개의 AST와 fixture
SHA256 `c038196ad9f748e482a446e4025e4c6c0746b23942c39f5f457ad37dd9a53795` 보존을 확인했다.

조회 불변과 완료 뒤 집계 변경을 대조했다. 의미 판단을 하는 문서 검사기를 추가하지 않았다.

독립 verifier의 제작 검사 결과는 다음과 같다. 전체 출력과 네 부분 보고는 실험 raw에 보존한다.

```text

Ran 96 tests (1 skipped)
OK (skipped=1)
test_hooks: 28 passed, 0 failed
8 passed, 0 failed
PASS  managed-settings 키·훅 계약
```

위 첫 두 줄은 요약이며 원문 명령·출력은 `raw/verification/maker-check-final.txt`에 있다.
skip은 기존 macOS 파일시스템 조건부 시험이다. production hook의 승인 없는 입력은 기대대로
rc2/BLOCKED였다. plugin/marketplace strict validation, skill quick validation도 통과했다.
공통 기준·권한·모델·템플릿 경계와 설치 source/cache 파일 해시 일치를 독립 확인했다.

**1,168.59초**다. T3의 두 result를 중복 합산하지 않았다. CLI의 가격표 기준 추정치이며 구독
청구액·Codex 비용·사람의 검토 시간을 포함하지 않는다. 부수 Haiku 사용량도 원문에 남긴다.
