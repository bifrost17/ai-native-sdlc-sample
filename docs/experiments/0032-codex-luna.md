# 0032 — Codex Luna 대상 선택형 SDLC 실험 설계

2026-09-13. **상세 설계 완료·독립 리뷰 수용 / 설치·모델 실행 전.** 사용자가 요청한 것은 상세 실험 설계다.
이번 문서 작성 중 수행한 것은 저장소·공식 문서·설치된 CLI의 도움말과 모델 목록 조회다.
실제 Luna 호출, 스킬 설치, 제품 구현, 실험 통과 판정은 아직 하지 않았다.

## 목적과 판정의 기준

[북극성 플레이북](../verification/north-star-playbook.html)을 사람이 개입하는 실제 개발에서
대체로 따르는지 확인한다. Codex에 옮길 때 스킬을 발견하는 데 그치지 않고, 중요한 합의가
설계·계획·구현·검증·인도에 이어지는지가 목적이다. 완벽한 호출률이나 무오류 에이전트는 목표가 아니다.
새 의미 검사기·훅·자동 승인 시스템을 만드는 실험으로 확대하지 않는다.

최근 [0030 Sonnet 전체 실행](0030-optional-sonnet.md)은 문서 선행 갱신과 같은 커밋을 지켰지만
완료 검토를 두 번 놓쳐 HUMAN이 복구했다. [0031](0031-optional-feedback-adoption.md)은 선택형
팀 패키지0.1.3의 짧은 채택 안내를 추가한 뒤 JSON 부분 실행에서 문서 선행·스킬 본문·최신 native
검토·결과 대기를 관측했다. 이번에는 **같은 선택형0.1.3을 Codex에 맞춰 설치한 전체 개발 사슬**을 본다.
0031의 부분 성공을 전체 흐름 성공으로 미리 간주하지 않는다.

[0029 OpenCode](0029-optional-opencode.md)는0.1.1 전체 실행에서 D7 문서 갱신이 구현 뒤로 밀렸고,
0.1.2 부분 실행에서는 사람이 검증 방식을 명시한 뒤 선행 갱신을 관측했다. 이번 기록은
[0029–0030 비교](comparisons/0029-vs-0030.md)에 이어 같은 업무 계약·문서 시점·검토·회귀·HUMAN 복구를
나란히 비교한다. CLI·모델·설치판·명시 입력·전체/부분 범위가 달라 단일 변수 대조나 모델 순위로 해석하지 않는다.

질문은 네 가지다.

1. 현재 Codex CLI에서 팀 스킬·작성 예시·검증자와 프로젝트 지침을 의미 손실 없이 연결할 수 있는가?
2. Luna가 실제 질문과 사람의 수락을 거쳐 구체적인 spec/plan, 작은 PR 단위, 공동 공개 제어를 구성하는가?
3. 구현 후 새 업무 요구를 받으면 별도 문서 상기 없이 영향 spec/plan을 **다음 의존 시험·구현 주기 전**에
   고치고 관련 구현과 **같은 커밋**에 담는가? 문서 묶음의 연결 파일도 영향에 따라 포함한다.
4. 선택한 검증 방식에 맞는 독립 기대·회귀 검증을 수행하고, 완료 전 최신 범위를 검토해 그 결과를
   기다리는가? 검증자의 잘못된 의견도 현재 계약과 실제 증거로 판단하는가?

## 역할·모델과 실험 단위

| 역할 | 선택 | 책임과 제한 |
|---|---|---|
| HUMAN | 이 작업의 Codex root, [기존 페르소나](PERSONA.md) | 제품 오너·엔지니어 역할을 구별한다. 업무 결정, 산출물 리뷰, 독립 관측, 대상 SHA 수락과 로컬 merge를 맡는다. 구현 정답을 대신 쓰지 않는다 |
| 개발 AGENT | 별도 Codex CLI의 `gpt-5.6-luna`, `high` | 의도·설계·계획·코드·시험을 만들고 질문한다. 작은 Python 변경이지만 문서 개정과 검토 인계가 함께 필요해 high를 선택한다. 실행 중 임의 상향하지 않는다 |
| native 검증자 | Codex custom agent `sdlc-verifier`, `gpt-5.6-sol`, `high` | 현재 합의·문서 묶음·변경·회귀를 대조한다. 보고만 하고 구현·수락·merge하지 않는다. 교차 문서 판단의 중요도에 맞춘 선택이다 |

이는 **Luna 주도 개발 + Sol 독립 검토의 팀 워크플로 실험**이다. Luna 단독 성능이나 모델 간 순위
실험이 아니다. 초반부터 Luna-only/모델별 추론 수준의 조합을 모두 실행하지 않는다. 필요하면 이후
별도 조건으로 설계한다. 요청한 Luna가 실제로 실행되지 않으면 다른 모델로 바꿔 성공 처리하지 않는다.

개발자는 이 대화에서 fork한 앱 하위 에이전트 대신, 별도 제품 디렉터리의 **새 `codex exec` 세션**으로
시작한다. 제작·실험 정답이 든 현재 문맥을 전달하지 않기 위해서다. 다음 업무 대화는 관측한 동일
session ID로 resume한다. `--last`, 매 턴 새 세션, 자동 답변 대본을 사용하지 않는다.
개발 Luna의 native 검증자는 Codex 내부 하위 에이전트로 실행하며 root가 몰래 대신 리뷰한 것을
native 호출로 기록하지 않는다. 본 사례는 순차 두 PR가 적절하므로 병렬 구현 성공을 주장하지 않는다.

설계 시 확인한 CLI는 `0.153.4`이며 공개 모델 목록에 Luna와 Sol이 있다. 이는 실제 추론 실행의
증거가 아니다. 실행 당시 CLI·설정·요청 모델/effort·관측 모델/effort를 각각 저장한다. effort가
요청 설정으로만 확인되면 그 한계를 그대로 쓴다. [런타임 설계와 공식 근거](designs/codex-luna/runtime-and-evidence.md).

- HUMAN 자료: [human.json](datasets/v6/F04-release-json/human.json), 페르소나와 독립 observer.
  제품 디렉터리·개발자 세션에 전달하지 않는다. D7도 공개 시점 전에는 전달하지 않는다.

실행 직전 source tree와 파일 해시를 다시 고정한다. 다른 세션의 변경이 있으면 자동으로 최신 판을
섞지 않고 대상 판을 결정해 기록한다. 원래 표본 안에서 설치·스킬 본문을 몰래 수정하지 않는다.

설치는 먼저 **제품 실험 프로젝트 범위**로 한다. 사용자의 현재 전역 Codex 설정이나 기존 스킬을
덮어쓰지 않으면서 Git에 설치판을 보존할 수 있다. 설치 결과가 검증되면 Codex용 재사용 안내·어댑터를
템플릿 리포의 팀 패키지에 반영하는 후속 변경으로 다룬다. 이 설계에서 영구 사용자 설치는 하지 않는다.

```text
product/
  CLAUDE.md                     # 원래 선택형 프로젝트 지침
  AGENTS.md                     # Codex 진입: 위 지침 읽기 + 선택한 팀 절차 연결
  .agents/skills/
    <13 team skill folders>/    # SKILL.md뿐 아니라 scripts/references/assets 등 전체
    capture-intent/
    design-spec/
    plan/                       # 자체 작성 예시 3개, 원래 명시 사용 의미 보존
  .codex/agents/sdlc-verifier.toml
  .codex/config.toml            # 실험에 필요한 최소 모델·메모리·동시성 설정
  templates/, docs/, intent/, PROJECT-POLICY.md, REVIEW.md, ...
  tracker.py, tests/test_tracker.py, requests.json
```

Codex는 프로젝트 `.agents/skills`를 지원하며 custom agent는 `.codex/agents/*.toml`로 정의한다.
Claude의 plugin 명칭·도구 표현·agent frontmatter를 그대로 복사하지 않는다. 본문 판단 기준은 유지하고
플랫폼 경로·호출 표현만 변환한다. 변환 전후 diff와 전체 파일 manifest를 남긴다.
[공식 skills](https://learn.chatgpt.com/docs/build-skills),
[공식 subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

`AGENTS.md`는 `CLAUDE.md`·참조 정책을 먼저 읽도록 연결하고, 명시 채택한 sdlc-feedback의 이벤트 안내만
더한다. 문서 전문을 두 벌로 유지하지 않는다. 자동 주입 목록만 보고 성공 처리하지 않고 smoke에서
실제 지침 읽기를 확인한다. 이 연결이 불안정하면 본실험 전에 하나의 원문에서 만든 Codex용 사본으로
수정하고 설치 판을 새로 고정한다. 본실험 중 반복 프롬프트로 정책을 주입해 설치 결함을 가리지 않는다.

일반 제품 템플릿에는 특정 스킬 이름을 강제하지 않는다. 활성 스킬과 채택 안내는 순수 사용판에서
파생한 **선택 설치 seed에만** 넣는다. F04와 무관한 보험 예시 스킬·제작 리서치·과거 정답은 복사하지 않는다.
설치할16개 전체 이름·의존 경로·변환 범위는 [스킬 감사](designs/codex-luna/skill-portability-audit.md)에 둔다.

## 실행 순서와 한도

다음 표는 향후 실행 계획이다. 비용은 실제 CLI가 제공하는 사용량만 기록하며 API 단가로 계정 비용을
추정하지 않는다. 시간은 모델·검토자 대기를 포함한 실행 구간의 벽시계 시간이다. native 자식 호출은
root CLI 호출 수와 별도 집계한다. HUMAN은 대기 중에도 진행 상황을 확인하며 같은 결과를 재요청하지 않는다.

| 단계 | 범위와 입력 | 상한 | 다음 단계 조건 |
|---|---|---|---|
| P0 정적 준비 | 순수 사용판→설치 seed, 경로·frontmatter·참조·전역 오염·Git·기준 시험 확인 | 모델 호출0 | manifest·설정·접근 한계와 native 변환 근거 확정 |
| P1 가벼운 smoke | 별도 disposable 제품, 지침·스킬 명시 읽기·작은 편집/시험·native 호출/대기/종료·resume와 두 번째 fresh 검토 | root CLI 최대3회, 합계15분. 설치 오류 수정 후 새 세션 재시도1회까지, 두 시도 합계25분 | Luna 실제 실행, 기록 수집, 설치 body 전달, child 결과 대기·새 호출, 허용된 Git 경로가 관측되어야 함 |
| P2 본실험 r01 | 새 seed/새 Luna 세션, F04 전체, 두 PR·D7·새 복제본 인도 | root CLI 최대12회 또는60분 중 먼저 도달 | 핵심 기준 평가. 충분하면 즉시 종료 |
| P3 조건부 보완 | 중요한 실패를 1~2개로 묶어 원인 분류→최소 변경→새 seed·새 세션의 영향 범위 재실험 | 보완 묶음1회, 부분 최대3호출/25분. 전체 재실험이 필요하면 이를 대신해 최대12호출/60분 | 실패 재현 범위와 전체 제품 회귀를 통과하면 종료. 예산 내 미해결은 미해결로 남김 |

P1에서 알려준 스킬명·검토 요청·tiny 변경은 **명시 호출 기능 점검**이며 자연 사용이나 SDLC 전체
성공으로 세지 않는다. smoke 결과물·질문·기억을 P2에 전달하지 않는다. P1이 통과해도 본실험의
자발적 행동은 별도로 판정한다. 도구 제한으로 native를 실행하거나 결과를 관측할 수 없으면 플랫폼
준비 실패로 멈춘다. root의 별도 리뷰를 같은 조건의 대체 성공으로 취급하지 않는다.

P3의 부분 재실험은 **실패한 사건 직전의 제품 상태**에서 파생한다. D7 이후의 좁은 누락이면 r01에서
고정한 `pre-json` 상태를 수락/검토 범위와 함께 export하고 미래 JSON·복구·검토 정답의 refs/객체가
없는 새 설치 seed를 만든다. 과거 공개 기록이 남았다면 그 문맥 차이를 밝히고 무교육 사례로 해석하지 않는다.
최초 intent→spec→plan의 인계·초기 검증 방식 선택·PR 분할이 문제이거나 변경 영향이 전 사슬에
걸치면, 부분 표본 대신 최초 F04 baseline부터 전체 재실험을 선택한다. 두 재실험을 모두 실행하는 예산은 아니다.

비TDD가 전혀 선택되지 않더라도 TDD 선택은 허용된다. 그 경우 선택형의 비TDD 실행을 검증했다고
쓰지 않는다. 그 미관측을 보완할 필요가 있으면 P3 예산을 명시적 비TDD 업무 조각에 사용하며 자연
선택과 구분한다. 단순히 모든 방식·스킬을 한 번씩 채우기 위한 추가 표본은 만들지 않는다.

## HUMAN이 진행할 실제 대화

고정된 문장 순서가 아니라 관측할 사건과 업무 결정만 고정한다. root는 표의 질문을 대신 만들어
개발자에게 정답 목록을 제공하지 않는다. 실제 질문에 관련 사실을 답하고 제안·문서를 리뷰한다.
단계 수락은 읽은 artifact SHA·이유·권한 범위로 남기며 이미 위임한 작업을 다시 허가받게 하지 않는다.

| 사건 | HUMAN 행동 | 관측점 |
|---|---|---|
| 시작 | 공개 문제 카드의 사내 담당자 조회·주간 집계 불편과 작은 로컬 CLI 범위만 전달 | 기존 제품·프로젝트 지침 탐색, 필요한 질문, intent의 목표/범위 |
| 의도·설계 협의 | D1–D6 중 관련 질문에 답한다. 잘못된 가정이 문서에 있으면 구현 전에 바로잡는다 | 정확 owner/빈 결과/null, 출력·부작용·공개 계약, 작은 문제에 맞는 구체성 |
| 계획 수락 | 실제 파일·작업 순서·독립 기대·검증 방식·PR 묶음과 공개 전환을 읽는다 | 두 관련 PR를 합친 하나의 일반 공개 단위, 얇은 설정과 독립 테스트 가능성 |
| PR1 목록 | 제출 diff·시험·검토를 읽고 OFF의 기존 흐름/ON의 부분 기능을 관측한 뒤 대상 SHA 수락·merge | 작은 검토 단위, 최신 main 통합, 일반 사용자에게 미완성 기능 숨김 |

PR1/PR2는 기존 F04와 비교할 기본 계획이다. Luna가 다른 합리적인 묶음을 제안하면 업무 가치와
의존성을 먼저 검토한다. 비교 조건상 두 인도가 필요하면 그 이유를 설명해 합의하고 HUMAN의
유도를 기록한다. 임의로 구현 분할이 자발적이었다고 쓰지 않는다. 문서마다 브랜치를 만들지 않는다.

D7의 계약 본문은0030/0031과 유지한다. 기존 prompt의 “20개 테스트”는 과거 실행 사실이므로
이번에 그대로 재생하지 않는다. 도입부는 “상태 요약의 최초 구현과 테스트 결과를 확인했습니다”로
작성하고 실제 관측 수는 별도 기록한다. 나머지는 정확 세 정수 키 `all/open/done`, 기본 텍스트,
owner·빈 결과·파일 불변·공동 OFF/ON 유지, 파일 출력 불필요라는 동일 요구다. 실제 전송문과
과거 prompt의 차이를 저장한다. 숨겨진 D7을 PR2 계획이나 초기 payload에 섞지 않는다.

최초 완료 제출에서 중요한 문서/검토 누락이 보이면 **먼저 원래 결과를 고정**한 뒤 실제 업무
영향으로 피드백한다. 피드백이 “문서를 갱신해 달라”처럼 직접 상기한 경우도 숨기지 않는다.
같은 세션에서 복구한 결과와 새 실험의 자발적 수행은 별개다. 맞는 결과가 나올 때까지 같은
prompt를 무한히 반복하거나 통과한 시도만 남기지 않는다.

## 평가표와 증거의 우선순위

숫자 합계로 통과시키지 않는다. 제품 결과와 프로세스 판정을 나란히 기록하고 HUMAN이 근거를 읽는다.
**관측된 중요한 spec/plan 누락·늦은 갱신은 시험이 모두 통과해도 자연 수행 실패**다. 현재 문서가
정확한데 시간 순서 로그가 없다면 실패를 꾸며내지 않고 순서 미검증으로 남긴다.

| 항목 | 다시 확인할 근거 | 북극성 연결 |
|---|---|---|
| 업무·설계·계획 인계 | 의도와 확인된 결정, 구체 구조/동작/계약, 실제 파일·작업·검증, 수락 SHA. 불필요한 다이어그램 수는 채점하지 않음 | 2–4장, V4-11 |
| 변경 문서 동기화 **핵심** | D7 공개→영향 spec/연결 문서·plan의 성공한 쓰기→다음 의존 시험·구현 사건, 해당 commit의 문서+코드+시험. 최종 diff만으로 선후 관계 추정 금지 | V4-11 |
| 선택형 검증 | plan의 방식·이유·독립 기대·실제 순서. TDD 선택 조각만 의미 있는 RED→GREEN 요구, 비TDD에 가짜 RED/예외 승인 요구 금지 | 4·8·9장, 선택형 정책 |

| 최신 검토와 대기 | developer가 인계한 base/현재 합의/diff, native child ID·현재 파일/실행 결과·반환, 그 뒤 parent 완료. 검토 뒤 의미 있는 변경이 있으면 그 범위의 새 확인 | V7-08/09, V8-02 |

회귀는0030/0031의 독립 observer 계약을 재사용한다. 실제 gate 이름 등 합의한 매개변수만 연결하고
기대값을 구현 출력에서 만들지 않는다. 기존55명령/9판정은 과거 구성 수이며 이번 실행 수·테스트 수를
미리 맞출 합격 기준이 아니다. 변경·통합·fresh 결과와 종료 코드를 실제로 기록한다.
v6 원본의 TDD 관측 문구는 보존하되 이번 선택형에서 자동 필수 조건으로 해석하지 않는다.

상태는 항목별 `자연 수행`, `HUMAN 피드백 후 복구`, `실패`, `미검증`, `해당 없음`으로 적는다.
전체 결론에는 “제품 수락 가능”과 “관측 범위에서 절차 목표 달성”을 분리한다. 중요한 절차 실패를
복구한 실행은 그대로 보존하며, 그 실패를 겨냥한 새 실행이 통과했을 때만 보완 효과로 기록한다.

변하지 않은 플레이북 원문·고정 양식 설명·역할 원칙을 매 실행 다시 읽혀 채점하지 않는다.
첫 Codex 전환에서 지침 로딩·스킬 경로·검토 권한·기록 방식은 새 조건이므로 재평가한다.
이후에는 변경 영향과 주요 인계·전체 제품 회귀를 확인한다. 실제 조직 승인, hosted PR/CI,
운영 배포, 장기 운영, 완전한 도구 권한 차단은 이 로컬 실험에서 미관측이다.

출력만 보충한다. CLI 스키마에 없는 모델/선후 관계를 요약문으로 만들어 넣지 않는다.

실험 종료 시 bundle verify, refs와 원본/정제본 manifest, 최초 실패와 최종 결과를 확인한다.
maker의 문서 색인에는 방법·판정·근거 링크만 합치고 제품 코드는 실험 refs에 둔다.
북극성 주석은 **실제 통과한 범위만** 업데이트한다. 이 설계만으로 Codex 실증 주석을 추가하지 않는다.

## 보완 분류와 종료

- **설치·플랫폼 문제:** skills 경로/본문 전달, tool 이름, native 로드, resume/logging 등의 문제다.
  adapter만 먼저 고치고 smoke를 새 세션에서 확인한다. 본문 SDLC 방법론 결함과 구분한다.
- **템플릿/팀 지침 공백:** 여러 산출물 사이에 필요한 연결이 빠졌고 기존 규칙으로 해소되지 않는
  중요한 문제다. 북극성 해당 절을 다시 읽고 가장 작은 안내·예시 변경을 선택한다.
- **에이전트 수행 실수:** 충분한 지침을 놓치거나 검토가 잘못 판단했다. 원래 관측을 보존하고
  사람이 피드백한다. 모든 실수마다 정책·체커를 추가하지 않는다.
- **실험 설계/증거 문제:** 미래 요구 유출, 잘못된 oracle, 과거 수치 강요, 세션/모델 확인 불가다.
  오염·미검증으로 표시하고 필요한 경우 새 표본을 만든다. 제품이나 방법론 실패로 전가하지 않는다.

핵심 문서 동기화와 제품 회귀·인도가 확보되고 주요 인계가 대체로 작동하면 끝낸다. 사소한 표현,
관계없는 스킬, 의미 없는 추가 RED 때문에 반복하지 않는다. 같은 중요한 실패가 보완 후에도 남거나
예산이 끝나면 한계·다음 제안을 남긴다. 이번 설계의 결과물은 이 문서와 설치 감사·공식 근거·독립 리뷰이며,
아직 실험 통과나 활성 Codex 배포판을 의미하지 않는다.

북극성을 대조하면서0030/0031의 native 검토 주석 두 문단이 plan 양식 예시인 V4-12 아래에
