## 전체 프로세스와 부분 검증

전체 프로세스 실행은 문제 제기부터 intent, spec, plan, 구현·시험, 리뷰·수락, 로컬 인도와 사용 확인,
유지보수 인계까지 한 개발 사슬을 진행한다. 여섯 단계는 필요에 따라 되돌아갈 수 있다.
이 데이터에는 운영 서비스가 없으므로 배포는 새 임시 디렉터리에서 CLI를 인도·실행하는 수준이며,
유지보수는 확인된 사용 결과의 분류와 남은 질문 인계까지다. 새 사고를 꾸며내거나 프로덕션 운영을
검증했다고 쓰지 않는다. 실제 결함이 발견되면 관측한 사실로 후속 사슬을 열거나 범위 밖으로 기록한다.

정규식·채점기·단일 spec 같은 부분 검증은 임시 작업 공간에서 수행할 수 있다. 매번 전체 프로세스
브랜치를 만들 필요는 없다. 기록에는 `partial`과 검사한 단계를 쓰며 전체 개발 사슬 완료와 구분한다.

## 목표 수준과 반복 개선

통과는 플레이북을 완벽하게 재현했다는 뜻이 아니다. 사람이 개입하는 개발에서 주요 흐름이
대체로 잘 작동하고, 요구한 결과를 얻었으며, 중요한 회귀가 남지 않았다고 HUMAN(Codex root)이
근거를 읽고 판단한 상태다. 사소한 표현 차이, 적절한 단계 생략, 선택하지 않은 스킬은 실패가 아니다.
운영 환경이 없는 항목은 미관측으로 남긴다. 템플릿을 비대하게 만드는 검증 장치보다 간결한 안내,
예시와 인계를 먼저 개선하고 에이전트의 해결 방식에 재량을 둔다.

합의한 중요한 요구·설계 변경이 spec/plan에 빠진 채 인도되면 **중요한 실패**다. 코드와 시험이
통과해도 문서를 이어받는 다음 작업의 근거가 깨진다. HUMAN이 누락을 지적해 복구한 기록은
복구의 증거이며 그 실행의 자발적 갱신 실패를 통과로 바꾸지 않는다. 재실험에서는 업무 변경과
필요한 수락·커밋만 전달하고 문서 갱신을 따로 상기하지 않았는지 공개 대화로 확인한다.

북극성 주석에서 실제 흐름에 영향이 큰 보완 2~3개를 골라 한 묶음으로 시험한다. 적용한 템플릿 판과
원래 판을 보존하고, 관측된 실패에는 HUMAN이 동작·기대·영향으로 피드백한다. 필요한 부분을 고친 뒤
재실험하며 통과한 범위만 주석에 근거와 함께 반영한다. 예산 내에 통과하지 못하면 미완료로 남긴다.

회귀 범위는 전체 흐름을 덮되 매번 모든 문단을 모델에 보내지 않는다. 첫 실행에는 챕터 2~13의 항목을
아래처럼 사람이 분류하고, 다음 실행은 변경 diff와 새 관측에 따라 그 분류를 갱신한다. 별도 평가
프로그램을 만들지 않고 실행 기록의 작은 표를 사용한다.

- **이번 실행에서 다시 볼 것:** 바뀐 안내·정책·스킬의 항목과 연결된 앞뒤 단계, 지난 실패·미결 항목.
- **매번 볼 전체 흐름:** 의도·질문 → 설계·정책 → 계획 → 구현·회귀 시험·리뷰 → 인도·피드백에서
  중요한 인계가 끊기지 않았는지, 범위와 사실이 보존됐는지, 사람의 판단과 실제 검증이 남았는지.
- **고정 가이드 재사용:** 변경되지 않은 설명·역할 원칙·양식·측정법은 원문/참조 파일의 변경 여부와
  기존 근거만 확인한다. 영향이 없으면 이전 판정을 재사용하고 제외 사유와 근거 판을 기록한다.
  참조가 바뀌거나 새 관측과 모순되면 다시 평가한다. 관련 설정·데이터·페르소나·모델 조건도 확인하며,
  `CLAUDE.md`나 세션 설정 변경은 인용문이 같아도 행동에 영향을 줄 수 있다.
- **이번 환경에서 미관측:** 실제 조직 승인·호스티드 CI·배포·운영·장기 지표 등은 통과로 계산하지 않는다.
  필요성은 남기되 이를 채우기 위한 기능을 작은 템플릿에 억지로 추가하지 않는다.

관련 자동 시험은 전체 실행하되, 그 통과를 전체 플레이북의 실증으로 확대하지 않는다. 중요한 회귀가
있으면 새 개선만 좋다는 이유로 통과시키지 않는다. 동일 데이터 반복은 피드백 후 확인이고 독립적인
성공률 표본은 아니다. 새로운 사례는 별도 실행으로 구분한다.

## 기준과 작업 공간

`main`에는 방법·버전별 데이터·실행 색인·정제된 템플릿 개선 근거를 둔다. 제품 코드, 생성된
intent/spec/plan, 공개된 대화와 실행 출력은 실험 통합 브랜치와 그 단계 브랜치에 둔다.
데이터의 `baseline/` 코드는 작은 초기 상태를 재현하는 입력이며 이 제작 저장소의 제품 소스가 아니다.

원래 전체 실행의 기준 tree는 **`codex/use-template@a2bbfe1bdc00152c9c063a764d1e32667ce2e2b4`**다.
후속 실행은 아래 실행 색인의 사용 후보와 해당 데이터 manifest를 따라 시작 판을 고정한다.
이 tree는 제작 자료·자동 로드 스킬·플러그인을 제외한 16개 파일이다. 선택적 자체 제작 예시는
`examples/`에 있고 자동 로드되지 않는다. 이 커밋의 부모는 제작 커밋 `c9e5747`이므로 사용 브랜치
자체의 Git 이력까지 제거됐다고 말하지 않는다. 실험 복제본에서 아래 방식으로 이력 노출을 제한한다.
브랜치 이름만 저장하지 말고 시작 시 해시와 파일 목록을 기록한다. 기준 해시는 실행마다 확인하며,
아직 확정하지 않았다면 `unresolved`로 남긴다. 이 문서를 쓴 `main`의 기준은 `c9e5747`이다.
사용 브랜치를 갱신한 후에도 진행 중인 실행의 기준은 바꾸지 않는다.

HUMAN은 제작 저장소에서 데이터와 판단 근거를 읽고, AGENT는 별도 복제본에서 작업한다.
로컬 저장소를 복제할 때도 사용 tree만 전달한다. `--depth 1 --single-branch --branch codex/use-template
--no-local`을 사용한 새 복제본에서 기준 해시와 shallow 경계를 확인한다. 위 고정 커밋이 더 이상
브랜치 tip이 아니면 전체 이력을 받아 해결하지 말고 고정된 tree의 별도 얕은 복제/스냅샷을 준비하고
원본 해시를 기록한다. AGENT 복제본에서 제작 부모 커밋과 `main` ref가 조회되지 않는지 확인한다.
단순 worktree는 다른 브랜치와 Git 객체를 공유하므로 비공개 사실을 숨기는 경계로 취급하지 않는다.
복제 후 AGENT에게 보이는 ref·이력·작업 디렉터리를 확인하고 그 결과를 남긴다.

HUMAN만 `human.json`을 읽는다. AGENT 작업 공간에는 선택한 사례의 `public.json`, 데이터 fixture,
manifest에 열거된 baseline 파일만 복사한다. 파일별 원본 경로와 해시, 복사 결과를 기록한다.
`human.json`, 테스트 oracle, 제작 자료, 다른 사례의 결과는 복사하지 않는다. 도구의 작업 범위도
실험 복제본으로 맞춘다. 접근 범위를 제한할 수 없거나 비공개 사실이 유출됐다면 그 한계를 기록하고
오염된 실행을 깨끗한 실행처럼 비교하지 않는다.

공개 문제 카드에는 질문 대본이나 비공개 결정의 질문 목록을 넣지 않는다. AGENT가 문제와 기존
동작에서 필요한 질문을 찾게 하고, 이미 공개된 질문을 반복한 것을 질문 발견의 근거로 세지 않는다.
HUMAN의 비공개 읽기·oracle 명령·미공개 기대값은 진행 중인 AGENT 복제본 밖의 HUMAN 전용 기록에
둔다. 실험 브랜치에는 공개된 대화와 관측 출력, AGENT 산출물·정제한 도구 기록만 넣는다.
HUMAN 전용 기록의 위치와 제한은 실행 색인에 남긴다.

## 스킬과 환경을 먼저 기록한다

기본 실행은 팀 제공 스킬을 선택하지 않은 조건이다. 스킬을 시험하려는 실행만 오너가 명시적으로
선택한 자체 제작 예시 또는 별도로 제공된 팀 스킬을 추가한다. 특정 스킬 이름은 필수가 아니다.
예시를 선택하면 본문의 출처·판·자체 제작 근거와 설치 위치를 기록한다. 예시 폴더가 있다는 사실을
자동 로드·적용의 증거로 삼지 않는다.

제작 환경에 영구 설치된 사용자 플러그인은 별도 사용 브랜치에서도 로드될 수 있다. 따라서 실행 전에
CLI 판, 사용자·프로젝트·관리 설정, 로컬/사용자 스킬, 설치 플러그인, MCP와 자동 실행 hook을 조사한다.
설치 목록은 `claude plugin list --json`, 지원 인자는 해당 설치의 `claude --help`로 확인할 수 있다.
계정·토큰 값은 기록하지 않는다.

사용자 설정을 빼는 `--setting-sources project,local`은 가능한 구성 요소 하나다. 이것만으로 사용자 스킬,
관리 설정, 플러그인이 모두 제거됐다고 가정하지 않는다. 필요하면 분리된 설정 프로필을 사용하고
**실제 세션에 제공된 스킬·플러그인 목록**을 선택 목록과 대조한다. 선택하지 않은 제작 스킬이 로드됐다면
원인을 없앤 새 세션으로 다시 시작하거나 해당 실행을 환경 오염으로 표시한다. 개인의 영구 설치를
임의로 지우지 않는다. `--safe-mode`는 프로젝트 지침까지 끄므로 템플릿 적용 실험의 기본값으로 쓰지 않는다.

지침 파일의 존재와 실제 내용 전달은 구분한다. 자동 주입 여부를 직접 관측할 수 없다면
온보딩에서 프로젝트 지침을 읽게 하고 성공한 도구 결과를 보존할 수 있다. 이전 실행과 온보딩
조건도 바뀌었다면 개선 문구만의 효과로 해석하지 않는다. 자동 주입 원문이 로그에 없다는 이유만으로
미전달을 단정하거나, 특정 도구 이름만 검사해 다른 방식의 성공한 읽기를 놓치지 않는다.

## 브랜치와 단계 수락

0016 이후 GitHub Flow 실험에서는 제품 복제본의 `main`과 짧은 PR 단위 작업 브랜치를 사용한다.
계획에서 실제 업무 가치·의존성·검증을 보고 PR 묶음과 순서를 정하며 단계마다 브랜치나 PR을
만들지 않는다. 한 기능의 구현·관련 시험·설명을 함께 검토할 수 있다. 단계 수락은 해당 문서의
커밋 SHA와 HUMAN의 결정·이유를 보존하고 최종 구현 PR 머지와 구분한다.

기존 GitHub 제작 저장소를 쓸 경우 제품의 `main`은 원격의 전용 실험 통합 브랜치에 대응시킨다.
PR의 실제 base/head를 기록하고 제작 저장소의 원격 `main`을 실험 통합 대상으로 쓰지 않는다.
단일 계정의 모의 HUMAN 리뷰·merge는 실제 조직의 서로 다른 사람 간 승인 검증이 아니다.
GitHub PR 객체·댓글·merge를 실제로 실행했는지, 로컬 Git만 실행했는지, 누가 Git/PR 작업을
수행했는지 구분한다. 실험 종료 시 완료 브랜치를 먼저 로컬 기록 refs에 보존한 뒤 원격 작업
브랜치를 정리할 수 있다. 고정된 기준·결과·대화·검증은 지우지 않는다.

각 통합 후에는 기존 동작과 새 동작을 확인한다. 선행 변경을 반영한 최신 통합 상태에서 남은
PR을 검증하고, 마지막에는 인도와 필요한 복구 대조를 한다. 순차 작업이 적절했다면 실행하지 않은
병렬 세션을 검증했다고 쓰지 않는다. 아래는 F01-r01까지 사용한 **역사적 단계 브랜치 방식**이며,
기존 실행의 재현과 단계별 부분 실험을 위한 기록으로 보존한다.

HUMAN이 실험 복제본에 `experiment/<date>-<case>-<run>` 통합 브랜치를 만든다. 시작 전 AGENT가
baseline 시험을 실행하고 HUMAN이 입력 상태와 출력, 복사된 파일을 확인한다.
단계 브랜치는 통합 브랜치의 마지막 수락 커밋에서 갈라 만든다.

| 단계 | 브랜치 접미사 예 | HUMAN이 읽는 증거 |
|---|---|---|
| 문제·의도 | `-intent` | 사용자 불편, 범위, 실제 질문·답, 미결 질문 |
| 요구·설계 | `-spec` | 구체적 수용 조건, 선택된 정책 적용, 충돌·오너 결정 |
| 구현 계획 | `-plan` | 파일·작업 순서·검증 방법·위험과 spec 연결 |
| 구현·시험·리뷰 | `-build` | 코드 diff, 재현·회귀·기존 시험, 실제 실행, 리뷰 발견 |
| 로컬 인도·인계 | `-handoff` | 새 디렉터리에서 실행, 사용 설명, 남은 제약·후속 문제 |

예를 들어 통합 브랜치가 `experiment/2026-09-10-f01-r01`이면 intent 브랜치는
`experiment/2026-09-10-f01-r01-intent`다. 통합 ref 아래에 `/intent`를 붙이지 않는다.

HUMAN은 실제 artifact를 읽고 수락·수정 요청·범위 변경 이유를 답한다. 수락한 단계 커밋만 통합
브랜치로 합치고 source/target/merge 해시와 실행한 Git 명령을 기록한다. 로컬 merge로 진행한 것은
실제 PR·조직 branch protection 검증과 구분한다. Claude가 스스로 수락자로 서명하지 않는다.
같은 파일의 `Status:` 값을 바꿔 승인을 흉내 내지 않는다. 형식 점검용 hook은 추가하지 않는다.

## 한 세션에서 실제로 대화한다

Codex root가 [HUMAN](PERSONA.md), Claude Code가 AGENT다. HUMAN은 고정된 순서의 문장을
재생하지 않는다. AGENT의 질문·제안·artifact·시험 결과를 보고 다음 행동을 고른다.
`public.json`의 문제 카드는 시작할 맥락이며 정해진 대화 대본이 아니다.

AGENT는 Sonnet, effort low로 시작한다. 요청한 별칭과 실제 관측 모델을 모두 기록한다.
한 개발 사슬 안에서는 같은 Claude 세션을 계속 사용한다. headless 호출을 이어야 한다면 실제
session ID와 `--resume <session-id>` 사용 여부를 기록하고 같은 실행 디렉터리·설정을 유지한다.
매 턴 새로운 세션을 만들고 연속 대화라고 쓰지 않는다. 재시작·context reset·모델 변경이 필요하면
이유, 이전 session 연결, 전달한 요약과 이후 관측 범위 변화를 남긴다.

각 HUMAN/AGENT 턴의 역할, 시각, 본문, 가리킨 artifact 커밋, 새로 공개한 사실/결정 ID를 남긴다.
도구 호출은 요청뿐 아니라 성공·실패 결과를 함께 저장한다. 계정 정보·비밀·숨겨진 추론은 보존 대상이 아니다.
입력이 길어지면 HUMAN은 이미 합의된 사실을 요약할 수 있으나 새로운 답이나 구현 방법을 끼워 넣지 않는다.

첫 pilot 권장 한도는 **F01 한 건, 60분 또는 HUMAN 턴 12회 중 먼저 도달하는 시점**이다.
AGENT의 한 응답에 포함된 도구 호출 수를 HUMAN 턴으로 세지 않는다. 조사 없이 이 한도가 적절하다고
단정하지 않는다. 실행 전 오너가 바꿀 수 있고 도중 연장은 이유와 새 한도를 먼저 기록한다.
한도에 도달하면 현재 단계와 미완료 사항을 남긴다. 미완료를 수락이나 통과로 바꾸지 않는다.
wall time, 모델 응답 시간, 토큰·비용은 실제 제공된 값만 기록하며 없는 값은 `unknown`이다.

## 결과를 읽는 방법

제품 결과와 프로세스 관측을 분리한다. HUMAN의 oracle은 합의한 외부 동작을 검사하며 특정 구현이나
클래스 이름을 요구하지 않는다. 이미 합의한 결정을 바꾼 경우 기존 oracle을 조용히 고치지 않고
오너 결정과 새 기대값, 기준 결과도 함께 남긴다. 각 사례는 동일한 초기 상태에서 독립 실행한다.

스킬은 선택·가용 여부, 해당 단계에서의 적합성, 본문을 실제 읽은 성공 기록, 산출물에 적용된
구체적 제약을 따로 본다. 이름을 언급했거나 스킬 도구를 호출했다는 이유만으로 적용됐다고 보지 않는다.
해당 없는 스킬을 선택하지 않은 판단도 정상 대조다. 스킬 없는 기본 실행에 스킬 미사용 감점을 주지 않는다.

완료·실패·판정 불가·예산 중단·환경 오염을 구별한다. 단위 시험·LLM 채점은 HUMAN 리뷰의 근거이며
자기 승인 장치가 아니다. 세 사례의 작은 표본으로 전체 SDLC의 일반적 성공률을 주장하지 않는다.

종료 시 통합 브랜치에 `EXPERIMENT.md`, 공개된 턴 기록, `raw/`, artifact와 시험 결과를 보존하고 기준·최종
커밋을 고정한다. 원본을 실험 브랜치에서 지우거나 `main`으로 합치지 않는다. `main`의 실행 색인에는
case/판/seed, 기준·최종 해시, 브랜치, 범위, 결과, 근거 경로만 추가한다. 템플릿 개선은 별도 변경으로 다룬다.
