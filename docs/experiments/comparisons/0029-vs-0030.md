# 선택형 0.1.1/0.1.2 OpenCode와 0.1.2 Claude Sonnet: 0029–0030 비교

2026-09-12. [0029](../0029-optional-opencode.md)와
[0030](../0030-optional-sonnet.md)의 관측 비교다. 두 실행은 같은 F04 v6, seed 102와 제품 계약을
사용했지만 모델만 바꾼 대조 실험은 아니다. 목표도 무인 자동화나 완벽한 하네스가 아니라 HUMAN이
함께할 때 중요한 흐름을 대체로 잘 따르는지 확인하는 것이다.

0029의 전체 사슬은 선택형 패키지 0.1.1에서 수행했고, 0.1.2는 JSON 후속 요구 부분만 새 세션으로
재시험했다. 0030은 source `4bb463d7ee900e9ec687f400474aabbcb948b839`의 선택형 패키지 0.1.2로
전체 사슬을 수행했다. CLI, 모델, 요청한 effort, 플러그인 전달 방식, 전체/부분 범위, 누적 대화 문맥,
HUMAN 피드백도 함께 다르다. 따라서 아래 결과로 모델 순위, TDD의 인과 효과, 패키지 버전 하나의 효과,
성공률을 주장하지 않는다.

## 선택형에서 본 방법 선택

0030은 대부분의 새 동작에 **구현 후 테스트**, 파일을 읽기 전에 게이트가 거부해야 하는 R6에만
**TDD**를 선택했다. 이 선택은 HUMAN이 특정 방법을 먼저 지정한 결과가 아니며, 위험과 검증 필요에 따라
혼합한 정상적인 선택형 동작이다. 다만 최초 plan의 단계 설명은 선택과 모순됐고 HUMAN이 구현 전에
보정했다.

보정 뒤 PR1의 R6에서는 인자 파싱을 위한 최소 scaffold 다음 자동 시험을 작성했다. 게이트가 없어
파일 읽기 오류가 먼저 나오는 의미 있는 RED를 관측하고, 게이트를 파일 읽기 앞으로 옮긴 뒤 같은 시험의
GREEN을 확인했다. 나머지 PR1 동작은 제품 변경 뒤 여덟 시험을 한 묶음으로 추가했다. PR2도 여섯 개의
개별 주기가 아니라 게이트 배관과 집중 시험, 이어서 요약 구현과 여섯 시험을 더한 **두 개의 응집된 묶음**이었다.
따라서 0030은 자연스러운 혼합 적용의 근거지만, 모든 비R6 동작을 하나씩 구현·시험한 근거는 아니다.

0029도 0.1.1 전체 실행에서 새 동작 TDD와 기존 회귀 활용을 섞어 선택했다. 0.1.2 부분 재시험은 HUMAN이
구현 후 테스트를 명시했으므로 자연 선택 사례가 아니다. 두 실행 모두 non-TDD 자체를 실패로 처리하지
않았고, 선택한 방식의 이유·독립 기대·실제 순서를 평가했다. 이 관찰은 TDD나 구현 후 테스트 중 하나가
보편적으로 우월하다는 결론을 지지하지 않는다.

## D7 후속 요구와 인계

0030의 07 프롬프트는 `summary --json`이라는 업무 계약만 전달했고 파일명, 스킬, 문서 순서, 시험 전략,
검토자를 알려주지 않았다. 공개 사건은 영향 spec 수정 → plan 수정 → 제품 수정 → 시험 추가 → 전체25시험
통과였고, 해당 문서·코드·시험은 `79745ab` 한 커밋에 들어갔다. 0029의 0.1.1 전체 실행에서 같은 D7의
spec 갱신이 구현 뒤로 밀린 것과 대비되는 강한 통과 사례다.

그러나 0030은 07 끝에서 최신 독립 검토를 다시 빠뜨렸다. HUMAN이 08에서 이를 요구했고, 같은 요청에서
PR2 실행 기록의 과장도 정정하게 했다. 최종 native 검토는 JSON 포함 최신 변경을 실제로 검토했지만,
이 성공은 HUMAN 상기 뒤의 복구다. 문서 선행 성공 하나를 전체 인계의 자율 성공으로 확대하지 않는다.

## 스킬과 native 검토의 실제 사용

0030 init에는 프로젝트 작성 예시3개와 팀 스킬13개, 합계16개가 등록됐다. 실제 본문 사용이 확인된 것은
`spec-policy-pass` 호출과 그 과정에서 읽은 `data-compliance`, `brand`뿐이다. `capture-intent`,
`design-spec`, `plan` 작성 스킬과 설치된 `tdd` 본문의 실제 호출·읽기는 확인되지 않았다. 산출물이 그
형식을 따랐다는 사실만으로 본문 사용을 소급하지 않는다. 설치16개를 사용16개나 스킬 전체 통과로 세지
않는다.

native verifier는 05·06·08에서 각각 실제 Agent 호출·완료와 Sonnet 5 child event가 확인됐다. 05와08은
HUMAN이 누락을 지적한 뒤 수행했고, 06은 같은 누적 세션이 05의 상기를 이미 받은 상태에서 수행했다.
따라서 06은 문맥 내 학습된 개선으로 기록하되, 새 문맥의 무힌트 활성화 근거로 부르지 않는다. 요청한
medium 설정은 보존돼 있지만 medium이라는 추론 강도가 실제로 적용됐는지를 별도 계측한 결과는 없다.

0029도 설치·발견 수와 실제 관련 본문 사용을 구별했다. 두 실행에서 공통으로 확인한 것은 완결된 선택
패키지와 native 검토자가 CLI에 전달될 수 있다는 점이다. 모든 설치 스킬의 자연어 활성화, 모든 본문의
적용 정확도, 어떤 모델에서든 같은 결과가 난다는 보편성은 확인하지 않았다.

## 현재 판단

0030 r02는 **사람과 함께 중요한 선택형 흐름을 대체로 수행한 범위의 통과**다. 자연스러운 혼합 전략,
R6의 진짜 RED→GREEN, D7의 무힌트 spec→plan→code→test와 같은 커밋, 25시험 및 55명령·9판정 통과,
실제 Sonnet 5 native 검토가 이를 지지한다. 동시에 첫 plan 모순, 정책 스킬 오독, 최신 검토 누락 두 번,
PR2 실행 기록 과장은 HUMAN 개입 없이 해결되지 않았다.

HUMAN의 최종 provenance·상태 정정 `d073279`는 `git diff/show`만으로 한 커밋 내부의 시간 순서를
증명할 수 없고 공개 event가 그 순서를 증명한다는 경계를 확정했다. 로컬 통합 main `9a187f8`과 fresh
디렉터리는 각각 전체25시험과 55명령·9판정이 통과했고 제품·fresh 작업트리도 깨끗했다. 이는 로컬 합성
인도 근거이며 hosted PR/CI, 실제 회사 공개·운영 배포 근거는 아니다.

0030에서는 선택형 템플릿을 추가로 수정하지 않는다. 발견한 오류마다 정책·검사기를 늘리지 않는 고정
원칙을 유지하고, 이번 실행은 source `4bb463d`의 행동과 HUMAN 복구를 있는 그대로 보존한다. 개별
계획·기록 오류는 HUMAN 검토로 복구됐으므로 source patch 사유로 삼지 않는다. 다만 최신 변경 뒤 native
검토를 04와07에서 반복해 빠뜨린 활성화 공백은 별도의 좁은 후속 관찰 후보로 남긴다. 이 공백 때문에
0030을 자율 전체 통과로 부르지는 않는다.
