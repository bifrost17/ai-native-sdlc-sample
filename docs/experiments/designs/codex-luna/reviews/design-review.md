# Codex Luna 실험 설계 독립 리뷰

2026-09-13. 리뷰어는 설계 검토용 Astra/xhigh 하위 에이전트다. 제품 개발 Luna나 native 검증자 Sol의
실행 결과가 아니다. 읽기·정적 대조와 이 리뷰 파일 작성만 수행했고, 스킬 설치·제품 구현·Codex 모델
개발 실험·Git commit은 하지 않았다. 최초 발견과 수정본 재확인을 함께 남긴다.

  쓰기 순서를 요구하는 규칙은 아니다. 같은 commit만으로 시간 순서를 증명하지 않는다는 기준도 있다.

  native 동작을 확인한 것이 아니다.

## 최초 중요 발견과 최소 수정

### R1. native verifier를 만드는 지시가 두 종류였다 — 수정 확인

초기 스킬 감사의 「최소 Codex adapter」는 `team-resources/agents/sdlc-verifier.md`에 원문을 두고
TOML에는 그것을 읽으라는 wrapper만 넣으며 전문을 중복 복사하지 말라고 했다. 같은 시점 런타임
「P0: native verifier 변환」은 TOML의 `developer_instructions`에 전문을 직접 넣도록 했다.
원래 sdlc-feedback은 개발자도 Review criteria를 읽게 하므로, 이는 단순한 문서 표현 차이가 아니라
설치 산출물과 개발자/검증자의 기준 전달 경로가 달라지는 문제였다.

최소 수정은 한 경로를 선택해 설치 tree·skill 링크·native 본문·manifest를 모두 맞추는 것이다.
수정본은 `.codex/agents/sdlc-verifier.toml`에 원문의 기준을 직접 넣고 개발자도 그 안의 criteria를
참조하도록 통일했다. 감사의 adapter 4·6항과 런타임 TOML 예시는 일치한다. `sandbox_mode`도 둘 다
`workspace-write`를 명시하고, 보고 전용은 지침과 전후 관측의 조건이며 기술적인 쓰기 차단으로
과장하지 않는다. 원문 source/hash와 변환 diff를 별도로 보존하는 선택은 타당하다.

### R2. 작성 스킬의 P2 명시 호출이 자연 사용 관측과 충돌했다 — 수정 확인

초기 감사는 `capture-intent`, `design-spec`, `plan`을 HUMAN이 본실험 초기 단계마다 명시 선택하게 했다.
본 설계는 업무 대화로 진행하고 명시 기능 점검과 본실험을 분리했다. 그대로 실행하면 P2의 작성
행동에 서로 다른 개입이 들어가고, 어느 수준의 자연 사용을 측정했는지 일관되게 설명하기 어려웠다.

수정본은 원래 explicit-only 정책을 유지하고 명시 기능 점검을 P1로 분리한다. P2의 명시 사용 부재를
실패로 세지 않으며, 파일·양식·예시를 실제 읽고 적용한 증거와 자연 skill invocation을 구별한다.
스킬 16개 전부를 호출시키는 정답표도 만들지 않는다. 기존 팀 정책의 의미를 바꾸지 않는 최소 수정이다.

### R3. 관측할 수 없는 effort와 불필요한 문서 순서가 gate가 됐다 — 수정 확인

초기 감사 평가표는 parent/child metadata의 `Luna/high`, `Sol/high`를 모델 gate로 요구했다.
반면 본 설계는 high가 요청·설정으로만 확인되면 내부 적용 미확인을 남기도록 했다. 또한 감사는
`spec→plan`을 고정 순서처럼 적었지만 본 설계와 원본 팀 스킬의 핵심은 영향받은 두 문서가 모두
다음 의존 검증·구현 주기 전에 현재화되는 것이다.

수정본은 실제 모델 관측과 high의 설정·내부 적용을 분리했고, 내부 effort metadata 부재만으로
설치 준비를 실패 처리하지 않는다. spec과 plan 사이 순서도 고정하지 않는다. 중요한 늦은 갱신은
실패, 역사적 순서 증거가 없는 경우는 미검증으로 나누는 본 설계와 일치한다.

### R4. `skills.config` 경로에 공식 자료 자체의 상충이 있었다 — 수정 확인

[공식 설정 참조 보존본](../evidence/config-reference.md)의 `skills.config.<index>.path`는 skill
folder라고 설명하지만 [skills 보존본](../evidence/skills.md)의 disable 예시는
`/path/to/skill/SKILL.md`를 사용한다. 초기 런타임은 folder path 하나를 확정했다. 실제 런타임이
다른 형식을 기대하면 설정을 파싱한 채 관련 전역 스킬이 남아 실험 조건이 달라질 수 있다.

수정본 런타임은 두 후보 중 현재 CLI의 실제 catalog에 비활성화가 반영되는 형식을 확인해 고정한다.
설정 parse나 파일 존재만으로 성공 처리하지 않으며, 남는 관련 스킬은 혼합 조건/오염으로 구분한다.
문서만으로 어느 쪽이 맞는지 추측하지 않는 최소한의 확인이다.

### R5. 동시 native 1개 제한에 완료 thread의 종료 절차가 빠졌다 — 수정 확인

[subagents 보존본](../evidence/subagents.md)의 제한 설명은 동시에 **열린** spawned thread 수다.
완료한 thread를 닫는 동작도 별도로 설명한다. 초기 P1은 한 차례 검토·반환·resume만 확인했다.
완료가 슬롯 해제를 뜻한다고 가정하면 PR1 다음의 PR2/D7 fresh 검토가 시작되지 않거나 이전 child를
재사용한 결과를 새 문맥 검토로 잘못 셀 여지가 있었다.

수정본 런타임은 반환·결과 보존 후 child를 닫고 이력을 유지하게 한다. P1은 같은 developer session의
후속 호출에서 두 번째 fresh native 검토와 서로 다른 child ID를 확인한다. 시작할 수 없으면 runtime
준비 실패이며 기존 child 재사용을 대체 성공으로 세지 않는다. 기존 최대 3 root 호출 안의 명시
smoke로 확인하고 검토 방법론은 바꾸지 않는 수정이다.

### R6. P3 부분 재실험의 시작 상태와 전체 재실험 전환 기준이 비어 있었다 — 수정 확인

초기 본 설계는 새 seed·새 세션·영향 범위 재실험을 규정했지만, D7 이후 좁은 실패의 seed가 어느
상태여야 하는지 정하지 않았다. 최종 JSON·복구·검토 결과가 든 seed에서 시작하면 관측할 변경을
건너뛰거나 답안을 전달한다. 초기 인계 실패까지 좁은 후속 변경으로 시험하면 보완 효과도 확인하기 어렵다.

수정본 「실행 순서와 한도」는 D7의 좁은 실패를 `pre-json` 사건 직전 상태에서 export하고 미래
객체를 제외하며, 초기 intent/spec/plan 인계·방식 선택·PR 분할 또는 전 사슬 영향이면 baseline부터
전체 재실험하게 했다. 부분과 전체를 모두 실행하는 예산으로 해석하지 않는다. 과거 공개 기록이
남는 경우 무교육/단일 원인 효과를 주장하지 않는 점도 0031의 비교 한계를 유지한다.

## 경미한 사항과 실행 때 확인할 한계

- 감사 「설치·발견 preflight」의 도입은 전체 목록을 추론 전 작업처럼 표현하지만 5·6항은 실제
  모델 pilot이다. 본 설계 P0=0회/P1 구분에 맞춰 정적 항목과 동적 smoke의 호출 예산을 명시하면 충분하다.
- `.codex/agents/...`는 제품 root 기준이다. 실제 설치된 sdlc-feedback의 Markdown 링크는 그 파일을
  기준으로 `../../../.codex/agents/sdlc-verifier.toml`이어야 한다. 원래 verifier 상대 링크를
  root 표기만으로 치환하지 말고 P0 링크 검사에서 실제 파일로 해석되는지 확인해야 한다.
- `prompt-input`의 실행 옵션과 출력은 본실험의 실제 launch 조건을 반영해야 한다. 현재 도움말은
  `exec`와 동일한 모든 인자를 보장하지 않으므로 debug 출력만으로 실제 exec 환경의 완전 격리를
  주장할 수 없다. 동명 스킬은 경로와 본문 선택을 확인하며, 관련 전역 도구가 남으면 조건을 공개한다.
- `workspace-write`, 별도 clone, 메모리 설정은 같은 OS 사용자의 모든 HUMAN 자료 읽기를 차단하지
  않는다. 설계가 명시한 입력/refs/객체 분리와 실제 접근 trace로 관측 범위만 판단해야 한다.
  관측된 유출은 제품/방법론 실패와 분리한다. 무접근 trace가 OS 차원의 접근 불가능을 증명하지는 않는다.
- 공개 event/target-session 보충 경로, native metadata, 종료·timeout 처리는 P1에서 확정할 사항이다.
  예산 소진으로 중단한 뒤에도 대상 child가 계속 실행되지 않도록 실행기가 소유한 session/process와
  파일 상태를 확인해야 한다. 이번 설계 리뷰에서 미구현 transport를 검증 완료로 판단하지 않는다.
- 설치 16개·source 59파일의 정적 수는 확인했지만 모든 스킬의 실제 동작을 시험한 것이 아니다.
  F04에 무관한 스킬의 오호출 가능성을 차단하는 대규모 새 장치를 추가할 근거도 없다.

## 최종 판정

**수정본은 상세 실험 설계로 수용 가능하다. 현재 재확인한 범위에 남은 중요한 설계 차단 사항은 없다.**
주요 최초 모순은 설치 기준 한 곳으로 통일, 명시 smoke와 자연 관측 분리, 관측 한계 표기, 같은 세션의
연속 fresh 검토, 실패 직전 상태의 재실험으로 보완됐다. 관련 구현과 같은 commit·다음 의존 주기 전
spec/plan 갱신·HUMAN 수락/통합·다중 업무 대화·실제 파일 근거를 핵심에 두고, 사소한 모델 실수마다
새 정책·자동 승인·추가 검사기를 만드는 방향으로 확대하지 않는다.

이는 P0/P1을 이미 통과했다는 판정이 아니다. 실제 설치·Luna 개발·Sol native 검토·자연 사용·제품
회귀·인도는 모두 향후 실행의 증거가 필요하다. 본 설계가 그 차이를 명시하고 실패/미검증의 중단
경계를 마련했으므로 실행 전 상세 설계로서의 목적에는 맞는다.

별도 확인한 북극성 수정은 0030/0031의 기존 두 문단을 V4-12에서 V7-09로 옮긴 것뿐이다.
현재 Git diff의 삭제/추가 본문은 같고 새 Codex 실증 문단이나 판정 변경은 없다.

추후 수정의 재판정은 이 기록을 지우지 않고 아래에 추가한다.

## root 마감 기록

위 독립 재확인 이후 root가 본 설계의 상태를 설계 완료로 바꾸고 이 리뷰 결과와 정적 검증 링크를
