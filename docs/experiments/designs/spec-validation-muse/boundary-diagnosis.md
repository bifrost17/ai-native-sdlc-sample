## N1 — 정수 token 문법과 정수값: 실제 계약 결정 필요

근거는 `contracts.md:4–7`의 “정수”, “부동소수는 허용하지 않는다”와 JSON 전달,
`spec.md:17` AC4의 부동소수 거절이다. 문서는 정수값 검사인지 JSON 숫자 token의
소수점/지수 표기 검사인지 명시하지 않는다.

입력 `2.0`, `2.00`, `1e3`은 JSON 파서에서 정수값으로 읽을 수 있지만 수신자가 사용하는
언어의 정수 타입으로는 다르게 분류된다. 한 수신자가 성공시키고 다른 수신자가 invalid_input을
반환할 수 있어 단순 내부 구현 선택이 아니다. “plan에서 어느 쪽이든 선택해도 공유 의미 불변”은 성립하지 않는다.

제품 코드 실행 없이 기존 Python/Node의 파서만 대조한 실제 결과(rc=0):

```text
Python json.loads + type(value) is int:
2      -> int, True
2.0    -> float, False
2.00   -> float, False
1e3    -> float, False

Node JSON.parse + Number.isInteger:
2      -> True
2.0    -> True
2.00   -> True
1e3    -> True
```

권고: 허용값 기준 또는 token 문법 기준을 contracts에 정하고 AC4에 구별되는 작은 입력 예를 연결한다.
그 다음 parser 구현·라이브러리를 plan에서 선택한다. 어떤 정책이 더 낫다는 결정은 이 진단에서 대신하지 않는다.

## N2 — stale_attempt와 invalid_result: 기존 의미의 재확인, 새 큰 공백 아님

`contracts.md:19`는 readiness → 입력 유효성 → ID/attempt → 업무 판단 순서를 명시한다.
`:14`는 현재 calculating의 같은 ID/attempt라는 전제 뒤에 저장 values의 합계 검증을 둔다.
`recovery.md:13–14`도 ack 유실 후 같은 result가 다시 오면 calculating 상태가 아니어서 stale_attempt라고 정한다.

형식상 유효한 total이 저장 합계와 다르면서 attempt도 낡았다면 ID/attempt 판정이 먼저라는 해석이
기존 계약에서 나온다. 반면 total의 타입/형태 자체가 잘못됐다면 입력 유효성의 invalid_input이 먼저다.
이 두 종류를 섞어 “항상 stale_attempt 우선”이라고 plan에 새 규칙을 쓰면 기존 입력 우선순위와 어긋날 수 있다.
필요하면 contracts에 기존 순서를 명확히 하는 한 문장을 두면 충분하며 별도 수락 게이트나 재설계는 필요하지 않다.

## N3 — safe integer 최대값: 작은 명료화, 임의 선택지는 아님

`contracts.md:20–21`은 안전 정수 최대값과 도달 시 dispatch 차단/운영자 unavailable을 이미 정한다.
이 용어를 JavaScript/JSON 상호운용의 안전 정수로 읽으면 최대값은 9007199254740991이며,
실제 Node `Number.MAX_SAFE_INTEGER`도 같은 값을 반환했다.

극단 경계의 숫자가 중복 기재되지 않았다는 이유로 전체 인계를 막을 필요는 없다. 다만 여러 언어의
“내 정수 타입에 안전한 최대값”을 각각 선택하라는 뜻으로 plan에서 임의 상한을 정하면 공유 계약이
달라진다. contracts에 용어의 수치/정의를 고정하고 내부 저장 타입은 그 값을 정확히 표현하는 범위에서
선택하면 된다. 이 숫자 명료화는 실제 최대 dispatch 횟수까지 실행하라는 요구가 아니다.

## N4 — 살아 있는 W의 compute 유실: 유효한 숨은 전제, 지원 실패와는 구분

`contracts.md:13`은 C가 attempt를 커밋한 후 compute를 한 번 전달한다고 정한다.
`recovery.md:10–12`에서 원장 상태는 전달 전에 calculating이 된다. W가 실제로 종료하면
`:24`의 종료 확인 뒤 queued/새 attempt 경로가 있고, C 재시작은 `:25`로 복구된다.

그러나 두 process가 살아 있는 동안 compute가 전달되지 않거나 유실된다면 W는 결과를 만들지 못하고,
C는 종료 증거를 얻지 못한다. 현재 문서에는 이 사건 자체의 관측·재전달·운영 재개가 별도로 없다.
따라서 통신 구현의 신뢰 가정에 따라 정상 결과로 수렴하거나 calculating에 남을 수 있다.

다만 `spec.md:8` R4/AC6–AC8은 process 재시작을 명시하고 임의의 live-W 메시지 손실까지
지원한다고 직접 약속하지는 않았다. 그러므로 이를 이미 약속한 장애 복구가 실패했다고 확정하거나
자동 재전송/timeout 기능을 필수로 추가하는 것도 과도하다.

권고: C→W 전달에서 필요한 신뢰성/실패 통지 조건을 계약의 전제로 명시하거나, 이 사건이 지원 밖이면
남는 관찰 상태와 운영 재개 경로를 정한다. 새로운 timeout·같은 attempt 재전송·W 종료 처리를
선택한다면 해당 contracts/recovery/AC를 갱신해야 한다. compute가 순수하고 중복 결과가 같다는
사실은 새 재전달의 시점/종료 권한/재개 규칙이 이미 결정됐다는 뜻이 아니다.
plan에는 그 결정에 맞는 IPC 수단과 검증 순서를 둘 수 있다. 전제를 plan에서만 발명하지 않는다.

## N5 — 5초 재시도와 10초 timeout: 안전 규칙은 있음, 시각 기준 명확화 필요

`recovery.md:15–17`은 한 행당 한 outstanding, 5초 재시도, 10초 timeout을 적는다.
timeout 후 이전 R 처리가 살아 있어도 같은 key/total로 원자 멱등 저장하는 상황을 명시하므로
원격 처리의 생존과 C가 기다리는 현재 호출을 같은 것으로 세어 영구 정지시킬 이유는 없다.

하지만 “연결 실패 후 timeout”과 5초의 기준점은 모호하다. t=0 호출이 t=10에 timeout이면
다음 시도를 t=10에 허용할지 t=15에 할지, 연결이 된 채 응답이 없는 경우도 10초에 끝나는지
문장만으로 확실하지 않다. 단일 outstanding은 이 중복 금지만 해결하며 정확한 시각을 선택하지는 않는다.

이는 중복 발행 방지 의미를 깨는 확정 결함은 아니다. 시간 선택이 필요한 경우 recovery의 한 문장으로
deadline 시작점과 재시도 간격 기준을 명확히 하고 plan에서 timer 구현을 정하면 된다.
별도 상태표·대형 timeout 설계·성능 목표를 새로 만들 필요는 없다.

## 이전 preflight와 실험 해석 정정

실제 네 입력 SHA는 기존 `boundary-preflight.md`와 모두 같다. 새 버전이 추가 문제를 만든 것이 아니라
같은 입력의 N1과 전송 전제/N5 모호성을 앞선 preflight가 충분히 구별하지 못했다.
따라서 이 입력을 완전히 충분한 무결함 대조로 간주하고 모든 N1–N5를 false positive로 계산하면 안 된다.
이 기록이 앞선 “중요한 공백을 확인하지 못함” 판단의 한계를 보완하며 원본 preflight는 역사로 남긴다.

04의 parent와 child는 실제로 설계 전용 범위를 전달하고 결과를 기다렸다. 하지만 두 보고서가
N1–N5를 모두 의미 불변 plan 명확화로 낮춘 판단은 별도 한계로 남긴다. 스킬 선택·위임 실행의 관측과
계약 충분성/정당 이월의 정확한 판정은 같은 통과가 아니다.

실행한 추가 확인은 Python/Node의 스칼라 JSON 파서 대조와 네 입력 SHA 대조뿐이다.
제품 실행·실제 통신 손실 재현·설계 수정은 수행하지 않았다. 이는 입력/결과 진단이며 추가 Muse 실험이나
독립 최종 제작 검증으로 계산하지 않는다.
