# 0033 — intent·spec·plan과 하위 설계의 작성 충실도

2026-09-13. **수락 당시 문서는 이번 로컬 시제품을 설계하고 구현하기에 충분하다.**
특히 spec의 하위 파일은 참고 부록이 아니라 입력·출력·구조·데이터·동작을 소유하는 설계 정본이다.
중요한 API·저장소·동시성 결정을 구현자가 새로 만들어야 하는 공백은 발견하지 못했다.
다만 사람의 탐색을 돕는 도식, 경계 입력의 작은 문구 정리, 현재 plan의 최신 상태 표시는 보완할 만하다.

이 판단은 **문서 충분성**에 관한 것이다. [0033 실행](../../0033-astra-medium-f05.md)의 남은 PR3 시험,
D7 요구 변경과 문서 동기화, 최종 인도까지 통과했다는 뜻은 아니다.

## 기준과 평가 방법

북극성 [Playbook](../../../verification/north-star-playbook.html)의 요구사항·설계 play는 intent의 문제를 풀고,
열린 질문·정책 우려를 처리한 스펙을 엔지니어링 팀에 인계하도록 한다. 이어 plan play는 실제 파일·작업 순서·
검증을 명시하고, 앞선 대화를 보지 않은 엔지니어가 구현할 수 있을 때까지 계획을 다듬도록 한다.
모든 내부 메서드나 UML을 미리 고정하는 요구는 아니다. 그 기준과 현행
[설계 지침](../../../../tdd-optional/project/examples/skills/design-spec/references/design-depth.md),
[실행 지침](../../../../tdd-optional/project/examples/skills/plan/references/execution-depth.md)을 함께 적용했다.

- root: 수락 intent·spec 전체 집합·plan·기존 코드와 현재 문서 변경, 최초 질문/답변 및 새 S2 인계·후속 프롬프트를 대조했다.
- Astra/high 독립 리뷰: **spec 네 파일만 먼저 읽고** 판단을 고정한 뒤 intent·baseline·plan을 읽었다.
  새 제품 코드와 실행 결과를 보지 않아 구현 성공을 역으로 명세 충분성에 대입하지 않았다.
- Sol/high 독립 리뷰: 수락 계획과 관측된 제품 코드·문서·공개 실행 근거를 역추적했다.
  실행하지 않은 계획 시험과 계획에 쓰지 않은 시험을 구별했다.
- 이번 검토는 문서·코드 읽기와 정적 대조다. 새 제품 개발 실험이나 전체 제품 시험은 실행하지 않았다.

실험 개발자의 Astra/medium 설정과 이번 사후 리뷰의 모델·추론 설정은 별개다.
동일한 코드 생성 능력이나 모델 간 성능 비교를 측정한 검토가 아니다.

## 각 문서의 충실도

**intent: 충실하다.** 개인 JSON 대장의 변경 공유 어려움과 수동 주간 보고가 문제로 적혀 있고,
공유 상태 변경과 같은 데이터의 CSV라는 업무 결과로 이어진다(4–19행).
전체 가져오기·낡은 버전 거부·현재값 no-op·필터·원본 보존은 실제 HUMAN 답변과 일치한다(21–38행).
약 200행/5명은 시험 규모로 기록하고 입력 상한으로 발명하지 않았다(42–43행).
API·flag·입력 거부의 구체적 형식은 설계의 제안으로 남겼고, 모르는 회사 기준은 시제품 밖의 열린 질문으로 구별했다(69–78행).

성공 기준이 상세하므로 요구사항 성격의 문장도 많지만, 문제와 원하는 결과를 잃은 기능 목록은 아니다.
업무자가 정한 충돌·원본 보존 조건을 담은 것이며, API·DDL·내부 알고리즘을 intent에서 먼저 강제한 사례가 아니다.
Git/대행/검토 기록 설명이 상대적으로 길어 가볍게 읽는 의도 문서로서는 압축 여지가 있다.
실험의 업무 답변을 발명 없이 보존한 문서로 판단하며 이 길이를 모든 제품의 기본 양식으로 삼을 필요는 없다.

**spec와 하위 설계: 충실하다.** 설계 집합의 각 파일과 소유 결정·필수 읽기를 spec 66–75행에서 선언한다.
OpenAPI는 JSON 모양·라우트, contracts는 파싱·오류 우선순위·호출, storage는 데이터·원자성을 소유한다.
불일치하면 구현자가 임의로 한쪽을 선택하지 않고 spec을 고치도록 되어 있다.
다음은 중요한 결정을 실제로 닫은 사례다.

| 개발자가 알아야 할 것 | 이미 정해진 내용 | 수락 원본 근거 |
|---|---|---|
| 구성과 책임 | 별도 service.py, config/model/service/storage/http/csv_export 책임, RequestService의 네 메서드·입력·반환·오류 | storage 29–55행 |
| 데이터와 저장 수명 | 정확한 입력 키·타입·null/누락·Unicode·version 상한, DDL와 user_version, DB 생성 주체·연결 모드·수명·스키마 거부 | storage 5–27, 57–89행 |
| 초기 가져오기 | 전체 입력 검증 뒤 DB 접근, BEGIN IMMEDIATE 안의 빈 상태 재검사, 전체 삽입/커밋·롤백, 실패한 빈 파일 잔류의 이유 | storage 91–104행 |
| 원자적 변경 | ID→version→전이→값 차이의 검사 순서, 한 UPDATE·영향 행 수, 커밋한 DTO 반환, no-op와 실제 변경 경합의 차이 | storage 106–126행 |
| 외부 호출과 실패 | 명령/옵션·종료 코드·stdout/stderr, 경로/메서드·DTO, framing/MIME/JSON 검증 순서와 고정 오류 | contracts 5–123행 |
| CSV 일치 | 같은 조회 함수·필터/정렬, UTF-8/BOM·CRLF·quote·null, 전체 구성 후 출력, 시점이 다른 조회의 한계 | contracts 125–136행 |
| 실행·공개 경계 | 127.0.0.1, 명시 DB 경로, 프로세스 시작 시 flag, 기본 OFF·업무 guard·health 예외·같은 코드 공개/중단 | spec 77–95행, contracts 16–25행 |
| 수용 기대 | R/AC 연결, 고정 ID·행·version, 실제 두 작업의 겹침, 전후 전체 행·원본 바이트 보존 | spec 23–51행 |

예를 들어 변경은 다음 순서만으로도 구현의 중요한 판단이 결정된다.

1. 쓰기 잠금을 얻은 트랜잭션에서 ID가 있는지 확인한다.
2. 전달한 version을 먼저 비교한다. 현재 값과 같더라도 낡은 버전이면 충돌이다.
3. 현재 done에서 open으로 가는지 확인한다.
4. 실제 차이가 없으면 version을 올리지 않고 현재 DTO를 반환한다.
5. 차이가 있으면 owner/status/version을 한 UPDATE로 바꾸고 영향 행을 확인한다.
6. 트랜잭션 안의 결과를 보관하고 COMMIT한 뒤 응답한다. 이후 응답 손실은 확정한 DB를 되돌리지 않는다.

이 순서와 no-op가 먼저 성공한 경합에서 뒤의 실제 변경도 성공할 수 있다는 예외까지 spec에 있다.
plan에서 처음 만들거나 구현자의 상식에 맡긴 중요한 설계가 아니다.

OpenAPI 하나만 떼면 JSON 중복 키·lexical 정수·오류 우선순위·CSV·트랜잭션을 알 수 없다.
하지만 OpenAPI 6행부터 부가 계약을 명시하고 spec이 전체 집합을 읽도록 하므로 파일 분리는 설계 누락이 아니다.
`$ref` 45개(고유 10개)의 대상 해석과 JSON 파싱은 다시 확인했다. 전용 OpenAPI validator 통과로 표현하지 않는다.

**plan: 구현을 시작하기에 충분하다.** 파일별 변경 역할과 spec/AC, 실행 환경이 구체적이다(9–34행).
가져오기→조회/CSV→버전 변경의 세 PR은 각 통합판에서 시험할 수 있고, 일반 OFF를 유지한다(74–88행).
공유 파일과 통합 의존성 때문에 순차로 진행할 이유도 있으며, 작은 순수 CSV 함수의 별도 병렬화까지 검토했다.
TDD 대상과 구현 후 시험 대상을 나누고, 각 PR의 작업·독립 기대·회귀·완료 조건을 연결한다(90–166행).
실제 프로세스/HTTP barrier, 독립 SQL snapshot, 실패 주입, 명령 및 사람의 loopback 대행은 실행 상세에 해당한다.
spec에서 빠뜨린 클래스/API 설계를 plan이 대신 채운 것으로 보이지 않는다.

## 하위 설계만으로 개발할 수 있는가

**spec.md와 선언된 세 하위 파일을 함께 읽고 기존 저장소를 볼 수 있다면, 이번 범위의 중요한 설계를
다시 묻지 않고 개발할 수 있는 수준이다.** “storage.md 하나만으로 HTTP까지 구현”하는 독립 파일 구성은 아니다.
의도와 수락 판, 작업·검증 순서는 상위 문서와 plan을 함께 읽는 것이 정해진 인계 방식이다.

남겨 둔 구현 재량은 DTO의 구체적 Python 표현, repository 보조 메서드 이름, 함수 내부 분할과 시험 지원 코드 구성이다.
외부 계약·원자성·상태 전이를 바꾸지 않는 이런 재량을 모두 제거할 필요는 없다.
인증·감사·다중 호스트·운영 SLA를 설계하지 않은 것은 수락된 로컬 합성 시제품 범위에 따른 결정이다.

실행 근거도 이 판단을 제한적으로 뒷받침한다. 새 S2의 시작 프롬프트는 문서 경로·수락 SHA·인계 상태와 PR1 지시를 주었고,
S1 설계 대화를 넘기지 않았다. 후속 06–08 프롬프트도 결과·검토·통합·다음 PR·예산을 전달했으며 새 업무 설계를 답하지 않았다.
S2는 PR1/2를 통합하고 PR3 후보까지 구현했다. HUMAN·독립 검토의 도움이 있었으므로 무개입 개발 성공은 아니다.
첫 HTTP 결함도 기존 응답 헤더·정확 경로 계약을 구현이 어긴 것으로, 해당 계약 자체를 뒤늦게 설계한 사례가 아니다.

설계 집합에 다이어그램은 **0개**다. 구조표·메서드 계약·트랜잭션 순서가 그 질문에 답하고 있어
그림이 없다는 이유로 중요한 설계가 빠졌다고 판정하지 않는다. 다만 여러 경계를 가진 이번 사례에서
사람이 전체를 빠르게 이해하도록 표현하는 수준은 개선할 수 있다.

## 구체적인 보완점과 적용 수준

| 보완점 | 영향과 근거 | 적절한 보완 범위 |
|---|---|---|
| 구조·대표 동작의 시각적 탐색 | 책임/데이터/순서가 여러 표·절에 분산돼 첫 독자가 경로를 조립해야 한다. storage 29–55, 91–126행 | 이 F05 사례에 컴포넌트 한 장과 변경 시퀀스 한 장을 기존 계약에서 도출하면 유용하다. 새 설계를 추가하거나 모든 변경에 UML을 강제할 근거는 아니다 |
| `/requests/` 경계 표현 | contracts 64행의 빈 ID=400과 끝 slash=404가 이 입력에서 겹쳐 읽힌다. 유효 요청이나 데이터 무결성의 중요한 공백은 아니다 | `/requests/`는 404, `/requests/%20`은 400이라는 예시 한 줄로 읽기 모호성을 없앤다. 원본은 평가 입력으로 보존한다 |
| 현재 plan 상태와 후속 HUMAN 결과 연결 | 관측 plan 347–350행과 decisions 138–143행은 HTTP 결과가 아직 없다고 남긴 마지막 개발 호출의 기록이다. 이후 execution E18(462–480행)은 실제77시험·216관찰 결과를 연결했다 | 다음 인계 전에 plan·decisions의 현재 상태 요약에서 E18·코드판과 남은 전용 시험을 연결한다. 당시 기록을 지우거나 에이전트가 이미 결과를 받았다고 소급하지 않는다 |

세 번째는 실행이 끝난 뒤의 **현재 상태 가독성** 보완이다. 수락 당시 plan이 실행 불가능했다는 증거가 아니며,
HUMAN의 사후 기록과 개발자의 마지막 인계 사이에 생긴 차이다. 그래도 다음 사람이 plan에서 작업을 이어받게 하려면
현재 상태를 명확히 잇는 편이 낫다. intent/spec의 draft·대기 표현은 decisions D1–D3와 plan 4–7행에서
역사적 수락 원문으로 읽는 규칙을 제공하므로 무수락이나 문서 동기화 실패로 세지 않는다.

이 결과로 템플릿의 필수 절·훅·검사기를 늘릴 이유는 없다. 설계 표현을 더 좋게 만들고 싶다면 현행
design-depth 지침의 컴포넌트·시퀀스 예시를 이 규모의 사례에서 적용하는 것이 먼저다.
설계/plan 스킬 본문 사용을 실제로 관측하지 못한 점과 산출 문서가 충분한 점도 별도로 평가한다.
이번 분석은 문서 품질 검토이며, 예시 보강이나 실험 제품의 문서 개정은 실행하지 않았다.
