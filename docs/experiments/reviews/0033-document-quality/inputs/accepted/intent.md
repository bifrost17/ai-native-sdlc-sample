# Intent: 사내 요청 대장의 공유 상태와 CSV 추출
Author: 사용자(의도 제안자·제품 오너·담당 엔지니어)의 요청을 Codex가 정리. Status: draft.

## Problem

사내 요청 대장을 JSON 파일과 개인 CLI로 관리해 여러 담당자의 변경을 공유하기 어렵다.
주간 보고서에는 대장 내용을 수동으로 옮겨 적는다. 근거는 사용자의 최초 요청과
`public.json`(case_id: F05-team-service, dataset_version: 7.0.0), 후속 업무·범위 결정이다.

현재 `tracker.py`는 JSON의 요청을 조회하고 완료 처리한다. 제공된 합성 `requests.json`에는
`id`, `title`, `owner`, `status`가 있으며, 담당자 없는 항목은 null이다.
시제품에서 아래 결과를 검증한다. 실제 데이터 사용과 사내망 공유는 이번 검증 범위에 포함하지 않는다.

## Proposed outcome

기존 JSON 요청을 SQLite로 처음 가져온다. 담당자는 동일 기기의 로컬 HTTP API에서 같은
저장소를 조회하고 담당자를 바꾸거나 완료 처리한다. 같은 데이터에서 CSV를 추출해 주간 보고서에 사용한다.

성공의 기준은 다음과 같다. 세부 입력·응답 계약과 검증 방법은 이 기준을 바탕으로 spec과 plan에서 정한다.

- 새 저장소 또는 요청이 없는 저장소에 한 번 초기 가져오기한다. 요청이 이미 있으면 반복 가져오기,
  병합, 덮어쓰기를 모두 거부한다. 원본 JSON은 읽기만 한다. 잘못된 행이나 중복 ID가 하나라도 있으면
  전체 실패하며 일부 요청이 남아서는 안 된다. 빈 입력을 포함한 구체적 거부 계약은 설계에서 제안한다.
- 가져올 필드는 `id`, `title`, `owner`, `status`다. id/title은 비어 있거나 공백만인 값을 제외한
  문자열이다. owner는 같은 조건의 문자열 또는 null이다. status는 `open` 또는 `done`이다.
  문자열을 임의로 trim하거나 대소문자를 바꾸지 않는다.
- 담당자 교체·배정 해제, `open`에서 `done`으로의 변경, 담당자와 상태의 한 번 변경을 지원한다.
  완료 후에도 담당자를 바꿀 수 있다. 완료 취소와 id/title 변경은 제외한다.
- 변경할 때 읽은 정수 버전을 전달한다. 오래된 버전은 같은 값을 보내더라도 충돌로 거부한다.
  현재 버전에서 실제 값이 달라지면 버전이 증가하고, 현재 값 그대로라면 증가하지 않는다.
  같은 버전으로 서로 다른 두 쓰기가 경합하면 최대 하나만 성공해야 한다. 두 변경의 실제 동시 실행을 시험한다.
- 담당자는 자유 입력이며 대소문자를 구분한다. 별도 사용자 디렉터리는 없다. owner와 status를 각각
  또는 함께 정확히 필터하고 ID 오름차순으로 정렬한다. owner 필터를 생략하면 null 담당자도 포함한다.
- CSV는 현재 상태를 UTF-8 표준 CSV로 stdout에 출력한다. 열은 `id,title,owner,status,version`
  순서이며 null 담당자는 빈 셀이다. API와 같은 저장소·필터·정렬을 사용한다. 쉼표·따옴표·한글을
  표준 CSV reader로 복원할 수 있어야 하며 빈 결과도 헤더를 출력한다.
- 조회와 CSV는 업무 데이터를 변경하지 않는다. OFF 상태, 잘못된 요청, 충돌 때문에 요청 데이터가
  바뀌어서는 안 된다.

## Affected users and systems

- 초기 사용자는 동일 기기에서 시험하는 사내 운영 담당자다. 합성 요청 약 200개 이하,
  담당자 5명 이하를 예상한다. 이는 예상 시험 규모이며 강제 입력 한도로 확정한 값은 아니다.
- 기존 시스템은 `tracker.py`의 `list`, `show`, `complete`와 JSON 파일이다.
- Python 표준 라이브러리와 SQLite를 사용해 가져오기·관리 CLI, 로컬 HTTP API, CSV 추출을 추가한다.
- 사용자가 의도 제안자, 제품 오너, 담당 엔지니어를 맡는다. 이번 합성 데이터 시제품의 정책·운영 범위,
  코드 검토·로컬 통합 및 최종 공개 판단도 사용자가 맡는다. 회사 전체의 정책 결정 권한을 뜻하지 않는다.

## Constraints

- 기존 CLI와 JSON 사용 동작을 보존한다. 가져온 뒤 JSON과 SQLite를 자동 동기화하지 않는다.
- HTTP는 동일 기기의 `127.0.0.1`로만 시험한다. 웹 화면, 사내망 공개, 로그인, 실제 데이터,
  외부 연동·전송, 실제 배포와 원격 push는 제외한다.
- 완료 이력·시간, CSV 파일 출력·수식 방어·집계, 운영 로그·변경 이력 기능을 추가하지 않는다.
  로그인 없는 합성 데이터 시제품에 행위자 식별·감사 이력 저장을 구현하지 않는 범위를 사용자가 승인했다.
  이는 회사 기준을 대신하는 결정이 아니며 실제 도입 시 별도로 확인한다.
- 새 HTTP·관리 CLI·CSV는 하나의 공개 단위로 기본 OFF다. 개발 검증에서는 ON으로 완성된 부분을
  시험하고, 최종 수락 후 같은 코드로 공개할 수 있어야 한다. `/health`는 OFF에서도 작동한다.
  기존 CLI는 영향을 받지 않는다. 공개 flag는 인증 수단이 아니다. 구체적 flag와 계약은 설계에서 제안한다.
- 구현은 3~4개의 작은 PR을 선호한다. 분할, 선행 관계, 독립 작업 가능 여부와 그 근거는 계획에서 정한다.
- 의도·spec은 사용자가 PO로, plan과 코드 통합은 엔지니어로 검토한다. 검토한 의도·설계·계획을
  바탕으로 구현한다. Git stage/commit/merge는 사용자가 대행한다.
- 단계 수락·검증과 사람의 결정은 저장소 문서에 보존한다. 사용자가 실제 커밋을 만든 뒤 대상 SHA와
  수락 여부·근거를 전달한다. 이번 답변은 업무·범위 결정이며 문서의 커밋 수락을 대신하지 않는다.
  현재 수락 SHA는 없고, spec·plan·구현은 아직 시작하지 않았다.
- 환경 제한으로 로컬 HTTP 검증을 실행할 수 없으면 명령을 제공하고 사용자의 실행 결과를 받는다.
- 문서는 한국어로 작성한다. 개발 검증 자료에 기술적 시간 기록이 필요하면 UTC를 사용한다.
