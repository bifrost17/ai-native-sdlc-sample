# PROJECT-POLICY — 프로젝트에서 정할 내용
Owner: 사용자(이번 합성 데이터 시제품 범위). Status: draft.

이 문서는 사용자가 제품 오너 겸 담당 엔지니어로 답한 업무·범위 결정을 기록한다.
적용 대상은 [사내 요청 대장 시제품](intent/0001-shared-requests/intent.md)이다. 회사 전체 정책을
대신 정하지 않는다. 회사 기준은 미제공이며 실제 도입 시 별도로 확인한다.

이번 답변으로 시제품 범위 판단은 승인됐으나 문서의 단계 수락은 아직 대기 중이다. 사용자가
문서를 읽고 실제 커밋을 만든 뒤 대상 SHA와 수락 여부·근거를 전달한다. `Status: draft.`는 유지한다.

## 역할과 인계

| 항목 | 결정 |
|---|---|
| 프로젝트 이름과 범위 | 사내 요청 대장 합성 데이터 시제품 — 기존 CLI 보존, SQLite 초기 가져오기, 로컬 HTTP 조회·변경, CSV 추출 |
| 의도를 제시하고 확인할 사람 | 사용자 — 최초 요청에서 문제와 범위 제시 |
| 의도와 요구·설계를 승인할 제품 책임자 | 사용자 — 제품 오너 역할을 맡겠다고 명시 |
| 계획을 검토하고 구현을 맡을 엔지니어 | 사용자 — 담당 엔지니어로 문서 검토. Codex는 검토된 의도·설계·계획에 따라 구현 작업 수행 |
| 코드 검토와 통합 책임자 | 사용자 — 담당 엔지니어로 코드 검토·로컬 통합 판단 |
| 정책·운영·배포의 결정자 | 사용자 — 이번 시제품의 정책·운영 범위와 최종 공개 판단. 실제 배포 제외, 회사 전체 정책 결정자는 미정 |
| 브랜치 전략과 통합 대상 | GitHub Flow · `main` — [정책](docs/GIT-WORKFLOW.md) |
| 머지 방식 | merge commit. 변경하려면 승인 원본 SHA 보존·대응 방식을 함께 기록 |
| 단계 수락과 최종 통합 | 단계는 대상 SHA와 사람의 결정 기록, 구현은 검증·리뷰 후 PR 머지 |
| 단계 수락·검증 기록을 남길 위치 | 저장소의 `intent/0001-shared-requests/` 아래 문서. 수락 기록은 대상 문서·SHA·결정자 역할·결정·근거, 검증 기록은 명령·대상 판·실제 결과·미실행 한계를 보존 |

이번 세션의 Git stage/commit/merge는 사용자가 대행한다. 사용자가 제출물을 읽고 대상 커밋과
결정을 전달한다. 의도와 spec은 PO로, plan과 코드 통합은 엔지니어로 검토한다.
원격 push와 실제 배포는 이번 범위에서 제외한다. 구현은 3~4개 작은 PR을 선호하며,
분할·의존 관계·독립 작업 가능 여부는 plan에서 근거와 함께 정한다.

## 적용할 정책

| 항목 | 값·출처·판·결정자 |
|---|---|
| P1 — 용어·이름·표기·시간대 | 사용자 답변: 문서는 한국어. 요청 필드는 id/title/owner/status, 변경 버전은 version, 상태는 open/done. 문자열 원문과 대소문자 보존. 개발 검증 자료의 기술적 시간은 UTC. 회사 용어 기준은 미제공 |
| P2 — 민감 데이터·사용 범위·로그·보존 기간 | 합성 요청만 사용. 실제 데이터, 운영 로그·변경 이력·행위자 식별·감사 이력 저장 기능 제외. 회사 민감 필드 분류와 보존 기간은 미제공이며 임의로 정하지 않음 |
| P3 — 사용자 범위·외부 전송·준수할 규정 | 동일 기기의 127.0.0.1 시험만 허용. 사내망 공개·외부 연동·외부 전송·실제 배포 제외. 회사 규정은 실제 도입 전 별도 확인 |
| 인증·권한·역할 경계 | 로그인·사용자 디렉터리 제외. 공개 flag는 인증 수단이 아님. 시제품 범위·공개 결정은 사용자 담당 |
| 외부 의존성·사용 한도·실패 시 동작 | Python 표준 라이브러리와 SQLite. 예상 시험 규모는 합성 요청 약 200개 이하·담당자 5명 이하이며 강제 한도가 아님. 잘못된 가져오기는 전체 실패, 기존 요청이 있으면 가져오기 거부. OFF·잘못된 요청·충돌 시 요청 데이터 불변 |
| 스키마·접근성·사용성 등 제품에 적용할 기준 | intent의 입력·버전·필터·CSV 기준을 따름. 웹 화면 제외. 추가·누락 필드 거부, API/CLI 및 flag 계약은 spec에서 제안해 PO 검토 |

적용 근거는 사용자의 이번 답변 1–7이다. P1–P3는 회사 기준이 아닌 이 시제품의 범위 결정이다.
[brand](.agents/skills/brand/SKILL.md)의 B1–B3에 따라 문구를 명료하게 쓰고 정한 용어를 일관되게 사용한다.
[data-compliance](.agents/skills/data-compliance/SKILL.md)의 C1–C2에 따라 자격증명을 넣지 않고
데이터·예외를 무분별하게 노출하지 않는다. API 응답 모델 등 구체적 적용은 spec에서 다룬다.

C3는 접근·변경 이력에 행위자 역할·ID, 업무 식별자, UTC를 요구한다. 사용자는 로그인 없는
합성 데이터 시제품에 한해 행위자 식별·감사 이력 저장 및 운영 로그·변경 이력 기능을 구현하지 않는
범위를 승인했다(답변 6). 이 차이를 C3 충족으로 표시하지 않으며, 회사 정책의 예외 승인으로도
확대하지 않는다. 실제 도입 시 회사의 인증·감사·보존 기준과 결정자를 별도로 확인한다.
개발 검증·사람의 결정 기록은 저장소 문서에 남기며 제품의 운영 이력 기능과 구분한다.
스킬 적용 판과 출처는 intent 말미에 기록한다.

## 검증과 운영

| 항목 | 실제 명령·방법·성공 기준 |
|---|---|
| 제품 실행과 빌드 | 구체적 명령은 spec·plan에서 결정. 새 HTTP는 127.0.0.1로만 실행 |
| 테스트·린트·관련 동작 확인 | 기존 세 테스트와 기존 CLI 동작 보존, 초기 가져오기 원자성, 실제 두 변경의 동시 실행, 조회·CSV 일치, OFF/오류/충돌 시 요청 데이터 불변을 검증. 구체적 명령은 plan에서 결정 |
| 새·변경 동작의 개발 방식 | 작업별로 TDD / 동작별 구현 후 테스트 / 기존 테스트 활용 / 혼합 중 적합한 방식을 선택한다. plan의 Order 또는 작업 블록에 방식·이유·독립된 기대·구현/검증 순서를 적는다. non-TDD 선택 자체에 별도 예외 승인을 요구하지 않는다. |
| 방식과 무관한 검증 기준 | 수락한 spec/AC·독립 입력에서 기대를 정하고 실제 출력에 맞춰 기대를 만들지 않는다. 모든 AC와 영향받는 기존 동작을 검증하고 회귀 근거를 보존한다. 기존 시험만으로 부족한 새 동작은 검증을 보강한다. 명령·코드판·결과·미실행/한계는 정한 위치에 남긴다. |
| 선택한 방식의 적용 | TDD는 의미 있는 실패를 관측한 뒤 최소 구현·재검증한다. 구현 후 테스트는 작은 동작마다 구현과 검증을 끝낸 뒤 다음 동작으로 간다. 기존 테스트 활용은 관련 AC의 실제 커버리지를 대조한다. 혼합은 작업별 경계를 명시한다. 이미 만족한 동작에 RED를 꾸미거나 사후 시험을 TDD 이력으로 소급하지 않는다. |
| 결함 진단과 계획 변경 | 버그 수정은 증상을 먼저 재현하는 진단을 권장하며 수동·임시 스크립트·자동 시험을 구분한다. 재현의 제약은 기록하고 의미 있는 회귀 보호를 남긴다. 실제 테스트 보호가 적용될 때는 그 범위를 따른다. 선택 방식/검증이 바뀌면 이유와 plan을 관련 구현 커밋에 담고, 계약·권한 변경은 기존 수락 절차를 따른다. |
| 탐색·직접 관찰 | UI·기술 탐색은 질문·제약·관찰 방법과 폐기/제품 편입 조건을 정한다. 자동 시험·브라우저·수동 확인은 증명할 동작에 맞게 선택한다. 학습 목표의 달성과 제품 완료를 구분하며, 편입할 동작은 관련 spec·plan과 필요한 회귀·통합 검증으로 연결한다. |
| 검증 근거를 남길 위치 | `intent/0001-shared-requests/` 아래 검증 기록. HTTP 실행이 제한되면 Codex가 로컬 명령을 제공하고 사용자의 실행 결과와 대상 판을 기록 |
| CI와 필요한 검사·검토 | CI 명령·환경은 미정. 구현 완료 전 채택한 sdlc-feedback 검토를 수행하고, 사용자가 코드 검토·로컬 통합 판단 |
| 배포·기능 공개 권한, 설정 위치, 수락·중단 기록과 되돌리는 방법 | 사용자 최종 수락 후 새 HTTP·관리 CLI·CSV를 한 공개 단위로 같은 코드에서 공개. 기본 OFF, 개발 검증 ON. /health는 OFF에서도 동작하며 기존 CLI는 영향 없음. flag·설정 위치·중단 및 되돌림 절차는 spec·plan에서 제안. 공개 수락·중단 결정은 변경 폴더에 기록. 실제 배포 제외 |
| 운영 지표·이상 징후·대응과 인계 | 운영 로그·변경 이력·완료 이력·시간·집계 기능 제외. 시제품 시험·공개 판단은 사용자 담당. 실제 운영 기준은 도입 전 별도 확인 |

[검증 방식 선택 가이드](docs/TESTING-STRATEGY.md)로 plan의 판단을 구체화한다. 테스트 작성 순서와
검증 수단은 구분한다. 기존 기준을 읽고 영향을 확인하는 것은 모든 방식에 필요하지만, 새 자동 시험·
별도 에이전트·전체 검사 체계를 모든 작은 변경에 일괄 추가하지 않는다. 중요한 판단 근거와 실제 결과를
남기며, 팀이 선택한 독립 검토와 보호 통제는 그 적용 범위를 따른다.
플레이북의 버그 test-first·시험 동결 처방을 선택형에서 조정한 범위는
[가이드의 플레이북 적용 설명](docs/TESTING-STRATEGY.md#플레이북을-적용하는-범위)에 명시한다.
