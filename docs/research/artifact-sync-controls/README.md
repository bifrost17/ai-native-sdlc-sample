# spec/plan 누락을 줄이는 실행 장치 검토

2026-09-11. 상태: **권고안**. 실제 사용 템플릿·런타임 설정·GitHub 병합 규칙은 아직 바꾸지 않았다.
현재 기준은 제작 4bd422e, 사용 후보 add296d다.

## 권고

팀 공용 실행 환경에서 **인도 전 독립 검토를 자동 호출**하고, GitHub에서 **최신 변경에 대한
사람의 검토 없이 병합되지 않게** 하는 조합을 우선한다. 템플릿은 얇게 유지하고 이 장치는 팀이
설치·관리한다. 스킬은 검토 방법을 제공할 수 있지만 호출 자체의 강제는 실행 환경이 맡아야 한다.

[북극성 V4-11](../../verification/north-star-playbook.html#V4-11)은 계획 이탈 시 같은 커밋 갱신과
동기화 hook의 고려를 명시한다. V10-05/07과 리뷰 챕터는 spec·plan 준수 리뷰와 사람의 승인을
다룬다. 자동화 장치를 쓰지 말라는 뜻으로 '얇은 템플릿'을 해석할 필요는 없다.

## 세 가지 수단과 적용 순서

| 순서 | 수단 | 맡길 일 | 보장하지 못하는 것 |
|---|---|---|---|
| 1 | 인도 전 hook + 별도 검토자 | 최신 업무 결정·spec·plan·diff를 직접 읽는 검토를 자동 호출하고 중요 누락을 구현 에이전트에 되돌린다. | 의미 판단의 무오류, 꺼진 hook이나 다른 도구 경로까지의 강제 |
| 2 | GitHub PR 필수 사람 검토 | 최신 변경의 문서·검증 근거를 사람이 수락하기 전 main 병합을 제한한다. | 사람이 충분히 검토했는지, 우회 권한 보유자의 행동 |
| 필요 시 | 검토 결과의 필수 CI check | 현재 PR 커밋에 유효한 검토 기록이 없으면 실패시켜 누락된 실행을 잡는다. | 기록이 있다는 사실만으로 문서 내용의 정확성 |

처음부터 별도 승인 상태기계·범용 문서 검사기·매 편집마다 모델 호출을 만들지 않는다. 첫 장치의
실행/누락이 실제 문제로 남을 때 세 번째 수단을 추가한다. GitHub의 기존 기능으로 해결되는 경계는
템플릿 코드로 다시 구현하지 않는다.

## 인도 전 검토의 구체적 동작

1. 팀이 선택한 프로젝트에서 작업 인도 시점에 실행한다. 질문·설계 수락 대기 같은 정상 중간
   응답은 허용하며 매 파일 편집마다 모델을 호출하지 않는다. 최초 실험은 Sonnet·낮은 추론으로 한다.
2. 작성자의 완료 요약만 믿지 않고 작업 관련 사용자 요청·수락 기록, 현재 spec/plan과 실제 diff를
   읽는다. 업무 변경이 문서와 코드 양쪽에서 빠진 경우는 diff만으로 발견하기 어려우므로 최신
   업무 결정을 입력에서 빼지 않는다. 전체 비공개 대화나 숨겨진 추론을 PR로 복사하지 않는다.
3. 세 가지를 판단한다: 합의한 동작이 spec에 있는가, 중요한 구현·검증 변경이 plan에 있는가,
   문서·실제 변경·검증 결과가 모순되지 않는가. 단순히 문서 파일을 수정했는지는 합격 기준이 아니다.
4. 중요한 누락이 있으면 구체적 근거와 함께 보완하게 한다. 의미가 불명확하거나 수락이 필요한
   결정은 사람에게 넘긴다. 검사 오류·시간 초과를 통과로 기록하지 않는다. 자동 재시도는 제한한다.
5. 변경된 최종 판에 대해 다시 검토한다. 예전 diff의 통과 결과를 새 코드에 재사용하지 않는다.
   문서가 영향받지 않은 버그 수정이나 이미 계획된 회귀 시험 추가는 정상적으로 통과시킨다.

`Stop`은 매 응답 종료에 발생하므로 위의 '인도' 구분과 반복 방지를 실험해야 한다. 공식 문서상
Stop hook은 응답 종료를 막아 작업을 계속하게 할 수 있지만, 사용자 중단·API 오류·반복 상한 등이
있어 절대적인 완료 통제 경계는 아니다. 현재 agent hook은 실험 기능으로 명시되어 있다. 짧은
시제품으로 적합성을 확인하되 운영 배포에서는 공식 권장인 command hook과 명시적으로 제한한
별도 검토 호출을 검토한다. [Claude Code hooks](https://code.claude.com/docs/en/hooks#agent-based-hooks),
[Stop 동작](https://code.claude.com/docs/en/hooks#stop).

## 최종 병합 경계

PR의 승인과 검토 근거를 최신 변경에 연결한다. 필요한 경우 기존 승인 무효화/최신 push 검토를
사용하고, 개발 AGENT에게 검토 규칙 변경·승인 우회 권한을 주지 않는다. 팀 담당자가 설정을 관리한다.
로컬 Git hook은 우회하거나 끌 수 있으므로 단독 강제 수단으로 삼지 않는다.
[GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

CI check를 추가한다면 최신 SHA에 대한 검토 결과인지 확인하고, 평가 오류나 미실행은 별도로 실패
처리해야 한다. GitHub는 일부 `skipped`/`neutral` 상태도 필수 check 충족으로 인정하므로 단순히
job을 필수로 지정한 것만으로 검토 실행을 보장한다고 주장하지 않는다. 검사 설정의 변경·결과 발행
권한도 고려한다. [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

현재 단일 계정의 모의 HUMAN 실험은 실제 조직의 권한 분리를 입증하지 못했다. 설치 범위·계정 권한·
저장소 요금제에서 가능한 병합 설정을 실제 적용 전에 확인해야 한다. 새 승인 시스템을 만들지는 않는다.

## 다음 실험의 합격 조건

기존 [0017 사례](../../experiments/0017-artifact-sync.md)와 실제 누락 기록을 재사용해 다음을 비교한다.

- 코드·시험만 바뀌고 필요한 spec/plan이 빠진 인도를 감지한다.
- 문서에 형식적 수정만 하고 새 요구를 빠뜨린 경우도 감지한다.
- 문서 변경이 필요 없는 수정과 질문·수락 대기는 잘못 차단하지 않는다.
- hook 미실행·검토 오류·옛 결과 재사용을 통과로 보고하지 않는다.
- 사람의 문서 갱신 상기 없이 보완으로 이어지는지와 추가 호출·지연·오탐을 기록한다.

실행 장치는 **검토가 생략되지 않는 경계**를 강화한다. spec/plan이 의미적으로 항상 옳다는 보장은
모델 검토나 사람 검토 어느 쪽도 하지 못한다. 이 한계를 인정하면서 중요한 누락의 발견·복구를
반복 가능하게 만드는 것이 이번 권고의 목표다. 아직 설치나 동작 검증을 완료한 설계는 아니다.
