# Spec: 청구 상태 조회 API 와 상태 변경 고객 통지 (from intent 0011-claim-status-notify)
Upstream: intent.md@4045be5580d36dc69b350f9ccb6975aa848f3436. Status: draft.
Skills applied: design-spec@016705e, claim-data-compliance@f993c28, claim-notice-compliance@f993c28, secure-api-review@016705e.
## Requirements
- R1 고객은 포털에서 자기 청구의 상태를 본다. `GET /portal/claims/{claimNumber}/status` 는 세션의 고객이 소유한 청구에만 답하고, 소유가 아니면 그 청구 번호의 존재 여부를 알리지 않는다.
- R2 상담사는 고객 대신 같은 상태를 조회한다. `GET /agent/claims/{claimNumber}/status` 는 본인확인 기록 ID 를 필수로 받고, 기록이 없거나 확인되지 않으면 상류 조회 전에 거절한다(C7).
- R3 두 경로의 응답 필드는 이 spec 이 아래 표에 열거한 것뿐이다(C2). 표에 없는 필드는 응답에 없다. 상류(claims-core) 응답이나 도메인 객체를 그대로 직렬화하지 않는다.
- R4 주민등록번호·계좌번호·연락처의 전체 값은 응답·화면·통지 본문 어디에도 나가지 않는다(C1). 자르는 자리는 응답/통지 DTO 를 만드는 경계이고, 프런트에서 가리는 것은 R4 를 만족하지 않는다.
- R5 상태가 바뀌면 고객에게 통지한다. 발송 전에 **그 채널의** 수신 동의 기록을 확인하고, 확인하지 못하면 보내지 않는다(C4). 미동의·확인 실패 채널의 몫을 다른 채널이 대신 지지 않는다.
- R6 통지 본문에는 세 가지만 담는다 — 어느 청구(청구 번호), 어느 상태 변경(무엇에서 무엇으로), 문의 경로(C5). 지급 예정 금액·금액 산정 근거·보류 사유 상세·청구 내용·인증 없는 상세 링크는 담지 않는다.
- R7 한 번의 상태 변경은 채널당 최대 한 건의 통지를 낳는다. 상류 이벤트가 두 번 와도 두 번 보내지 않는다.
- R8 조회와 통지는 모두 이력에 남는다: 누가(역할 + 내부 ID) · 무엇을(청구 번호) · 언제(UTC), 보존 3년(C6). 대리 조회 이력에는 본인확인 기록 ID 를 병기하고, 거절된 대리 조회도 남긴다(C7).
- R9 로그·오류 메시지·audit 이벤트에 쓰는 식별자는 청구 번호와 내부 ID 뿐이다(C3). 요청·응답 본문 전체를 로그로 찍지 않는다. 고객에게 돌려주는 오류 본문에는 상관관계 ID 만 싣는다.
- R10 두 엔드포인트의 경로·질의 파라미터는 OpenAPI 스키마로 검증하고, 스키마에 없는 질의 파라미터가 오면 거절한다(`secure-api-review` 2항).
## Design
**구조.** 새 서비스 `claims-status` 하나가 두 읽기 경로와 한 통지 워커를 갖는다. 상태의 정본은 상류 claims-core 이고, 이 서비스는 청구 데이터를 저장하지 않는다 — 캐시도 두지 않는다. 캐시는 저장이고, 저장은 C1·C6 이 관리해야 할 대상을 넓힌다. 저장하는 것은 이력뿐이다.

**데이터 흐름(조회).** 게이트웨이 JWT → 포털/상담 콘솔 세션 → `claims-status` → claims-core 읽기 → 역할별 응답 모델 → 이력 1건.

**데이터 흐름(통지).** claims-core 상태 변경 이벤트 → 통지 워커 → 이벤트 중복 판정(R7) → 고객 연락처 DB 에서 **채널별** 동의 기록 조회(읽기 전용) → 동의가 기록된 채널만 발송 → 채널마다 이력 1건(발송 또는 미발송 + 사유 코드).

**응답 허용 목록(C2).** 고객 경로와 상담사 경로가 같은 네 필드를 쓴다. 상담사가 고객보다 더 볼 이유가 이 요구에는 없기 때문이고(C2 마지막 항은 "볼 이유가 없으면 목록을 나눈다"), 이유가 생기면 그때 목록을 나눈다.

| 필드 | 왜 필요한가 | 근거 |
|---|---|---|
| `claimNumber` | 고객이 어느 청구인지 식별한다 — Problem 의 "내 청구 어떻게 됐나요" | C2 열거, C3 이 허용하는 식별자 |
| `status` | 요구된 값 그 자체. `접수`·`심사중`·`지급`·`보류` 넷의 열거형 | C2 |
| `statusChangedAt` | 언제 바뀌었는지가 없으면 고객이 다시 전화한다 | C2, 시각은 UTC(C6 과 같은 규칙) |
| `receivedAt` | 접수 후 며칠이 지났는지를 고객이 스스로 판단한다 | C2 |

목록에 **없는** 것(상류가 보내더라도 경계에서 버린다): 고객명, 주민등록번호, 계좌번호, 연락처(마스킹본 포함), 지급 예정 금액, 금액 산정 근거, 보류 사유 상세, 담당 사정인의 이름·연락처, 진단명·사고 경위·의무기록.

**권한과 오류.** 소유자 불일치는 `404` 로 답한다 — `403` 은 그 청구 번호가 존재한다는 사실을 알려 주기 때문이다. 본인확인 기록 없음/확인 실패는 `403` 이고, 거절도 이력에 남는다. 상류 장애는 `503`. 모든 오류 본문은 `{"correlationId": "..."}` 뿐이다(C3·R9). 청구 번호는 C3 이 허용하는 식별자이므로 경로에 두어도 되고, 개인정보는 경로·질의 문자열에 두지 않는다.

**대리 조회 계약(C7).** `verificationRecordId` 는 필수 질의 파라미터다(`GET /agent/claims/{claimNumber}/status?verificationRecordId=...`). 기록 ID 자체는 식별자이므로 접근 로그에 남아도 C3 에 어긋나지 않고, 본인확인에 쓴 값(고객이 불러 준 생년월일·주소 등)은 요청에도 이력에도 넣지 않는다. 없거나 확인되지 않으면 claims-core 를 부르기 **전에** 거절한다 — 통과시키고 나중에 기록하지 않는다.

**통지 규칙.** 거래성 통지다 — 구독 해지 문구로 발송 근거를 만들거나, 제목을 열람률로 최적화하거나, 추가 상품을 권유하지 않는다. 동의 조회가 실패하거나 상태가 불명이면 기본값은 **발송하지 않음**이고, 미발송 건은 청구 번호와 내부 ID 만으로 오류를 남긴 뒤 지수 백오프로 3회까지 **동의 조회를 재시도**한다(발송을 재시도하는 것이 아니다). 3회 후에도 확인되지 않으면 미발송으로 종결한다. 링크는 본문에서 바로 열리는 인증 없는 상세 링크를 두지 않고 로그인 뒤 포털 화면으로 보낸다(C5).

발송에 쓰는 이메일 주소·전화번호는 연락처 DB 에서 읽어 **발송 봉투(수신자 필드)** 에만 쓴다. 본문·응답·이력·로그에는 그 값이 마스킹본으로도 들어가지 않는다(C1·C3).

본문 형태(상태 4종 × 채널 2종 = 템플릿 8개, 문구는 F1 이 풀린 뒤 확정):
> 청구 `{claimNumber}` 의 상태가 `{이전 상태}` 에서 `{새 상태}` 로 바뀌었습니다. 자세한 내용은 포털에 로그인해 확인하시거나 `{문의 경로}` 로 문의해 주세요.

**중복 방지(R7).** 상류 이벤트 전달은 최소 1회(at-least-once)라고 가정한다 — 같은 상태 변경 이벤트가 두 번 올 수 있다. 워커는 `claimNumber` + `이전 상태` + `새 상태` + `statusChangedAt`(UTC) 으로 만든 키를 채널별 발송 이력과 대조하고, 이미 발송 이력이 있는 (키, 채널) 조합은 다시 보내지 않는다. 상태가 실제로 바뀌지 않은 이벤트(이전 상태 = 새 상태)는 통지하지 않는다. 판정에 쓰는 저장소는 이력 자체이므로 청구 데이터를 새로 저장하지 않는다.

**이력(C6·C7).** 이벤트 세 종류 — `STATUS_VIEWED`, `NOTICE_SENT`, `NOTICE_SUPPRESSED`. 각 행: `actorRole`, `actorId`(내부 ID), `claimNumber`, `occurredAtUtc`, 대리 조회면 `verificationRecordId`, 통지면 `channel` 과 (미발송이면) `reasonCode`. 「누가」는 이름·이메일이 아니라 역할 + 내부 ID 로 적는다. 보존 3년 — 로그 순환·보존 설정에 3년 미만을 넣지 않는다.

**`secure-api-review` 점검(항목별).**
1. 인증 — 두 엔드포인트 모두 게이트웨이 JWT 뒤에 있다. 포털/콘솔이 JWT 를 검증해 세션을 넘기고 애플리케이션은 세션만 읽는다(스킬의 org note, 0002 F3·0008 F4 와 같은 답). 익명 경로는 `/health` 뿐이고 새 인증 수단은 만들지 않는다.
2. 입력 검증 — 두 경로 모두 `GET` 이라 요청 본문이 없다. 항목 2 를 경로·질의 파라미터에 적용한다: `claimNumber` 와 `verificationRecordId` 를 OpenAPI 스키마로 검증하고, 스키마에 없는 질의 파라미터는 거절한다(R10).
3. Audit — 이 chain 에는 상태를 바꾸는 엔드포인트가 없다(→ Out of scope). 항목 3 은 해당 없음이고, 읽기 경로의 이력은 C6 이 따로 요구하는 것이다(R8).
4. 데이터 분류 — pii 로 표시된 필드는 허용 목록에 하나도 없고(R3), 로그·오류·audit 에도 나가지 않는다(R9). C3 은 같은 자리를 audit 이벤트까지 넓힌다.
## Constraints
- 기존 게이트웨이 JWT 인증만 쓴다. 새 인증 수단을 만들지 않는다(intent.md 에서 이어옴).
- 회사 정책(보안 · 컴플라이언스 · 브랜드 · UX)을 따른다(intent.md 에서 이어옴). 보안의 정본은 `.claude/skills/secure-api-review/SKILL.md`, 컴플라이언스의 정본은 `policies/compliance.md` 다. 브랜드와 UX 는 이 레포에 정본도 스킬도 없다 → F1.
- 고객 연락처 DB 는 읽기 전용이다(intent.md 에서 이어옴). 동의 기록도 읽기만 하고, 동의의 수집·철회·정정은 이 서비스가 하지 않는다.
- (설계 중 발견) `policies/compliance.md` 는 `Status: draft v0 — 오너 서명 대기` 다. 이 spec 이 인용한 C1–C7 의 문면은 서명 전까지 바뀔 수 있다 → F2.
- (설계 중 발견) `claim-data-compliance` 는 보안 조항의 정본으로 `policies/api-security.md` 를 가리키지만 그 파일이 없다(`ls policies` → `compliance.md` 하나) → F6.
- (설계 중 발견) 상담 콜의 41% 가 포털·통지로 옮겨 가면 claims-core 읽기 호출이 그만큼 는다. 캐시를 두지 않기로 했으므로 호출 예산은 상류 팀과 합의해야 한다. 이 spec 은 예산을 정하지 않는다 — plan 의 위험으로 넘긴다.
- (설계 중 발견) SMS 는 길이 제한이 있어 C5 의 세 요소를 다 넣으면 문의 경로가 잘릴 수 있다. 잘라야 한다면 문의 경로를 남기고 나머지를 줄인다.
- (레포 규약) 이 chain 의 `src/`·`tests/` 파일은 각자 구현하는 R/AC 절을 첫 줄에 적는다(CLAUDE.md).
## Open questions from intent
- Q1 (알림에 지급 예정 금액을 넣어도 되는가 — 정책 오너) **carried forward — 정책 오너.** C5 는 "금액 산정 근거"를 명시적으로 뺐지만 금액 **자체**가 거기 들어가는지는 정본이 말하지 않는다. `claim-notice-compliance` 의 "애매하면 덜 싣는 쪽"에 따라 이 spec 의 기본값은 **미포함**(R6)이고, 답이 오면 R6 과 템플릿 8개를 고친다. 구현은 이 답을 기다리지 않는다.
- Q2 (상담사가 조회할 때 고객 본인확인은 어떻게 하는가 — 상담센터장) **부분 답 + carried forward — 상담센터장.** 계약 부분은 C7 이 이미 고정한다 — 본인확인 **기록이 있을 때만** 조회가 열리고, 없거나 확인할 수 없으면 거절하며, 이력에 기록 ID 를 병기한다(R2·R8). 상담사가 무엇을 물어 확인하는지와 그 기록을 어느 시스템이 발급하는지는 정책이 정하지 않으므로 상담센터장이 정한다. 그 답이 정하는 것은 `verificationRecordId` 의 발급처 하나이고, 엔드포인트 계약은 바뀌지 않는다.
## Flagged concerns
- F1 intent.md 는 브랜드·UX 정책을 지키라고 하는데 이 레포에는 그 정책의 스킬도 정본도 없다(`ls .claude/skills` → 브랜드·UX 없음; `docs/ADOPTING.md` 첫 행이 같은 빈자리를 가리킨다). L3 253 은 정책 스킬을 spec 의 선행조건으로 둔다 — 이 spec 은 그 조건을 만족하지 못한 채 쓰였다. 따라서 통지 문구와 포털 화면 문안은 여기서 확정하지 않고 형태만 정했다. 누가 정하는가: 정책 오너(스킬을 세울지)와 고객경험팀 김하늘(문구).
- F2 컴플라이언스 정본이 `draft v0`, 오너 서명 대기다. 서명 없는 조항 위에 응답 허용 목록과 통지 규칙을 세웠다. 누가 정하는가: 정책 오너(서명 = 개정 PR 머지).
- F3 동의를 확인하지 못해 통지를 못 보낸 건을 포털 조회로 갈음할 수 있는가 — `claim-notice-compliance` 가 "정책이 말하지 않는다"고 명시하고 여기로 올리라고 한 자리다. 갈음할 수 없다면 Problem 의 일부(상태 변경을 고객이 제때 안다)가 그 고객들에게는 풀리지 않는다. 누가 정하는가: 정책 오너.
- F4 포털 **화면**에 보류 사유를 보여도 되는가 — C5 는 통지에만 걸리고, C2 는 필드마다 근거를 적으라고만 한다. 보류가 41% 콜의 가장 큰 몫이면 사유 없는 "보류" 한 줄은 다시 전화를 부른다. 이 spec 의 기본값은 미포함(R3 허용 목록)이고 문의 경로가 그 자리를 맡는다. 누가 정하는가: 정책 오너.
- F5 이메일과 SMS 양쪽에 동의가 기록된 고객에게 한 번의 상태 변경을 두 채널로 다 보내는가, 한 채널만 고르는가. C4 는 채널마다 동의를 따로 보라고만 하고 중복을 다루지 않는다(R7 은 같은 이벤트의 재전달만 막는다). 이것은 UX·브랜드 판단인데 그 스킬이 없다(F1). 이 spec 은 정하지 않는다. 누가 정하는가: 고객경험팀 김하늘.
- F6 `claim-data-compliance` 가 `policies/api-security.md` 를 보안 조항의 정본으로 가리키는데 그 파일이 없다. 이 spec 은 대신 `secure-api-review` 스킬을 정본으로 삼았다. 누가 정하는가: 정책 오너(파일을 두거나 스킬 문면을 고치는 PR).
## Out of scope
- 사정인 전용 조회 엔드포인트. 사정인은 사정 도구에서 상태를 이미 본다 — intent 가 사정인을 든 것은 상담사 전화를 받는 쪽이기 때문이고, 이 chain 이 그 전화를 없앤다. C2·C7 의 사정인 문면은 그 경로가 생길 때 적용한다.
- 상태를 **바꾸는** 경로 일체. 이 chain 은 읽기와 통지뿐이다.
- 포털·상담 콘솔의 화면 구현과 문안 확정(F1).
- 통지 발송 인프라 — 전송률, 템플릿 엔진, 백오프의 구현 세부. `claim-notice-compliance` 가 다루지 않는다고 명시한 자리다.
- 동의 기록의 수집·철회 경로. 연락처 DB 는 읽기 전용이다.
- claims-core 의 상태 모델 변경. 네 상태는 intent 가 준 것을 그대로 쓴다.
- plan.md 와 코드. 이 문서는 spec 이다.
## Acceptance criteria
- AC1 → R1 다른 고객의 청구 번호로 `GET /portal/claims/{claimNumber}/status` 를 부르면 `404` 이고 본문 키는 `correlationId` 하나다. 없는 청구 번호도 같은 `404`·같은 본문이다. 자기 청구면 `200` 과 허용 목록 네 필드가 온다.
- AC2 → R2 `verificationRecordId` 없이 `/agent/...` 를 부르면 `403` 이고 claims-core 호출은 0 회다. 확인되지 않는 기록 ID 도 `403`·호출 0 회다.
- AC3 → R3 상류 응답에 허용 목록 밖 필드를 넣은 픽스처로 두 엔드포인트를 부르면, 응답 본문의 키 집합이 정확히 `claimNumber`·`status`·`statusChangedAt`·`receivedAt` 넷이다.
- AC4 → R4 상류와 연락처 DB 가 주민등록번호·계좌번호·연락처 전체 값을 보낸 픽스처에서, 그 값들이 응답 본문·통지 본문·이력·로그 어디에도 문자열로 나타나지 않는다.
- AC5 → R5 동의 조회가 실패하거나 기록이 없는 채널에는 발송 호출이 0 회다. 이메일 동의만 있는 고객에게 SMS 발송 호출은 0 회이고, 그 건은 `NOTICE_SUPPRESSED` 이력 1행을 남긴다.
- AC6 → R6 생성된 통지 본문에 청구 번호·이전 상태·새 상태·문의 경로가 있고, 금액·사유 상세·인증 없는 상세 링크는 없다.
- AC7 → R7 같은 상태 변경 이벤트를 두 번 넣으면 채널당 발송 호출은 1 회이고 `NOTICE_SENT` 이력도 채널당 1행이다. 이전 상태 = 새 상태인 이벤트는 발송 호출 0 회다.
- AC8 → R8 조회 1회와 통지 1건마다 이력 1행이 생기고, 각 행에 `actorRole`·`actorId`·`claimNumber`·`occurredAtUtc`(UTC)가 있다. 대리 조회 행에는 `verificationRecordId` 가 더 있고, 거절된 대리 조회도 행을 남긴다. 보존 설정 값이 3년 이상이다.
- AC9 → R9 전체 경로를 한 번 태운 뒤 로그·오류 본문·audit 이벤트를 모아 grep 하면, 청구 번호와 내부 ID 밖의 식별자가 하나도 없다. 고객에게 간 오류 본문의 키는 `correlationId` 하나뿐이다.
- AC10 → R10 스키마에 없는 질의 파라미터를 붙여 두 엔드포인트를 부르면 거절되고, 형식이 맞지 않는 `claimNumber` 도 상류 호출 없이 거절된다.
