# 선정 방법과 근거의 범위

조사 기준일: 2026-09-11. 목적은 다른 세션에서 설계 중인 `spec.md`와 `plan.md`에 참고할 **실제 작성된 우수 문서**를 찾는 것이다. 이 조사에서 새 템플릿을 설계하거나 기존 템플릿을 수정하지는 않았다.

## 무엇을 모범적이라고 판단했는가

문서의 인지도와 프로젝트의 인지도는 다른 근거다. 유명 저장소의 파일이라는 이유로 선정하지 않았으며, 모든 독자가 동의한다는 보편적 평판도 주장하지 않는다. 본문 평가, 실제 검토, 구현 연결을 함께 제시해 추천 판단을 검토할 수 있게 했다.

| 평가 축 | 시스템 설계문서에서 확인한 것 | 구현계획에서 확인한 것 |
|---|---|---|
| 문제와 경계 | 요구·제약·비목표, 외부 시스템과의 책임 경계 | 달성할 결과와 선행 결정, 변경 범위 |
| 설명의 연결 | 구성 요소 → 데이터·요청·상태 흐름 → 선택 이유 | 작업 → 의존성 → 중간 산출물·제품 상태 |
| 실패를 다루는 정도 | 예외·일관성·복구·운영 제약 | 실패 판정·검증·전환 조건·복구 |
| 검증 가능성 | 구현자가 같은 동작을 도출할 수 있는 계약 | 실행·관찰할 항목과 완료 판정 |
| 실제 사용 근거 | 원저자·공식 보관·리뷰·연결된 구현 | 계획 이력·PR·코드·테스트·출시와의 연결 |
| 에이전트 적합성 | 문맥 없이도 읽을 용어·경계·규범적 동작 | 구체 경로·작업 단위·실행/검증 순서·재개에 필요한 상태 |

모든 문서에 모든 항목을 요구하지 않았다. 데이터 이전과 작은 UI 기능에 같은 복구 분량을 요구하는 것은 부적절하다. 대신 각 문서의 가장 강한 용도와 빠진 부분을 명시했다. 점수의 정밀함으로 품질을 과장하지 않도록 수치 순위는 만들지 않았다.

## 탐색 경로

1. **공식 프로젝트의 설계·RFC 보관소**에서 원문을 찾고 작성자, 상태, 토론과 구현 링크를 따라갔다. 웹앱·웹 프레임워크를 우선했다.
2. **AOSA·성능 아키텍처 교재**에서 유명 웹앱의 구조 설명을 확인했다. 사전 설계와 사후 해설을 별도로 표시했다.
3. **공개 계획과 구현 PR을 양방향으로 추적**했다. 계획 → 코드뿐 아니라 코드에서 발견한 제약 → 계획 개정도 확인했다. Openverse가 이 경로에서 강한 사례였다.
4. **에이전트용 실제 계획 파일**을 찾았다. `plan.md`, `PLANS.md`, `docs/plans`, `docs/superpowers/plans`, `ExecPlan`, `For agentic workers` 등으로 탐색하되, 빈 양식과 작성 가이드는 실제 사례에 포함하지 않았다.
5. **커뮤니티 추천을 발견 경로로 사용**했다. 검색 결과에 나온 글은 원문과 댓글을 구분하고, 후보 문서의 품질 판정은 원문으로 돌아가 확인했다. Aside 접속·열람 범위와 실패는 [커뮤니티 조사 기록](working/community-research.md)에 별도 기록한다.
6. **선정과 별도의 비판 검토**로 과장된 주장, 에이전트 실행 증거의 부족, 사후 문서를 사전 계획으로 오인하는 문제를 점검했다.

## 근거를 읽는 방법

Aside 실제 브라우저 열람은 [HN Design Docs at Google](https://news.ycombinator.com/item?id=23915521)과 [Ask HN 실제 문서 요청](https://news.ycombinator.com/item?id=24184906) 두 건에서 성공했다. Chromium·Ganeti 모음 등이 추천되었지만, 이 추천을 최종 7개 문서에 대한 커뮤니티 보증으로 사용하지 않았다. Reddit 대상 페이지는 네트워크 보안 차단으로 브라우저 본문·댓글을 읽지 못했다.

HN에서는 실제 문서를 요청했는데 다시 작성법 글이 답으로 나오는 문제, 설명이 길어져도 구현 불확실성이 사라지지는 않는다는 반론을 확인했다. 그래서 방법론과 실제 사례를 분리하고, 문서의 길이보다 해당 문제에 필요한 결정·검증의 연결을 평가했다. [실제 문서를 다시 요구한 댓글](https://news.ycombinator.com/item?id=24188700), [설계를 완전한 청사진으로 취급하는 데 대한 반론](https://news.ycombinator.com/item?id=23917227).

- **본문 확인:** 파일의 내용과 해당 절을 읽었다는 뜻이다.
- **리뷰 확인:** 특정 검토자·댓글·승인 기록을 확인했다는 뜻이다. 저장소 별 수나 일반적인 도구 인기로 대체하지 않았다.
- **구현 연결 확인:** 병합 기록과 변경된 코드·테스트 파일을 확인했다는 뜻이다. 계획이 전체 프로젝트 성공의 원인이었다는 증명은 아니다.
- **작성자 실행 보고:** PR 또는 완료 기록에 적힌 결과다. 이번 조사에서 독립적으로 실행한 결과와 구분한다.
- **공식 출시 확인:** 프로젝트가 해당 기능의 공개 제공을 알린 자료다. 현재 모든 환경에서의 동작을 검증했다는 뜻은 아니다.

대상 저장소의 전체 빌드와 외부 서비스 연동은 재실행하지 않았다. 이는 문서와 공개 구현 근거를 비교하는 조사이며, 각 소프트웨어의 품질 인증이 아니다. 에이전트용이라는 분류도 에이전트 지시·사용 기록을 근거로 하며, 모든 작업이 자율 실행되었다는 의미는 아니다.

## 버전과 출처 처리

문서에 적힌 날짜, 최초 공개 이력, 후속 변경 날짜를 구분한다. 가능한 경우 변경되지 않는 커밋 링크를 함께 제공한다. 현재 `main`의 완성도 높은 문서가 최초 구현 당시에도 같은 내용이었다고 가정하지 않는다. 영구 URL이 없는 교육 자료는 원문과 공식 작성·보관 기록을 연결했다.

보고서 본문은 필요한 설명만 한국어로 요약하고, 선정한 원문 전체는 재현 가능한 고정판을 중심으로 [`originals/`](originals/README.md)에 별도 보관한다. 외부 원문·고정판 링크는 각 사례에 그대로 유지하며, 상세 조회 범위는 각 사례의 출처 및 [작업 메모](working/root-research.md)에 있다.

## 제외·보류한 대표 유형

| 유형 또는 후보 | 제외·보류 이유 |
|---|---|
| 빈 `spec.md`·`plan.md` 템플릿, 에이전트에게 계획 쓰는 법을 알려 주는 skill | 실제 프로젝트의 구체 계획이 아니므로 본 선정 수에 포함하지 않음 |
| 시스템 설계 면접의 가상 Twitter·YouTube 설계 | 실제 제약·검토·구현의 추적성이 더 높은 원문 우선 |
| SocialCalc / EtherCalc 아키텍처 장 | 우수한 보조 자료지만 교육·사후 해설의 중복을 줄이기 위해 MediaWiki 우선 |
| Openverse 민감 콘텐츠 처리·인기도 계산 계획 | 원문을 읽었으나 동일 프로젝트 중복과 선정 사례와의 역할 중복을 줄임 |
| 검색에서만 발견한 React Grid Layout rewrite RFC, OpenTranscribe gist | 원문·이력 검증이 부족한 발견 후보를 최종 선정으로 승격하지 않음 |
| 계획 작성 도구의 인기도·홍보 사례 | 도구의 채택과 개별 계획의 완성도는 별도 판단 |
| Superpowers 초기 Visual Brainstorming 계획 | 파일 날짜와 달리 공개 Git 이력에서는 구현 뒤에 문서가 추가됨. 인증 개선 계획은 반대로 계획 → 구현 선후 관계가 확인되어 선정 |
| BranchLab Trace Physics + Golden Corpus | 구체 작업과 실제 코드·테스트 대응은 강하지만 계획과 구현이 같은 최초 커밋에 있어 사전 계획성 미입증. 보조 사례로 유지 |
| EveryInc Unified Plan Doc Artifact | 본문과 완료 조건의 산출물 요구가 서로 충돌해 제외 |
| BanyanDB replication / Rhapsody xfail 계획 | 테스트 선택·집계 명령의 정밀성 우려가 남아 최상급 선정 보류·제외 |

각 조사 경로의 구체 후보와 원문 링크는 `working/` 아래 메모에 남겼다. 발견만 한 후보와 정독·이력 확인을 마친 후보를 구분한다.

에이전트 계획 후보를 당초 예상한 15–20건까지 넓히지는 못했다. 도구 대기 이후 범위를 좁혀 실제 이력 검증을 우선했고, 최종 구현계획은 사람을 위한 우수 계획 2건과 에이전트용 계획 1건으로 구성했다. 부족한 근거를 가진 agent plan을 수량을 맞추기 위해 추가하지 않았다.
