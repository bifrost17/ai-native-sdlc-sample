# 독립 비판 검토

검토일: 2026-09-11. 최종 후보 7건과 README·상세 평가·방법론을 검토했다. 새로운 후보 검색이나 대상 코드·테스트 실행은 하지 않았다. 기존 조사자의 판단을 그대로 승인하지 않고 Openverse 두 계획, Superpowers 최초 계획, GitLab 설계의 핵심 절, MediaWiki 장을 원문에서 별도로 확인했다. Symphony·Django의 Git 이력 및 모든 PR 리뷰를 이번 분담에서 재조회한 것은 아니다. P3 계획 커밋의 직접 자식 구현 관계는 상위 조사자가 확인한 증거를 사용했다.

## 필수 수정 권고

### R1. P2의 복구 한계를 구체화해야 한다

- 위치: `implementation-plans.md` P2 「모범적인 부분」, 검토 당시 37행.
- 현재 평가는 위험 표현이 낙관적이고 정량 기준이 부족하다는 수준이다. 그러나 원문 `Rollback`은 새 인스턴스와 DAG를 제거하면 어느 시점에도 되돌릴 수 있다고 설명하고, 바로 다음 `Risks`는 운영 미디어 테이블과 Elasticsearch 인덱스 전체를 교체한다고 인정한다.
- 판단: 신규 실행 경로 제거와 이미 변경된 데이터 복원은 별개다. 기존 서버 철거 후의 복구, 백업 복원 절차·조건도 이 단락에는 없다. 이것은 단순 표현의 낙관성보다 실질적인 계획 공백이다. 단계적 전환이라는 장점은 유지하되 완성된 데이터 복구 계획처럼 읽히지 않게 해야 한다.
- 권고 문장: “새 인스턴스·DAG 제거는 실행 경로를 되돌리는 설명이며, 이미 교체된 운영 테이블·인덱스를 복원하는 절차와 기존 서버 철거 후의 복구는 구체화하지 않는다.”
- 필수 수정 여부: **예 — P2를 복구 방식의 모범으로 참고하도록 추천하는 평가의 정확성을 위해.** 후보 교체까지 필요하지는 않다.
- 원문: [Ingestion Server Removal — Rollback / Risks](https://docs.openverse.org/projects/proposals/ingestion_server_removal/20240328-implementation_plan_ingestion_server_removal.html#rollback). 독립 열람에서 두 절을 함께 확인.

선정 유지 판단: 구현계획을 3건 채우기 위해 위험을 용인하는 것은 부적절하다. 그와 별개로 이 문서의 환경 비교, 기존 경로와의 공존, staging·production 검증 후 철거, 실제 발견에 따른 개정은 독립적인 추천 가치가 있다. 따라서 **단계적 교체와 계획 변경 추적의 모범**으로 한정 추천할 수 있다. **데이터 복구·안전한 전환의 완성된 모범**으로 추천하면 기준 미달이다. 이 한계는 상세 평가에만 숨기지 말고 요약표에서도 보여 주는 것이 좋다.

### R2. README의 미존재 검토 문서 링크를 납품 전에 해결해야 한다

- 위치: `README.md` 「근거와 추가 자료」의 `review.md`, 검토 당시 58행.
- 검토 시작 시 파일 목록에는 `review.md`가 없었다. 이 독립 검토 파일은 `working/independent-review.md`이므로 링크 대상과 다르다.
- 필수 수정 여부: **예 — 상위 작업자가 최종 반영 내역을 작성하거나 링크를 실제 파일로 수정해야 한다.** 검토 중 작성 예정인 파일일 수 있으므로 최종 누락으로 단정하지는 않는다.

## 보완하면 좋은 부분과 경계

1. **P3의 “저장소 차단 예외”는 의미가 모호하다.** `implementation-plans.md` 71행에서 repository가 아니라 브라우저 `sessionStorage` 접근 차단을 뜻한다면 그렇게 적는 편이 정확하다. 독립 열람한 최초 계획 Task 1은 저장 호출을 직접 실행하지만 Task 3은 읽기 예외를 처리한다. 따라서 이 계획의 코드 블록 자체를 완결된 인증 구현으로 복사하기에는 한계가 있다. 현재도 실제 구현이 보강되었다고 설명하므로 선정 취소 사유는 아니다. **문구 수정 권고.** [최초 계획 Task 1 / Task 3](https://github.com/obra/superpowers/blob/83b5d3a963ed63d8231ecb3276c8368caf1857a3/docs/superpowers/plans/2026-06-10-visual-companion-auth-hardening.md)
2. **사전성 증거를 정확히 표현했다.** P3 첫 문단의 agentic workers 지시, Task 6에서 이미 통과한 테스트를 RED라고 부르지 말라는 조건, Task 10의 이벤트 파일 확인은 원문에서 확인된다. Git 부모 관계는 문서가 구현 커밋보다 앞서 저장되었음을 지지하지만 실제 작업 순서 전체나 자율 실행 transcript를 증명하지 않는다. 보고서가 이 구분을 유지하는 것은 적절하다. 변경 불필요.
3. **D4는 품질보다 분류 적합성이 약하다.** MediaWiki 장은 요청과 저장 구조를 이해시키는 좋은 실제 시스템 설명이다. 하지만 사전 설계의 결정을 추적할 `spec.md` 모범과는 다르다. 현재 README와 상세 문서에서 교육·사후 해설이라고 반복 표시하므로 치명적인 범주 오류는 아니다. 최종 답변에서도 “설계·아키텍처 문서 4건, 그중 사후 해설 1건” 정도로 유지하는 편이 좋다. [MediaWiki 장](https://aosabook.org/en/v2/mediawiki.html)
4. **다양성은 충분하지만 넓지는 않다.** 구현계획 3건 중 2건이 Openverse이며 에이전트용은 1건이다. 웹앱 기능·운영 전환·로컬 웹 UI라는 역할 차이는 뚜렷하고, 사용자 요청이 에이전트용 가산이라면 수량 요건과 충돌하지 않는다. 다만 여러 조직의 보편적 합의를 대표하는 목록으로 표현하면 안 된다. 현재 방법론의 조사 범위 제한은 유지해야 한다.
5. **D3의 장점은 지지되지만 닫힌 운영 계약은 아니다.** 원문은 기존 SLI 여유를 활용한 지연 목표와 단계적 규칙 배포를 설명한다. 반면 전체 요청 흐름의 종합 SLI 부족, 환경별로 달라지는 관찰 시간도 인정한다. 보고서가 수치의 현재 유효성이나 프로덕션 안정성을 보증하지 않고 설계 설명 방식만 추천하는 수준은 적절하다. [HTTP Routing Service](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/cells/http_routing_service/)

## 가장 강한 선정과 가장 약한 선정

- **가장 강한 선정: P1 Openverse Dark Mode.** 사용자에게 익숙한 웹앱 기능이고, 원문에서 기대 동작 조합·병렬 작업·중간 화면 상태·시각회귀·복구가 연결된다. 별도 승인·구현·출시 근거까지 갖추어 문서 품질과 실제 채택을 구분해 평가하기 쉽다. 다만 디자인·색 이름 선행 승인은 여전히 필요하며, 실제 UI를 이번에 재실행한 것은 아니다. [원문](https://docs.openverse.org/projects/proposals/dark_mode/20240325-implementation_plan_dark_mode.html)
- **가장 약한 선정: D4 MediaWiki AOSA — 이번 요청의 사전 설계 참고 적합성 기준.** 유명 실제 웹앱의 설명 품질은 강하지만 역사적 사후 해설이므로 결정 전 대안 검토·승인·완료 계약을 직접 모범으로 삼기 어렵다. 명시적으로 보조 성격을 유지하면 포함은 타당하다. 구현계획만 비교하면 **P2**가 전체 미완료 상태와 데이터 복구 공백 때문에 가장 약하다.

## 종합 판정

설계 4건·계획 3건이라는 수량, 실제 프로젝트 선호, 웹 관련성, 에이전트용 가산이라는 핵심 요청은 충족한다. 현재 확인 범위에서 선정 전체를 무효화할 정도의 사실 오류나 계획 내부 모순 은폐는 발견하지 못했다. 다만 R1의 데이터 복구 한계와 R2의 링크를 해결한 뒤 납품하는 것이 적절하다. “모범”은 모든 절이 완벽하다는 인증이 아니라 어떤 작성 방식을 왜 참고할 만한지에 대한 제한된 추천으로 남겨야 한다.
