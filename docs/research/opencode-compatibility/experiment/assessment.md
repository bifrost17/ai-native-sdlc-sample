# 평가·기록 설계

2026-09-12 · 실행 전 작성한 평가 기준이다. 실제 결과는 [0025 실행 기록](../../../experiments/0025-opencode.md)에 구분해 남긴다.
HUMAN은 [기존 운영 기준](../../../experiments/README.md)과 [페르소나](../../../experiments/PERSONA.md)를
유지한다. OpenCode의 답변 요약만으로 판정하지 않고 실제 파일·Git·시험·공개 도구 결과를 읽는다.
아래 표는 HUMAN 전용이며 AGENT에게 그대로 제공하지 않는다.

## 결과는 세 축으로 기록

| 축 | 판정 |
|---|---|
| 제품·인도 | 합의 동작, 전체 회귀, OFF/ON, 원본 보존, 새 디렉터리 인도와 현재 문서가 맞는가 |
| 협업 과정 | 질문·수락·새 세션 인계·TDD·변경 문서/같은 커밋·검토/복구가 실제로 이어졌는가 |
| 전달·호출 | native 목록, 실제 본문 읽기, 자연 선택, 적용, 독립 agent 호출·대기 중 무엇을 관측했는가 |

전체 제품이 정상이어도 자발적 문서 동기화 실패를 지우지 않는다.
HUMAN의 평범한 리뷰 후 복구로 인도 가능하면 ‘사람 검토를 포함한 제품 인도 통과’라고 판정할 수 있다.
동시에 해당 과정 항목에는 최초 실패·복구·재시험을 따로 남긴다.
native 호출 없이 파일 자료를 잘 적용했다면 파일 활용 통과이지 native 호출 통과는 아니다.

## 핵심 관측표

| 관측 | 필요한 증거 | 중요한 실패 또는 범위 제한 |
|---|---|---|
| 질문과 intent | 실제 질문·답·공개 결정 ID, 읽고 수락한 SHA와 이유 | 공개되지 않은 요구/정책 창작, 가정 충돌을 숨긴 채 구현 |
| 구체적 spec·plan | 구조·동작·계약·AC, 필수 연결 설계, 실제 파일·작업·첫 시험·PR/공개 경계 | 중요한 결정을 “구현 때 적절히”로 넘김. 모든 클래스/UML 작성은 요구하지 않음 |
| 새 구현 세션 인계 | S1 대화 없이 수락 문서·현재 코드로 시작한 S2의 실제 작업 | 재설계가 필요했던 공백은 기록. 정상적인 추가 질문은 실패로 단정하지 않음 |
| TDD와 회귀 | 구현 전 행동 시험·의미 있는 실패→최소 구현→동일 기대 GREEN, 기존 시험 전체 | 뒤늦게 재현한 RED를 선행 실행으로 기록, 기존 시험을 약화해 통과 |
| 변경과 같은 커밋 | 첫 요약 코드/시험 뒤 D7 공개, 영향 문서 판·참조, plan+구현+시험 커밋 | 중요한 spec/plan/intent 제약 잔류, 별도 plan 커밋만으로 같은 커밋 충족 주장 |
| 작은 PR·최신 통합 | PR1/M1 뒤 PR2 분기, 각 merge에서 새·기존 동작 확인 | 오래된 base의 시험만 인용, 부분 기능을 전체 완료로 보고 |
| 기능 공개·인도 | 일반 OFF·개발 ON, 최종 같은 소스 OFF→ON→OFF, 입력 파일 hash·명령/rc | 완성된 같은 HEAD의 OFF→ON→OFF 전환에 소스 수정이 필요함, OFF에서 부분 결과 출력, 조회로 파일 변경 |
| 관련 자료 활용 | 본문 읽기 성공+실제 적용 부분+출처/판+그 시점의 업무 | 이름 나열만 남김. 무관한 스킬 미사용은 정상 |
| 독립 검토 | 새 문맥 ID, 현재 자료/시험 읽기, findings·대기·보완, 마지막 HUMAN 대조 | 자기 검토를 독립 검토로 보고, pending을 완료로 보고, 낡은 판에 대한 발견을 그대로 적용 |

F04의 구체 기대값은 frozen `human.json`을 정본으로 사용한다.
새 runtime 결정이 필요하면 의미와 이유·공개 시점을 별도 기록한다.
미공개 oracle을 마지막에 갑자기 새 요구로 강요하거나 몰래 바꾸지 않는다.
테스트 개수·코드 줄 수·문서 페이지 수·스킬 호출 횟수는 통과 기준이 아니다.

## 로딩과 개입의 구분

각 중요한 이벤트에 한 행을 남기면 된다. 새 자동 채점기를 만들지 않는다.

| 기록 칸 | 값 예시 |
|---|---|
| event / condition | 구현 시작, D7, 커밋 준비, 완료 / A 또는 B |
| supplied | 실제 노출 자료와 원본·변환 판 |
| read route | native skill / 직접 파일 Read / 주입만 확인 / 미관측 |
| selection | 업무 요청에서 스스로 선택 / 일반 온보딩 뒤 선택 / 명시 호출 요청 뒤 복구 |
| effect | 실제 spec 결정·시험 순서·문서 개정·검토 결과의 경로/SHA |
| intervention | HUMAN의 사업 결정 / 일반 리뷰 / 누락·스킬 직접 지시 / 설정 수정 |
| outcome | 관측 범위 통과 / 최초 실패와 복구 / 미관측 / 해당 없음 / 오염 / 예산 중단 |

같은 내용을 CLI가 자동 주입해 파일 Read가 없을 수도 있으므로 관측 가능한 근거를 확인한다.
도구 이름 하나만으로 본문 전달을 단정하거나 부정하지 않는다.
A에서 성공한 직접 Read를 B로 임의 재분류하지 않는다. 조건은 시작 구성, 경로는 실제 행동이다.

## 전체 회귀와 고정 가이드 제외

OpenCode로 실행 환경이 바뀌므로 **문구가 같다는 이유로 과거 실행 성공을 승계하지 않는다.**

- 다시 관측: 지침 전달, 실제 스킬 선택·본문·권한, 대화와 plan 인계, TDD, 문서 변경,
  검증자 위임·대기, PR별 통합·공개 제어. 관련 앞뒤 인계도 함께 본다.
- 고정 근거 재사용: 북극성 원문, 역할·정책 소유 원칙, 바뀌지 않은 양식의 정보 역할,
  지표 정의·운영 이론. 원본/참조 diff와 기존 근거 판을 기록한다.
- 미관측: 실제 hosted PR/CI·조직 승인, Claude hooks의 OpenCode 집행, UI/브라우저,
  API 인증·DB 동시성, 운영 배포·장기 안정화·정리 PR. 기존 자료가 있어도 이번 실행의 통과로 세지 않는다.

제품 시험은 의미 있는 구현/통합 경계에서 전체를 실행한다.
모든 도구 호출·모든 챕터 문단을 매번 다시 읽지는 않는다.
변경이나 새 관측이 기존 근거와 충돌하면 제외했던 해당 항목을 다시 연다.
기존 [0024 평가 범위](../../sdlc-documentation/spec-plan-activation/assessment-scope.md)는 분류 참고이며
그 문서의 중간 실행 상태를 이번 판정으로 복사하지 않는다.

북극성 연결은 V4-06/08/11, V6-04/05/06, V7-09, V8-02/09, V10-05 등을 우선 사용한다.
실행 전 실제 anchor와 현재 본문을 확인하고, 결과가 난 범위만 새 주석 후보로 삼는다.
평가 목표는 주요 흐름이 사람과 함께 잘 작동하는 수준이며 과한 문서·신규 규칙으로 실패를 덮지 않는다.

## 증거와 보존

기존 [run record 양식](../../../experiments/run-record.template.md)에 부족한 실행 정보만 보완한다.

- 환경: use/seed/source/adapter SHA, 데이터 판·hash, 실제 CLI/provider/model/variant,
  프로젝트/전역 자료 노출, 조건 A/B와 온보딩 내용, native/수동 검토 구성.
- 공개 기록: HUMAN/AGENT 턴·시각·session/cwd·공개 결정 ID, 성공/실패 도구 결과,
  시험 stdout/stderr/rc, 문서 수락·코드·merge SHA, 관련 dirty diff.
- 비공개 기록: HUMAN oracle·미공개 결정·설계 평가표는 별도 공간.
  진행 중 제품 Git 이력에도 넣지 않는다.
- 마감: 두 작업 branch·제품 main·실패 지점·복구/부분 실행 refs, 공개 로그 manifest와 hash,
  평가 세 축, 미관측·예산·다음 결정.

처음부터 공개 도구/응답만 보존하며 비밀·계정 값·숨겨진 추론/signature를 수집하지 않는다.
출력 수집은 공개 text/tool/result 사건만 저장하도록 준비 단계에서 확인한다.
JSON 전체에 reasoning/signature가 섞인다면 디스크에 쓰기 전에 제외하고 공개 출력만 보존한다.
UTF-8을 깨뜨리지 않는 수집 방식으로 종료 코드·크기·파싱을 확인한다.
필요한 전달·기록 도우미는 사건 보존만 맡고 자동 후속 대화·판정·수정은 하지 않는다.
출력 수집 실패는 실행 실패와 구분하며 일부 출력만으로 성공을 확정하지 않는다.
최종 비용/토큰은 실제 제공된 값만 기록한다. 부모 합계에 포함된 자식 비용을 다시 더하지 않는다.

실험 결과·정제 근거는 maker에 색인하고 제품 전체 이력은 실험 refs에 둔다.
이번 설계 단계에서는 실행 결과표·주석을 채우거나 미실행 명령을 실행 근거로 만들지 않는다.
