# 현행 템플릿 개선 후보의 독립 검토

현재 인계 보완(2026-10-03 Asia/Seoul): 이 문서의 아래 후보 판단·32개 보고서 목록·실험 제안은 최초 검토 시점의 기록이다. 후속 사용자 지시로 현재 범위는 **조사와 보완안**이며 개발 실험은 별도 지시 전 시작·재개하지 않는다. 현재 결론은 [보완안](recommendations.md), 조사 범위·잔여 공백은 [coverage](coverage.md)를 따른다. 이후 [0018 middle](cases/0018-followups-middle.md)이 T06/07/09/10/11/12/13/15/16을, [authority](cases/0018-followups-authority.md)가 T14 권한·준비 수명과 T26의 주요 인도 사건을, [0001 후속](cases/0001-project-structure.md)이 T2 adapter와 T3 선택·지문 경계를 보완했다. 아래의 이전 미검토 목록을 현재 인계에 그대로 적용하지 않는다. 현재도 0018 pure GoalWatch 전 상태·retained authority·DTO 이식 전량과 0001 모든 adapter/선택 경계·94 gate 전량 감사는 미검토이며, 원 실행 로그와 실제 모델·OS의 한계는 남는다. 조사 중 작성된 0.1.9 source `ec47695`와 진입점 보완 `74e1148`은 검토 후보이며 main·전역 설치 반영이나 실사용 효과를 뜻하지 않는다. [0037](../../experiments/0037-openwebagent-history-feedback.md)의 부분 실행·조직 차단·공급자 인증 오류·사용자 중단을 보존하고, 완료된 비교 쌍·전이 평가가 없으므로 효과는 미입증으로 둔다. root 조율자의 독해·보완과 이 검토는 사람 수락이나 독립 제품 실행을 대신하지 않는다. 최초 입력 manifest와 원판 스냅샷은 그대로 보존했다.

**세 후보를 실제 개발 비교에 남기되, 현행 템플릿 결함으로 확정하지 않는다.** 우선순위는 첫 실제 연결을 앞당기는 계획 예시(C3), 앱 셸과 사용 상태에서 UI를 비교하는 탐색 예시(C2), 설계의 검증 경계를 계획에 넘기는 짧은 안내(C1)다. 현재 0.1.8에는 공유 계약·독립 기대·UI 관찰·통합판 검증이 이미 있다. 추가할 내용은 그 판단을 언제, 어느 실제 경계에 적용할지 명료하게 하는 것이다. 효과는 개발 재실험 전까지 미검증이다.

검토 기준일은 2026-10-03 Asia/Seoul이다. [조사 기준](baseline.md)의 배포 원본과 최초 WIP5를 구분했다. 검토 중 작업트리에서 진행 중인 `changes/` 이전 등 별도 변경은 WIP5에 포함하지 않는다. 이 검토는 [사례 보고서](cases/)와 고정된 현행 작성 지침을 대조한 독립 판단이다. 사례 작성자가 읽은 모든 Git 객체·PR 원문을 다시 읽거나 당시 제품 실행을 재현한 감사는 아니다. 입력 보고서 해시는 [비공개 입력 목록](../../../.local/research/openwebagent-template-history/20261003/analysis/candidate-review/input-manifest.json)에 남겼다.

## 후보 판정

### C1. 설계의 AC와 검증 경계를 연결

**조건부 채택: 작성 안내의 명료화.** 독립 기대를 먼저 정하라는 규칙은 이미 충분히 있다. 남은 질문은 설계가 약속한 효과를 어떤 실제 경계·상태·환경에서 구별할 수 있는지, 가상 경계가 무엇을 가리는지다.

독립 사건은 [0004](cases/0004-text2sql-user-console.md)의 스텁 UI 통과 후 실엔진 gold 소비 실패(#319→#321), [0010](cases/0010-sqllab-permission-repair.md)의 캐시/권한 분기를 피한 기존 시험, [0018](cases/0018-desktop-feature-port.md)의 실제 엔진 구독 상태와 후보 상태 차이다. [0026](cases/0026-text2sql-settings-followups.md)→[0028](cases/0028-description-save-race.md)의 순차 version 검사와 실제 동시 저장 차이는 하나의 연속 사건으로 센다. “검증 방법이 전혀 없었다”는 가설은 반박된다. 0006·0012·0013·0014에는 독립 기대와 실행 절차가 구체적으로 계획돼 있었다.

뒤에 도착한 [0015](cases/0015-sqllab-execute-path-defects.md)의 실제 파일·별도 프로세스 잠금 시험은 가짜 fixture의 사각을 직접 다룬 긍정 대조다. [0020](cases/0020-wsl-full-gate-reference.md)의 WSL full FAIL 보존과 축소 재측정 분리도 기존 지침이 처리하는 사례다. [0033](cases/0033-sqlexec-fetch-landing-confusion.md)은 리뷰 전 모델 관찰을 최종 절대경로 판의 효과로 바꾸지 않는 회귀 평가 입력으로 쓸 수 있다.

우선 수정 위치는 `tdd-optional/project/examples/skills/design-spec/SKILL.md`의 **Acceptance criteria** 항목 끝이다. 현재 문장 “Give consequential expected results a basis …”와 vague R을 proof로 복제하지 말라는 문장은 유지한다. 여기에 다음 의미를 한 문장으로 연결하는 것이 최소안이다.

> 결과를 가르는 AC에는 관찰할 실제 경계와 필요한 상태·데이터·환경을 식별하고, 가상 경계가 가리는 효과나 아직 실행할 수 없는 전제는 영향과 필요한 시점에 연결한다. 구체 명령·fixture 구성은 plan에서 정한다.

판단의 변화는 “409라는 기대를 적었으니 충분하다”에서 “같은 판을 읽은 두 요청이 실제 저장 경계를 통과해야 이 기대를 판별한다”로 옮기는 것이다. 모든 AC에 새 열·양식·명령을 복제할 필요는 없다. [TESTING-STRATEGY](../../../tdd-optional/project/docs/TESTING-STRATEGY.md)의 ‘먼저 정할 것’과 plan Proof가 이미 같은 내용을 처리한다면 해당 참조만 연결하고 추가 문장은 줄인다. 이 후보를 현재 템플릿의 검증 부재 결함으로 부르는 것은 기각한다.

### C2. UI 탐색에서 기존 컴포넌트·앱 셸·실사용 상태를 비교

**조건부 채택: 기존 탐색 예시의 선택지 보완.** [0018](cases/0018-desktop-feature-port.md) T00b는 실제 제품 컴포넌트를 Vite/Chromium에 마운트하고 DOM·PNG·초점을 비교했다. [0021](cases/0021-sqllab-ui-improvements.md)은 HTML 목업 대신 실행한 참조 제품의 캡처·측정값을 썼다. 둘 다 “HTML만 보았으므로 실제 컴포넌트를 쓰라”의 근거로 쓸 수 없다.

반복된 공백은 다른 곳이다. 0018의 Working 행 이동·picker 가림은 결합한 부모 배치에서 나타났다. 0021의 포털·토스트·Run→Stop·긴 오류 행은 제품 앱 셸과 동적 상태의 차이였다. [0025](cases/0025-settings-modal-pane-scroll.md)→[0027](cases/0027-sqllab-popups-owui-style.md)의 Esc 실패도 전역 앱 핸들러와의 결합에서 드러났다. 이는 서로 독립된 경계 사례를 제공한다. 한편 [0023](cases/0023-text2sql-settings-owui-style.md)의 첫 AFTER 스크롤 악화와 수정은 실제 사용 절차가 설계를 교정한 긍정 사례다. 0023·0025의 공통 PR #421을 성공 두 번으로 계산하지 않는다.

우선 수정 위치는 `tdd-optional/project/examples/skills/plan/examples/disposable-ui-exploration.md`의 **Order 1–3 / Risks**다. 현재 예시는 컴포넌트 재사용·키보드·viewport·가짜 API 한계를 이미 적었으나 대표 구현이 `spikes/request-confirmation.html` 하나여서 독자가 제품 비연결 HTML을 기본 절차로 좁게 읽을 여지가 있다. 예시 제목이나 모든 정책 파일을 바꾸기보다 다음 선택 근거를 넣는다.

> 배치가 질문이면 가벼운 mock을 쓰고, 기존 이벤트·포털·초점·스타일 결합이 질문이면 실제 컴포넌트를 격리된 제품 경로 또는 앱 셸에서 관찰한다. 기준 화면·상태·데이터와 가짜 연결을 표시하고, 해당 질문에 필요한 정상·오류·진행·긴 내용 조합을 고른다.

기존 “제품 route/build/import는 수정하지 않는다”는 **이 가상 예시의 범위**로 남기고 모든 UI 탐색의 금지 규칙으로 읽히지 않게 한다. 실제 UI 편입이 허용된 작업이면 현재 spec/plan 범위로 판단한다. 시각 비교에는 무엇을 보존할지와 사람의 최신 피드백을 연결한다. 0021의 Superset 목표에서 공용 칩으로 바꾼 D31 같은 새 선호를 최초 결함으로 다시 분류하지 않는다. 작은 수정마다 사용자에게 새 승인을 받거나 모든 상태 prototype을 만들게 하는 제안은 기각한다.

### C3. 가장 위험한 실제 연결을 첫 인도 순서에 배치

**우선 채택: 실행 상세의 순서 선택 예시.** 독립 역사 근거가 세 후보 중 가장 강하다. [0003](cases/0003-sqllab-port.md)은 API·부품이 순서대로 머지됐지만 H의 첫 실제 마운트에서 Run 봉쇄·사용자 문맥·rison 결함을 찾았다. [0004](cases/0004-text2sql-user-console.md)는 구현 #317 후 스텁 UI #319, 실엔진 #321 순서로 결합 오류를 좁혔다. [0005](cases/0005-performance-quality-fixes.md)의 초기 T18 후보는 owner/명령 부품이 있어도 실제 Session 소비자가 없었다. 0003 후속 0010·0011은 추가 독립 사례 수로 부풀리지 않는다.

추가로 읽은 [0001](cases/0001-project-structure.md) N1은 관측 writer가 임시 경로에 쓴 보고를 정리하고 다음 run의 reader는 다른 경로에서 찾는 결함이었다. 작은 gate 하나라도 생성→보존→다음 회차 읽기를 먼저 실행할 근거다. 활성화 전 리뷰에서 차단됐으므로 사용자에게 잘못된 cache를 제공한 사고로 쓰지 않는다. [0017](cases/0017-sqllab-port-defects.md)의 공유 네트워크 코어 우회는 위험한 연결이 UI/API 호출만이 아니라 배포 네트워크일 수도 있음을 보완한다.

0018의 구현 전 B/F 접점·공유 파일 표와 0021의 선행/병렬·하네스 설계는 “전체 인터페이스 설계가 없었다”의 반증이다. [0014](cases/0014-sqllab-query-time-unit.md)는 생산·기존 행 이행·프런트 계약을 같은 인도로 묶었고 0027도 공용 프레임→소비자의 순서를 지켰다. 추가할 판단은 공유 문서의 양보다 최초 실제 연결의 시점에 있다.

우선 수정 위치는 `tdd-optional/project/examples/skills/plan/references/execution-depth.md`의 **인도 지도와 작업 상세**, “큰 변경은 먼저 어떤 결과를 어떤 PR로 main에 넣는지…” 다음이다. 현재 ‘개별 테스트 GREEN 이후 최신 main과 합친 전체 계약·데이터·사용 흐름을 검증’과 ‘첫 인도’는 유지하되 다음 선택을 연결한다.

> 이번 인도에 영향을 주는 전체 공유 인터페이스와 대표 순서를 먼저 읽고, 가장 위험한 경계를 실제 소비자가 통과하는 작은 경로를 어느 작업에서 처음 실행할지 정한다. 모듈 내부 완료 뒤로 첫 연결을 미루는 경우에는 필요한 선행 작업, 그전의 대체 관측과 남는 가정을 설명한다.

여기서 실제 연결은 사용자 공개·운영 배포와 다르다. 격리된 후보나 허용된 시험 경로도 가능하다. health check만 연결했으면 그 범위만 기록한다. 계약 double은 유용하지만 실제 공급자 의미의 증명을 대신하지 않는다. 예상되는 선택 변화는 “서버 전부→화면 전부→마지막 E2E”에서 “한 사용자 행동→실제 API/저장 또는 엔진 효과를 먼저 연결→인접 동작 확장”이다. 모든 작업을 수직으로만 나누거나 기반 PR을 금지할 근거는 없다.

## 효과를 판별할 개발 사례 두 개와 도구 이전 한 회

아래는 **미실행 실험 제안**이다. 역사 보고서를 재작성하거나 계획만 검토하는 작업으로 대체하지 않는다. 실행자는 실제 코드를 만들고 선택한 사용자 흐름을 끝까지 실행해야 한다. 같은 시작 코드·업무 요청으로 기준판과 후보판을 각각 새 문맥에서 수행하고, 기대와 대표 입력은 실행 전에 고정한다. 현재 후보를 알고 있는 조사자가 일반 사용자 요청에 정답 구현을 숨겨 넣으면 지침 효과를 구별할 수 없다.

| 개발 사례 | 한정된 실제 구현 범위와 독립 관측 | 후보 효과를 구별할 부분 |
|---|---|---|
| A. 기존 앱의 설정 팝업에 저장·취소 흐름 연결 | 기존 dialog와 앱 셸을 사용하는 작은 화면. 가짜 입력만 쓴 초기 탐색 후 격리된 실제 API 저장까지 연결한다. listbox가 열린 Esc, 초점 복귀, 저장 실패 초안, 긴 오류 내용·좁은 패널을 해당 요구 범위에서 재현한다. 서버 저장은 별도 조회로 대조한다. | C2가 실제 셸의 이벤트/포털과 상태를 일찍 선택했는지, C1이 화면 성공과 저장 효과를 나눴는지, C3가 모든 부품 완성 전 첫 실제 저장 경로를 실행했는지 본다. 픽셀 수치로 심미 수락을 대체하지 않고 기존 화면과 사람 피드백의 기준을 남긴다. |
| B. 두 소비자가 같은 설명을 갱신하는 낙관적 동시 저장 | 두 작은 소비자→공유 저장소의 판 검사·성공/충돌 처리. 격리 DB에 실제 두 세션을 만들고 동일 판 동시 저장, 첫 행 생성, 순차 낡은 판, 관련 없는 유일 제약 실패를 관찰한다. 전체 제품·DB 방언 이식은 하지 않는다. | C1이 실제 트랜잭션 경계·독립 기대·실패 효과를 설계에 연결했는지, C3가 양 소비자와 저장소를 먼저 관통시켰는지 본다. 시험 double만 통과한 경우 실제 경합을 미검증으로 남겼는지 평가한다. |

최소 다섯 회는 **A 기준판/후보판, B 기준판/후보판, 후보판의 다른 도구 이전 한 회**로 구성할 수 있다. 다섯 번 모두 실제 개발·회귀·통합 결과를 남기고 계획 검토를 실행 횟수에 넣지 않는다. 기준판은 고정 0.1.8 또는 0.1.8+WIP5 중 하나로 실험 전에 명시해야 한다. 두 판의 차이를 세 후보 외 다른 정책 변경과 섞지 않는다. 현재 진행 중인 `changes/` 경로 이전 등을 두 비교군에 똑같이 반영할지는 실험 setup에서 고정한다.

도구 이전은 같은 후보·같은 개발 사례를 다른 실제 coding tool에서 독립 수행한다. 역사 도구가 확인된 사례에서만 그 도구를 원도구라고 쓴다. 역사 모델·추론을 모르면 **역사 모델 미상, 현재 가용 모델로 대체**라고 기록한다. 다른 도구에서 한 번 성공해도 도구 일반성이나 모델 우위를 입증하지 않는다. 실제 실행 수단이 없으면 이전은 미실행으로 남기며 이름만 바꾼 같은 실행으로 채우지 않는다.

비교에서 남길 것은 첫 실제 경계 실행 전후의 발견, 계약·계획의 수정 이유, 미검증 범위를 완료로 오인했는지, 독립 AC와 인접 회귀, 불필요한 승인·문서 중복·선행 확정의 증가다. 시간·토큰을 비교한다면 준비·실패·재시도·검토·수정까지 포함하고 누락을 밝힌다. A/B 각 한 쌍으로 인과 효과의 통계적 일반화를 하지 않는다. 기준판도 성공하면 후보의 추가 이득 미관측으로 기록한다. 후보가 더 많은 문서만 만들면 문장을 줄이거나 철회한다.

## 인계 제한

아래 목록은 middle·authority·0001 후속 보고서를 받기 전의 최초 검토 기록이다. 현재의 조사 범위는
상단 인계 보완과 [coverage](coverage.md)를 따른다. 특히 아래 T06–T16의 “별도 검토 여부 확인”은
그 당시 상태이며, 현재는 middle 후속 보고서가 연결돼 있다. 전량 코드·상태·실행 감사가 아닌 한계는 유지한다.

이 검토에서 읽은 사례 보고서는 0001, 0003–0018, 0020–0021, 0023–0033과 번호 없는 PR 보고서다. 총 30개 번호 사례에 0018 후반 보완·번호 없는 보고서를 더한 32개 보고서이며, 보고서 단위 대조를 원문 전체 재감사로 세지 않는다. 0002·0019·0022는 이 목록에 없으며 전체 모집단의 포함/제외 근거는 수집 색인 담당 결과와 결합해야 한다. 0007·0009·0012·0031의 미착수/문서 단계, 0016의 좁은 정적 수리, 0032의 후속 UI 표시 연결은 구현 실패 횟수로 일괄 계산하지 않았다.

0001도 T2 실제 adapter 전량, T3 선택/지문 전체, 94 gate 감사 원자료의 중요 미검토가 남는다. 후보 선정의 중간 판단을 전 개발건 조사 완료로 쓰면 안 된다.

0018의 [후반 보완](cases/0018-followups-late.md)은 T17·T19–25의 주요 계약·인도·후속을 추가 검토했다. T22 부모/T23 자식의 결합 배치와 T19 handle/T21 terminal 소비 경계는 C2/C3를 보강한다. 최초 파일럿의 미검토 목록을 그대로 현재 목록으로 쓰면 안 된다. 이 보완 이후에도 T06/07/09/10/11/12/13/15/16의 전체 사슬과 #435 private lifecycle·인증/정리 경합의 세부는 별도 검토 여부 확인이 필요하다. 보완 보고서도 전체 코드·모든 리뷰와 런타임을 감사하지 않았다. 추가 조사에서 선행 실제 연결이 이미 충분했거나 다른 원인이 드러나면 C3의 0018 지지 강도를 낮춰야 한다. 현재 C3의 근거는 0003·0004·0005만으로도 독립 반복 기준을 만족하므로 0018 미검토를 억지로 완료 처리할 이유는 없다.

현행 0.1.8의 중대한 재현 결함은 이 검토에서 실행하지 않았다. 역사상의 독립 반복 사건은 세 후보를 비교 실험에 올릴 근거이며 현재 문장 변경의 효과를 증명하지 않는다. 템플릿·제품·전역 설치를 수정하거나 commit하지 않았다.
