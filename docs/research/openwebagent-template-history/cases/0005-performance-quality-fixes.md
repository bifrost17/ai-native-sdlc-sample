H1은 **부분 지지와 강한 반증이 공존**: 최초 설계들이 철회됐지만 실제 데이터와 엔진 계약 학습이 원인이며 “설계 부족 때문에만 변경”으로 묶기 어렵다. 실 경합·provider binding·프로젝트 첫 전송은 선행 공유 계약/검증 부족을 드러냈다. H2는 **부분만 평가 가능**: T24 운영 UI와 T26 Desktop 앱 렌더링을 구별했고 T26은 보류라 시각 동등성 수락은 없다. HTML 목업 효과를 판단할 자료도 없다. H3는 **강한 지지**: owner/DB/transport/UI 단편 통과가 제품 첫 흐름을 보장하지 않았고, #365에서 draft→폴더 저장→첫 전송 순서가 깨졌다. H4는 **부분 지지**: 후보·병합판/실배포 방법은 구체화됐지만 #354 결합 뒤 전체 재실행과 #365 시퀀스 조합은 처음 검증 범위에서 빠졌다.

현재 0.1.8 정본은 첫 수직 인도, 공유 권위/실패 계약, 최신 결합판·실화면 검증, 미실행 표기를 이미 요구한다([기준 비교](../baseline.md)). 이 사례의 잔여 개선 후보는 **장기 재설계에서 철회된 계획을 현재 착수 입력과 명확히 갈라, 최초 제품 흐름과 위험한 순서 조합을 계획의 조기 관측 지점으로 놓는 예시**다. 템플릿 구현 결함으로 확정하기 전 프로젝트 계획 이탈·에이전트 경합 오독·후보/CI/운영 환경의 범위를 따로 봐야 한다. GitHub formal review API가 비었다고 자체 기록의 별도 독립 검토를 없었다고 말하지 않는다.
