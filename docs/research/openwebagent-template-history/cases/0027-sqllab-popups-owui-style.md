여섯 축: **의도 보존**은 0021 완료 후 SQL Lab 팝업을 합치고, 각 화면에 맞는 내비(목록+상세/섹션/데이터 소스)로 구현했다. **설계 충실성**은 `plan.md:35-55`의 명시적 이탈(5→3PR, 새 `SettingsTabNav`, 목록 상태·이력 debounce, 프레임 Esc 예외, PR-C 추가 Browser)까지 포함해 평가하면 높다. **계획 실행 가능성**은 PR-A→B→C 최신 main 순서와 파일·AC·브라우저 레인이 구체적이다. **PR·병렬 분할**은 공유 부품 먼저, 소비자 둘을 뒤에 둔 순차 경계가 실제 머지 SHA로 확인된다. **변경 피드백**은 각 PR의 독립 검토·코드 리뷰 발견을 후속 커밋에 반영했고 PR-B/C TDD 이탈을 숨기지 않았다. **검증·보고**는 레인 `d0027` 실제 앱·캡처·사용성 실측과 시험을 구분한다. PR-A 269파일 중 1실패, B 497 중 2실패, C 499 중 2실패는 각 PR 본문이 인접하지 않은 기존 소스 문자열 검사로 판단하지만 수정 전 판 재실행은 하지 않았다고 한다. `npm run check` 기존 7840오류 기준선은 변경 파일 신규 오류 0과 다르며 전체 PASS가 아니다. 원 실행 출력·rc는 이 조사에서 독립 확보하지 못했다.

사용자 가설: H1은 **부분 지지**(설계 뒤 구현에서 전역 Esc·실데이터 시각·초안 규칙을 구체화; 변경을 plan/spec에 기록), H2는 **지지**(정적 HTML/클래스가 맞아도 0025 Esc는 실제 앱에서 깨졌고 레인이 이를 잡음), H3는 **반증과 지지 혼합**(선행 0021 통합 순서를 지켰고 공통 부품을 먼저 머지해 큰 충돌은 피했으나 화면 사이 전역 이벤트와 데이터 소스 초안 통합 결함은 늦게 드러남), H4는 **부분 지지**(초기 plan의 레인·시험이 유효했고 B/C 일부는 구현 뒤 시험으로 이탈). 원인은 제품의 앱 이벤트/상태·실데이터 경계와 일부 계획 이탈이다. 0.1.8·WIP의 문서 갱신·검증 방식/이유/순서 규칙이 이미 있으므로 단독 템플릿 결함으로 중복 제안하지 않는다.
