판정: **검토 완료, 실행 증거에는 한계 있음.** 작은 결함 수정의 성공 대조 사례다. 기존 0024·0026의 `stale_version` 약속이 실제 동시 저장에서 깨지는 것을 발견했고, 저장소와 두 라우트의 경계를 함께 고쳤다. 새 문맥 구현 검토가 첫 저장·새 열의 500을, PR 코드 리뷰가 중복 열 이름을 경합으로 잘못 알리는 문제를 찾아 같은 PR에서 보완했다. 이 사례만으로 템플릿의 추가 통제가 필요하다고 결론 내리지 않는다.

## 여섯 평가축

| 축 | 판정·근거 |
|---|---|
| 의도 보존 | **대체로 충족.** intent의 “같은 version이면 한쪽만 성공, 다른 쪽은 409”가 spec FR01–03과 최종 코드로 이어진다. SQL Lab의 version 생략, 무변경, 복원은 FR04로 보존한다. 첫 표·열 500 수정은 새 범위가 아니라 FR02의 기존 500 금지를 채운 보완이다. |
| 설계 충실성 | **정적 확인.** 저장소의 재확인·기대+1, 이력 version 유일 제약, 라우트의 `StaleDescriptionVersion`/선별된 `IntegrityError` 변환이 설계와 대응한다. PostgreSQL·MySQL의 실제 동시성은 관찰하지 못했다. |
| 계획 실행 가능성 | **가능하되 기록 순서 한계.** T01/T02 저장소·라우트, T03 개발 스택, T04 검토 보완, T05 PR 리뷰 보완으로 작업과 AC가 연결된다. 초기 plan은 이미 완료 기록을 담고 있어 사전 수락·실제 TDD 순서의 독립 근거가 아니다. |
| PR·병렬 분할 | **적절.** 두 화면이 공유하는 저장소 불변식을 한 PR과 한 트랜잭션 경계로 고쳤다. 프런트 변경은 없고, 두 화면의 기존 409 처리 계약을 재사용했다. 별도 병렬 담당·핸드오프의 실행 사실은 확인되지 않는다. |
| 변경 피드백 | **실질적 보완.** 구현 검토의 첫 행 500과 코드 리뷰의 중복 이름 오탐을 같은 PR에서 수정하고, spec·plan에도 이유를 적었다. 복원 경합 등 범위 밖 지적을 닫힌 문제로 오인하지 않고 후속 후보로 남겼다. |
| 검증·보고 정확성 | **근거 경계가 비교적 명확하나 독립 실행 미확인.** plan은 5개 최초 RED, 100 GREEN, 검토 뒤 120, PR 리뷰 뒤 3 RED·123 GREEN과 `:3080` 8회/4회·23/23을 보고한다. 시험 코드는 최종 Git에 있다. 다만 컨테이너 명령·출력·프로세스 rc, 임시 e2e 스크립트는 수집하지 못했고 이번 조사에서 재실행하지 않았다. ## 사용자 가설과 원인 분리

1. **설계가 부족해 구현 중 변경됐는가?** 동시 저장의 핵심 경계는 최초 spec에 있었다. 첫 표·열의 행 유일 제약은 구현 검토가 뒤늦게 발견했고 FR02/AC08–10에 구체화했다. 이는 설계의 예외 경로 누락이라는 좁은 결론이다. 설계 전체가 부실했다거나 템플릿 결함이라는 일반화는 근거가 없다. 원인 후보는 제품의 제약 순서와 검토 사례 선택이며 현재 템플릿 책임으로 귀속하지 않는다.
2. **UI HTML과 실제 동작은 일치했는가?** 0028은 UI·HTML 파일을 바꾸지 않았고 백엔드 두 엔드포인트를 고쳤다. 기존 화면이 version을 보내고 409 초안을 처리한다는 0026 계약·소스는 확인했지만, 이 PR의 HTML 캡처나 브라우저 양방향 경합 관측은 없다. 따라서 화면 정합성 전체를 통과로 판정하지 않는다.
3. **모듈 늦은 통합이 전체 인터페이스·순서를 깨뜨렸는가?** 두 경로가 공유 저장소를 쓴다는 통합면을 바로 수정한 사례다. 뒤늦은 별도 모듈 착지나 병렬 충돌의 근거는 없다. 실제 인터페이스 누락은 최초 저장소 설계가 이력 version 충돌만 예상해, 그 전에 일어나는 표·열 행 충돌을 빠뜨린 점이다. 검토가 이를 드러내고 두 라우트 모두 보완했다.
4. **검증을 초기에 식별하지 못했는가?** TDD와 e2e의 조합은 plan에 있고, 수정 전 결함 재현도 문서가 보고한다. 하지만 첫 문서 커밋에 실행 완료 기록이 이미 있어 초기에 결정했는지는 확인되지 않는다. 첫 표·열의 실제 두 세션 시험은 검토 뒤 추가되었다. 완전히 미식별이라는 판단보다 **경계 사례를 나중에 보강**했다는 판단이 근거에 맞는다.

현행 배포 기준은 제작 저장소 0.1.8(`67739c8`), 미커밋 WIP 후보는 별도다. 0.1.8 plan 양식은 검증 방식·이유·독립 기대, TDD라면 구현 전 RED, PR 끝의 통합 확인, 변경·실행 기록을 이미 요구한다. 현행 WIP도 이를 유지한다. 이 사례는 그 통제가 유용했던 성공·보완 사례로 두고, 원본 로그 없는 TDD 시간 순서나 다른 DB 방언 성공을 템플릿 개선 효과로 계상하지 않는다. 제품 코드, 현재 템플릿, 정책은 이 조사에서 수정하지 않았다.
