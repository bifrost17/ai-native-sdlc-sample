## 유지할 실험 전제

원래 v1 tracker 코드와 세 시험, v10의 비정렬 네 행,
원래 초기 intent/spec/plan·색인을 새 제품에 재현한다. 후보 source와 설치 자산은 별도
template branch에 고정하고 그 위에 fixture main과 작업 branch를 둔다. 기존 0039 제품의
main·작업판·snapshot과 partial 판정을 보존한다.

root는 HUMAN(Codex simulated)으로 실제 응답을 읽고 같은 세 업무 사건을 진행한다.
hana 정확 일치 필터의 설계, 이유 없는 ID 정렬 제안, 이유를 명시한 파일 순서 제약 해제와
구현·검증·로컬 인도를 순서대로 다룬다. 첫 두 단계는 구현을 허용하지 않는다.
`design-spec`와 `plan` 사용은 0039와 같이 명시한다. feedback을 새로 이름으로 지시하거나
최종 plan 요약 갱신 정답을 HUMAN의 후속 메시지에 넣지 않는다.

예산은 parent 3회와 native verifier 최대 1회, 합계 최대 4회·15분이다.
사전 모델 응답이나 추가 인계 모델을 사용하지 않는다. 로컬 제품 인도이며 원격 PR·main 머지·
배포·전역 설치는 범위에 없다. 성공 여부에 따라 같은 사례를 추가로 반복하지 않는다.

## 중요한 설계 위험과 해석 경계

### 시작 업무의 동일성과 후보 교체를 분리해야 한다

`exact baseline`은 원래 업무의 초기 문서·코드·시험·fixture 바이트가 같다는 뜻이어야 한다.
후보의 PROCESS/REVIEW·plan 작성 안내·feedback·verifier는 의도한 변경 대상이다.
제품 전체가 0039와 바이트 동일하다고 쓰면 후보 설치와 모순된다. 같은0.1.10 버전 표기만으로
후보를 식별할 수도 없다.

0039의 실제 `setup/baseline-documents.json`과 `setup-product.py`를 읽었다.
원 초기 업무 문서의 실제 내용은 원 제품 main `d3c23f3`의 Git 객체와 대조할 수 있다.
최종 작업판이나 단계1·2 snapshot에서 초기 문서를 가져오면 이미 학습한 결정과 완료 흔적이
시작판에 섞인다. 새 baseline의 tracker/tests/requests와 초기 업무 문서·색인 지문은 원 main과
비교하고, 전달 자산의 차이는 source와 patch·설치 manifest에 따로 남긴다.
실행 전 이 구분을 확인하면 별도 모델 호출이나 제품 수정으로 통제를 늘릴 필요가 없다.

### HUMAN의 자연 응답을 고정 대본과 혼동하면 안 된다

0039의 Q1·Q2 번호와 질문 내용은 실제 응답에서 나온다. 새 에이전트가 다른 질문을 하거나
질문하지 않으면 그 응답을 읽고 같은 업무 결정을 전달한다. 존재하지 않는 Q1을 승인하는
원문 재생이나 빠진 plan 요약만 겨냥한 후속 지시는 관찰 조건을 바꾼다.
HUMAN의 모든 실제 입력을 보존하고 원 대화와 달라진 내용·이유를 보고서에 밝힌다.

초기 스킬 명시는 이미 조건의 일부다. feedback을 스스로 선택했다는 사건을 관찰하더라도
이 실행을 모든 스킬에 대한 무힌트 자연 채택으로 부를 수 없다. 명시 작성 스킬과 채택한
프로젝트 안내가 있는 같은 세 단계 업무 안에서의 선택으로 한정한다.

### 최종 요약만으로 검토 전 갱신을 증명할 수 없다

검토 요청 전에 올바른 요약을 작성한 경우, verifier가 누락을 지적한 뒤 고친 경우,
HUMAN이 인계 누락을 알려 고친 경우는 다른 사건이다. 최종 commit에 올바른 plan이 있다는
사실이나 commit 시각으로 이 순서를 추정하면 안 된다.

원문 edit/read/task 이벤트에서 native 검토 요청 시점의 plan·색인 바이트와 실제 실행 근거를
재구성하거나 요청 직전 snapshot을 남긴다. 작성 시각과 요청 input, 검토 반환 뒤 변경을
연결한다. 요청 전 요약에는 실제 끝난 구현·시험과 아직 진행하지 않은 최종 검토·commit·
사람 수락을 구분해야 한다. 이후 검토와 commit이 끝나면 남은 일을 다시 맞출 수 있다.
미래 자기 commit SHA를 먼저 넣게 하거나 순서만 맞추려고 반복 commit하지 않는다.

### 검토에 포함한다고 쓴 요청과 실제 대조는 다르다

parent의 task prompt가 plan·색인·근거 경로를 전달했는지 확인한다. child가 실제 해당 파일과
diff·Git 상태·실행 결과를 읽고 완료/미검증/다음 일을 대조한 기록도 확인해야 한다.
도구 호출 성공이나 `문제 없음`이라는 최종 답변만으로 전체 대조를 인정하지 않는다.
child의 native 설정·모델·variant와 실제 반환·parent 대기를 구분해 기록한다.
동작 검사만 수행했다면 최종 요약이 우연히 올바르더라도 검토 범위의 관찰은 미흡하다.

이 재시험은 plan 누락을 인위적으로 주입하는 검출 민감도 시험을 포함하지 않는다.
현재 자료가 서로 맞아 child가 이를 확인한 경우, 그 대조는 관찰할 수 있지만 낡은 요약을
항상 찾아낸다는 결론은 낼 수 없다. child는 발견을 보고하고 parent가 수정한다.
child 권한 표기만으로 실제 쓰기 차단을 증명하지 않는다.

### 예산이 완료 사실을 바꾸면 안 된다

15분은 첫 parent dispatch부터 마지막 종료까지의 실제 wall time으로 산정하고 native 시간을
포함한다. CLI dispatch 시간 합계와 wall time을 따로 둔다. 모델의 내부 tool round-trip은
parent/child 호출 수와 구분한다. native 재개나 추가 세션이 생기면 실제 호출 기록에 남긴다.
등록돼 있으나 미호출인 verifier와 반환되지 않은 검토도 각각 미관측·미완료다.

예산 종료 시점에 검토·commit·인도가 남았다면 그 상태와 보존판을 보고한다.
관찰을 채우기 위한 추가 HUMAN 힌트나 다섯째 모델 호출로 4회 재시험을 성공으로 바꾸지 않는다.
OpenCode CLI·provider/model metadata가 0039와 달라지면 환경 차이로 공개한다.
동일 공개 모델명이 실제 제공 모델의 불변성을 보장하지는 않는다.

보존한다. 원 보고·HUMAN 조건·oracle·제작 연구는 제품에서 읽을 수 없게 하고 인증·숨은 추론은
공개 기록에서 제외한다. 설치 확인과 스킬 목록은 실제 본문 접근의 대체 증거가 아니다.

## feedback 본문 읽기와 가능한 결론

feedback 본문 읽기를 HUMAN이 새로 강제할 필요는 없다. 이번 질문은 후보 프로젝트를 받은
에이전트가 같은 업무 사건에서 어떻게 행동하는지다. 설치는 정확히 확인하되 실제 읽기 여부는
원문 이벤트에서 관찰한다. 읽기 미관측을 이유로 실패를 없애거나 추가 호출하지 않는다.

| 실제 기록 | 허용되는 결론 |
|---|---|
| 설치·catalog만 확인 | 후보가 전달됐음; 본문 접근·사용은 미관측 |
| PROCESS/plan 안내 접근, feedback 본문 접근 없음 | 후보 프로젝트 안내 아래에서 관찰한 행동; feedback 본문의 실제 사용은 미관측 |

본문 접근을 확인해도 특정 문구의 인과 효과나 에이전트의 내부 판단을 입증하지 않는다.
접근이 없더라도 올바른 시점의 갱신과 최종 정합성 자체는 관찰할 수 있다.
양쪽 구분을 보고하면 문구 효과를 과장하지 않고 행동 결과를 보존할 수 있다.

0039 partial과 원 제품은 유지한다. 0040이 통과하면 새 후보·새 실행에서 같은 작은 업무의
현재 인계가 맞았다는 별도 결과를 남긴다. 단일 재시험은 성공률, 다른 도구, 새 독자의 인계,
강제 중단 복구, 모든 추천 전제 반증, 큰 누적 설계와 전체 SDLC를 입증하지 않는다.
