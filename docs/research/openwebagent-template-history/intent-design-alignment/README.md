# 설계 변경을 현재 의도와 연결하는 보완 설계

Status: activated candidate — 0.1.10 source·설치 확인 완료,0039 핵심 관측 통과/최종 plan 인계 부분

설계 책임자는 추가 요구·추천안·브레인스토밍 선택을 반영하기 전에 **바꾸려는 이유와 현재 의도의
관계**를 확인한다. 중요한 선택의 근거를 실제 spec의 관련 설계에 남긴다. 현재 목적을 유지하는
구현 방법 선택은 위임 범위에서 진행하고, 의도와의 중요한 충돌·근거 부족은 먼저 드러낸다.
기존 `sdlc-feedback`과 작성 안내를 보완하는 안을 추천한다. 새 의미 검사 훅·스킬·승인 단계는 기본으로 추가하지 않는다.

이 문서는 사용자 설계 위임에 따른 제안이다. source 기준은 `c724213`의 선택형0.1.9이며, 이후
제작 intent/spec/plan의 설계 범위만 개정했다. 그 설계 시점에는 활성 정책·스킬·훅·설치판을 변경하지 않았다.
설계 검토와 실제 효과를 분리한다. 후속 적용은 문서 끝의 2026-10-04 기록으로 구분한다.

## 사용자 문제와 북극성

사용자는 큰 설계에서 추가 요구와 브레인스토밍 결정이 왜 필요한지 보존되지 않아, 추천을 채택하거나
사람이 판단한 뒤에도 원래 의도와 다른 설계가 커지는 일을 경험했다고 설명했다. 반복 수정의 토큰과
위험을 줄이려는 요청이며 의도 없는 요구·설계 편입을 원인 가설로 제시했다. 특정 세션의 원인으로
독립 입증한 사실은 아니다. 0038의 plan 요약 누락도 이 원인 가설의 증거로 사용하지 않는다.

[북극성 intent 절](../../../verification/north-star-playbook.html#intent-md로-포착하기)은 요청자의 언어로
무엇·왜·제약을 기록하고 brainstorming 중 질문과 원저자의 정정을 통해 이를 다듬는다.
[요구·설계 절](../../../verification/north-star-playbook.html#요구사항과-design)은 같은 product owner가
spec을 아이디어와 대조해 명시된 문제를 푸는지, intent의 미결 질문이 답해졌거나 이월됐는지 검토한다.
spec과 intent의 쌍은 무엇을 요청했고 무엇을 결정했는지를 남긴다. 따라서 의도와 설계를 연결하고
우려를 편입 전에 드러내는 방향은 북극성과 맞는다. 아래 사건별 절차와 선택의 근거 표현은 팀의 보완 설계이며
플레이북이 새 훅·모든 결정의 짝 표·반복 승인까지 요구한다고 해석하지 않는다.

현행 규칙은 이미 의도 제약 대조·설계의 이유/대안·영향 문서 갱신을 안내한다.
[현재 안내 조사 전문](current-guidance.md)은 그 지침과 **요구로 굳어지기 전 제안의 목적·전제 확인**이라는
진입 공백을 구분한다. 기존 안내를 적용할 사건에서 누락했다는 사실과 지침 자체의 공백을 혼동하지 않는다.
[독립 설계 전문](astra-proposal.md)의 제안·반론을 함께 보존한다.

## 역할과 기록의 구분

- intent는 해결할 문제, 원하는 변화와 성공의 의미, 이유, 범위·제약을 요청자의 언어로 보존한다.
  모든 FR/NFR·기술 선택을 역작성하거나 의도 항목을 전부 번호로 만들지 않는다.
- spec은 요구/AC와 구조·동작·계약을 결정한다. 중요한 선택에 의도·현재 계약·정책·관측 근거를
  연결하고, 그 선택이 왜 문제를 해결하며 어떤 의도를 보존하는지 설명한다.
- plan은 현재 spec에서 실행·검증·PR·인계를 연결한다. 설계 근거의 변경이 실행 의미를 바꾸면
  해당 작업을 갱신한다. plan에서 중요한 설계를 새로 결정하거나 과거 spec을 현행 정본으로 승계하지 않는다.

추천안은 해결 방법이며, 검증하지 않은 전제는 가정이다. 사람의 채택은 그 제안의 해당 범위에 대한
권한으로 사용한다. 추천에 딸린 다른 목표·제약 변경까지 자동 승인됐다고 확대하지 않는다.
반대로 기존 의도도 고정 불변이 아니다. 사용자가 목적·제약을 명확히 바꾸면 이전 내용과 바뀐 이유를
보존하고 현재 intent를 갱신한다. 이미 명확하게 받은 결정을 다시 승인받지 않는다.

## 설계에 반영하기 전의 짧은 대조

후속 요구, 설계를 바꾸는 brainstorming 선택, 에이전트 추천의 채택, 중요한 발견·전제 반증이 사건이다.
모든 대화·표현 수정·내부 리팩터링이 이 사건인 것은 아니다. 현재 세션에서 같은 판의 관련 intent 문단과 최신 결정을
이미 확인했고 그 내용이 바뀌지 않았다면 그 문맥을 사용한다. 판/결정이 바뀌거나 문맥을 잃었으면 현재 내용을
확인한다. 파일 전체를 반복해서 읽거나 별도 모델을 매번 호출하지 않는다.

설계 담당자는 실제 편입 전에 다음을 같은 대화에서 대조한다.

1. **출처와 이유:** 무엇을 원하는지와 왜인지의 근거를 현재 intent·직접 발언·확인된 관측에서 찾는다.
   사용자 요청, 에이전트 제안, 아직 확인하지 않은 가정, 실제 채택 결정을 구별한다.
   이유가 없으면 가능한 해석을 추정으로 표시하며 사용자 의도인 것처럼 문서에 쓰지 않는다.
2. **현재 의도와 영향:** 해당 문제·기대 결과·제약을 계속 만족하는지, 어느 목적을 더 잘 해결하는지,
   무엇을 약화·대체하는지 설명한다. 사용자 선택의 사실 전제도 중요한 것은 확인한다.
3. **진행 또는 확인:** 위임과 기존 결정으로 명확한 범위는 진행한다. 목적·고정 제약과 중요한 충돌,
   큰 재작업을 만드는 이유 불명, 선택의 중요한 전제 반증이 있으면 영향을 설명하고 빠진 결정만 묻는다.
   영향받는 편입을 미정으로 두되 독립된 설계 작업은 계속할 수 있다.
4. **정본에 반영:** 의도가 그대로면 intent를 유지하고 spec의 관련 요구/설계·근거와 영향 plan을 고친다.
   실제 목적·제약 또는 이를 이해하는 핵심 배경이 바뀌면 intent의 해당 산문부터 개정하고 하류 문서를 맞춘다.
   잘못 기록된 의도/배경은 정정하고 목표가 같아도 낡은 제약은 남기지 않는다. 구현에 들어가기 전
   개정하고 해당 구현과 함께 커밋하는 기존 절차를 따른다.

의도와의 연결은 “intent 링크가 있다”거나 “사람이 좋다고 말했다”로 끝내지 않는다. 중요한 설계의
인과를 설명할 수 있어야 한다. 정책이나 기술 제약에서 나오는 설계에는 그 출처·필요성과 사용자 목표에
미치는 영향을 적는다. 모든 설계를 사용자 발언에서 억지로 도출하거나 그럴듯한 why를 발명하지 않는다.

| 상황 | 진행·기록 방법 |
|---|---|
| 이유·의도 관계가 명확하고 위임 범위 안의 선택 | 질문 없이 선택하고 중요한 설계의 근거를 짧게 남긴다. |
| 사용자 의도는 그대로인 구체 요구/계약 개정 | 현재 intent를 대조하고 영향 spec/plan을 개정한다. 형식적인 intent 변경은 하지 않는다. |
| 중요한 이유가 빠지고 서로 다른 해석이 설계를 크게 바꿈 | 구체 영향과 해석을 보여 주고 결정에 필요한 한 질문을 한다. 해당 편입은 미정으로 둔다. |
| 기존 목표·고정 제약과 충돌하지만 의도 변경은 불명확 | 충돌하는 두 내용·대안·비용을 설명한다. 설계 위임만으로 목표를 교체하지 않는다. |
| 최신 발언이 목적/제약 변경을 명확히 지시 | 범위와 이유를 현재 intent·하류 정본에 반영한다. 같은 결정을 다시 묻지 않는다. |
| 추천의 중요한 사실 전제가 틀렸거나 새 근거로 무너짐 | 기존 추천의 잘못된 전제와 영향을 인정한다. 이미 선택됐어도 근거를 정정하고 대안/필요한 재결정을 제시한다. |
| 목표 간 trade-off가 이미 허용됨 | 허용된 우선순위/범위로 판단한다. 모든 목표를 동시에 완벽히 만족한다고 쓰지 않는다. 미결 우선순위만 확인한다. |
| 합의한 설계와 다르게 구현된 결함 | 구현을 고친다. 결과에 맞춰 intent/spec을 바꾸어 정당화하지 않는다. |

중요성은 사용자 결과·범위·고정 제약·공유 계약·상당한 비용/재작업에 미치는 영향으로 판단한다.
일반적인 내부 분해나 작은 문구 수정에 같은 부담을 주지 않는다. 사람의 결정에 이견이 있으면 원래 목표와
구체 영향을 근거로 정중하게 설명한다. 사실상 가능한 선택의 trade-off를 알고 유지하겠다는 명확한
결정을 받았다면 그 범위 안에서 진행한다. 목표 변경·정책 예외의 권한은 기존 프로젝트 역할을 따른다.

## 실제 spec에 남기는 근거

기존 SP의 인과 설명·대안·미결 자리에서 중요한 개정의 **요청/선택 → 의도 구절 → 설계 이유/보존·긴장**을
짧게 읽을 수 있게 한다. 현재 문서 경로·관련 절과 필요하면 기준 판을 사용한다. intent에 새 ID를 강제하거나
전수 매핑 표·별도 결정 장부를 만들지 않는다. 같은 이유가 여러 SP를 묶으면 공통 설명에서 연결한다.

아래는 작성법 예시이며 실제 제품 요구나 수락 기록이 아니다.

```text
SP02 조회 화면
의도 근거: intent.md의 Proposed outcome “기존 화면에서 여러 결과를 빠르게 비교한다”.
후속 선택: 필터를 유지한 채 결과를 더 볼 수 있게 해 달라는 요청.
선택 이유: 공통 표 컴포넌트의 펼침 범위를 늘린다. 비교 순서와 기존 필터를 유지한다.
기존 화면 전체를 새 카드 UI로 바꾸는 대안은 비교 밀도와 기존 UI 유지 제약을 약화해 이번에는 채택하지 않는다.
```

“카드로 바꾸자”라는 요청만 왔고 비교 목적과 기존 UI 유지 제약이 충돌하면, 카드가 해결하려는 불편과
허용할 trade-off를 묻는다. 반면 사용자가 이미 “한 항목을 자세히 보는 데 목적을 바꾸겠다”고 명확히
지시했다면 그 결정으로 intent와 설계를 갱신한다. 같은 질문을 반복하지 않는다.

## 큰 설계와 새 세션에서의 적용

초기에는 현재 목적·핵심 제약·이번 미결만 짧게 확인하고, 큰 설계를 바꾸는 중요한 선택을 해당 시점에
대조한다. 대량 문서 작성 뒤 이유를 만들어 맞추지 않는다. 수많은 내부 선택을 순차 승인받는 방식도 쓰지 않는다.
주요 경계·가정·trade-off가 정리된 설계 구간에서 기존 설계 검토를 재사용하고, 변경 영향이 없는 범위는 반복 검토하지 않는다.
작은 선택이 누적돼 대상·성공의 모습·비용을 바꾼 경우도 기존 설계 묶음 인계에서 대조한다.
전체 설계 인계의 선언된 정본 전체 검토는 유지한다. 좁은 변경 영향 검토를 전체 정합성 통과로 확대하지 않는다.

대화의 중요한 새 선택은 결정한 시점에 실제 정본에 남긴다. 새 세션은 현재 intent와 최신 spec의 관련
근거·미결, plan/실제 색인과 사용한 판을 읽는다. 과거 원 요청을 보존하되 최신의 명시적 개정을 과거
의도와 혼동하지 않는다. 정본에 없는 중요한 이유를 추측해 일을 이어가지 않는다.
독립 검토자는 요구 충족뿐 아니라 “이 선택이 현재 의도의 문제를 계속 해결하는가, 설명의 전제는
확인됐는가, 목적 변경을 설계 위임에서 과도하게 추론했는가”를 기존 설계 검토에서 확인한다.
새 문맥·강한 모델도 같은 잘못된 전제를 공유할 수 있으며 기계적인 의도 보장으로 보고하지 않는다.

## 훅과 다른 수단의 선택

| 방안 | 가능한 효과·비용 | 이번 결정 |
|---|---|---|
| 기존 스킬의 편입 전 의미 대조·중요 선택 근거 | 왜를 확인하는 시점이 앞당겨진다. 현재 세션 문맥을 활용하며 중요한 미결만 질문한다. 판단 실수는 가능하다. | 기본 추천 |
| 기존 설계 검토의 의도/전제 항목 보강 | 큰 구간·중요 개정에서 잘못된 목표나 전제를 다시 읽는다. 기존 검토 범위를 사용한다. | 함께 적용할 설계 |
| 기존 U7 선택 hook | 이미 의미 판단한 결과의 필수 개정 문서 포함을 확인한다. intent가 실제 개정된 경우만 그 경로를 선언한다. | 실행 계약 그대로 재사용 가능 |
| spec 변경 시 intent 파일 변경/짝/해시를 항상 검사 | 두 파일의 변경/존재는 확인하지만 목적 일치는 모른다. 목적이 같은 올바른 설계도 불필요한 intent 편집을 하게 된다. | 추가하지 않음 |
| 매 설계 편집마다 별도 모델 검토 훅 | 모델 오류·허위 일치 가능성이 있고 지연/비용·중복 검토가 늘어난다. | 추가하지 않음 |
| 독립 기본 intent 검토 스킬/장부 | 현재 feedback·작성/설계 검토와 책임이 겹치고 발견/설치/상태의 부담이 생긴다. | 현재 근거로는 추가하지 않음 |

U7 hook의 JSON 필드나 기계 판정은 늘리지 않는다. `documents`에 intent 경로를 넣는 것은 기존 의미
검토에서 실제 개정이 필요하다고 판단한 경우다. 빈 목록·재계산·잘못된 이유로 통과할 수 있으며
의도-설계 짝 확인을 의미 정합성의 통과로 부르지 않는다. 템플릿이 팀 스킬 설치를 자동 강제하지도 않는다.

## 후속 구현 위치와 검증 계획

아래는 **후속 구현 제안**이다. 이번 설계에서 활성 source에 적용하지 않는다.
우선 feedback·design-spec의 변경 진입을 정리하고 PROCESS에 짧은 정책 연결을 둔다. 나머지 행은
현재 표현과 실제 충돌/중복을 대조해 필요한 경우에만 맞춘다. 모든 파일의 수정 자체가 완료 조건은 아니다.

| 실제 경로 | 보완할 의미 | 부담 제한 |
|---|---|---|
| `tdd-optional/project/docs/PROCESS.md` | 후속 요구/중요 설계 편입의 이유·현재 의도 대조, 불명확한 충돌만 확인 | 기존 단계별 인계·구체성 절에 짧게 연결, 새 승인 절 없음 |
| `tdd-optional/org-skills/skills/sdlc-feedback/SKILL.md` | description/변경 진입에 brainstorming 선택·추천 전제와 편입 전 목적 대조 | 같은 개발 세션, 매번 verifier 호출 없음 |
| `tdd-optional/project/examples/skills/design-spec/SKILL.md` | 실제 정본 편입 전 의도 관계·전제·긴장/결정 이유의 책임 | 작성 스킬의 명시 선택 유지 |
| `tdd-optional/project/templates/spec.md` | 현재 근거·인과 설명이 충분하면 유지; 누락이 있으면 중요한 개정의 의도 연결·선택 이유만 안내 | 새 전수 표·필수 열 추가 없음 |
| `tdd-optional/org-skills/agents/sdlc-verifier.md`, `tdd-optional/project/REVIEW.md` | 기존 설계 검토에서 현재 문제 해결·목적 변경/추천 전제 대조 | 기존 검토 이벤트만 사용 |
| `tdd-optional/project/examples/skills/design-spec/examples/` | 위임 내 정상 개정·중요 충돌/전제 반증의 짧은 예시 | 기존 예시 범위에서 추가/보완, 큰 교육 패키지 없음 |

capture-intent는 이미 해결책과 목적을 구분하므로 현재 안내를 먼저 사용한다. plan에는 근거가 바뀐 설계와
작업을 연결하는 현행 규칙을 유지한다. 추후 구현에서 실제 충돌이 발견된 부분만 보완한다.
Codex·Claude 공통 source/검토 기준을 함께 맞추고 Codex patch dry-run/적용·동반 자료·Claude strict 확인을
실행한다. OpenCode 전달본도 공통 의미를 유지하는지 확인한다. 버전·설치판 갱신은 실제 구현 인도 때 처리한다.

후속 효과 검증은 사용자 지시 후 고정 입력·실제 대화·개정 순서·새 세션 인계를 관측한다. 정상 사례와
실패 복구를 구분하며 이번에 시뮬레이션 문답으로 행동 통과를 주장하지 않는다.

| 검증 입력 | 중요한 기대 | 인접 회귀·한계 |
|---|---|---|
| 목적/why가 이미 명확한 작은 변경 | 질문 없이 영향 spec/plan만 개정, intent 형식 수정 없음 | F01 정도에 장부·질문·추가 모델 부담이 생기지 않음 |
| 추가 UI 요구가 기존 비교 목적/일관성 제약과 긴장 | 편입 전 구체 충돌과 결정에 필요한 질문, 근거를 관련 설계에 보존 | 모호한 심미성을 자동 통과로 하지 않음 |
| 에이전트 추천의 중요한 전제가 새 관측으로 반증 | 추천 오류·영향·대안 설명, 의도와 합의 범위 유지 또는 명시 개정 | 이미 채택됐다는 이유로 전제를 숨기지 않음 |
| 사람이 목표/제약 변경을 명확히 지시 | 기존 결정 권한으로 intent부터 실제 하류 정본 갱신 | 원래 의도 고수·중복 승인으로 명시 지시를 방해하지 않음 |
| 큰 설계 일부와 새 세션 인계 | 현재 intent·관련 spec 근거·미결과 plan만으로 목적/선택/다음 일을 설명 | 원문 대화가 없다는 이유로 이유를 발명하지 않음; 추적의 형식이 의미 검토를 대신하지 않음 |

대체로 이 중요한 흐름을 지키는 수준을 목표로 한다. 실패가 나오면 실제 설치/읽기·권한·지침 공백과
충분한 지침의 미준수를 구분한다. 결과가 불명확하면 보류하며 실수마다 훅·규칙을 늘리지 않는다.

## 보존과 현재 한계

현재 안내·독립 제안·정본·적대적 리뷰를 각각 전문으로 남기고 [원본 안내](../originals.md)의
세션 공개 응답·도구 값·바이트 스냅샷/manifest에 연결한다. root는 통합 설계를, 제안자는 제안을,
검토자는 발견을 소유한다. 중요한 지적의 최초 상태와 후속 개정을 함께 보존한다.
사용자 요청 원문은 `.local/research/openwebagent-template-history/20261003/intent-design-alignment/request-<sha256>.md`에
원문 그대로 보존하고 `request-manifest.json`에서 원 세션·행·시각·길이·해시를 연결한다.
이 문서만으로 실제 누락율·토큰 절감·설계 품질 개선을 입증하지 않는다. 의도 의미를 완전히 보장하거나
사람/에이전트 판단 실수를 막는 하네스가 목표가 아니다. 이번 인도는 설계·검토이며 활성 적용·실험은 남는다.
