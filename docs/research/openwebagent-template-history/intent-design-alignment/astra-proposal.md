# 의도와 요구·설계 개정의 정합성 보완안

Status: draft. 작성일: 2026-10-03, Asia/Seoul.
범위: 독립 설계 제안. 활성 정책·스킬·훅 변경, 설치, 실험, 제품 구현은 수행하지 않았다.

추가 요구를 설계에 반영하기 전에, 기존 세션이 그 요구의 이유와 현재 의도 사이의 관계를 짧게 확인하도록 권고한다. 필요한 근거는 spec의 기존 요구 근거와 설계 설명에 남긴다. 문제·기대 결과·제약이나 그 이해에 필요한 배경이 달라질 때만 intent의 해당 문장을 고친다. 큰 설계에서도 모든 요구를 intent에 되써 넣거나 모든 개정에 질문·승인·검토 모델을 붙이지 않는다.

## 기존 지침과 남은 공백

“의도를 확인하라”는 일반 규칙은 이미 있다. 의도가 그대로면 고치지 말라는 제한, 구현 전 영향 문서 개정, 정본 참조, 사람의 기존 결정을 재사용하라는 제한도 있다. 이를 새 원칙처럼 여러 파일에 다시 붙이면 길이만 늘어난다.

남은 위험은 추가 요청을 해석하는 시점에 있다. 에이전트가 추천한 해법을 사람이 “좋다”고 채택하면, 해법 채택이 그 해법의 사실 전제와 비용까지 검증한 것으로 번질 수 있다. 이후 spec·plan·코드가 서로 잘 맞아도 원래 해결하려던 문제와 멀어질 수 있다. 최종 diff 역추적은 이미 지출한 설계·구현 비용을 되돌리지 못한다.

따라서 보완하려는 것은 다음 두 판단이다.

- 추가 요구가 현재 목적을 구체화하는지, 수단만 바꾸는지, 목적·제약 자체를 바꾸는지 먼저 구별한다.
- 결정이 내려졌다는 사실과 결정의 전제가 맞다는 사실을 구별한다. 사람이 선택한 방안도 기존 목표·확인 사실·정책과 충돌하면 근거와 대안을 제시한다.

장기 대화의 작은 선택들이 누적되어 큰 전환이 되는 경우도 포함한다. 개별 요청마다 형식 검토를 추가하는 대신, 기존 설계 묶음 인계에서 누적 결과가 여전히 같은 문제를 해결하는지 확인한다.

0038은 이 공백의 직접 실증이 아니다. 그 사례의 확인된 실패는 이미 명시된 현재 plan 요약 갱신을 놓친 것이다. 반면 북극성의 0024 주석은 제약이 바뀌었는데 상류 문장이 남은 실제 관측으로, 목표의 동일함만 확인해서는 부족하다는 근거가 된다. 어느 한 사례도 이번 보완의 효과나 실패율을 입증하지 않는다.

## 추천하는 판단과 기록

### 요청을 받는 순간

실제 의미가 있는 요구·설계 변경을 받으면, 현재 intent의 문제·기대 결과·제약과 관련 spec 결정을 함께 읽는다. 현재 세션에서 같은 판을 읽었고 달라지지 않았다면 다시 읽어 토큰을 쓰지 않는다. 문구 수정, 설명 보강, 계약을 유지하는 내부 분해까지 매번 이 사건으로 취급하지 않는다.

작성자는 요청과 기존 기록에서 이유를 찾는다. 명시된 이유가 있으면 사용하고, 앞서 합의한 문제로 충분히 설명되면 그 연결을 사용한다. 빈칸을 메우기 위해 사람의 동기를 만들어 쓰지 않는다. 단순 기능 추가라도 독립된 목적을 해결한다면 별도 개발건이나 후속 범위가 적절한지 기존 색인 규칙으로 판단한다.

해당 판단은 기존 spec 근거 칸이나 SP의 선택 설명에서 읽을 수 있어야 한다. 모든 요구에 새 열을 붙이거나 같은 문장을 반복하지 않는다. 기록량은 의도와 선택 사이에서 잃기 쉬운 의미에 비례한다. 이미 `R2: intent 제약`, `SP01: 기존 배열 순회로 충분`처럼 이유와 보존 조건이 읽히면 별도 문장이 필요 없다.

새로 남겨야 할 때는 보통 다음 정도면 충분하다. 아래는 합성 예시이며 실제 사용자 결정이 아니다.

> 재접속 후 처리 경과를 알 수 없어 반복 문의하는 문제를 줄이려는 선택이다(intent의 Problem). 오너는 알림에서 결과 내용을 숨기고 처리 상태만 보이도록 결정했다. 기존 상태 조회 API의 결과 열람 권한은 유지한다. 서비스 전체 결과 기밀성을 새로 약속하는 변경은 아니다.

이 문장의 역할은 요청의 이유, 영향을 받는 범위, 남는 제약을 설계와 묶는 것이다. 역할·기한·ID·승인 표를 매번 채우는 장부로 확대하지 않는다.

### 지식과 결정의 구분

| 구분 | 다루는 방식 |
|---|---|
| 제안 | 채택 전 해법 후보로 둔다. intent의 확정 제약이나 spec의 결정으로 자동 승격하지 않는다. |
| 가정 | 근거가 아직 없는 전제다. 틀렸을 때 바뀌는 결정과 확인 시점을 필요한 경우에만 적는다. |
| 사람의 결정·명시 지시 | 실제 선택과 허가 범위를 사용한다. 같은 답을 재확인하지 않으며, 결정이 확인 사실까지 만든다고 보지 않는다. |
| 확인 사실 | 관측·공식 정책·검증 가능한 입력 등 확인한 출처와 범위로 표현한다. 오래된 spec의 서술은 현행 사실로 자동 승계하지 않는다. |
| 추론 | 기존 근거에서 작성자가 연결한 설명임을 드러낸다. 결정에 민감한 추론을 요청자의 발언처럼 쓰지 않는다. |

전부에 고정 태그를 붙일 필요는 없다. “오너가 요청했다”, “관측 결과”, “현재 가정”처럼 문장 안에서 구분돼도 된다. 중요한 추천은 채택되기 전에 기대 이익, 남는 위험, 선택을 좌우하는 가정을 함께 설명한다. 사용자의 짧은 동의에 설명하지 않았던 비용이나 범위 전환까지 포함시키지 않는다.

### 질문과 반론

추가 요구의 이유를 모른다고 항상 멈추지 않는다. 기존 목표에 맞는 작은 가역적 선택이고 권한·데이터·큰 비용·공유 계약에 영향을 주지 않으면, 가장 좁은 해석과 근거를 밝히고 허가된 범위에서 진행한다. 이유가 불명확하고 답에 따라 구조·범위·성공 기준이 달라지면, 선택을 가르는 질문 하나를 우선한다. 이미 읽을 수 있는 자료의 사실은 먼저 조사한다.

합성 질문 예시:

> 캐시 추가는 재접속 지연을 줄이려는 요청으로 이해했습니다. 지금은 최신 상태를 놓치지 않는 것이 우선인데, 일정 시간 지난 값을 보여도 되는 요구로 바뀐 것인지가 설계를 가릅니다.

실제 대화에서는 미정인 선택을 짧은 질문으로 제시한다. 목적이 명확하면 해결책의 세부를 묻는 대신 작업한다. 답이 필요한 것은 영향받는 선택이며, 독립 조사·현재 합의 범위의 작성까지 모두 멈추지 않는다. 질문 응답의 지연이나 침묵을 동의로 해석하지 않는다.

사용자의 판단이 관측 사실이나 기존 제약에 어긋나면 정중히 반론한다. 예를 들어 “전체 목록을 내려주고 화면에서 가리면 권한은 유지된다”는 결정에 대해, 수신자가 이미 데이터를 받는다는 경계와 기존 접근 제한을 설명한다. 이어 서버에서 권한 범위를 제한하는 대안을 제시한다. 반론은 선택의 의도를 공격하지 않고, 전제·영향·대안에 집중한다.

이때 세 권한을 구별한다. 사실의 옳고 그름은 선호나 승인의 대상이 아니므로 증거를 확인한다. 사업 목적·우선순위 변경은 해당 오너의 결정이다. 정책 예외는 실제 정책 권한자의 결정이며, 일반 요청자가 “그냥 하자”고 했다고 정책이 바뀌지 않는다. 반대로 정책이 아닌 에이전트의 취향을 오너 결정을 막는 규칙으로 만들지 않는다. 근거와 비용을 이해한 오너가 자기 권한 범위의 목표 변경을 명시하면 그 결정을 반영한다.

### 의도를 바꾸는 경계

중요한 변경에서 현재 의도의 문제·결과·제약이나 이를 해석하는 핵심 배경이 달라지면 intent의 해당 본문을 개정한다. 과거 문제 서술이 사실과 다르거나 이유가 빠져 다음 독자가 목표를 다르게 해석할 경우에도 해당 문장을 정정·보충한다. 목표가 같다는 이유로 낡은 제약을 남기지 않는다.

반대로 요구가 상세해지거나 같은 목적의 기술 수단이 바뀌었다는 이유만으로 intent를 늘리지 않는다. 새 세부 이유가 해당 SP의 기술 선택만 설명하면 spec에 둔다. 상류에 보존할 필요가 있는 배경과 설계 선택의 근거를 구별한다.

기존 의도와 새 요청이 충돌하면 두 구절과 영향을 먼저 드러낸다. 이미 명시된 목표 변경 지시와 권한이 충분하면 그에 따라 개정하며 같은 결정을 다시 묻지 않는다. 새 해법 선택만으로 목표 교체까지 허용됐는지는 불명확하면, 영향을 받는 결정만 확인한다. 어느 경우에도 먼저 intent를 새 해법에 맞춰 고쳐 충돌이 없었던 것처럼 만들지 않는다.

현재 본문에는 현재의 이해를 둔다. 개정 이유와 결정의 출처는 기존 spec·PR·보존 대화에 연결하고 Git 이력은 유지한다. intent에 모든 대화·폐기안·설계의 진화를 쌓지 않는다. 중요한 목적·제약 개정은 spec의 요구·AC·선택 근거와, 존재한다면 plan의 영향 작업·검증으로 이어진다. 아직 plan을 만들 단계가 아니면 연결할 후속 범위만 남기며 없는 plan을 만들지 않는다.

## 사건별 처리

| 사건 | 판단·진행 | 문서 영향 |
|---|---|---|
| 오타, 의미가 같은 설명, 계약 불변 내부 정리 | 질문 없이 수정 | 실제 의미가 달라진 문서만. intent 개정 없음 |
| 기존 목표를 구체화하는 추가 요구, why 명확 | 기존 답과 근거로 진행 | 관련 spec·AC, 필요한 plan. 기존 근거가 충분하면 새 기록 없음 |
| why 불명확하나 작은 가역적 선택 | 좁은 해석·추론을 밝히고 진행 | 필요한 spec 설명. 새 승인 없음 |
| why에 따라 공유 구조·범위·비용이 크게 달라짐 | 자료 확인 후 미정 선택만 질문 | 기존 Open questions에 영향과 필요한 시점. 의존 설계의 준비 완료 주장 제한 |
| 에이전트 추천을 사람이 채택 | 채택 범위와 근거 전제 대조 | 사실로 검증되지 않은 전제는 가정으로, 선택 근거는 SP에 |
| 사람 결정이 확인 사실과 충돌 | 증거·영향·대안 제시 | 틀린 사실을 계약으로 굳히지 않고 의존 결정을 해소 |
| 목적·제약과 충돌하나 변경 의사 불명확 | 기존 구절과 새 결과를 비교해 필요한 결정 확인 | 충돌을 우려에 기록. 임의 intent 교체 금지 |
| 권한자가 목적·제약 변경을 이미 명시 | 재질문 없이 실제 변경 반영 | intent 해당 부분, spec 근거·요구·AC, 존재하는 plan |
| 정책 충돌 | 실제 정책 출처·권한 확인 | Flagged concerns와 해당 정책 오너. intent 수정으로 예외를 만들지 않음 |
| 코드가 같은 계약을 위반 | 구현 결함으로 수정 | spec을 결함에 맞춰 바꾸지 않음. 필요 시 기존 plan의 수정·검증 작업 |
| 장기 설계의 묶음 인계·재개 | 현재 의도와 누적 변경·미결 영향 대조 | 기존 spec 진입점·현재 plan 요약. 새 전역 상태 장부 없음 |
| 독립 목적의 추가 기능 | 기존 개발건과 결합 이유 판단 | 기존 색인 규칙에 따라 후속 건 연결 가능. 폴더마다 새로운 승인 단계 없음 |

## 큰 설계와 비용 관리

spec 진입점은 전체 문제·범위와 설계 정본의 위치를 안내하고, 각 정본은 자신이 책임지는 결정과 필요한 의도 구절을 참조한다. 이미 있는 SP·FR/NFR·R·AC를 사용한다. intent 문장 전부에 식별자를 부여하거나 FR별 역매핑을 강제하지 않는다. 읽을 수 있는 경로와 절만으로도 연결이 분명하면 충분하다.

분할 기준은 길이가 아니라 책임과 의존성이다. 같은 정책·상태 소유권·복구 계약을 바꾸는 묶음은 함께 읽어야 한다. 다른 문서의 동일한 결정 설명을 복제하지 않고 정본에 연결한다. 로컬 설계만 보면 맞아 보이는 변경도 공유 경계나 목적에 영향을 주면 관련 묶음까지 검토한다. 현재 착수 작업의 공통 계약을 “후속 문서”로 미뤄서도 안 된다.

처음 진입하거나 목표가 바뀔 때는 현재 intent 전체와 spec의 범위·정본 지도를 읽는다. 이후 같은 세션의 좁은 변경은 실제 변경된 부분, 관련 의도 구절, 영향을 받는 공유 계약을 우선 읽는다. 기존 전체 설계 인계 검토에서는 선언된 정본 전체를 읽는 원칙을 유지한다. 부분 검토를 전체 준비 완료로 보고하지 않는다.

목적의 재확인은 턴 수나 토큰 수에 따른 정기 질문이 아니다. 기존 인계, 새 공유 계약 채택, 주요 제약 변경, 컨텍스트가 끊긴 재개처럼 실제 사건에 붙인다. 묶음의 작은 결정들이 사용자의 대상·성공 모습·비용 전제를 바꾸었는지 그 자리에서 확인한다. 단순 상태 질문은 개정·재검토 사건이 아니다.

F01은 부담을 줄이는 기준 사례다. 담당자 필터의 정확 일치·완료 포함·무쓰기·기존 출력 유지가 현재 자료로 정해져 있으면 현재 R/SP/T 연결로 충분하다. 추가 의도 표, 요약 카드, 새 파일, 질문, 검토자 호출은 필요 없다. 이 사례에서 별도 양식을 채우게 되는 설계는 축소해야 한다. 이미 충분한 문서를 “적용 흔적” 때문에 고치는 것도 실패로 본다.

## 대안 비교

| 대안 | 이득 | 비용·놓치는 범위 | 판단 |
|---|---|---|---|
| 현행 문구 유지 | 추가 토큰·도구 없음 | 중요한 추가 요청의 초기 해석을 뒤 단계 대조까지 미룰 수 있음 | 기준선. 실험에서 같은 성능이면 유지 가능 |
| 기존 작성·feedback에 변경 입력 판단을 짧게 보완 | 비용 지출 전에 이유·충돌 확인, 기존 문서 재사용 | 의미 판단은 여전히 모델에 의존 | 추천 |
| 모든 spec 개정에 intent 개정·동반 stage 요구 | 파일 쌍 존재를 쉽게 확인 | 정상 spec-only 수정 오탐, 의미 없는 수정, 개정 이력 오염 | 배제 |
| 매 개정마다 의도 질문·오너 확인 | 불명확한 목적을 자주 노출 | 답이 명확한 변경도 지연, F01 비용 증가, 질문 피로 | 배제 |
| intent 전 항목 ID·요구 역매핑 장부 | 기계적 탐색이 쉬움 | 의도를 FR/NFR 장부로 바꿈, 모든 변경의 유지비 | 배제 |
| 중요한 설계마다 자동 모델 리뷰 훅 | 다른 문맥의 발견 가능성 | 지연·토큰·권한·운영 비용, 공통 오해를 막지 못함 | 별도 기본 기능으로 채택하지 않음 |
| 기존 U7 선언에 의도 관계 필드를 추가 | 커밋 때 판단 환기 | 자기선언을 하나 더 만들 뿐 의미 보장 없음 | 초기안에 포함하지 않음 |
| 선택적 비차단 의도·spec 알림 | 잊은 파일 열람을 환기할 수 있음 | 편집 패턴 오탐·알림 피로, commit 시점이면 늦음 | 반복 누락이 관측된 팀의 후속 선택지 |

얇은 훅을 원하더라도 “spec 변경이면 intent도 변경”으로 짝지으면 안 된다. 의도의 내용이 그대로인 정상 변경을 실패로 만들기 때문이다. 아직 채택하지 않은 후속 후보로는, 실제 설계 변경이 있는 기존 인계 자리에서 관련 intent 경로를 보여 주는 비차단 알림 정도가 가능하다. 이 알림도 의미 검사·읽기 인증·목표 변경 승인으로 표현하지 않는다. 커밋마다 새 영구 확인 상태를 쓰거나 모델을 호출하는 방향으로 확장하지 않는다.

U7은 추천안에서 수정하지 않는다. 필요한 intent 개정이 실제로 있다면 기존 세션이 기존 `documents` 목록에 그 경로를 포함할 수 있다. 이미 앞선 커밋에서 개정·수락된 상류 문서는 다시 stage할 필요가 없다. U7 통과는 잘못된 목표를 함께 기록한 경우나 거짓 빈 목록을 발견하지 못한다. 이 한계를 유지한 채 의미 검토와 포함 확인을 구별한다.

아래는 후속 구현이 허가될 경우의 편집 제안이며 이번에 적용하지 않았다. 같은 긴 규칙을 여러 진입점에 복제하지 않는다.

| `tdd-optional/org-skills/skills/sdlc-feedback/SKILL.md` | Change or acceptance의 실제 diff 추적 앞에 위 판단을 연결한다. 이미 충분한 목표·제약 대조 문구를 대체·합쳐 중복을 줄인다. |
| `tdd-optional/project/examples/skills/capture-intent/SKILL.md` | 최초 포착뿐 아니라 후속 배경·목표 정정에도 기존 문서를 부분 개정한다는 범위를 짧게 명확화한다. 질문 반복 금지와 제안 보존은 유지한다. |
| `tdd-optional/project/docs/PROCESS.md` | 질문·리뷰 결정 반영 문단에 목적·제약 충돌의 권한 구분과 암묵적 목표 교체 금지를 짧게 연결한다. |
| `tdd-optional/project/REVIEW.md`와 verifier의 공통 기준 | 중요한 설계 선택이 해결하려는 문제와 근거를 읽을 수 있는지, 목표 충돌을 spec 상호 일치로 가리지 않았는지 기존 Policy and scope 기준에 합친다. 새 리뷰 사건은 만들지 않는다. |
| `tdd-optional/project/examples/skills/plan/SKILL.md` | 새 상세 절차는 넣지 않는다. spec/intent가 달라질 때 영향 작업·검증을 연결하는 현행 문구로 충분하다. 필요하면 표현 한 문장만 일치시킨다. |
| `tdd-optional/project/templates/intent.md` | 다섯 절·작성량을 유지한다. 기본적으로 수정 없음. FR/NFR, 의도 ID, 개정 장부를 추가하지 않는다. |
| `tdd-optional/project/templates/spec.md` 및 traceability 안내 | 기존 요구 근거·SP 선택 이유로 표현 가능하므로 새 필수 절·열 없음. 기존 문구가 이를 막는 경우에만 보완한다. |
| `tdd-optional/project/docs/GIT-WORKFLOW.md`, U7 hook | 현행 개정·권한·동반 커밋 계약 유지. 기본 수정 없음. |

가장 작은 보완은 design-spec와 feedback의 해당 문단을 다듬는 것이다. PROCESS·review·capture-intent의 수정은 내용 충돌이나 실제 진입점 누락을 확인한 범위에서만 함께 한다. 모든 파일의 변경을 이 설계의 수락 조건으로 두지 않는다. 이후 배포 adapter의 복제본·판 표시는 저장소의 기존 전달 경로를 확인해 동기화하되, 이 문서 작성만으로 설치·적용 완료를 주장하지 않는다.

설계 스킬에 넣을 수 있는 핵심 문구 후보:

> 중요한 추가 요구나 설계 선택을 반영하기 전에, 요청의 이유를 현재 intent의 문제·기대 결과·제약과 대조한다. 이미 답한 이유는 재사용하고, 부족한 이유가 선택의 결과를 크게 바꿀 때만 묻는다. 제안 채택은 그 전제의 사실 확인과 구별한다. 기존 목표·제약과 충돌하면 근거·영향·대안을 먼저 드러내고, 권한 있는 사람의 명확한 변경 지시 없이 목적을 바꾸지 않는다. 필요한 연결은 기존 요구 근거나 설계 선택 설명에 남긴다. 문제·결과·제약 또는 핵심 배경이 달라지면 intent의 해당 부분과 영향을 받는 spec·plan을 개정한다. 나머지 intent 문장이나 충분한 기존 근거를 형식적으로 다시 쓰지 않는다.

이 후보는 적용 전 실제 문단과 합쳐 길이·중복을 줄여야 한다. 양식, 승인, hook 계약은 바꾸지 않는다.

## 후속 검증 설계 — 미실행

효과를 확인할 후속 실험은 사용자 허가를 받은 뒤 별도 격리 저장소에서 한다. 현행 0.1.9와 문구만 보완한 후보를 비교하며, 문구 효과와 hook 효과를 섞지 않는다. 같은 모델·추론 수준·입력·도구 권한을 사용하고 실제 응답 metadata를 보존한다. 보완이 여러 문단에 걸리면 묶음 효과만 보고하며 개별 문장의 인과 효과를 주장하지 않는다.

공개 입력은 실제 업무 요청처럼 작성하고 정답 분류·기대 질문 목록을 에이전트에게 주지 않는다. HUMAN의 뒤늦은 교정 전 결과와 교정 후 복구를 구별한다. 기대 판정은 실행 전 공개 요청·고정 사실·기존 합의에서 정하고, 에이전트의 결과에 맞춰 바꾸지 않는다. 원문 prompt·공개 response/tool 기록, 문서 판과 실제 커밋, 질문 시점·후속 작업 순서를 보존한다. 숨은 추론과 자격증명은 수집하지 않는다.

| 사례 | 기대하는 관찰 |
|---|---|
| F01의 명확한 작은 추가 요구와 오타 수정 | 이유 재질문·intent 형식 수정·추가 검토 모델·새 장부 없음 |
| 큰 설계에서 현재 목표를 유지하는 새 수단 | 관련 의도·제약과 선택 근거가 spec에서 읽힘. 목표가 같으면 intent 불필요 수정 없음 |
| “항상 세 줄”과 JSON 추가처럼 낡은 제약이 남는 변경 | 새 목표가 같아도 충돌 발견. 명시된 변경 결정 사용, 관련 intent 구절 정정 |
| 에이전트의 미확인 성능 추천을 사람이 짧게 채택 | 해법 채택과 성능 사실 구분. 필요 관측이나 가정을 남김 |
| 사용자 결정이 접근 경계의 확인 사실과 충돌 | 정중한 반론·영향·실현 가능한 대안. 임의 사실 덮어쓰기 없음 |
| 충분히 설명된 오너의 목적 변경 | 이미 주어진 권한 재사용, 중복 질문 없이 영향 intent/spec/plan 개정 |
| why 미정인 큰 구조 선택 | 최소 질문을 의존 작업 전에 하고, 독립 작업은 진행 |
| 여러 작은 추가 요구가 누적된 긴 대화 | 기존 묶음 인계에서 대상·목표·비용의 누적 전환 감지 |
| 분할 설계의 다른 문서에 있는 제약 충돌 | 현재 부분 문서의 일치만으로 전체 정합성 통과하지 않음 |
| 외부 정책과 추가 요구 충돌 | 목표 변경 권한과 정책 예외 권한을 구별 |

판정은 최종 문서가 그럴듯한지에 한정하지 않는다. 중요한 충돌을 언제 발견했는지, 그 전에 진행한 의존 설계·구현이 있었는지, 이유를 발명했는지, 실제 영향을 받는 본문을 고쳤는지를 본다. 비용은 질문 수, 불필요한 intent 개정, 반복 읽기, 모델 호출, 벽시계 시간과 제공 가능한 사용 토큰으로 비교한다. 파일 존재나 새 문구 재현만으로 통과시키지 않는다.

설계 검토와 실제 대화 실행을 분리한다. 먼저 소수의 고정 사례로 보완 자체의 충돌·과잉 부담을 검토하고, 이후 대표 대화를 실행한다. F01에서 정상 흐름 비용이 늘거나 현행 지침과 성과가 같으면 보완 문구를 축소하거나 현행 유지로 돌아갈 수 있다. 반복 횟수·예산·성공률 목표는 아직 합의하지 않았으므로 숫자를 정책으로 발명하지 않는다. 한 사례의 성공은 장기 설계 전체의 안정성 근거가 아니다.

## 한계와 열린 결정

이 설계는 의미 판단을 개선하려는 권고다. 자동 방지·완전 동기화·토큰 절감 효과를 입증하지 않았다. 모델은 충돌을 놓칠 수 있고, 사람이 틀린 전제를 확신할 수 있으며, 서로 잘 맞는 intent/spec/plan 전체가 잘못된 문제를 풀 수도 있다. 실제 관측과 사람의 검토를 계속 사용한다.

현재 사용자 지시는 목적과 설계 방향의 위임을 포함한다. 따라서 이 연구 문서를 쓰기 위해 별도 목적 질문이나 단계 수락을 요청할 필요는 없다. 활성 정책 반영·설치·실험은 현재 범위 밖이다.

후속 채택에서 남은 결정은 보완을 design-spec/feedback 두 곳으로 시작할지, 실제 여러 도구의 진입점 일치를 위해 PROCESS·review까지 함께 다듬을지다. 추천은 최소 두 곳부터 내용을 정리하고 중복·누락을 대조하는 방식이다. 비차단 알림도 필요성의 반복 관측이 생기기 전에는 보류한다. 구체 실험 모델·예산·횟수는 후속 검증을 실행할 때 정한다. 그 미정은 현재 설계 비교를 막지 않으며 실행 허가를 대신하지 않는다.
