# 조사 결과와 템플릿 보완안

현재 요청 범위는 **조사와 보완안**이다. 개발 실험은 사용자 지시로 중단했으며 별도 지시 전 재개하지 않는다.
이미 작성한 0.1.9 소스는 `codex/plan-specificity-policy`의 검토 후보로 보존한다. 실험 통과·main 반영·
전역 설치·원제품 업데이트는 이번 결과가 아니다.

## 조사에서 확인한 것

원격 main `a08295f2f7f492efd3ef4787c4ed3d1a1d8f118e`, PR 340건·브랜치114개·이슈135개를 고정했다.
개발건은 번호 있는30개와 번호 없는4개로 묶었다. [coverage](coverage.md)에 모든 건의 보고서·PR·
조사 상태·한계를 연결한다. 채택 이전 미연결122PR은 원본을 보존하며 조사 경계에 따라 제외했다.
번호 변경·여러 개발건에 걸친 PR과 같은 결함의 후속 수정은 중복 사건으로 세지 않았다.

이는 34건 모두의 전체 코드·모든 상태 조합·원 실행 로그를 감사했다는 뜻은 아니다. 특히 0001의
gate 전량·모든 adapter 소비자와 0018의 일부 상태/권한 조합·DTO 이식 범위는 미검토다.
원격 밖 Windows 대화와 일부 Mac 실행 원문은 확보하지 못했다. 모델·OS·작성 순서는 그 한계 안에서
판단하며, 계획에 적힌 모델명·브랜치 접두사·같은 커밋을 실제 행동 증거로 바꾸지 않는다.

| 관측 | 사건 근거 | 현재 템플릿에 대한 판단 |

반증도 있다. 0018은 실제 컴포넌트·DOM/PNG 탐색을 이미 했고 0021은 실제 참고 화면의 캡처·실측과
병렬 접점 계약을 작성했다. 많은 변경은 요청자의 새 결정 또는 정상적인 발견이었다. 따라서 “설계가
전혀 없었다”, “모듈 분할이 항상 틀렸다”, “HTML을 금지하면 해결된다”로 결론내리지 않는다.
현재 배포0.1.8과 조사 시작 때의 WIP5는 [baseline](baseline.md)에서 구별한다.

## 우선 보완 세 가지

### 1. 위험한 실제 연결을 첫 인도에 넣는다

이번 인도에 참여하는 경계의 책임·입력·결과/오류·상태 소유자·대표 실패 순서를 spec에서 확인한다.
plan은 가장 위험한 연결을 통과하는 **작은 실행 경로를 먼저** 배치하고 그다음 내부 확장·병렬 작업을
진행한다. 모든 모듈을 완성한 뒤 첫 E2E를 하는 기본 순서를 피한다. 필요한 인프라 때문에 늦으면
실제 연결 시점·그전의 대체 관측·남는 가정을 적는다.

반영 후보: 기존 `plan/references/execution-depth.md`. 새 계획 파일이나 통합 프로그램을 만들지 않는다.
공유 타입 일치와 health check는 그 범위의 증거이며 사용자 기능 완료는 아니다. 미래의 모든 인터페이스·
내부 메서드를 미리 고정하거나 병렬 수행을 금지하지 않는다.

### 2. UI 설계의 실행 자료를 실제 앱과 연결한다

시각 기준은 기존 화면·공통 컴포넌트/스타일과 사람의 기대에서 정한다. 배치만 비교할 때는 HTML도
유효하다. 키보드·겹침·초점·상태·API 결합이 중요하면 설계 중 실제 컴포넌트와 앱 셸의 격리 경로를
구현해 관찰한다. 해당 화면의 핵심 상태와 기존 UI를 비교하고 사람의 피드백을 설계 결정으로 남긴다.

반영 후보: 기존 `design-spec/references/design-depth.md`와 UI 탐색 예시. 자료의 판·실행 위치·상태/
데이터·가상 연결·채택 범위·남은 검증을 인계한다. 초기 코드를 제품에 계속 쓸 수 있지만 실제 연결과
품질/회귀 확인을 거친다. 모든 화면의 사전 완성이나 Storybook 설치는 요구하지 않는다. 자동 시험이
심미성과 사용자 기대의 수락을 대신하지 않는다.

### 3. 설계에서 검증 접근을 정하고 plan에서 실행한다

중요한 AC/설계는 독립 기대의 출처, 통과할 실제 경계, 입력/환경, 실패를 유도할 지점과 관측할 효과,
가상화 한계를 연결한다. 예컨대 “403이면 값 유지”는 화면 문구뿐 아니라 실제 거절 응답과 저장소
재조회로 구별한다. plan은 이 접근을 실제 파일·시험/관찰 절차·순서·완료 조건으로 연결한다.

반영 후보: 기존 spec 양식의 AC 안내와 설계/실행 참고 지침. 모든 AC의 표를 증식하거나 spec에 테스트
본문·모든 명령을 중복하지 않는다. TDD 선택과 검증 방법은 구별하고 선택형을 유지한다.

이 세 가지는 현행 규칙의 부재를 새로 메우기보다 **적용 판단을 명료화하는 묶음**이다.
[독립 후보 검토](candidate-review.md)와 [원전 조사](design-methods.md)에 반론·근거·한계를 남겼다.
기존 지침이 이미 처리하는 개별 에이전트 실수에 새 정책을 하나씩 추가하지 않는다.

## 사용자가 추가로 요청한 전달·기록 정책

| 보완 | 구체안 | 부담을 줄이는 경계 |
|---|---|---|
| PR 본문 | 목적/결과, 설계·plan 범위·의존/base, 실제 대상판의 검증과 한계, 남은 일/인계. 리뷰 후 최종 diff에 맞춤 | 작은 정리는 목적·변경과 확인만. 전문은 링크. PR 생성/검사 통과를 승인·전체 완료로 바꾸지 않음 |
| 커밋 메시지 | `type(scope): 변경 결과`, 의미 있는 변경은 이유·개발건/설계·작업·실제 검증/미실행 사유 | scope 선택, 오탈자 제목만 허용, merge/revert 예외, 과거 이력 재작성·commitlint 없음 |
| 개발건 이름 | `changes/<NNNN>-<slug>/` 아래 intent.md/spec.md/plan.md. Task는 plan의 T와 구분 | 번호·내부 문서 유지. 기존 채택 intent 경로와 제작 이력을 강제로 옮기지 않음 |
| 총괄 문서 | `changes/README.md`에 현재 상태·plan/대상판/PR·남은 범위/다음 일의 색인 | 상세 작업표·시험 장부 복제 없음. 생성·중요 인도/변경·중단/인계 때 관련 행만 갱신 |
| 과거 spec | 당시 판의 근거로 읽고 현행 정책·현재 적용 계약·실제 코드/설정과 대조, 보존/대체/미확인 범위를 이번 spec에 명시 | 과거 수락/최신 번호만으로 현재 전체 설계 승계 금지. 코드 결함을 정당화하도록 설계를 자동 덮어쓰지 않음 |

기존 공통 설계 정본이 있으면 그것을 참조한다. 모든 프로젝트에 별도 아키텍처 문서 세트를 추가하라는
정책이 아니다. 상세 설계와 상태의 정본을 하나씩 유지하고 개발건 README는 찾는 경로만 제공한다.
[기록 정책 설계](change-records-design.md), [전달 정책 검토](delivery-review.md)를 연결한다.

## 현재 후보와 아직 입증하지 않은 것

조사 도중 작성한 source는 `ec476959ca20c2e44fd9d2cbfcbb5b0c7eeffc23`(패키지0.1.9), 진입점 버전
보완은 `74e1148`이다. 이전 WIP5도 함께 보존·대조된 묶음이므로 각 문구의 독립 효과를 주장하지 않는다.
source 정적 검토와 make check103건(1skip), shell suites, Claude strict manifest·Codex/OpenCode
patch 적용은 확인했다. 검토에서 발견한 두 진입점의 버전 불일치는 수정하고 재확인했다.

실험은 사용자의 범위 변경으로 중단했다. 부분 구현·설치 준비·인증 실패는 [0037 기록](../../experiments/0037-openwebagent-history-feedback.md)에
남긴다. 완료된 비교 쌍·전이 평가가 없으므로 실사용 효과·인접 회귀·자연적인 스킬 선택은 미입증이다.
현재 요청의 결론은 위 보완안이며, 새 개발 실험이나 배포·전역 설치는 사용자 후속 지시 후 다룬다.
