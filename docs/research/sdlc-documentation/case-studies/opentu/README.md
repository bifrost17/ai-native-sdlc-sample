# Opentu 실제 제품: 두 플레이어의 재생 모드 공유

**분류: 별도 제품 프로젝트, 기존 기능 확장.** Opentu는 캔버스에서 AI 생성 작업, 미디어, 도구와 지식 자료를 함께 다루는 웹 애플리케이션이다. [프로젝트 README](evidence/project-readme.md)는 정식 사이트와 배포 방법, 제품 코드 구조를 제공한다. SDD 양식을 배포하는 프레임워크나 공식 튜토리얼이 아닌 별도 애플리케이션이라는 뜻에서 제품으로 분류했다. 실제 유료 고객 수, 운영 규모, 서비스 품질까지 확인한 분류는 아니다. README의 옛 `aitu` 링크도 그대로 남겼으며 연구자가 정정하지 않았다.

대상 변경은 기존 오디오 재생 서비스에 순차 재생, 목록 반복, 한 곡 반복, 무작위 재생을 추가하는 작은 기능이다. 떠 있는 플레이어와 음악 도구 화면이 같은 상태를 공유해야 한다는 문제가 출발점이다. 기준 구현은 2026-04-09의 [commit 204da5a](https://github.com/ljquan/opentu/commit/204da5a4433aa8e7b41b509cafc40ee99b94da07), 보관 기록은 2026-04-29의 [commit a614f3e](https://github.com/ljquan/opentu/commit/a614f3e5041de3f75f675b9bd894f1142cb4f376)다. 다음 연결은 단순한 `openspec/` 폴더 존재가 아니라 두 커밋의 문서와 코드 내용을 읽어 확인했다.

## 실제 산출물과 연결

| 단계 | 보관 자료 | 확인되는 내용 |
| --- | --- | --- |
| 의도와 영향 | [proposal](artifacts/proposal.md) | 두 UI의 경험 불일치, 공유 서비스, 모드 저장, 오디오·낭독 종료 후 자동 재생 |
| 요구사항과 예시 | [spec](artifacts/specs/canvas-audio-playback/spec.md) | 두 화면 간 선택 동기화와 네 가지 큐 종료 동작을 GIVEN/WHEN/THEN으로 표현 |
| 실행 계획 | [tasks](artifacts/tasks.md) | 서비스, 두 화면, 단위 테스트, OpenSpec 검증의 다섯 완료 항목 |
| 구현과 테스트 | [implementation patch](evidence/implementation.patch) | 위 문서 추가와 서비스·UI·storage key·hook·회귀 테스트 변경이 같은 commit에 포함 |
| 현재 명세로 반영 | [canonical spec](artifacts/canonical-spec-after-archive.md), [archive metadata](evidence/archive-selected-files.json) | 세 변경 문서가 내용 변경 없이 보관 경로로 이동하고 통합 명세가 추가됨 |

proposal은 구체적 파일 경로 세 개를 적어 다음 작업자가 영향 범위를 찾게 한다. 별도 `design.md`는 이 변경에서 확인되지 않았다. 서비스 공유라는 구현 방향은 proposal에 담고 tasks에서 서비스와 화면 작업을 나눈다. 따라서 네 문서를 모두 채우지 않아도 작은 변경의 의도, 동작, 작업 분해를 전달하는 사용 형태다. 이것이 프로젝트 전체에서 설계 문서를 생략한다는 뜻은 아니다. 인접 변경에는 별도 설계 파일이 존재하지만 이번 사례의 양식으로 가져오지 않았다.

명세의 반복 모드 예시는 코드에서 `getNextQueueIndexForAutoAdvance()`의 분기와 대응한다. 순차 모드는 큐 끝에서 중지하고 목록 반복은 첫 항목으로 돌아간다. 한 곡 반복은 현재 항목을 처음부터 재시작하고, 무작위 모드는 가능한 경우 다른 항목을 선택한다. 기존 `playPrevious()`와 `playNext()`는 순차 이동을 유지한다. 자동 종료 동작을 요구한 명세를 수동 버튼의 동작 변경까지 넓혀 해석하지 않는 데 도움이 되는 차이다. 무작위 선택의 재시도 횟수와 마지막 대체 선택은 코드의 구체화이며 명세에 직접 정해진 알고리즘은 아니다.

테스트 diff에는 기본값과 저장·복원, 순차 종료, 목록 반복, 한 곡 반복, 무작위 다음 항목, 낭독 반복 사례가 추가된다. 브라우저의 실제 오디오를 듣는 테스트가 아니라 mock audio와 speech synthesis를 사용하는 서비스 수준 검사다. 두 UI가 모드 setter와 공유 상태를 사용하는 변경도 같은 patch에 있다. 다만 두 화면 간 동기화를 실제 브라우저에서 검증한 실행 결과까지 확보한 것은 아니다. 테스트 파일이 있다는 사실과 사용자 시나리오의 실행 성공은 구별해야 한다.

## 계획과 기록이 어긋나는 지점

첫째, proposal과 tasks에는 로컬 저장과 새로고침 후 복원이 포함되고 코드·테스트에도 구현됐지만, 이 변경의 spec에는 영속성 전용 시나리오가 없다. 이는 최종 문서 간 상세 수준의 차이를 보여 준다. 구현 중 요구가 바뀌었다는 시간 순서 증거는 아니므로 사후 범위 확장이라고 단정하지 않는다. 다만 다음 변경자가 spec만 읽으면 저장 계약을 놓칠 수 있어, 어떤 문서가 유지할 요구의 기준인지 명확히 할 필요가 있다.

둘째, 구현 commit의 제목은 음악 플레이어의 시간 표시 fallback 수정이다. 실제 diff에는 재생 모드 기능과 명세가 함께 들어 있다. [연결된 PR #146](https://github.com/ljquan/opentu/pull/146)은 제목이 `Develop`이고 본문이 없으며 여러 기능을 함께 병합한 기록이다. 따라서 이 PR을 재생 모드만의 승인 문서처럼 제시할 수 없다. 검토 가능한 근거는 구체적 commit의 파일과 diff에 있으며, 팀에서는 작은 변경 ID를 commit 또는 PR 설명에 남기는 편이 검색과 인수인계를 개선한다.

셋째, tasks는 공개 경로에 처음 나타나는 commit부터 모두 완료 표시다. [경로 이력](evidence/change-path-history.json)에서 이후 보관 이동을 확인했지만, 초안과 미완료 작업 목록을 별도 commit으로 확보하지는 못했다. 계획이 구현을 실제로 이끌었는지, 구현 후 기록됐는지 판단할 수 없다. [보관 metadata](evidence/archive-selected-files.json)는 세 문서의 이동을 additions/deletions 0인 rename으로 보고하므로, archive 시점에 내용을 새로 다듬었다고 주장할 수도 없다.

넷째, [구현 SHA의 workflow 조회](evidence/implementation-workflow-runs.json)는 조사 시점에 일치하는 실행을 반환하지 않았다. 이를 테스트 미실행이나 실패로 해석하지 않는다. 보관된 실행이 없거나 다른 SHA에서 수행됐을 수 있다. 이 사례에서 확정할 수 있는 검증 수준은 테스트 구현과 작성자의 완료 표시까지이며, CI 통과나 배포 후 검증은 미확인이다. 저장소의 최신 CI 상태로 과거 변경의 성공을 대체하지 않았다.

## 팀에 주는 시사점

작은 기존 기능에는 짧은 의도, 상태 공유 경계, 구체적 사용자 예시, 코드 경로와 작업 목록만으로도 읽을 수 있는 변경 묶음을 만들 수 있다. 반면 영속성처럼 관찰 가능한 계약이 proposal에만 남으면 현재 명세가 불완전해질 수 있다. 완료 시에는 핵심 계약이 기준 문서에 반영됐는지 확인하고, 테스트 성공 주장에는 실행 URL을 남기는 것이 실용적이다. 문서 수를 늘리는 것보다 변경 ID, 구현 diff, 검증 기록의 연결을 유지하는 편이 이 사례에서 더 직접적인 개선점이다.

소스 수준의 한 제품·한 기능 관찰이며 SDD의 효과, 작성 순서, 사람과 에이전트의 기여도, 전체 제품의 정합성을 입증하지 않는다. 원본 문서와 patch는 [MIT LICENSE](licenses/LICENSE)를 확인하고 바이트 그대로 보관했다. API 자료는 원본 응답에서 사실 필드만 선택한 `api-metadata`로 표시하고, 판·경로·원본 링크·해시는 [sources.json](sources.json)에 기록했다. 외부 코드를 설치하거나 실행하지 않았다.
