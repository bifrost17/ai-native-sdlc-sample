# 우리 양식을 만드는 방법 비교와 추천

2026-09-11 · 사전 조사에 이은 설계 접근 권고. 양식 채택이나 운영 반영의 완료 기록이 아니다.

## 최우선 전제와 설계 대상

목표는 Anthropic AI-Native SDLC Playbook의 취지에 맞는 **우리 팀의 intent·spec·plan 양식**을
만드는 것이다. 흐름 유지는 이미 정해진 전제이며 이번 설계의 성과가 아니다. 기존 양식도
비교 대상이다. 목차와 표현을 보존하기보다 다음 작동을 얼마나 잘 지원하는지 판단한다.

- 요청자가 자기 말로 문제·바라는 변화·제약을 설명하고, 에이전트의 오해를 바로잡는다.
- 관련 팀 스킬을 적용하여 요구와 설계를 함께 구체화하고, 사람이 중요한 판단과 우려를 검토한다.
- 사람과 에이전트가 같은 기록을 읽고 다음 작업을 이어간다.
- 실행 계획은 실제 코드와 검증에 연결되고, 구현 중 발견을 관련 문서에 반영할 수 있다.
- 사내 개발의 규모와 위험에 맞춰 상세도를 조절하며, 양식이 새로운 인계 병목을 만들지 않는다.

앞의 네 가지는 플레이북의 [소개](https://academy.claude.com/courses/ai-native-sdlc-playbook/introduction),
[intent](https://academy.claude.com/courses/ai-native-sdlc-playbook/capture-intent),
[요구·설계](https://academy.claude.com/courses/ai-native-sdlc-playbook/requirements-and-design),
[plan](https://academy.claude.com/courses/ai-native-sdlc-playbook/plan-mode)을 기준으로 삼았다.
사내 팀의 얇은 운영과 상세도 조절은 이 프로젝트에 적용하는 설계 판단이다.

## 가능한 접근

앞의 네 가지는 양식의 출발점을 고르는 방법이다. 뒤의 네 가지는 선택한 출발점과 결합할 수 있는
설계·표현·검증 방법이다. 모두를 서로 배타적인 대안으로 취급하지 않는다.

| 접근 | 어떻게 만드는가 | 장점 | 주의할 점 |
|---|---|---|---|
| 가까운 세트 수정 | 한 프로젝트의 문서 묶음과 작성 규칙을 바탕으로 조정 | 용어·구조가 일관되고 시작이 빠름 | 문서 역할과 도구·조직 전제가 함께 들어온다. 변경 폭이 커지면 세트의 장점이 줄어든다. |
| 문서별 기반 선정 | intent/spec/plan에 각각 가장 가까운 기본 형태를 선택 | 문서마다 목적에 맞는 출발점 확보 | 세 문서 사이의 중복·공백·갱신 관계는 우리가 정리해야 한다. |
| 항목별 조합 | 요구 표현·설계 질문·검증 설명 등 필요한 부분을 가져옴 | 특정 부족을 정확하게 보완 | 좋은 항목을 모두 더하면 문서가 커지고 용어·상세도가 어긋난다. |
| 원칙에서 새로 설계 | 독자와 다음 판단·행동을 정의한 뒤 양식을 만듦 | 우리 목적과 표현을 일관되게 구성 | 설계자의 취향이나 누락을 실제 사용 전에는 알아차리기 어렵다. |
| 완성 예시부터 도출 | 대표 개발 건의 좋은 문서를 먼저 작성한 뒤 빈 양식을 추출 | 항목의 필요성과 작성 깊이가 실제 내용으로 드러남 | 특정 업무 하나에 맞춰지지 않도록 다른 유형으로 확인해야 한다. |
| 공통 핵심과 조건부 상세 | 기본 기록은 일정하게 두고 필요한 설계 상세만 추가 | 작은 작업부터 복잡한 작업까지 같은 체계로 처리 | 상세 추가 판단이 모호하면 중요한 정보가 빠질 수 있다. |
| 한 기록 안에서 읽는 깊이 구분 | 앞에는 핵심 변화·판단·우려, 뒤에는 근거와 실행 상세 배치 | 사람이 검토할 부분을 찾기 쉽고 에이전트도 전체 근거에 접근 | 사람용 요약과 에이전트용 상세가 다른 결정을 말하지 않아야 한다. |
| 작은 비교 실험으로 선택 | 후보를 같은 개발 요청과 중간 변경 상황에 적용 | 형식의 취향보다 작성·검토·인계 결과로 선택 | 문서 길이·항목 수·스킬 호출 수만으로 평가하면 목적을 놓친다. |

## 추천 조합

**문서별 출발점을 고른 뒤 완성 예시를 먼저 쓰고, 공통 핵심과 상황별 상세를 갖춘 우리 양식으로
다시 구성한다.** 항목별 조합은 부족한 부분을 보완하는 데 쓰고, 작은 비교 실험으로 선택한다.

전체 외부 세트 하나를 첫 선택으로 권하지 않는 이유는 역할 차이다. Spec Kit의 plan은 기술
설계에 가깝고 실행 작업은 tasks에 있다. OpenSpec은 proposal·행동 변경분·design·tasks를
현재 명세와 연결한다. 둘 다 유용하지만 이름을 바꾸는 정도로 우리 문서 역할과 일치하지 않는다.
[역할 비교와 원문](comparison.md).

| 우리 문서 | 권하는 출발점 | 선택적으로 참고할 내용 |
|---|---|---|
| intent | 플레이북 실제 예시 | 요청자의 문제·원하는 결과·영향·제약·열린 질문. 요청자의 해결 제안과 필수 제약은 구별한다. |
| spec | 플레이북이 요구하는 판단을 기준으로 우리 구조 설계 | Spec Kit의 사용자 시나리오·수용 기준, Kiro의 유지할 동작, OpenSpec의 설계 결정, Fuchsia의 약속/예시 구분, TensorFlow의 사용 예시와 영향, MADR의 선택 이유 |
| plan | 플레이북의 파일·순서·위험·검증 예시 | 큰 변경이나 병렬 작업에만 작업별 문맥·의존·소유 경계·통합 검증. 기존 PR 전략과 연결한다. |

이 표는 모든 출처의 항목을 동시에 추가하라는 뜻이 아니다. 예컨대 spec의 설계 결정 한 단락이
선택 이유·대안·위험을 충분히 설명하면 세 개의 별도 표를 만들 필요가 없다. 동일한 의미는 우리
용어와 상세도로 다시 쓰고, 한 정보의 기준 기록을 정해 다른 문서에서 참조한다.

## 양식과 작성 스킬의 역할

양식에는 **다음 사람이 알아야 할 답**을 남긴다. 질문 순서, 저장소 탐색, 대안 비교, 정책 적용,
회귀 탐색, 상세 절의 필요 판단은 작성 스킬이 돕는다. 그 결과 중요한 결정·제약·미해결 우려는
문서에 남아야 하며 스킬의 내부 판단으로 숨겨서는 안 된다.

예를 들어 데이터 이행이 없는 변경에는 빈 migration 절을 매번 남기지 않을 수 있다. 이행이 있는
변경에서는 스킬이 필요성을 알아보고 대상·호환성·실패 대응·검증을 적절한 깊이로 문서화한다.
이를 위해 모든 가능한 경우를 처리하는 양식 생성기나 새 검증 프로그램부터 만들 필요는 없다.

기존 작성·검토 스킬을 기준으로 보완한다. 특정 외부 스킬 이름과 설치를 범용 양식의 필수 조건으로
박아 넣지 않고, 우리가 제공하는 스킬은 팀의 기본 예시로 구분한다. 이 설계 접근을 골랐다는 이유만으로
새 스킬이나 CLI의 추가 설치가 결정되는 것은 아니다.

## 실행 순서 제안

1. 작은 사내 기능과 버그 수정을 골라, 사람이 승인·구현 판단을 할 수 있는 intent/spec/plan 예시를 쓴다.
2. 각 항목이 어떤 판단·후속 행동을 돕는지 설명하고 중복이나 장식적인 항목을 제거한다.
3. 공통 양식을 추출하고, API 변경·데이터 이행·병렬 구현 같은 경우의 상세 확장 예시를 만든다.
4. 다음 구현자가 원래 대화 없이 문서를 읽고 요청 이유·제약·선택 근거·검증 방법을 설명할 수 있는지 본다.
5. 최대 두 후보를 기존 실험 데이터·사람 페르소나로 비교한다. Codex가 사람 역할, Claude Code가
   개발 에이전트 역할을 맡아 대화하며, 구현 중 설계나 요구가 바뀌는 상황도 포함한다.

예시를 먼저 만든다는 것은 **양식을 설계하는 방법**이다. 실제 개발에서 코드를 먼저 만들고
명세를 사후 작성하자는 절차가 아니다. 비교 실험에서는 초기 의도 포착부터 문서 작성·구현·변경 반영을
순서와 대화 기록으로 확인한다. Claude Code는 사용자의 자원 선호에 맞춰 Sonnet을 기본으로 한다.

선정 시에는 핵심 의도 누락, 근거 없는 가정, 중요한 질문의 방치, 구현자가 다시 추측해야 하는 부분,
문서와 코드의 불일치, 불필요한 작성·갱신 부담을 함께 본다. 핵심 판단의 품질이 비슷하다면 더 단순하고
유지하기 쉬운 후보를 택한다. 사소한 표현 차이나 모든 항목의 기계적 충족을 완벽하게 만들려 하지 않는다.

## 현재 양식도 재검토할 예

현재 intent 제목과 Problem의 강한 해결책 배제 문구가 요청자의 초기 해결 제안까지 지우게 만드는지
살펴볼 필요가 있다. 플레이북 예시에는 포털에서 조회한다는 제안이 들어 있다. 현재 plan의
실패 테스트부터 시작하는 고정 예시도 플레이북의 필수 작업 순서와 동일하지 않다. TDD의 가치는
별도 판단하되, 모든 작업의 순서를 북극성이 정한 것으로 표현하지 않는다.

이 두 항목은 새 설계에서 검토할 후보이며, 이번 문서 작성으로 운영 양식을 수정하지는 않았다.
