# 정보 배치 비교와 선택

root가 먼저 기능·버그·두 PR·합성 이행의 완성 계획을 작성한 뒤 양식을 도출했다. 이어 같은 F01을
[작업별 묶음](alternative-feature.md)으로 다시 써 [네 절 배치](../../../../.claude/skills/plan/examples/feature.md)와 비교했다.
단순 양식 이름 비교가 아니라 실제 파일·작업·검사·갱신이 어디에 놓이는지를 대조했다.

| 판단 | A: 네 절 + 필요한 단계 상세 | B: 작업별 Files/Action/Check/Risk |
|---|---|---|
| 작은 기능 | 파일·공통 명령·위험을 한 번씩 읽음 | 같은 시험 파일과 show/complete 회귀가 두 묶음에 반복 |
| 결함 | 재현 커밋→수정 커밋, 한 PR이라는 구분이 쉬움 | 작은 단계가 별도 작업/PR처럼 보이지 않게 보충 필요 |
| F02 여러 PR | 순서에 PR 목적/main 결과, Proof에 연결 | 각 PR을 묶음으로 하면 잘 맞지만 공통 회귀 반복 가능 |
| M01 병렬/이행 | 역할·입력·통합을 필요한 PR 절에만 확장 | 인계 묶음에는 유용하나 전체 전환·복구 조건이 흩어지기 쉬움 |
| 새 파일 발견 | Files와 관련 단계/Proof만 수정 | 여러 묶음의 반복 경로·검사를 동시에 찾아야 함 |

A를 기본으로 선택한다. B의 장점인 단계별 결과와 검증 인접성은 A의 Order of work에서 Proof를
참조하는 방법으로 가져온다. 큰 작업에만 PR별 블록·인계 내용을 확장하고 모든 계획에 WP 표·
독립 tasks.md·상태 원장을 만들지 않는다. 두 배치를 모두 강제하는 병합안도 중복 때문에 제외한다.

양식의 안내 길이가 작성 문서의 최소 길이는 아니다. 작은 F01/B01은 한 PR과 몇 단계이며 M01만
공유 계약·병렬 역할·운영 조건이 길다. 시험 코드 전체·helper 이름·일률적 TDD 순서는 정하지 않는다.
기존 네 제목과 metadata를 유지해 현재 소비자를 바꿀 필요도 줄였다.
