# SDLC 문서와 설계 양식 조사 계획

## Objective

Anthropic AI-Native SDLC Playbook을 북극성으로 삼아, 사내 서비스 개발에 사용하는 얇은
템플릿·팀 스킬·정책을 보완할 공개 레퍼런스를 조사한다. 문서 항목 수나 도구의 인기로
순위를 매기지 않고, 사람과 에이전트가 같은 기록으로 판단하고 작업을 이어갈 수 있는지 평가한다.

## Scope

- 기준: Anthropic의 intent → requirements/design spec → implementation plan과 피드백 흐름.
- 기존 조사 문서화: Google의 공개 엔지니어링 문서 지침, Fuchsia RFC, TensorFlow RFC.
- Spec 기반 개발 프로젝트: GitHub Spec Kit(`specify` CLI), OpenSpec, Kiro Specs,
  BMAD Method, GSD(Get Shit Done), Spec Kitty의 핵심 양식과 작성·갱신 흐름을 비교한다.
- 인접 비교 대상: Superpowers의 대화 → spec/design → 구현 계획 스킬 흐름,
  MADR의 중요한 설계 결정 기록. 이들을 동일한 종류의 SDD 프레임워크로 단정하지 않는다.
- 실제 적용 사례: 공개 소프트웨어 저장소 2~3개에서 작성된 spec과 관련 계획·작업·코드·PR 이력을
  조사한다. 프레임워크 자체 개발, 공식 데모, 별도 제품 프로젝트를 구분하고, 가능한 경우 별도 제품
  프로젝트를 최소 1개 포함한다. 근거가 부족하면 빈자리를 추정으로 채우지 않고 한계를 기록한다.
- 기존 대상과 다른 유용한 원칙이나 반례가 있는 추가 후보는 후보 색인에 남기고, 심층 조사 여부와
  그 이유를 기록한다. 별 수나 인기 순위만으로 추가하지 않는다.
- 결과는 연구 자료와 참고 양식이다. 운영 템플릿 변경, 도구 설치, 실험 실행은 이번 조사 범위에 포함하지 않는다.

## SDD Projects and Artifacts

아래는 수집 대상을 정하는 질문이다. 실제 파일명·양식 존재 여부·필수성은 조사할 판의 공식 원문에서
확인하고, 도구가 배포하는 빈 양식과 실제 프로젝트에서 채워진 산출물을 구분한다.

| 프로젝트 | 양식과 워크플로에서 확인할 내용 |
|---|---|
| [GitHub Spec Kit](https://github.com/github/spec-kit) | constitution, spec, plan, tasks의 역할; 명세 유지 방식과 문서·구현 정합성 검토 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | proposal, 명세 변경분, design, tasks; 현재 명세로 반영하고 변경을 보관하는 과정 |
| [Kiro Specs](https://kiro.dev/docs/specs/) | 요구사항·설계·작업, 버그 분석, 간소화된 흐름; 정식 배포 양식과 공식 예시의 구분 |
| [BMAD Method](https://github.com/bmad-code-org/BMAD-METHOD) | 초기 의도, spec/PRD, 아키텍처, 작업 단위; 작은 변경과 큰 개발 건의 적용 조건 |
| [GSD](https://github.com/gsd-build/get-shit-done) | 프로젝트 요구와 진행 맥락, 단계별 계획·검증 기록; 장기 작업에서 맥락을 이어가는 방식 |
| [Spec Kitty](https://github.com/spec-kitty/spec-kitty) | spec, plan, work package, 수용·검토 기록; 병렬 작업과 산출물 관계 |
| [Superpowers](https://github.com/obra/superpowers) | 대화로 정리한 spec/design과 작업 계획; 별도 빈 양식 또는 스킬 내부 작성 지침 |

각 프로젝트에서 우선 핵심 양식 2~5개와 그 양식을 생성·수정·검토하는 지침을 수집한다.
작업 범위상 필요한 원문은 더 포함할 수 있지만, 설치 패키지 전체를 보관하는 것을 목표로 하지 않는다.
필수 항목·선택 항목·상황별 양식을 표시하고, 안정 릴리스와 개발 브랜치의 지침을 섞지 않는다.

## Questions

1. 문서는 요청자의 의도, 검토된 요구사항·설계, 구현 계획, 결정 이력 중 무엇을 기록하는가?
2. 작성·질문·검토·승인·구현의 역할은 사람과 에이전트 사이에서 어떻게 나뉘는가?
3. 다음 작업을 진행할 만큼 구체적이면서 사람이 핵심 결정을 읽기 쉬운가?
4. 작은 변경과 큰 변경, 신규 개발과 기존 시스템 변경에 어떻게 대응하는가?
5. 구현 중 발견으로 의도·설계·계획이 달라지면 어떤 기록을 언제 갱신하는가?
6. 사용자 예시, 수용 기준, 테스트와 연결되는가? 문서가 있다는 사실과 검증 성공을 구별하는가?
7. 필수 양식, 선택 지침, 도구·스크립트 의존성, 조직별 거버넌스를 구별할 수 있는가?
8. 우리 팀에 선택적으로 참고할 원칙과 과도하게 무거운 기본값은 무엇인가?
9. 실제 프로젝트에서 양식의 어떤 부분을 사용·확장·생략했으며, 명세의 변경이 구현·검증 이력과 연결되는가?
10. SDD 프레임워크가 문서를 다음 작업의 입력으로 사용하는 범위와 별도 실행 도구에 의존하는 범위는 어디까지인가?

## Method

1. 공식 저장소·공식 문서부터 확인하고, 템플릿뿐 아니라 생성 명령·워크플로·검토 지침을 함께 읽는다.
2. Git 기반 원문은 조회 시점의 commit SHA로 고정한다. 원본 양식과 관련 라이선스를 수정 없이 저장한다.
3. 각 자료에 원본 URL, 판, 조회 시각, 파일 종류, 로컬 경로, SHA-256, 이용 조건을 남긴다.
4. 양식 파일을 공개하지 않은 자료는 그 사실을 기록한다. 공식 예시, 추출본, 자체 재구성을 원본 양식으로 표시하지 않는다.
5. Google 전체 공통 양식과 특정 프로젝트의 양식을 구분한다. 보관된 자료의 현재 운영 여부를 추정하지 않는다.
6. 실제 작성 사례로 양식의 사용 폭을 확인한다. `.specify`나 `specs/` 디렉터리가 존재한다는 사실만으로
   SDD를 충실히 운영한다고 판단하지 않는다. 가능하면 명세·계획·관련 코드 diff·테스트·PR의 연결을 확인한다.
7. 실제 사례는 작은 기능과 기존 기능 변경을 우선하고, 큰 개발 건은 문서 분할과 작업 의존 관계를 읽을
   수 있는 한 사례로 제한한다. 변경 전후 기록을 확보할 수 없으면 최종 산출물의 구조만 분석했다고 명시한다.
8. 문서 분석과 실행 검증을 구분하며, 효과에 관한 벤더 주장이나 작성된 테스트 계획을 실제 통과 결과로
   취급하지 않는다. 파생 프로젝트는 원본과의 관계를 밝혀 같은 주장을 독립된 근거처럼 중복 집계하지 않는다.
9. 레퍼런스별 분석을 작성하고 공통 비교표, 명칭 대응표, 선택적 적용 권고를 종합한다.
10. 다운로드 무결성, 출처 연결, 상대 링크, 라이선스 구분을 확인하고 저장소의 기존 검사를 실행한다.

## Execution notes — 2026-09-11

공식 자료 12개와 실제 적용 2건을 [README](README.md)에 정리했다. 배포된 원본 양식은 28개다.
Anthropic 예시, Kiro의 짧은 형식, GSD·Superpowers의 지침 내 구조를 별도 빈 양식으로 세지 않았다.
Google 공통 양식과 공개되지 않은 제품의 빈 양식은 임의로 만들지 않고 확보 한계를 기록했다.

실제 사례는 독립 제품 Opentu 1건과 OpenSpec 자체 적용 1건이며 모두 OpenSpec 형식이다.
다른 프레임워크의 실사용 효과 비교로 일반화하지 않는다. 큰 개발 건의 문서 확장은 TensorFlow의
분산 서비스 RFC와 프레임워크 작업 분할 지침으로 분석했으며 대규모 SDD 실행 이력 사례를
추가 확보한 것으로 표시하지 않았다. CLI 설치·대화 실험·운영 템플릿 반영은 수행하지 않았다.

원본 양식 28개는 고정 URL과 다시 대조했다. 로컬 출처 파일 162개와 하위 manifest 14개를
전체 색인과 검증했으며 `make check`는 통과했다. 상세 범위와 한계는 [검증 기록](verification.md)에 있다.
