# Fuchsia RFC

Fuchsia RFC는 이해관계자가 설계의 영향을 이해하고 합의한 결정을 기록하는 문서다. AI-native
SDLC 전체를 설명하는 자료는 아니지만, 설계 검토에 필요한 정보의 깊이를 정하는 기준으로
유용하다. 이 조사에서는 Fuchsia 저장소의 커밋으로 고정한 양식과 작성·운영 지침을 보관했다.

## 양식과 작성 원칙

[원본 양식](templates/rfc-template.md)은 문제·요약·이해관계자·요구사항·설계·구현·성능·사용성·
호환성·보안·개인정보·테스트·문서화·대안 등을 다룬다. 일부 설명은 FIDL을 예로 들며 해당 영역으로
교체하도록 안내한다. 이 도메인 전제를 우리 사내 서비스의 보편적인 필수 항목으로 옮겨서는 안 된다.[^1]

[작성 지침](evidence/rfc-best-practices.md)의 핵심은 설계의 수용 여부에 실제 영향을 미치는
내용을 충분히 쓰는 것이다. 모든 구현 세부를 정할 필요는 없다. 작성자는 어떤 내용이 약속이고
어떤 내용이 예시인지 명확하게 해야 한다. 문서 밖에서 합의한 중요한 결론도 기록에 반영한다.[^2]

이는 사람과 에이전트가 함께 읽는 문서에 직접 도움이 된다. 예시 API의 이름을 확정된 계약으로
오인하거나, 반드시 지켜야 할 권한 경계를 단순 설명으로 읽으면 구현 방향이 달라진다.
우리 spec에서도 결정·제안·예시의 구분이 문장으로 드러나야 한다는 것이 적용 판단이다.

## 문서의 수명

승인된 RFC는 당시 설계에 이해관계자가 동의했다는 역사적 기록이다. 기능이 변할 때 계속 고치는
사용 설명서와 목적이 다르며, 지침은 승인 후 RFC를 큰 폭으로 계속 수정하는 방식을 권하지
않는다. 관련 기능 설명서는 따로 유지하도록 한다.[^2]

우리의 작업 중인 spec/plan에 이 수명 규칙을 그대로 적용하면 구현 중 변경을 따라가기 어렵다.
기록의 의미를 먼저 구분해야 한다. 작업을 수행할 현재 계획은 갱신하고, 중요한 결정의 과거 판은
Git 이력으로 보존할 수 있다. 모든 변경에 별도의 ADR이나 RFC를 만드는 것은 추가 운영 선택이다.

## 단계별 대응

| Fuchsia의 관심사 | 우리 흐름에서 참고할 자리 | 적용 수준 |
|---|---|---|
| 문제·범위·배경 | intent의 문제와 제약 | 요청자의 언어를 유지한다. |
| 중요한 설계 선택·영향·대안 | spec의 Design | 실제 결정이 있는 경우 이유와 단점을 쓴다. |
| 인터페이스·호환성·보안 | spec의 요구·제약·수용 기준 | 영향을 받는 항목을 구체화한다. |
| 구현 순서·검증 | plan의 Order of work·Proof | 실제 코드 경로와 검증으로 이어간다. |
| 위원회·공개 합의 운영 | 조직의 의사결정 절차 | 사내 팀 기본 절차로 자동 채택하지 않는다. |

## 적용 판단과 한계

참고 우선순위는 높다. 특히 중요하지 않은 세부를 남겨 검토 부담을 키우지 않는 원칙과, 결정의
의미를 명확하게 쓰는 원칙을 차용할 가치가 있다. 반면 양식 전체를 강제하거나 승인 이후의 문서
수명까지 복사하는 것은 부적절하다. 본 조사는 원문에 적힌 절차를 분석했으며 Fuchsia의 실제
최신 운영 전체나 이 양식의 정량적 생산성 효과를 검증한 것은 아니다.
