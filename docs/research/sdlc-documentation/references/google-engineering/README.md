# Google의 설계 문서와 기술 문서 지침

Google의 공개 자료에서 확인되는 것은 팀이 승인한 설계 문서 양식과 독자에 맞춘 작성 원칙이다.
모든 Google 조직이 쓰는 단일한 공개 빈 양식은 확인하지 못했다. Fuchsia와 TensorFlow의 양식은
각 프로젝트의 별도 자료이며, 이 폴더는 두 프로젝트의 정책을 Google 전체 정책으로 일반화하지 않는다.

## 설계 문서의 목적

『Software Engineering at Google』은 주요 프로젝트의 설계를 구현 전에 검토하는 관행을
설명한다. 팀의 양식에 따라 설계하고, 주요 결정·대안·보안·개인정보·국제화·저장 등에 관한
고려를 협업 문서에 담는다. 2020년에 출판된 공개 관행 설명이므로 현재 Google 전체의 운영
규칙이라고 단정할 수 없다.[^1]

이 자료가 시사하는 것은 설계 문서가 선택의 근거와 협업을 담아야 한다는 점이다. AI가 글을
작성하더라도 이해관계자가 판단해야 할 기술·업무 선택은 남는다. 반면 사람이 모든 항목을
작성하고 회의와 조직 간 인계로 내용을 계속 재해석하는 절차까지 함께 가져올 필요는 없다.

## 한 파일과 여러 파일

Technical Writing의 큰 문서 지침은 하나의 긴 문서와 연결된 여러 문서를 모두 허용한다.
독자가 목적에 맞는 내용을 찾을 수 있도록 개요·계층·탐색·점진적인 설명을 구성하는 데 초점을
둔다. 입문 독자와 상세 참조를 찾는 독자가 요구하는 깊이도 다르다.[^2]

우리 문서에 대한 해석은 다음과 같다.

| 판단할 상황 | 권고 |
|---|---|
| 작은 기능의 결정이 몇 가지인 경우 | 기존 spec 안에서 필요한 설명을 끝낸다. |
| 상세 API·데이터 모델이 본문의 핵심을 가리는 경우 | spec 내부 하위 절이나 링크된 상세 문서로 구조화한다. |
| 여러 파일에서 같은 결정이 반복되는 경우 | 기준 기록을 정하고 다른 문서는 참조한다. |
| 사람이 짧은 요약만 보고 승인할 위험이 있는 경우 | 중요한 제약·위험·판단 요청은 요약에서도 보이게 한다. |

이 권고는 Google의 고정 파일 구조가 아니라 우리 팀의 적용 판단이다. 한 파일이 긴지 짧은지보다
사람과 에이전트가 같은 결정과 근거에 접근하는지가 중요하다. 링크를 많이 만드는 것도 목적이
아니다. 연결이 끊기거나 여러 문서가 서로 다른 최신 상태를 주장하면 오히려 인계가 어려워진다.

## 수집 자료와 이용 조건

- [큰 문서 구성 지침 원본 HTML](evidence/organizing-large-documents.html): Google Developers의 공개
  페이지를 수정 없이 저장했다. 페이지 본문은 CC BY 4.0, 코드 예시는 Apache 2.0 표기를 따른다.
- 책은 CC BY-NC-ND 4.0으로 공개되어 있다. 여기에는 책 전체나 편집한 장 사본을 재배포하지 않고
  원문 링크와 분석을 보관했다.[^3]
- 이 두 자료는 작성 지침이다. `templates/`에 Google 공통 공식 양식이라는 파일을 생성하지 않는다.

## 적용 판단

문서 앞에서 문제와 핵심 결정을 이해하고 필요할 때 상세한 계약·흐름·제약으로 내려갈 수 있게
구성하는 원칙을 차용할 가치가 있다. 상세도 선택은 업무의 위험과 불확실성에 따라 한다.
별도 위원회, 특정 협업 도구, 회사 전체 공통 목차를 우리 사내 서비스 개발의 기본값으로 삼을
근거는 이번 자료에서 얻지 못했다.
