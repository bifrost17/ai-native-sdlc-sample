# Kiro Specs

Kiro는 요구사항·설계·작업 문서를 에이전트의 개발 흐름과 연결하는 제품이다. 이 조사는 공개
문서에 설명된 흐름을 분석한다. Kiro를 설치하거나 실제 생성 세션을 실행하지 않았으므로, 문서에
적힌 동작을 실측 성공이나 누락 방지 보장으로 취급하지 않는다.

## 산출물과 시작점

기능 개발은 `requirements.md`, `design.md`, `tasks.md`를 생성한다. 버그 수정은 첫 문서가
`bugfix.md`가 된다. 요구사항 우선과 설계 우선 흐름이 있으며, 설계 우선은 기존 아키텍처나
기술 제약에서 시작해 가능한 요구사항을 도출한다.[^1][^2]

| Kiro 문서 | 역할 | Anthropic 흐름과 비교 |
|---|---|---|
| requirements | 사용자 이야기와 수용 기준 | intent의 원래 문제를 정리한 뒤 나오는 요구사항에 가깝다. |
| design | 기술 구조·상호작용·오류와 검증 접근 | Anthropic combined spec의 설계 부분과 겹친다. |
| tasks | 실행 가능한 작업과 진행 상태 | plan의 실행 분해와 겹치지만 파일별 계획과 동일한 고정 계약은 아니다. |
| bugfix | 현재 결함·기대 동작·유지할 동작 | 버그의 intent와 회귀 경계를 함께 구체화하는 참고 요소다. |

Kiro의 파일 수를 우리 구조로 그대로 옮길 이유는 없다. 특히 `requirements.md`를 `intent.md`의
새 이름으로 바꾸면 요청자의 말로 의도를 보존하는 목적이 흐려진다. 기술적 출발점을 존중하되
해결할 문제와 기대 결과를 잃지 않도록 하는 것이 우리 팀의 적용 판단이다.

## 구체적인 요구 문장과 회귀 경계

공식 설명은 요구사항에 EARS 형식을 사용한다. [보관한 짧은 패턴](evidence/ears-pattern.txt)은
조건·사건과 기대 동작을 연결하는 예시다. 이 두 줄을 완전한 빈 requirements 양식이나 EARS
전체 문법으로 표시하지 않는다.[^2]

버그 문서는 잘못된 현재 동작, 올바른 기대 동작, 계속 유지되어야 할 동작을 분리한다. 설계와
작업은 재현·수정·회귀 검증으로 이어지도록 안내한다.[^3] 우리 팀에는 중요한 버그나 이전에 회귀가
있던 변경에서 유지할 동작을 명시하는 원칙이 유용하다. 모든 사소한 수정에 별도 bugfix 문서와
특정 테스트 기법을 의무화할 필요는 없다.

## 간소화와 갱신

Quick Spec은 앞에서 질문한 뒤 요구사항·설계·작업을 한 번에 생성하며 중간 단계별 승인 대기를
줄인다. 산출물 자체는 유지되고 이후 검토·수정할 수 있다. 문서가 충분한 것과 단계마다 사람이
멈춰야 하는 것은 별개의 선택이라는 사례다.[^4]

Best practices는 요구사항을 바꾼 뒤 설계를 다듬고 작업 목록을 동기화하는 구체적인 행동을
설명한다. 설계 우선에서는 변경된 설계를 기준으로 요구사항을 다시 검토하고 작업을 동기화한다.
모든 파일이 아무 행동 없이 자동으로 항상 일치한다는 뜻은 아니다. 이 가이드에서는 사람이
수정·재검토·동기화를 요청하는 지점이 드러난다.[^5]

기능별로 여러 spec을 유지하라는 권고도 있다. 팀 전체의 소프트웨어를 거대한 단일 명세로
확장하기보다 기능별 맥락을 이어가는 접근이다. 우리 팀에서는 명세 분할과 PR 분할을 동일한
단위로 고정하지 않고 의존 관계와 검증 가능성을 별도로 판단하는 것이 적절하다.

## 원본 양식의 공개 여부

공식 Specs·Feature·Bugfix·Quick·Best practices 페이지에서 파일 역할과 짧은 형식 예시를
확인했다. 이 조사 범위에서는 별도 배포되는 버전 고정 가능한 빈 양식 묶음을 찾지 못했다.
공식 웹 제품에서 생성된 파일을 내려받을 수 있다는 설명과, 제품의 빈 양식 원본이 공개되어
있다는 주장은 다르다. 따라서 템플릿을 임의로 재구성해 공식 원본이라고 저장하지 않았다.

메타데이터에는 공식 링크를 보관하고, 본문 재배포 이용 조건이 확인되지 않은 전체 문서는
복제하지 않았다. Kiro의 소프트웨어 라이선스와 포함된 오픈소스 고지가 문서 전체의 오픈
라이선스라는 뜻도 아니다.[^6]

## 적용 판단

갱신 이벤트를 작업 흐름에 붙이는 방법, 중요한 회귀 경계를 요구 문장으로 남기는 방법,
간소화된 흐름에서도 산출물을 유지하는 접근을 참고할 가치가 높다. 특정 제품 UI, 모든 변경의
다단계 승인, 문장 형식만으로 요구사항이 완전하다는 주장은 우리 기본 정책으로 가져오지 않는다.
