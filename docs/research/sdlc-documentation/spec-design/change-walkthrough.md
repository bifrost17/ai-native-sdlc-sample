# 새 발견이 들어왔을 때 spec의 현재 계약을 고치는 예시

root가 작성한 합성 전후 대조다. 실제 개발 에이전트가 자동으로 이렇게 행동한 관측 기록은 아니다.
입력과 후속 결정은 [M01 context](../../../../.claude/skills/design-spec/examples/migration/context.md)에 있다.

## 발견 전: 미확인 사항을 인계 허가로 취급하지 않음

최초 설계 시점에는 SQLite 전환·보존·복구 원칙을 검토할 수 있지만, JSON의 다른 소비자는 모른다.
그 상태를 다음처럼 표현해야 한다. 아래는 초안의 관련 부분을 설명하는 발췌이며 별도 승인본이 아니다.

```markdown
## Open questions
- Q1 carried forward: API 밖에서 JSON을 읽거나 쓰는 소비자는 아직 확인하지 못했다.
  업무 오너·운영 담당이 확인한다. 소비자가 있으면 전환 범위와 호환성이 달라지므로 plan 인계 전에 필요하다.
## Flagged concerns
- F1: 직접 소비자 미확인. 새 DB만 갱신하면 다른 소비자가 옛 JSON을 읽거나 별도 쓰기로 데이터를
  갈라놓을 수 있다. 업무 오너·운영 담당의 확인과 호환 방향 결정 전에는 전환 설계를 인계하지 않는다.
```

여기서 carried forward는 초안에 보존했다는 뜻이다. 사람 이름이 있다는 이유로 미결이 해소됐거나
planning-ready가 됐다는 뜻은 아니다. 제목·도입부에서도 F1이 현재 판단을 막음을 알린다.

## 발견과 결정 뒤: 관련 절 자체를 수정

운영 담당이 야간 보고서의 JSON 직접 읽기를 확인했고, 기존 읽기 계정·GET API로 전환하기로
업무 오너와 결정했다. [최종 예시](../../../../.claude/skills/design-spec/examples/migration/spec.md)는 다음을 반영한다.

| 바뀐 의미 | 기록한 위치 |
|---|---|
| 보고서가 새 처리 결과를 읽고 오류 때 옛 값으로 대체하지 않음 | R5 |
| 보고서의 전환 전후 호환성과 API 오류 결과 확인 | AC6 |
| 이중 쓰기·영구 JSON 미러를 선택하지 않은 이유 | Design의 소비자 결정 |
| 보고서 전환을 같은 전달 범위에 포함 | Constraints and scope |
| 확인되지 않은 소비자를 실제 확인·결정으로 대체 | Q1 answered와 해소된 F1의 의미 |

이미 plan이 있었다면 보고서 변경 경로·전환 의존·통합 검증·PR 범위를 함께 맞춰야 한다.
실행 파일이나 순서가 달라지면 그 계획 변경은 관련 구현과 같은 커밋에 남는다. 이 예시에서는
plan 인계 전 발견이므로 존재하지 않는 plan을 고쳤다고 주장하지 않는다.

## 수정하지 않아도 되는 것

같은 계약을 유지하는 helper 이름이나 코드 배치 변경은 그 자체로 spec 수정 이유가 아니다.
누락됐던 시험을 같은 계약에 추가하는 것도 spec의 요구가 달라졌다는 뜻은 아니다. 해당 plan의
검증 설명이 달라지면 거기만 맞춘다. 반면 재시도 의미·데이터 보존·권한·호환 계약이 바뀌었다면
단순 구현 세부라는 이름으로 spec에서 빼면 안 된다.
