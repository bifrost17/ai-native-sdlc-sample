# Spec: 담당자 조건으로 요청 목록 좁히기
Upstream: intent.md@2dd4386. Status: draft.
References applied: templates/spec.md@dbfd371(양식); examples/skills/design-spec/SKILL.md@dbfd371
(실험 오너가 명시적으로 선택한 작성 지침 — `disable-model-invocation`은 자동 호출을 막는 선택 방식
설정이며 판 정보가 아니므로 별도로 표기하지 않는다); tracker.py@2dd4386, requests.json@2dd4386,
tests/test_tracker.py@2dd4386(현재 계약과 시험 범위 확인); PROJECT-POLICY.md@210bcfa(역할·정책·검증
항목 미정 확인, 검증 명령·기록 위치는 이번 실험 범위에서 아래와 같이 결정됨).

기존 `list`/`show`/`complete` 명령과 JSON 계약을 유지하면서 `list --owner <ID>`로 담당자 문자열이
정확히 일치하는 요청만 기존 순서로 좁혀 본다. 조회이므로 파일을 바꾸지 않는다.

이 개정은 실험 런타임 결정 D4(HUMAN, 이번 대화, 구현 착수 전 사용자 피드백)를 반영한다. D4는
`--owner` 조회의 기본 범위를 바꾼다: 이전 판(Q1)은 완료 건을 기본 포함했지만, 이번 결정은
"우선 미완료만 보고 필요하면 완료도 같이 본다"는 실제 사용 흐름에 맞춰 기본을 미완료로 좁히고
새 옵션 `--include-done`으로 완료 포함을 선택하게 한다. 옵션 없는 `list`의 전체 상태·전체 담당자
출력은 이 결정의 영향을 받지 않는다.

## Requirements
- R1. `list --owner <ID>`(단독)는 `owner` 필드가 주어진 문자열과 대소문자까지 정확히 일치하고
  `status`가 `open`인 행만 requests.json의 기존 순서로 출력한다. `owner`가 `null`인 행은 어떤
  문자열과도 일치하지 않는다.
- R2. `list --owner <ID> --include-done`은 같은 담당자 일치 조건에서 `status`에 관계없이(완료 포함)
  requests.json의 기존 순서로 출력한다.
- R3. `--include-done`을 `--owner` 옵션 자체를 생략한 채 쓰면 사용법 오류다. 파일을 읽거나 바꾸기
  전에 종료 코드 2를 반환하고 stderr에 사용법을 알린다. `--owner ''`처럼 빈 문자열 값을 명시한
  경우는 옵션을 생략한 것이 아니라 담당자 문자열 `""`로 조회한 것이며, R1·R2·R6에 따라 정상 처리한다
  (이번 데이터에는 `owner`가 `""`인 행이 없으므로 빈 결과·rc=0이 되지만, 그것은 값이 일치하지
  않아서이지 사용법 오류가 아니다).
- R4. 옵션 없는 `list`는 상태·담당자로 좁히지 않고 현재처럼 전체 행을 원래 순서·열로 출력한다.
- R5. `show`/`complete`의 동작·출력 열·JSON 필드는 바꾸지 않는다.
- R6. `--owner`가 있는 모든 조회(단독, `--include-done` 동반)는 파일을 변경하지 않는다. 일치하는
  행이 없으면 stdout은 비고 종료 코드는 0이다.

## Acceptance criteria
- AC1 → R1,R6: `list --owner hana`는 requests.json 기준 미완료 R-101만 출력하고(완료된 R-103 제외),
  실행 전후 파일 바이트가 같다.
- AC2 → R2,R6: `list --owner hana --include-done`은 R-101, R-103을 그 순서로 출력하고 파일은
  변경되지 않는다.
- AC3 → R1,R6: 존재하지 않는 담당자(`nobody`), 대소문자만 다른 값(`HANA`), 화면 표시용 플레이스홀더
  `-`를 각각 기본 조회(단독 `--owner`)로 실행하면 모두 stdout이 비고 종료 코드 0이며 파일은
  변경되지 않는다. 마지막 사례는 `display()`가 `null` 담당자를 `-`로 보여주는 것과 실제 담당자
  문자열 일치를 혼동하지 않는지 확인한다.
- AC4 → R3: `list --include-done`(`--owner` 옵션 자체를 생략)을 실행하면 종료 코드 2, stderr에
  사용법 메시지, 파일 변경 없음을 확인한다. 대조로 `list --owner ''`와 `list --owner '' --include-done`은
  둘 다 사용법 오류가 아니라 stdout이 비고 종료 코드 0이며 파일이 변경되지 않음을 확인해, 빈 문자열
  값과 옵션 생략을 구현이 혼동하지 않는지 드러낸다.
- AC5 → R4,R6: 옵션 없는 `list`는 requests.json의 네 행(열린 것과 완료된 것 모두, 담당자 제한 없이)을
  원래 순서·열로 출력한다.
- AC6 → R5: `show`/`complete`의 정상 동작(대상 조회, 없는 ID, 반복 `complete`의 멱등성)은
  tests/test_tracker.py의 기존 시험으로 확인한다. 이 시험에는 파일을 읽거나 파싱할 수 없을 때의
  I/O 오류 처리 경로를 확인하는 시험은 없으므로, 그 경로의 회귀를 이번 작업에서 새로 확인할지는
  plan에서 정한다.

## Design
argparse의 `list` 하위 명령에 선택 인자 `--owner`(문자열, 기본값 `None`)와 `--include-done`(플래그)을
추가한다. 인자를 파싱한 뒤 `--include-done`이 있는데 `args.owner is None`이면(옵션 자체를 생략한
경우) 사용법 오류로 처리해 rc=2를 반환한다(R3). 이 판정은 반드시 `args.owner is None`으로 하고
빈 문자열의 참·거짓 여부(`not args.owner`)로 판정하지 않는다 — 그렇게 하면 `--owner ''`처럼 빈
문자열을 명시한 경우까지 옵션 생략으로 오판해 사용법 오류가 돼 버린다. 이 확인은 파일을 읽기 전에
끝내 조회의 무변경 성질(R6)에 영향을 주지 않는다.
`--owner`가 주어지면 JSON을 한 번 읽은 뒤 배열을 원래 순서대로 순회하며, 담당자 정확 일치에 더해
`--include-done`이 없으면 `status == "open"` 조건도 함께 만족하는 행만 남기고 기존 `display()`로
출력한다. 비교는 대소문자 변환이나 부분 일치를 하지 않으며, `None`은 어떤 문자열과도 같지 않으므로
별도 처리 없이 자연히 제외된다. `--owner` 미지정 시(즉 옵션 없는 `list`)에는 상태·담당자 제한 없이
현재 그대로 전체 출력한다. `show`/`complete`의 ID 조회 흐름에는 이 조건들을 넣지 않는다.

사용법 오류(R3)의 rc=2는 기존 파일 읽기·파싱 실패 시의 rc=2(main의 공통 `except`)와 값은 같지만
경로가 다르다 — 하나는 인자 검증 단계, 다른 하나는 파일 접근 이후다. 두 경로 모두 rc=2와 stderr
출력이라는 관측 가능한 계약은 같으므로 사용자 관점에서 구분할 필요는 없지만, 구현·시험에서는
서로 다른 코드 경로임을 인지한다.

별도 인덱스·캐시·정렬은 도입하지 않는다. 이미 배열 전체를 메모리에 읽는 현재 구조에서 조건을
하나 더 검사하는 선택이며, 다루는 데이터 규모에 기존 순회를 바꿀 성능 문제가 없다. 필터를
인라인으로 둘지 작은 함수로 뺄지, 사용법 오류를 어떤 parser 객체의 `.error()`로 낼지는 구현자가
정할 수 있는 사소한 선택이다.

## Constraints and scope
기존 `list`/`show`/`complete` 명령과 JSON 필드, 조회의 읽기 전용 성격을 보존한다(R5, R6).
업무 코드는 2~4파일 이내의 작은 변경이고 시험·문서는 별도다(intent.md 제약). 미배정 전용 조회,
복수 담당자 지정, 부분 일치·정렬, `open`/`done` 외 상태값에 대한 필터 확장, 새 저장소·프레임워크
도입은 이번 범위 밖이다.

## Open questions
- Q1 answered (changed by D4): `--owner` 단독은 미완료만, `--include-done`이면 완료도 포함한다.
  원래 F01 답변(완료 기본 포함)을 대체한다. 제품 책임자(HUMAN)의 결정이며 R1·R2·AC1·AC2에 반영했다.
- Q2 answered: 담당자 문자열은 대소문자까지 정확히 일치해야 하고, `null` 담당자는 어떤 문자열과도
  매칭하지 않는다. 미배정 전용 조회는 이번 범위에서 하지 않는다. 없는 담당자를 조회하면 빈 stdout과
  종료 코드 0이다. 제품 책임자(HUMAN)의 결정이며 R1·R2·R6·AC3에 반영했다.
- Q3 answered, D4로 사용법 확장: 기본 사용법은 `list --owner <ID>`이고, 완료 포함은
  `list --owner <ID> --include-done`이다. `--include-done`을 `--owner` 옵션 자체를 생략한 채 쓰면
  사용법 오류(R3)이지만, `--owner ''`처럼 빈 문자열 값을 명시한 경우는 옵션 생략이 아니라 정상
  조회다. 옵션 없는 `list`는 현재와 동일하게 유지한다(R4). 제품 책임자(HUMAN)의 결정이며
  R1~R4·AC1,2,4,5에 반영했다.
- 설계 중 추가된 새 미결 질문은 현재 없다.
