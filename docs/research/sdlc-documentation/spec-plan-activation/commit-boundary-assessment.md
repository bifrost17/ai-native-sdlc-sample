# T07 커밋 경계 독립 판단

2026-09-11 · Astra/high read-only 검토 응답을 root가 정리. 제품 fb6e374, spec 3c0e0c6, plan efa6a5b 기준.
아래는 실행 도중의 판단을 보존한 기록이다. 최종 실패·복구·후속 후보 판정은
[0024 결과](../../../experiments/0024-spec-plan-activation.md)에 있다.

**자발적 의미 동기화 성공, 같은 구현 커밋 기준 미충족, 최종 인도·검증 진행 중**으로 구분한다.
spec R6/AC8, plan 파일·TDD·P5·공개 검증, decisions의 진행 권한이 구현보다 먼저 갱신됐다.
fb6e374는 실제 spec/plan SHA를 명시하고 그 계획의 JSON 구현을 담는다. 중요한 JSON 계약 자체를
문서에서 누락하여 다음 인계를 깨뜨린 상황은 아니다. PR2 진행 중 범위를 바꾸고 구현 전에 재계획한 경우다.

그러나 제품 docs/GIT-WORKFLOW.md의 변경 계획·이유를 같은 구현 커밋에 담는 기준과 이번 실험 조건은
충족하지 않았다. fb6e374는 코드·시험·USAGE만 포함한다. 나중 merge commit이 공통 조상이 되어도
최초 관측을 성공으로 바꿀 수 없으며, 불필요한 코드 수정이나 이력 재작성으로 성공 형태를 꾸미지 않는다.

최종 리뷰에서 정정할 작은 현재 문서 불일치:

- plan 서두의 R1–R5/AC1–AC7 요약에는 상세의 R6/AC8이 빠져 있다.
- PR2 요약/P4의 P0–P4/P0–P3 표기는 상세 Done·공개 결정의 P0–P5와 달라 요약 독자가 JSON 검증을 놓칠 수 있다.
- 원래 요약 단계의 “이 PR의 유일한 RED”는 추가 JSON RED와 모순된다.
- 최초 초안의 구현 시작 대기 문장이 후속 진행 허가와 섞여 있다. decisions는 직접 지시와 문서 수락을 구별하므로 무단 구현의 근거는 아니다.

현재 제품을 마무리하는 데는 일반적인 머지 전 리뷰·교정으로 충분하다. 같은 커밋의 **자발적 성공 관측**까지
완료 조건으로 유지하려면 해당 경계만 새 clone/새 세션에서 업무 요청으로 시험해야 한다. 전체 재실험이나
템플릿 확대는 필요 없다. root는 원래 실패를 보존하고 기존 모델 선택 지침에 따라 Opus/high 부분 재시험을 선택했다.
TDD/feedback Skill 미호출과 실제 방법 적용, 자연어 리뷰에서 native Agent가 호출된 사실은 별도로 평가한다.

## 반복 관측 뒤 적용 범위 정정

새 Opus/high r01도 계획 ac1674b를 구현 2e1e4ed보다 먼저 별도 커밋했다. native 리뷰는 이를 초기 단계별
커밋의 정상 적용으로 해석했다. Astra는 maker와 use0024의 같은 문구를 다시 읽고, “단계별 커밋”이 최초 작성에
한정되지 않아 후속 변경의 같은 커밋 규칙과 적용 범위가 겹침을 확인했다. 기존 미충족 판정은 유지한다.
새 절이나 검사기를 만들지 않고 Git 정책의 두 곳만 명확히 하는 안을 권고했고 root가 채택했다.

- 최초 단계별 커밋 문장에 “새 작업의 최초”를 명시한다.
- 구현 시작 뒤 후속 변경의 plan은 구현 전에 갱신하되 별도 계획 커밋으로 분리하지 않고 같은 구현 커밋에 담는다고 명시한다.

새 use0024-r2@d4d2153은 원 use0024를 보존한 한 파일 수정이다. 제품은 원래 텍스트 요약 d4e24d9에
이 정책 파일만 적용한 fe61fe7을 새 partial 기준으로 삼는다. r02는 r01과 동일한 업무 prompt·Opus/high이며
동시 커밋이나 스킬을 HUMAN이 직접 상기하지 않는다. 같은 합성 데이터 반복이고 통계적 효과 증명은 아니다.
