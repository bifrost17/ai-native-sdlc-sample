# 활성화 후 실제 구현 실험 설계

2026-09-11 · HUMAN 운영용 제안. **실행 결과가 아니며 AGENT 복제본에 전달하지 않는다.**
실행자는 Codex root(HUMAN, simulated), 개발자는 실제 Claude Code다. 활성화·설치·제품 구현은 root가
별도로 수행한다. 이 문서는 [실험 운영](../../../experiments/README.md)과
[PERSONA](../../../experiments/PERSONA.md)를 따른다.

기본 선택은 **작은 CLI 전체 실행 1회**다. 새 사용판에서 질문·intent·spec·plan을 작성하고,
새 구현 세션이 두 PR을 순차 통합한다. 두 번째 PR 구현이 실제로 시작된 뒤 출력 요구를 추가해
TDD와 문서 동기화를 함께 관측한다. 중요한 실패가 남을 때만 그 경계를 재실험한다.
약 60분·HUMAN 대화 12턴을 운영 예산으로 삼되 고정 대본이나 자동 반복 횟수로 만들지 않는다.

## 사례와 자료 준비

제안 ID는 **F04-release-json**, 새 데이터 판 **6.0.0**이다. root가 실행 전에 확정한다.
seed 102의 동일한 네 행을 재사용하는 합성 후속 사례이며 독립 성공률 표본이 아니다.
F02의 ‘목록을 먼저 일반 인도’ 결정을 ‘두 기능을 함께 공개’로 바꾸므로 v2를 그대로 실행했다고 쓰지 않는다.

HUMAN이 새 manifest/public/human 자료를 마련하되 아래 입력 원본은 수정하지 않는다.

| 입력 원본 | AGENT의 초기 제품 위치 |
|---|---|
| datasets/v1/baseline/tracker.py | tracker.py |
| datasets/v1/baseline/test_tracker.py | tests/test_tracker.py |
| datasets/v2/F02/requests.json | requests.json |
| 새 F04 public.json | case.json |

원본 파일은 [v1 manifest](../../../experiments/datasets/v1/manifest.json)와
[v2 manifest](../../../experiments/datasets/v2/manifest.json)의 경로·해시로 확인한다.
제품의 사용 설명은 `USAGE.md`로 정하고 기존 세 명령만 설명한 초기판을 seed에 둔다.
`CLAUDE.md`/`PROJECT-POLICY.md`에는 실제 시험 명령
`python3 -m unittest discover -s tests -v`, Python 3.9+ 표준 라이브러리,
build/lint 별도 명령 없음, 로컬 JSON 도구라는 실제 조건을 채운다. maker의 `make check`는 제품 명령이 아니다.

초기 공개 카드에 실을 사실:

- 작은 사내 팀은 `list`, `show <ID>`, `complete <ID>`와 `--data <path>`를 사용한다.
  담당자의 요청을 찾기 위해 전체 목록을 눈으로 고르고, 주간 확인 때 상태별 건수도 수동으로 센다.
- 목록은 파일 순서대로 `id/status/owner-or-'-'/title`을 탭과 개행으로 출력한다.
  owner는 소문자 ASCII 또는 null, status는 open/done이며 fixture는 합성 데이터다.
- 담당자 목록과 주간 요약을 함께 공개하고 싶다. 개발 중에는 완성된 부분을 담당 엔지니어가
  로컬에서 먼저 확인할 수 있어야 한다. 서버·계정·네트워크·배포 서비스는 추가하지 않는다.
- 기존 명령·저장 필드를 유지하고 조회·요약은 요청 파일을 변경하지 않는다.

공개 카드에는 JSON 후속 요구, 비공개 결정 목록, 질문 유도 문장, 평가 기준을 넣지 않는다.
교육용 F03의 완성 spec/plan을 제품 입력으로 복사하지 않는다. 새 양식·정책에서 실제 문서를 작성하게 한다.

## HUMAN이 공개할 제품 결정

아래는 새 `human.json`에 둘 의미다. 관련 질문에 답하거나 spec에 다른 가정이 나타나면 구현 전에
공개한다. 답변의 순서·문장은 실제 대화에 맞춘다. 미공개 기대를 최종 검증에서 갑자기 요구하지 않는다.

| ID | 결정과 이유 |
|---|---|
| F04-D1 | `list --owner <ID>`는 정확 일치, done 포함, 원본 순서 유지. 없는 ID와 HANA는 빈 stdout/rc0, null은 문자열과 불일치. 옵션 없는 list는 기존 전체 목록이다. 최근 완료 건도 확인해야 한다. |
| F04-D2 | `summary [--owner <ID>]`는 `all<TAB>N`, `open<TAB>N`, `done<TAB>N` 순서의 세 줄/rc0. owner 선택은 목록과 같고 옵션 없으면 미배정도 포함한다. 없는 owner는 세 수 모두 0. 현재 상태 계약에서 all=open+done이다. |
| F04-D3 | 일반 사용은 두 기능 모두 완성해 HUMAN이 전체 흐름을 확인한 뒤 시작한다. PR1에서 목록만 테스트할 수 있어도 일반 공개는 아니다. 하나의 로컬 프로세스 설정으로 새 목록 선택과 요약을 함께 켜고 끈다. 설정 이름·오류 안내 문구는 AGENT의 제안을 보고 합의한다. |
| F04-D4 | 일반 OFF에서 새 동작은 비0과 분명한 stderr로 거부하고 데이터/부분 결과를 내보내지 않는다. 기존 list/show/complete는 유지한다. 설정은 운영자가 선택하는 로컬 프로세스 환경이며 인증 장벽이 아니다. |
| F04-D5 | 읽기 동작은 원본 바이트 불변. complete는 새 데이터 사본에서 해당 상태만 바꾸고 반복은 무쓰기여야 한다. 그 뒤 목록·요약에는 최신 상태가 반영돼야 한다. |
| F04-D6 | 공개 판단자는 HUMAN, 로컬 설정 적용자도 이번 모의 HUMAN이다. 인도 직후 ON/OFF 대조까지 수행한다. 정리는 아래 별도 수락 조건 전까지 하지 않는다. |

초기 기대값은 hana 목록 R-101/R-103, 전체 4/3/1, hana 2/1/1, nobody와 HANA 0/0/0이다.
fresh copy의 R-101 complete 후 hana는 2/0/2다. 원본 fixture와 기존 세 시험의 조건은 유지한다.

## 실행 흐름과 실제 변경 시점

1. **설치·격리 확인.** 활성화 판, 실제 사용자 설치의 플러그인 판·경로, CLI/모델/effort,
   적용 설정·스킬·hook·MCP를 기록한다. `--plugin-dir`로 제작 소스를 억지 주입한 실행을 영구 설치의
   자동 로드로 세지 않는다. 새 세션에 제공된 목록과 성공한 Skill/Read/Agent 도구 결과를 보존한다.
   실제로 제공되지 않은 관련 스킬은 환경 문제로 고치고 새 세션에서 시작한다. 불필요한 사용자 플러그인을 지우지 않는다.
2. **새 사용판→제품 seed.** 과거 use-template refs는 보존하고 새 사용판의 해시/파일 목록을 고정한다.
   해당 tree만 가진 별도 얕은 clone에서 제품 main과 seed를 만든다. maker 부모/main ref 조회 불가,
   shallow 경계, 전달 파일·해시를 확인한다. 연구·oracle·human 파일을 제품에 넣지 않는다.
   작업 경로 분리만으로 OS 수준 접근 차단까지 됐다고 주장하지 않는다.
3. **작성과 수락.** 자연 문제 설명과 설치된 관련 팀 스킬 사용 권한을 제공한다. AGENT가 질문하고
   intent/spec/plan을 작성하며 HUMAN은 실제 문서 판을 읽고 이유와 SHA로 수락한다.
   spec에는 선택 이유·대표 흐름·정확 출력/공개 계약, plan에는 파일·첫 행동 시험/예상 실패·최소 구현·
   통합 후 증거를 기대한다. 짧은 CLI에 별도 설계 문서나 UML을 억지로 늘리지 않는다.
4. **PR1 목록.** 수락된 plan과 선언된 문서/현재 코드만 새 구현 세션에 인계한다. 앞 대화는 전달하지 않는다.
   목록 선택과 공개 제어를 관련 시험·사용 안내와 함께 작은 PR로 검토·통합한다.
   일반 OFF/테스트 목록 ON/요약 아직 없음과 기존 동작을 실제 통합 main에서 확인한다.
5. **PR2 최초 구현.** 최신 main에서 파생해 수락된 요약 작업을 수행한다. HUMAN은 ‘요약 출력 형태를
   한번 보고 PR을 마무리하겠다’는 업무상 리뷰 시점을 두고 최초 코드·시험 결과를 확인한다.
   가능하면 미커밋 diff를 보되, 이미 커밋했다면 되돌리거나 최초 상태를 재연출하지 않는다.
6. **구현 중 업무 변경.** 최초 요약 구현과 시험이 관측된 뒤 아래 변경을 자연스럽게 공개한다.
   ‘문서를 갱신하라’, 파일명·누락 위치·스킬 호출명을 덧붙이지 않는다.
   새 spec 수락을 요청하면 실제 개정본을 읽고 그 SHA를 수락한다. 이미 받은 조사·초안 권한은 재질문시키지 않는다.
7. **PR2 통합·인도.** 변경 요구의 RED→GREEN, 기존 회귀, 관련 문서·구현 커밋과 PR diff를 확인한다.
   독립 native 검증과 HUMAN 리뷰를 기존 의미 있는 완료 지점에 묶는다. 마지막 diff에서 설치된 팀
   기준이 적용됐는지 확인하되 매 cycle 추가 reviewer를 만들지 않는다. 새 디렉터리에서 사용 안내대로
   인도하고 같은 HEAD/소스에서 OFF→ON→OFF 후 필요한 인도 상태로 돌린다.

F04-D7(위 6에서 처음 공개): 내부 자동화도 결과를 읽게 되어 `summary --json`이 필요하다.
stdout은 정확히 `all`, `open`, `done` 세 키의 정수 집계를 가진 JSON 객체이며 키 순서·공백은 무관하다.
기본 세 줄 출력, `--owner`, 빈 결과, 요청 파일 불변, 공개 제어는 그대로다. 파일 출력은 요구하지 않는다.
이는 [v3 R01](../../../experiments/datasets/v3/cases.json)의 의미를 F03형 세 집계 계약에 맞춘 새 결정이다.

PR2 작업을 미커밋으로 보여 주는 것은 한 번의 출력 리뷰 경계다. 도구 실행 도중 강제로 끊거나 매 TDD
cycle마다 사람에게 멈추게 하지 않는다. 최초 구현 전에 변경이 공개됐으면 ‘구현 중 변경’은 미관측이다.
그 사실을 쓰고 실제 관측된 후속 변화가 없는 한 성공으로 고쳐 쓰지 않는다.

## PR·스킬·검토의 최소 범위

목록 선택을 먼저 검토하고 같은 선택을 쓰는 요약을 이어 검토하는 두 PR이 적절하다. 같은 파일과
의미를 공유하므로 순차 작업한다. AGENT가 한 PR을 제안하면 단순 크기 위반으로 판정하지 않고
HUMAN이 이 검토 순서를 제품 엔지니어의 선택으로 설명한다. 단계마다 별도 PR을 만들지 않는다.
각 문서의 초기 커밋·수락 판은 첫 기능 PR 안에서 보존할 수 있다.

실제 hosted PR을 만들 수 있는 승인·환경이면 원격의 **전용 실험 통합 branch**를 base로 사용한다.
제품 main을 maker의 원격 main에 연결하지 않는다. base/head·수락·merge와 실행 주체를 기록하고
각 구현 head·최종 main을 maker의 로컬 기록 refs로 보존한다. 로컬 Git만 실행했다면 명확히 local-only로
남긴다. 단일 계정의 모의 리뷰/merge를 조직의 다른 사람 승인이나 hosted CI 검증으로 세지 않는다.

작성에는 실제 로드된 design-spec/plan과 관련 정책 검토, 구현에는 설치된 팀 TDD,
변경·커밋 준비에는 sdlc-feedback/검증자 기준이 관련된다. 이름 목록만으로 적용을 판정하지 않는다.
정확한 본문 판과 그 지침이 작업·시험·문서·검토에 준 영향을 읽는다. Skill 호출과 직접 Read는 별도로
기록하고 자연 요청에서 발견되지 않아 직접 요청한 복구를 자발적 발견 성공으로 바꾸지 않는다.
외부 API 보안·접근성·브랜드 등 이 CLI에 무관한 스킬을 전부 호출할 필요는 없다.

새 JSON 계약은 실제 요구 변경이므로 적절한 시험 추가다. 기존 GREEN 회귀를 일부러 RED로 만들지 않는다.
RED 로그에는 새 동작 부재라는 실패 이유가 보여야 하며 구문 오류·잘못된 환경 실패는 근거가 아니다.
plan이 영향 작업·검증·공개 단위와 새 spec 수락 판을 가리키고, 변경 구현과 같은 커밋에 갱신됐는지 본다.
spec이 수락을 위해 먼저 커밋된 경우에는 그 SHA와 후속 plan/구현 커밋 연결을 보존한다.

## 판정·후속 선택

통과는 제품 결과와 과정 관측을 나누어 기록한다. 전체 실험 기록에 다음 항목의 SHA·명령/rc·원 출력·
공개 대화 위치를 담은 작은 표면 충분하다. HUMAN의 미공개 사실·oracle 실행은 별도 기록에 둔다.

- 새 문서가 실제 코드/출력/공개 계약을 설명하고 새 세션이 그 문서로 PR1을 구현했는가.
- 새·변경 기능의 예상 RED와 기대를 유지한 GREEN, 기본 세 시험 및 인접 동작 회귀가 남았는가.
- PR2 구현 후 공개한 JSON 요구가 별도 문서 상기 없이 spec/plan·수락 참조와 관련 구현에 반영됐는가.
- PR1 부분 상태와 PR2 전체 상태가 실제 main에서 구분되며, 설정 공개·중단에 소스 변경이 없었는가.
- 실제 설치 판의 관련 스킬·검증이 관측됐으며 미실행을 완료라고 쓰지 않았는가.
- fresh directory 인도에서 기본/owner/빈 결과/JSON/complete 후 조회와 원본 보존이 재현됐는가.

문서 누락·회귀가 발견되면 HUMAN은 관측한 동작·기대·영향을 알려 복구하게 하고 첫 실패를 남긴다.
가벼운 표현 교정이나 한 번의 정상적인 spec 재검토는 별도 전체 재실험 사유가 아니다.
중요한 누락이 남으면 관련 활성 지침을 작게 고친 뒤 **새 clone/새 세션의 해당 구현 경계만** 재실험한다.
같은 JSON 요구 재사용은 피드백 후 확인이며 독립 표본이 아니다. 필요하면 v3 R02의 파일 출력 변화로
다른 표현을 시험하되 원본 보호/기존 파일 거부 같은 추가 범위를 명시하고 새 데이터 판으로 기록한다.
실패 없는 전체 실행을 무의미하게 두 번 반복하지 않는다. 반복 오류는 증거를 다시 읽고 Sonnet/medium에서
더 높은 effort 또는 Opus/high로 조정하며 실제 변경 시점·사유·사용량을 기록한다.

정리는 기본 완료 조건에서 분리한다. 공개·중단이 통과하고 예산이 남으면 HUMAN이 ‘로컬 모의 안정화
조건 충족’ 결정을 명시한 뒤 별도 작은 정리 PR로 임시 제어를 제거할 수 있다. 완성 기능·JSON·기존
회귀는 유지하고 수명이 끝난 OFF 거부 시험만 근거와 함께 정리한다. 실제 안정화 기간을 기다렸다고
쓰지 않는다. 생략하면 기존 F03의 정리 관측을 역사 근거로 재사용하고 **새 판의 정리는 미실행**으로 남긴다.

## W01은 지금 부트스트랩하지 않는다

[W01 입력](../spec-plan-design/candidate/examples/W01/context.md)은 React/Node의 기존 인증·저장소·
기능 설정·시험 환경이 이미 있다는 합성 계약이며 구현체가 없다. 새로 만들면 대부분의 비용이
기준 제품 제작에 들어가고 baseline 설계 선택과 이번 양식의 효과도 섞인다. 현재 잔여 핵심은 CLI로 관측 가능하다.

따라서 UI 렌더·브라우저 피드백, 서버 측 사용자 선별·인증·본인 데이터 보호, API/UI 전체 공개,
DB·동시성·운영 배포·장기 유지보수는 미관측으로 남긴다. 이를 실제로 검증할 필요가 생기면 먼저 별도
seed branch에서 W01 현행 계약을 구현·회귀 확인한 뒤 파생 기능 branch에서 독립 실행한다.
이번 CLI 통과를 W01 실행 가능성이나 전체 북극성 무오류 보장으로 확대하지 않는다.
