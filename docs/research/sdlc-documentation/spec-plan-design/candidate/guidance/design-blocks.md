# 필요할 때 선택하는 설계 블록

설계 양식의 Design에 필요한 블록만 가져온다. 각 계약의 이름과 도식의 이름을 맞춘다.
아래는 채울 형태이며 모든 항목·그림을 복사하라는 뜻이 아니다.
여섯 절은 spec 진입점에서 찾을 수 있게 하고 상세 정본은 여러 파일이어도 된다.

| 상황 | 남길 결정·표현 | 완성 예시 |
|---|---|---|
| 기존 흐름의 좁은 변화 | 정확 입력/출력·실패·삽입 위치. 짧은 표/문장으로 충분 | [F01](../examples/F01/spec.md) |
| API/공유 타입·객체 계약 | 입력/반환/오류·권한·호환·소유 관계. 관계가 복잡하면 클래스/컴포넌트 | [M01 architecture](../examples/M01/design/architecture.md) |
| 순서·경합·재시도가 결과를 바꿈 | 전제/부작용 시점·실패 분기·멱등성. 시퀀스 | [M01 storage](../examples/M01/design/storage.md) |
| PR별 준비/공개 상태가 다름 | 상태/허용/금지·제어·공개/중단·제거. 상태도 | [F03](../examples/F03/spec.md) |
| 저장/실행 위치·운영 경계 변경 | 프로세스/설정/데이터·전환·복구 책임. 배포 뷰 | [M01](../examples/M01/design/architecture.md) |

## 공유 인터페이스/API
| 이름·형태 | 입력/전제 | 반환·부작용 | 오류·권한·호환 |
|---|---|---|---|
| ‹경로+메서드 또는 클래스.메서드(필수 인자)› | ‹타입·null/누락·호출 주체› | ‹정확 형태·원자성› | ‹코드/예외·거부 시 상태·유지 소비자› |

## 데이터/상태
| 필드/상태 | 타입·허용값·소유자 | 유일성·순서·수명/전이 | 실패·호환 |
|---|---|---|---|
| ‹실제 이름› | ‹null/누락 포함› | ‹누가/언제 바꾸는가› | ‹보존/거부/복구› |

## 도식의 작은 작성 형태
Mermaid로 다음 요소를 선택한다. 완성 문법/렌더 결과는 위 예시와 검증 기록에 있다.
- 컴포넌트: `flowchart LR`, `A["실제 모듈·책임"] -->|"계약/데이터"| B["의존 모듈"]`.
- 시퀀스: `sequenceDiagram`, 실제 참여자와 호출/결과, 필요한 `alt` 실패 분기·효과 발생 시점.
- 클래스: `classDiagram`, 안정된 공개 메서드/속성과 의존·구현·소유 관계. 내부 메서드는 중요한 경우만.
- 상태: `stateDiagram-v2`, 상태별 허용/금지, 전이 이벤트·실패/중단을 표시.
- 배포: `flowchart`의 `subgraph`로 호스트/프로세스/신뢰 경계, 설정과 데이터 위치를 표시.

도식만으로 타입·오류/권한·동시성을 추측하게 하지 않는다. 표/문장과 역할을 나누되 같은 결정을
둘 다 다르게 정의하지 않는다. 다이어그램은 반드시 UML 형식일 필요가 없으며 클래스 그림 자체가
명확성을 높이지 않는 작은 변경에는 추가하지 않는다.

## 여러 설계 파일
예: spec.md는 R/AC·요약·정본 목록, design/api.md는 API 계약, design/storage.md는 스키마/원자성.
spec.md에서 정확 상대 링크와 소유 결정/필수 읽기 범위를 제공한다. 같은 Git 판의 문서 집합으로
인계·리뷰한다. 외부 정본은 판/스냅샷과 접근 경로를 특정한다. plan은 그 집합의 필요한 절을 참조한다.
요약과 상세가 어긋나면 한쪽을 임의로 믿지 말고 정본을 확인해 고친다. 분리 후에도 중요한 결정 누락은 안 된다.
