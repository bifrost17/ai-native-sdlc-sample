# 필요한 실행 상세와 문서 갱신

판단 기준의 정본은 [GitHub Flow](../../../../../GIT-WORKFLOW.md), [PR 크기](../../../../../PR-SIZE.md),
[공개 제어](../../../../../RELEASE-CONTROL.md)다. 아래는 정책을 대체하지 않고 이 변경의 답을
계획에 옮기는 형식과 예다. 활성 배치에서는 해당 프로젝트의 docs/ 세 정책을 연결한다.

여러 PR: `목적/포함 | 선행 | 머지 후 main·일반/시험 상태 | 남은 범위/Proof`를 작성한다.
파일 수나 LOC를 맞추기보다 하나의 검토 가능한 결과로 code/test/docs를 묶는다.
준비 PR도 기존 동작을 보존하며 독립 검증 가능해야 한다. 종속 PR은 선행 main 통합 후 시작하는 것이 기본.
stacked가 필요하면 실제 base/의존을 쓰고 선행 merge 후 base와 남은 diff를 다시 검증한다.
장기 기능 통합 브랜치·하나의 거대 PR을 큰 계획의 자동 결과로 만들지 않는다.

병렬: `작업 | branch/worktree | 소유 파일 | 공유 계약 판 | 통합/문서 조정자`.
실제 이름은 시작 시 정하되 경계·입력·책임은 계획에 남긴다. 같은 파일 작업은 순차 조정한다.
공유 계약 변화는 spec 집합과 영향을 조정한 뒤 관련 구현 커밋에 문서도 포함한다.
개별 테스트 GREEN 이후 최신 main과 합친 전체 계약·데이터·사용 흐름을 검증한다.

공개 분리: spec의 같은 제어를 재사용하고 PR별 상태·설정 위치/값·반영 시점·공개/중단·담당·제거 조건을
작업 순서/Proof에 채운다. 예시 [F03](../examples/F03/plan.md)의 phase별 기대가 다름을 참고한다.
일반 OFF에서도 배포 가능·기존 동작 유지가 필요하다. 기능 공개는 merge와 별도 결정일 수 있다.

운영: 실제 중지/전환/복구/재개 명령과 데이터 보존·대조를 확인한다. 미확인 입력은 담당·해결 시점을 쓰고
그 입력에 의존하는 단계만 기다린다. 코드 통합만으로 데이터 전환·권한·운영 리허설 성공을 주장하지 않는다.

## 영향받는 정본을 같은 구현 커밋에서 갱신
| 발견 | 변경할 정본 | 유지할 것 |
|---|---|---|
| 테스트/모듈 경로·작업 순서·PR 범위·증명 방법 변화 | plan과 이유 | 의미가 같은 spec |
| API/출력/오류/스키마·중요 설계/공개 계약 변화 | spec의 해당 정본·AC와 영향 plan, 이유 | 관계없는 정본 |
| 기존 계약을 그대로 확인하는 사례 추가/명백한 fixture 오타 수정 | 시험·실행/PR 근거, plan의 증명이 실제 달라지면 plan | 형식적 spec 편집 없음 |
| 요구/범위 자체 변화 | 관련 intent/spec/plan 및 필요한 사람 결정 | 허가된 범위 밖 임의 결정 없음 |

문서 하나당 별도 PR을 요구하지 않는다. 초기 문서의 입력 판·단계 수락 기록과 최종 PR 통합은 구별한다.
기존 plan이 spec@A를 참조하는 상황에서 한 구현 커밋에 spec과 plan을 고치면 그 미래 SHA를 쓸 수 없다.
이때 기존 Upstream A를 보존하고 바로 아래에 `Current change: 이 커밋의 spec.md 및 선언된 설계 정본 개정과
함께 읽는다. 변경 이유: ...; 결정 기록: ...`처럼 현재 변경을 명시한다. 커밋 후 다음 갱신/인계에서
확정된 실제 SHA를 참조할 수 있다. 존재하지 않는 해시나 “승인됨” 표기로 해결하지 않는다.
리뷰는 이전 수락 판과 현재 diff·현재 연결 정본을 함께 대조한다. 사람의 새 판단이 필요한 변화는 기존
피드백/수락 절차로 처리하며 이미 허가된 내부 선택을 매번 다시 승인받지 않는다.

이 방식의 [구체 갱신 예](../change-walkthrough.md)는 문서 diff 설계이며 제품 실행 기록이 아니다.
