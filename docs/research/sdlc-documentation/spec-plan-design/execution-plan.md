## 범위와 완료 조건

실제 spec·plan 양식, 작성 스킬·TDD 스킬·정책 연결 초안, 네 완성 예시, 독립 리뷰와 읽기 전용
인계 점검을 완성한다. 활성 템플릿·스킬·설치 환경·사용 브랜치·북극성 주석은 바꾸지 않는다.
제품 코드를 구현하거나 운영 실험을 실행하지 않는다. 중요 누락·모순이 해소되고 문서 인계가
가능하며 결과·한계가 파일과 Git 이력에 남으면 root가 설계 패키지 완료로 판단한다.

## 순서

1. 선행 연구를 커밋하고 공통 입력·출처·기준 판을 고정한다.
2. Codex, Astra/ultra, 실제 Claude Code Fable/max가 같은 조건에서 짧은 구조안과 대표 예시를
   독립 제안한다. 상대의 제안은 제출 전 읽지 않는다. 세 완성 패키지를 중복 제작하지 않는다.
3. root가 선택·기각 이유를 기록한다. F01/B01/F03/M01 완성 spec→plan 쌍을 먼저 작성하고
   양식·작성 지침·조건부 설계 표현·TDD 절차·정책 및 설치 초안을 도출한다.
4. 같은 후보 판을 새 Astra/ultra와 Fable/max 문맥에서 각각 리뷰한다. 상대 리뷰와 예상 판정은
   주지 않는다. root가 발견별 근거·영향·처리·잔여를 기록하고 수정한다. 후속 검토는 영향 범위에 집중한다.
5. 새 Sonnet/medium 두 세션이 F01·F03 문서만 읽고 작업·검증·PR 상태를 재구성한다. root는 실제
   응답을 읽고 후속 질문·변경 상황을 제시한다. 최초 실패와 복구를 보존한다. 제품 구현은 하지 않는다.
6. 상대 링크·스킬 형식·다이어그램 렌더링·출처 및 후보 해시를 확인하고 기존 make check를 수행한다.
   최종 후보·리뷰·한계·후속 반영/행동 실험 계획을 색인하고 커밋한다.

## 고정 설계 조건

- 북극성 원문과 우리 주석, 팀이 선택한 전체 동작 TDD 의무를 구분한다.
- spec의 여섯 정보 역할, plan의 네 정보 역할을 유지하며 실제로 채울 필드와 예시를 보강한다.
- spec.md는 진입점이며 단일 파일 강제가 아니다. 필요한 설계 정본을 연결하고 함께 갱신·리뷰한다.
  신규 사용자 조건은 inputs/spec-document-set.md에 보존한다.
- 구조·동작·계약·중요 데이터/인터페이스 설계는 spec, 파일·실행 순서·PR·통합·검증은 plan이다.
- 작은 변경의 상세는 짧게, 중요 경계는 구체적으로 쓴다. 모든 다이어그램·클래스·테스트 코드 강제 없음.
- TDD 공통 절차는 작은 자체 스킬, 의무는 기본 정책, 실제 실행 근거는 기존 실행/PR 기록이다.
- GitHub Flow·작은 PR·공개 제어·관련 구현과 문서의 동시 갱신을 유지한다.
- 정당한 테스트 정정/계약 변경과 기대값 약화를 구분하며 순수 리팩터링에 억지 RED를 만들지 않는다.
- 상류 양식·과거 데이터·승인/실패 기록은 보존한다. 합성 예시는 실제 승인·실행 성공으로 표현하지 않는다.

## 보존

공개 CLI 응답·도구 기록·모델/effort·인계 점검·검증 출력을 저장한다. 비공개 추론과 자격증명은
보존 대상이 아니다. 의미 있는 후보 판은 Git 커밋과 해시 manifest로 고정한다. 과거 결과를 덮어쓰지 않는다.
