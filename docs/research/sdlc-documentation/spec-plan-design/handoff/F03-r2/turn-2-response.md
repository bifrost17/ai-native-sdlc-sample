## 보완: P0 기준·통합 main 확인 시점

plan.md는 이 둘을 별도 언급하므로 작업 순서에 명시적으로 넣어야 한다.

- **기준 P0**: PR1 문단이 "기준 P0 → AC1 …" 순서로 적어놓았다. 즉 AC1용 새 RED 시험을 작성하기 **전에** 먼저 `python3 -m unittest discover -s tests -v`로 기존 `test_tracker.py`(P0)가 그대로 통과하는지 확인해 baseline 기준점을 잡는다. 이후 최소 구현(GREEN)과 리팩터링 뒤에도 P0를 다시 돌려 회귀 없음을 확인한다(SKILL 4단계 "run affected and neighboring tests"). PR2 착수 전에도 `tracker.py`를 다시 건드리므로 같은 방식으로 P0를 기준·회귀 양쪽에서 재확인해야 한다.
- **통합 main 검증**: "각 PR의 필요한 리팩터링 후 전체 시험, 최신 main과 결합한 판·통합 main 검증을 한다"는 문장대로, PR1·PR2 각각 리팩터링 직후 머지 전에 1회씩 수행하고, 공개 결정 전에는 spec Design이 요구하는 대로 "전체 AC1–6 + 최신 main 통합 검증"을 P4 리허설과 별도로 다시 한 번 종합 확인한다. 즉 통합 main 검증은 PR 단위(2회)와 공개 전 전체 단위(1회)로 총 세 지점에 있다.

## 네 공백 재평가

1. **공개 기록 서식** — 재검토 결과 공백 아님. `docs/RELEASE-CONTROL.md`가 이미 "실제 코드 판·대상·설정 값·결정자·근거"를 명시하고, 같은 문서가 "별도 필수 문서를 늘리지 않고 해당 절에 기록한다"고 못박는다. spec.md도 이 정책을 명시적으로 인용한다. `decisions.md`는 이 다섯 필드를 채우면 되는 기존 규칙의 적용이지, 새 템플릿을 발명해야 하는 공백이 아니다.
2. **오너/담당자 실체** — 재검토 결과 공백 아님. 이 사례는 애초에 가상이며, context.md가 "공개 담당은 합성 업무 오너(root 역할)"이라고 이미 배역을 지정했다. 가상 CLI 인계 범위에서 이를 실명으로 바꾸는 것은 문서의 공백이 아니라, 실제 채택 시점에 자연스럽게 채워지는 값일 뿐이다.
3. **cleanup 판정 절차("안정화", "구버전 의존 없음")** — 재검토 결과 공백 아님. RELEASE-CONTROL.md가 "고정 만료 일수나 별도 관리 시스템은 요구하지 않는다"고 명시적으로 선언한다. 즉 정성적 판단을 담당자 재량에 맡기는 것이 정책 그 자체의 설계이며, 새 고정 절차를 요구하는 것이 오히려 정책을 벗어나는 과잉 설계가 된다.
4. **CLI 문법 세부** — 재검토 결과 공백 아님. spec R1("list --owner ID")·R2("summary [--owner ID]")과 baseline의 argparse 서브파서 패턴(`--data`, subparsers, `add_argument("id")`)을 합치면 문법은 이미 완전히 결정된다: 기존 `list` 서브파서에 `--owner` 옵션 추가, 신규 `summary` 서브파서에 동일 옵션 추가. usage 문자열 같은 표현 방식은 구현 재량이지만 계약 판정에 영향 없는 문서 표현 수준의 재량이다.

## 결론

네 항목 모두 새 고정 서식이나 관리 절차를 추가할 필요가 없다. 기존 RELEASE-CONTROL 정책·spec R2/Design·시나리오가 이미 근거를 제공하며, 남는 것은 실제 채택 시점에 채울 "값"(실제 커밋 판, 실제 날짜, 실제 인물명)일 뿐 문서 구조상의 결손은 아니다. 처음 제시한 "공백" 지적은 과도했다.
