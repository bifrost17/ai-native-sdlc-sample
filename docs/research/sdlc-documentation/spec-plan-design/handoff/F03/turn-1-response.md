## 판단: 대화 없이 바로 구현 착수 가능한가

**불가능.** spec/plan은 기술 계약 면에서는 매우 구체적이지만(요구·AC·출력 바이트까지 고정), 실행에 필수적인 한 가지가 문서에 없습니다: **실제 제품 코드가 놓일 저장소 경로**. context.md/plan.md는 "tracker.py, tests/test_tracker.py, requests.json, USAGE.md"라는 파일명만 언급하고, 이 저장소 어디에 그 배치를 만들어야 하는지는 지정하지 않습니다. `inputs/baseline/`은 참조용 사본이라고 명시돼 있고(cases.md), 실제 작업 디렉터리는 별도로 정해져야 합니다. 이 한 가지를 빼면 나머지는 대화 없이 진행 가능한 수준으로 구체적입니다.

또한 spec.md·plan.md·intent.md 모두 `Status: draft`이며, "사용자 허가 범위는 설계 패키지 작성이며 제품 계획 승인/구현 실행이 아니다"라고 명시돼 있습니다. 즉 이 문서 자체가 **아직 구현 승인을 받은 상태가 아닙니다.** 인계받은 개발 에이전트는 착수 전에 이 draft가 정식 승인됐는지부터 확인해야 합니다.

## 실행할 작업 순서·파일·검증 (문서 기재 그대로, 미실행 계획)

**사전 확인**: 최신 main에서 `python3 -m unittest discover -s tests -v`로 기존 3개 시험(list 순서/읽기전용, show 정상/누락, complete 변경/반복) 통과 확인 → 회귀 기준선.

**PR1 (담당자 목록 + 공유 공개 제어)**
- 변경 파일: `tracker.py`, `tests/test_owner.py`(신규), `tests/test_release_control.py`(신규), `USAGE.md`
- 순서: `TRACKER_OWNER_INSIGHTS` 판정 함수 → OFF에서 `--owner`/`summary` 미등록 확인(RED 기대: 현재 `--owner` 미지원 rc2) → 최소 구현으로 GREEN → OFF 거부·설정값별(unset/0/false/공백/1/true/TRUE) 케이스 확인
- 머지 후 상태(계획): 일반 실행 OFF 유지, 개발자 TEST ON에서 목록 필터만 가능, summary는 ON에서도 아직 없음(단계 한정 관측, 영구 계약 아님)

**PR2 (all/open/done 집계, 같은 제어 재사용)**
- 변경 파일: `tracker.py`, `tests/test_summary.py`(신규), `tests/test_release_control.py`(갱신), `USAGE.md`
- 순서: summary 세 줄 출력 시험 먼저 작성·rc2 RED 확인 → 최소 집계 구현 → 담당자별/완료 후/설정 조합 확인, `test_owner.py` 재실행으로 회귀 확인
- 머지 후 상태(계획): 일반 OFF 유지, TEST ON에서 목록+집계 전체 가능 — **여기서 개발 구현 범위는 끝나지만 아직 공개 아님**

**공개/중단 결정 (코드 PR 아님)**
- PR2 통합 뒤 합성 업무 오너가 P0–P4 전체·최신 main 통합 검증을 확인한 후 별도로 `TRACKER_OWNER_INSIGHTS=1`을 일반 실행 환경에 적용/제거하는 결정. 이는 코드 변경이 아니라 환경설정 결정이며 기록만 남김.

**cleanup PR (조건부, 아직 미실행 조건)**
- 트리거: PR2 통합·공개/중단 관측 완료 + 구버전/롤백 대상의 flag 의존 없음 확인 + 오너의 정리 요청 세 가지 모두 충족 시에만 착수
- 변경: `tracker.py`에서 flag 분기 제거, 세 테스트 파일에서 OFF 거부 케이스만 제거(나머지 회귀는 유지), `USAGE.md`에서 flag 언급 제거
- 현재 예시에서 이 조건은 **미충족**(문서 명시).

## 예정 검증 vs 관측 사실 구분

**관측된 사실(문서에 실제 기재된 것)**: baseline 데이터 4행, baseline 3개 회귀 시험의 내용, 기존 tracker.py의 display 포맷/오류 처리 로직, spec의 계약 문구 자체.

**예정 검증(아직 실행되지 않은 계획)**: plan.md 스스로 "모든 시험은 예정이며 이름은 추가 계획", "Proof는 계획된 검사이며 실제 근거는 각 구현 PR/커밋 기록에 남긴다"고 명시. 즉 P0–P5 표, RED/GREEN 순서, OFF→ON→OFF 전환 관측, cleanup 검증은 전부 **미실행 계획**이며 실제 실행 증거가 아닙니다. 공개/중단 자체도 "이 합성 예시에서 아직 이행되지 않은 조건"으로 못 박혀 있습니다.

## 남은 결정 (문서가 위임하거나 비워둔 것)

1. **작업 경로 누락**: tracker.py 등 실제 배치 디렉터리가 어디인지 spec/plan/context 어디에도 없습니다 — 새 에이전트가 반드시 사람에게 확인해야 할 항목.
2. **draft 승인 여부**: spec.md·plan.md가 draft 상태로, 구현 착수를 승인하는 별도 확인이 문서상 없습니다(root 역할의 명시적 accept 기록 부재).
3. **공개(OFF→ON) 시점·주체**: "합성 업무 오너(root 역할)"가 결정한다고만 돼 있고, 실제 시점·승인 기준 통과 여부는 미기록.
4. **cleanup 조건 충족 여부 확인 주체**: "구버전/롤백 대상의 flag 의존 없음"을 누가 어떻게 확인하는지 방법론은 없고 선언만 요구됨.
5. **helper 함수 이름/구현 세부**: spec이 "helper 이름은 예시 수준이며 출력/제어 의미가 계약"이라 명시 — 구현 시 이름은 개발자 재량.

## 결론

기술 계약(요구·AC·출력 포맷·PR 분할·공개 제어 방식)은 대화 없이 실행 가능할 만큼 구체적입니다. 다만 (a) 실제 배치 경로 누락, (b) spec/plan이 아직 draft이고 명시적 구현 승인 기록이 없다는 두 가지는 개발 착수 전 반드시 확인이 필요한 진짜 공백입니다. 이 둘을 빼면 PR1→PR2→(조건부)cleanup 순서, 각 PR의 파일·시험·머지 후 ON/OFF 상태는 문서만으로 재구성 가능했습니다.
