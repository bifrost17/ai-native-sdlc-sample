# 독립 제안: 작은 계약과 실행 연결을 양식의 중심에 둔다

2026-09-11 · 독립 설계 후보. 운영 반영·제품 수락·실행 기록이 아니다. 다른 후보·모델 리뷰는 읽지 않았다.

## 1. 중심 아이디어와 정보 구조

**spec은 구현 방향을 바꾸는 결정을 고정하고, plan은 그 결정을 실제 파일과 선행 시험으로 연결한다.**
기존 여섯 절·네 절의 안내문을 채울 필드로 바꾼다. 작은 변경은 짧은 표와 한 단락으로 끝낸다.
상세의 기준은 “다음 구현자가 다시 결정해야 하는 중요한 것이 남았는가”다.

| spec 절 | 실제로 남길 필드 |
|---|---|
| Requirements | `R ID / 바뀔 동작·유지할 계약 / 근거` |
| Acceptance criteria | `AC ID → R / 조건·입력 / 관찰할 결과`: 대표 성공·실패·인접 회귀 |
| Design | `기존 연결점·흐름 / 중요한 경계의 책임·호출 형태·데이터·실패·불변식 / 선택 이유·감수할 영향` |
| Constraints and scope | `이어받은 제약 / 발견한 제한과 근거 / 제외 범위`: 앞의 R 참조 가능 |
| Open questions | `Q ID / answered·carried forward / 답의 근거 또는 영향·해결 주체·필요 시점` |
| Flagged concerns | `우려 / 근거·영향 / 결정할 사람 / 필요한 시점`: 없으면 살핀 범위 |

| plan 절 | 실제로 남길 필드 |
|---|---|
| Files that change | `확인한 경로(new 표시) / 변경 역할 / spec 참조`: 코드·시험·설명 |
| Order of work | `순서 / 만들 결과 / 선행 조건 / Proof 참조`: 여러 PR이면 목적·의존성·통합 후 main·남은 범위 |
| Risks | `깨질 동작·위험 단계 / 발견 방법 / 대응` |
| Proof | `AC·보존 동작 / 기존·추가 예정 시험과 경로 / 명령·관찰 / 기대 결과` |

Upstream·`Status: draft.`·적용 스킬의 출처와 판을 유지한다. 단계 수락은 기존 PR·결정 기록에서
확인한다. R·AC·시험명으로 연결하고, 새 식별 체계나 표를 채우기 위한 함수명·정량 목표는 만들지 않는다.

## 2. F01에 채운 작은 양식 조각

기존 feature의 **합성 작성 예시**다. 입력은 R-101=open/hana, R-102=open/min, R-103=done/hana,
R-104=open/null 순서다. 매 시험은 새 복사본을 사용하고 경로는 plan 예시의 제품 배치다.

**spec / Requirements·AC**

근거는 F01 intent 제약과 후속 답변 Q1–Q3이다.
- R1: `list --owner <ID>`는 담당자 문자열이 정확히 일치하는 요청을 완료 여부와 무관하게 파일 순서로 출력한다. null은 문자열과 일치하지 않는다.
- R2: 기존 list/show/complete·출력 열·JSON 형식을 유지한다. 조회는 파일을 바꾸지 않으며 일치 항목이 없으면 빈 stdout·rc=0이다.

| AC → 요구 | 입력 | 관찰할 결과 |
|---|---|---|
| AC1 → R1,R2 | `list --owner hana` | R-101, R-103만 이 순서·기존 출력 열로 표시, rc=0, 파일 바이트 동일 |
| AC2 → R1,R2 | `nobody`, `HANA`, `-`를 각각 담당자로 전달 | 각각 빈 stdout·rc=0, 파일 바이트 동일. 미배정 표시 `-`를 실제 담당자로 오인하지 않음 |
| AC3 → R2 | 옵션 없는 list, 기존 show/complete 사례 | 기존 결과 유지. list/show는 읽기 전용, complete의 정상 상태 변경과 반복 완료 동작 유지 |

**spec / Design**

| 경계 | 계약과 결정 |
|---|---|
| CLI 입력 | list에만 `--owner <ID>` 추가. 옵션이 없으면 기존 전체 목록 |
| 필터·출력 | `JSON 읽기 → list에서 정확 일치 필터 → 기존 display`. 대소문자 변환·부분 일치·재정렬 없음. show/complete의 공유 ID 조회는 그대로 |
| 구조 선택 | 기존 배열 한 번 순회면 충분. 새 저장소·인덱스·클래스 불필요. 내부 보조 함수 이름·분리는 구현 중 결정 |

나머지 절에는 미배정 전용·복수 담당자·정렬 제외, Q1–Q3 answered와 합성 답변 근거, 제공된 입력에서
외부 연동·권한·저장 형식 변경이 없어 별도 결정 우려가 없음을 남긴다.

**plan / Files that change·Order of work**

| 경로 | 이번 변경 |
|---|---|
| `tracker.py` | list 인자와 필터 연결(R1), 기존 출력·조회 경로 보존(R2) |
| `tests/test_owner.py` (new) | AC1–AC3의 추가 시험. 기존 `tests/test_tracker.py`도 회귀 검증에 사용 |
| `README.md` | 정확 일치·완료 포함·빈 결과·사용 예시(README 존재는 합성 조건) |

한 PR에서 기능·시험·설명을 함께 검토하고 공개한다. 추가 release flag는 필요하지 않다.

1. 기존 세 시험으로 기준 상태 확인. **제품 코드보다 먼저** `test_owner_exact_and_order`를 추가해 AC1 실패 관찰. 현재 미지원 옵션의 rc=2는 의도한 미구현 실패이며, fixture·실행 오류는 먼저 수정한다.
2. 최소 구현으로 통과시킨다. AC2도 시험 선행으로 진행하되 이미 만족하는 회귀에 억지 실패를 만들지 않는다. 녹색 상태에서 필요한 리팩터링 후 재검증한다.
3. AC3·기존 I/O 오류 보존과 사용 설명을 확인한다. 최신 main과 합친 결과 및 통합 후 결과를 검증한다. 이 PR로 공개 단위가 완성되며 남은 기능 PR은 없다.

**plan / Risks·Proof**

위험은 공용 경로 변경의 show/complete 회귀다. 기존 시험과 무옵션 회귀로 발견하고 필터를 list에 한정해 수정한다.

| 연결 | 예정 증명 |
|---|---|
| AC1–AC2 | 추가 예정 `tests/test_owner.py::test_owner_exact_and_order`, `test_owner_nonmatching`: 순서·전체 출력·rc·조회 전후 바이트 비교 |
| AC3·인접 회귀 | 기존 `tests/test_tracker.py`의 목록·조회·완료 세 시험, 추가 예정 `test_owner_no_option_and_io_error`: 무옵션 출력 및 없는 파일의 기존 rc=2·오류 접두사 |
| 통합 결과 | `python3 -m unittest discover -s tests -v`: 기존·추가 시험 모두 통과. Red/Green의 실제 명령·판·결과와 미확인 범위는 PR/실행 기록에 연결 |

기능 Red마다 커밋·PR은 강제하지 않는다. B01 버그는 재현 실패를 확인해 먼저 커밋하고 보호된 수정에서 시험을 약화하지 않는다.

## 3. 조건부 상세와 구현 중 갱신

**중요한 클래스·인터페이스·스키마는 spec에서** 실제 이름·책임·필요한 시그니처·필드 타입·누락/null·
오류·호환 규칙을 결정한다. 관계나 순서가 헷갈릴 때 그림을 추가한다. 아래는 표현 예시이며 제품 계약이 아니다.

| 그림 | 필요한 조건 | 작성할 최소 표현의 예 |
|---|---|---|
| 클래스 | 여러 구현의 공통 계약·소유 관계 | `RequestStore {list_requests(); complete_request(id)} ← Json/SQLite 구현`, 반환·오류는 계약 표 |
| 컴포넌트 | 모듈 경계·책임 변경 | `API → Store ← 보고서`, 직접 파일 읽기/API 이용 중 실제 선택 표시 |
| 시퀀스 | 재시도·동시성·실패 시점이 중요 | `요청 → 권한 확인 → 저장 → 응답`, 실패 분기·외부 효과 시점 추가 |
| 상태 | 전환 허용·중단 의미가 중요 | `일반 OFF/시험 ON → 전체 검증·사람 수락 → 일반 ON → 중단 시 OFF`, 비가역 효과 병기 |
| 배포 | 실행 주체·설정·데이터 위치가 중요 | M01 한 호스트에 `API / 야간 작업 / 저장소`, 중지·전환·재개 대상과 위치 표시 |

운영 전환은 spec의 호환·복구 계약을 plan의 실제 경로·순서·담당·증명으로 연결한다. M01의 미확인
호스트 명령은 확인 주체·전환 전 해결 조건을 남기고 발명하지 않는다.

F03 목록+집계의 spec은 일반 OFF·허용 시험 ON, 직접 접근·효과의 경계와 설정 실패 시 OFF를 정한다.
plan은 PR마다 `main 동작 / 일반·시험 노출 / 남은 범위 / Proof`를 채운다. 부분 ON 시험을 전체 수락으로
쓰지 않는다. 같은 제어·설정을 재사용하며 공개·중단 방법, 반영 지연/재시작, 담당자, 최종 전체 검증과
사람의 공개 수락, 제거 조건을 연결한다. 제거는 최종 코드·시험·문서와 구버전/복구 의존 확인 후 설정 순서다.

정확 일치→부분 일치는 spec 계약·AC, 경로·PR 순서 변경은 plan을 해당 구현 커밋에서 갱신한다.
상위 수락 판은 결정·커밋 기록 후 Upstream을 갱신한다. 사소한 내부 선택은 재승인하지 않는다.
TDD 절차·실패 대응은 소스·설치 안내를 갖춘 선택 가능한 자체 스킬 예시로, 새/변경 동작의 의무는 짧은 정책으로 둔다.

## 4. 가장 강한 반론과 채택하지 않을 요소

**반론: 표를 늘리면 작은 변경도 문서 완성을 기다리는 일이 된다.** 고정할 대상은 계약·중요 경계·선택
이유다. AC·시험은 다대다로 연결하고, F01은 위 조각 정도로 인계한다. 발견은 해당 문서에 갱신하며
미지의 사실을 확정 설계로 채우지 않는다. 설계를 무효화할 질문은 인계 전에 해결한다.

모든 그림 필수화, 내부 메서드 전체 명세, tasks 문서·상태 원장, 새 문서 검사기, 외부 스킬 의무는 채택하지 않는다.
리뷰어가 확인할 실패 사례:

- “정확 일치”라고 쓰고 구현자가 대소문자·null·순서를 다시 추측해야 하는가.
- plan에 시험이 있어도 실제 순서가 구현 → 시험이거나, Red가 실행 환경 오류인데 동작 실패로 기록됐는가.
- PR별 ON 성공을 전체 AC·일반 공개 승인으로 바꾸거나, OFF에서 직접 호출·기존 동작을 확인하지 않았는가.
- 문서 변경이 부록에만 있고 현행 계약은 낡았거나, 합성 예시·과거 수락·예정 검증을 현재 승인·성공으로 사용했는가.

근거 구분: [Anthropic 발췌](../inputs/north-star-excerpts.md)는 요구·설계 결합, 파일·순서·시험, 동시 갱신·검증 피드백의 근거다.
절 유지·TDD 의무·PR·공개 제어는 [brief](../brief.md)와 팀 정책의 결정, 필드·그림 표현은 이 후보의 제안이다.
F01 사실·명령은 [spec 입력](../../../../../.claude/skills/design-spec/examples/feature/context.md)과
[plan 입력](../../../../../.claude/skills/plan/examples/context.md)에 근거한다.

## 추가 의견: spec을 여러 정본 문서로 구성할 때

사용자가 보충한 “spec.md 단일 파일을 강제하지 않는다”는 조건에 동의한다. F01은 단일 파일로
충분하다. M01은 spec.md를 진입점으로 두고 API·저장 계약·이행 설계 등을 연결된 정본 문서로
분리할 수 있다. Design에는 중요한 결정 요약과 `문서 / 정본으로 정하는 범위 / 필요한 독자·시점 /
변경 시 함께 갱신할 부분`을 남긴다. plan은 작업별로 읽어야 할 설계 문서를 참조한다.

저장소 안의 문서들은 수락한 커밋 트리에서 함께 조회하고, 수락 기록에 세트의 포함 범위를 명시한다.
외부 문서는 정확한 판을 연결한다. 계약 변경은 해당 정본과 영향을 받는 요약·AC·plan을 갱신하되
무관한 문서를 형식적으로 고치지 않는다. 분리 기준은 문서 길이보다 독립적인 계약·독자·변경 이유다.
