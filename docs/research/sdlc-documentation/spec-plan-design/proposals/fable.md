제안은 아래와 같다. brief, 북극성 발췌, 현재 spec·plan 템플릿, design-spec·plan 스킬과 depth 참조, 연구 요약 두 편, TDD 스킬 비교, 세 운영 정책 문서, F01 feature 예시, F03 과거 plan만 읽었다. 다른 제안과 모델 리뷰는 열지 않았고 파일 편집과 명령 실행은 하지 않았다.

## 1. 중심 아이디어와 필드 구조

여섯 절과 네 절은 그대로 두고, 각 절의 안내 문장을 이름 붙은 슬롯으로 바꾼다. 슬롯은 표 하나 또는 고정된 한 줄이며, 채우거나 없음과 그 이유를 쓴다. 세션마다 깊이가 달라지는 원인은 자유 서술이므로, 다음 사람이 다시 추측하게 되는 세 가지만 표로 고정한다. 계약의 정확한 형태, 조건별 기대 결과, 그것을 증명하는 선행 테스트다. 나머지는 짧은 서술로 남긴다.

spec 슬롯:

| 절 | 슬롯 | 채울 열 |
|---|---|---|
| 머리 | 요약 세 줄 | 바꾸는 것, 유지하는 것, 사람이 결정할 것 |
| Requirements | R 목록 | ID, 조건과 결과 한 문장, 변경 또는 유지, 출처 |
| Acceptance criteria | AC 표 | ID, 조건, 행동, 기대 결과, 덮는 R. 실패나 인접 동작 사례 하나 이상 |
| Design | 접근 단락 | 선택, 버린 대안 하나, 감수하는 단점 |
| Design | 계약 표 | 이름, 종류, 형태, 구속력, 근거 R |
| Constraints and scope | 유지·제외 목록 | 이어받은 제약, 발견한 제약과 근거, 하지 않을 것 |
| Open questions | Q 표 | ID, answered 또는 carried forward, 답이나 미정, 근거·담당, 반영 위치 |
| Flagged concerns | 우려 표 | 근거, 영향, 결정자, 필요 시점. 없으면 살핀 범위 |

계약 표의 종류는 명령 옵션, 함수 시그니처, 스키마, 파일 형식, 상태 전이 중 하나다. 구속력이 계약인 행만 spec이 결정한 것이고, 예시 행은 구현자가 바꿀 수 있다.

plan 슬롯:

| 절 | 슬롯 | 채울 열 |
|---|---|---|
| Files that change | 파일 표 | 경로, 신규 또는 변경, 역할, 관련 AC나 계약 |
| Order of work | PR 블록 | 목적, 포함, 선행 PR, 머지 후 main 동작과 노출 상태, 남은 범위. 안의 단계는 기준, RED, GREEN, 정리, 통합으로 표기 |
| Risks | 위험 단락 | 가장 위험한 단계, 감지와 대응, 버린 실행 대안 |
| Proof | 증명 표 | AC, 테스트 파일::이름, 기존 또는 추가, 선행 여부, 명령, 기대 결과. 통합 확인과 검증 한계 행 포함 |

TDD 연결은 AC 표의 행이 증명 표의 행이 되고, 증명 표의 선행 열이 커밋 순서를 정하는 것이다. 정책 문장은 하나다. "새 동작과 변경 동작은 증명 표의 테스트를 먼저 써서 의도한 이유로 실패하는 것을 확인한 뒤 구현하고, 실행 출력을 PR에 남긴다." 결함은 재현 테스트 커밋과 수정 커밋으로 단계가 고정되고 선행 열에 재현 커밋을 적는다. 한 동작씩 진행, 저장소 실제 명령으로 RED 확인, 최소 GREEN, 리팩터, 테스트 약화 금지, test-after가 생기면 삭제 대신 사실을 밝히고 누락 테스트를 보강하는 절차는 `.claude/skills/tdd/SKILL.md` 한 파일에 둔다. 소스와 폴더 복사 설치 안내를 붙인 선택 가능한 기본 예시이며 외부 스킬 이름을 요구하지 않는다.

## 2. F01 작성 조각

현재 feature 예시는 구현 뒤 테스트를 추가한다. 아래 조각이 그 순서를 바꾼다.

```markdown
## Acceptance criteria
| AC | 조건 | 행동 | 기대 결과 | R |
|---|---|---|---|---|
| AC1 | context.md 데이터 복사본 | list --owner hana | R-101, R-103만 원래 순서. 파일 바이트 동일 | R1,R3 |
| AC2 | 같은 데이터 | --owner nobody, HANA, - 각각 | stdout 없음, rc=0, 파일 동일 | R1,R3 |
| AC3 | 같은 데이터 | 옵션 없는 list, 그리고 없는 파일 경로 | 네 행 원래 열. 없는 파일은 기존 rc=2와 오류 접두사 | R2,R3 |

## Design
| 이름 | 종류 | 형태 | 구속력 | R |
|---|---|---|---|---|
| list --owner | 명령 옵션 | 선택 인자 <ID>. 문자열 정확 일치, null 담당자는 비일치 | 계약 | R1 |
| 필터 위치 | 흐름 | JSON 읽기 뒤, display 앞, list에만 적용 | 계약 | R2 |
| filter_by_owner(rows, owner) | 함수 | 순서 유지 | 예시 | R1 |
```

```markdown
## Order of work
PR1, 유일. 목적: 담당자 필터. 선행: 없음. 머지 후: list --owner 즉시 사용, 공개 제어 없음. 남은 범위: 없음.
1. 기준: python3 -m unittest discover -s tests -v 로 기존 세 시험 통과 확인.
2. RED: tests/test_owner.py::test_owner_exact_and_order 작성 후 실행. --owner 미인식 argparse 오류로 실패해야 함.
3. GREEN: tracker.py list 파서에 인자 추가, 읽은 행 필터. 2의 시험만 통과시킴.
4. RED, GREEN 반복: test_owner_no_match_cases는 AC2, test_owner_no_option_and_io_error는 AC3.
5. 정리: 중복 제거, README.md 사용 예시. 전체 시험 재실행.
6. 통합: 최신 main과 합친 뒤 Proof 재실행, 출력을 PR에 첨부.

## Proof
| AC | 테스트 | 기존/추가 | 선행 | 명령 | 기대 |
|---|---|---|---|---|---|
| AC1 | tests/test_owner.py::test_owner_exact_and_order | 추가 | RED 먼저 | discover -p test_owner.py | 3단계 전 argparse 오류, 후 통과 |
| AC2 | 같은 파일::test_owner_no_match_cases | 추가 | RED 먼저 | 같음 | 빈 stdout, rc=0, 바이트 동일 |
| AC3 | 같은 파일::test_owner_no_option_and_io_error, 기존 세 시험 | 추가, 기존 | RED 먼저 | discover 전체 | 모두 통과 |
| 통합 | 최신 main 합친 판 | 기존 | 아니오 | discover 전체 | 모두 통과, 출력 PR 첨부 |
```

## 3. 조건부 표현, 문서 갱신, PR과 공개 제어의 연결

조건부 슬롯은 트리거가 맞을 때만 Design의 하위 절로 만든다. 트리거가 없으면 절도 N/A도 쓰지 않는다.

| 트리거 | spec Design에 추가 | plan에 대응 | 다이어그램 조건 |
|---|---|---|---|
| 공개 단위가 PR 여럿에 걸침, F03 | 공개 계약 표: 공개 단위, 일반 기본 OFF, 테스트 대상, 직접 접근을 포함한 제어 경계, 설정 실패 시 동작, 공개·중단 조건, 제거 후 유지 계약 | PR 블록의 노출 상태, 증명 표의 OFF 거부·ON 동작 행, 제어 이름·설정 위치·담당·제거 조건 | 없음 |
| 저장 표현 변경·이행, M01 | 이행 표: 현재·목표 표현, 불변식, 부분 실패, 공존·전환·복구 조건 | 전환 순서, 중지 조건, 확인 방법. 모르는 운영 명령은 담당과 해결 단계로 표기 | 상태, 전환 상태가 셋 이상일 때 |
| 외부 경계·API 전환 | 요청·응답 의미, 거부·실패 동작, 기존 소비자 호환 | 소비자별 확인 행 | 시퀀스, 호출 순서가 계약이고 참여자가 셋 이상일 때 |
| 새 타입이 여러 모듈에 걸침 | 계약 표에 의존 방향 | 파일 소유 경계 | 클래스 또는 컴포넌트 |

실행 위치나 설정 위치가 바뀔 때만 배포 다이어그램을 둔다. 다이어그램은 Mermaid 텍스트로 두고 계약 표처럼 계약인지 예시인지 표시한다. F03의 과거 spec과 plan은 형태 참고일 뿐 새 설계의 승인 근거가 아니다.

갱신 규칙은 행 단위다. 발견이 R, AC, 계약 표, 공개 계약 표를 바꾸면 spec의 해당 행을 고치고 이유를 커밋에 남긴 뒤 plan의 Upstream을 다시 고정한다. 파일, 순서, PR 경계, 증명 표만 바뀌면 plan 행만 고친다. 두 경우 모두 관련 구현과 같은 커밋이다. 계약 표에 없는 내부 선택은 재승인 대상이 아니다. PR 설명은 plan의 PR 블록을 옮기고 실행한 증명 표 행의 명령과 출력을 붙인다. reviewer는 diff를 계약 표와 증명 표에 대조한다. 공개 결정은 merge와 별개로 기존 운영 기록에 남긴다.

**가장 강한 반론과 완화.** 표를 강제하면 작은 변경도 형식 채우기가 되고, 표는 서술보다 사고를 덜 담아 채웠지만 얕은 문서가 된다. 완화는 세 가지다. 필수 표는 spec의 AC·계약·Q와 plan의 PR 블록·증명뿐이고 행은 한 문장이면 된다. 조건부 표는 트리거가 맞을 때만 만든다. 깊이는 표가 아니라 F01, B01, F03, M01의 완성 예시가 보여 주고, 접근 단락은 서술로 남긴다. 두 번째 반론은 AC와 테스트를 행으로 묶으면 테스트가 AC 복제가 되어 과적합한다는 것이다. 한 AC에 여러 테스트와 한 테스트에 여러 AC를 허용하고, 기대값은 구현이 아니라 데이터에서 정한다는 규칙을 TDD 스킬에 둔다.

**채택하지 않을 것.** Spec Kit식 tasks 파일이나 OpenSpec식 design 파일 분리, 모든 변경의 다이어그램 의무, 커버리지 수치, 별도 TDD 원장과 단계별 커밋 승인, plan에 테스트 코드 전문 복제, test-after 코드를 지우고 다시 시작하는 규칙, 특정 외부 스킬 이름 의무화.

**reviewer가 확인할 실패 사례.**
- AC 행이 R을 되풀이하고 기대 결과에 값이 없다. 예를 들어 "필터가 동작한다".
- 계약 표에서 내부 함수명이 계약으로 표시되거나 명령 옵션의 형태가 비어 있다.
- 증명 표의 테스트가 저장소에 없거나, 선행 표시인데 커밋 순서에서 구현이 먼저다.
- 공개 제어에서 OFF의 직접 접근 차단 행이 없거나 부분 ON 결과를 전체 AC 통과로 적었다.
- AC가 바뀌었는데 plan만 고치고 spec과 Upstream을 다시 고정하지 않았다.
- 트리거 없는 조건부 절을 N/A로 채워 문서가 커졌다.
- 다이어그램이 계약 표와 다른 흐름을 말한다.
- 계약 표 밖의 내부 선택이 Open questions로 올라와 재승인을 요구한다.
