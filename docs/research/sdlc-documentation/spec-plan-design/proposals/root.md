# Codex 독립 제안 — 기본 계약 표와 조건부 설계 블록

작성: root. 다른 두 모델의 제안 수신 전 고정한 제안이다.

## 중심 구조

빈 형식부터 늘리기보다 같은 개발건의 좋은 spec·plan을 먼저 작성하고 두 문서에서 반복되는
필드를 추출한다. spec의 여섯 역할·plan의 네 역할은 유지하되 답을 넣을 수 있는 행을 제공한다.
짧은 기능은 기본 표와 한 설계 단락으로 끝나고, 위험이 있는 계약만 추가 블록으로 확장한다.

spec 기본: `R | 바뀔/유지할 계약 | 근거` 및 `AC→R | 조건/입력 | 행동 | 기대/불변식`.
Design에는 `경계/책임·선택·이유`를 최소한 실제 이름으로 쓴다. API·데이터·상태·동시성·배포 경계가
바뀌면 해당 계약 표와 도식이 들어간다. 공통 가이드가 모든 빈 선택 절을 N/A로 채우게 하지는 않는다.

plan 기본: 변경 파일과 역할, 행동 단위 작업 순서, 핵심 위험, `AC/결과 | 대상/명령 | 기대 | 기존/추가`.
각 행동 작업에는 처음 실패로 구분할 사례와 연결할 구현이 있다. 모든 RGR cycle을 미리 나열하지 않는다.
PR 블록은 목적·선행·완료 후 main/공개 상태·남는 일·Proof 참조를 묶는다. 병렬 작업에는 파일 경계와
공유 계약 판·통합 담당을 명시한다. 테스트와 구현과 사용 설명은 같은 PR에 담는다.

## F01 조각

spec R1: owner는 대소문자를 구별한 정확 일치이며 완료 건 포함, null은 어느 문자열에도 비일치.
AC1: `--owner hana` → R-101/R-103 원순서, 파일 바이트 불변. AC2: nobody/HANA/- → 빈 결과·rc0.
설계: list의 JSON 읽기 후 필터→기존 display. show/complete에는 필터를 적용하지 않는다.

plan: tests/test_owner.py에 AC1을 먼저 쓰고 미지원 옵션/필터 부재로 실패하는지 확인한 뒤 tracker.py의
list 경로를 연결한다. AC2 사례를 하나씩 검증·필요한 구현 후 AC3 기존 명령·I/O 오류를 확인한다.
사용 설명과 한 PR, 최신 main 통합 결과의 unittest 전체를 확인한다. TDD 절차를 한 번 참조한다.

## 조건부 깊이

API는 입력/출력/오류/권한, 데이터는 필드/제약/소유/수명·복구, 상태는 전이·거부·중복을 명시한다.
컴포넌트 도식은 책임·의존, 시퀀스는 순서·실패, 클래스는 안정된 객체 계약, 배포는 실제 실행/신뢰 경계를
설명할 때 쓴다. 도식의 이름·화살표와 계약 표가 같아야 한다. 방법론 이름이나 장식 그림은 추가하지 않는다.

M01의 스키마/공유 함수/원자성 전략은 plan으로 넘기지 않고 spec에서 결정한다. 계획은 해당 결정을
구체적인 파일·시험·통합 순서로 옮긴다. 미확인 실제 운영 명령은 전환 단계 전 해결할 제한으로 남긴다.

## 반론과 대응

표도 빈 가이드로 퇴화할 수 있다. 네 연결된 완성 예시로 충분한 답의 깊이를 보여주고 새 소비자가
계약·첫 시험·PR 상태를 재구성하는지 확인한다. 반대로 예시의 모든 표를 복사하는 과잉을 막기 위해
필수 정보와 조건부 선택 이유를 작성 지침에서 구분한다. 고정 줄 수나 모든 다이어그램 의무는 두지 않는다.

실행이 문서와 달라지면 영향받는 정본만 갱신한다. 모든 테스트 이름·도구 출력의 원장을 plan에 두지 않는다.
스킬은 기본 규칙을 소유하고 실제 RED/GREEN과 이탈은 실행/PR에 남긴다. TDD가 요구 충족을 대신하지 않는다.
