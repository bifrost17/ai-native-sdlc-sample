이 판정은 문서 설계에 한정하며 제품 구현, 실제 TDD 이행, 설치·공개 또는 전체 실행 계획의 완료 판정이 아니다.

  입력을 중복 복제하는 새 체계나 설치 스크립트는 필요 없다.
- 비차단 이유: 현재 후보 내부 참조는 필요한 입력을 제공하고, 같은 문서 33–34행이 활성화 시

  활성화 작업의 빠뜨릴 여지를 줄인다.

**주요 검토 근거**

1. `templates/spec.md`, `skills/design-spec/SKILL.md`와 M01의 `spec.md`는 여섯 정보 역할을 유지하면서
   설계 문서 집합을 실제 인계·리뷰 범위로 취급한다. M01의 `design/architecture.md`는 facade와
   `SQLiteStore`의 반환·예외·연결 수명·권한 경계를, `design/storage.md`는 실제 필드·순서·검증·
   트랜잭션·import/export 계약을 소유한다. `design/operations.md`에는 전환·복구의 조건이 있다.
   이 결정들을 plan에 미룬 형태가 아니다. F01은 단일 파일의 짧은 흐름으로 같은 목적을 달성하므로
   모든 사례에 클래스 그림을 더할 이유도 없다.

2. F01의 `spec.md` AC1–4/Design과 `plan.md` Order/Proof는 실제 fixture, 정확 일치, 원순서,
   출력·바이트 불변, 기존 흐름 및 파일 오류를 연결한다. 예를 들어 `HANA`가 `hana` 행을 돌려주거나
   표시용 `-`를 null과 매칭하는 구현은 명확히 잘못된 결과다. plan은 최초 미지원 옵션의 rc2와
   원하는 행동의 기대값을 구별하고, 이미 GREEN인 인접 사례에 인위적인 실패를 요구하지 않는다.

3. B01의 `spec.md` Design과 `plan.md` Order는 입력 주변 네 ASCII 문자만 제거하고 원본 오류
   입력을 보존한다. 기본 `strip()`으로 NBSP까지 허용하는 반례가 구체적으로 배제된다. 실제 제어문자
   재현·실행·시험 선행 커밋 후 보호된 수정, 잘못된 재현은 보호 단계를 벗어나 다시 정정·고정하는
   절차가 연결되어 있다. 일반 기능 TDD에 새 시험 생성까지 막는 fix 모드를 적용하지도 않는다.

4. F03의 `spec.md` Design/AC5–7과 `plan.md` Order/Proof는 PR1의 목록 TEST ON, PR2의 전체
   TEST ON, 일반 공개, OFF 중단, 조건부 cleanup을 구별한다. PR1에서 ON인 summary가 없다는
   사실을 PR2의 영구 회귀로 고정하지 않는다. cleanup에서는 폐기되는 OFF 계약의 이유를 기록하고
   최종 기능 시험을 유지한다. 두 PR은 공유 파일 때문에 순차이며, 각 main 상태·남은 공개 범위·
   동일 코드의 설정 전환·전체 통합 증명이 명시되어 있다.

5. M01의 `plan.md` PR-A/B/C는 고정 저장 계약 아래 보고서와 신규 저장소를 병렬 준비하고,
   공유 문서 변경은 조정한 뒤 A/B 통합 이후 선택·API를 연결한다. 기본 JSON이 유지되는 main과
   실제 데이터 전환의 준비 상태를 혼동하지 않는다. 특히 전환 후 새 쓰기가 있거나 불명일 때
   옛 백업 JSON 또는 결함 있는 옛 writer로 복귀하는 반례는 운영 정본이 금지한다. 실제 운영
   명령을 모른다는 Q4는 담당·필요 시점·중지 조건을 가지므로 코드 설계를 막는 미정과 구별된다.

6. `skills/tdd/SKILL.md`와 `policy-and-delivery.md`는 모든 새/변경 동작에 대한 팀의 test-first
   의무를 북극성의 결함 재현 절차와 구별한다. 시험 기대값의 독립 근거, 환경 오류와 행동 RED의
   구별, 순수 리팩터링, 정당한 시험 정정, 구현 선행 이탈의 정직한 기록을 함께 다룬다.
   의무를 특정 외부 스킬의 설치 여부에 의존시키거나 매 cycle 승인·원장을 만들지 않는다.

7. `guidance/execution-blocks.md`의 동시 갱신 표와 `change-walkthrough.md`는 계약 변화와
   경로·증명 변화의 수정 대상을 구별한다. 연결된 설계 정본을 논의 메모로 대신하지 않으며,
   아직 존재하지 않는 현재 커밋 SHA를 발명하지 않고 `Current change`로 동시 개정을 연결한다.
   영향 없는 문서까지 형식적으로 고치라는 요구는 없다.

**범위와 한계**

실행 계획·추가 사용자 조건·북극성 발췌, 후보 README·두 양식·세 스킬·두 지침·정책/전달안·
변경 walkthrough, 네 예시의 intent/context/spec/plan 및 M01 설계 정본 세 파일을 읽었다.
필요한 고정 cases·데이터/코드/시험 참조, F03 역사 계약·계획, M01 합성 입력과 기존 플러그인
설치 안내를 대조했다. F03 역사 자료는 계약의 고정 입력으로만 사용했다. 제안 폴더·다른 리뷰어
출력·과거 모델 리뷰 결론은 읽지 않았다.

파일 및 Git의 읽기 전용 조회로 대상 HEAD와 후보를 확인했다. 전용 Read 도구가 없어 조회에는
읽기 전용 셸 명령을 사용했다. 제품 시험·이행 도구·설치 명령 실행, 다이어그램 렌더링 및 새 세션
인계 실험은 이 리뷰에서 하지 않았다. M01은 실제 제품 코드가 없는 가상 배치이며, 제공되지 않은
기존 오류 본문·운영 명령과 예정 시험의 성공을 확인한 것으로 해석하면 안 된다.
