# 실제 모범 문서에 비춰 본 spec·plan 전면 재검토

2026-09-11 · 검토 기준 `c09b5f1` · **판정: 기존 계약 설계는 보존하고, 양식과 대표 예시의 구성은 다시 다듬는다.**

아래는 보완 전 후보에 대한 재검토 기록이다. 이후 사용자 요청에 따른 후보 수정은
[보완 결과·리뷰·인계 기록](implementation/README.md)에 이어서 보존했다. 평가 당시의 진술을 현행 후보의 결함 목록으로 읽지 않는다.

사용자가 제공한 [실제 설계·계획 문서 조사](../../exemplary-design-and-plans/README.md)를 바탕으로 활성 양식과
[이전 설계 후보](../spec-plan-design/candidate/README.md)를 다시 평가했다. 북극성의 최우선 목표는 사람이 중요한 결정을 검토하고,
대화를 보지 않은 엔지니어·에이전트가 문서와 선언된 정본으로 구현을 이어가는 것이다. 문서의 길이·표·그림 수가 목표는 아니다.

**기존 후보에는 상세 설계가 있다. 그러나 그 상세를 읽고 작성하게 하는 양식은 아직 고르지 않다.**
정확한 계약을 표로 나열하는 데 비해, 왜 이 구조를 골랐고 요청이 어떻게 흐르며 무엇부터 구현하는지 설명하는 연결이 약하다.
좋은 예시가 빈 양식의 기본 표를 벗어나 산문·도식으로 작성된 점도 이 불균형을 보여준다.
이전 PASS의 계약·일관성 확인은 유효하지만, 그것만으로 실제 작성 품질과 독립 구현 능력까지 입증됐다고 볼 수 없다.

이번 산출물은 재검토와 구체적인 재구성 제안이다. 기존 후보와 활성 파일·설치 환경·북극성 주석은 보존했다.

## 우선 고칠 다섯 가지

| 순서 | 판단과 근거 | 보완 방향 |
|---|---|---|
| 1 | **함께 쓰는 지침이 충돌한다.** 후보는 다중 설계 정본을 허용하지만 팀 spec-policy-pass는 여전히 한 파일을 강제한다. 후보 전달안에도 그 문장을 바꾸는 항목이 없다. | 양식·작성 스킬·정책 검토 스킬의 역할을 맞춘다. 정책 스킬은 실제 정책 적용/충돌을 검토하고 파일 수·우려 최소 개수·표 사용을 강제하지 않는다. |
| 2 | **spec의 기본 작성 모양을 바꿔야 한다.** 만능 Design 표로는 현재 문제→제약→선택→흐름→정확한 계약을 자연스럽게 설명하기 어렵다. M01의 대안 비교는 이전 예시보다 오히려 약해졌다. | 설명과 대표 흐름을 중심으로 쓰고 인터페이스/필드/판정 표를 필요한 자리에 둔다. 여섯 정보 역할은 유지한다. |
| 3 | **plan은 한 작업의 실행 정보를 모아야 한다.** 파일·순서·명령·기대가 여러 표와 문단에 흩어진다. M01 같은 계획을 위임할수록 재조립 비용이 커진다. | PR 인도 지도 아래 작업별 목적·필수 설계·파일·선행 시험·최소 변경·완료 관측을 가깝게 배치한다. Proof는 전체 검증과 참조 색인으로 유지한다. |
| 4 | **정본을 찾는 경로와 설명용 맥락을 다듬어야 한다.** M01 기존 API 계약은 context에서 과거 합성 context로 한 번 더 이동해야 한다. 연구 출처·상태 안내와 제품 설명도 섞여 있다. | 필수 현재 계약과 보존용 이력을 구별해 직접 연결한다. spec 상단에서 현재/목표와 읽기 순서를 알리고, 합성·미확인 표시는 짧게 유지한다. 없는 관측을 발명하지 않는다. |
| 5 | **완성 예시의 유형이 부족하다.** 작은 CLI 세 건과 저장소 이행은 강하지만, UI·API를 잇는 사용 흐름 예시가 없다. design-blocks의 UI 예시 칸은 실제 예시 대신 안내다. | 작고 완성된 사내 웹 기능 spec→plan 한 쌍을 보강한다. 정상·빈 결과·로딩·실패·권한 중 해당하는 상태와 PR별 공개 상태, 실제 사용 흐름 검증을 보여준다. |

1은 확인된 소스 지침 충돌이고, 2–5는 문서의 작성·소비 품질을 개선할 설계 판단이다.
후자의 효과는 새 문서 작성/인계/구현 실험에서 확인해야 한다. 현재 설치된 Claude 플러그인이 어떤 판을 실제 로드하는지는 이번에 확인하지 않았다.

## 권장하는 재구성

spec은 먼저 변경의 맥락을 이해시키고 중요한 설계를 찾아 읽는 문서로 만든다. plan은 그 설계를 어떤 PR과 작업으로 제품에 넣을지
따라 읽는 문서로 만든다. 그 차이를 보이는 [구조 제안과 M01/F03 작성 예](structure-proposal.md)를 별도로 작성했다.
단순히 “더 구체적으로 쓰라”는 문장을 늘리는 대신, 실제 완성 예시를 먼저 다듬고 거기서 빈 양식과 작성 스킬을 도출한다.

| 정보 | 정본 역할 |
|---|---|
| 의도·원하는 변화·성공의 의미·원래 제약 | intent |
| 요구·관찰 가능한 판정·구조/동작/데이터/중요 인터페이스·선택 근거 | spec 및 연결된 설계 문서 |
| 실제 코드/테스트 경로·작업 순서·PR·병렬/통합·첫 시험·검증·운영 실행 | plan 및 필요한 실행 참조 |
| 모든 새/변경 동작을 시험 먼저 개발한다는 의무 | 얇은 팀 정책 |
| RED→최소 GREEN→필요한 REFACTOR, 시험 품질·예외/이탈 처리 | 설치 가능한 자체 TDD 스킬 |
| 실제 사용한 판·실패 이유·실행 출력·사람 결정 | 기존 PR/실행/결정 기록 |

spec.md는 계속 진입점이다. 파일 분리는 독자·결정 소유·갱신 범위에 맞춰 선택한다.
필수 정본을 함께 읽으면 되며, 모든 내용을 한 파일로 합치거나 모든 상세 파일에 같은 여섯 절을 반복하지 않는다.

## 유지할 것과 늘리지 않을 것

F01/B01의 짧지만 정확한 계약, M01의 스키마·원자성·복구, F03의 단계별 공개/cleanup 의미를 유지한다.
GitHub Flow·작고 응집된 PR·배포 가능한 main·개발 시험과 일반 공개의 구분도 그대로다.
설계가 바뀌면 영향받는 spec 정본과 plan을 관련 구현 커밋에서 갱신한다는 원칙 역시 유지한다.

모든 클래스 다이어그램, 모든 내부 함수, 분량 하한, 새로운 상태 원장·문서 의미 검사기를 추가하지 않는다.
도식은 질문에 답할 때 사용한다. 예를 들어 M01의 경합 시퀀스는 중요한 순서를 설명한다.
반면 Request가 dict임을 밝힌 클래스 그림은 논리 데이터형 설명으로 가능하지만 필수는 아니며, 더 읽기 쉬우면 인터페이스 표로 바꿀 수 있다.

모든 결정을 수치화하지 않는다. 팀의 운영 역량·기존 자산·중지 허용·고장 영향 같은 정성적 조건도 중요한 선택 근거다.
필요한 정확한 계약은 계속 구체적으로 쓰고, 근거 없는 성능 수치나 확인되지 않은 현재 동작을 만들어 넣지 않는다.

## 후속 작업과 검증

첫 보완은 함께 로드되는 정책 스킬의 충돌 범위를 전달안에 포함시키는 일이다. 다음에는 M01의 설명/정본 경로와 F03의 작업 배치를
다듬고, 작은 사내 웹 기능 완성본을 작성한다. 그 완성본에서 공통 양식·상황별 블록·작성 스킬을 도출한다.
이렇게 하면 추상적인 작성 규칙만 덧붙이는 일을 줄일 수 있다.

검증은 질문 수나 파일 목록의 일치율 하나로 통과를 판정하지 않는다. 새 세션이 중요한 계약을 추측하지 않고, 첫 시험의 실패를
예상한 이유로 확인하며, 실제 구현/통합/공개 상태를 증명하고, 발견된 변경을 올바른 정본에 갱신하는지 본다.
필요한 질문과 누락 때문에 되묻는 질문을 구별한다. 실제 코드에 맞춰 파일 경로가 바뀌고 계획도 갱신됐다면 정당한 개선일 수 있다.

프로세스 실험은 기존 합의대로 교육·템플릿 제작 자료를 제외한 사용 기준 브랜치에서 파생한 실험 브랜치에 남긴다.
root가 사람 역할을, Claude Code가 개발 역할을 맡아 실제 응답을 읽고 후속 질문/변경을 제시한다.
고정 대사를 강제하지 않고 같은 개발건·페르소나·입력 조건을 재사용한다. 결과에는 첫 시도와 보완 후를 구분한다.

실제 구현 검증은 작은 기능 한 건부터 시작한다. 이후 공개 상태가 바뀌는 F03형 변경과 병렬 계약 변경은 각각 필요한 때 추가한다.
매번 모든 북극성 문장을 다시 채점하지 않는다. 고정 안내는 변경 시 검토하고, 동작이 바뀐 범위와 기존 회귀 집합을 함께 확인한다.
대화 후 동작·TDD·정본 갱신이 대체로 안정적이면 그 관측 범위를 기준으로 판단한다. 모든 에이전트 실수를 없애려 하지 않는다.
실제 사용판 검증을 통과한 범위만 북극성 주석에 반영한다.
