# 검토 의견 처리와 이번 검증 범위

2026-09-11. 최종 판단은 root가 원문·현재 후보·반대 근거를 대조해 내렸다.
모델의 찬성 수를 통과 기준으로 삼지 않았으며, 초안 리뷰의 과장도 원본과 정정을 함께 보존했다.

## Decisions

| 의견 | 처리 | 근거/범위 |
|---|---|---|
| 정책 스킬의 한 파일 강제와 우려 유도 | **최우선 수정 대상으로 채택** | 사용자 다문서 조건·후보 design-spec과 org-skills spec-policy-pass §2–4가 충돌. 전달안에도 해결 작업 누락. 실제 설치 상태가 아니라 저장소 소스 판정 |
| Design 표를 설명·흐름 중심으로 재구성 | **채택** | 세 독립 검토와 root 비교에서 공통. 후보의 완성 예시도 대다수 산문 사용. 작은 F01 표는 유효하며 표 금지는 아님 |
| 한 작업의 파일/첫 실패/구현/완료를 가까이 배치 | **채택** | P3 Task의 전달 방식과 비교. M01 기존 내용 부재가 아니라 배치 문제. 작업 블록 도입에 고정 작업 수 문턱은 두지 않음 |
| M01 선택 논증·현재→목표 설명 개선 | **채택** | 후보의 JSON 잠금 기각 이유가 두 대안의 실제 차이를 충분히 설명하지 못함. 이전 활성 예시의 내구성/오류 정리/단일 writer 비용 설명을 되살림 |
| M01 기존 계약을 직접 찾는 읽기 경로 | **채택** | context→과거 합성 context의 우회. 사실·현재 계약·참고 이력의 역할을 구별. 미제공 오류 바이트를 발명하지 않음 |
| 사내 UI/API 완성 예시 | **채택** | UI 조건부 안내에 실제 예시가 없음. TDD/공개/사용자 흐름을 함께 보여줄 작은 사례를 우선, 대형 서비스 구축은 불필요 |
| 질적 유지/운영 비용의 설명 | **채택** | Django/P2의 선택 근거와 기존 M01 조건. 모든 비용을 새 숫자·AC로 만들지 않음 |
| 클래스 그림 제거 | **필수 수정으로는 기각** | Request는 dict라는 설명이 이미 있어 논리 데이터형으로 사용 가능. 그림이 읽기에 도움이 되는지에 따라 표로 바꾸는 선택은 허용 |
| F03의 PR 번호와 설계 상태 분리 | **낮은 우선 개선으로 채택** | 상태 의미는 spec, PR 대응은 plan에 두면 분할 변경 시 불필요한 결합 감소. 현재 그림의 교육적 가치는 인정 |
| 실제 대안이 있으면 항상 별도 문단 필수 | **완화** | 중요한 선택에는 이유·감수할 점 필요. 짧은 문장/표로 충분하면 별도 의식·목차 강제 없음 |
| 현재 동작/재현 근거가 전혀 없다 | **기각·리뷰어 철회** | F01/F03 plan의 예상 rc2, B01 재현 rc1, intent/context의 기준. 진입점의 직접 설명은 사용성 개선일 뿐 결손 사실과 다름 |
| 안내 삭제 규칙이 없다 | **기각·리뷰어 철회** | 후보 spec 마지막 문장에 명시. 주석은 렌더링에서 숨겨질 뿐 에이전트도 읽음; HTML 주석화는 자동 개선 아님 |
| Decision/Reviewers 필수 필드 | **기각·리뷰어 철회** | docs/GIT-WORKFLOW의 기존 문서/SHA/결정자/이유 기록과 중복. 필요하면 그 정본을 링크 |
| 기존 인계 실험이 한 번도 없다 | **기각·범위 정정** | Sonnet 읽기 전용 실제 점검·실패·후속 복구 기록이 존재. 실제 제품 구현/TDD는 미검증 |
| L4만 유일한 합격 기준, 질문/경로 불일치로 실패 판정 | **기각·리뷰어 철회** | 정책·우려·검증·인간 판단도 중요. 정당한 질문/발견/경로 변경은 개선일 수 있음 |
| 긴 P3 코드가 계획 실패를 입증, 내부 서비스는 스키마/응답 전문 불필요 | **기각·리뷰어 완화** | 단계 의존 코드가 유지 비용을 보일 뿐 실패 증거 아님. M01/F03처럼 정확한 계약이 필요한 반례 존재 |
| 양식 행 수 증가 자체가 품질 저하 | **기각·리뷰어 철회** | 작성 시간·재질문·실제 누락·갱신 비용을 봐야 함. 길이는 비용 단서이지 결론 아님 |

Opus의 [첫 리뷰](reviews/opus-r1.md)와 [후속 정정](reviews/opus-r2-addendum.md)을 함께 읽는다.
후속은 동일 세션에서 반대 근거를 읽고 정정한 결과이며 새로운 독립 리뷰 1건으로 세지 않는다.

## 범위를 구분한 결과

| 범위 | 판정 |
|---|---|
| 제공된 실제 문서와 후보의 구조/상세 비교 | 완료. 문서별 직접 읽은 범위는 각 검토의 Read scope 참조 |
| 기존 소스 지침의 모순 | 확인. 후보 활성화 계획에 spec-policy-pass 정합화 누락 |
| 구조 재구성안과 M01/F03 표현 예 | 작성. 기존 후보 계약을 대체·수락한 새 제품 spec은 아님 |
| 현재 repo의 기존 회귀 | make check rc0. 아래 출력 참조 |
| 새 양식/스킬 활성화·설치 | 이번 범위에서 미실행 |
| 새 후보로 실제 코드 구현/TDD·배포/공개·병렬 통합 | 이번 범위에서 미실행. 후속 사용 기준/파생 브랜치 실험 대상 |
| 북극성 주석 등급 | 변경하지 않음. 문서 리뷰만으로 행동 실험의 통과를 대신하지 않음 |

기존 `make check` 출력은 [원문 로그](validation/make-check.txt)에 보존했다:

```text
Ran 96 tests in 30.681s
OK (skipped=1)
test_hooks: 28 passed, 0 failed
8 passed, 0 failed
PASS  managed-settings 키·훅 계약
```

이는 현재 템플릿 저장소의 기존 테스트 결과다. 의미 기반 live eval이나 이 재구성안의 제품 구현 성공을 뜻하지 않는다.
이번 문서 검토 때문에 새 테스트·checker를 작성하지 않았다. 검토 산출물의 로컬 링크·입력 파일 해시·Git 변화는
[최종 파일 확인](validation/file-check.json)에서 별도로 확인한다.

## 모델과 공개 기록

- Astra/ultra: D1/D2 및 SPEC 구조 독립 판단. 높은 설계 난도에 맞춘 배정.
- Sol/high: D3/D4와 M01의 범위 한정 사실 대조. 새 설계 전체를 중복 작성하지 않음.
- Claude Code 2.1.265, `--model opus --effort high`: 독립 교차 검토 후 같은 세션에 정정 요청.
  응답 메타데이터의 실제 주 모델은 `claude-opus-5`. 최대 추론으로 호출하지 않았다.
- root: P1/P2/P3 및 활성/후보 비교, 반대 근거 확인, 발견 처리와 재구성안 작성.

Claude는 safe mode에서 Read만 허용했다. 이는 문서 비교를 위한 호출로, 설치된 팀 스킬의 자동 적용 실험이 아니다.
기록: [첫 호출 메타데이터](reviews/opus-r1-metadata.json), [후속 메타데이터](reviews/opus-r2-metadata.json),
[공개 프롬프트·Read 호출 목록](reviews/opus-read-trace.json). 43회 Read 호출과 오류 없음이 기록되어 있다.
도구 결과 본문은 내용 해시가 있는 입력 파일을 참조하며, 비공개 추론은 보존하지 않았다.

Claude 두 호출이 보고한 비용 합계는 **$3.046907**다. 첫 호출의 내부 보조 모델 비용이 포함되어 있으며,
Codex/Astra/Sol 비용이나 청구서 실측 총액은 아니다.
이번 새 연구 파일은 작업 트리에 보존했다. 사용자가 제공한 원문 폴더도 원래 작업 트리 상태로 유지한다.
