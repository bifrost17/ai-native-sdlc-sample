## 1. 수락 판·Upstream 표현 정정

394651e를 "직전 수락 판"이라고 쓴 것은 발명이었다. 확인 가능한 사실은 이것뿐이다:

- spec.md:2 `Status: draft`, spec.md:4 `Skills applied: none`, spec.md:8 "실제 제품 승인/실행은 아니며"
- context.md:61 "사용자는 2026-09-11 재검토대로 설계 패키지를 보완하도록 허가했다" → **작성/보완 허가**이지 단계 수락이 아니다
- GIT-WORKFLOW.md:19가 요구하는 수락 기록(대상 문서·커밋 SHA·결정자·결정과 이유)은 W01에 존재하지 않는다

그래서 394651e는 이 합성 예시의 **제작 입력 판**으로만 부르고, 사후에 "수락됨"으로 승격시키지 않는다.

**plan Upstream에 쓸 값**: PR-A 머지 SHA가 아니다. 머지 커밋은 제품 코드 통합 사실이고, Upstream은 "어느 spec 판을 근거로 이 계획을 썼는지"를 가리킨다. 둘을 섞으면 근거 추적이 끊긴다. 실제로 써야 할 것은 **이번 작업에서 읽고 사용한 spec.md 판**이며, 인계 프롬프트가 준 후보 판은 2d3f2dc다. 다만 파일 단위로 spec.md를 마지막에 바꾼 커밋이 2d3f2dc인지는 `git log -1 -- docs/.../examples/W01/spec.md`로 확인해야 하고, 나는 이 세션에서 실행하지 않았으므로 확인 필요 항목으로 남긴다. plan 스킬이 허용하는 표기는 "실제 판 + draft + 허가 한계"이므로:

```
Upstream: spec.md@<확인한 실제 SHA> — 실제 사용한 판. 사람 수락 기록 없음(context.md의 작성/보완 허가 범위). Status: draft.
Current change: 이 커밋의 spec.md 개정(수동 새로고침 요구/AC/UI states)과 함께 읽는다. 변경 이유: PR-A 머지 후 직원 후속 요청; 결정 기록: <PR/결정 기록 위치>.
```

PR-A 머지 SHA는 Upstream이 아니라 Delivery map/PR 기록의 "선행 통합 사실"로 따로 적는다.

- **새로고침 요구의 오너 수락**: 없음. Q2 원답은 브라우저 새로고침으로 충분하다고 했으므로 범위가 달라졌다. 근거·영향(없으면 공개 전 AC 확인의 근거가 빈다)·담당(포털 업무 오너)·필요 시점(공개 결정 전)을 Flagged concerns에 적고, 지금 "수락됨"으로 쓰지 않는다. 설계를 무효화하지 않는 추가 요구이므로 B1 구현은 막지 않는다
- **제품 수락/실행**: 없음. spec/plan 모두 `Status: draft` 유지
- **spec.md를 마지막에 바꾼 실제 SHA**: `git log`로 확인해야 하며 이번 세션에서 실행하지 않았다

파일 수정·실행·커밋은 하지 않았고, 위 내용은 이 가정 상황에 대한 인계 설명이다.
