## 중요한 발견

### R1 — 공개 전에 cleanup AC까지 요구하는 문장

**근거:** `examples/W01/spec.md:134`의 Release and disable은 포털 오너가 “완성 코드의 전체 AC”를
확인해 공개하도록 정한다. 그러나 같은 파일 `:33`의 AC8은 공개 후 제어를 제거한 판의 수락 기준이고,
`:136–137`의 cleanup은 공개 후 안정화/되돌림 관측·구버전 의존 해소와 오너 요청 뒤에만 수행한다.

**충돌과 영향:** 전체 AC를 문면 그대로 적용하면 공개 전에 AC8을 충족해야 하지만, AC8을 충족하는
cleanup은 공개 이후에만 가능하다. 공개 단위와 단계별 증명을 가르치는 예시에서 오너의 공개 판단 기준이
순환하고, 올바른 plan 실행 결과를 어느 AC 집합으로 판정할지 독자가 다시 정해야 한다.

**이미 있는 반대 근거:** W01 plan의 Delivery map(`:28–33`)과 Release/cleanup(`:95–106`)은
구현→공개 리허설/결정→조건 충족 후 cleanup의 올바른 순서를 제공한다. spec AC7도 API만 준비한 상태를
전체 공개 근거로 인정하지 않는다(`:32`). 따라서 공개 설계 전체가 빠졌거나 구현 순서가 잘못됐다는 발견은 아니다.
F03은 이미 공개 전 AC1–6와 cleanup AC7을 정확히 분리한다(`examples/F03/spec.md:59–67`).

**최소 수정:** W01 spec `:134`를 “공개 전 AC1–7과 OFF 복귀 근거를 확인한다. AC7은 같은 완성 판의
격리 사본 리허설로 확인하고, AC8은 공개 후 cleanup 판에서 검증한다”는 범위로 한정한다.
새 AC·gate·문서·시험 도구를 만들 필요는 없다.
