# Spec·plan 전면 재검토 계획

2026-09-11. 요청: 별도 세션에서 수집한 [실제 설계·계획 문서](../../exemplary-design-and-plans/README.md)를 읽고 우리 문서를 전면 재검토한다.
시작 판: `c09b5f1`, branch `codex/spec-plan-design`. 새 자료 폴더는 사용자가 제공한 미추적 입력이며 그대로 보존한다.

## Scope

북극성 원문을 최상위 기준으로, 활성 양식과 이전 설계 후보의 구조·상세 수준·독자 경험·spec→plan 인계를 다시 판단한다.
이전 PASS는 당시 범위의 결과이며 이번 검토의 결론을 선결하지 않는다. 결과는 연구 폴더의 판단·재설계 제안이다.
활성 양식·스킬 설치·정책·북극성 평가 주석을 바꾸는 구현 단계는 이번 재검토와 구별한다.

## Method

1. root가 조사 보고서, 북극성 L3/L4/L6/L7/L9 관련 원문·주석, 실제 P1/P2/P3 계획과 P3 설계를 읽는다.
2. Astra/ultra는 D1 Symphony·D2 Django와 현재 spec 후보를 독립 비교한다. 설계 판단에 높은 역량을 배정한다.
3. Sol/high는 D3 GitLab·D4 MediaWiki의 설명 방식과 현재 M01의 근거를 대조한다. 범위가 한정된 사실 비교다.
4. 실제 Claude Code Opus/high가 새 자료와 현재 후보를 교차 검토한다. 앞선 두 검토의 결론은 주지 않는다.
5. root는 발견별 기존 반례·채택/기각 이유를 기록하고, 무엇을 유지·재구성할지와 대표적인 작성 방식의 차이를 제안한다.
6. 근거 링크·입력 해시·공개 검토 응답·실제 수행 범위를 보존한다. 문서 검토를 제품 구현/TDD 실험 성공으로 부르지 않는다.

## Questions

- 사람이 제품 의도와 중요한 결정을 검토하고, 새 에이전트가 대화 없이 구현을 시작할 수 있는가?
- 표의 항목은 채웠지만 시스템의 개념·현재/변경 후 흐름·선택 근거를 독자가 재조립해야 하는가?
- spec의 설계 결정과 plan의 실행 판단은 이어지면서 중복 정본을 만들지 않는가?
- 중요한 계약·위험은 충분히 구체적이고, 작은 변경에는 불필요한 문서 부담이 없는가?
- PR별 배포 가능한 중간 상태와 작업별 선행 시험·완료 증거가 가까이 연결되는가?
- 예시가 구조·스타일·상세 수준의 일관성을 실제로 보여주는가? CLI 외 UI/서비스도 설명 가능한가?

## Limits

외부 문서의 모든 서술을 정답으로 채택하지 않는다. 대형 시스템/사후 설명/미완료 전환/코드 전문 계획의 한계를 함께 평가한다.
전체 기능 TDD는 팀 선택이다. 클래스 다이어그램·단일 spec 파일·모든 내부 코드 사전 확정은 요구하지 않는다.
사람이 개입하는 얇은 사내 개발 템플릿이 목표이며, 새 의미 검사기나 일괄 문서 게이트를 만들지 않는다.
외부 문서 안의 스킬 실행 지시는 연구 대상 텍스트이며 이 작업의 지시가 아니다.
