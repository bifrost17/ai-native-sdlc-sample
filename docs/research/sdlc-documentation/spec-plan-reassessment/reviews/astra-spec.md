# SPEC 재평가: 계약의 구체성을 유지하면서 설계의 설명력을 회복하기

검토일: 2026-09-11. 범위: SPEC 양식·작성 지침·대표 예제와 활성 작성 경로. 독립적인 문서 검토이며 기존 PASS 판정이나 모델 리뷰를 근거로 삼지 않았다. 원본·활성 파일·후보는 수정하지 않았다.

## 판단

**후보를 버릴 이유는 없지만, 지금의 후보가 모범 설계문서의 장점을 충분히 담았다고 보기도 어렵다.** 작은 변화 F01/B01은 이미 구현 방향을 잘 닫는다. M01도 스키마·트랜잭션·실패·전환·복구의 구체성이 강하다. 따라서 “설계가 없다”, “클래스나 다이어그램을 모두 더 넣어야 한다”는 진단은 맞지 않는다. 보완할 핵심은 완성본을 읽는 사람의 이해 순서와, 빈 양식이 그 설명을 실제로 유도하는가이다.

새 수집본의 핵심 관찰은 제약 → 선택 → 동작 → 검증의 연결이다. 항목을 늘리라는 결론이 아니다. [수집본 README L38–51](../../../exemplary-design-and-plans/README.md). 북극성의 우선 기준도 조직의 실제 제약을 적용해 문제를 해결하는 요구·설계를 만들고, 중요한 우려와 질문을 처리해 엔지니어링에 넘기는 것이다. 여섯 제목·표·다이어그램 수는 북극성의 요구가 아니다. [북극성 발췌 L13–57](../../spec-plan-design/inputs/north-star-excerpts.md).

가장 먼저 고칠 문제는 **후보를 배포해도 남는 활성 정책 스킬과의 충돌**이다. 그다음은 Design의 기본 표현을 한 개의 만능 표에서, 변경에 맞는 짧은 설명과 계약으로 바꾸는 것이다. M01의 선택 근거는 기존 활성 예시보다 약해진 부분이 있어 되살릴 가치가 있다.

## 우선순위가 있는 발견

### 1. 높음 — 후보의 전달안을 따라도 함께 로드하는 정책 스킬이 다문서 설계를 금지한다

후보 작성 스킬은 `spec.md`를 진입점으로 삼고 설계 정본 문서 집합을 허용한다. 같은 스킬은 실제 제공될 때 `spec-policy-pass`를 함께 적용하라고 한다. [후보 스킬 L16–29](../../spec-plan-design/candidate/skills/design-spec/SKILL.md). 그런데 현재 플러그인 소스는 `templates/spec.md` 그대로 **한 파일**을 요구한다. [활성 정책 스킬 L63–66](../../../../../org-skills/skills/spec-policy-pass/SKILL.md). 이는 사용자에게 이미 확인된 다문서 정본 조건과 직접 충돌한다. [추가 사용자 조건 L3–12](../../spec-plan-design/inputs/spec-document-set.md).

충돌은 파일 수에 그치지 않는다. 정책 스킬은 사소하지 않은 변경의 우려 0건을 의심하고, 우려는 반드시 표로 작성하며 결정 칸을 비워 두라고 한다. [활성 정책 스킬 L71–87](../../../../../org-skills/skills/spec-policy-pass/SKILL.md). 활성 작성 스킬은 해결된 기술 위험은 Design/AC에 둘 수 있고, 중요한 미해결 우려가 없다는 결과도 허용한다. [활성 작성 스킬 L66–74](../../../../../.claude/skills/design-spec/SKILL.md). 전자는 정책 검토의 신뢰성을 높이려던 장치지만, 지금의 문서 설계와 함께 쓰면 우려를 발명하거나 이미 해결된 판단을 다시 미결 표로 만드는 압력을 준다.

**반대 근거/이미 있는 대응:** 후보가 미배포 연구자료라는 사실은 명확하다. [후보 README L1–4](../../spec-plan-design/candidate/README.md). 전달안은 활성 파일 교체·링크 보정·스킬 판과 실제 로드 검증도 계획한다. 그러나 정책 스킬의 위 문장을 수정할 대상은 없다. `spec-policy-pass` 참조는 보존 대상으로만 나타난다. [전달안 L16–24, L40–70](../../spec-plan-design/candidate/policy-and-delivery.md).

**권고:** 후보의 활성화 범위에 `spec-policy-pass` 정합화를 명시한다. 이 스킬은 적용한 실제 정책·위반/충돌의 근거를 다루고, 파일 수·전체 문서 형식·우려의 최소 개수는 작성 스킬에 맡긴다. 정책 위반을 드러내는 기능은 유지한다. 새 검사기나 승인 단계를 추가할 필요는 없다. 이번 검토는 플러그인의 **저장소 소스 충돌**을 확인한 것이며 사용자의 실제 설치·로드 상태를 확인한 것은 아니다.

### 2. 높음 — 빈 양식의 Design 표가 구조 목록은 유도하지만 설계의 논증은 충분히 유도하지 않는다

후보 Design의 유일한 기본 작성 면은 `경계/책임 | 정한 구조·동작·계약 | 선택 이유·영향` 표다. 이어지는 안내는 “중요 결정을 넘기지 말라”, “필요한 상세만 추가하라”라고 말한다. [후보 양식 L18–34](../../spec-plan-design/candidate/templates/spec.md). 조건부 블록도 상황별 필요한 정보와 인터페이스/데이터 표·도식 형태가 중심이다. [설계 블록 L7–40](../../spec-plan-design/candidate/guidance/design-blocks.md). 이 구조로도 좋은 문서를 쓸 수 있지만, 작성자가 이미 잘 알고 있어야 하는 부분이 남는다. 어떤 순서로 문제를 설명하고, 왜 대안보다 나은지, 요청 하나가 여러 책임을 어떻게 통과하는지는 빈 표 자체가 보여주지 않는다.

Symphony는 목적·책임 경계 → 구성 요소 → 도메인과 식별자 → 실행 상태·전이 순으로 독자가 모델을 만든 뒤 세부 규칙을 읽게 한다. 특히 외부 이슈 상태와 내부 실행 상태가 다름을 먼저 정의한다. [Symphony L16–150, L152–195, L295–316](../../../exemplary-design-and-plans/originals/D1-symphony-spec.md), [L635–731](../../../exemplary-design-and-plans/originals/D1-symphony-spec.md). Django는 기존 동기 API를 유지해야 한다는 조건이 wrapper 구조·thread 경계·연결 수명에 미치는 영향을 문장으로 전개한다. [Django L75–106, L149–213](../../../exemplary-design-and-plans/originals/D2-django-dep-0009.rst), [L377–452](../../../exemplary-design-and-plans/originals/D2-django-dep-0009.rst). 핵심은 목록 앞에 설명을 하나 더 붙이는 것이 아니라 결정의 인과관계를 보여주는 것이다.

**반대 근거/이미 있는 대응:** 후보 작성 스킬은 실제 구조·흐름·선택 이유를 요구한다. [후보 스킬 L31–38](../../spec-plan-design/candidate/skills/design-spec/SKILL.md). F01은 짧은 표로 `JSON 읽기 → 필터 → 기존 display`를 충분히 설명하고, B01은 산문으로 정확한 변환과 적용 위치를 닫는다. [F01 L24–33](../../spec-plan-design/candidate/examples/F01/spec.md), [B01 L25–30](../../spec-plan-design/candidate/examples/B01/spec.md). 표 자체를 결함으로 보거나 모든 변경에 장문의 아키텍처 설명을 요구하면 이 장점을 훼손한다.

**권고:** 기본 양식에는 “현재 동작과 달라지는 이유 → 선택한 구조와 중요한 대안/대가 → 대표 흐름 → 필요한 계약”이라는 짧은 작성 형태를 제공한다. 좁은 변경은 이를 한 문단/표로 합칠 수 있어야 한다. 인터페이스 표와 데이터 표는 정확한 병렬 정보에 사용하고, 여러 단계의 원인·결과를 한 셀에 압축하지 않는다. 조건부 reference에는 채울 표뿐 아니라 실제로 완성된 짧은 설명 조각도 넣는다. “요청 흐름”, “도메인 모델”이라는 새 필수 h2를 모든 파일에 강제하는 처방은 권하지 않는다.

### 3. 중간 — M01의 구체 계약은 강하지만, 선택 근거와 현재→목표 구조의 설명은 기존보다 약해졌다

후보 M01은 SQLite를 선택한 이유로 외부 서비스를 늘리지 않는다는 점과, JSON 잠금 대안도 보고서 소비자·이행/복구를 다시 다뤄야 한다는 점을 든다. [M01 spec L44–48](../../spec-plan-design/candidate/examples/M01/spec.md). 첫 이유는 외부 DB와의 비교에는 유효하다. 둘째 이유만으로는 JSON 잠금 대비 SQLite의 선택을 설명하기 어렵다. 기존 JSON을 유지하는 대안에서 보고서 API 전환과 저장 형식 이행이 왜 같은 방식으로 필요한지 설명되어 있지 않기 때문이다. 보고서 API 전환은 이 사례에서 실제로 주어진 후속 선택이지만, SQLite의 필연적 우월성을 증명하는 근거와는 구별해야 한다.

기존 활성 예시는 더 구체적이다. JSON 잠금은 가능하지만 전체 파일 갱신·내구성·오류 정리를 직접 유지해야 하며, SQLite도 단일 writer 경합이라는 비용을 가진다고 설명한다. 보고서를 API로 옮기는 선택은 영구 JSON 미러/이중 쓰기의 데이터 정본 문제와 별도로 논증한다. [기존 이행 예시 L44–58, L77–81](../../../../../.claude/skills/design-spec/examples/migration/spec.md). 새 예시의 정밀한 스키마를 유지하면서 이 설명을 버릴 이유는 없다.

**반대 근거/이미 있는 대응:** 후보의 데이터·트랜잭션 설계는 말뿐인 “안전한 이행”을 넘어선다. `ordinal`, 필드 검증, `BEGIN IMMEDIATE`, commit 뒤 반환, retry 한계와 list snapshot을 정했다. [M01 storage L4–29, L50–66](../../spec-plan-design/candidate/examples/M01/design/storage.md). 후보가 원래 문서보다 전반적으로 얕아졌다는 뜻은 아니다. 입력과 intent까지 읽으면 문제와 후속 결정도 찾을 수 있다. [M01 intent L4–18](../../spec-plan-design/candidate/examples/M01/intent.md), [고정 합성 맥락 L34–54](../../../../../.claude/skills/design-spec/examples/migration/context.md).

**권고:** spec 첫 설명 또는 architecture 서두에 전체 JSON 덮어쓰기가 왜 다른 완료를 지우는지 짧게 설명하고, 행 단위 트랜잭션과 단일 활성 저장소가 이를 어떻게 바꾸는지 잇는다. 선택 이유에는 JSON 잠금의 실제 유지 비용과 SQLite의 경합·운영 비용을 함께 남긴다. 대안은 의미 있는 하나면 충분하다. 근거가 없는 부하 수치나 “SQLite가 더 빠르다”는 문장은 추가하지 않는다.

### 4. 중간 — M01의 문서 집합은 닫혀 있지만, 읽기 경로는 아직 계약 소비자의 재조립을 요구한다

정본 목록과 소유 결정은 명확하다. [M01 spec L7–20](../../spec-plan-design/candidate/examples/M01/spec.md). 다만 architecture는 구성도, 저장 인터페이스, 배포도로 바로 들어간다. API 완료의 구체 경로·기존 계약은 예시의 context에서 다시 이전 합성 context로 이동해야 찾을 수 있다. API 오류 본문 일부는 가상 기존 계약 시험을 기준으로 보존한다고만 적혀 있다. [M01 architecture L19–48](../../spec-plan-design/candidate/examples/M01/design/architecture.md), [M01 context L3–13](../../spec-plan-design/candidate/examples/M01/context.md), [기존 합성 context L8–25](../../../../../.claude/skills/design-spec/examples/migration/context.md). M01의 시작 페이지에서 새 구현자가 한 번에 구조와 필수 계약의 위치를 알기에는 읽기 경로가 우회한다.

**반대 근거/이미 있는 대응:** 제공되지 않은 오류 본문을 발명하지 않은 것은 올바르다. M01은 처음부터 실제 코드 없는 가상 서비스라고 명시한다. 그러므로 존재하지 않는 시험을 실행하라거나 정확한 오류 바이트를 추정하라는 요구는 부적절하다. 또한 다문서라는 사실 자체가 결함은 아니다. 부작용·권한·동시성·복구는 실제로 해당 정본에 적혀 있다.

**권고:** 교육용 M01의 필수 입력 계약을 하나의 안정된 읽기 경로로 연결하고, architecture에서 “기존 HTTP 계약은 어느 고정 입력의 어느 부분이며 무엇이 주어지지 않았는가”를 직접 가리킨다. 실제 제품에서는 OpenAPI/기존 계약 문서/확인한 시험 중 하나를 정본으로 식별하면 된다. 모든 기존 API를 복사할 필요는 없다. 아울러 웹 사용자의 완료 한 번을 권한 확인 → facade → 저장 transaction → 결과/재조회까지 설명하는 짧은 흐름을 두면 도표와 계약을 이어 읽기 쉽다.

후보의 멱등성은 이미 강하다. 응답을 받지 못했을 때 재조회/동일 완료 재시도가 안전하다는 기존 예시의 표현도 복원할 만하다. [기존 이행 예시 L25–38, L50–52](../../../../../.claude/skills/design-spec/examples/migration/spec.md). 이는 새 분산 트랜잭션 요구가 아니라 이미 가진 반복 완료 계약의 의미를 사용자 경계까지 설명하는 보완이다.

### 5. 중간 — 정성적 아키텍처 판단이 “수치가 없음”에 가려질 수 있다

후보는 성능 수치를 발명하지 않도록 잘 제한한다. [설계 블록 L15](../../spec-plan-design/candidate/guidance/design-blocks.md), [M01 spec L50–59](../../spec-plan-design/candidate/examples/M01/spec.md). 그러나 측정 가능한 AC와 계약 표가 문서의 중심이라, 운영자가 감당할 수 있는 구성인지·기존 자산을 얼마나 재사용하는지·고장과 변경의 영향이 어디까지 미치는지 같은 정성적 선택은 부차적인 문장이 되기 쉽다.

Django는 호환성뿐 아니라 점진 전달 가능성·유지 가능성·중도 중단 시 남는 가치로 설계를 설명한다. 완벽한 내부 비동기화를 제품 가치와 혼동하지 않는다. [Django L699–714, L853–912](../../../exemplary-design-and-plans/originals/D2-django-dep-0009.rst). 수집본의 GitLab/MediaWiki 평가도 제품 요구와 구조·운영을 잇는 설명을 강조한다. 단, 이번 독립 검토는 두 문서의 원문을 읽지 않았고 이 주장은 수집본 평가에 대한 관찰로 한정한다. [시스템 설계 상세 L59–87](../../../exemplary-design-and-plans/system-designs.md).

**반대 근거/이미 있는 대응:** 활성 작성 스킬은 supported quality requirements와 credible alternative/accepted drawback을 허용하고, 활성 depth reference도 operating cost를 다룬다. [활성 스킬 L43–58](../../../../../.claude/skills/design-spec/SKILL.md), [활성 depth L12–17](../../../../../.claude/skills/design-spec/references/design-depth.md). 이는 완전히 없는 기능이 아니라 후보의 압축 과정에서 약해진 유도다.

**권고:** 중요한 구조 변경의 결정 문단에는 “어떤 제약을 만족하고, 어떤 비용을 받아들이며, 어떤 조건이 달라지면 재검토할지”를 쓴다. 정성적 판단을 모두 숫자나 새 AC로 바꾸지 않는다. M01에서는 단일 호스트·중지 허용·외부 서비스 없음이 SQLite를 가능하게 하고, 경합 제한과 운영 이행 부담을 받아들이는 정도면 충분하다.

### 6. 낮음 — F03는 공개 상태를 잘 설명하지만 PR 번호를 설계 상태 이름에 고정할 필요는 없다

F03의 일반 OFF/시험 ON, 부분 구현과 완성 코드의 차이, 공개/중단/정리 조건은 좋은 설계 내용이다. [F03 L33–65](../../spec-plan-design/candidate/examples/F03/spec.md). 다만 상태도의 `PR1`, `PR2`와 merge 이벤트는 계획의 작업 분할이 바뀌면 설계 상태도 함께 바꿔야 하는 연결을 만든다. [F03 L43–59](../../spec-plan-design/candidate/examples/F03/spec.md).

**반대 근거:** 여러 PR 중 어떤 제품 상태가 가능한지 보여주려는 교육 예시라 현재 표기는 이해하기 쉽다. 이 이유만으로 상태도를 제거하거나 단계별 제품 상태를 전부 plan으로 옮겨서는 안 된다.

**권고:** 일반 원칙에서는 설계 상태를 `목록만 시험 가능`, `목록+집계 시험 가능`, `일반 공개`, `상시 제공`처럼 기능/허용 상태로 이름 붙이고, 계획이 PR 번호를 그 상태에 대응시킨다. 이번 합성 예시의 PR 표기는 주석으로 남길 수 있다. spec은 상태의 의미와 전환 전제, plan은 그 상태에 이르는 작업과 시험·담당·순서를 소유한다.

## 여섯 역할과 표에 대한 결론

여섯 정보 역할은 유효하다. Requirements는 바뀔/지킬 것, Acceptance criteria는 관찰할 기대, Design은 구조·동작·계약과 선택 이유, Constraints and scope는 제약·제외, Open questions는 남은 판단, Flagged concerns는 사람의 중요한 결정이다. 다만 이 여섯 역할만으로 도메인·전체 구조·대표 흐름이 자동으로 생기지는 않는다.

현재 사용자 조건의 “여섯 역할 유지”는 지킨다. 여섯 영문 제목까지 항상 같은 순서로 두는 것은 팀의 형식 선택이며 북극성으로 정당화할 수는 없다. 이번 보완은 제목 개편 없이도 가능하다. 우선 Design 안의 구체적인 설명 형태를 개선하고, 역할과 제목을 동일시하는 강제는 추후 양식 결정에서 완화할 수 있다. 역할의 소재를 찾기 쉽다는 장점을 잃지 않는 범위다.

표는 다음 경우 유지한다: R/AC의 참조, 실제 인터페이스의 병렬 계약, 데이터 필드, 실패별 보존/대응. 설명은 다음 경우 문장/순서 있는 흐름으로 쓴다: 현 구조에서 문제가 생기는 이유, 제약 때문에 선택한 구조, 요청의 진행과 실패 분기, 대안의 장단점. 특히 “선택 이유·영향” 칸에 여러 원인과 결과가 붙으면 표 밖 결정 문단으로 빼는 편이 읽기 쉽다. F01의 짧은 표는 그대로 유효하고 B01의 짧은 산문도 유효하다.

## 권장하는 대표 형태

모든 항목을 복사하는 새 만능 목차보다 두 개의 완성 형태를 권한다.

**좁은 변경:** F01/B01 수준을 유지한다. 짧은 변화 설명, R/대표 AC, 1개 Design 문단 또는 작은 표, 필요한 제약·질문·우려면 충분하다. 별도 용어집·도식·대안 목록을 강제하지 않는다.

**여러 책임을 건드리는 변경:** `spec.md`는 짧은 문제/선택 요약과 정본 목록을 제공하고 기존 여섯 역할을 보존한다. Design 본문에는 다음 설명이 해당 변경에 필요한 만큼 들어간다. 파일 분리는 선택이며 각 결정의 정본은 한 곳이다.

1. 현재 구조와 바꿀 이유. 필요한 도메인 개념·식별자·소유자·불변식을 여기서 설명한다.
2. 선택한 구조와 중요한 대안/대가. 기존 자산·팀의 운영 조건이 선택에 어떻게 작용하는지 잇는다.
3. 대표 정상 흐름과 결과를 바꾸는 실패·재시도 흐름. 실제 인터페이스/상태에 연결한다.
4. 필요한 정확한 계약. API·스키마·원자성·설정·권한·호환을 표/예시/도식 중 맞는 표현으로 쓴다.
5. 해당할 때 전환·복구·공개 조건. 실제 실행 명령·작업·TDD 순서는 plan에서 구체화한다.

M01의 시작 설명은 기존 사실만으로도 다음 정도로 쓸 수 있다. 이는 기존 후보를 교체한 문서가 아니라 새 형태의 설명 예다.

> 현재 서비스는 요청 목록 전체를 JSON으로 읽고 다시 쓴다. 서로 다른 요청의 완료가 겹치면, 나중에 저장한 목록이 먼저 완료한 요청의 옛 상태를 포함할 수 있다. 이번 변경은 저장 단위를 요청 행의 트랜잭션으로 바꾸어 이 유실을 없앤다. 요청의 ID·필드·순서와 웹/API 계약은 유지한다.
>
> 기존 단일 호스트에 SQLite를 사용하고 API의 저장소 facade가 활성 저장소 하나를 선택한다. JSON 잠금도 가능하지만 전체 파일 갱신과 내구성·오류 정리를 직접 유지해야 한다. SQLite를 선택하는 대신 writer 경합의 제한된 대기와 중지 상태의 이행·복구 도구를 운영한다. 기존 경합 대기 설정은 유지하며 새 성능 개선 수치를 약속하지 않는다.
>
> 야간 보고서는 옛 JSON을 직접 읽으므로 저장소 전환만 하면 갱신을 놓친다. 확인된 후속 결정에 따라 보고서를 기존 GET API와 읽기 계정으로 옮긴다. 영구 JSON 미러나 이중 쓰기는 두지 않는다. 완료 요청은 기존 권한 검사 뒤 저장소로 전달되며, 대상 행의 확인·갱신을 한 트랜잭션에 두고 commit 후 결과를 반환한다. 같은 완료는 재시도해도 결과가 같다.
>
> 저장 필드·원자성·이행 도구 계약은 storage가, 구성·호출 경계는 architecture가, 최신 쓰기를 포함한 복구와 안전한 재개 조건은 operations가 소유한다. 실제 호스트 명령은 미확인 운영 입력으로 남아 있으며 확인·리허설 전에는 전환하지 않는다.

이 설명 다음에 기존 M01의 상세 계약을 연결하면 된다. 클래스 도식은 공유 인터페이스를 가르치는 교육적 용도가 있을 수 있지만, `Request`가 실제로 dict라고 이미 밝힌 이 얇은 서비스에서 반드시 필요한 그림은 아니다. 컴포넌트/동시성 흐름으로 관계를 이해했고 표로 호출 계약을 알 수 있다면 생략해도 된다. [M01 architecture L23–42](../../spec-plan-design/candidate/examples/M01/design/architecture.md).

## 유지·변경·제거할 것

| 판단 | 대상 | 이유 |
|---|---|---|
| 유지 | 여섯 정보 역할, 구체적인 R/대표 AC, 초안/실행 사실 구별 | 북극성의 인계·사람 판단에 도움이 된다. |
| 유지 | F01/B01의 작은 크기와 정밀한 동작, M01의 상세 저장/복구 계약 | 새 모범 사례를 이유로 이미 충분한 작은 문서를 늘릴 필요가 없다. |
| 유지 | 다문서 정본·결정 소유·변경 시 영향받는 plan 동기화 | 구현자가 문서를 조합해도 서로 다른 계약을 갖지 않게 한다. |
| 변경 | Design의 기본 작성 면과 완성 예시 | 나열보다 현재 문제·제약·선택·동작의 연결을 유도한다. |
| 변경 | M01의 선택 논증·기존 계약 읽기 경로 | 구체성 보강 과정에서 얇아진 설명을 기존 좋은 산문과 결합한다. |
| 변경 | 후보 활성화 전달안의 정책 스킬 정합화 | 함께 읽는 지침이 서로 다른 문서 형태를 강제하지 않게 한다. |
| 제거/완화 | 한 파일 강제, 중요한 우려의 최소 개수 암시, 우려 표 일률 강제 | 정책 검토를 실질적인 판단으로 유지하고 문서 형식이 판단을 지배하지 않게 한다. |
| 추가하지 않음 | 고정 분량, 모든 클래스/함수/도식, 모든 질문을 새 gate로 만드는 검사 | 얇은 사내 서비스와 실제 결정의 크기에 맞지 않는다. |

TDD는 팀의 의무로 그대로 둔다. spec은 판정 가능한 결과·불변식을 정하고 plan은 실제 선행 시험과 작업·검증을 배치한다. 새 사례가 더 자세하다는 이유로 spec에 모든 테스트 코드와 실행 순서를 옮길 필요는 없다. 북극성은 plan의 파일·순서·증명을 별도로 요구하며, 후보도 일반 TDD 확대가 팀의 선택임을 구별한다. [북극성 L91–103](../../spec-plan-design/inputs/north-star-excerpts.md), [전달안 L6–14](../../spec-plan-design/candidate/policy-and-delivery.md).
