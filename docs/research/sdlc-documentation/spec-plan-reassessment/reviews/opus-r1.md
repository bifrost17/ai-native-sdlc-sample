# spec·plan 후보 재평가 (독립 검토, Opus)

## 결론

**구조를 갈아엎을 필요는 없다. 정보 역할(spec 6 / plan 4)은 북극성과 실제 모범 사례 양쪽에 잘 맞고, M01의 분리 정본 방식은 오히려 이번에 읽은 원문들보다 앞선다. 다만 후보는 "형식(form)"에서 한 번 잘못된 선택을 했다 — 거의 모든 결정을 3~4열 표 셀에 압축해 넣는 것이다.** 이것은 절 수의 문제가 아니라 표현 형태의 문제이며, 사람이 읽기도 에이전트가 실행하기도 원문들보다 불리하다. 배포 전 조건부 수정을 권한다: (1) Design/Order of work의 산문 우선 전환, (2) plan의 실행 단위 통합, (3) 실제 변경 1건으로 "대화 없이 구현" 검증 1회. 이 셋을 하지 않은 채 배포하면 후보는 기존 배포본보다 지시문 질량만 두 배 무거운 양식이 된다.

## 우선순위 발견

### F1. Design이 표에 갇혀 있다 — 후보 스스로 그 형식을 버린 증거가 있다

`candidate/templates/spec.md:22-24`의 Design은 `경계/책임 | 정한 구조·동작·계약 | 선택 이유·영향` 3열 표가 유일한 뼈대다. 그런데 후보의 가장 좋은 산출물인 `examples/M01/design/storage.md`와 `architecture.md`는 그 표를 전혀 쓰지 않고 산문 + 도식 + 필드 표로 썼다. `examples/F01/spec.md:25-31`에서 표가 성립한 것은 결정이 네 줄짜리였기 때문이고, `examples/F03/spec.md:34-41`은 표를 포기하고 산문으로 갔다. 즉 세 예시 중 둘이 템플릿의 기본형을 이탈했다.

원문들은 이유가 분명하다. P3 설계문서 `Design §1`의 "Why `sessionStorage`" 세 문장(`P3-...-design.md:87-90`)은 위협모델·대안·감수할 점을 한 흐름으로 잇는데, 셀에 넣으면 끊긴다. Symphony `§3.1`의 8개 컴포넌트 책임, `§3.2` 추상화 계층도 마찬가지다. 북극성의 plan.md 예시(`north-star-excerpts.md:109-127`)조차 표가 없다.

**권고:** Design 본문은 "구조 → 계약 → 선택 이유/감수할 점" 산문을 기본형으로 하고, 표는 `guidance/design-blocks.md:20-28`의 인터페이스/데이터 표처럼 **열거형 계약에만** 쓴다. 표를 없애자는 것이 아니라 기본값을 뒤집자는 것이다.

### F2. plan의 실행 단위가 세 곳으로 흩어져 있다

후보에서 한 작업을 실행하려면 `Files that change` 표(경로), `Order of work`의 번호 문단(순서·예상 실패), `Proof` 표(명령·기대)를 합쳐야 한다. P3의 강점은 정확히 그 반대다. `Task 1`은 파일 → RED 시험 → 실행 명령 → 최소 구현 → GREEN 확인을 한 블록에 담아 그 블록만 읽고 실행할 수 있다.

후보의 손해는 복잡할수록 커진다. `examples/M01/plan.md:35-38`은 PR-B의 네 개 RGR 사이클과 "thread 실행만 하고 직렬 완료된 결과를 동시성 증거로 쓰지 않는다"는 중요한 판정 기준을 한 문단에 압축하고 실제 명령은 `P-B1` 행으로 넘긴다. 병렬 세션·서브에이전트에 한 작업씩 넘기려면(북극성 L7) 이 형태는 재조립 비용을 매번 물린다.

**권고:** 여러 작업이 있는 plan에 한해 선택형 **작업 블록**을 허용한다 — `작업 N: 이름 / 파일 / 먼저 쓸 시험과 예상 실패 / 실행 명령 / 통과 조건`. Proof 표는 없애지 말고 AC 매핑과 통합 증명의 요약으로 남긴다(P3에는 이 상위 매핑이 없어 `Self-Review Checklist`의 "spec coverage" 한 줄로 때운다 — 여기서는 우리가 낫다). F01 같은 한 PR 변경은 지금의 짧은 서술을 유지한다.

### F3. 대안과 비목표가 셀 한 조각으로 축소됐다

조사 README가 스스로 내린 결론은 "좋은 문서는 항목 수보다 결정 사이의 연결이 강했다… 선택 이유가 대안과 연결되며"(`README.md:40`)다. 그런데 후보에서 대안은 `선택 이유·영향` 열의 일부일 뿐이고, 비목표는 `Constraints and scope`의 "제외한다" 목록에 섞인다. 원문들은 모두 이것을 1급으로 다룬다: P1 `Rejected alternative approach`(왜 `dark:` 전용을 버렸는가), P3 설계의 `Threat Model` 범위 밖 2항목 + `Deferred Work`(왜 샌드박스 iframe을 지금 하지 않는가), Symphony `§2.2 Non-Goals`. `examples/M01/spec.md:47-48`의 JSON 잠금 대안 두 줄은 좋은 사례지만 양식이 요구해서 나온 것이 아니다.

**권고:** 새 절을 만들지 말고 Design 말미에 "검토한 대안과 버린 이유 / 이번에 하지 않는 것과 그 조건" 한 단락을 **실제 대안이 있었을 때 필수**로 지정한다. skill(`design-spec/SKILL.md:34`)은 이미 "meaningful choice/reason/tradeoff"를 말하지만 양식에 자리가 없어 셀로 눌린다.

### F4. spec에 "지금 관찰된 동작·실패"를 적을 자리가 없다

P3 설계의 `Current Failures` 5항목은 재현된 사실이고, 그래서 계획의 RED 단계가 신뢰를 얻는다. Symphony `§1 Problem Statement`도 같은 역할이다. 후보 `templates/spec.md`는 요약 한 줄 뒤 바로 Requirements로 간다. 그런데 `templates/plan.md:21`은 "기존 기준 확인 또는 재현"을 요구한다 — **무엇을 재현할지는 어디에도 적히지 않는다.** F01/F03/M01 어디에도 "현재 이렇게 동작한다/실패한다"는 관측이 없다(결함 예시 B01은 이번 범위에서 읽지 않았으므로 그쪽 처리 여부는 판단하지 않는다).

**권고:** 절 추가 없이 `templates/spec.md:5`의 요약 블록에 "현재 확인된 동작/실패와 확인 방법"을 명시 항목으로 넣는다. 비용은 한두 줄이고, plan 1단계와 Proof의 RED 기대가 여기에 걸린다.

### F5. 템플릿의 지시문이 내용과 섞여 삭제 경계가 없다

`templates/spec.md:26-28, 30-31, 47-48`은 "중요한 결정을 '구현 시 적절히'로 넘기지 않는다", "조건부 표를 모두 N/A로 남기지 않는다" 같은 **규칙**을 양식 본문에 ‹›로 넣는다. 이는 skill의 내용이고(`design-spec/SKILL.md:34`가 이미 같은 말을 한다), 채우는 사람에게는 "어디까지 지우는가"가 불명확해진다. 배포본 `templates/spec.md`는 절당 한 줄로 훨씬 가볍다 — 후보는 지시문 질량을 두 배 늘렸다.

P1 원문은 정답을 보여 준다: 모든 안내가 `<!-- -->` 주석이고(`P1-openverse-dark-mode.md:5-6, 10, 17, 24, 157, 186-195`), 질문형이며, 렌더링에서 사라지고, "이 템플릿은 망라적이니 필요 없는 절은 지워라"를 첫 줄에 적어 둔다. 덧붙여 P1에는 `Reviewers` 체크박스가 있고 북극성 03은 "product owner가 스펙을 승인"을 governance로 요구하는데, 후보 spec 머리에는 **결정자/리뷰어 줄이 없다**. `examples/F03/spec.md:58`이 "공개 담당은 합성 업무 오너(root 역할)"로 본문에서 임시 처리하는 것이 그 증상이다.

**권고:** 안내를 HTML 주석으로 옮기고, 규칙성 문장은 skill로 회수한다. 머리글에 `Decision/Reviewers:` 한 줄을 추가한다(빈 슬롯 하나가 절 하나보다 싸다).

## 유지할 강점과 반론

- **`examples/M01/design/storage.md`는 낮추지 말아야 한다.** `ordinal` 열, `BEGIN IMMEDIATE`, "timeout=5는 설정 상한이지 응답 시간 성능 계약이 아니다", "파일 존재 자체는 성공 신호가 아니다"는 Symphony `§14`급 정밀도이고, P2가 데이터 복구에서 빈틈을 남긴 바로 그 지점(`implementation-plans.md:49`)을 정확히 막는다. 간결화의 이름으로 건드릴 대상이 아니다.
- **spec 진입점 + 설계 정본 목록(`examples/M01/spec.md:9-20`)은 원문들보다 낫다.** Symphony는 한 파일이 비대해졌고, P3 쌍은 설계→계획 연결이 암묵적이다. "같은 Git 판의 문서 집합"과 "결정 하나에 정본 하나"는 유지한다.
- **정직성 규칙은 독립적으로 잘 도출됐다.** `skills/tdd/SKILL.md:18-19`의 "이미 GREEN인 사례를 RED로 만들지 않는다"는 P3 `Task 6`(`:551`)과 같은 판단이고, `examples/F03/plan.md:33`의 "PR1의 단계 한정 관측을 영구 회귀로 고정하지 않는다"는 P1의 Launch plan보다 정교하다.
- **반론으로서의 표:** `examples/F01`처럼 작은 변경에서는 표가 실제로 P1 원문보다 빨리 읽힌다. F1의 권고는 "표 금지"가 아니라 기본값 전환임을 다시 밝힌다.

## 권장하는 문서 구조·깊이·스킬 변경

- **구조:** spec = 요약(현재 관찰 포함) → R → AC → Design(산문 + 필요한 계약 표/도식 + 대안·비목표) → 제약/범위 → 미결 질문 → 우려. 작으면 한 파일, 크면 정본 목록. plan = Files → (필요 시) 작업 블록 → Order/PR 표 → Risks → Proof.
- **깊이 예시:** 지금 세 예시가 모두 CLI/저장소다. **사용자에게 보이는 흐름 예시가 하나도 없다.** `guidance/design-blocks.md:10, 15`의 "UI·통합 사용 흐름"과 "성능·외부 의존" 행은 완성 예시 자리가 "해당 제품의 실제 mock/계약"으로 비어 있어 사실상 안내가 없다. 내부 사내 서비스에서 가장 흔한 사례가 여기다. P1식으로 "요청/화면 하나를 끝까지" 설명하는 작은 예시 1건(중간 통합 상태에 '화면 변화 없음'을 명시하는 단계 포함)을 추가하는 것이 M01을 더 다듬는 것보다 가치가 크다.
- **skill 변경:** `design-spec/SKILL.md`에 대안·비목표·현재 관찰 세 항목을 명시(각 한 줄), 양식에서 회수한 규칙 문장을 흡수. `plan/SKILL.md`에는 작업 블록을 **언제 쓰는지의 기준**(작업 3개 이상 또는 병렬·인계 예정)을 넣는다. 양쪽 모두 절을 늘리지 말고 기존 불릿에 붙인다.

## P3 쌍에서 가져오지 말 것

P3의 spec/plan 쌍은 연결의 모범이지 서술의 모범이 아니다. **계획 안의 긴 구현 코드 전문**은 그 자체로 실패했다 — `P3-...-plan.md:124-130`은 "Task 4가 `securityHeaders`를 도입한다고 가정한다. Task 1을 먼저 하면 임시로 이렇게 쓰고 Task 4에서 교체하라"라고 한 문서 안에서 자기 코드를 수습하고 있고, 실제 구현은 또 달라졌다(`implementation-plans.md:73`). 개인 절대 경로(`:76` `/Users/drewritter/...`), 외부 스킬 이름 강제(`:3` "REQUIRED SUB-SKILL: superpowers:subagent-driven-development"), 그리고 사소한 변경까지 4단계 체크박스를 씌우는 의례(`Task 8`의 `.gitignore` 한 줄을 RED/GREEN으로 포장)는 모두 가져오지 않는다. 마지막 항목은 F2의 작업 블록을 **선택형**으로 두어야 하는 이유이기도 하다. Symphony에서는 RFC 2119 어휘와 필드 단위 스키마 전수(`§5.3`), 응답 JSON 전문(`§13`)을 가져오지 않는다 — 다중 구현체를 위한 상호운용 규격의 장치이지 얇은 사내 서비스의 것이 아니다. P2의 낙관적 Risks와 모호한 데이터 복구도 반례로만 쓴다.

## 새 검증이 확인해 줄 것

지금 후보의 근거는 "우리가 쓴 예시가 좋아 보인다"에 머문다. 문서 리뷰를 한 번 더 하는 것으로는 더 나아가지 못한다. 필요한 것은 실행 검증이다.

1. **대화 없는 인계 시험(최우선).** 이 저장소의 실제 작은 변경 1건으로 후보 skill로 spec+plan을 쓰고, 대화를 보지 않은 새 세션이 산출물만으로 구현하게 한다. 측정: 되물은 질문 수, 임의 가정 수, 실제 변경 파일 집합이 `Files that change`와 일치하는지, 관측된 RED가 계획의 예상 실패와 같은지. 이것이 북극성 L4(`north-star-excerpts.md:97`)가 요구하는 유일한 합격 기준이며 우리는 아직 한 번도 시험하지 않았다.
2. **작성 비용 대조.** 같은 변경을 배포본 양식과 후보 양식으로 각각 작성해 시간·분량·삭제 누락(`grep -n '‹'`로 지시문 잔존 확인)을 비교한다. 후보의 추가 지시문 질량이 값을 하는지가 여기서 갈린다.
3. **병렬 인계 시험.** M01식 A/B 분할을 실제 두 세션에 주고 공유 계약 판 한 줄로 충돌 없이 통합되는지 본다(북극성 L7).
