# 문서 구조 재구성 제안

2026-09-11. 연구용 제안이며 활성 양식이나 이전 후보를 교체한 결과가 아니다.
이전 후보의 중요한 계약은 유지하고, 실제 작성 결과의 구조를 바꾸는 방식이다.

## Spec: 제품과 시스템을 이해한 뒤 중요한 결정을 찾아 읽기

여섯 정보 역할은 유지한다. Requirements/Acceptance criteria/Design/Constraints and scope/Open questions/Flagged concerns라는
영문 절 이름을 당장 바꿀 필요는 없다. **그 안의 모든 답을 표 한 행으로 압축하는 기본 모양**을 바꾼다.

```text
spec.md
  짧은 변경 설명, 중요한 미해결 판단, upstream/상태/출처
  Requirements                   변경·보존 동작, 근거
  Acceptance criteria            대표 성공·실패·회귀의 판정
  Design
    Context and approach         현재 문제 → 이번 선택 → 바뀐 사용자/시스템 흐름
    Concepts and boundaries      중요한 이름·책임·정본·현재/목표 구분
    Behavior and contracts       대표 경로, 필요한 인터페이스/데이터/상태/실패
    Decisions and tradeoffs      갈림길의 선택 이유·대가·필요한 미정
    설계 정본 링크               상세가 분리됐을 때만
  Constraints and scope
  Open questions
  Flagged concerns
```

이는 선택 가능한 내부 구조다. F01 같은 좁은 변경은 Design 한 문단과 입출력 예시로 위 질문에 답할 수 있다.
새 소제목을 전부 쓰거나 용어 사전·대안·정본 파일을 별도로 만들 의무는 없다. API/스키마처럼 비교할 값은 표가 좋고,
어떻게/왜 작동하는지는 연결된 문장·흐름·필요한 그림이 좋다. 읽기 순서와 정본은 한 번 명확하게 안내한다.

spec.md 밖 상세도 같은 여섯 절을 복제하지 않는다. 예를 들어 design/storage.md는 그 저장 설계에 필요한 순서로 쓴다.
입구에서 상세 파일의 결정 소유 범위를 알리고, 그 결정은 상세를 정본으로 삼는다. 요약은 정본 링크와 함께 설명하고 재정의하지 않는다.

### M01: 현재 Design 설명을 어떻게 바꿀지

[현재 후보](../spec-plan-design/candidate/examples/M01/spec.md)는 SQLite 선택과 정본 링크를 제시한다.
아래는 같은 합성 사실을 사람이 이해할 수 있는 순서로 풀어쓴 예다. 새 요구나 실제 관측을 추가한 것이 아니다.

> 현재 가상 서비스는 완료할 때 JSON 전체를 읽어 다시 쓰므로, 겹친 완료가 서로의 결과를 덮을 수 있다.
> 이번 변경은 기존 웹/API 계약을 유지하면서 그 쓰기를 SQLite의 짧은 트랜잭션으로 옮긴다.
> 야간 보고서는 JSON을 직접 읽고 있어 저장소만 바꾸면 오래된 결과를 읽게 된다. 따라서 보고서를 기존 API의 소비자로
> 먼저 전환하고, 이후 서비스 facade가 고른 저장소를 모든 소비자가 같은 경로로 보게 한다.
>
> 단일 호스트이고 운영 중지가 허용되므로 별도 DB 서비스를 늘리지 않는 SQLite를 선택한다.
> JSON 잠금 보강도 가능하지만 전체 파일 갱신의 잠금·내구성·실패 정리를 직접 유지해야 한다.
> 대신 이번 선택은 이행/복구 도구와 단일 writer 경합을 다룰 책임을 남긴다.
> 구체적인 트랜잭션·5초 잠금 설정은 storage 정본, 전환 후 최신 쓰기 보존과 재개 조건은 operations 정본을 따른다.

앞선 후보의 'JSON 잠금도 보고서/이행/복구를 다시 다뤄야 한다'는 이유만으로는 선택을 충분히 구별하지 못한다.
SQLite에도 필요한 비용이다. [이전 활성 예시의 선택 이유](../../../../.claude/skills/design-spec/examples/migration/spec.md)를
참고해 양쪽의 실제 비용을 설명한다. 대안 수를 늘리라는 뜻은 아니다.

### M01: 대표 동작을 끝까지 잇는 예

설계 파일에는 아래 흐름을 한 번 설명하고 그에 대한 상세 계약을 연결한다. AC와 SQL 전문을 복제하지 않는다.

1. 기존 사용자의 완료 요청을 API가 인증·권한 검사한다. 거부하면 facade의 쓰기를 호출하지 않는다.
2. facade가 시작 때 선택한 저장소의 complete_request(id)를 호출한다. 선택/DB 검증 실패는 시작 단계에서 드러낸다.
3. SQLiteStore가 쓰기 트랜잭션을 얻어 해당 ID만 완료한다. 다른 완료는 잠금을 얻은 뒤 자기 ID를 바꾸므로 앞선 완료를 덮지 않는다.
4. commit 후 기존 행 형태를 반환하고 API는 기존 완료 응답으로 전달한다. 잠금/저장 실패는 rollback 후 기존 503 의미로 전달한다.
5. 이후 목록과 야간 보고서는 같은 API→활성 저장소 경로의 최신 데이터를 읽는다. 보고서의 옛 JSON fallback은 없다.

정확한 권한/예외는 [architecture](../spec-plan-design/candidate/examples/M01/design/architecture.md),
원자성과 타입은 [storage](../spec-plan-design/candidate/examples/M01/design/storage.md)가 소유한다.
기존 경합 시퀀스는 여전히 유용하다. 그림을 추가한다면 더 많은 UML을 전시하기보다 위 흐름에서 모호한 경계만 보여준다.
현재/목표/전환 중 어댑터를 한 그림에 표시한다면 어느 것이 활성인지 범례로 구별한다.

## Plan: 인도 지도를 보고, 맡은 작업을 따라 실행하기

네 정보 역할은 유지하되 Order of work 안에 **PR별 인도 지도 → 작업별 실행 상세**를 둔다.
파일·시험·기대가 전부 독립 목록이 되지 않게 연결한다. 기존 F01 정도의 작은 변경은 지금처럼 짧게 쓸 수 있다.

```text
plan.md
  이 설계를 제품에 넣는 순서의 요약, 필수 입력과 현재 판
  Files that change              전체 영향 색인, new/기존·역할
  Order of work
    인도 지도                    PR 목적·선행/병렬·머지 후 동작/노출·남은 일
    PR-A
      작업 1                     목적/정본 → 파일·첫 시험 → 최소 변경 → 완료 관측
      작업 2                     필요한 경우 같은 방식
      PR 통합 확인               최신 main 결합, 머지 후 확인
    PR-B ...
    공개/전환                    해당할 때만 실제 책임·절차/운영 정본
  Risks                          아직 놓치기 쉬운 위험과 대응, 상세 참조
  Proof                          AC·회귀·통합·운영 증거의 색인과 공통 명령
```

작업은 함수나 커밋 단위와 같지 않다. 한 동작과 그 시험/설명이 응집되고, 다음 담당자가 이어받을 결과가 있어야 한다.
작업의 목적·입력·파일·첫 실패·완료 조건은 중요한 판단을 가능하게 할 만큼 구체적으로 쓰되,
이 필드 이름을 모든 작업에 반복할 의무는 없다. 새 테스트 전체 코드·모든 RGR 순환의 사전 원장은 기본값으로 만들지 않는다.

### F03 PR2의 작업을 모아 쓰는 예

아래는 [현행 후보 plan](../spec-plan-design/candidate/examples/F03/plan.md)의 같은 내용을 한 작업 옆에서 읽는 표현이다.
실제 수행 결과가 아니다. 처음부터 명령·시험이 없는 자료를 새로 완성했다는 뜻도 아니다.

> **담당자 집계를 공유 공개 제어 뒤에 연결한다.** PR1이 main에 들어간 판에서 시작한다.
> spec AC3/4의 출력 계약과 Design의 동일한 TRACKER_OWNER_INSIGHTS 제어를 사용한다.
> 수정은 tracker.py와 USAGE.md, 시험은 새 tests/test_summary.py 및 기존 tests/test_release_control.py다.
>
> 먼저 test_summary.py의 전체 집계 사례에서 ON 환경의 summary가 `all\t4\nopen\t3\ndone\t1\n`과 rc0를
> 내도록 기대하고 `python3 -m unittest discover -s tests -p test_summary.py -v`를 실행한다.
> PR1에는 summary가 없으므로 예상 실패는 argparse rc2다. fixture/import 오류는 이 동작의 실패 근거가 아니다.
> 기존 제어를 재사용해 읽기·집계·출력의 최소 경로를 연결한다. 다음에 담당자별·완료 후 집계와 무쓰기 사례를 시험 먼저 확장한다.
>
> 완료 확인은 AC3/4의 모든 조합과 기존 목록·OFF 거부 회귀다. PR1에서 ON summary가 없었던 관측은
> 영구 회귀가 아니므로 이 단계의 성공을 막는 기대값으로 남기지 않는다.
> 전체 `python3 -m unittest discover -s tests -v`를 최신 main과 결합한 판에서 확인하고 PR 검토로 넘긴다.
> 머지 후 통합 main에서도 확인한다. 이 PR 뒤 일반 사용은 여전히 OFF이며 시험 ON에서 두 기능이 모두 동작한다.
> 일반 공개는 전체 공개 단위의 P4 리허설과 오너 결정에 연결한다. 이 작업 하나의 통과가 공개 승인은 아니다.

Proof의 P3 행은 위 작업과 AC3/4를 가리킨다. 같은 기대값을 여러 곳에 다시 적어 서로 다른 정본을 만들지 않는다.
실제 구현에서는 named test/명령을 현실에 맞게 검증하고, 바뀌면 이유와 함께 plan을 관련 코드 커밋에 갱신한다.

## 상세화와 파일 분리의 선택

| 변경 성격 | 충분한 기본 형태 | 추가할 때의 이유 |
|---|---|---|
| F01/B01처럼 좁은 계약 변경 | 짧은 spec, 한 PR의 plan, 정확한 입력/출력 사례 | 읽는 사람이 중요한 동작을 다르게 추측할 여지가 있을 때만 상세 |
| UI/API 등 여러 경계를 잇는 기능 | 짧은 진입 설명, 대표 흐름, 필요한 화면/계약, PR별 작업 | 경계 사이의 상태·오류·권한을 한 곳에서 설명해야 할 때 |
| M01처럼 데이터/운영 경계가 다른 변경 | spec 진입점 + 책임별 상세 정본, plan 인도 지도 + PR별 작업 | 상세 문서의 독자·결정 소유자·갱신 범위가 달라질 때 |

파일을 나누는 이유는 분량 숫자나 PR 수가 아니라 읽기/소유 경계다. spec은 한 파일이어도 되고 여러 파일이어도 된다.
큰 plan도 plan.md를 인도 지도와 색인으로 두고 PR별 상세를 연결할 수 있지만, 작은 계획을 자동 분할하지 않는다.
한 구현자가 맡은 작업의 필수 정본을 정확히 찾아 읽을 수 있어야 한다. 보존용 연구 기록은 구현의 필수 입력과 구별한다.

미래 작업의 불확실성을 '나중에 적절히'로 감추지 않는다. 어떤 결정이 언제 필요하고 어느 작업만 막는지 밝힌다.
현재 승인/인계할 작업에는 필요한 중요한 결정을 채운다. 그 문서가 아직 해소하지 않은 뒤 단계까지 구현 준비가 끝났다고 주장하지 않는다.

## 작성 스킬을 어떻게 바꿀지

1. 관련 정책/코드/입력을 읽은 뒤 먼저 이 변경의 중심 문제와 대표 동작을 말한다. 불필요한 양식 칸부터 채우지 않는다.
2. 중요한 결정과 기존 제약을 연결한 완성 예시를 선택해 읽는다. 작은/여러 경계/운영이라는 상황의 차이를 설명한다.
3. spec에서 결정의 정본을, plan에서 맡을 작업의 정본과 증거를 찾을 수 있는지 사람과 함께 검토한다.
4. '정책을 모두 읽었다'는 행정적 흔적이 제품 설명을 압도하지 않게 한다. 적용한 실제 스킬/판·원 prompt는 기존 기록에 보존한다.
5. TDD 공통 기법은 자체 스킬, 의무는 얇은 정책, 계약별 기대는 spec, 작업별 첫 시험과 경로는 plan, 실제 증거는 PR/실행 기록이라는 배치를 유지한다.

이 제안을 적용할 때 기존 spec-policy-pass의 한 파일 강제와 불필요한 우려 유도 문구도 함께 정합화해야 한다.
양식만 고치고 함께 로드되는 지침을 그대로 두면 작성 결과가 다시 흔들릴 수 있다.
