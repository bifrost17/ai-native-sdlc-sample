33 Skills are how an organization makes its institutional knowledge operational. The instructions are explicit, version controlled, applied broadly, and updated centrally when policy changes. The rule of thumb: write a skill for institutional knowledge that must be applied consistently; don't write a skill

39 Getting started
40 
41 Prerequisites
42 : None required. Having a
43 CLAUDE.md
44 helps, because it keeps the agent's working knowledge in the repo, but a skill does not depend on it.
45 Infrastructure
46 : One policy with a named owner and a written source of truth.
47 How to execute it
48 
49 Pick one piece of knowledge that is enforced inconsistently today. This could be a security standard, an API design convention, or a brand rule.
50 Write it as a skill, a folder containing a
51 SKILL.md
52 whose frontmatter says when it triggers and whose body says what to do. An engineer writes it from the policy owner's source of truth, using Claude to help.
53 Put the skill in the repo at
54 .claude/skills/<name>/
55 so it ships with the code, or distribute it organization-wide through a plugin.
56 Test that the skill triggers. Ask Claude to do the relevant task in different ways and confirm the skill loads each time.
57 When the policy changes, change the skill and have the policy owner sign off on the change.
58 Engineers pick up the new version automatically in their next session.

71 # Secure API review
72 When you create or change an API endpoint:
73 1. Authentication: every endpoint requires the gateway JWT;
74 no anonymous routes outside /health.
75 2. Input validation: validate request bodies against the OpenAPI
76 schema and reject unknown fields.
77 3. Audit: every state-changing endpoint emits an audit event with
78 actor, action, entity and timestamp.
79 4. Data classification: fields tagged pii in the schema must never
80 appear in logs or error messages.
81 Run scripts/check-endpoints.sh and include its output in your summary.
82 Governance considerations
83 
84 A skill is a control, though an advisory one. It makes Claude likely to apply the policy while the code is written, and nothing forces a session to comply with it. A policy that must always hold needs something deterministic behind the skill, such as a hook that blocks the action or a review pass that re-checks the policy at the PR. The skill makes violations rare and the hook makes them close to impossible. Skill invocations are logged in session traces, and the policy owner reviews skill changes like code.
85 How to measure it
86 
87 Leading indicator
88 : Time from the policy owner approving a policy change to the updated skill merging, taken from the PR on the skill folder.
89 Lagging indicator
90 : PR review findings that cite the policy, which should fall toward zero once the skill is applying the policy while the code is written. Where the findings don't fall toward zero, either the skill isn't triggering or its text has drifted from the official policy.
91 Hooks as build-time guardrails
92 
93 A skill is an advisory control, while a hook is the deterministic layer behind it. Most of Claude's actions are file edits and shell commands during implementation, so the build phase is where hooks can end up firing most often.
94 Build-phase hooks can:
95 Block edits to protected paths such as generated classes or a frozen package
96 Run the formatter and linter after file edits so drift never accumulates
97 Keep credentials out of the diff
98 Back any skill whose policy has to hold without exception
99 A hook runs on each action that matches it, so build-phase hooks should be fast and scoped to the file that changed. Heavier checks such as the full test suite belong at the commit or the PR.
