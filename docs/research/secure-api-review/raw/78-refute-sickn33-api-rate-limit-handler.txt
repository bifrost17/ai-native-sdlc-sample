    29	## How It Works
    30	
    31	### Step 1: Classify the response
    32	
    33	Determine whether a failed request is retryable or terminal.
    34	
    35	| Status | Classification | Action |
    36	|--------|---------------|--------|
    37	| 200-299 | Success | Return response |
    38	| 400, 401, 403, 404 | Terminal client error | Do not retry — fix the request |
    39	| 408, 429 | Retryable (rate limit / timeout) | Retry with backoff |
    40	| 500, 502, 503, 504 | Retryable (server error) | Retry with backoff |
    41	
    42	### Step 2: Parse rate limit headers
    43	
    44	Always check upstream hints before computing your own delay.
    45	
    46	```typescript
    47	function getRetryDelay(
    48	  response: Response,
    49	  attempt: number,
    50	  maxDelayMs = 60_000
    51	): number {
    52	  // Prefer upstream hints
    53	  const retryAfter = response.headers.get("Retry-After");
    54	  if (retryAfter) {
    55	    const seconds = Number(retryAfter);
    56	    if (Number.isFinite(seconds) && seconds >= 0) {
    57	      return Math.min(seconds * 1000, maxDelayMs);
    58	    }
    59	    // HTTP-date format
    60	    const date = new Date(retryAfter).getTime();
    61	    if (Number.isFinite(date)) {
    62	      return Math.min(Math.max(0, date - Date.now()), maxDelayMs);
    63	    }
    64	  }
    65	
    66	  // GitHub documents x-ratelimit-reset as Unix epoch seconds.
    67	  const githubReset = Number(response.headers.get("x-ratelimit-reset"));
    68	  if (Number.isFinite(githubReset)) {
    69	    return Math.min(
    70	      Math.max(0, githubReset * 1000 - Date.now()),
    71	      maxDelayMs
    72	    );
    73	  }
    74	
    75	  // Fallback: capped exponential backoff with full jitter.
    76	  const cap = Math.min(1000 * 2 ** attempt, maxDelayMs);
    77	  return Math.floor(Math.random() * cap);
    78	}
    79	```
    80	
    81	Provider-specific reset headers do not share one unit or format. For example,
    82	some APIs return durations while GitHub returns epoch seconds. Parse an
    83	additional header only after checking that provider's current documentation.

    85	### Step 3: Implement the retry loop
    86	
    87	```typescript
    88	async function fetchWithRetry(
    89	  url: string,
    90	  options: RequestInit,
    91	  maxRetries = 3,
    92	  maxElapsedMs = 120_000,
    93	  retryNonIdempotent = false
    94	): Promise<Response> {
    95	  const startedAt = Date.now();
    96	  const method = (options.method ?? "GET").toUpperCase();
    97	  const replaySafe = ["GET", "HEAD", "OPTIONS", "PUT", "DELETE"].includes(method)
    98	    || retryNonIdempotent;
    99	
   100	  for (let attempt = 0; attempt <= maxRetries; attempt++) {
   101	    const response = await fetch(url, options);
   102	
   103	    if (response.ok) return response;
   104	
   105	    // Terminal errors — do not retry
   106	    if ([400, 401, 403, 404, 422].includes(response.status)) {
   107	      throw new Error(`Terminal error ${response.status}: ${response.statusText}`);
   108	    }
   109	
   110	    if (!replaySafe) {
   111	      throw new Error(
   112	        `${method} was not retried because replay safety was not explicitly established`
   113	      );
   114	    }
   115	
   116	    // Retryable — but exhausted attempts
   117	    if (attempt === maxRetries) {
   118	      throw new Error(`Failed after ${maxRetries} retries: ${response.status}`);
   119	    }
   120	
   121	    const remaining = maxElapsedMs - (Date.now() - startedAt);
   122	    const delay = Math.min(getRetryDelay(response, attempt), remaining);
   123	    if (delay <= 0) {
   124	      throw new Error(`Retry deadline exceeded after ${maxElapsedMs}ms`);
   125	    }
   126	
   127	    // Release the connection before waiting when the body is not needed.
   128	    await response.body?.cancel();
   129	    console.warn(
   130	      `Request failed (${response.status}), retrying in ${Math.round(delay)}ms (attempt ${attempt + 1}/${maxRetries})`
   131	    );
   132	    await new Promise(resolve => setTimeout(resolve, delay));
   133	  }
   134	
   135	  throw new Error("Unreachable");
   136	}
   137	```

   139	### Step 4: Add a client-side rate limiter (proactive)
   140	
   141	Prevent hitting upstream limits in the first place with a token bucket or sliding window.
   142	
   143	```typescript
   144	class TokenBucket {
   145	  private tokens: number;
   146	  private lastRefill: number;
   147	  private queue: Promise<void> = Promise.resolve();
   148	
   149	  constructor(
   150	    private maxTokens: number,
   151	    private refillRate: number // tokens per second
   152	  ) {
   153	    this.tokens = maxTokens;
   154	    this.lastRefill = Date.now();
   155	  }
   156	
   157	  async acquire(): Promise<void> {
   158	    const ticket = this.queue.then(() => this.acquireOnce());
   159	    this.queue = ticket.catch(() => undefined);
   160	    return ticket;
   161	  }
   162	
   163	  private async acquireOnce(): Promise<void> {
   164	    this.refill();
   165	    if (this.tokens < 1) {
   166	      const waitMs = ((1 - this.tokens) / this.refillRate) * 1000;
   167	      await new Promise(resolve => setTimeout(resolve, waitMs));
   168	      this.refill();
   169	    }
   170	    this.tokens -= 1;
   171	  }
   172	
   173	  private refill(): void {
   174	    const now = Date.now();
   175	    const elapsed = (now - this.lastRefill) / 1000;
   176	    this.tokens = Math.min(this.maxTokens, this.tokens + elapsed * this.refillRate);
   177	    this.lastRefill = now;
   178	  }
   179	}
   180	
   181	// Usage: limit to 60 requests/minute
   182	const limiter = new TokenBucket(60, 1);
   183	
   184	async function rateLimitedFetch(url: string, options: RequestInit) {
   185	  await limiter.acquire();
   186	  return fetchWithRetry(url, options);
   187	}
   188	```

   245	## Best Practices
   246	
   247	- ✅ Always respect `Retry-After` headers — they come from the provider who knows their limits
   248	- ✅ Add jitter to backoff to prevent thundering herd when multiple clients retry simultaneously
   249	- ✅ Log every retry with status code, delay, and attempt number for debugging
   250	- ✅ Set a maximum total timeout to avoid hanging indefinitely
   251	- ✅ Use a client-side rate limiter proactively rather than only reacting to 429s
   252	- ✅ Retry state-changing requests only with a provider-documented idempotency mechanism and a stable key
   253	- ❌ Don't retry 4xx client errors (except 408 and 429) — fix the request instead
   254	- ❌ Don't use fixed delays — exponential backoff distributes load more evenly
   255	- ❌ Don't retry without a cap — unbounded retries can amplify outages
   256	- ❌ Don't ignore per-endpoint limits — some APIs have different quotas per route
   257	
   258	## Limitations
   259	
   260	- This skill does not replace environment-specific validation, testing, or expert review.
   261	- Token bucket is approximate for distributed systems — use Redis-backed rate limiting for multi-instance deployments (for example the `upstash-ratelimit` skill, or any shared-store limiter).
   262	- Some APIs use non-standard rate limit headers; check provider documentation.
   263	- The elapsed-time cap shown here bounds retry waits, not a single hung network call; combine it with an `AbortSignal` or client timeout.
   264	
   265	## Common Pitfalls
   266	
   267	- **Problem:** Retrying too aggressively during an outage amplifies the problem.
   268	  **Solution:** Use exponential backoff with jitter and a circuit breaker for sustained failures.
   269	
   270	- **Problem:** Multiple instances of your app all retry at the same time (thundering herd).
   271	  **Solution:** Add randomized jitter (`Math.random() * 0.3 * delay`) to decorrelate retries.
   272	
   273	- **Problem:** Retry-After header contains an HTTP-date instead of seconds.
   274	  **Solution:** Parse both formats — check if the value is numeric first, then try Date parsing.
   275	
   276	- **Problem:** Client-side limiter doesn't account for concurrent requests already in-flight.
   277	  **Solution:** Serialize acquisition within one process, decrement before send, and use a shared distributed limiter across instances.
