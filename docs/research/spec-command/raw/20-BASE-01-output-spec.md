# Spec: 청구 상태 변경 고객 통지 (from intent 0011-claim-status-notice)
Upstream: intent.md@9e39bd5. Status: draft.
Skills applied: brand@2db39c6, compliance@2db39c6, ux@2db39c6, secure-api-review@7c13202.

## Requirements
- **R1** 사정인이 claims-core 에서 청구 상태를 변경하면, 그 청구의 고객에게 24시간 이내에 통지(문자 또는
  앱 푸시)가 발송된다. (intent Problem: 상태 변경 후 고객 인지까지 평균 2.7일 → Proposed outcome: 24시간
  이내)
- **R2** 통지 채널은 고객별로 결정된다 — 포털 앱이 설치·로그인 이력이 있고 푸시 수신 동의가 있으면 앱
  푸시, 아니면 문자(SMS). 두 채널 모두 없으면(동의 미확인) 발송하지 않는다.
- **R3** 통지 문구는 brand 정책(B1–B7)과 UX 정책(U1–U3, U6)을 따른다: 청구 상태는 고정 5어휘(B4)만
  쓰고, 상태별 「다음 예정」 한 줄을 포함하며(U2), 존댓말·단문·과장 없이 쓴다(B1–B3, B7).
- **R4** 통지 링크는 포털 SSO 로그인 뒤에만 해당 청구 화면을 보여준다. 로그인 전에는 청구 내용(상태 포함)
  이 어떤 형태로도 노출되지 않는다. (intent Constraint 1)
- **R5** 통지는 claims-core 에 이미 있는 전화번호/디바이스 토큰만 쓰고, 새 PII 를 수집하지 않는다. (intent
  Constraint 2)
- **R6** 통지는 해당 채널의 수신 동의가 기록된 고객에게만 보낸다(C4). 동의 상태를 확인할 수 없으면 보내지
  않고, 그 사실을 억제(suppressed) 사유와 함께 기록한다.
- **R7** 통지 본문에는 근거(청구 번호, 상태 변경 사실)와 문의 경로만 싣고, 사유 상세·금액 산정 근거 등
  민감 정보는 싣지 않는다(C5). 주민등록번호·계좌번호·전화번호 전체는 어떤 통지에도 싣지 않는다(C1).
- **R8** claims-core → notify-gw 간 통지 발송 호출과 고객의 통지 열람·청구 조회는 모두 감사 로그로
  남는다: 누가(역할/ID, 사정인 또는 system), 무엇을(청구 번호), 언제(UTC), 보존 3년(C6). 로그에는 PII 를
  싣지 않는다(C3).
- **R9** "내 청구 어떻게 됐나요" 상담 콜이 월 3,900건에서 2,000건 아래로 내려간다. (intent Proposed
  outcome — 발송 후 별도로 측정하는 비즈니스 지표, 본 스펙의 직접 산출물은 아님)

## Design
### Flow
1. 사정인이 claims-core 에서 청구 상태를 변경 → claims-core 가 내부 도메인 이벤트
   `ClaimStatusChanged{claim_id, prev_status, new_status, changed_by, changed_at(UTC)}` 를 emit.
2. 새 컴포넌트(가칭 `claim-notice-dispatcher`, claims-core 부속 워커로 배치 — 별도 서비스 신설 없이
   기존 이벤트 버스 소비자로 최소화)가 이벤트를 소비:
   a. 고객의 채널별 수신 동의 상태를 조회(C4) — 동의 없음/미확인이면 발송 안 함 + R6 로그.
   b. 상태값을 brand B4 다섯 어휘로 매핑(이미 claims-core 상태값이 이 다섯 개와 1:1이라고 가정 — 아니면
      매핑 테이블 필요, "Open questions" 아님이지만 구현 시 확인 필요).
   c. 템플릿 엔진으로 채널별 메시지 생성(아래 "메시지 템플릿").
   d. notify-gw 의 기존 발송 API 를 호출(신설 아님, 기존 SMS/푸시 발송 엔드포인트 재사용) — 호출은
      service-to-service 인증(게이트웨이 JWT, secure-api-review 항목 1)을 쓰고, 요청 스키마 외 필드는
      거부(항목 2), 호출 자체가 상태 변경을 유발하지 않는 발송 트리거이지만 "상태 변경 이벤트에 대한
      side-effect 호출"이므로 감사 이벤트를 emit(항목 3) — actor=system(claim-notice-dispatcher),
      action=notify_sent, entity=claim_id, timestamp. 응답/로그에 전화번호·디바이스 토큰 전체를 남기지
      않는다(항목 4, C3).
3. 고객이 통지의 링크를 탭/클릭 → 포털 SSO 로그인(미로그인 시) → 해당 청구 상세 화면으로 랜딩. 이 경로는
   포털에 이미 있는 "청구 상세" 라우트를 재사용하고, 새 미인증 엔드포인트를 만들지 않는다(R4).

### 메시지 템플릿 (brand/UX 적용)
- SMS (문자, 90자 제한): `[회사명] ○○○ 고객님, 청구 {번호} 상태가 「{다섯 어휘 중 하나}」로
  바뀌었습니다. {다음 예정 한 줄}. 확인: {링크}` — 회사명 공식 표기(B5), 날짜 표기 불필요(상태 변경 자체를
  알리는 것이므로 생략 가능), 이모지·느낌표 없음(B7), "즉시"·"보장" 등 미확약 표현 금지(B2).
- 앱 푸시(문자수 제약 없음): 위 내용 + 상태 변경 시각(YYYY-MM-DD, 24시간제, KST — B6).
- 두 채널 모두 U2(상태별 다음 예정 문구), U5(중복 안내 금지 — 링크 한 번, 문구 한 번)를 따른다.
- 접근성(U6): 푸시 알림의 아이콘/뱃지에는 대체 텍스트를 붙이고, 상태 구분을 색상에만 의존하지 않는다
  (포털 청구 상세 화면 쪽 요구사항 — 기존 화면이 이미 U6 을 만족하는지 별도 확인 필요, 본 스펙 범위 밖).

### 야간 발송 (22:00–08:00 KST)
설계상 발송 여부를 기능 플래그로 분리한다: `night_dispatch_enabled` (기본값 off). 사정인 팀 요청대로
즉시 켤 수 있게 구조는 준비하되, 켜는 결정 자체는 "Flagged concerns" 참조 — CX 팀장 결정 전에는 off로
운영하고, 22:00–08:00 발생 이벤트는 큐에 쌓아 08:00 이후 일괄 발송한다.

## Constraints
(intent.md 그대로 + 설계 중 발견한 사항)
- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다. (intent)
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다. (intent)
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다. (intent)
- 통지 링크는 짧아야 한다(문자 90자 제한). (intent)
- 야간(22:00–08:00 KST)에도 상태 변경 즉시 보내 달라는 사정인 팀 요청이 있다. (intent — 단, 허용 여부는
  미결, "Flagged concerns" 참조)
- (설계 중 발견) claims-core 의 내부 상태값과 brand B4 다섯 어휘가 1:1로 매핑되는지 확인되지 않았다 —
  구현 전 claims-core 상태 enum 확인 필요.
- (설계 중 발견) notify-gw 발송 API 가 service-to-service 인증(게이트웨이 JWT)을 이미 요구하는지, 감사
  이벤트를 이미 emit 하는지 확인되지 않았다 — 없다면 이번 작업 범위에 추가해야 한다.

## Open questions from intent
- 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — carried forward: 컴플라이언스
  오너. (설계는 C5 "근거를 담아야 한다"에 따라 청구 번호 포함을 기본값으로 잡았으나, 확정은 오너 결정.)
- 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — carried forward: 보안 오너. ("Flagged
  concerns" 참조 — 설계는 결정 전까지 자체(퍼스트파티) 단축 링크를 기본안으로 제안.)
- 야간 발송을 허용할 것인가 — carried forward: 고객경험팀장. (설계는 `night_dispatch_enabled` 플래그로
  결정 전 기본 off, 08:00 이후 일괄 발송으로 처리.)

## Flagged concerns
1. **외부 단축 URL vs 보안/컴플라이언스 최소 노출 원칙** — intent 는 마케팅팀 요청으로 외부 단축 URL
   검토를 요구하지만, 외부 단축 URL 은 (a) 제3자 서비스에 "이 전화번호/디바이스가 이 청구 링크를
   클릭했다"는 트래픽 패턴을 노출할 수 있고 (b) 피싱 도메인으로 악용되기 쉬워 고객이 진위를 판별하기
   어렵다. 이는 compliance C1/C2(최소 노출)의 정신과 배치될 수 있다. 이 스펙은 이를 해결하지 않는다 —
   보안 오너가 결정할 사안이며(intent 의 open question), 결정 전까지 설계는 퍼스트파티 단축 링크를
   기본값으로 둔다.
2. **문자 90자 제한 vs 필수 문구 요소** — brand(고정 5어휘 유지, 과장 없는 문장), UX(U2, 상태별 다음
   예정 문구 포함), compliance(C5, 근거 명시)를 모두 지키면서 90자 안에 청구 번호 + 상태 + 다음 예정 +
   링크를 다 넣기 어려운 상태(특히 「보완요청」처럼 다음 행동이 긴 경우)가 있을 수 있다. 이 스펙은 상태별
   문구를 사전에 카피 검수해 90자를 넘는 경우 앱 푸시로 강등하거나 문구를 축약하는 규칙까지는 정하지
   않았다 — 카피 확정 시 브랜드/컴플라이언스 오너와 함께 상태별 실측이 필요하다.
3. **야간 즉시 발송 요청 vs 정책 공백** — 사정인 팀은 22:00–08:00 즉시 발송을 요청하지만, brand/UX/
   compliance 정책 문서 어디에도 발송 시간대에 대한 조항이 없다. 이 스펙은 정책 공백을 정책 위반으로
   간주하지 않고, intent 의 open question 그대로 고객경험팀장 결정에 맡긴다. 결정 전 기본값은 off(주간
   일괄 발송)로 설계했다 — 이는 사정인 팀의 요청을 지연시키는 선택이므로, 그 자체가 결정이 필요한
   트레이드오프임을 명시한다.

## Out of scope
- claims-core 의 상태 전이 규칙 변경.
- 신규 수신 동의 수집 플로우 구축(기존 동의 기록이 있다고 가정).
- 상담 콜 감소 목표(R9)의 측정/대시보드 구축 — 이 스펙은 통지 발송만 다룬다.
- 포털 청구 상세 화면 자체의 UX 개편(U3, U4, U6 기존 화면 준수 여부는 별도 검토).
- 앱 미설치·푸시 미동의 고객을 문자 채널로 자동 전환하는 로직 이상의 새 채널(이메일 등) 추가.

## Acceptance criteria
- **AC1 → R1** 상태 변경 이벤트 발생 시각부터 통지 발송 완료까지 24시간 이내인 것이 감사 로그로
  확인된다.
- **AC2 → R2** 앱 설치+푸시 동의 고객은 푸시로, 그 외 문자 동의 고객은 SMS 로, 둘 다 없는 고객은
  발송되지 않고 억제 로그가 남는 것을 테스트로 확인한다.
- **AC3 → R3** 발송된 메시지 표본을 brand(B1–B7)·UX(U2) 체크리스트로 검수해 위반이 없다.
- **AC4 → R4** 로그아웃 상태로 통지 링크에 접근하면 로그인 화면으로만 이동하고, 청구 상태·번호 등 어떤
  내용도 로그인 전 화면에 노출되지 않는다.
- **AC5 → R5** 발송 로직의 데이터 소스가 claims-core 기존 필드(전화번호/디바이스 토큰)뿐이고, 신규 PII
  수집 API/필드가 코드에 없다.
- **AC6 → R6** 동의 미기록 고객으로 상태 변경 이벤트를 발생시키면 발송되지 않고 억제 사유가 기록된다.
- **AC7 → R7** 발송된 메시지 본문에 사유 상세·금액·주민등록번호·계좌번호·전화번호 전체가 없다(자동 검사
  + 표본 수검).
- **AC8 → R8** 발송 1건당 감사 이벤트 1건 이상(actor/entity/timestamp 포함, PII 없음)이 3년 보존
  스토리지에 쓰인다.
