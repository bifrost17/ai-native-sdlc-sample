## Requirements
- **R1** 사정인이 claims-core 에서 청구 상태를 변경하면, 그 청구의 고객이 24시간 이내에 통지(문자 또는 앱 푸시, 앱 설치 여부로 채널 결정)를 받는다.
- **R2** 통지 본문은 변경된 상태를 brand B4 의 다섯 어휘(접수·심사중·보완요청·지급완료·종결) 그대로 표시하고, 어느 청구에 대한 통지인지 식별 가능한 근거와 문의 경로를 포함한다(compliance C5).
- **R3** 통지의 링크를 누르면 포털 SSO 로그인을 거친 뒤에만 해당 청구의 상세 화면이 보인다. 로그인 전에는 청구 내용이 어떤 형태로도 노출되지 않는다.
- **R4** 상태 변경 이벤트 발생부터 통지 발송까지, 그리고 통지 클릭부터 포털 진입까지의 이력이 actor·청구번호·시각(UTC) 으로 감사 기록되고 3년 보존된다(compliance C6).
- **R5** 수신 동의가 기록되지 않은 고객에게는 통지를 보내지 않는다(compliance C4).
- **R6** 존재하지 않거나 권한 없는 청구 링크에 접근하면, 유효한 청구에 접근했을 때와 동일한 응답 모양과 지연으로 처리한다(api-security S6).

## Design
- **트리거**: claims-core 의 상태변경 이벤트(사정인 액션)를 notify-gw 가 구독 — 포털/상담사 쪽에서 폴링하지 않는다. claims-core 상류 호출은 상태 변경 시 1건뿐이므로 50rps 예산(S5)에 영향 없음.
- **동의 확인**: notify-gw 가 발송 직전 claims-core 에 저장된 채널별 동의 플래그를 조회 — 플래그가 없거나 불명확하면 발송하지 않고 감사 로그에 `skipped_no_consent` 로 남긴다(C4).
- **본문 구성**: 템플릿은 `[청구번호 식별자] 상태(B4 어휘) + 문의 경로 + 포털 딥링크` 세 요소로 고정. 사과문·이모지·확약형 문구는 넣지 않는다(B1·B2·B3·B7). 상세(다음 예정 안내 등, ux U2)는 포털 화면에 싣고 통지 본문에는 최소 요소만 둔다 — 그래도 C5 가 요구하는 "근거+문의경로"는 통지 본문 자체에 있어야 하므로 본문 밖으로 밀어낼 수 없다(아래 Flagged concerns #1).
- **링크**: 포털 도메인의 클레임 상세 경로로 직접 연결(SSO 게이트 통과 전에는 청구 요약조차 렌더링하지 않음) — S1 세션 계약을 그대로 따른다. 단축 URL 여부는 미결(Flagged concerns #3).
- **감사**: notify-gw 발송 이벤트와 포털 클릭 이벤트 각각 actor(시스템/고객)·entity(청구번호)·timestamp(UTC) 로 기록, 3년 보존 테이블에 적재(C6, S3).
- **포털 화면**: 상태 표시는 U2 대로 다섯 어휘 + 상태별 "다음 예정" 한 줄(예: 보완요청 → 제출해야 할 서류 안내), 색만으로 구분하지 않고 문구 병기(U6).

## Constraints
(intent.md 원문 그대로, 이후 설계 중 발견한 것 추가)
- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다.
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다.
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다.
- 통지 링크는 짧아야 한다(문자 90자 제한) — 마케팅팀 요청으로 단축 URL 사용을 검토한다.
- 야간(22:00–08:00 KST)에도 상태 변경 즉시 보내 달라는 사정인 팀 요청이 있다.
- (발견) 통지 발송은 수신 동의가 기록된 채널에만 가능하다(C4) — claims-core 에 동의 플래그가 이미 있는지는 미확인(Flagged concerns #5).
- (발견) 상태 변경 트리거는 이벤트 구독으로 구현해 claims-core 50rps 예산(S5)을 넘기지 않는다.

## Open questions from intent
- 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — carried forward: 컴플라이언스 오너 (Flagged concerns #2).
- 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — carried forward: 보안 오너 (Flagged concerns #3).
- 야간 발송을 허용할 것인가 — carried forward: 고객경험팀장 (Flagged concerns #4).

## Out of scope
- 앱 미설치→설치 유도, 마케팅성 알림.
- 상담사가 대리 조회할 때의 본인확인 절차 변경(C7 은 기존 절차가 있다고 전제하고 이 spec 은 건드리지 않는다).
- 단축 URL 서비스 선정/계약(Flagged concerns #3 이 "예"로 결정된 뒤의 별도 작업).
- 야간 발송 유예/배치 큐잉 메커니즘 설계(Flagged concerns #4 가 "허용"으로 결정된 뒤에만 필요).

## Acceptance criteria
- **AC1 → R1** 사정인이 상태를 바꾼 시각으로부터 24시간 이내에 해당 청구 고객에게 통지가 발송된 기록이 감사 로그에 있다.
- **AC2 → R2** 발송된 통지 본문에 B4 의 다섯 어휘 중 하나, 청구 식별 근거, 문의 경로가 모두 포함되어 있다(사람 검수 또는 템플릿 린트로 확인).
- **AC3 → R3** 로그인하지 않은 상태로 통지 링크에 접근하면 청구 데이터가 응답에 없고 SSO 로그인 화면으로 이동한다.
- **AC4 → R4** 발송·클릭 이벤트가 actor·청구번호·UTC 시각으로 감사 테이블에 남아 3년 보존 정책이 걸려 있다.
- **AC5 → R5** 동의 플래그가 없는 고객 계정으로 상태를 바꿔도 통지가 발송되지 않고 `skipped_no_consent` 감사 이벤트만 남는다.
- **AC6 → R6** 존재하지 않는 청구번호와 타인의 청구번호로 링크에 접근했을 때 응답 모양과 지연이 동일하다.
