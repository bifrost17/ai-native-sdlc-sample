## Requirements
- **R1** 사정인이 청구 상태를 변경하면, 시스템은 변경 시각으로부터 24시간 이내에 고객에게 통지(문자 또는 앱 푸시 중 하나)를 발송한다.
- **R2** 통지 본문에는 변경된 청구 상태(브랜드 5개 어휘 중 하나), 마스킹된 청구 식별자, 문의 연락처, 포털의 해당 청구 화면으로 이어지는 링크가 포함된다.
- **R3** 통지의 링크를 열면 고객은 기존 포털 SSO 로그인 화면으로 이동하고, 로그인을 마치기 전에는 청구 내용(상태·금액·사유 등 어떤 항목도)이 화면에 보이지 않는다.
- **R4** 통지는 앱 푸시 수신 동의가 기록된 고객에게는 푸시로, 그렇지 않고 문자 수신 동의만 기록된 고객에게는 문자로 발송한다. 두 채널 모두 동의 상태를 확인할 수 없는 고객에게는 발송하지 않는다.
- **R5** 문자로 보내는 통지 본문은 90자 이내다(링크 포함).
- **R6** 상태 변경마다 통지 발송 시도(성공/실패, 채널, 대상 고객)를 역할·ID·청구번호·UTC 시각과 함께 기록하고 3년 보존한다.
- **R7** 통지에는 claims-core 에 이미 저장된 전화번호 외의 신규 개인정보를 수집하거나 사용하지 않는다.

## Design
- claims-core 가 청구 상태 변경 시 상태변경 이벤트를 발행한다. notify-gw 가 이를 구독해 통지를 생성·발송한다.
- 통지 문구는 브랜드 정책(B1–B7)과 UX 정책(U1–U3)을 따르는 고정 템플릿에서 생성한다: `[회사 공식명] 청구(마스킹된 식별자) 상태 변경: <5개 어휘 중 하나>. 문의 <대표번호>. 확인 <링크>`.
  - 실측 예시(문자, 상태=보완요청): `[OO보험] 청구(12-****) 상태 변경: 보완요청. 문의 1588-0000 확인 https://abc.kr/A1b2C3d4` → 71자(공백 포함, `wc -m` 실측). U2 가 요구하는 "다음 예정" 한 줄(예: "필요서류를 제출해 주세요")까지 넣으면 86자로 늘어 90자 한도에 4자 여유만 남는다 — 다른 상태·더 긴 안내문에서는 초과할 수 있다. 이 계산의 전제(회사명 약칭 길이, URL 길이)는 아래 「Flagged concerns」#1 로 올린다.
- 링크는 청구ID 를 직접 노출하지 않는 단기 토큰 딥링크 리졸버(신규 엔드포인트, notify-gw 또는 포털 배포)가 발급한다. 리졸버는 secure-api-review 의 인증(포털 SSO 세션 또는 게이트웨이 JWT)·입력 검증·감사 이벤트·PII 비로그 요건을 적용받는다. 토큰은 로그인 완료 전까지 청구 내용을 반환하지 않는다.
- 채널 결정 로직: claims-core/고객 프로필에 기록된 푸시·문자 수신 동의 플래그를 조회해 우선순위(푸시 > 문자)로 채널을 고른다. 동의 플래그가 없거나 조회 실패 시 발송하지 않고 실패로 기록한다(R6).
- 발송·확인 이력은 compliance C6 형식(역할·ID·청구번호·UTC)으로 감사 로그에 남긴다.
- 야간(22:00–08:00 KST) 발송 여부는 발송 게이트를 설정 가능한 플래그로 설계하되, 기본값은 정책 결정(「Flagged concerns」#4) 이후 정한다.

## Constraints
- 기존 포털 SSO 로그인만 사용한다. 통지 링크는 로그인 없이 청구 내용을 보여주지 않는다. (intent)
- 신규 PII 수집 없음 — claims-core 에 이미 있는 전화번호만 사용한다. (intent)
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다. (intent)
- 문자 통지는 90자 이내여야 한다. (intent)
- 마케팅팀이 단축 URL 사용을 요청했으나 채택 여부는 미정이다. (intent, 아래 미결)
- 사정인 팀이 야간(22:00–08:00 KST) 즉시 발송을 요청했다. (intent, 아래 미결)
- (설계 중 발견) 딥링크 리졸버 엔드포인트는 secure-api-review 의 인증·입력검증·감사·PII 비로그 요건을 모두 적용받는다.
- (설계 중 발견) 통지 본문의 청구 식별자는 마스킹한다 — compliance C1 이 연락처·계좌·주민번호에 요구하는 최소 노출 원칙을 청구 식별자에도 준용했다(단, C1 이 청구번호를 직접 지정하지는 않는다 — 「Flagged concerns」#3 참고).

## Open questions from intent
- 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — carried forward: 컴플라이언스 오너. 이 spec 은 잠정적으로 마스킹된 식별자(예: 뒤 2~4자리만)로 설계했으나 확정은 아니다. 「Flagged concerns」#3.
- 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — carried forward: 보안 오너. 「Flagged concerns」#2.
- 야간 발송을 허용할 것인가 — carried forward: 고객경험팀장. 「Flagged concerns」#4.

## Out of scope
- 상담사·사정인이 통지 문구를 수동으로 편집하는 기능.
- 청구 상태 조회 화면 자체의 재설계(기존 포털 화면은 그대로 두고, 통지에서 그 화면으로 연결만 한다).
- 이메일 채널 — intent 는 문자·푸시만 요구한다.
- 단축 URL 서비스 선정/계약 — 채택이 결정되면 별도 spec.

## Acceptance criteria
- **AC1 → R1** 상태 변경 이벤트 발생 시각과 통지 발송 완료 시각의 차이가 24시간 이하임을 감사 로그로 확인할 수 있다.
- **AC2 → R2** 발송된 통지 샘플에 상태(5개 어휘 중 하나)·마스킹된 청구 식별자·문의 연락처·링크가 모두 존재한다.
- **AC3 → R3** 로그인하지 않은 상태로 통지 링크를 열면 청구 상세 데이터가 응답/화면 어디에도 포함되지 않고, 로그인 페이지로만 이동한다.
- **AC4 → R4** 푸시 동의만 있는 고객·문자 동의만 있는 고객·둘 다 없는 고객 세 케이스에서 각각 푸시 발송·문자 발송·미발송(+실패 기록)이 일어난다.
- **AC5 → R5** 발송된 모든 문자 통지 본문의 문자 수(`wc -m` 또는 동등 계산)가 90 이하다.
- **AC6 → R6** 임의 상태 변경 1건에 대해 감사 로그에서 역할·ID·청구번호·UTC 시각·발송 성공여부를 모두 조회할 수 있고, 3년 보존 설정이 되어 있다.
- **AC7 → R7** 통지 발송 코드 경로에서 claims-core 기존 전화번호 필드 외의 신규 개인정보 입력·저장 지점이 없다.
