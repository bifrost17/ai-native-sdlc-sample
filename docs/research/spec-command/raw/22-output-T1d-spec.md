## Requirements
- **R1** 사정인이 claims-core 에서 청구 상태를 바꾸면, 해당 청구의 고객에게 24시간 이내에 SMS 또는 앱
  푸시 통지가 발송된다(단, C4 — 수신 동의가 기록된 채널이 있을 때만; 동의 상태를 확인할 수 없으면
  발송하지 않는다).
- **R2** 통지 문구는 고객이 관찰 가능한 형태로: brand B4 다섯 어휘 중 하나로 바뀐 상태를 명시하고,
  어느 청구인지 알 수 있는 마스킹된 참조(예: 청구번호 뒤 4자리)를 포함하고, 문의 경로(전화번호 등)를
  포함한다(C5). 문자 통지는 전체 90자 이하다.
- **R3** 통지의 링크를 탭/클릭하면 고객은 포털 기존 SSO 로그인 화면(미로그인 시) 또는 로그인 상태를
  거쳐 해당 청구의 상태 화면으로 한 번에 이동한다. 로그인 전에는 청구 상세(상태·사유·금액 등)가
  어떤 형태로도 노출되지 않는다.
- **R4** 포털의 청구 상태 화면은 brand B4 다섯 어휘와 ux U2 의 "다음 예정" 한 줄을 상태마다 표시한다.
- **R5** 모든 통지 발송 시도(성공/실패/미발송)와 통지 링크를 통한 조회는 누가·무엇을·언제(UTC) 로
  기록되고 3년 보존된다(C6). 사정인의 상태 변경 자체도 actor·action·entity·timestamp 로 audit 이벤트가
  남는다(S3).
- **R6** 딥링크 토큰은 1회용·단기 만료이며 추측 불가능하고, 존재하지 않거나 권한 없는 토큰에 대해
  같은 응답과 같은 지연을 준다(S6).

## Design
- claims-core 가 상태 변경 시 `claim.status_changed` 이벤트를 발행한다(신규 또는 기존 이벤트 버스 확장 —
  구현 단계에서 확정). notify-gw 가 이를 구독해 고객 채널(consent 기록 기준: SMS 또는 앱 푸시)로 통지를
  만든다.
- 통지 본문의 링크는 청구번호·상태 등 PII/상세를 담지 않는 불투명 1회용 토큰
  (`https://<portal-domain>/n/<opaque-token>`)이다. 포털이 토큰을 받으면: 미로그인 시 SSO 로그인으로
  보내고, 로그인 후 토큰을 서버측에서 청구 ID 로 교환해 해당 청구 화면으로 리다이렉트한다. 토큰은
  단기 만료(예: 72시간) 후 무효화된다.
- SMS 본문은 자체 도메인 단축 링크(`claim.example.kr/n/...`, 위 예시)를 사용한다. 아래 "숫자 제약 검증"
  에서 보듯 자체 도메인 링크로도 90자 제약을 지킬 수 있으므로, 외부 단축 URL 서비스는 길이상
  필수는 아니다 — 다만 마케팅팀이 별도 이유(추적 등)로 요청했으므로 이 판단은 spec 이 대신 내리지
  않고 Flagged concerns 로 넘긴다.
- 포털 상태 화면(R4)은 기존 화면에 U2 "다음 예정" 한 줄을 추가하는 정도로 확장한다. SMS/푸시 본문에는
  "다음 예정" 상세를 넣지 않고 포털 화면에서만 보여준다(아래 Flagged concerns #1 참고).
- 감사 로그(R5)는 기존 audit 이벤트 파이프라인에 `notification.sent`/`notification.skipped`/
  `link.redeemed` 이벤트 타입을 추가하는 형태로 설계한다. PII(전화번호 전체 등)는 로그에 넣지 않고
  내부 고객 ID·청구 ID만 사용한다(C3).

### 숫자 제약 검증 (문자 90자)
예시 문구로 실제 세어 확인함(세지 않음 아님):
"○○○ 고객님, 청구(1234) 상태가 보완요청으로 바뀌었습니다. https://claim.example.kr/n/abc123 문의: 1588-0000"
→ 85자. 90자 이내다. (상태 어휘·마스킹된 청구 참조·자체 도메인 링크·문의 경로를 모두 포함한 채로 여유
5자.) 단, 여기에 U2 의 "다음 예정" 한 줄(예: " 다음: 서류제출필요", 약 10자)을 더하면 95자로 90자를
넘는다 — 이것이 Flagged concerns #1 이다.

## Constraints
(intent.md 원문 그대로 재기재 + 발견분 추가)
- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다. → R3, Design 의
  불투명 토큰으로 만족.
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다. → 새 필드 추가 없음.
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다. → R2, brand/compliance 스킬 적용.
- 통지 링크는 짧아야 한다(문자 90자 제한) — 단축 URL 사용은 검토 중. → 위 "숫자 제약 검증" 참고,
  Flagged concerns #3.
- 야간(22:00–08:00 KST)에도 상태 변경 즉시 보내 달라는 요청이 있다. → Flagged concerns #2, 정책
  근거 없음.
- (발견) claims-core→notify-gw 이벤트, 포털 토큰 교환 엔드포인트는 secure-api-review 의 S1/S2/S3/S6
  을 만족해야 한다.
- (발견) 포털의 토큰 교환이 claims-core 를 호출해 청구 상세를 가져온다면 S5(상류 50rps 한도)에 걸린다
  — Flagged concerns #4.

## Open questions from intent
- 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — **answered**: 전체
  청구번호는 안 되고, C1 이 허용하는 마스킹(뒤 4자리 등)만 가능. R2·Design 반영.
- 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — **carried forward: 보안 오너**. 길이
  제약만으로는 자체 도메인으로 충분함을 확인했으나(위 검증), 외부 단축 URL 사용 여부 자체는 정책
  공백이라 결정을 넘긴다(Flagged concerns #3).
- 야간 발송을 허용할 것인가 — **carried forward: 고객경험팀장** (intent 가 지정한 결정자 그대로).
  정책 문서 어디에도 발송 시간대(quiet hours) 조항이 없다(Flagged concerns #2).

## Out of scope
- 통지 채널 확장(이메일 등) — intent 는 SMS/앱 푸시만 언급.
- 상담사/사정인 화면의 변경 — intent 의 대상은 고객 통지·고객 포털 화면이다.
- 동의 수집 UI/플로우 자체(동의가 없으면 안 보낸다는 것만 요구, 동의 획득 경로는 별도 트랙).
- 야간 발송·단축 URL 여부의 최종 결정 — Flagged concerns #2, #3 의 결정자가 정한다.

## Acceptance criteria
- **AC1 → R1** 상태 변경 후 24시간 이내에, 동의가 기록된 채널로만 통지가 발송된 로그가 남는다.
  동의 미기록 청구는 발송 로그 없이 `notification.skipped` 로 남는다.
- **AC2 → R2** 발송된 통지 문구가 90자 이하이고, brand B4 다섯 어휘 중 하나·마스킹된 청구 참조·문의
  경로를 포함한다(자동 검사 가능한 3항목).
- **AC3 → R3** 로그인하지 않은 상태에서 통지 링크를 열면 청구 상세가 응답에 전혀 포함되지 않고 SSO
  로그인 화면으로 리다이렉트되며, 로그인 후 해당 청구 화면에 도달한다.
- **AC4 → R4** 포털 상태 화면에 다섯 어휘 중 현재 상태와 "다음 예정" 한 줄이 표시된다.
- **AC5 → R5** 통지 발송·링크 사용·상태 변경 각각에 대해 actor·entity(청구 ID)·timestamp(UTC) 가 있는
  audit 레코드가 존재하고, PII 전체값이 로그에 없다.
- **AC6 → R6** 만료되었거나 존재하지 않는 토큰으로 접근 시, 실제 존재하는 청구의 토큰과 응답 모양·지연이
  구분되지 않는다.
