## Problem (intent 그대로)
청구 상태가 바뀌어도 고객이 스스로 포털에 들어오지 않으면 알 수 없다. "내 청구 어떻게 됐나요" 상담 콜이
월 3,900건, 상태 변경 후 고객 인지까지 평균 2.7일 걸린다.

## Requirements
- R1. 사정인이 청구 상태를 변경하면 해당 청구의 고객은 24시간 안에 문자 또는 앱 푸시로 통지를 받는다.
- R2. 통지 본문에는 어느 청구의 어떤 상태 변경인지(근거)와 문의 경로가 포함된다(compliance C5).
- R3. 통지의 링크를 누르면 고객은 포털 SSO 로그인 화면으로 이동하고, 로그인 후에만 해당 청구의 상태
  화면으로 이동한다. 로그인 전에는 청구 내용이 어떤 형태로도 드러나지 않는다(intent 제약,
  compliance C1/C2).
- R4. 상태 화면·통지 문구는 brand B4 의 다섯 상태 어휘(접수·심사중·보완요청·지급완료·종결)만 쓰고,
  각 상태에 ux U2 의 「다음 예정」 한 줄을 붙인다.
- R5. 통지 발송 이력과 딥링크 접근 이력은 역할/ID·청구 번호·UTC 시각으로 기록하고 3년 보존한다
  (compliance C6, secure-api-review S3).
- R6. 통지는 연락처에 대한 수신 동의가 기록으로 확인된 경우에만 보내고, 확인할 수 없으면 보내지
  않는다(compliance C4).
- R7. 새 PII 는 수집하지 않는다 — claims-core 에 이미 있는 전화번호만 쓴다(intent 제약).

## Design
1. **트리거**: claims-core 가 상태 변경 시 이벤트(웹훅 또는 큐 발행)를 알림 서비스로 보낸다. 알림
   서비스가 claims-core 를 폴링하지 않는다 — 이 경로는 S5(claims-core 50 rps 상류 예산)를 소비하지
   않는다는 전제다 (Flagged concerns #5).
2. **발송**: 알림 서비스가 고객의 채널(SMS 전화번호 또는 앱 푸시 토큰)과 동의 상태(C4)를 확인한 뒤
   notify-gw 로 SMS 또는 푸시를 보낸다. 동의 미확인 시 미발송.
3. **문구 조립**: 상태별 템플릿에서 B4 상태 어휘, U2 다음 예정 한 줄, C5 근거(청구 번호·상태)와 문의
   경로를 채운다. 어조는 B1–B3, 표기는 B6–B7 을 따른다.
4. **딥링크**: 알림에는 청구 내용을 담지 않는 서명된 단기 토큰 링크만 싣는다. `GET
   /notify/redirect?token=...` 는:
   - 토큰을 청구 ID 로 교환하기 전에 포털 SSO 로그인을 요구한다(S1 — 세션만 읽으므로 org note 충족).
   - 로그인 후 `/claims/{id}` 로 리다이렉트한다.
   - 존재하지 않거나 권한 없는 토큰은 존재하는 토큰과 같은 응답·지연을 준다(S6, 열거 방지).
   - 리다이렉트 성공/실패를 actor·action·entity(청구 번호)·timestamp(UTC) 로 audit 기록한다(S3, C6).
5. **상태 화면**: 기존 포털 청구 화면에 U2 「다음 예정」 한 줄을 추가한다. 별도 신규 조회 API는 없다 —
   기존 청구 상세 응답 필드를 그대로 쓴다(C2, 필드 추가 없음이므로 근거 조항 불필요).

## Constraints (intent 그대로 + 추가)
- 기존 포털 SSO 로만 인증. 통지 링크는 로그인 없이 청구 내용을 보여주지 않는다.
- 새 PII 수집 없음, claims-core 기존 전화번호만 사용.
- 통지 문구는 브랜드·컴플라이언스 정책을 따른다.
- 통지 링크는 문자 90자 제한 안에 들어가야 한다.
- 사정인 팀은 22:00–08:00 야간에도 상태 변경 즉시 발송을 요청했다.
- (추가) 알림 서비스는 claims-core 를 폴링하지 않고 이벤트 구독으로만 동작한다(S5 보호).
- (추가) 딥링크 토큰은 단기 유효(제안: 24시간)하고 1회 교환 후 무효화한다 — claims-core/notify-gw
  구현팀 확인 필요(미확인, 아래 #4 아님, 설계 세부사항이라 별도 확인 항목으로 둠).

## Open questions from intent
1. 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 —
   **answered**: 예. compliance C3 은 청구 번호를 PII 로 보지 않고 식별자로 허용하며, C5 는 오히려
   통지 본문에 「어느 청구」 근거를 요구한다. 단 사유 상세·금액 등 상태 이외의 민감 정보는 넣지 않는다.
2. 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 —
   **carried forward: 보안 오너** (Flagged concerns #2).
3. 야간 발송을 허용할 것인가 —
   **carried forward: 고객경험팀장** (Flagged concerns #3).

## 요약 (우려 먼저)
정책 5건을 걸었고, 그중 3건이 열려 있다: (1) SMS 90자와 brand/compliance/ux 문구 요건이 동시에
충족 불가(충돌, 3개 오너), (2) 단축 URL 가부(공백, 보안 오너), (3) 야간 발송 가부(공백,
고객경험팀장). 나머지는 미확인 1건(동의 기록 범위)과 추정 1건(토큰 수명)이다. 요구·설계는 위 다섯
항목이 결정되기 전에도 엔지니어링에 넘길 수 있는 수준으로 정리했으나, 문구 최종본은 항목 1이 풀려야
확정된다.
