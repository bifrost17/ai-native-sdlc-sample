## Problem (carried from intent)
청구 상태 조회는 고객이 포털에 직접 들어와야만 확인할 수 있다. 상태 변경 후 고객 인지까지 평균 2.7일이
걸리고, "내 청구 어떻게 됐나요" 상담 콜이 월 3,900건(전체의 31%) 발생한다. 「보완요청」 상태에서는 서류
제출까지 평균 6일이 추가로 걸린다.

## Requirements
1. 사정인이 청구 상태를 변경하면 24시간 이내에 고객에게 통지(SMS 또는 앱 푸시)를 발송한다.
2. 통지는 상태 변경 건(어느 청구, 어떤 상태)을 특정할 수 있는 정보와 문의 경로를 포함한다.
3. 통지의 링크는 포털 SSO 로그인 후에만 해당 청구 화면을 보여준다 — 로그인 없이 청구 내용이 노출되지
   않는다.
4. 통지에 쓰이는 상태 어휘는 접수·심사중·보완요청·지급완료·종결 다섯 가지로 고정한다.
5. 통지 발송 이력(누가 트리거했는지, 어느 청구, 언제)을 감사 로그로 남긴다.
6. 새 PII를 수집하지 않는다 — claims-core 에 이미 있는 연락처만 사용한다.

## Design
- claims-core 가 청구 상태 변경 이벤트를 발행하면, notify-gw 가 이를 구독해 SMS/푸시를 발송한다.
- claims-core → notify-gw 이벤트 수신 엔드포인트는 게이트웨이 JWT 인증을 요구하고(secure-api-review
  항목 1), 요청 바디를 스키마로 검증하며(항목 2), 상태 변경 감사 이벤트를 actor·action·entity·timestamp
  로 남긴다(항목 3, compliance C6과 겹침). PII 태그 필드(연락처 등)는 로그·오류 메시지에 남기지 않는다
  (항목 4, compliance C3과 겹침).
- 통지 문면(초안, 90자 이내 확인 — 아래 「수치 제약 확인」 참조):
  `청구 {청구번호} {상태}. 확인 {딥링크} 문의 {대표번호}`
  - 상태 어휘는 brand B4 고정 다섯 개 중 하나.
  - 딥링크는 포털 SSO 로그인 페이지를 거쳐 해당 청구 화면으로 리다이렉트(로그인 전 청구 내용 비노출).
  - 「보완요청」 상태일 때는 포털 화면(딥링크 도달 후)에서 ux U2 에 따라 "다음 예정"(제출 서류 안내)을
    한 줄 보여준다 — SMS 본문 자체에는 넣지 않는다(길이·compliance C5의 "사유 상세" 과다 노출 방지 균형).
- 포털 청구 상세 화면의 상태 표시는 brand B4 다섯 어휘 그대로 쓰고, ux U2 에 따라 상태별 "다음 예정"
  한 줄을 덧붙인다.

## 수치 제약 확인 (문자 90자)
아래 초안 문구를 실제로 세었다(한글 1자 = 1로 계산):

`청구 1234567 보완요청. 확인 https://ex.kr/c/AbC1 문의 1588-0000`

→ 53자. 90자 제한 안에 들어오며, 청구 식별(compliance C5), 상태 어휘(brand B4), 문의 경로(compliance
C5)를 모두 포함한다. "다음 예정"(ux U2)은 SMS 본문이 아니라 딥링크 도달 후 포털 화면에 둔다 — U2 자체는
"상태 표시" 문맥의 요구이며 SMS 요약 통지까지 적용된다고 단정하지 않았다(아래 Flagged concerns #1 참조).

## Constraints (carried from intent + discovered here)
- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다.
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다.
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다.
- 통지 링크는 짧아야 한다(문자 90자 제한) — 마케팅팀 요청으로 단축 URL 사용을 검토한다.
- 야간(22:00–08:00 KST)에도 상태 변경 즉시 보내 달라는 사정인 팀 요청이 있다.
- (discovered) compliance C4: 통지는 수신 동의가 기록된 채널로만 보낸다. 동의 상태를 확인하지 못하면
  보내지 않는다 — claims-core 연락처에 채널별(SMS/푸시) 동의 상태가 있는지 확인 필요(아래 미확인 #2).
- (discovered) compliance C6/C7: 통지 발송 이력은 3년 보존하고 누가·무엇을·언제를 남긴다. 대리 조회는
  본인확인 기록이 있을 때만 — 이 기능은 고객 본인 알림이라 C7 대리조회 요건은 직접 해당하지 않는다.

## Open questions from intent
1. 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — **carried forward
   (컴플라이언스 오너)**. compliance C5는 통지 본문에 "어느 청구"인지 근거를 요구하고, C1은 주민번호·
   계좌번호·연락처 전체만 금지해 청구번호는 대상이 아니다 — 정책 문면상으로는 청구번호 포함이 C5를
   만족시키는 쪽에 가깝지만, intent가 이 질문을 컴플라이언스 오너에게 명시적으로 넘겼으므로 이 spec은
   대신 결정하지 않고 그대로 넘긴다.
2. 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — **carried forward (보안 오너)**. 아래
   Flagged concerns #2 참조 — 이 저장소의 정책 스킬(brand/compliance/ux) 중 외부 단축 URL 사용을 다루는
   조항이 없다(공백).
3. 야간 발송을 허용할 것인가 — **carried forward (고객경험팀장)**. 아래 Flagged concerns #3 참조.

## What this spec does not cover
- plan.md, 구현 순서, 코드 변경 — 이 spec 승인 후 plan mode에서 다룬다.
- 단축 URL 사용 여부, 야간 발송 허용 여부, 앱 푸시에 대한 C4 적용 여부의 최종 결정 — 위 표의 결정자가
  정한다.
