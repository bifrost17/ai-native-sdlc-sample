## Requirements
- R1. 사정인이 claims-core 에서 청구 상태를 바꾸면, 그 청구의 고객에게 24시간 이내에 SMS 또는 앱 푸시
  통지가 발송된다.
- R2. 통지는 다섯 개 상태 어휘(접수·심사중·보완요청·지급완료·종결) 중 바뀐 상태와, 그 상태의 "다음 예정"
  한 줄, 문의 경로를 포함한다.
- R3. 통지의 링크를 탭하면 포털 SSO 로그인(미로그인 시)을 거쳐 해당 청구 상세 화면으로 바로 이동한다.
  로그인 전에는 링크만으로 청구 내용이 보이지 않는다.
- R4. 통지는 고객이 해당 채널(SMS 또는 푸시)에 대해 수신 동의가 기록되어 있을 때만 발송된다. 동의 상태를
  확인할 수 없으면 발송하지 않는다.
- R5. 모든 통지 발송 시도(성공/미발송)와 통지 링크를 통한 청구 조회는 누가·무엇을·언제 형식으로 3년간
  감사 로그에 남는다.
- R6. 통지 본문·통지 로그·오류 메시지 어디에도 주민등록번호·계좌번호·전화번호 전체·심사 사유 상세·금액
  산정 근거는 실리지 않는다.

## Design
- **트리거**: claims-core 의 상태 변경이 이벤트(claim-status-changed: claim_id, new_status,
  changed_at)를 발행한다. 새 경로가 claims-core 를 폴링하지 않으므로 S5(50rps 상류 예산)에 새 부하를
  더하지 않는다.
- **통지 서비스(신규, notify-gw 뒤에 붙는 내부 컴포넌트)**: 이벤트를 구독해 (1) 고객의 채널별 수신 동의를
  조회하고 (2) 동의가 있으면 딥링크 토큰을 발급해 (3) notify-gw 로 SMS/푸시 발송을 요청한다.
- **딥링크**: `https://<portal>/c/<opaque-token>` 형태. 토큰은 청구 번호나 고객 식별자를 값 자체에
  담지 않는 opaque 값(서버 조회용)으로, 미로그인 상태에서는 SSO 로그인 화면으로만 리다이렉트하고
  로그인 후 세션(고객 역할 키)으로 토큰을 청구로 해석해 상세 화면을 보여준다. 이는 intent 제약("링크는
  로그인 없이 청구 내용을 보여 주면 안 된다")과 C1(연락처·식별자 전체 노출 금지), S6(존재하지 않는/권한
  없는 청구 번호에 동일 응답)을 함께 만족한다.
- **엔드포인트(신규)**: `POST /internal/notify/claim-status`(이벤트 컨슈머→통지 서비스, 서비스 간 인증,
  S1 게이트웨이 JWT), `GET /c/{token}`(포털, 세션 필요 — S1 은 포털이 세션으로 처리), 두 경로 모두 상태
  변경 엔드포인트이므로 S3 audit 이벤트(actor=system/customer, action, entity=claim_id, timestamp)를
  emit. 요청 스키마는 OpenAPI 로 정의하고 미지정 필드는 거부(S2).
- **본문 어휘**: 상태 다섯 개(B4)에 각 상태의 "다음 예정" 한 줄을 U2 대로 미리 정의해 둔다(예: 보완요청
  → "제출해야 할 서류를 확인해 주세요", 지급완료 → 다음 행동 없음 문구 생략 가능 — U2 는 "다음 예정"이
  있을 때 붙이라는 것이므로 종결 상태의 안내는 열린 질문으로 아래에 남긴다).
- **채널**: 앱 설치 고객은 푸시(글자수 제약 없음, 링크 자유), 미설치 고객은 SMS(90자 제약, 아래 §문자
  90자 참조).
- **보관**: 통지 이력·조회 이력은 청구 번호(내부 ID) 로만 남기고, 전화번호 등 연락처는 이력에 저장하지
  않는다(C3).

### 문자 90자 — 실측
아래 문구로 실제로 세어 봤다(공백·구두점 포함, 링크는 예시 도메인/토큰 길이):

> `OOO 고객님, 청구 1234567 상태: 보완요청. 필요 서류를 제출해 주세요. 확인 https://acme.kr/c/AbC12345 문의 1588-0000`

88자 (직접 카운트). 90자 제약은 지키지만 여유가 2자뿐이다. 이 여유는 다음 조건에서 쉽게 깨진다:
- 청구 번호가 7자리보다 길어지면(사내 채번 규칙 미확인),
- 도메인이 `acme.kr` 보다 길어지거나 마케팅팀이 제안한 외부 단축 URL을 쓰지 않으면(도메인 길이는
  아직 확정 안 됨),
- "다음 예정" 문구가 보완요청보다 긴 상태(예: 종결 사유 안내가 필요한 경우)가 생기면.

C5(근거+문의 경로 필수)와 U2(다음 예정 한 줄 필수)를 모두 넣고 B4 어휘를 그대로 쓰면 88자가 사실상
하한에 가깝다 — 아래 「Flagged concerns」#1 로 올린다.

## Constraints
(intent.md 원문 그대로 재기재, 이후 설계 중 발견한 것 추가)
- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다. → 위 딥링크
  설계로 반영.
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다.
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다.
- 통지 링크는 짧아야 한다(문자 90자 제한) — 마케팅팀 요청으로 단축 URL 사용을 검토한다.
- 야간(22:00–08:00 KST)에도 상태 변경 즉시 보내 달라는 사정인 팀 요청이 있다.
- (설계 중 발견) 통지 발송 전 채널별 수신 동의 기록 조회가 필요하다(C4) — 현재 claims-core/포털에
  이 동의 기록이 존재하는지 미확인(아래 Flagged concerns #4).
- (설계 중 발견) 딥링크 토큰은 청구 번호를 값에 노출하지 않는 opaque 토큰이어야 한다(C1, S6).

## Open questions from intent
- 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — **carried forward: 컴플라이언스
  오너.** C1 은 "연락처 전체"를 금지할 뿐 청구 번호 노출은 명시적으로 다루지 않는다(공백) — 위 실측
  문구는 청구 번호를 포함해 88자로 넣었지만, 이 자체가 허용되는지는 정책 공백이라 오너 결정이 필요하다.
- 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — **carried forward: 보안 오너.** 아래
  Flagged concerns #2.
- 야간 발송을 허용할 것인가 — **carried forward: 고객경험팀장.** 아래 Flagged concerns #3.

## Out of scope
- 상담사·사정인 화면에서의 상태 변경 UI 자체(기존 CS 시스템 기능, 이 spec 은 상태 변경 "이후"의 통지만
  다룬다).
- 이메일 채널(intent 는 문자·푸시만 요구).
- 수신 동의를 새로 수집하는 흐름(동의 UI/API 신설은 범위 밖 — 기존 기록 유무를 전제로 하며, 없다면
  Flagged concerns #4 의 결정에 따라 별도 intent 가 필요할 수 있다).

## Acceptance criteria
- AC1 → R1: 사정인이 상태를 바꾼 시각부터 24시간 이내에 해당 청구 고객에게 SMS 또는 푸시가 발송된
  기록이 감사 로그에 있다.
- AC2 → R2: 발송된 통지 본문에 다섯 어휘 중 하나, 그 상태의 다음 예정 한 줄, 문의 경로(전화번호 등)가
  모두 포함돼 있다.
- AC3 → R3: 로그인하지 않은 브라우저/기기에서 통지 링크를 열면 청구 내용이 아닌 SSO 로그인 화면이
  뜨고, 로그인 후에만 해당 청구 상세로 이동한다.
- AC4 → R4: 해당 채널에 수신 동의 기록이 없는 고객에게는 발송 시도 자체가 기록되지 않거나
  "미발송(동의없음)"으로만 기록된다.
- AC5 → R5: 통지 발송 이력과 딥링크를 통한 조회 이력이 각각 역할/주체·청구 번호·시각으로 3년 보존
  로그에 남아 있다.
- AC6 → R6: 통지 본문·로그·오류 메시지 샘플을 감사했을 때 주민등록번호·계좌번호·전화번호 전체·사유
  상세·금액 산정 근거가 어디에도 없다.
