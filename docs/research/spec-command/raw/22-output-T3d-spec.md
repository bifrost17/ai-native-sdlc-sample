## Requirements
- **R1** 사정인이 청구 상태를 변경하면, 해당 청구의 고객은 24시간 이내에 SMS 또는 앱 푸시로 통지를 받는다.
- **R2** 통지 문구의 상태 명칭은 brand B4 의 다섯 어휘(접수·심사중·보완요청·지급완료·종결) 중 하나이며, 동의어를 쓰지 않는다.
- **R3** 통지에는 그 상태에 대한 「다음 예정」 한 줄(ux U2)과 문의 경로(compliance C5)가 포함된다.
- **R4** 통지의 딥링크를 누르면 고객은 기존 포털 SSO 로그인 화면으로 이동하고, 로그인 후에만 해당 청구의 상태 화면이 보인다. 로그인 없이 청구 내용이 노출되는 경로는 없다.
- **R5** 통지는 claims-core 에 이미 있는 전화번호/푸시 토큰만 사용한다 — 새 PII 수집 항목은 없다.
- **R6** 채널(SMS/푸시)별로 수신 동의가 기록된 고객에게만 발송한다. 동의 상태를 확인할 수 없으면 발송하지 않는다(compliance C4).
- **R7** 모든 발송 시도(성공·스킵 포함)는 청구 번호·채널·발송결과·시각(UTC)으로 3년 보존 기록된다(compliance C6).
- **R8** SMS 본문은 90자 이내다(마케팅팀 요청 제약, intent 원문).

## Design
- claims-core 의 상태변경 이벤트(기존에 존재하는 상태 변경 커밋 지점)에 발송 트리거를 구독시킨다 — 새 폴링·새 조회 엔드포인트를 만들지 않는다(S5 상류 호출 예산에 영향 없음).
- 발송 서비스가 이벤트를 받으면: (1) 고객의 채널별 동의 상태 조회 → 미동의/미확인이면 스킵 기록만 남기고 종료(R6), (2) brand B4 어휘 + ux U2 다음-예정 템플릿으로 본문 구성, (3) 기존 notify-gw 로 SMS/푸시 발송, (4) 발송 결과를 audit 이력에 기록(R7).
- 딥링크는 새 인증 우회 경로를 만들지 않고, 기존 포털의 청구 상세 화면 URL(SSO 세션 필요)을 그대로 가리킨다. 앱 미설치 고객(SMS 전용)도 동일하게 로그인 화면을 거친다.
- 채널 선택 우선순위: 앱 설치 및 푸시 동의가 있으면 푸시, 없으면 SMS 동의를 확인해 SMS. 두 채널 모두 미동의면 발송하지 않는다.

## Constraints
(intent.md 원문 그대로)
- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다.
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다.
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다.
- 통지 링크는 짧아야 한다(문자 90자 제한) — 마케팅팀 요청으로 단축 URL 사용을 검토한다.
- 야간(22:00–08:00 KST)에도 상태 변경 즉시 보내 달라는 사정인 팀 요청이 있다.

(설계 중 추가로 발견한 제약)
- **discovered-1** S5(상류 호출 예산): 발송 트리거는 claims-core 의 상태변경 이벤트 구독이어야 하며, 딥링크 클릭 이후 청구 조회는 포털이 이미 쓰는 기존 조회 경로를 재사용한다 — 이 기능이 추가하는 신규 claims-core 호출은 없다.
- **discovered-2** C2(응답 필드 허용 목록): 통지 본문에 넣는 필드는 청구 번호·상태명·다음 예정 문구·문의 경로로 한정한다. 사유 상세·금액은 넣지 않는다(C5).
- **discovered-3** C6(보존): 발송 로그의 보존 기간 3년은 이 기능이 새로 만드는 저장소이므로 기존 audit 저장소 스키마에 맞출지 신규 테이블을 둘지는 구현 단계(plan) 결정 사항이다.

## Open questions from intent
- 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — **carried forward: 컴플라이언스 오너**. compliance C5 는 통지 본문에 "근거(어느 청구, 어느 상태 변경)"를 적으라고 요구하므로 청구 번호 자체는 C5 취지에 부합하는 방향이지만, C1 이 열거하는 PII(주민번호·계좌번호·전화번호 전체)에 청구 번호는 없다. 다만 "휴대전화를 습득/공유하는 제3자에게 청구 존재를 노출"하는 위험은 어느 조항도 다루지 않는 공백이라 최종 판단은 컴플라이언스 오너에게 넘긴다(아래 Flagged concerns #3).
- 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — **carried forward: 보안 오너**. 근거 조항 없음(아래 Flagged concerns #2).
- 야간 발송을 허용할 것인가 — **carried forward: 고객경험팀장**. 브랜드·컴플라이언스·UX·API보안 정책 어디에도 발송 시간대 제약이 없다(아래 Flagged concerns #4).

## Flagged concerns
우려를 정책 결정자에게 조항 번호와 함께 넘긴다. 결정 칸은 비워 둔다.

| # | 우려 | 종류 | 근거 조항 | 결정자 | 결정 |
|---|---|---|---|---|---|
| 1 | SMS 90자 제한 안에 상태명(B4)·다음 예정(U2)·근거+문의 경로(C5)·딥링크를 모두 넣을 수 없다 | 충돌 | brand B4 · ux U2 · compliance C5 · intent 의 "문자 90자 제한" | 브랜드 오너 · 컴플라이언스 오너 | (비움) |
| 2 | 외부 단축 URL 서비스를 딥링크에 써도 되는가 | 공백 | 조항 없음(C1/C2 는 단축 URL 을 다루지 않는다) | 보안 오너 | (비움) |
| 3 | 앱 미설치 고객 SMS 본문에 청구 번호를 실어도 되는가 — 휴대전화를 제3자가 보는 경우의 노출 위험 | 공백 | 조항 없음(C1 의 PII 열거에 청구 번호 없음, C5 는 "근거" 포함을 요구할 뿐 위험을 다루지 않음) | 컴플라이언스 오너 | (비움) |
| 4 | 야간(22:00–08:00 KST) 즉시 발송을 허용할 것인가 | 공백 | 조항 없음(brand/compliance/ux/api-security 어디에도 발송 시간대 조항 없음) | 고객경험팀장 | (비움) |
| 5 | 발송 로그 3년 보존을 기존 audit 저장소로 할지 신규로 할지 | 미확인 | compliance C6 은 보존 기간만 정하고 저장 위치는 정하지 않음 | 엔지니어링(plan 단계에서 확인) | (비움) |

**수치 제약 확인(spec-policy-pass 요구 P2)**: 90자 제약을 실제로 세었다. 예시 문구 "[회사명] ○○○ 고객님, 청구 12345678 상태가 보완요청으로 변경되었습니다. 서류 제출: https://example.co.kr/c/ab12cd" 는 한글 포함 약 70~95자 사이로 변동하며(청구번호 자릿수, URL 길이에 따라 90자를 넘을 수 있음) — **정확히 90자를 넘는지 여부는 위 Flagged concerns #1(상태명+다음예정+근거+문의경로를 다 넣을 자리가 없음)로 인해 문구가 확정되지 않아 세지 못함**. 문구가 확정되면 반드시 재확인한다.

## Out of scope
- 상담사·사정인 화면의 변경(이 spec 은 고객 통지 경로만 다룬다).
- 알림 문구의 다국어 지원.
- 단축 URL 서비스 도입 여부와 그 벤더 선정(보안 오너 결정 이후 별도 작업).
- 야간 발송 배치/지연 큐 설계(고객경험팀장 결정 이후 필요 시 별도 spec).

## Acceptance criteria
- **AC1 → R1** 사정인이 상태를 바꾼 시각으로부터 24시간 이내에 해당 청구 고객에게 통지가 발송된 기록이 있다.
- **AC2 → R2** 통지 본문의 상태 명칭이 접수·심사중·보완요청·지급완료·종결 중 하나와 정확히 일치한다.
- **AC3 → R3** 통지 본문에 다음 예정 한 줄과 문의 경로가 존재한다.
- **AC4 → R4** 로그인하지 않은 상태로 딥링크를 열면 청구 내용이 보이지 않고 로그인 화면으로 이동한다.
- **AC5 → R5** 발송에 사용된 연락처는 claims-core 기존 레코드의 값과 동일하며, 새로 수집된 필드가 없다.
- **AC6 → R6** 해당 채널에 동의 기록이 없는 고객에게는 발송 시도가 없고 스킵 기록만 남는다.
- **AC7 → R7** 모든 발송/스킵 건에 청구 번호·채널·결과·UTC 시각이 기록되어 있고 3년 보존 설정이다.
- **AC8 → R8** 확정된 SMS 본문 길이를 세어 90자 이하임을 확인한 기록이 spec 또는 plan 에 있다(현재는 미확정 — Flagged concerns #1 해결 후 재확인).
