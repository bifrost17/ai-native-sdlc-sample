# Spec: 청구 상태 변경 고객 통지 (from intent 0011-claim-status-notice)
Upstream: intent.md@a5dfb88. Status: draft.
Skills applied: brand@0c29619, compliance@0c29619, ux@0c29619, secure-api-review@0c29619(해당 없음 — 사유는 Constraints 뒤 참고).

## Requirements
- R1: 사정인이 claims-core 에서 청구 상태를 변경하면, 시스템은 24시간 이내에 고객에게 문자 또는 앱 푸시로 통지를 발송한다.
- R2: 통지에 포함된 링크는 포털 SSO 로그인 후에만 해당 청구의 상세 화면을 보여준다. 비로그인 상태에서는 청구 내용이 노출되지 않는다.
- R3: 통지 발송에 사용하는 전화번호는 claims-core 에 이미 저장된 값만 쓰고, 이 기능을 위해 신규로 전화번호나 그 밖의 PII 를 수집하지 않는다.
- R4: 통지 문구는 상태 어휘(브랜드 B4의 다섯 개: 접수·심사중·보완요청·지급완료·종결), 청구 근거, 문의 경로를 포함한다.
- R5: 통지 발송·조회 이력(누가·무엇을·언제)을 감사 로그로 남기고 3년 보존한다.
- R6: 상담사·사정인이 고객을 대신해 청구를 조회하는 경우, 본인확인 기록이 있을 때만 허용하고 그 기록 ID 를 함께 남긴다.

## Design
- claims-core 의 상태 변경 이벤트(상태 필드 업데이트)를 트리거로, 신규 통지 오케스트레이션 로직이 notify-gw 에 문자/푸시 발송을 요청한다. 기존 notify-gw·SSO·claims-core 를 그대로 재사용하고 신규 데이터 저장소는 만들지 않는다.
- 발송 채널 우선순위: 앱 푸시 가능(앱 설치 + 푸시 토큰 유효) 고객은 푸시, 아니면 문자.
- 링크는 포털의 기존 SSO 진입점을 거치는 딥링크(청구 ID 를 담은 리다이렉트 파라미터)로, SSO 세션이 없으면 로그인 화면으로 보내고 로그인 후 원래 청구 화면으로 복귀시킨다. 로그인 전 화면에는 청구 내용을 렌더링하지 않는다(R2 충족 지점).
- 발송·조회 이벤트는 기존 audit 파이프라인에 청구 번호·내부 ID·역할·UTC 시각으로 기록한다(PII 미포함, compliance C3/C6).
- 대리 조회(상담사·사정인)는 기존 본인확인 절차의 기록 ID 를 조회 이벤트에 함께 남긴다(compliance C7).

## Constraints
(intent.md 원문)
- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다.
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다.
- 통지 문구는 브랜드 정책과 컴플라이언스 정책을 따른다.
- 통지 링크는 짧아야 한다(문자 90자 제한) — 마케팅팀 요청으로 단축 URL 사용을 검토한다.
- 야간(22:00–08:00 KST)에도 상태 변경 즉시 보내 달라는 사정인 팀 요청이 있다.

(설계 중 발견)
- notify-gw 는 문자/푸시 두 채널을 이미 지원하므로 신규 게이트웨이 연동은 필요 없다. 채널 선택 로직만 추가한다.
- secure-api-review 는 이 변경에 해당 없음: claims-core 상태 변경은 기존 내부 이벤트이고, 이 스펙은 신규 외부 노출 엔드포인트를 만들지 않는다(알림 오케스트레이션은 내부 트리거, notify-gw 호출은 기존 내부 연동 재사용). 신규 엔드포인트가 생기면 이 스킬을 다시 적용해야 한다.

## Open questions from intent
- 앱 미설치 고객에게 문자를 보낼 때 청구 번호를 문자 본문에 넣어도 되는가 — answered: 넣는다. compliance C5 가 통지 본문에 "어느 청구"인지 근거를 담도록 요구하므로 청구 번호 표기는 정책상 요구사항이다(주민번호·계좌번호·연락처 전체 같은 C1 대상이 아님).
- 단축 URL 서비스(외부)로 청구 화면 링크를 보내도 되는가 — carried forward: 보안 오너. 근거 조항 없음(공백, 아래 Flagged concerns #2).
- 야간 발송을 허용할 것인가 — carried forward: 고객경험팀장. 근거 조항 없음(공백, 아래 Flagged concerns #3). intent 는 사정인팀 요청만 기록했고, 반대급부(고객 야간 수신 부담)를 정하는 정책이 없다.

## Out of scope
- 상담사 콜 응대 스크립트·콜센터 프로세스 변경.
- 신규 알림 채널(이메일 등) 추가.
- claims-core 상태 모델 자체의 변경(다섯 어휘 확정은 기존 brand B4 를 따름, 신규 상태 추가 없음).
- 단축 URL 서비스 자체의 도입·계약(결정 이후 필요하면 별도 스펙).

## Acceptance criteria
- AC1 (→R1): 사정인이 상태를 변경한 시각부터 24시간 이내에 해당 고객에게 문자 또는 푸시가 1건 발송된 기록이 감사 로그에 있다.
- AC2 (→R2): 통지 링크를 비로그인 상태에서 열면 청구 내용이 아닌 로그인 화면으로 이동하고, 로그인 후에만 해당 청구 상세가 보인다.
- AC3 (→R3): 발송 대상 전화번호가 claims-core 기존 레코드와 일치하고, 이 기능 도입으로 신규 전화번호 입력·수집 UI/필드가 추가되지 않았다.
- AC4 (→R4): 발송된 통지 문구에 다섯 어휘 중 하나, 청구 근거, 문의 경로가 모두 포함된다(단, Flagged concerns #1 이 해결되기 전까지는 90자 제한과 동시 충족이 미확정).
- AC5 (→R5): 발송·조회 이벤트마다 감사 로그에 행위자·청구 번호·UTC 시각이 남고, 보존 기간 설정이 3년으로 되어 있다.
- AC6 (→R6): 상담사·사정인의 대리 조회 시도 중 본인확인 기록이 없는 경우 조회가 차단되고, 성공한 조회에는 본인확인 기록 ID 가 audit 이벤트에 남는다.
