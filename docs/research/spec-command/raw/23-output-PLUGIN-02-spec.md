## Requirements

- R1. 사정인이 청구 상태를 바꾸면, 고객은 24시간 이내에 문자 또는 앱 푸시로 통지를 받는다.
- R2. 통지에는 청구 상태(brand B4 다섯 어휘 중 하나)와 다음에 고객이 할 일이 담긴다(우려 #1 이 풀릴 때까지
  문구 최종형은 미정).
- R3. 통지의 링크를 누르면 고객은 포털 로그인(SSO)을 거쳐서만 해당 청구 화면을 본다 — 로그인 없이 청구
  내용이 보이면 안 된다(intent 제약, 변경 없음).
- R4. 수신 동의가 확인되지 않은 고객에게는 통지를 보내지 않는다(C4).
- R5. "내 청구 어떻게 됐나요" 상담 콜이 월 3,900건에서 2,000건 아래로 줄어드는지 콜 로그로 추적한다
  (intent.md 의 성과 지표를 그대로 가져옴).

## Design

- **트리거**: claims-core 의 청구 상태 변경 이벤트(우려 #5 — push 인지 polling 인지 미확인) → notify-gw
  발송 요청. 상태 변경 후 발송까지 지연은 R1 의 24시간 한도 안에서 설계한다.
- **채널 선택**: 앱 설치·푸시 수신 동의가 있으면 푸시, 없으면 문자(둘 다 C4 동의 기록이 있는 채널만).
- **통지 본문**: 다섯 상태(접수·심사중·보완요청·지급완료·종결)별로 「다음 예정」 한 줄을 정의한다(U2).
  우려 #1(글자수)과 #3(청구번호 노출)이 풀리기 전에는 최종 문구를 확정하지 않는다.
- **링크**: 포털 SSO 로그인 화면을 거쳐 해당 청구로 랜딩. 단축 URL 사용 여부는 우려 #2 의 결정에 따른다
  (미사용 결정 시 90자 제약이 더 빠듯해져 우려 #1 과 함께 재검토 필요).
- **감사 로그**: 통지 발송(성공/실패/재시도)마다 역할·청구번호·시각(UTC)을 기록하고 3년 보존한다(C6).
  로그 자체에는 전화번호 등 PII 를 남기지 않는다(C3).
- **상류 호출**: notify-gw → claims-core 조회(있다면)는 캐시하거나 이벤트 payload 에 필요한 필드를
  실어 보내 별도 조회를 줄인다(S5). 구체적 캐시 정책은 우려 #5 확인 후 정한다.
- **엔드포인트/보안**: claims-core → notify-gw 간 새 내부 호출이 생기면 게이트웨이 JWT 인증(S1),
  스키마 검증(S2), 상태 변경 audit 이벤트(S3), pii 필드 로그 금지(S4)를 적용한다. 고객이 누르는 딥링크는
  기존 포털 SSO 세션 계약을 그대로 쓰고 새 역할별 세션 키를 만들지 않는다(S7 — 변경 없음이므로 위반 아님).
  존재하지 않는/권한 없는 청구 번호에 대해 포털이 이미 동일 응답을 주는지는 별도 확인 대상이 아니다(기존
  경로 재사용, 신규 아님).

## Constraints (intent.md 에서 그대로 + 이 spec 에서 발견)

- 기존 로그인(포털 SSO)만 쓴다. 통지 링크는 로그인 없이 청구 내용을 보여 주면 안 된다.
- 새 PII 수집 없음. 전화번호는 이미 claims-core 에 있는 것만 쓴다.
- 통지 문구는 브랜드 정책(brand)과 컴플라이언스 정책(compliance)을 따른다 — 다만 이 두 정책과 문자
  90자 제한이 동시에 지켜지지 않을 수 있다(우려 #1).
- 통지 링크는 짧아야 한다(문자 90자 제한). 단축 URL 사용 여부는 미정(우려 #2).
- 야간(22:00–08:00 KST) 발송 허용 여부는 미정(우려 #4).
- (신규) 통지 이력은 C6 에 따라 3년 보존, 역할·청구번호·시각(UTC)으로 기록한다.
- (신규) notify-gw 로 넘기는 상태 변경 이벤트에 claims-core 상류 호출 예산(S5, 50 rps)을 넘지 않는
  설계가 필요하다.
