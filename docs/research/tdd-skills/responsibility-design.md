# TDD를 스킬과 spec·plan에 어떻게 배치할 것인가

설계 자문일: 2026-09-11. **권고안이며 아직 활성 템플릿·정책에 적용하거나 행동 실험을 통과한
상태가 아니다.** 공개 스킬 비교는 [comparison.md](comparison.md), 근거 원문은
[sources.json](sources.json)에 보존한다.

## 권고: 반복 절차의 주 소유자는 작은 TDD 스킬

TDD는 문서 양식보다 구현 중 반복하는 판단에 가깝다. 테스트가 의도한 이유로 실패했는지,
어디까지 구현하면 되는지, 기대값이 구현을 그대로 따라가는지, 언제 구조를 정리할지를 계속
판단한다. 이 절차는 한 스킬에서 관리하는 편이 적절하다.

그러나 스킬만 설치하면 충분하다는 뜻은 아니다. 스킬은 이번 기능의 정답·중요한 경계·실제 파일·
통합 순서를 대신 결정할 수 없다. spec과 plan에는 개발건의 고유한 정보를 남겨야 한다.
**절차를 세 곳에 나누어 복사하는 방식이 아니라, 각 정보의 정본을 하나씩 정하는 방식**이다.

| 위치 | 이곳이 소유하는 정보 | 이곳에 반복하지 않을 정보 |
|---|---|---|
| 기존 팀 정책·항상 읽는 지침 | 새 동작·동작 변경은 TDD로 수행한다는 의무, 절차의 정본 연결 | 상세 RGR 설명·예외 사례집 |
| 작은 TDD 스킬 | 한 행동씩 의도한 RED→최소 GREEN→필요한 REFACTOR, 테스트 품질, 이탈·예외 대응 | 기능별 요구·AC·파일·PR 계획 |
| spec.md | 요구와 구조·동작·계약, 중요한 설계 결정, 관찰 가능한 수락 시나리오와 기대 결과 | 테스트 실행 순서·명령·실행 로그 |
| plan.md | 계약과 실제 테스트 경계·경로의 연결, 먼저 확인할 행동, 작업·PR 순서, 통합 검증 | 공통 TDD 교과서·모든 테스트 코드·매 cycle의 기록 |
| 기존 실행/PR 기록 | 실제 RED 이유와 GREEN 결과·명령, 최종 통합 근거와 미확인 범위 | 별도 TDD 상태 파일·중복 보고서 |

새로운 문서 체계를 다섯 개 만들자는 뜻이 아니다. 이미 있는 정책·spec·plan·PR에 맞는 정보를
남기고, 재사용 절차를 작은 스킬 하나로 분리한다. 특정 외부 플러그인은 필수화하지 않는다.

기존 기본 지침에 남길 최소 문구는 다음 정도다. 상세 절차를 읽지 못하더라도 단순히 test-after로
바꿔 진행할 수 없게 하는 요약이며, 아래 경계 사례를 모두 이 문장에 욱여넣지는 않는다.

> 새 동작·동작 변경은 그 행동의 테스트가 예상한 이유로 실패함을 실행으로 확인한 뒤, 같은 기대를
> 유지하며 최소 구현·재검증한다. 필요한 리팩터링과 회귀 검증을 수행한다. 세부 방법·예외는 팀의
> TDD 절차를 따른다.

반복 적용할 팀 지식을 명시적이고 버전 관리되는 스킬로 운영하는 것은 북극성의 방향과 맞는다.
다만 스킬은 자문적 통제이며 기계적 강제와 같지 않다.
[Anthropic skills](https://academy.claude.com/courses/ai-native-sdlc-playbook/skills-as-institutional-knowledge).

## 북극성과 이번 팀 선택의 경계

플레이북은 계획에 변경 파일·작업 순서·증명할 테스트를 명시하고 대화 없이 인계할 수 있을 만큼
다듬도록 한다. 구현이 계획에서 벗어나면 관련 커밋에서 계획을 갱신한다. 그러므로 스킬에 맡긴다는
이유로 plan의 테스트 경로·방법·순서를 생략해서는 안 된다.
[Anthropic plan mode](https://academy.claude.com/courses/ai-native-sdlc-playbook/plan-mode).

플레이북의 feedback loop는 구현 중 반복되며 마지막 verifier와 역할이 다르다. 명시적인
test-first·예상 실패 확인·재현 테스트 커밋·수정 중 테스트 보호는 **버그 수정**에 대한 지침이다.
새 기능까지 TDD를 필수화하는 것은 사용자가 선택하려는 팀 정책이다.
[Anthropic feedback loop](https://academy.claude.com/courses/ai-native-sdlc-playbook/give-claude-a-feedback-loop).

TDD의 테스트 목록은 행동을 생각하는 출발점이고, 실제 테스트 코드는 하나씩 작성하여 구현과
번갈아 발전시킨다. 모든 테스트와 구현 코드를 계획에서 먼저 확정하는 방식은 이 피드백을
약하게 할 수 있다. GREEN 뒤 정리할 이유가 없다면 refactor 변경을 억지로 만들 필요도 없다.
[Kent Beck, Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd).

## 대안을 선택하지 않는 이유

| 대안 | 강점 | 우리 조건에서의 핵심 실패 |
|---|---|---|
| 스킬만 설치하고 문서는 그대로 | 작고 중앙에서 개선 가능 | 기존 plan이 구현→테스트 순서를 지시하거나 검증 경계를 빠뜨림 |
| spec에 TDD 전체를 포함 | 요구와 테스트를 함께 볼 수 있음 | 제품 설계와 개발 절차가 섞이고 문서마다 같은 규칙을 복사 |
| plan에 모든 테스트·RGR 순서를 완성 | 실행자가 따라가기 쉬움 | 계획이 코드 사전 복제본이 되고 발견에 따른 설계 발전·갱신 비용이 커짐 |
| 작은 스킬 + 문서의 구체적 적용 | 공통 지식과 변경 정보를 각각 관리 | 스킬 미로딩과 추상적인 계획을 기본 지침·예시·리뷰로 보완해야 함 |
| 실행 가능한 명세를 기본으로 | 일부 계약과 테스트의 어긋남을 줄일 수 있음 | DSL·fixture·도구 비용. 테스트 선작성 여부나 설계의 충분함까지 보장하지 못함 |

API schema, 상태 전이 표, 계산 예시를 실행 가능한 계약에 연결하는 방법은 필요할 때 쓸 수 있다.
다만 모든 개발건에 Gherkin 같은 별도 형식을 추가하거나 새로운 실행 프레임워크를 기본화할
이유는 아직 없다. 관찰 가능한 기대값이 있다는 사실과 자동화되어 있다는 사실도 구분한다.

## spec에 남길 테스트 설계의 깊이

spec에는 “어떻게 참·거짓을 구별하는가”를 담는다. 조건·입력·행동·기대 결과, 중요한 오류와
불변식, 유지할 인접 계약을 구체화한다. 기대 결과는 요구·정책·검증된 예시에서 나와야 하며,
현재 구현의 계산을 그대로 재사용해 만들면 독립적인 기준이 사라진다.

Design에는 구조와 협력 관계도 계속 필요하다. 상태 전이가 핵심이면 상태/시퀀스 표현, 여러
컴포넌트의 책임이 핵심이면 컴포넌트 뷰, 클래스 간 계약이 중요하면 클래스 설계를 구체화한다.
TDD를 채택한다고 이미 결정해야 할 구조·계약을 테스트 작성자에게 떠넘기는 것은 아니다.

반면 아직 알 수 없는 모든 내부 메서드·mock 구조를 미리 정하는 것도 아니다. 시간·난수·외부
부작용 제어처럼 검증 가능성에 영향을 주는 중요한 경계는 설계에서 다룬다. 기존 안정된 경계로
검증할 수 있으면 테스트만을 위해 새 인터페이스나 클래스를 발명하지 않는다. 공개 계약 중심이란
모든 테스트를 비싼 HTTP/E2E로 쓰라는 뜻이 아니다. 안정된 도메인 모듈에서도 행동을 검증한다.

spec의 AC와 테스트 함수는 1:1이 아니다. 하나의 AC가 여러 사례를 필요로 할 수도 있고 하나의
테스트가 관련 불변식을 함께 확인할 수도 있다. 문서의 모든 문장을 기계적으로 테스트로 바꾸지 않는다.

## plan에는 TDD의 적용을 구체화

현재 네 정보 역할을 유지할 수 있다. 단순한 “TDD 적용” 한 줄로 테스트 계획을 대체하지 않는다.

- **Files that change:** 실제 구현·테스트·문서 경로와 변경 내용. 새 경로임을 구분한다.
- **Order of work:** 검토 가능한 행동 단위와 먼저 드러낼 미구현/결함, 그 뒤 연결할 구현,
  후속 행동과 통합 순서. 대표 첫 테스트는 구체화하고 전체 세부 cycle은 구현 중 발전시킨다.
- **Risks:** 단위 테스트가 놓칠 연동·인접 동작·공개 상태, 그 위험을 드러낼 검증.
- **Proof:** AC/중요 계약→테스트 대상·실행 명령·예상 결과, 기존/추가 검사, PR 통합 시 확인할 범위.

TDD 공통 절차는 계획에서 한 번 참조한다. 작은 작업은 문장 몇 개로 연결하고, 복잡한 작업은
`작업/AC | 먼저 확인할 행동·테스트 경로 | 구현 대상 | 통합/검증` 표로 읽기 쉽게 만들 수 있다.
이것을 모든 작업에 필수인 새 장부로 만들지 않는다. 계획의 테스트 코드는 모호한 계약을 설명할 때
짧은 예시로 사용할 수 있지만 모든 구현·테스트 코드를 미리 복사하도록 요구하지 않는다.

실제 실행 후 RED/GREEN 출력은 기존 실행/PR 기록에 둔다. plan은 계획이 달라졌을 때 갱신한다.
테스트마다 상태·타임스탬프·출력 표를 plan에 추가하면 갱신 경합과 문서 비용이 커지고, 계획과
관측 사실의 경계도 흐려진다. 중요한 재현·불변식·이탈의 근거는 축약하더라도 남긴다.

## 작은 예시: 담당자별 요청 목록

기존 합성 [기능 예시](../../../.claude/skills/plan/examples/feature.md)를 이용한 **보강 제안**이다.
아래 경로와 명령은 사용 제품 예시의 것이며 이 리서치에서 실행해 성공했다는 뜻이 아니다.
책임 배치를 설명하기 위한 발췌이며 원 spec의 전체 요구·제약과 기존 plan의 I/O 검증을 유지한다.

**spec의 계약·설계**

> list --owner hana는 담당자가 정확히 일치하는 요청만 기존 순서로 출력한다. 대소문자를 구별한다.
> 완료 건도 포함하고 null 담당자는 어떤 문자열과도 일치하지 않는다. 없는 담당자는 빈 stdout·rc=0이다.
> 조회는 파일 바이트를 변경하지 않는다. 옵션이 없는 list와
> show/complete의 기존 동작은 유지한다. 기존 list 경로의 읽기 후·출력 전 필터를 사용한다.

| 수락 사례 | 입력/조건 | 관찰 결과 |
|---|---|---|
| AC1 | 예시 데이터에서 --owner hana | R-101, R-103 순서; 파일 바이트 동일 |
| AC2 | --owner nobody, HANA, - 각각 | 빈 stdout, rc=0; 파일 바이트 동일. 미배정 화면 표시를 실제 ID로 오인하지 않음 |
| AC3 | 옵션 없는 list 및 기존 show/complete | 기존 계약 유지; complete의 정상 저장은 허용 |

**plan의 적용**

> tracker.py, 신규 tests/test_owner.py, README.md를 하나의 PR에 담는다. 기존 검사를 확인한 뒤
> 먼저 AC1의 담당자 필터 테스트를 쓰고 옵션 미지원/필터 미적용이라는 의도한 실패를 확인한다.
> 해당 동작을 최소 구현하고, AC2의 빈 결과·대소문자·미배정 표시 사례를 하나씩 진행한다. AC3의
> 보존 검사와 없는 파일의 기존 rc=2·오류 접두사 회귀 검사를 확인하며 필요한 정리를 한다. 최신 main과 합친 결과에서
> `python3 -m unittest discover -s tests -v`로 기존 검사와 새 검사를 확인한다.

**스킬이 실행 중 맡을 판단**

> 실행 환경이 깨져 실패했다면 AC1의 RED로 인정하지 않는다. 의미 있는 미구현 실패를 확인하고
> 같은 테스트를 GREEN으로 만든다. 다음 사례가 이미 GREEN이면 실제 계약을 검증하는지 확인하고
> 불필요한 구현은 하지 않는다. 안정된 동작을 유지하며 필요한 리팩터링을 한다.

이 예시는 별도 OwnerFilter 클래스, 테스트 전용 API, 스크립트 원장, 테스트마다 PR을 필요로 하지 않는다.

## 실행·갱신·인계의 경계

| 상황 | 권고 처리 |
|---|---|
| 승인된 행동의 구현 시작·새 작업으로 전환 | 해당 spec/plan과 TDD 절차를 읽고 현재 행동부터 수행. RED마다 사람 승인 없음 |
| 새 세션/하위 에이전트 인계 | 작업의 AC·공유 설계·테스트 경로·절차 위치를 함께 전달. 테스트 하나만 주고 spec을 숨기지 않음 |
| 플러그인 호출 실패 | 저장소에 제공된 정본을 직접 읽을 수 있게 구성. 설치 유무는 TDD 의무를 면제하지 않음 |
| 정본 자료 자체 누락 | 기본 지침의 최소 test-first 규칙으로 가능한 범위를 수행하고 자료 누락을 명시. 절차 준수를 보장했다고 주장하지 않음 |
| 필요한 실행 환경 부재 | 환경을 먼저 확보. 불가능하면 검증 한계와 계속할 범위의 결정을 드러냄; 환경 실패를 RED로 세지 않음 |
| 새 API가 아직 없어 컴파일 실패 | 확인된 계약 부재와 무관한 구문·환경 오류를 구분. 단순 도구 오류를 기능 실패로 보고하지 않음 |
| 테스트가 처음부터 통과 | 이미 충족된 행동/보존 검사인지, 잘못된 테스트인지 확인. 일부러 제품을 망가뜨려 RED를 만들지 않음 |
| 구현을 먼저 한 실수 | test-after였음을 기록. 검증을 보완하고 다음 행동부터 TDD 회복. 무조건 삭제·재시작하거나 TDD였다고 주장하지 않음 |
| 순수 리팩터링 | 기존 GREEN을 먼저 확인하고 계속 유지. 필요한 characterization test는 추가하되 억지 RED는 만들지 않음 |
| 요구 변경으로 테스트 기대가 달라짐 | 변경된 계약을 spec에 반영하고 정당한 새 기대를 시험. 테스트 약화로 실패를 숨기는 행위와 구분 |
| 테스트 자체의 기대값·fixture·대상이 잘못됨 | 기존 계약이라는 독립 근거로 바로잡고 변경 이유·검증을 남김. 제품 계약이 같으면 spec을 형식적으로 바꾸지 않음 |
| 내부 helper/fixture 정리 | 계약·계획된 경로·검증 방법이 같으면 문서를 형식적으로 고치지 않음 |
| 계약·설계·검증 계획 변화 | 영향받는 spec/plan의 정본과 이유를 관련 구현에 반영; 필요한 사람 결정은 기존 정책을 따름 |

TDD 테스트를 쓸 수 없다는 이유로 기능 개발 전체를 자동 면제하지 않는다. 순수 문서나 동작을
바꾸지 않는 설정 정리는 다른 검증이 적절할 수 있다. 반대로 설정·UI라는 이름이어도 권한·상태·
공개 동작을 바꾸면 검증 가능한 계약을 먼저 찾는다. 시각·접근성·운영 검사는 TDD로 모두 대체되지 않는다.

테스트 삭제·skip·assertion 약화로 GREEN을 만들면 안 되지만, 테스트를 영구 불변으로 만들면
정당한 제품 변경과 테스트 리팩터링도 막힌다. 현행 fix 보호 모드에서는 테스트 수정이 필요한
변경을 별도 합의된 테스트 작성 단계로 처리한다. 일반 기능에 이 모드를 적용하지 않는다.

새 세션에서 실패하는 테스트를 발견했다는 사실만으로 이전 작업자가 의도한 RED라고 판단하지
않는다. 계획·변경 내역과 남긴 핵심 실패 이유를 확인한다. 새로운 상태 원장은 필요 없지만 인계
문맥까지 없애지는 않는다. 계약에서 도출할 수 있는 추가 입력/기대값은 테스트에 남길 수 있으며,
모든 구체적인 기대값을 spec이나 plan에 먼저 추가하도록 요구하지 않는다.

## 작은 PR·main의 GREEN과 공존

RGR은 구현 중 피드백 단위이고 PR은 검토·통합 단위다. 작업 브랜치의 RED 순간이나 재현 테스트
커밋이 있다는 사실은 main의 배포 가능성과 충돌하지 않는다. 하나의 PR에 테스트·구현·관련 문서를
함께 담고 최종 통합 결과를 GREEN으로 머지한다.

버그 수정은 북극성대로 재현 테스트를 먼저 커밋하고 보호한 채 고친다. 일반 기능은 모든 RED와
GREEN마다 커밋하거나 PR을 나누도록 강제할 이유가 없다. 브랜치의 중간 실패 검사를 정당한
최종 통과처럼 보고하지 않으며 main으로 실패한 중간 상태를 머지하지 않는다.

반복 중에는 좁은 검사를 사용하고 영향을 주는 인접 검사를 함께 실행한다. 작업 완료·PR 경계에는
프로젝트가 요구하는 전체/통합 검증을 수행한다. 큰 suite에서 매 테스트마다 전체를 실행하는
규칙도, 마지막까지 관련 검사만 돌리고 전체가 통과했다고 말하는 방식도 피한다.
여러 PR의 공개 제어는 기존 [정책](../../GIT-WORKFLOW.md)과 [공개 제어](../../RELEASE-CONTROL.md)를
유지하며 일반 OFF/테스트 ON의 실제 경계를 확인한다.

전체 기능의 수락 시나리오는 spec에서 미리 검토하되, 아직 구현할 차례가 아닌 모든 시나리오의
실패 테스트를 main에 먼저 넣지는 않는다. 각 PR이 맡은 행동의 테스트·구현을 함께 통합한다.
후속 기능의 수락 검사를 이후 PR에서 추가하는 것과 현재 PR에 필요한 검사를 skip해 통과시키는
것은 다르다. 완료된 내부 행동을 공개 제어 뒤에서 시험할 수 있어야 한다.

## 가장 강한 반론과 남는 한계

“스킬을 두어도 에이전트가 읽지 않거나 순서를 어기면 끝 아닌가?”라는 반론은 맞다. 문서와
스킬은 의무와 판단 기준을 명확히 하며 행동을 유도한다. 실행 순서를 기술적으로 완전히 보장하지는
못한다. 긴 plan이나 실행 가능한 spec도 그 자체로 선작성과 올바른 기대값을 보장하지 못한다.

그렇다고 TDD 의무를 권장으로 낮추거나 검토 대상을 최종 결과만으로 한정하지 않는다. 관측한
test-first 수행·순서 이탈과 복구는 과정 평가이고, 테스트·요구 충족은 결과 평가다. 사후에 이전
구현에서 실패시킨 시험은 회귀 검증의 근거가 될 수 있지만 선작성의 증거는 아니다. 두 평가를
구분해 기존 실행/PR 기록에서 확인한다. 반대로 시험 하나의 GREEN만으로 모든 요구가 증명됐다고
단정해서도 안 된다.

그래서 최소 의무는 항상 읽는 지침에 남기고, plan 예시는 실제 test-first 순서를 보여주며,
실행 출력·기존 PR 리뷰로 관측한다. 에이전트와 리뷰어의 판단 오류까지 막는 새 프로그램으로
확장하지 않는다. 테스트가 GREEN이어도 요구·중요 설계가 빠졌다면 완료가 아니다. 어려운 경계는
적합한 모델·추론 수준의 검토와 사람 판단을 사용한다.

## 구현에 들어간다면 함께 고칠 범위

현재 feature plan 예시는 1단계에서 필터 구현, 2단계에서 테스트 추가를 지시한다. 이 연구의
팀 선택과 불일치하므로 보강 때 반드시 수정한다. 과거의 bug-only 판단·실험은 당시 기준의 기록으로
보존한다. 북극성 원문도 팀의 새 선호에 맞춰 고쳐 쓰지 않는다.

활성 정책의 짧은 의무·호출 시점, 작은 TDD 스킬의 원본과 설치/사용 자료, spec의 구체적인 수락·설계
양식, plan의 test-first 작업 예시, 관련 리뷰 기준과 사용 템플릿 전달본까지 같은 방향으로 맞춘다.
이 절차에서 특정 외부 스킬을 필수 이름으로 묶거나 전용 상태 검사기를 추가하지 않는다.

후속 실험은 작은 새 기능, 보호된 버그 수정, 변경된 요구로 테스트도 바꾸는 사례, 새 세션 인계를
포함하면 된다. 실제 RED 이유·GREEN·계약 충족·문서 갱신·통합 상태를 보며, 순수 리팩터링과
문서 수정에 불필요한 절차가 생기지 않는지도 함께 본다. 매번 고정 가이드 전체를 평가하지 않는다.
기존 전체 검사와 변경 영향 중심 검토는 유지한다. 아직 이 실험을 실행하지 않았으므로 통과로
표시하거나 북극성 주석 등급을 올리지 않는다.
