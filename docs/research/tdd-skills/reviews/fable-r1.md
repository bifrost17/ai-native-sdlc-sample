읽기 도구만 허용한 독립 설계 자문. 아래는 최종 답변 원문이며 비공개 추론은 포함하지 않는다.
일부 권고를 root가 채택하지 않았다. [판단 기록](review-record.md)을 함께 읽는다.

추천은 **최소 역할 분담**입니다. TDD는 한 종류의 정보가 아니므로 정본도 하나가 아닙니다. 팀 규칙 한 줄은 CLAUDE.md, 변경별 시험 대상과 선행 순서는 plan, 루프 절차와 시험 품질 판단은 출처를 밝힌 얇은 자체 tdd 스킬이 갖고, spec은 TDD를 말하지 않습니다. 파일은 읽기만 했고 명령은 실행하지 않았습니다. 원문 인용은 "원문 N강"으로 표시했고 나머지는 설계 추론입니다. glebis·addyosmani 원문과 기존 결론 문서는 독립성을 위해 읽지 않았습니다.

**왜 자체 얇은 스킬인가.** 외부 이름을 정책에 묶지 않는다는 결정을 따릅니다. superpowers를 통째로 쓰지 않는 이유는 무게가 아니라 규칙 내용입니다. 사전 구현 코드를 삭제하고 재시작하라는 절대 규칙과 예외마다 사람 허가를 받으라는 규칙은, 승인 범위 안 내부 변경을 재승인하지 않는다는 결정과 충돌합니다. 무겁다는 평은 측정된 적이 없으므로 근거로 쓰지 않았습니다. mattpocock 현재 판의 시험 지점마다 사용자 확인, ecc의 단계별 checkpoint 커밋과 커버리지 수치와 별도 보고서, glebis의 슬라이스마다 역할 셋과 상태 파일은 얇은 정책과 작은 PR 원칙에 맞지 않습니다. kirjolab의 스무 줄 현지화가 가장 가까운 본보기입니다. 거기에 ecc의 RED 판정 기준 한 줄과 superpowers의 "실패를 직접 보지 않았으면 무엇을 시험하는지 모른다" 한 줄을 더하면 충분합니다.

## 판단 2에서 7

**2. spec과 시험 설계의 겹침.** 겹침은 파생이지 중복이 아닙니다. AC의 조건·행동·기대값이 시험 단정의 독립 기대값 출처입니다. mattpocock과 kirjolab 모두 기대값은 구현 알고리즘과 독립된 출처에서 와야 한다고 쓰며, 이 팀에서 그 출처는 수락된 spec입니다. spec Design의 구속 계약이 곧 시험 지점입니다. CLI 옵션, 엔드포인트, JSON 필드처럼 남에게 보이는 경계에서 시험합니다. 기능 예시 spec은 내부 함수 이름을 구현자에게 맡긴다고 이미 갈라 두었습니다.

미리 정할 것은 넷입니다.
- 관찰 가능한 동작과 대표 사례의 문자 그대로의 결과.
- 시험할 공개 경계. 경계를 새로 만들거나 옮기는 것은 지속되는 설계 결정입니다.
- 보존할 기존 계약. 회귀 시험의 대상이 됩니다.
- 수용을 바꾸는 실패 의미. 예시의 정확 일치, null 제외, 빈 결과 rc=0이 이 부류입니다.

시험을 쓰며 발견할 것은 내부 분해와 이름, 슬라이스 순서와 시험 개수, 시험 파일 내부 구성, AC가 열거하지 않은 변형 입력, 공개 경계 아래 단위 시험의 유무입니다. 귀속 규칙은 하나면 됩니다. 발견이 "무엇이 옳은가"를 새로 정하면 spec AC로 가고 구현 커밋과 함께 갑니다. 이미 정한 규칙의 또 다른 사례면 시험 파일에만 남습니다. 검증 가능과 자동화는 다릅니다. design-spec 스킬은 수동 관찰을 허용하므로, 어떤 AC를 자동 시험으로 덮고 어떤 것을 관찰로 덮는지는 plan Proof의 검증 한계가 정합니다.

**3. 스킬만으로 충분한가, 모든 사이클을 plan에 써야 하는가.** 둘 다 아닙니다. 스킬만으로 부족한 이유는 셋입니다. 원문 6강 governance는 스킬을 권고적 통제로 두고 항상 성립할 정책에는 결정론적 뒷받침을 요구합니다. plan.md만 받은 새 세션이 구현한 관측이 이미 있으므로, 인계 문서가 순서를 담지 않으면 순서는 사라집니다. 스킬은 시험 대상을 모르고, 대상과 AC의 연결은 plan Proof만 갖습니다. 반대로 모든 사이클을 plan에 쓰면 수평 슬라이싱이 되고 plan이 비대해집니다. 원문 4강의 "벗어나면 같은 커밋에서 plan 갱신" 규칙 때문에 사이클마다 plan을 고치게 되어 diff와 plan의 일치 지표가 의미 없이 나빠집니다.

최소 구조는 양식에 새 절을 만들지 않는 것입니다. plan 스킬의 결함 문장 옆에 한 문장을 더합니다. "그 외 새로 추가·변경하는 동작은 각 AC를 증명할 시험을 이름으로 정하고, 그것을 통과시키는 코드보다 먼저 쓴다. 루프는 팀 tdd 스킬을 따른다." Order of work 2단계 자리표시자를 "동작의 시험을 먼저 추가해 실패를 확인한 뒤 구현하고 연결한다"로 바꿉니다. 기능 예시의 1·2단계 순서를 바꿉니다. 그것이 전부입니다. 기존 기능 예시의 Order of work만 이렇게 바뀝니다.

```markdown
## Order of work
한 PR로 기능·시험·설명을 함께 검토한다. 최신 제품 main에서 시작한다.
1. 기존 세 시험으로 기준 동작을 확인한다.
2. tests/test_owner.py에 AC1 사례를 먼저 추가하고 --owner 미구현으로 실패함을 확인한다.
   list 파서에 선택 인자를 연결하고 읽은 행을 필터링해 통과시킨다.
   AC2, AC3 사례도 같은 방식으로 하나씩 추가해 통과시키고 사용 설명을 함께 고친다.
3. 최신 main과 합친 결과로 Proof 전체를 확인하고 인도한다. 후속 PR은 없다.
```

Proof 절은 현재 예시 그대로 둡니다. 시험 이름과 AC 대응, 기존 검사와 추가 검사의 구분, 예정 검사라는 문장이 이미 필요한 전부입니다. 사이클 수는 적지 않습니다.

**4. 스킬 누락, 미설치, 세션 변경, plan만 전달.** 설치 없이 살아남는 닻이 셋입니다. plan.md의 Order of work 문장과 Proof의 시험 이름, 저장소에 동봉된 plan 스킬과 양식이 그 문장을 만들게 하는 것, CLAUDE.md 관례 한두 줄입니다. 셋 다 체크아웃이 곧 배포라 설치가 없습니다. 스킬이 있으면 plan과 CLAUDE.md는 "팀의 tdd 스킬"이라는 역할명으로만 가리킵니다. 없으면 에이전트의 일반 TDD 지식으로 후퇴합니다. 스킬의 가치는 TDD의 정의가 아니라 우리 판단, 곧 시험 지점·AC 기대값·예외·갱신 규칙이므로 후퇴가 치명적이지 않습니다. 실수 완전 차단이 목표가 아니라는 결정과 맞습니다.

세션 변경에는 상태 원장을 두지 않습니다. 시험 파일과 git 이력이 상태이며, 새 세션은 스위트를 돌려 실패한 시험이 남은 RED임을 압니다. 뒤를 받치는 것은 새 프로그램이 아니라 기존 장치의 한 줄입니다. REVIEW.md Compliance 패스에 "새·변경 동작에 그 변경 없이는 실패할 시험이 있고 기대값이 AC로 추적되는가, 기존 시험 약화는 발견"을 더합니다. 원문 8강은 훅의 대안으로 리뷰 반려를 명시합니다. 결함 모드 훅은 그대로 둡니다. PR 설명의 검증 근거에 새 시험의 실패 확인 줄과 통과 출력을 남깁니다. GIT-WORKFLOW가 이미 요구하는 "변경과 검증 근거"의 구체화이지 새 형식이 아닙니다.

**5. GREEN과 요구 충족.** GREEN은 코드가 시험대로 한다는 증명이지 시험이 spec대로라는 증명이 아닙니다. 사슬은 사람이 수락한 AC, AC 값을 베낀 시험, 그 시험의 GREEN입니다. 리뷰가 첫 연결을 보고 실행이 둘째 연결을 봅니다. 시험은 코드의 알고리즘으로 기대값을 계산하지 않고 문자 그대로의 값, 예시 데이터, spec에서 가져옵니다. AC에 값이 없으면 시험을 쓰기 전에 plan에 값을 적거나 spec을 고칩니다.

시험을 바꾸는 diff의 허용 사유는 셋뿐입니다.
- 수락된 spec AC 변경을 따르는 변경. AC ID를 인용하고 spec·시험·코드가 같은 커밋에 있습니다.
- 단정과 관찰 동작이 같은 구조 정리.
- 결함 사슬에서는 없음. 그 외는 리뷰 발견이며, 시험은 바뀌었는데 AC가 안 바뀌었으면 발견입니다.

리팩터링은 GREEN 뒤 구현자의 루프 안에서 작게 합니다. 별도 단계나 재승인이 아닙니다. 지킬 것은 스위트가 계속 GREEN이고 단정이 바뀌지 않는다는 것 하나입니다. 리팩터링이 단정을 바꾸게 만들면 시험이 구현에 결합됐거나 리팩터링이 아닙니다. mattpocock 현재 판의 "리팩터링은 리뷰 단계" 규칙은 완성된 동작을 작은 PR 하나에 담는 원칙과 맞지 않아 채택하지 않습니다. 대표 AC만 시험하므로 GREEN이 요구 충족 전체는 아닙니다. 인접 동작 검사, verifier 관측, 의도와 위험을 보는 사람의 통합 승인이 나머지를 맡습니다. 원문 8강 governance가 승인자를 code owner로 두는 이유입니다.

**6. RED와 main GREEN의 공존.** RED는 작업 브랜치의 상태이지 main의 상태가 아닙니다. PR 머지 시점의 head가 CI GREEN이면 main은 항상 GREEN입니다. 기본 merge commit은 브랜치 안 RED 커밋을 이력에 남기지만 main 끝은 GREEN입니다. 결함 흐름은 원문 8강 그대로입니다. 재현 시험을 먼저 별도 커밋하고, 시험을 건드리지 않는 수정 커밋을 이어 한 결함 PR에 담습니다. 제작 저장소에서는 훅이, 사용 저장소에서는 리뷰가 시험 무편집을 지킵니다. 여기서 RED 커밋은 증거이므로 있어야 합니다.

기능 흐름에서 RED는 작업 트리의 순간이지 커밋 단위가 아닙니다. 사이클마다 커밋을 요구하지 않습니다. 기본 커밋 단위는 한 동작의 시험과 구현이 함께 GREEN인 상태이고, RED 증거는 PR 설명의 실패 출력 발췌입니다. task·commit·PR이 1:1이 아니라는 결정과 일치합니다. 공개 제어가 있는 다단계 기능에서 슬라이스의 시험은 노출 플래그와 무관하게 CI에서 돕니다. 다음 슬라이스의 시험을 미리 써서 skip 표시로 머지하지 않습니다. 원문 8강 CLAUDE.md 블록이 실패 시험의 skip과 삭제를 금하고, 수직 슬라이싱이 미리 쓰지 말라고 합니다. 시험은 그것을 통과시키는 코드와 같은 PR로만 main에 갑니다. 설정 실패 시 OFF 같은 제어 동작 자체도 AC와 시험을 가진 동작입니다. squash를 택한 팀은 RED 커밋이 사라지므로 GIT-WORKFLOW의 원본 보존 규칙대로 PR 기록에 남깁니다.

**7. 사람 판단, 문서 갱신 생략, 회귀 범위, 실험 사례.** 스킬이 있어도 사람 판단이 남는 지점은 다음입니다.
- 동작 변경인지 기계적·문서·생성물인지와 그때의 대체 검증.
- 시험을 위해 공개 경계를 새로 만들거나 옮기는 것이 지속 설계 결정인지.
- 발견한 변형 입력이 새 계약인지 기존 규칙의 사례인지.
- 시험 변경이 허용 사유 셋 중 무엇인지.
- UI처럼 자동화 한계가 있는 곳의 관찰 범위.
- RED가 의도한 이유의 실패인지 설정 오류인지.

문서를 고치지 않는 작은 변화는 내부 함수 이름과 분해, 헬퍼 추출, 계획된 파일 안의 시험 정리, 이미 정한 규칙에 사례 시험 하나 추가, PR 경계와 Proof 대상이 안 바뀌는 단계 내부 순서 조정입니다. Proof에 적은 파일명이 바뀌면 같은 커밋에서 한 줄 고칩니다. 그래서 Proof는 개별 시험 이름을 위험한 단계의 닻일 때만 적고, 나머지는 파일과 AC 대응으로 적는 편이 유지비가 낮습니다. 회귀 범위는 루프 중에는 좁은 시험만, 커밋·PR·완료 보고 전에는 단일 명령 전체 스위트입니다. 이웃의 집합은 spec의 보존 계약이 정하고 기존 스위트가 기준선입니다. 뮤테이션 검사는 위험한 단계에만 선택합니다.

이후 실행 실험의 최소 사례입니다. 대화 서너 번이면 되고 하네스는 필요 없습니다. 실행 결과는 만들지 않았습니다.
1. 스킬 있음, plan.md만 준 새 세션의 기능 구현. 시험 선행, 의도한 이유의 RED, 통과, PR 기록을 봅니다. 0022 관측은 구현 성공만 봤고 순서는 보지 않았습니다.
2. 스킬 없음, 같은 조건. 판단 4의 닻이 실제로 순서를 지키는지 봅니다.
3. 결함 사슬. 재현 커밋 선행과 수정 커밋의 시험 무편집을 봅니다.
4. 구현 중 요구 변경. spec AC·시험·코드가 한 커밋에 있고 AC를 인용하는지 봅니다.
5. 대조군. 코드 먼저 쓴 브랜치를 리뷰 패스가 잡는지 봅니다.
6. 문서만 바꾸는 요청. 시험을 꾸미지 않고 대체 검증을 말하는지 봅니다.

## 반론, 미해결, 과잉 설계

**가장 강한 반론.** "기능의 test-first는 사후에 검증할 수 없다. 코드를 먼저 쓰고 RED 출력을 만들어 붙이면 리뷰어는 구별하지 못한다. 그러면 의무는 의식이나 허구가 된다." 이 반론은 옳습니다. 순서 자체는 프로그램 없이 증명되지 않습니다. 그래서 리뷰 기준은 순서가 아니라 결과여야 합니다. 결과는 "변경 없이는 실패할 시험이 있고 기대값이 AC로 추적된다"이며, 구현을 되돌리거나 뮤테이션으로 사후 검증할 수 있습니다. test-first는 에이전트가 그 결과에 도달할 확률이 가장 높은 절차라서 스킬과 plan이 요구하지만, 결함 외에는 순서를 증명하려 들지 않습니다. 순서를 증명하려면 RED 커밋 강제나 트랜스크립트 보존뿐이고 둘 다 사용자가 원치 않는 비용입니다. 팀은 이 한계를 알고 선택해야 합니다.

**둘째 반론.** "정본이 네 곳이면 결국 중복된다. 스킬을 버리고 plan 스킬의 Proof만 강화하라." 유효한 반론입니다. 스킬을 유지하는 이유는 루프가 구현 시점에 호출되고 독립적으로 버전·교체되어야 하기 때문이며 ADR-219의 논리와 같습니다. 그러나 중복은 한 줄 원칙을 어기는 순간 생깁니다. 스킬이 스무 줄을 넘기 시작하면 이 반론이 이깁니다.

**셋째 반론.** 모든 기능 TDD는 플레이북 밖의 팀 선택이고, 작은 추적 시험을 만드느라 느려질 수 있습니다. 예외 목록과 대체 검증 진술로 비례를 지키고, 절대 규칙이 아닌 기본값으로 둡니다.

**답하지 못한 문제.**
- 공개 제어의 테스트 대상 ON 설정과 시험 픽스처의 관계. plan이 PR마다 적어야 하지만 여기서 설계하지 않았습니다.
- UI 시각 루프에서 TDD의 범위. 원문 8강의 스크린샷 루프이며 검증 한계로만 다룹니다.
- tdd 스킬이 다양한 문구에서 실제로 로드되는지. 원문 6강 4단계의 트리거 시험은 팀 몫이고 미측정입니다.
- 구현 스킬의 출처와 판 기록. spec에는 Skills applied가 있지만 plan과 PR에는 없습니다. 양식을 늘리지 말고 PR 설명에 적는 정도로 둡니다.
- REVIEW.md 한 줄 추가는 팀 정책 파일 수정입니다. 작지만 오너 승인 대상입니다.

**과잉 설계 경고.**
- spec에 TDD 절이나 시험 설계 절을 두지 않습니다.
- plan에 사이클 목록, 커버리지 수치, 증거 보고서 파일을 두지 않습니다.
- 기능에 RED 커밋을 강제하지 않습니다.
- 시험 지점마다 사용자 확인, 슬라이스마다 역할 셋과 상태 파일을 두지 않습니다.
- test-first를 감지하는 새 훅을 만들지 않습니다. 순서는 훅으로도 잡히지 않으며 결함 모드 훅 하나면 됩니다.
- 루프 절차를 CLAUDE.md에 넣지 않습니다. 한 페이지 규칙과 ADR-219의 이유입니다.
- verifier 서브에이전트를 TDD 필수로 묶지 않습니다.
