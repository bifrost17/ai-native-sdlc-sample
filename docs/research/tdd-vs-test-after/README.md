# 에이전트 개발에서 TDD와 구현 후 테스트

조사일: **2026-09-12**. 대상: 에이전트 연구 11건, 사람 대상 연구·종합 연구 5건, 공개 실무 실험 2건, 웹·에이전트 프로젝트 8개의 PR/MR 72건. 새로운 비교 실험은 수행하지 않았다. 공개 실험 데이터 재집계와 원문 검증을 수행했다.

## 질문에 대한 답

**모든 에이전트 작업에 엄격한 TDD를 강제할 근거는 부족하다. 작은 단위로 구현하고 곧바로 테스트·수정하는 방식은 합리적인 대안이며, 일부 공개 실험의 완료 실행에 기록된 API 비용은 더 낮았다.** 다만 이것은 기능 전체를 완성할 때까지 검증을 미루는 방식이 우수하다는 결론은 아니다. 가장 가까운 공개 비용 비교에서는 두 방식의 결과도 달랐다. [Finster 실험과 원자료 재집계](practitioner-evidence.md)

반대 근거도 있다. 구현 전에 테스트 정보를 제공하면 최종 정확성이 높아진 연구가 있고, 잘못된 구현을 본 뒤 만든 테스트가 그 오류를 그대로 받아들이는 현상도 관찰된다. 그러나 **선행 테스트 정보의 가치, 테스트의 독립성, 엄격한 RED–GREEN 순서의 가치는 구분해야 한다.** 이 세 가지를 같은 조건에서 분리해, 실제 웹앱 변경의 품질·수리·시간·비용을 모두 비교한 충분한 근거는 찾지 못했다. [TENET](https://arxiv.org/abs/2509.24148v4), [구현 노출과 테스트 오류 연구](https://arxiv.org/abs/2607.05139v1)

따라서 `plan.md`에는 **검증할 동작과 성공 기준을 먼저 정하고, 작업별로 TDD·작은 구현 후 테스트·기존 테스트 활용을 선택하게 하는 구조**를 권한다. 이는 아래 근거를 종합한 설계 권고이며, 이 템플릿 자체의 효과를 실험으로 검증했다는 뜻은 아니다.

| 판단 | 근거에 맞는 확신 수준 |
|---|---|
| 에이전트에게 TDD를 지시하면 언제나 품질이 높아진다 | 지지하지 못함. 개선·무효·악화 결과가 공존하며 비교군도 서로 다르다. |
| 작은 구현 → 테스트 반복이 TDD보다 효율적일 수 있다 | 제한적으로 지지. 소규모 공개 비용 실험은 있으나 실제 웹앱·여러 모델로의 일반화는 낮은 확신. |
| 전체 구현 후 한꺼번에 테스트하는 것이 가장 효율적이다 | 지지하지 못함. 이 방식이 더 비싼 공개 사례도 있다. |
| 구현을 그대로 정답으로 삼는 테스트를 경계해야 한다 | 중간 수준의 직접 근거. 다만 결함 검출 연구를 전체 개발 생산성으로 확대할 수 없다. |
| 유명 프로젝트가 테스트를 요구하므로 모두 TDD로 개발한다 | 성립하지 않음. 공식 요구, 공개 커밋 순서, 실제 로컬 작업 순서는 다르다. |

## 무엇을 비교했는가

| 방식 | 이 보고서의 정의 |
|---|---|
| 엄격한 TDD | 작은 동작마다 의미 있는 실패를 확인하고, 최소 구현으로 통과시킨 뒤 정리한다. |
| 구현 후 테스트 | 구현한 뒤 테스트를 작성하고 수정한다. **동작별 반복**과 **전체 구현 뒤 일괄 검증**을 따로 본다. |
| 혼합 방식 | 인수 조건·핵심 계약은 먼저 정하고 세부 테스트는 구현 전·중·후에 배치한다. |

기존 인간 테스트를 프롬프트에 넣는 것, 버그 재현 스크립트를 먼저 실행하는 것, 모든 테스트를 한꺼번에 먼저 만드는 것은 엄격한 TDD와 같지 않다. 연구의 제목보다 실제 처리 절차와 비교군을 기준으로 읽었다. [상세 조사 방법](methodology.md)

## 에이전트 연구와 공개 실험 비교

아래 수치는 각 실험 안에서만 비교한다. 서로 다른 모델·과제의 성공률이나 달러 비용으로 기법의 전체 순위를 만들지 않았다. 논문별 모델 버전·평가 분모·표본·재현 자료는 [11개 논문 근거 카드](working/agent-studies.md)에 있다.

| 연구·모델·대상 | 실제 비교와 관찰 | 질문에 적용할 수 있는 범위 |
|---|---|---|
| [TENET v4](https://arxiv.org/abs/2509.24148v4), DeepSeek-V3, 저장소 함수 980개 | 기존 테스트를 사후 수정에만 제공할 때 42.65%, 사전·사후 모두 제공할 때 49.18%. 평균 토큰 합은 6.7% 증가. | 테스트를 미리 **읽는 정보 효과**에 유리한 근접 근거. 에이전트의 테스트 작성 순서 비교는 아니다. |
| [TDD-Agent v1](https://arxiv.org/abs/2608.16742v1), GPT-5-mini·DeepSeek-V3.2·Qwen3-Coder | 테스트 생성 지시의 기여는 LiveCodeBench에서 +0.58~1.65%p. 전체 반복 시스템의 개선은 더 크다. | test-after 대조군이 없고 실행·수정 기회가 결합된다. 전체 개선을 TDD 순서의 효과로 볼 수 없다. |
| [TDAD v2](https://arxiv.org/abs/2603.17973v2), Qwen3-Coder 30B, SWE-bench 100건 | 기본/TDD 지시의 해결률은 모두 31%. 테스트 단위 회귀 실패율은 6.08→9.94%. | 절차 지시만의 이점이 없었던 반례. 빈 패치 제외로 분모가 다르며, 테스트 영향 범위 검색의 효과와 구별해야 한다. |
| [Agent-generated tests v2](https://arxiv.org/abs/2602.07900v2), mini-SWE-agent, SWE-bench 500건 | GPT-5.2에 새 테스트 작성을 장려해도 해결 359건으로 같고 토큰은 증가. 다른 모델에서는 테스트 억제로 해결률도 하락. | 새 테스트의 추가 비용과 모델 차이를 보여준다. 차이가 통계적으로 유의하지 않다는 것은 동등하다는 증명이 아니다. |
| [Coding before testing v1](https://arxiv.org/abs/2607.05139v1), 5개 모델, 함수·라이브러리 과제 | 선택된 어려운 의미 오류의 평균 검출은 구현 노출 후 14%, 요구사항만 제공하면 25%. | 구현과 테스트가 같은 오해를 공유하는 위험의 직접 근거. 전체 개발 비용·출시 결함률 연구는 아니다. |
| [Finster 공개 matrix](https://devteam.bryanfinster.com/docs/experiments/05-final-results/), Sonnet 4.6, 계산기 과제 4개 | 작은 구현 후 테스트 지시 약 $0.99, 동작별 TDD 지시 $1.59, 전체 구현 후 테스트 지시 $2.09. 세 방식의 외부 인수 테스트는 모두 통과. | 완료 cell의 기록 비용. RED 수행 준수는 확인되지 않았고 재시도·중단 비용은 빠질 수 있다. 작은 과제·단일 모델의 제한된 비교. |
| [Dan Luu, 2026-09-07](https://danluu.com/agentic-testing/), GPT-5.6 Sol, Rust Zstd | 조건별 80회. TDD 지시는 기본 지시보다 완전 통과율이 낮았고 비용은 비슷하거나 낮았다. | 기본 지시도 테스트하며 엄격한 test-after 비교군이 아니다. TDD 지시 준수도 불완전하다. |
| [TDDev v1](https://arxiv.org/abs/2605.17242v1), Sonnet 4.6·Qwen3.5, 웹앱 | 전체 구현 후 검증 루프와 작은 단계 루프의 우열이 모델에 따라 달랐다. | 기준군 도구·재시도 차이, 같은 모델의 판정, 여러 시도의 테스트별 최고값 합산, 표·표본 불일치로 확신을 낮췄다. TDD의 큰 우월성을 입증하는 자료로 채택하지 않았다. |

추가로 [ClassEval-TDD](https://arxiv.org/abs/2602.03557v1), [TGen](https://arxiv.org/abs/2402.13521v2), [TDFlow](https://aclanthology.org/2026.eacl-long.70/), [LLM4TDD](https://arxiv.org/abs/2312.04687v1), [TiCoder](https://arxiv.org/abs/2404.10100v2)를 검토했다. 선행 테스트·인간 피드백·반복 수정의 가능성을 보완하지만, 동일 조건의 자율 에이전트 TDD 대 test-after 비교는 아니다. TDFlow처럼 일반적으로 숨기는 인간 테스트를 입력으로 제공한 결과는 표준 SWE-bench 순위와 직접 비교하지 않았다.

### 전체 시간·비용·변경 용이성에서 남는 빈칸

대부분의 연구는 숨겨진 테스트 성공률에 집중한다. **최초 코드 생성부터 검증·재작업·사람 검토까지 완료하는 시간**을 같은 조건으로 측정한 근거는 부족하다. 토큰 수, API 비용, wall-clock 시간은 서로 대체하지 않았다. 작은 계산기의 후속 변경량도 장기간 운영하는 웹앱의 변경 용이성과 같지 않다. 따라서 “TDD가 몇 배 느리다”, “유지보수 비용을 몇 % 줄인다” 같은 보편 수치는 제시하지 않는다.

## 사람 대상 연구는 무엇을 말하는가

| 연구 | 관찰 | 에이전트로 옮길 때의 한계 |
|---|---|---|
| Nagappan 등, 2008, 산업 팀 4개 | 비교 프로젝트보다 결함 밀도가 낮았지만 초기 개발 시간이 늘었다는 보고. | 비무작위 사례 비교, 시간은 관리자의 추정. 팀·테스트 노력 차이와 순서 효과를 분리하지 못한다. |
| Rafique·Mišić, 2013, 메타분석 | 작은 품질 개선, 생산성은 일관되지 않음. 산업·학술 환경 차이. | 비교군과 테스트 노력의 이질성. 사람의 학습·작업 비용은 에이전트와 다르다. |
| Fucci 등, 2016/2017, 전문가 39명 | 짧고 일정한 작업 주기가 품질·생산성과 관련되고 테스트 순서는 최종 설명 변수에서 빠짐. | 상관관계이며 사후 테스트의 우월성을 입증하지 않는다. |
| Santos 등, 2020, 실험 12개·411명 | 평균은 반복적 test-last 쪽이 높았으나 통계적으로 유의하지 않음. | TDD 초보·짧은 작은 과제. 비유의성은 동등성의 증명이 아니다. |
| Ghafari 등, 2020 | 정의·참여자·과제·프로젝트·비교군 차이가 결론 불일치의 원인이라고 분석. | 새로운 효과 비교 실험이 아니라 연구 해석을 위한 배경 근거다. |

각 행의 원문·수치·연구 설계·보관 PDF는 [사람 대상 연구 상세](human-studies.md)에 연결했다. 사람 연구만으로 에이전트의 비용 구조나 최적 순서를 결정하지 않았다.

## 유명 프로젝트의 정책과 관찰 사례

아래는 **공식 지침과 공개 이력의 요약**이다. 8개 프로젝트에서 기능·버그·리팩터링별 2건을 먼저 조사했고, 순서 불명 조건에 따라 각각 1건씩 추가해 총 72건을 확인했다. 저장한 후보 내 최신 병합 순서로 골랐으며 API 조회 상한 때문에 전체 24개월의 최신 적격 PR을 완전히 열거했다고 보장하지 않는다. 이는 사례 조사이지 TDD 사용률 추정이 아니다.

| 프로젝트 | 확인한 공식 정책 | 9건에서 관찰한 사실·예외 |
|---|---|---|
| Django | 회귀 테스트와 전체 스위트 통과. 버그 테스트는 수정 없이 실패해야 함. | 7건 코드·테스트 같은 커밋, 2건 새 테스트 없음. 작성 순서를 복원할 수 없음. |
| Rails | 코드 기여에 테스트. 코드 없이는 실패하고 함께 통과해야 함. 영향 컴포넌트 검증을 권함. | 7건 같은 커밋, 2건 새 테스트 없음. 모든 변경의 일반 TDD 의무는 확인한 가이드에 없음. |
| React | 버그·신규 기능 테스트와 기존 검사 통과 요구. | 8건 같은 커밋, 1건 새 테스트 없음. 현재 CONTRIBUTING이 연결하는 기존 공식 가이드도 확인함. |
| Next.js | 수정이 없으면 테스트가 실패하는지 확인하도록 요구. | 7건 같은 커밋, 1건 새 테스트 없음, 구현 커밋 뒤 테스트 1건. 공개 커밋 순서가 로컬 작성 순서를 입증하지는 않음. |
| GitLab | 적절한 테스트·회귀 방지·CI 통과. | 8건 같은 커밋, 1건 새 테스트 없음. Shift Left 문구를 작성 순서 규칙으로 해석하지 않음. |
| OpenHands | 현재 Agent Canvas 저장소의 행동 변경에 “TDD tests” 문구. 명시적인 RED-first 단계는 없음. | 9건 같은 커밋. 한 PR은 구현 완료 후 테스트만 기준판에 이식해 실패를 재현한 기록이 있음. 테스트의 판별력과 최초 작성 순서는 다름. |
| SWE-agent | 저장소 기여에는 테스트 권장, 순서 규칙 없음. **사용자 작업용 기본 프롬프트**는 임시 오류 재현→수정→재실행. | 5건 같은 커밋, 2건 기존 검사만, 2건 기록 부족. 기본 프롬프트의 재현 우선과 영구 테스트 작성 TDD를 구분함. |
| Superpowers | 사용자용 TDD 스킬은 엄격한 RED–GREEN을 요구. 저장소 자체는 구조 검사와 LLM 행동 평가를 구분. | 4건 같은 커밋, 4건 기존 평가 관련 기록, 1건 일부 probe의 테스트 커밋 선행과 실패 실행 작성자 보고. 원 실행 로그·중간 CI는 없음. |

정책의 고정 커밋 URL, 예외, PR별 변경·CI 근거는 [웹 프로젝트 45건 상세](working/web-projects.md)와 [에이전트 프로젝트 27건 상세](working/agent-projects.md)에 있다. **새 테스트가 없다는 것은 무테스트 개발을 뜻하지 않으며, 같은 커밋이라는 것은 구현 후 테스트의 증거가 아니다.** Superpowers의 정책은 main에서 읽었고 일부 최근 PR은 dev·기능 브랜치에 병합됐다. 일부 PR이 같은 병합 커밋을 공유하므로 표본을 72개의 독립 실험으로 취급하지 않는다.

기존 조사에서 높이 평가했던 Superpowers 인증 개선 계획도 재검토했다. 계획 `83b5d3…`는 구현 `b17d54…`에 그래프상 선행하지만, 구현과 테스트는 같은 구현 커밋에 있다. PR의 RED–GREEN 요약은 작성자 보고이며 원래 실행 artifact·CI를 확보하지 못했다. **좋은 계획 문서라는 판단과 계획대로 TDD를 실행했다는 판단은 별개**다. [추적 근거와 원문 위치](working/agent-projects.md)

## 실무자·커뮤니티에서 확인한 반론

thoughtbot의 Rails 사례는 사람이 테스트를 검토하고 에이전트가 구현하는 구체적 시연을 제공한다. Beck·Fowler·DHH의 대화는 자동 테스트의 가치에 동의해도 매번 테스트부터 작성해야 하는지는 다르게 판단할 수 있음을 보여준다. 두 자료 모두 통제 비교 실험은 아니다.

Aside Browser로 HN 두 스레드와 Reddit 한 스레드의 본문·댓글을 읽었다. 낮은 가치의 테스트를 양산했다는 경험, TDD와 사람 검토가 유용했다는 반례, 탐색 뒤 검증을 강화한다는 경험, 별도 적합성 테스트로 에이전트를 교정한 사례를 함께 기록했다. 커뮤니티의 경험담이나 논문 재소개를 독립 실험으로 세지 않았다. [당사자 자료·댓글 원문·브라우저 기록](practitioner-evidence.md)

## 상황별 선택에 대한 권고

다음은 증거를 바탕으로 한 적용 판단이다. 표의 각 상황에서 우월성이 직접 검증됐다는 의미는 아니다.

| 작업 | 기본으로 고려할 접근 | 선행해야 할 것 | 구현 후 보완·예외 |
|---|---|---|---|
| 재현 가능한 버그 | 최소 재현 우선. 그 테스트로 작은 TDD 루프가 자연스러우면 사용 | 현재 코드에서 의도한 이유로 실패하는 재현과 기대 결과 | 구현 뒤 만든 테스트도 기준판에 재생해 유효성 확인 가능. 원래 test-first라고 보고하지 않음. |
| 명세가 안정된 신규 기능·도메인 로직 | 인수 조건 선행 + TDD 또는 동작별 구현 후 테스트 | 정상·경계·오류 예제와 외부 동작 | 짧은 단위마다 실행·수정. 내부 구조를 고정하는 테스트는 최소화. |
| UI·사용성 탐색 | 짧은 구현·브라우저 확인 반복, 동작이 안정되면 테스트 보강 | 사용자 목표, 핵심 흐름, 관찰할 성공 기준 | 배치·색상 같은 탐색을 모두 단위 테스트로 선고정할 필요 없음. 중요한 상호작용·접근성은 직접 검증. |
| 동작 보존 리팩터링 | 기존 테스트를 먼저 확인하고 작은 변경 뒤 실행 | 보존할 동작과 기존 검증 범위 | 부족한 관찰 지점에는 특성화 테스트 추가. 변경마다 새 테스트를 만들 필요는 없음. |
| 인증·권한·결제·데이터 변경 | 계약·금지 동작 선행, 핵심 경계는 테스트 우선 고려 | 독립적으로 정의한 권한 행렬·불변 조건·실패/복구 기준 | 자체 테스트 통과만으로 완료하지 않고 통합·마이그레이션·회귀 증거 확인. TDD라는 이름만으로 충분하지 않음. |
| 폐기할 spike·작은 가역 변경 | 빠른 구현과 직접 확인 | 무엇을 알아낼지, 확인 방법, 폐기/제품 반영 조건 | 제품에 편입할 때 안정된 요구사항과 필요한 회귀 검증을 갖춤. |

## 에이전트용 plan.md에 반영할 구조

`TDD 필수` 한 줄보다 아래 항목이 작업별 판단을 검토하기 쉽다. 현재 저장소의 템플릿 파일은 수정하지 않았으며, 별도 설계 작업에 넘길 권고안이다.

```markdown
### 검증 전략
- 선택: TDD / 동작별 구현 후 테스트 / 기존 테스트 활용 / 혼합
- 선택 이유: 작업의 불확실성, 기존 검증 범위, 실패 영향
- 선행 인수 조건: 외부에서 관찰할 동작과 정상·경계·실패 예제
- 정답의 근거: 요구사항·프로토콜·기준 데이터 등 구현과 독립된 기준

### 구현 단계별 확인
- 이 단계에서 바뀌는 동작:
- 실행할 검사 또는 브라우저 절차:
- 기대 결과와 완료 증거:
- 버그 수정이면 기준판 실패 / 수정판 통과 확인 방법:
- 기존 검사로 충분하거나 새 테스트를 미루는 경우의 이유:

### 완료 검증
- 새 테스트 외에 기존 회귀·통합 검사로 확인할 범위:
- 구현과 테스트가 같은 오해를 공유하지 않는지 확인할 방법:
- 남은 미확인 항목과 영향:
```

독립 검증은 반드시 별도 에이전트를 추가한다는 뜻이 아니다. 요구사항에서 만든 기대값, 외부 적합성 테스트, 기준 데이터, 다른 구현과의 비교도 사용할 수 있다. 별도 에이전트를 쓰더라도 같은 잘못된 전제를 공유하면 독립성이 보장되지 않는다. 검사 범위는 변경의 영향에 맞추고, 저비용 변경에 가치 없는 테스트 수를 강제하지 않는 편이 낫다.
