## Phase 1 — Deployment tool (`mcp_server/tools/deployment.py`)

No LLM calls. Manages dev-server subprocesses keyed by resolved `project_dir` path.

### API

#### `detect_framework(project_dir: str) -> dict`

Reads `package.json` and identifies the framework by inspecting `dependencies` and `devDependencies`.

Returns:
```python
{
    "framework": str,      # "nextjs" | "react" | "vue" | "vite" | "express" | "unknown"
    "dev_command": str,    # command used to start the server
    "default_port": int,   # expected port the server listens on
}
```

Detection order (most specific first):

| Framework | Trigger condition | Default port |
|-----------|-------------------|--------------|
| `nextjs`  | `next` in deps | 3000 |
| `react`   | `react` + `vite` in deps | 5173 |
| `vue`     | `vue` in deps | 5173 |
| `vite`    | `vite` in deps | 5173 |
| `express` | `express` in deps | 3000 |
| `unknown` | no match / no `package.json` | 3000 |

If `scripts.dev` or `scripts.start` is present in `package.json`, those take precedence over the inferred command.

---

#### `start_app(project_dir, port=None, timeout=30, env=None) -> dict`

Spawns the dev server subprocess. Polls every 0.5 s until the port is reachable or `timeout` seconds elapse.

- If the default port is already in use, falls back to a random free port.
- If a server for `project_dir` is already running, returns the existing info without spawning a new process.
- Uses `start_new_session=True` so the whole process group can be cleanly killed later.

Returns:
```python
{"url": str, "port": int, "framework": str}
```

Raises `RuntimeError` if the process exits prematurely or the port never opens.

**Auto-recovery on failure:** If the primary spawn fails, `start_app` attempts
recovery before raising the error:

1. **`npm install`** — if `package.json` exists but `node_modules/` is missing,
   runs `npm install` (timeout 60s) then retries with the original detection.
2. **Heuristic entry-point scan** — searches `server.js`, `index.js`, `app.js`,
   `main.js` for `.listen()` pattern. Extracts port from source code via regex.
   Falls back to static HTML serving if `.html` files exist but no JS server found.

This handles common coding-agent mistakes: forgetting `npm install`, using
non-standard entry points (`app.js` instead of `server.js`), or generating
standalone HTML without `package.json`.

---

#### `stop_app(project_dir: str) -> None`

Terminates the dev server for `project_dir`. Sends `SIGTERM` to the entire process group; escalates to `SIGKILL` if the process does not exit within 5 s. No-op if no server is registered for that directory.

## Phase 2 — Test Case Generation (`mcp_server/tools/test_generation.py`)

Single LLM call per invocation (claude-sonnet-4-6). No subprocess or browser.

### Two modes

#### Convert mode — `generate_test_cases(requirements, ui_instruct)`

Receives WebGen-Bench `instruction` + list of `ui_instruct` items (`task` +
`expected_result` per item). One LLM call converts each item into a full
structured test case: derives a `feature` name, expands the high-level `task`
into concrete `steps[]`, maps `expected_result` → `expected`, assigns a
sequential `test_id`.

Used as a preprocessing step before experiments: all WebGen-Bench items are
converted once, saved as the fixed test-case input for all conditions.

#### Generate mode — `generate_test_cases(requirements)`

Receives only `requirements`. One LLM call with chain-of-thought: the model
first lists all features it identifies, then outputs one test case per feature.

Used for RQ1: generate mode output vs convert mode output (reference) measures
test-case quality independently of execution results.

### Test-case format

```json
{
    "test_id":  "TC-01",
    "feature":  "User can create a task",
    "steps": [
        "Navigate to the registration page",
        "Enter email 'testuser@example.com' and password 'Test@1234'",
        "Navigate to the task creation page",
        "Enter task title 'Test Item' and click Submit"
    ],
    "expected": "New task 'Test Item' appears in the task list"
}
```

### Opinionated defaults (injected in both modes)

| Placeholder | Value |
|-------------|-------|
| email | `testuser@example.com` |
| password | `Test@1234` |
| name | `Test User` |
| generic string | `Test Item` |

### `_parse_test_cases(text) -> list[dict]`

Extracts a JSON array from LLM output. Tries (in order):
1. Content between `<json>…</json>` tags
2. Content in a ` ```json … ``` ` code fence
3. First top-level JSON array in the raw text

Raises `ValueError` if no array is found.

## Phase 3 — Testing Agent (`mcp_server/testing_agent/`)

Executes structured test cases against a deployed web application using a real
browser and real LLM calls. No pre-generated Playwright scripts — the agent
grounds and executes each step at runtime based on what it observes.

### Architecture

Two modules:

- **`browser.py`** — `BrowserSession` async context manager: one isolated
  Playwright browser context per test case
- **`agent.py`** — `run_test_case()`: the per-test execution loop with two
  types of LLM calls (grounding + verification)

### `browser.py` — BrowserSession

```python
async with BrowserSession(app_url) as session:
    obs  = await session.observe()   # {accessibility_tree, screenshot}
    await session.act(action_dict)   # execute a Playwright action
```

#### `observe() -> dict`

Returns the current page state as two representations:

| Key | Type | Content |
|-----|------|---------|
| `accessibility_tree` | `str` | ARIA snapshot in YAML format (via `locator.aria_snapshot()`) |
| `screenshot` | `str` | base64-encoded PNG |

**Why ARIA snapshot instead of a DOM tree:**
`page.accessibility.snapshot()` was removed in Playwright 1.47. The direct
replacement is `page.locator('body').aria_snapshot()`, added in Playwright 1.46.
A JS-evaluated DOM tree was considered but rejected after measuring the size
difference on real pages:

| Representation | Simple page | Realistic app (nav + form + table) |
|----------------|-------------|-------------------------------------|
| ARIA snapshot  | 100 chars   | 1,259 chars |
| DOM tree (JSON) | 1,003 chars | 9,247 chars |
| **Ratio**      | **10× larger** | **7× larger** |

The ARIA snapshot is also semantically richer for LLM grounding: it exposes
roles (`textbox`, `button`, `combobox`) rather than raw HTML tags (`input
type=text`, `button`), which maps directly to how natural-language steps
describe user interactions.

#### `act(action: dict) -> None`

Dispatches one Playwright action from a dict produced by the grounding LLM:

| Action | Required keys | Effect |
|--------|--------------|--------|
| `navigate` | `url` | `page.goto(url)` |
| `click` | `selector` | `page.click(selector)` |
| `fill` | `selector`, `value` | `page.fill(selector, value)` |
| `press` | `key` | `page.keyboard.press(key)` |

**Chromium executable:** The installed Playwright 1.58 cannot auto-download
its expected binary due to network constraints. The pre-installed
`chromium-1194` binary is used directly:
```
/root/.cache/ms-playwright/chromium-1194/chrome-linux/chrome
```
Override via `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` environment variable.

### `agent.py` — Unified Agent Loop

#### `run_test_case(test_case: dict, app_url: str) -> dict`

Executes one structured test case and returns a result dict. The LLM drives the
browser end-to-end in a loop: each iteration it sees the full test context,
trajectory of actions taken so far, and current page state, then decides whether
to execute a browser action or issue a verdict.

**Input (`test_case`):**
```json
{
    "test_id":  "TC-01",
    "feature":  "User can add a task",
    "steps":    ["Fill the task input with 'Buy milk'", "Click the Add button"],
    "expected": "'Buy milk' appears in the task list"
}
```

**Output:**
```json
{
    "result":         "pass" | "fail" | "partial",
    "trajectory":     [
        {"step": "Fill #task-input with 'Buy milk'", "action": {...}, "status": "executed"},
        {"step": "Click #add-btn", "action": {...}, "status": "executed"}
    ],
    "failure_report": ""
}
```

**Agent loop (max 15 iterations):**

```
Browser opens app_url automatically (BrowserSession.__aenter__).

For each iteration:
  1. observe()          → ARIA snapshot + screenshot
  2. Build user message:
     - Full test context: feature, steps, expected (constant)
     - Trajectory so far: actions taken + results (grows)
     - Current page state: ARIA tree + screenshot
  3. LLM call → returns ONE JSON object:
     - {"action": "click/fill/press/navigate", ...} → execute action
     - {"verdict": "pass/fail/partial", "reason": "..."} → terminate
  4. If action:
     - Execute via session.act()
     - On success: record in trajectory, continue
     - On Playwright error: record error, continue (LLM self-corrects)
  5. If verdict:
     - Return {result, trajectory, failure_report}

If loop exhausted → return fail.
```

**Key properties:**
- **Stateful**: LLM sees full trajectory each iteration, enabling self-correction
- **Handles observational steps**: "Locate the menu" doesn't need a browser action —
  the LLM confirms it sees the element and moves on
- **Fail-safe**: Playwright errors don't terminate — LLM retries with corrected selectors
- **Unified**: Same LLM call handles action selection and final verdict (no separate
  grounding + verification phases)
- **Relative URL resolution**: `"/"` → `app_url + "/"`

#### LLM calls

**Single unified call** (one per iteration):

- Input: full test context (feature, steps, expected) + trajectory so far +
  ARIA snapshot + screenshot of current page
- Output: a single JSON object — either an action dict (`{"action": "click", ...}`)
  or a verdict dict (`{"verdict": "pass", "reason": "..."}`)
- System prompt instructs the model to output only JSON (no prose)
- Thinking tags (`<think>...</think>`) from reasoning models are stripped before parsing

**Provider support:**

| Provider | Env var `TESTING_AGENT_PROVIDER` | SDK | Image format |
|----------|--------------------------------|-----|-------------|
| Anthropic (default) | `anthropic` | Anthropic SDK | `source.type=base64` |
| Together.ai | `together` | OpenAI SDK | `image_url` data URI |

Model is configurable via `TESTING_AGENT_MODEL` environment variable.

## Phase 4 — Development Protocols (`protocols/`)

Orchestration scripts that **programmatically enforce** the TDD workflow and
development ordering. The protocol holds the test-case queue, drives the dev
agent, triggers deployment and test execution, and gates progression. This is
genuine enforcement — the agent cannot skip steps or reorder the loop.

Two protocols implement the two experimental conditions:

| File | Condition | Strategy |
|------|-----------|----------|
| `whole_project.py` | A — Whole-project | Build all features once, then deploy → test → fix in a loop |
| `incremental.py` | B — Incremental | Build one feature at a time, test with growing regression suite |

Both protocols share the same dependency-injection contract (no hardcoded
subprocess calls) so they can be fully unit-tested without a real browser or
LLM.

### Shared constants

```python
MAX_ATTEMPTS = 5   # maximum deploy-test-fix iterations per protocol/feature
```

`MAX_ATTEMPTS` is a research variable. All attempts are logged so
`accuracy@k` (k = 2..5) can be computed post-hoc — the plateau point
becomes the recommended production budget.

---

### `whole_project.py` — Condition A

```python
from protocols.whole_project import run_whole_project

result = run_whole_project(
    test_cases   = [...],          # all structured test cases
    dev_agent    = agent,          # object with .implement(test_cases), .fix(report)
    start_app    = lambda: ...,    # deploy the application
    run_tests    = lambda tcs: {   # returns {"results": [...]}
                       "results": [{"test_id": ..., "result": ..., "failure_report": ...}]
                   },
    log_result   = lambda attempt, results: ...,
    max_attempts = 5,              # optional override
)
# result = {"log": [{attempt, results, all_pass}, ...], "final_pass": bool}
```

**Execution flow:**

```
dev_agent.implement(all_test_cases)          ← build once

for attempt in 1..MAX_ATTEMPTS:
    start_app()
    results = run_tests(all_test_cases)
    log_result(attempt, results)             ← always logged for accuracy@k
    if results.all_pass: break
    dev_agent.fix(classify(results))         ← called after every failing attempt
```

`dev_agent.fix` receives a human-readable classification report that
distinguishes *regressions* (previously passing tests now failing) from
*new failures* (features not yet confirmed passing). This is produced by
`_classify(results, passed_suite)`.

---

### `incremental.py` — Condition B

```python
from protocols.incremental import run_incremental

result = run_incremental(
    test_cases   = [...],          # test cases processed in order
    dev_agent    = agent,          # object with .implement(tc), .fix(report)
    start_app    = lambda: ...,
    run_tests    = lambda tcs: {"results": [...]},
    log_result   = lambda tc, attempt, results: ...,
    max_attempts = 5,
)
# result = {"passed_suite": [...], "failed": ["TC-id", ...], "log": [...]}
```

**Execution flow:**

```
passed_suite = []

for tc in test_cases:
    dev_agent.implement(tc)

    for attempt in 1..MAX_ATTEMPTS:
        start_app()
        outcome = run_tests(passed_suite + [tc])   ← regression suite + current
        log_result(tc, attempt, outcome)
        if outcome.all_pass:
            passed_suite.append(tc)
            break
        dev_agent.fix(classify(outcome, passed_suite, tc))
    else:
        mark_failed(tc)                            ← never joins passed_suite
```

**Key property:** `passed_suite` only ever contains *confirmed-passing*
features. A feature that hits the attempt ceiling is abandoned without
contaminating the regression baseline for subsequent features.

---

### `_classify(results, passed_suite, current_tc)` — failure report format

Both protocols call `_classify` to build the string passed to
`dev_agent.fix`. Example output:

```
Regressions (1): TC-01
New failures (1): TC-02
  [TC-01] Playwright action failed at step 2: 'Click Submit'. Error: ...
  [TC-02] Grounding failed at step 1: 'Click the Export button'. ...
```

The distinction between regressions and new failures gives the dev agent
precise information about whether a code change broke existing functionality
or simply hasn't implemented a new feature yet.

---

### `run_tests` return format

Both protocols expect `run_tests` to return:

```python
{
    "results": [
        {
            "test_id":        "TC-01",
            "result":         "pass" | "fail" | "partial",
            "failure_report": str,   # empty string on pass
        },
        ...
    ]
}
```

`all_pass` is `True` only when every entry has `result == "pass"`.
`"partial"` counts as a failure for the purpose of loop continuation.

## Phase 5 — Experiment Infrastructure (`experiment/`)

Three modules that load benchmark data, run experiment cases, and compute
metrics. All depend on the Phase 1–4 implementations via dependency injection
so they can be fully tested without a real browser, LLM, or subprocess.

### `experiment/loader.py` — reproducible sampling

```python
from experiment.loader import sample_cases

cases = sample_cases(
    bench_path     = "data/test.jsonl",
    converted_path = "data/converted_test_cases.jsonl",
    n              = 5,
    seed           = 42,
)
# Each case: all original bench fields + "test_cases": [...]
```

`sample_cases` uses `random.Random(seed)` to draw a fixed random sample from
the full benchmark. The seed makes experiment runs reproducible: calling with
the same seed always returns the same case IDs in the same order.

Each returned item contains all original WebGen-Bench fields (`id`,
`instruction`, `Category`, `ui_instruct`, …) plus a joined `test_cases` list
from the converted JSONL file. Items with no converted entry receive an empty
`test_cases` list.

### `experiment/metrics.py` — accuracy@k

```python
from experiment.metrics import load_log, compute_accuracy_at_k, summarize

entries = load_log("results/000001_A.jsonl")
print(summarize(entries))
# {"accuracy@1": 60.0, "accuracy@2": 60.0, "accuracy@3": 80.0,
#  "accuracy@4": 80.0, "accuracy@5": 80.0}
```

**Log entry format** (one JSON object per line):

```json
{
    "case_id":        "000001",
    "condition":      "A",
    "tc_id":          "TC-01",
    "attempt":        1,
    "result":         "pass",
    "failure_report": ""
}
```

**Extended experiment summary** (`build_summary` in `full_experiment.py`) groups
per-condition results and separates cases that never passed from those that
eventually did, so that accuracy averages are not silently diluted:

```python
{
    "per_condition": {
        "A": {
            "accuracy@1": 66.7,   # averaged over eventually-passed cases only
            "accuracy@2": 83.3,
            "accuracy@3": 83.3,
            "accuracy@4": 83.3,
            "accuracy@5": 83.3,
            "never_passed":        1,    # cases that failed every attempt
            "n_eventually_passed": 2,    # cases counted in accuracy@k averages
            "final_pass_rate":    "2/3", # human-readable fraction
        },
        ...
    },
    "per_case_condition": {
        "000001": {
            "A": {"final_pass": True,  "accuracy@1": 100.0, ...},
            "B": {"final_pass": False, "accuracy@1":   0.0, ...},
        },
        ...
    }
}
```

`never_passed` cases are shown explicitly in reports but excluded from the
`accuracy@k` average, keeping the metric unbiased.

**`compute_accuracy_at_k(log_entries, k)`**

For each unique `tc_id`, determines the best result achieved by attempt ≤ k
(priority: pass > partial > fail), then applies the WebGen-Bench formula:

```
accuracy@k = (N_pass + 0.5 × N_partial) / N_total × 100
```

| k | Interpretation |
|---|---|
| 1 | 1 build (no fix) |
| 2 | 1 build + 1 fix |
| 3 | 1 build + 2 fixes |
| 4 | 1 build + 3 fixes |
| 5 | 1 build + 4 fixes (full budget) |

`accuracy@k` is guaranteed monotone non-decreasing: a test case that passes
at attempt ≤ k also passes at attempt ≤ k+1.

**`append_log_entry(log_path, entry)`** — writes one JSON entry to a JSONL
log file, creating the file (and parent directories) if needed.

### `experiment/runner.py` — per-case orchestration

```python
from experiment.runner import run_case

summary = run_case(
    case         = {"id": "000001", "instruction": "...", "test_cases": [...]},
    condition    = "A",            # "A" | "B" | "C" | "D"
    dev_agent    = my_agent,       # .implement(tcs), .fix(report)
    start_app    = lambda: None,   # callable() → None
    run_tests    = lambda tcs: {"results": [...]},
    log_path     = "results/000001_A.jsonl",
    max_attempts = 5,
)
# summary = {"case_id", "condition", "log_path", "final_pass"}
```

Maps each condition to a protocol:

| Condition | Protocol used | Notes |
|-----------|--------------|-------|
| A — Whole-project | `run_whole_project` | Tools provided; loop enforced externally |
| B — Incremental | `run_incremental` | Tools provided; feature-by-feature loop |
| C — Agentic TDD | `run_whole_project` | Same loop, but dev_agent received TDD knowledge in its prompt |
| D — Baseline | single implement + evaluate | No fix loop; run_tests called once to measure accuracy |

Each attempt is logged in real time via `append_log_entry` so the file is
readable even if a run is interrupted.

**`run_case` always overwrites** an existing log at `log_path` before starting,
so re-running a condition gives a clean file (no stale entries from a
previous partial run).

## Phase 6 — MCP Server (`mcp_server/server.py`)

Registers all three logical tools (five callable names) with the Python MCP
SDK and exposes them via **stdio transport**. Any MCP-compatible coding agent
(Claude Code, OpenCode, etc.) can connect by adding the server to its MCP
configuration.

### Starting the server

```bash
python -m mcp_server.server
```

The server reads from stdin and writes to stdout using the MCP JSON-RPC
protocol.

**Claude Code** — configure in `.claude/settings.json`:

```json
{
  "mcpServers": {
    "tdd-web-agent": {
      "command": "python",
      "args": ["-m", "mcp_server.server"],
      "cwd": "/path/to/tdd-web-agent"
    }
  }
}
```

**OpenCode** — configure in `.opencode.json` in your project root:

```json
{
  "mcpServers": {
    "tdd-web-agent": {
      "type": "local",
      "command": "python",
      "args": ["-m", "mcp_server.server"],
      "env": {
        "PYTHONPATH": "/path/to/tdd-web-agent"
      }
    }
  }
}
```

`type: "local"` tells OpenCode to launch the server as a child process over
stdio. Because OpenCode does not support a `cwd` field, `PYTHONPATH` is used
instead so that `python -m mcp_server.server` resolves the package correctly
from any working directory.

---

### Registered tools

| Tool name | Maps to | Required args |
|-----------|---------|---------------|
| `generate_test_cases` | `tools/test_generation.py` → `generate_test_cases()` | `requirements` |
| `start_app` | `tools/deployment.py` → `start_app()` | `project_dir` |

### Error handling

Input validation is handled **inside the dispatcher** (not by the MCP SDK's
schema validator). This means:

- Missing required arguments → `{"error": "Missing required argument: 'project_dir'", "tool": "start_app"}`
- Unknown tool name → `{"error": "Unknown tool: 'foo'", "tool": "foo"}`
- Runtime exception (e.g. port never opens) → `{"error": "<exception message>", "tool": "start_app"}`

The server **never crashes** on bad input. Subsequent calls in the same
session continue to work normally.

## ArtifactsBench Integration

The framework generalises beyond WebGen-Bench to **ArtifactsBench** (Tencent, 2025) — a
1,825-sample benchmark of self-contained HTML/CSS/JS artifacts (games, charts, widgets).
Since ArtifactsBench artifacts are single HTML files, the evaluation modality changes from
*test execution* to *screenshot-based VLM judging*, while the TDD protocol is unchanged.

### Pipeline

```
ArtifactsBench question + GT checklist
  → HtmlDevAgent (Claude Code)  → index.html (single self-contained file)
  → start_app (static_html)     → python3 -m http.server <port>
  → screenshot_and_judge        → Claude Sonnet evaluates screenshot vs GT checklist
  → (on failure) fix loop       → HtmlDevAgent fixes with failed items as feedback
```

Tool 1 (`generate_test_cases`) is **not used** in this pipeline. The ground-truth
checklist is passed directly to both the dev agent and the VLM judge, so scores are
directly comparable across conditions.

### Experimental conditions

| Condition | Prompt | Fix loop |
|-----------|--------|----------|
| **A** | Standard — "build this; satisfy every checklist item" | Yes, up to `MAX_ATTEMPTS` |
| **C** | TDD — "read checklist first, write minimal code to pass each item" | Yes, up to `MAX_ATTEMPTS` |
| **D** | Standard — same as A | No — single attempt, baseline |

Fix-loop feedback for A and C = list of failed checklist items + VLM failure reasons
from the previous judge pass. The fix prompt instructs the agent to read the existing
`index.html` and make the minimal changes needed to resolve each failure.

### New components

| File | Purpose |
|------|---------|
| `mcp_server/testing_agent/screenshot_judge.py` | `screenshot_and_judge(checklist, url)` — Playwright screenshot → Claude Sonnet VLM → per-item pass/fail + 0–100 score |
| `experiment/artifacts_loader.py` | `fetch_artifacts_samples(n, seed)` — fetches samples from HuggingFace (cached in `data/artifacts_cache.json`) |
| `run_artifacts_bench.py` | End-to-end orchestration: loads samples, runs conditions A/C/D, writes `results/artifacts_<ts>/report.md` |

### Static HTML deployment (new in `deployment.py`)

`detect_framework` returns `framework="static_html"` when a directory contains
`.html` files but no `package.json`. `start_app` then launches `python3 -m http.server
<port>` instead of a Node.js dev server — no npm required.

```python
detect_framework("/tmp/snake_game/")
# → {"framework": "static_html", "dev_command": "python3 -m http.server", "default_port": 8080}
```

### Example results (3 samples, seed=42, dev agent: claude-haiku-4-5-20251001)

Using GT checklist directly as judge input for all conditions:

| Sample | Difficulty | A final | C final | D final |
|--------|------------|---------|---------|---------|
| Data Science | Medium | 71.4% | 71.4% | 71.4% |
| Game Development | Medium | 100.0% | 100.0% | 85.7% |
| Web Applications | Easy | 100.0% | 100.0% | 100.0% |
| **avg** | | **90.5%** | **90.5%** | **85.7%** |

Key observations:
- A and C both reach 100% on Game Dev and Web Apps; the fix loop resolves the game restart-button issue that D misses.
- Data Science is stuck at 71.4% across all conditions and all 5 attempts: the two failing items (hover highlight, tooltip on hover) are inherently dynamic and cannot be confirmed from a static screenshot — a hard ceiling for screenshot-based evaluation.
- A and C perform identically on these samples; the TDD prompt (condition C) does not add measurable benefit over a standard prompt when the checklist is already visible.
