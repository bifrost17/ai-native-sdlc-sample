# 조항 × 스킬 — ux (S4)

행은 `policies/ux.md` 의 조항 ID, 열은 채택·설계한 스킬. 칸은 **덮음** · **부분** · **—**.
「덮음」의 뜻: 그 스킬을 로드한 세션이 그 조항을 실제로 확인하게 만드는 문장이 있다.
「부분」: 소재는 건드리지만 조항이 요구하는 데까지 가지 않는다(예: 「로딩 상태를 보여라」는 있으나
예상 시간·확인 시점을 적으라는 말은 없다).

## 채택·설계한 집합

| 조항 | claims-ux-copy (설계) | claims-ux-interaction (설계) | ux-copy (채택 · Apache-2.0) | accessibility (채택 · MIT) |
|---|---|---|---|---|
| **U1** 오류 메시지 세 요소 | **덮음** | — | **덮음** | 부분 |
| **U2** 다섯 어휘 + 「다음 예정」 | **덮음** | — | — | — |
| **U3** 대기 안내(예상 시간·확인 시점) | **덮음** | — | 부분 | — |
| **U4** 파괴적 동작(확인 + 되돌리기) | — | **덮음** | 부분 | — |
| **U5** 한 화면에 한 번 | — | **덮음** | — | — |
| **U6** 접근성 3요소 | — | **덮음** | — | **덮음** |

여섯 조항이 모두 덮인다. 근거는 각각:

- **U1** — 설계분이 조항 원문을 인용하고 세 요소를 하나씩 확인하게 한다(순서·문장 수는 정책이 아니라 스킬의 기본값이라고 본문에 밝혔다)(`skills/claims-ux-copy/SKILL.md`
  U1 절). 채택분 `ux-copy` 는 같은 형(型)을 영문 일반 규범으로 준다: `Structure: What happened + Why + How to fix`.
- **U2** — 설계분만. 다섯 어휘(접수·심사중·보완요청·지급완료·종결)와 상태마다의 「다음 예정」 한 줄을
  화면·목록·알림 어디서나 한 단위로 두게 한다. 어휘의 정본은 브랜드 **B4** 다.
- **U3** — 설계분만 실질적으로 덮는다. 채택분 `ux-copy` 의 `### Loading States` 는 `Set expectations, reduce anxiety`
  한 줄이라 수치·시점 요구가 없다(부분).
- **U4** — 설계분이 「확인 단계」와 「되돌리는 경로」를 **둘 다** 요구하고, 어느 한쪽만으로는 안 된다고 못박는다.
  채택분 `ux-copy` 는 확인 다이얼로그의 꼴(`Delete 3 files?` · 버튼에 동작 이름)까지만 간다(부분).
- **U5** — 설계분만. 사실 하나당 자리 하나, 주 동작 하나, 같은 안내를 배너·헬퍼·툴팁으로 되풀이하지 않기.
- **U6** — 설계분이 바닥선 세 가지(대체 텍스트 · 색만으로 구분 금지 · 키보드만으로 조작)를 지고,
  채택분 `accessibility` 가 같은 세 가지를 코드 수준으로 덮으면서 WCAG 2.2 전체 감사 절차를 준다
  (48행 `Images require alt text`, 129행 `Don't rely on color alone`, 171행 `All functionality must be keyboard accessible`).

## 「덮음」이 실제로 뜨는가 — 트리거로 본 단서

행렬은 「그 스킬을 로드하면 조항을 확인하게 된다」를 말한다. **로드되느냐**는 따로 재야 한다
(`trigger-tests.md`). 실측에서 나온 두 가지를 여기 붙여 둔다.

- **U1 의 채택분은 청구 레포 안에서 단독으로 뜨지 않는다.** 같은 자리를 설계분 `claims-ux-copy` 가
  먼저 가져간다(raw/26·27). 정책이 걸린 자리이므로 그것이 옳은 동작이라 트리거를 고치지 않았고,
  채택분은 도메인 밖(사내 관리 도구)에서 떴다(raw/35·36). **U1 을 실제로 지고 있는 것은 설계분이다.**
- **U6 의 채택분은 설계분이 불러 줘야 뜬다.** 처음에는 감사 스킬이 설계분에 가려 1/3 이었다(raw/32 성공,
  33·34 실패). 설계분 U6 절에 「마크업·화면을 건드리면 `accessibility` 를 함께 로드하라」를 넣고 다시
  시험했다(raw/42~44). 행렬의 U6 두 칸은 그 짝을 전제로 읽어야 한다.

## 겹침

- **U1 이 둘에 있다** — 설계분 `claims-ux-copy` 와 채택분 `ux-copy`. 모순이 아니라 층이 다르다:
  채택분은 마이크로카피 **일반형**(영문 예시, 빈 상태·CTA·툴팁까지), 설계분은 **청구 도메인의 문면**
  (한국어, 실패 분기 열거, 내부 코드 금지의 범위, 로그와 화면의 분리). 트리거도 갈린다 —
  채택분은 "빈 화면 문구"·"버튼 라벨" 같은 일반 카피 요청에서 떴고(raw/26·27), 설계분은 청구·오류·상태·대기
  문구 요청에서 떴다(raw/20~22).
- **U6 이 둘에 있다** — 설계분 `claims-ux-interaction` 과 채택분 `accessibility`. 설계분은 **모든 변경이
  통과해야 하는 바닥선**, 채택분은 **감사 절차**(자동 검사 → 수동 키보드 → 스크린리더 → 심각도)다.
  설계분 U6 절의 마지막 문단이 채택분을 이름으로 가리켜 경계를 긋는다.
- **U4 의 절반이 채택분에도 있다** — `ux-copy` 의 확인 다이얼로그 절. 설계분이 「확인만으로는 U4 를
  만족하지 않는다」를 명시하므로 한 답에 같이 놓여도 지시가 갈리지 않는다(집합 시험 raw/50).

## 모순

**집합 안에는 없다.** 확인한 범위는 `trigger-tests.md` 의 집합 시험(네 스킬을 모두 넣고 같은 과제를 시킴).
다만 한 곳은 **간극**이라 적어 둔다: 채택분 `ux-copy` 는 확인 다이얼로그의 예로
`Describe consequences: "This can't be undone"` 를 든다. 그 자체로 U4 와 부딪히지는 않지만(경고는 필요하다),
**되돌리는 경로**를 요구하지 않으므로 그것만 따르면 U4 에 못 미친다. 그래서 설계분이 U4 절 첫 문단에서
「확인만으로도, undo 만으로도 U4 를 만족하지 않는다」를 못박고, 채택분 PROVENANCE 4번에도 같은 말을 적었다.

**집합 밖에서는 흔했다** — 기각 사유의 다수가 이것이다. 되풀이된 세 가지:

1. **「undo 가 확인보다 낫다」** — 정책 U4 는 둘을 함께 두라고 한다. wondelai/skills `ux-heuristics`
   (`Undo beats "Are you sure?" dialogs`, `prefer undo over confirmation dialogs`) ·
   cuellarfr/design-skills `error-prevention.md`(`Confirmation dialogs ("Are you sure?") are excise… Undo is almost
   always better.`, `Delete immediately. Show "Undo" toast for 10 seconds`) · vercel-labs/web-interface-guidelines
   (`Destructive actions need confirmation modal or undo window—never immediate` — **또는**로 본다).
2. **대기 문구를 시간 없이 끝내기** — vercel-labs `command.md` 의 `Loading states end with "…"`,
   thedaviddias `loading-indicators`(즉시 피드백까지만). U3 은 예상 시간이나 확인 시점을 요구한다.
3. **브랜드와 부딪히는 문면 관행** — szilu `09-ux-writing.md` 의 느낌표 성공 문구(`Order placed!`)와
   유머러스한 로딩 문구는 브랜드 B7·B1 에 걸린다. 토스 계열 3종의 해요체 강제(`Avoid mixing formal styles
   like 합니다, 하십시오`)는 어조를 정하는 자리(B1·S2 레인)를 침범한다.

## 빈칸과 이유

집합에는 **조항 차원의 빈칸이 없다**. 아래는 「기존 스킬로 덮지 못해 설계로 메운 자리」와 그 이유다.

| 빈칸 | 무엇을 못 찾았나 | 왜 비었나 |
|---|---|---|
| **U2 를 덮는 기존 스킬** | 열어 본 스킬 30여 개 중 **0건** | 상태 어휘는 **조직의 도메인 언어**다. 세상의 UX 스킬은 「용어를 일관되게 쓰라」까지만 말하고(예: `ux-copy` 의 `Consistent: Same terms for the same things everywhere`), 어떤 낱말인지는 조직이 정한다. 다섯 어휘·「다음 예정」은 `policies/brand.md` B4 와 `policies/ux.md` U2 에서만 나온다 |
| **U3 를 덮는 기존 스킬(쓸 수 있는 것)** | 정량 요구가 있는 것 2건뿐, 둘 다 못 쓴다 | cuellarfr/design-skills 는 `Estimate time when possible — "About 2 minutes remaining"` 로 정확히 U3 를 말하지만 **같은 파일이 U4 와 모순**이라 집합에 들일 수 없다. talkstream/ru-text 는 `укажите типичное время`(전형적 소요 시간을 적어라)로 같은 말을 하지만 **러시아어 전용** 규칙이다. 영어권 스킬은 일관되게 「로딩 상태를 보여라」에서 멈춘다 |
| **U5 를 덮는 기존 스킬** | 0건 | 「같은 정보는 한 화면에 한 번만」은 화면 **편집** 규칙이라 문구 스킬에도 감사 스킬에도 없다. 가장 가까운 것이 oil-oil/ui-ux-guide 의 `One primary submit action` 과 content-designer 의 `Combine redundant information` 인데, 둘 다 중복 **금지**가 아니라 간결함의 조언이다 |
| **U4 를 덮는 기존 스킬** | 0건(가장 가까운 것도 택일) | 위 「모순」 1번. 업계 관행이 정책과 반대 방향이라, 찾을수록 반례가 쌓였다 |
| **한국 법정 접근성 기준(KWCAG 2.2)** | 스킬 1건 있으나 **라이선스 없음** | jun-2525/kwcag22-skills 가 5.1.1·5.4.1·6.1.1 을 조항 번호로 덮지만 LICENSE 파일이 없다(a11ykr/kwcag22 도 같음). 채택분 `accessibility` 는 WCAG 2.2 기준이라 조항 번호가 다르다. 어느 기준을 정본으로 삼을지는 정책 결정 → README 「정책 오너에게 묻는다」 2번 |
| **한국어 문구 규범** | 스킬 4건 있으나 전부 어조 스킬 | 토스 계열 3종과 gayoung0316 은 해요체·존댓말 수준을 정하는 스킬이다. 그것은 이 레인이 아니라 브랜드 정책(B1)과 S2 의 소관이라 채택하지 않았다. 설계분은 문면의 **구성**만 다루고 어조는 브랜드 스킬에 넘긴다 |
| **웹이 아닌 화면의 U6** | 없음 | 채택분의 예시는 전부 HTML/CSS/JS 다. 사정인·상담사 화면이 웹이 아니면 코드 패턴을 옮길 수 없고, 설계분의 세 가지 바닥선만 남는다 → README 「남는 구멍」 |

## 이 집합이 통제하지 않는 것

- **어조·표기**(존댓말, 금칙어, 날짜·금액·시각 표기) — `policies/brand.md` B1~B7, S2 레인.
- **문서 산문**(README·정책 문서의 문체) — 이 레인의 대상이 아니다.
- **강제력** — 스킬은 권고적 통제다(레슨: `A skill is a control, though an advisory one.`
  `raw/40-lesson-notes.txt`). U 조항을 어긴 변경을 **막으려면** 훅이나 리뷰 통과가 뒤를 받쳐야 한다.
  이 레포에는 그런 훅이 없다 → README 「정책 오너에게 묻는다」 3번.
