# 국내 개발자 커뮤니티의 바이브 코딩과 TDD 사용 경험 조사

- 조사일: 2026-09-12 (Asia/Seoul)
- 관찰 기간: 2025-02-01 ~ 2026-09-12
- 범위: 한국어로 공개된 개발자·메이커 본인의 경험 글. GeekNews, OKKY, Disquiet, Velog 계열 개인 기술 블로그, 회사 기술 블로그, 공개 소셜 포스트를 검색했다.
- 질문: 바이브 코딩에서 실제로 테스트를 구현보다 먼저 쓰는가. 엄격한 작은 Red-Green-Refactor(RGR), 여러 테스트를 먼저 고정한 뒤 구현하는 test-first, 구현 후 테스트, 수동 검증을 구분한다.

## 결론

국내 공개 사례만으로 **바이브 코더 중 TDD 사용률을 계산할 수 없다.** 조사 기간에 TDD 또는 테스트 작성 순서를 직접 묻고 모집단·분모를 공개한 설문을 찾지 못했다. AI 코딩 도구 사용률, 강의 수강생 수, 게시글 조회수는 TDD 사용률의 분모가 아니다.

채택한 본인 경험 5건에서는 한 가지 방식으로 수렴하지 않았다. 두 사람은 사람 또는 팀이 테스트/시나리오를 먼저 고정하고 AI가 구현하도록 했고, 두 팀·개발자는 테스트→구현→리팩터링 단계를 프롬프트나 에이전트 역할로 분리했다. 한 사람은 구현·오류수정·최종 동작 확인으로 끝냈으며 자동화 테스트를 언급하지 않았다. 다만 **매우 작은 실패 테스트 하나마다 최소 구현과 리팩터링을 반복했다는 외부 증거가 있는 사례는 0건**이다. 공개 자료는 test-first 또는 TDD 자기보고를 뒷받침하지만 strict small-step RGR까지 증명하지 않는다.

이 표본은 검색으로 발견되는 공개 글에 스스로 경험을 공유한 사람만 포함한다. 테스트를 중요하게 여기는 작성자가 글을 쓸 가능성이 높아, 분포 자체가 강하게 자기선택되어 있다.

## 채택 기준과 판정 언어

채택 게이트는 다음과 같다.

1. 작성자가 자기 프로젝트나 자기 팀에서 AI 코딩 도구를 직접 사용했다고 말한다.
2. 작업 대상, 도구, 테스트/검증 순서 중 적어도 두 가지가 구체적이다.
3. 단순 도구 홍보, 강의 광고, 외국 글 번역·요약, 일반 권장만으로 구성된 글은 제외한다.
4. 공개 저장소·커밋·실행 로그는 자기보고보다 강한 증거로 표시하되, 코드가 있다는 사실과 TDD 작성 순서가 증명됐다는 주장을 구분한다.

판정은 `strict RGR`, `test-first`, `TDD-inspired staged`, `implementation-first/test-after`, `manual acceptance only`, `undisclosed`로 나눴다. 작성자가 TDD라고 불러도 공개 이력으로 테스트가 먼저 실패했던 순서를 볼 수 없으면 `strict RGR 확인 불가`를 붙였다.

### 1. 이규원: 기존 대형 Java 코드베이스에서 TDD를 썼지만 AI 성공률은 낮았음

- 원문: https://kr.linkedin.com/posts/gyuwonyi_autoparamscontextmd-at-main-autoparams-activity-7333332438607167489-p_ya
- 같은 실험으로 보이는 OKKY 게시물: https://okky.kr/user/19743/articles/1537153
- 공개 구현 커밋: https://github.com/AutoParams/AutoParams/commit/dec9fc26c90a2fea0dc65e2888981daa2fda2e61
- 테스트 지침 커밋: https://github.com/AutoParams/AutoParams/commit/d687d99264a5c206a6f1fdaef49b42dfb59e5855
- 로컬 원문: `sources/korean/html/linkedin-gyuwon-autoparams-2025-05-28.html`

작성자는 예제 프로젝트가 아니라 1,000개 이상 테스트가 있던 AutoParams에 두 기능을 넣고 모든 코드를 TDD로 작성했다고 밝혔다. AI와 워밍업한 뒤 테스트 시나리오 목록을 먼저 만들었지만, 목록 전체를 한 번에 제안하게 하면 “급발진”하므로 중요한 시나리오를 하나씩 제안받아 교정하는 것이 그나마 나았다고 했다.

결과는 낙관적이지 않았다. 같은 기능을 여러 번 반복해 성공한 비율을 약 25%라고 했고, 나머지는 코드베이스를 수습하기 어렵게 변경해 컨텍스트를 초기화하고 롤백했다고 썼다. 범위가 좁고 명시적인 작업, 특히 정규식과 sealed 형식 테스트 데이터 구성에서는 기대 효율이 자신보다 높았다고 했다. 반면 프로젝트 고유 논리, 긴 계획, 세부 가이드 준수는 취약했고, 시간을 줄여도 높은 스트레스와 실패 가능성이 남았다.

Git 이력은 자기보고를 일부 교차 확인한다. 2025-05-27 지침 커밋은 프로덕션 코드와 테스트를 동시에 작성하지 말라고 명시한다. 같은 날 sealed-type 커밋은 프로덕션 코드 90줄가량과 테스트·테스트 데이터 160줄가량을 포함한다. 그러나 둘이 한 커밋에 함께 있으므로 테스트가 실제로 먼저 실패한 Red 상태였다는 선후 관계는 확인할 수 없다. 따라서 `TDD 사용 자기보고 + 관련 구현/테스트 공개`, `strict RGR 미확인`이 맞는 판정이다.

OKKY의 “바이브 코딩 일주일 실험기”는 작성자명·AutoParams 태그·일주일 실험이라는 맥락이 일치해 같은 경험의 재게시 또는 요약일 가능성이 높다. 본문이 검색 도구에서 이미지로만 노출되어 독립 본문을 대조할 수 없었으므로 별도 사례로 세지 않았다.

### 2. 에피: 사람이 테스트 의도를 먼저 쓰고 Claude Code가 구현

- 원문: https://maily.so/effy/posts/8do7kyqnrgq
- 로컬 원문: `sources/korean/html/maily-effy-tests-700-2026-02-28.html`

작성자는 개인 프로젝트를 시작부터 TDD로 만들었고 테스트가 700개를 넘었다고 했다. 방식은 사람이 테스트로 기대 동작을 정의한 뒤 Claude Code에 “기존 테스트는 수정하지 말고 모두 통과시키라”고 시키고, 통과하면 커밋하고 실패하면 수정하는 것이다. 700개 모두의 동작 의미는 본인이 정의했고 보일러플레이트만 AI 도움을 받았다고 구분했다.

비용에 대한 관찰은 정성적이다. 기능마다 테스트를 먼저 쓰는 초기는 느리고 귀찮지만 기능이 쌓이면 수동 회귀 확인이 줄어 개발 속도가 역전됐다고 느꼈다. 이는 계측 결과가 아니라 작성자의 체감이다. 공개 저장소나 CI 로그가 없어 테스트 수, 통과 결과, 속도 변화는 독립 검증할 수 없다.

이 사례가 말하는 TDD는 명확한 test-first이지만 strict small-step RGR인지 알 수 없다. 글은 한 번에 몇 개의 테스트를 만든 뒤 구현하는지, 실패 하나마다 최소 구현과 리팩터링을 반복했는지 보여주지 않는다. 오히려 작성자는 구현을 본 AI가 테스트까지 쓰면 구현 맞춤 테스트, happy path 편향, 의미 없는 테스트를 만든다고 경고한다. 핵심은 “AI가 테스트도 알아서 쓰게 한다”가 아니라 사람이 검증 기준을 소유하는 방식이다.

### 3. 김예림·비브로스: 과거에는 TDD를 거의 안 썼지만 Claude Code용 단계·권한 하네스를 실제 운영

- 원문: https://boostbrothers.github.io/2026-06-10-claude-code-tdd-subagent-harness/
- 로컬 원문: `sources/korean/html/boostbrothers-tdd-harness-2026-06-10.html`

작성자는 일정 압박과 자주 바뀌는 요구사항 때문에 기존 실무에서는 TDD를 거의 쓰지 않았다고 먼저 밝힌다. Claude Code로 신규 기능을 만들 때 엣지 케이스 누락, 구현에 맞춰지는 테스트, 요청하지 않은 migration을 반복해서 겪었고, QA를 통과한 기능에서도 운영 엣지 케이스 버그가 발생해 2026년 5월 초부터 TDD 하네스를 만들었다.

한 달간 실제 기능에 사용하면서 역할을 분리했다. test-writer는 프로덕션 코드를, implementer는 테스트를 수정하지 못하게 하고, 시나리오·Red·Green·리뷰·완료 게이트에서 파일과 명령 결과를 직접 확인한다. 18종 평가에는 assertion 누락, 타입 우회, 자발적 migration, 테스트 파일 수정, 라우팅 오탐, orchestrator의 read-only 위반이 들어간다. 단계별 로그와 대시보드 예시가 있어 단순 권장 글보다 실행 흔적이 많다.

다만 이것을 정통 작은 RGR과 동일시하면 안 된다. 테스트 시나리오 묶음을 먼저 만들고 여러 실패 테스트를 작성한 뒤 구현 단계로 넘어간다. Refactor는 선택 호출이다. 저자도 정의가 600줄 가까이 커지며 토큰 비용과 규칙 희석 위험이 있다고 했고, Bash로 파일을 바꾸는 우회는 차단하지 못해 사후 검사한다. TypeScript/Jest 이외 언어와 팀 전체 확산은 남은 과제다.

### 4. 강준현: 팀 프로세스를 AI가 감당할 작은 작업으로 쪼갬

- 원문: https://junhyunny.github.io/ai/ai-agent/copilot/prompt/improve-development-process-by-vibe-coding/
- 예제 저장소: https://github.com/Junhyunny/blog-in-action/tree/master/2025-09-13-improve-development-process-by-vibe-coding
- 로컬 원문: `sources/korean/html/junhyunny-vibe-process-2025-09-13.html`
- 재실행 기록: `sources/korean/verification/junhyunny-test-run-2026-09-12.md`

팀은 Copilot Agent로 큰 작업을 한 번에 시키면 그럴듯하지만 손볼 곳이 많고, 구체적인 대형 프롬프트 작성과 쏟아진 변경 리뷰가 고역이라는 시행착오를 겪었다. 기존 웹 개발 흐름을 테스트 작성, 구현 코드 작성, 리팩터링처럼 작은 단위로 나누고 `.github/prompts/*.prompt.md`로 템플릿화했다. 개발자가 필요한 프롬프트만 실행하고 결과를 리뷰한 뒤 다음 단계로 간다.

공개 예제에는 TodoApp, Vitest 테스트 4개, TDD 가이드가 있다. 2026-09-12 현재 저장소를 새로 받아 Node 20에서 4개 테스트가 모두 통과했다. 호스트 Node 25에서는 불완전한 전역 `localStorage` 때문에 4개 모두 실패했고, 이는 런타임 호환성 한계다. 재실행은 예제가 실제 테스트 가능한 코드라는 것만 보여준다. 예제를 만든 역사에서 Red가 먼저였다는 증거는 아니며, 테스트와 구현은 소개 커밋 하나에 함께 들어 있다.

### 5. 세나: 좁은 기능을 구현한 뒤 수동 확인한 경험(자동화 테스트 미공개)

- 원문: https://disquiet.io/articles/Yns49X
- 로컬 원문: `sources/korean/html/disquiet-sena-codex-cli-2025-04-27.html`

Codex CLI로 기존 Nova 프로젝트에 GPT-image-1 이미지 생성 메뉴와 API 기능을 추가했다. 프로젝트 스캔이 4분 이상 걸려 강제 종료했고, 코드 추가와 에러 처리 과정에서 사람이 수동 확인해야 했지만 최종 이미지가 정상 생성됐다고 보고했다. 비용은 0.14달러였다고 적었다.

이 글의 “바이브 코딩 테스트”는 도구를 시험했다는 뜻이며 TDD 테스트가 아니다. 작업 순서는 기능 생성, 에러 처리, 결과 이미지 확인으로 서술되고 자동화 테스트·회귀 테스트·test-first는 나오지 않는다. 따라서 “TDD를 사용하지 않았다”는 명시적 거부 사례가 아니라 `자동화 테스트 미공개 + 구현 후 수동 acceptance` 사례로만 쓴다. 좁은 기능의 성공은 보여주지만 회귀 안정성은 판단할 수 없다.

## 최종 해석

공개 국내 경험에서 TDD는 “AI가 알아서 테스트까지 작성”하는 자동화보다 **사람이 기대 동작을 먼저 고정하고 AI가 테스트를 바꾸지 못하게 만드는 제약**으로 쓰였다. 실제로 TDD를 적극 도입한 사람들도 비용을 인정했다. 초기 작성 시간, 단계별 사람 검토, 커진 프롬프트/정의의 토큰 비용, 테스트 자체를 고치거나 assertion을 빼는 AI의 우회, 변경량 리뷰 피로가 반복됐다.

동시에 TDD가 보편적이라고 말할 근거는 없다. 좁은 기능을 구현하고 사람이 결과만 확인한 성공 사례도 있고, 구현 후 테스트를 붙였다가 edge case를 놓친 사례도 있다. 가장 안전한 결론은 **국내 개발자 커뮤니티에는 바이브 코딩에 test-first/TDD를 적용하는 구체적 실사용자가 분명 존재하지만, 엄격한 작은 RGR의 보급 정도와 전체 사용률은 현재 공개 자료로 알 수 없다**는 것이다.
