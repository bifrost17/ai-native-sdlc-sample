# Intent: 사슬을 기계가 강제하는 레퍼런스가 없다

## Problem (문제)
플레이북은 intent → spec → plan 을 버전관리에 쓰고 다음 단계가 그것을 읽는다고
말한다. 그런데 그 사슬을 **기계가 강제하는** 레퍼런스가 없다. 공개 레퍼런스 레포
7개를 받아 실측했더니, 아티팩트 검증기를 두고 있다고 주장한 곳은 여럿이었지만
실효인 곳은 **0개**였다. 뚫린 자리는 매번 같은 종류였다: 코드 펜스 안의
`status: accepted` 를 문서의 주장으로 읽어 위조가 통했고, 훅 파일은 있는데
`settings.json` 에 배선이 없었고, 자리표시자를 대괄호로 잡으려다 정상 산문
(`[Art. 4]`)을 반려했고, 검사식이 한국어를 만나 전량 통과했다. 스캐폴드는 있고
강제는 없는 상태를 「도입했다」고 부르는 것이 지금의 기본값이다.

## Proposed outcome (원하는 결과)
읽는 사람이 세 가지를 **직접 확인**할 수 있는 레포가 남는다.
`make check` 하나로 강제가 살아 있는지(그리고 무엇을 안 보는지) 확인되고,
`git log --reverse` 로 사슬이 커밋 이력으로 읽히고, 규칙을 일부러 깨뜨리면
그 자리가 지정된 code 로 빨개진다. 「검증기가 있다」가 아니라 「검증기가 무엇을
잡는지 그 자리를 픽스처로 상주시켰다」가 완료 조건이다.

## Affected users and systems (영향 범위)
이 레포를 30분 안에 훑을 사람 · 사슬을 자기 조직에 옮겨 갈 사람 · CI(GitHub
Actions) · 로컬 훅 · 브랜치 보호 규칙. 외부 서비스와 조직 계정은 영향 범위 밖이고,
그것을 요구하는 플레이는 이월 원장에 이름으로 남긴다.

## Constraints (제약)
- C1 표준 라이브러리만 쓴다. 검증기·지표·검출기에 서드파티 의존을 두지 않는다 —
  읽는 사람이 설치 없이 돌릴 수 있어야 하고, 의존이 생기면 그 순간 레퍼런스가
  아니라 제품이 된다.
- C2 산문은 한국어로 쓰되 파일명·frontmatter 키·상태 어휘·절의 영문 토큰은 영어로
  고정한다. 리터럴 검사가 언어를 타면 죽는다.
- C3 플레이북 원문은 짧은 축자 인용과 출처 표기까지만 쓴다. 예제 코드 블록을 통째로
  옮기지 않고 우리 소재로 다시 쓴다.

## Open questions (미결)
- Q1 예제 사슬의 주제를 무엇으로 할 것인가 — 플레이북 예제(청구 상태 자가조회)를
  한국어로 재현할지, 우리 실제 요구에서 하나를 끌어올지. 답할 사람: 사용자.
- Q2 `created`(첫 대화 시각)를 발의자 자기 신고로 둘 것인가 — git 이 모르는 유일한
  값이라 대안이 없어 보이는데, 그렇다면 「신고값」이라고 지면에 못 박아야 한다.
  답할 사람: 사용자.
