# Spec: 사슬을 기계가 강제하는 샘플 레포 (from intent 0001)

## Requirements (요구)
- R1 아티팩트 검증기가 있고, 그 검증기가 무엇을 잡는지 각 자리마다 픽스처로 상주한다.
  red 픽스처는 「빨갛기만 하면 통과」가 아니라 **지정한 code 로** 빨개져야 한다.
- R2 강제층 훅 5개가 있고, 파일 존재가 아니라 **설정에 배선됐는지**를 시험이 잰다.
  차단 메시지에는 사유와 승인 경로가 함께 들어간다.
- R3 CI 가 게이트를 돌려 PR 을 실제로 막는다. 게이트는 SKIP 을 통과로 세지 않는다.
- R4 플레이북의 지표 쌍을 전부 지면에 적고, 이 샘플에서 계산 가능한 것만 스크립트로
  계산한다. 계산 불가는 빈칸이 아니라 **왜 불가인지**로 채운다.
- R5 사슬 3본(메타 · 기능 · 결함)이 실제 시간축 커밋으로 남는다. 사슬의 diff 자체가
  레포이므로, 사슬을 읽으면 레포가 왜 이 모양인지가 읽힌다.

## Design (설계)
검증기는 축마다 **어휘의 소유자**를 먼저 정하고 그 소유자가 우리인 것만 열거한다.
우리 규약이 소유하는 것(키 집합 · 상태 어휘 · 절 이름과 순서 · ID 규약)은 열거해도
다음 판에 죽지 않는다. 마크다운 문법은 하나만 신뢰한다 — 코드 펜스와 인라인 코드를
**모든 판정보다 먼저** 지운다. git 이 소유하는 것(상류 sha 해석 · 브랜치 위 승인)은
`git show`·`git diff` 라는 단일 통로로만 읽는다.

강제는 세 층으로 겹치되 각 층이 서로의 사각을 맡는다. 훅은 빠른 되먹임이지만 끄면
사라지고, CI 는 못 끄지만 detached HEAD 에서 브랜치 판정을 못 하고, 브랜치 보호는
둘 다 우회해도 남는다. 어느 층도 혼자 완결이라고 말하지 않는다.

`skills_applied` 가 빈 목록인 것은 기록 누락이 아니다. 이 사슬은 스킬이 존재하기 전에
쓰였고, 스킬은 이 spec 의 R2 가 만들어 내는 산출물이다.

## Constraints inherited (상속한 제약)
- C1 표준 라이브러리만 쓴다 — 검증기·지표·검출기 전부. 읽는 사람이 설치 없이 돌릴 수
  있어야 한다.
- C2 산문은 한국어, 파일명·frontmatter 키·상태 어휘·절의 영문 토큰은 영어로 고정한다.
- C3 플레이북 원문은 짧은 축자 인용과 출처 표기까지만. 예제는 우리 소재로 다시 쓴다.

## Constraints discovered (발견한 제약)
- C4 브랜치 위의 `accepted` 를 예외 없이 막으면 **승인 PR 자체가 빨개진다**. 승인 행위가
  곧 `status:` 를 고치는 커밋이기 때문이다. 그래서 「바뀐 줄이 `status:` 하나뿐인 승인」만
  통과시키는 예외를 둔다(D16). 폭이 한 줄을 넘으면 「고치면서 승인」이 된다.
- C5 CI 의 PR 체크아웃은 detached HEAD 라 브랜치 판정이 아예 돌지 않는다. 그 자리를
  조용히 비우지 않기 위해 판정 포기는 note 로 출력하고, 정본 방어는 브랜치 보호로 옮긴다.
- C6 단일 소유자 레포에서는 자기 PR 을 자기가 승인할 수 없다. 승인 경로의 실증은
  「리뷰 없는 PR 이 머지 불가」를 한 번 남기는 것으로 대신한다.

## Open questions from intent (intent 의 미결)
- Q1 answered: 플레이북 예제(청구 상태 자가조회)를 한국어로 재현한다. 우리 실제 요구를
  끌어오면 이 레포를 읽는 사람이 우리 도메인부터 배워야 해서 30분 투어가 깨진다.
- Q2 carried: `created` 는 자기 신고로 두되 지면에 「신고값」이라고 못 박는다. git 이
  모르는 유일한 값이라 대안이 없다는 판단이지만, 신고값을 지표(첫 대화 → 커밋 시간)의
  기점으로 쓰는 것이 타당한지는 지표가 실제로 돌아간 뒤에 다시 본다 — 소유자는 사용자.

## Flagged concerns (플래그)
- F1 검증기가 그린이라는 것은 「규약을 지켰다」이지 「좋다」가 아니다. 이 구분이 README 와
  `--help` 양쪽에 없으면, 다음 사람이 검증기를 품질 게이트로 오해한다. 소유자는 이 레포.
- F2 D16 의 전이를 허용 표(`ACCEPT_TRANSITIONS`)가 정의한다 — `draft`→`accepted` ·
  `draft`→`rejected` · `draft`→`superseded` · `accepted`→`superseded`. 이 표가 다스리는
  것은 **`accepted` 로 들어오는 전이뿐**이다: 검사 전체가 「지금 파일이 `accepted` 일
  때」만 도므로 도착 상태는 언제나 `accepted` 이고 나머지 세 줄은 도달하지 않는다.
  「표에 없는 전이는 전부 거부한다」던 옛 문면은 거짓이었다 — 표 밖 전이
  (`accepted`→`draft` · `accepted`→`rejected` · `superseded`→`draft`)는 이 축의
  사정거리 밖이라 그냥 지나간다. 특히 `accepted`→`draft` 는 이 검사가 **스스로 처방하는
  경로**(내용을 바꾸려면 draft 로 되돌려 다시 검토받는다)라 표에 넣어 거부하면 안 된다.
  표를 「완성」하려 하면 승인된 문서를 고칠 방법이 사라진다.
  그래서 `rejected` → `accepted` 와 `superseded` → `accepted` 되살리기가 red 다(둘 다 그
  전까지 통과했고, 뒤엣것은 지면 어디에도 없던 갈래였다). 승인 게이트의 안전한 기본값이
  deny-by-default 라는 근거로 **부모 세션이 잠정 결정**했고, 표 한 줄 편집으로 되돌릴 수
  있다. 되살리기를 열어 둘지는 여전히 판단이 남아 있다 —
  **product owner 확인 대기**. 소유자는 product owner.

## Out of scope (범위 밖)
실제 배포 대상 · 조직(Team/Enterprise) 계정이 필요한 관리형 설정과 관리형 코드 리뷰 ·
API 키가 필요한 evals 의 상시 실행 · OpenTelemetry 지표. 이것들은 지우지 않고 이월
원장에 **승격 조건과 함께** 남긴다 — 「안 했다」와 「못 한다」는 다르고, 승격 조건이
없으면 이월은 그냥 망각이다.

## Acceptance criteria (수용 기준)
- AC1 → R1 red 픽스처 전량이 각자 EXPECT 의 code 다중집합과 정확히 일치해 rc=1 이고,
  green 픽스처는 rc=0 이다. 템플릿은 반드시 rc=1 이다(게이트 상주 음성 대조).
- AC2 → R2 훅 파일을 지우지 않고 설정의 배선만 지워도 시험이 빨개진다.
- AC3 → R3 게이트 요약이 `N passed, M failed, K skipped` 를 찍고 M>0 이면 CI 가 실패한다.
- AC4 → R4 지표 스크립트가 계산 가능한 항목에 실값을, 불가한 항목에 사유를 출력한다.
- AC5 → R5 `intent/*/` 아래 세 사슬의 아티팩트 전량이 검증기 rc=0 이고, 게이트의 사슬
  검사가 SKIP 이 아니라 PASS 로 바뀐다.
