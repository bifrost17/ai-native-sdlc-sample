# Spec: 청구 상태 조회 엔드포인트 (from intent 0002)

## Requirements (요구)
- R1 인증된 세션으로 자기 청구 ID 를 조회하면 상태 · 다음 단계 · 예정일이 돌아온다.
  세션이 없으면 조회 자체가 거부되고 어떤 청구 값도 돌아오지 않는다.
- R2 응답에 나가는 필드는 허용 목록 한 곳이 정한다. 상류 원장에 필드가 새로 생겨도
  응답은 넓어지지 않는다 — 허용 목록에 이름을 더하는 커밋 없이는 아무것도 추가로
  나갈 수 없다.
- R3 같은 청구 ID 를 TTL(60초) 안에 다시 조회하면 상류 claims-core 를 다시 부르지
  않는다. TTL 이 지나면 다시 부른다.
- R4 응답 조립은 한 함수 · 허용 목록은 한 곳 · 라우트 등록은 한 파일 · 상류 접근은 한
  모듈로 모은다. 이 네 가지는 산문 규약이 아니라 기계가 재는 계약이다.

## Design (설계)
모듈 넷으로 자른다. 자르는 기준은 「무엇이 하나여야 하는가」이고, 그것이 곧 결정론
백스톱(`scripts/check_endpoints.sh`)이 재는 축이다.

`records.py` — 상류 claims-core 접근. 원장 레코드를 **거르지 않고** 그대로 돌려준다.
여기에만 TTL 캐시가 있다(R3). 캐시 키는 청구 ID, 값은 (만료시각, 레코드)이고
프로세스 메모리를 벗어나지 않는다.

`response.py` — 응답 단일 통로. `RESPONSE_FIELDS` 와 `build_response()` 가 여기
하나씩만 있다. `build_response` 는 허용 목록으로 딕셔너리를 만들어 직렬화하는 것
말고 아무것도 하지 않는다 — 거른 뒤 다시 넓히는 한 줄이 들어올 자리를 없앤다.

`routes.py` — 라우트 등록 단일 파일. 핸들러는 세션을 확인하고, 상류에서 레코드를
받아, 통로에 넘겨 반환한다. 레코드가 통로 말고 다른 곳으로 가는 경로가 없다.

엔드포인트 시그니처
```
GET /claims/<claim_id>/status
handler: get_claim_status(claim_id, session, now=None)
  session=None                → 200 {"error": "unauthenticated"}
  세션은 있으나 건이 없음/남의 건 → 200 {"error": "not_found"}
  정상                          → 200 응답 스키마
```

응답 스키마 — 허용 목록 네 개가 전부다
```
{"claim_id": "C-1001", "status": "심사중",
 "next_step": "손해사정 결과 접수", "due_date": "2026-09-15"}
```

없는 건과 남의 건을 같은 `not_found` 로 합친다 — 구분해 응답하면 청구 ID 의 존재
여부가 응답 차이로 새어 나간다(F2).

## Constraints inherited (상속한 제약)
- C1 새 개인식별정보를 포털 세션에 넣지 않는다 — 주민등록번호 · 계좌번호 · 내부 심사
  메모는 상류 레코드에 들어 있지만 응답 허용 목록에 없다.
- C2 기존 인증만 쓴다 — 핸들러는 포털이 넘긴 세션 객체의 유무만 본다. 새 토큰 발급 ·
  새 권한 모델 · 상담사 대리 경로를 만들지 않는다.
- C3 상류 claims-core 는 50rps 제한이다 — TTL 캐시가 그 한도를 지키는 장치이고,
  캐시가 없으면 이 기능은 켜지 않는다(R3).

## Constraints discovered (발견한 제약)
- C4 캐시가 들고 있는 것은 **거르기 전 원장 레코드**다. 상류를 한 번만 부르려면
  캐시가 통로 앞에 있어야 하기 때문이다. 그래서 캐시는 `records.py` 안에만 두고
  프로세스 메모리 밖(세션 · 디스크 · 로그)으로 내보내지 않는다. C1 을 지키는 것은
  「캐시에 PII 가 없다」가 아니라 「캐시가 통로를 우회하는 출구를 만들지 않는다」다.
- C5 「다음 단계」와 「예정일」은 상류 원장에 이미 `next_step` · `due_date` 로 있다.
  이번 범위에서 새로 계산하지 않는다 — 계산을 넣으면 상류와 포털이 서로 다른 답을
  말하기 시작한다.

## Open questions from intent (intent 의 미결)
- Q1 carried: 제3자 손해사정인 위임 조회는 이번 spec 이 답하지 않는다. 위임 관계의
  정본이 어디인지가 정해지지 않았고(청구운영팀 ↔ 법무), 그것이 정해지기 전에 만든
  권한 모델은 반드시 다시 만들어야 한다. 별도 intent 로 넘긴다 — 이번 설계는 위임
  경로를 「없음」으로 두되, 나중에 붙일 자리를 막지도 않는다(허용 목록과 통로가
  하나이므로 필드를 넓히는 결정이 한 곳에서만 일어난다).

## Flagged concerns (플래그)
- F1 TTL 60초 동안 옛 상태가 보인다. 「지급완료」로 바뀐 직후 최대 60초는 「심사중」이
  보이고, 그 사이 가입자가 콜센터에 전화하면 상담사와 화면이 다른 말을 한다.
  60초가 맞는 값인지 판단할 사람: 청구운영팀장.
- F2 없는 건과 남의 건의 응답을 합쳤다(위 설계). 열거 공격은 막지만, 자기 건인데
  오타로 못 찾은 가입자에게도 같은 문구가 나간다. 문구를 나눠 달라는 요청이 오면
  그것은 정책 변경이지 구현 변경이 아니다 — 판단할 사람: 법무 개인정보 담당.

## Out of scope (범위 밖)
상담사 대리 조회 · 손해사정인 위임 조회(Q1) · 청구 접수와 수정 · 상태 변경 알림
(푸시 · SMS) · 포털 화면(프론트엔드) 자체 · 상류 claims-core 의 캐시 무효화 통지.
이번 spec 은 조회 API 와 그 API 가 지켜야 하는 네 가지 단일성까지다.

## Acceptance criteria (수용 기준)
- AC1 → R1 세션 객체를 넘기고 조회하면 네 필드가 돌아오고, 세션을 None 으로 넘기면
  `unauthenticated` 만 돌아온다(응답 어디에도 청구 값이 없다).
- AC2 → R2 상류 레코드에 없던 민감 필드를 새로 넣고 조회해도 응답 키 집합이 변하지
  않는다. 이 판정에 쓰는 허용 목록은 구현에서 가져오지 않고 시험이 독립적으로 다시
  적은 것이다.
- AC3 → R3 같은 ID 를 TTL 안에 두 번 조회하면 상류 호출 수가 1 이고, TTL 을 넘겨
  세 번째로 조회하면 2 가 된다.
- AC4 → R4 `bash scripts/check_endpoints.sh src` 가 rc=0 이다.
