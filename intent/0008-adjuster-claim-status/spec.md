## Requirements
- R1 사정인 세션이 있고 그 사정인에게 배정된 건이면 `claim_id`·`status`·`due_date` 가 돌아온다 (Problem: 사정인이 전화로 묻는 두 값 + 어느 건인지).
- R2 세션이 없으면 `unauthenticated` 만 돌아오고 상류 조회도 일어나지 않는다 (Constraints: 기존 인증만).
- R3 사정인 세션이 아니거나(고객 세션 등) 세션에 사정인 번호가 없으면 `not_found` 이고 상류 조회도 일어나지 않는다. 고객 세션은 이 경로에서 아무것도 보지 못한다 (Constraints: 사정인 계정으로만).
- R4 배정되지 않은 건과 없는 건은 바이트 단위로 같은 `not_found` 로 답한다 — 구분하면 청구 번호의 존재 여부가 샌다. 형식이 틀린 번호는 `invalid_claim_id` 이고 입력을 되비추지 않으며 상류를 부르지 않는다 (0002 R4·0007 과 같은 규칙).
- R5 사정인 응답에 나가는 필드는 **사정인 전용** 허용 목록 한 곳이 정한다. `next_step`(내부 처리 단계)·가입자 이름·주민번호·계좌·내부 심사 메모는 응답·오류 문구 어디에도 실리지 않고, 원장에 새 필드가 생겨도 응답은 넓어지지 않는다 (보안·법무 확인: 상태와 예정일만).
- R6 배정 판정은 원장 레코드의 사정인 번호와 세션의 사정인 번호 일치 하나다. 어느 한쪽이 비어 있으면(없음·`None`·`""`) 불일치다 — 「양쪽이 비면 일치」는 intent 0005 가 고친 결함이다. 사정인 **이름은 판정에 쓰지 않는다**(이름은 겹친다; 정본은 번호다).
- R7 이관은 다음 조회부터 즉시 반영된다 — 사정인 경로는 캐시된 원장 레코드로 배정을 판정하지 않고 매 조회 상류를 읽는다 (클레임 운영팀장 결정: 이관된 사정인이 60초 더 보는 것은 안 된다 / claims-core 팀: 초당 50건은 전 경로 합산이고 이 규모의 1:1 호출은 여유가 있다).
- R8 값이 실제로 나간 조회는 접근 기록을 하나 남긴다 — **사정인 번호·청구 번호·시각 셋뿐**이다. 가입자 개인정보·`status`·`due_date`·`next_step` 은 기록에 들어가지 않는다 (보안팀·법무 결정: 열람 기록은 남겨야 하고, 이 셋은 고객 개인정보가 아니라 접근 기록이라 「새 개인정보 저장 금지」와 충돌하지 않는다).
- R9 0002 의 고객 자가조회는 변하지 않는다 — 응답 키 집합 네 개와 AC1~AC5 가 그대로 통과한다. 0002 경로는 접근 기록을 남기지 않는다(R8 은 사정인 경로의 규칙이다; 고객 자가조회에 기록을 붙이는 것은 별건이다).
- R10 사정인 응답의 `status` 는 원장이 닫아 둔 다섯 값 중 하나다 — 접수 · 심사중 · 보완요청 · 지급완료 · 종결 (claims-core 팀: 닫힌 집합이고 내부 어휘는 `status` 가 아니라 내부 메모 필드에만 있다 / 법무·보안: 다섯 값 전부 사정인에게 나가도 된다). 집합은 코드에 상수로 적히고, 원장에 여섯 번째 값이 들어오면 시험이 빨개진다 — 넓히는 것은 커밋(결정)이지 흘러드는 변화가 아니다.
## Design
새 패키지를 만들지 않는다. `src/claims_status/` 안에서 「하나여야 하는 것」(상류 접근·응답 조립)은 계속 하나로 두고, 두 청중의 차이만 새 파일로 가른다.
- `records.py` — 상류 접근의 유일한 문. `fetch_claim(claim_id, now=None, cached=True)` 로 인자 하나를 늘린다. `cached=False` 면 TTL 을 보지 않고 상류를 부르며, 받은 레코드로 캐시를 갱신한다(고객 경로가 더 신선해질 뿐 나빠지지 않는다). 기본값이 `True` 라서 0002 의 호출부와 AC5 의 호출 수 계산은 그대로다.
- `response.py` — 응답 조립의 유일한 문. `ADJUSTER_FIELDS = ("claim_id", "status", "due_date")` 와 `STATUS_VALUES = ("접수", "심사중", "보완요청", "지급완료", "종결")`(R10 의 닫힌 집합을 적어 두는 자리) 을 더하고, `build_response(record, fields)` 로 **인자를 필수로** 바꾼다. 기본값을 남기면 새 호출자가 인자를 잊었을 때 고객용 목록(=`next_step` 포함)이 조용히 나간다 — 빠뜨리면 터지는 쪽으로 둔다. 0002 의 호출 한 곳(`routes.py`)은 `RESPONSE_FIELDS` 를 명시하도록 한 줄 고친다(0002 의 시험은 손대지 않는다).
- `audit.py` (새 파일) — 접근 기록의 유일한 문. `record_access(adjuster_id, claim_id, at)` 하나뿐이고, 남기는 키도 그 셋뿐이다(R8). 원장 레코드를 통째로 받지 않는다 — 인자로 못 받으면 실수로도 실릴 수 없다. 시각은 UTC 벽시계를 **인자로** 받는다: `records.py` 의 `now` 는 캐시 만료용 단조 시계라 기록의 시각으로 쓸 수 없고, 시험이 시간을 통제해야 하기 때문이다. 기록을 어디에 쌓는가(파일·상류 감사 서비스)는 이 spec 이 정하지 않는다 — Out of scope.
- `adjuster_routes.py` (새 파일) — `/adjuster/claims/<claim_id>/status` 에 `get_adjuster_claim_status(claim_id, session, now=None, at=None)`. `routes.py` 의 `route` 데코레이터와 `CLAIM_ID_RE` 를 임포트해 쓴다(번호 형식 규칙은 0007 이 고친 `\A…\Z` 하나뿐이어야 한다 — 복사하지 않는다).
- 판정 순서: 세션 없음 → `unauthenticated` · 사정인 세션 아님/번호 없음 → `not_found` · 번호 형식 불일치 → `invalid_claim_id` · (여기까지 상류 호출 0·기록 0) → `fetch_claim(cached=False)` → 배정 불일치·없는 건 → `not_found`(기록 0) → `build_response(record, ADJUSTER_FIELDS)` → `record_access(...)`. 기록은 값이 나가는 것이 확정된 뒤에 남긴다 — 「열람 기록」이므로 열람이 실제로 일어난 조회에만 붙는다(F8).
- 세션 계약(포털 팀 확정): `{"role": "adjuster", "adjuster_id": "<사정인 번호>"}`. 원장 계약(claims-core 팀 확정): 「담당 사정인」 칸은 두 필드 — `adjuster_id`(번호)와 `adjuster_name`(이름). 판정도 기록도 번호만 쓴다. `adjuster_name` 은 이 경로에서 읽지 않는다.
- 두 청중이 같은 원장 레코드를 읽고 서로 다른 허용 목록으로 좁힌다. 필터는 `response.py` 한 곳, 상류는 `records.py` 한 곳, 청중별 규칙은 각자의 라우트 파일 — 넓히는 커밋이 곧 결정의 기록이라는 0002 의 구조를 그대로 잇는다.

secure-api-review 점검: ① 인증 — 익명 경로 없음. 포털의 기존 사정인 세션 없이는 아무 값도 나가지 않고 새 토큰·새 권한을 만들지 않는다. 게이트웨이 JWT 는 포털이 검증해 세션으로 바꿔 주므로(포털 팀·보안팀 확정) 규칙 ①은 포털 층에서 충족되고 이 앱은 세션만 본다. ② 입력 검증 — GET 이라 본문 없음, 경로 인자 `claim_id` 는 `C-<숫자>` 형식만 통과, 세션의 모르는 키는 읽지 않는다(허용 키만 본다). ③ 감사 — 상태를 바꾸지 않는 읽기 전용이지만 보안팀·법무 결정으로 열람 기록을 남긴다(R8). 규칙 문면은 actor·action·entity·timestamp 넷을 말하고 이 기록은 셋이다(actor=사정인 번호, entity=청구 번호, timestamp) — 이 경로의 action 이 「조회」 하나뿐이라 셋으로 족하다는 것이 결정 내용이고, 넷째 필드가 필요하면 그것은 감사 소비자 쪽의 요구다. ④ 데이터 분류 — pii(이름·주민번호·계좌)와 내부 메모·`next_step` 은 응답·오류 문구·접근 기록 어디에도 없다. `status` 의 값 집합은 닫혀 있고 다섯 값 전부 반출이 허가됐다(R10).
## Constraints
intent 0008 에서 그대로 옮긴 것:
- 기존 인증만 쓴다 — 포털에 이미 있는 사정인 계정 그대로. 새 계정·새 로그인 없음.
- 보여 주는 값은 상태와 예정일 둘. `next_step` 은 내부 처리 단계라 사정인에게 나가지 않는다.
- 배정의 정본은 claims-core 원장의 「담당 사정인」 칸 하나 — 포털은 배정 정보를 따로 들고 있지 않는다. 칸에는 개인 사정인의 이름과 사정인 번호가 들어가고, 위탁 법인 소속이어도 개인으로 적으며, 한 건에 한 사람이다.
- 이관되면 그 순간부터 안 보인다(핸들러가 원장의 칸을 바로 바꾼다).
- 종결된 건은 종결 뒤에도 보인다 — 정산 확인용.
- 청구 번호로 건별 조회. 목록 화면은 이번이 아니다.
제품 오너가 정책 소유자에게 확인해 넘긴 것(1차, spec 착수 시):
- 배정된 사정인에게 그 건의 상태와 예정일만 보여 주는 것은 허용된다(보안팀·법무). 가입자 개인정보·내부 심사 메모·다음 단계는 사정인 화면으로 나가면 안 된다. 새로 저장하는 개인정보는 없어야 한다.
- 사정인 로그인 세션에는 사정인 번호가 실려 있고, 사정인 세션과 고객 세션이 구분된다(포털 팀).
- claims-core 는 읽기만 한다.
2차(F1~F7 회신, 2026-09-09):
- 이관된 사정인이 60초 더 보는 것은 안 된다(클레임 운영팀장). 초당 50건 한도는 전 경로 합산이고, 하루 40건 규모의 1:1 호출은 여유가 있다(claims-core 팀).
- `status` 는 닫힌 집합 다섯 — 접수 · 심사중 · 보완요청 · 지급완료 · 종결. 내부 어휘는 `status` 에 들어가지 않고 내부 메모 필드에만 있다(claims-core 팀). 다섯 값 전부 사정인 반출 허가(법무·보안팀).
- 열람 기록은 남긴다 — 사정인 번호·청구 번호·시각 셋만. 이 셋은 고객 개인정보가 아니라 접근 기록이므로 「새 개인정보 저장 금지」와 충돌하지 않는다(보안팀·법무).
- 게이트웨이 JWT 는 포털이 검증해 세션으로 바꿔 준다; 앱은 세션만 본다(포털 팀·보안팀). 0002 F3 도 같은 답이지만 0002 의 spec 파일은 이 사슬에서 고치지 않는다.
- 종결 후에도 「담당 사정인」 칸은 지우지 않는다(claims-core 팀). 정산은 종결 후 30일 안에 끝난다(클레임 운영팀장).
- 「담당 사정인」 칸은 두 필드 `adjuster_id`·`adjuster_name`, 판정은 번호로(claims-core 팀). 세션 키는 `role`="adjuster" 와 `adjuster_id`(포털 팀).
- `due_date` 는 원장 값이다 — 계산하지 않는다(claims-core 팀).
- 사정인 화면은 이번 범위 밖으로 둔다; 브랜드·UX 기준 스킬은 화면을 만드는 사슬에서 만든다(제품 오너).
설계하며 발견한 것:
- 허용 목록이 이제 둘이다 — 하나의 상수로는 두 청중을 못 맞춘다. `build_response` 의 필드 인자를 필수로 만들어, 목록을 고르지 않는 호출이 성립하지 못하게 한다.
- 캐시 우회(R7)와 0002 의 TTL 캐시(0002 R5)는 같은 상류를 두 정책으로 읽는다. 두 정책이 한 모듈에 공존하는 것은 `fetch_claim` 의 `cached` 인자 하나로 드러내고, 어느 경로가 어느 정책인지는 호출부가 명시한다.
- 판정을 상류 조회보다 앞에 둔다(R2·R3·R4의 「상류 호출 0」). 없는 번호·남의 세션으로 상류 예산을 태우지 못하게 하는 것은 0002·0006 이 이미 세운 규칙이다.
- 사정인 이름은 원장에 있어도 읽지 않는다. 판정에 쓰면 동명이인이 남의 건을 보고, 응답이나 기록에 실으면 R5·R8 위반이다.
- 접근 기록의 시각은 캐시의 시계와 다른 시계다 — 단조 시계는 벽시계 시각이 아니다. `audit.record_access` 가 시각을 인자로 받는 이유이고, 두 시계를 한 인자로 합치면 기록이 「부팅 후 12.3초」가 된다.
- 접근 기록에 원장 레코드를 넘기지 않는다. 인자가 세 스칼라뿐이면 기록이 넓어지는 실수가 문법으로 막힌다 — 응답의 허용 목록과 같은 장치다.
## Open questions from intent
네 개 모두 답이 왔다 — carried forward 는 0 이다.
- 사정인에게 상태·예정일을 보여 주는 것이 개인정보 측면에서 괜찮은가 → **answered**: 허용된다 — 상태와 예정일만, 가입자 개인정보·내부 메모·다음 단계 금지 (보안팀·법무, 제품 오너 전달 2026-09-09). 「새로 저장하는 개인정보 금지」는 열람 기록 세 값(사정인 번호·청구 번호·시각)까지 막는 것이 아니라는 것이 2차 회신이다. R5·R8·R10 이 받는다.
- 포털 사정인 세션이 어느 사정인인지 가리키는가 → **answered**: 세션에 사정인 번호가 실려 있고 사정인/고객 세션이 구분된다; 게이트웨이 JWT 는 포털이 검증해 세션으로 바꾸므로 앱은 세션만 본다 (포털 팀·보안팀). R1·R3 이 받고, secure-api-review ① 점검이 이것으로 닫힌다.
- 「예정일」이 원장 값인가 계산 값인가 → **answered**: 원장 값이다, 계산하지 않는다 (claims-core 팀). R1 의 `due_date` 는 원장 값을 그대로 통과시킨다. 0002 spec 이 가정으로 두었던 자리가 여기서 확정됐다.
- 초당 50건 제한이 이 경로에도 걸리는가 → **answered**: 걸린다 — 다만 한도는 전 경로 합산이고 하루 40건 규모에서는 1:1 호출이어도 여유가 있다 (claims-core 팀). 그래서 R7 이 캐시를 우회한다. 사정인 조회량이 자릿수로 늘면(목록 화면·자동 폴링) 다시 볼 자리다.
## Flagged concerns
일곱 개 모두 소유자 결정이 왔다(제품 오너 전달, 2026-09-09). 아래는 결정과 그것이 닿은 자리다.
새로 생긴 자리 하나(F8)는 F3 의 답이 만든 것이고, 진행을 막지 않는다.
- **F1 (해소) 「이관 즉시 안 보임」 vs TTL 캐시.** 결정: 이관된 사정인이 60초 더 보는 것은 안 된다(클레임 운영팀장). 초당 50건은 전 경로 합산이고 하루 40건 규모의 1:1 호출은 여유가 있다(claims-core 팀). → 초안의 선택(캐시 우회)이 그대로 확정. **R7 · AC7**. 같은 회신이 「초당 50건」 carried 도 닫았다. 다시 열리는 조건: 사정인 조회량이 자릿수로 늘 때(목록 화면·자동 폴링) — 그때 한도는 합산이라 고객 경로와 함께 본다.
- **F2 (해소) 「상태」의 값 집합.** 결정: `status` 는 닫힌 집합 다섯 — 접수 · 심사중 · 보완요청 · 지급완료 · 종결이고, 내부 어휘는 `status` 가 아니라 내부 메모 필드에만 있다(claims-core 팀). 다섯 값 전부 사정인 반출 허가(법무·보안팀). → **R10 · AC10**. 집합을 `response.py` 의 상수와 시험 양쪽에 적어, 여섯 번째 값이 원장에 들어오면 시험이 빨개지게 한다 — 허가받은 것은 이 다섯이지 「status 라는 필드」가 아니다.
- **F3 (해소 — 초안과 반대로) 열람 기록.** 결정: 남겨야 한다. 사정인 번호·청구 번호·시각 셋만이고, 그 셋은 고객 개인정보가 아니라 접근 기록이라 「새 개인정보 저장 금지」와 충돌하지 않는다(보안팀·법무). → **R8 · AC8**, 그리고 Design 에 `audit.py`(기록의 유일한 문, 스칼라 세 인자, 벽시계 주입). 초안의 R8 은 「아무것도 남기지 않는다」였다 — 뒤집힌 요구다.
- **F4 (해소) 인증의 정본.** 결정: 포털이 게이트웨이 JWT 를 검증해 세션으로 바꾼다; 앱은 세션만 보면 된다(포털 팀·보안팀). → secure-api-review ① 점검이 이것으로 닫혔고 **R2·R3** 의 세션 판정이 그대로 유효하다. 0002 F3 도 같은 답이지만 0002 의 spec 파일은 이 사슬에서 고치지 않는다 — 0002 를 손보는 것은 별건의 커밋이다.
- **F5 (해소) 종결 뒤에도 보임.** 결정: 종결 후에도 「담당 사정인」 칸은 지우지 않는다(claims-core 팀). 정산은 종결 후 30일 안에 끝난다(클레임 운영팀장). → 제약이 성립한다. **R6** 의 판정을 바꿀 필요가 없다. 종결 건에 별도 만료를 두지 않는 것도 이 답의 결과다 — 30일은 칸이 유지되는 한 자연히 덮인다.
- **F6 (해소) 브랜드·UX.** 결정: 화면은 이번 범위 밖 그대로 두고, 브랜드·UX 기준 스킬은 화면을 만드는 사슬에서 만든다(제품 오너). → **Out of scope** 에 그대로. 이 spec 은 「UX 기준에 맞췄다」고 말하지 않는다 — 맞출 기준이 아직 없다.
- **F7 (해소) 계약의 이름.** 결정: 칸은 두 필드 `adjuster_id`(번호)·`adjuster_name`(이름)이고 판정은 번호로(claims-core 팀). 세션 키는 `role`="adjuster" 와 `adjuster_id`(포털 팀). → Design 의 계약 두 줄이 가정에서 확정으로 바뀌었다. 파싱은 생기지 않는다. **R6 · AC6** 이 이름을 판정에서 배제하는 것을 지킨다.
- **F8 (새로 생김 — F3 의 답이 만든 자리) 남지 않는 것 두 가지.** ① 기록은 값이 나간 조회에만 붙는다(「열람 기록」의 문면대로). 그래서 배정 안 된 번호를 훑는 시도는 `not_found` 만 돌려주고 아무 데도 남지 않는다 — 청구 번호가 `C-<숫자>` 라 훑기가 쉽다는 점과 같이 봐야 한다. 실패 시도까지 남기려면 그것은 「열람 기록」이 아니라 접근 시도 기록이고 결정이 다시 필요하다. ② 기록을 어디에 얼마나 보관하는지(저장소·보존 기간)를 이 spec 은 정하지 않았다 — 접근 기록의 보존 기간은 법무가 정할 자리다. 둘 다 진행을 막지 않는다: 이 spec 대로 구현하면 ①은 「덜 남긴다」쪽이고 ②는 배선 시점의 결정이다. 결정: 보안팀(①), 법무 개인정보 담당(②).
## Out of scope
배정 건 목록 화면 · 포털 프론트엔드(사정인 화면의 문구·표시·접근성 — F6 결정으로 이번 범위 밖) · 청구 서류 열람과 업로드 · `next_step` 을 사정인에게 보여 주는 일 · 고객 자가조회 경로의 동작 변경(0002) · 0002 spec 파일의 F3 갱신 · 상담사 대리 조회 · 상태 변경 알림 · claims-core 쪽 변경(읽기만 한다) · 실제 HTTP 서버·라우터 배선(핸들러 함수까지) · 사정인 계정 발급과 권한 관리 · 접근 기록의 저장소와 보존 기간(`audit.record_access` 까지; 어디에 쌓고 얼마나 두는가는 F8②).
## Acceptance criteria
- AC1 → R1 사정인 세션(`adjuster_id` 가 원장의 배정과 일치)으로 조회하면 키 집합이 정확히 {claim_id, status, due_date} 이고 값이 비어 있지 않다. 판정에 쓰는 키 집합은 구현에서 임포트하지 않고 시험이 따로 적은 것이다.
- AC2 → R2 세션 `None` 이면 `{"error":"unauthenticated"}` 이고 상류 호출 수 0.
- AC3 → R3 고객 세션(`{"subscriber_id":"S-77"}`)·`role` 이 사정인이 아닌 세션·`adjuster_id` 가 없거나 `None`·`""` 인 세션은 모두 `{"error":"not_found"}` 이고 상류 호출 수 0.
- AC4 → R4 배정 안 된 건과 없는 건의 응답이 바이트 단위로 같다(`{"error":"not_found"}`). 형식이 틀린 번호(`"C-1001' OR 1=1 --"`, `"C-1001\n"`)는 `{"error":"invalid_claim_id"}` 이고 입력 문자열이 본문에 없으며 상류 호출 수 0.
- AC5 → R5 원장 레코드에 새 민감 필드를 심어도 응답 키 집합이 같고, `next_step` 의 값·가입자 이름·주민번호·계좌·내부 메모 문자열이 본문에 없다.
- AC6 → R6 원장의 `adjuster_id` 가 없거나 `None`·`""` 인 행은 같은 값의 세션으로도 `not_found` 이고, 사정인 **이름**만 일치하고 번호가 다른 세션도 `not_found` 다.
- AC7 → R7 조회 직후 원장의 배정을 다른 사정인으로 바꾸고 TTL(60초) 안에 다시 조회하면 옛 사정인은 `not_found`, 새 사정인은 세 필드를 받는다.
- AC8 → R8 성공 조회 1건마다 접근 기록이 정확히 1건 늘고, 그 기록의 키 집합이 정확히 {adjuster_id, claim_id, timestamp} 이며, 주어진 시각이 그대로 실린다. 기록 본문에 가입자 이름·주민번호·계좌·내부 메모·`status`·`due_date`·`next_step` 의 값이 없다. `unauthenticated`·`not_found`·`invalid_claim_id` 로 끝난 조회는 기록을 0건 남긴다(F8①의 선택을 못 박는 시험이다).
- AC9 → R9 `tests/test_claims_status.py`·`tests/test_claims_status_defect.py`·`tests/test_claims_status_format.py`·`tests/test_claims_status_incident.py` 가 한 줄도 고쳐지지 않은 채 그대로 통과하고, 고객 자가조회를 아무리 불러도 접근 기록은 0건이다.
- AC10 → R10 원장 표본의 모든 행의 `status` 가 다섯 값 {접수, 심사중, 보완요청, 지급완료, 종결} 안에 있고, 원장에 여섯 번째 값을 심으면 이 시험이 실패한다. 판정에 쓰는 다섯 값은 구현에서 임포트하지 않고 시험이 따로 적은 것이다(0002 의 허용 키 규율과 같다).
