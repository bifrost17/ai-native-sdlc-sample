## Requirements
- R1 사정인 세션이 있고 그 사정인에게 배정된 건이면 `claim_id`·`status`·`due_date` 가 돌아온다 (Problem: 사정인이 전화로 묻는 두 값 + 어느 건인지).
- R2 세션이 없으면 `unauthenticated` 만 돌아오고 상류 조회도 일어나지 않는다 (Constraints: 기존 인증만).
- R3 사정인 세션이 아니거나(고객 세션 등) 세션에 사정인 번호가 없으면 `not_found` 이고 상류 조회도 일어나지 않는다. 고객 세션은 이 경로에서 아무것도 보지 못한다 (Constraints: 사정인 계정으로만).
- R4 배정되지 않은 건과 없는 건은 바이트 단위로 같은 `not_found` 로 답한다 — 구분하면 청구 번호의 존재 여부가 샌다. 형식이 틀린 번호는 `invalid_claim_id` 이고 입력을 되비추지 않으며 상류를 부르지 않는다 (0002 R4·0007 과 같은 규칙).
- R5 사정인 응답에 나가는 필드는 **사정인 전용** 허용 목록 한 곳이 정한다. `next_step`(내부 처리 단계)·가입자 이름·주민번호·계좌·내부 심사 메모는 응답·오류 문구 어디에도 실리지 않고, 원장에 새 필드가 생겨도 응답은 넓어지지 않는다 (보안·법무 확인: 상태와 예정일만).
- R6 배정 판정은 원장 레코드의 사정인 번호와 세션의 사정인 번호 일치 하나다. 어느 한쪽이 비어 있으면(없음·`None`·`""`) 불일치다 — 「양쪽이 비면 일치」는 intent 0005 가 고친 결함이다. 사정인 **이름은 판정에 쓰지 않는다**(이름은 겹친다; 정본은 번호다).
- R7 이관은 다음 조회부터 즉시 반영된다 — 사정인 경로는 캐시된 원장 레코드로 배정을 판정하지 않고 매 조회 상류를 읽는다 (Constraints: 이관되면 그 순간부터 안 보인다). F1 을 함께 읽을 것.
- R8 이 경로는 새로 저장하는 것이 없다 — 로그·감사 이벤트·조회 이력을 남기지 않는다 (보안·법무 확인: 새로 저장하는 개인정보 없음). F3 을 함께 읽을 것.
- R9 0002 의 고객 자가조회는 변하지 않는다 — 응답 키 집합 네 개와 AC1~AC5 가 그대로 통과한다.
## Design
새 패키지를 만들지 않는다. `src/claims_status/` 안에서 「하나여야 하는 것」(상류 접근·응답 조립)은 계속 하나로 두고, 두 청중의 차이만 새 파일로 가른다.
- `records.py` — 상류 접근의 유일한 문. `fetch_claim(claim_id, now=None, cached=True)` 로 인자 하나를 늘린다. `cached=False` 면 TTL 을 보지 않고 상류를 부르며, 받은 레코드로 캐시를 갱신한다(고객 경로가 더 신선해질 뿐 나빠지지 않는다). 기본값이 `True` 라서 0002 의 호출부와 AC5 의 호출 수 계산은 그대로다.
- `response.py` — 응답 조립의 유일한 문. `ADJUSTER_FIELDS = ("claim_id", "status", "due_date")` 를 더하고, `build_response(record, fields)` 로 **인자를 필수로** 바꾼다. 기본값을 남기면 새 호출자가 인자를 잊었을 때 고객용 목록(=`next_step` 포함)이 조용히 나간다 — 빠뜨리면 터지는 쪽으로 둔다. 0002 의 호출 한 곳(`routes.py`)은 `RESPONSE_FIELDS` 를 명시하도록 한 줄 고친다(0002 의 시험은 손대지 않는다).
- `adjuster_routes.py` (새 파일) — `/adjuster/claims/<claim_id>/status` 에 `get_adjuster_claim_status(claim_id, session, now=None)`. `routes.py` 의 `route` 데코레이터와 `CLAIM_ID_RE` 를 임포트해 쓴다(번호 형식 규칙은 0007 이 고친 `\A…\Z` 하나뿐이어야 한다 — 복사하지 않는다).
- 판정 순서: 세션 없음 → `unauthenticated` · 사정인 세션 아님/번호 없음 → `not_found` · 번호 형식 불일치 → `invalid_claim_id` · (여기까지 상류 호출 0) → `fetch_claim(cached=False)` → 배정 불일치·없는 건 → `not_found` → `build_response(record, ADJUSTER_FIELDS)`.
- 세션 계약(포털 팀 확인을 이 spec 이 이름 붙인 것): `{"role": "adjuster", "adjuster_id": "<사정인 번호>"}`. 원장 계약: 레코드의 `adjuster_id` 가 「담당 사정인」 칸의 사정인 번호. 키 이름이 실제와 다르면 이름 바꾸기지 설계 변경이 아니다 — F7.
- 두 청중이 같은 원장 레코드를 읽고 서로 다른 허용 목록으로 좁힌다. 필터는 `response.py` 한 곳, 상류는 `records.py` 한 곳, 청중별 규칙은 각자의 라우트 파일 — 넓히는 커밋이 곧 결정의 기록이라는 0002 의 구조를 그대로 잇는다.

secure-api-review 점검: ① 인증 — 익명 경로 없음. 포털의 기존 사정인 세션 없이는 아무 값도 나가지 않고 새 토큰·새 권한을 만들지 않는다. 「게이트웨이 JWT」와 「포털 세션」의 관계는 여전히 미확정 — F4. ② 입력 검증 — GET 이라 본문 없음, 경로 인자 `claim_id` 는 `C-<숫자>` 형식만 통과, 세션의 모르는 키는 읽지 않는다(허용 키만 본다). ③ 감사 — 상태를 바꾸지 않는 읽기 전용이라 규칙 문면상 감사 이벤트 대상이 아니다. 다만 외부 제3자가 고객 청구 정보를 보는 경로라는 점에서 문면과 취지가 갈린다 — F3. ④ 데이터 분류 — pii(이름·주민번호·계좌)와 내부 메모·`next_step` 은 응답·오류 문구에 없다; 이 모듈은 로그를 남기지 않는다. 단 `status` 는 **값**이 무엇인지 아무도 열거하지 않았다 — F2.
## Constraints
intent 0008 에서 그대로 옮긴 것:
- 기존 인증만 쓴다 — 포털에 이미 있는 사정인 계정 그대로. 새 계정·새 로그인 없음.
- 보여 주는 값은 상태와 예정일 둘. `next_step` 은 내부 처리 단계라 사정인에게 나가지 않는다.
- 배정의 정본은 claims-core 원장의 「담당 사정인」 칸 하나 — 포털은 배정 정보를 따로 들고 있지 않는다. 칸에는 개인 사정인의 이름과 사정인 번호가 들어가고, 위탁 법인 소속이어도 개인으로 적으며, 한 건에 한 사람이다.
- 이관되면 그 순간부터 안 보인다(핸들러가 원장의 칸을 바로 바꾼다).
- 종결된 건은 종결 뒤에도 보인다 — 정산 확인용.
- 청구 번호로 건별 조회. 목록 화면은 이번이 아니다.
제품 오너가 정책 소유자에게 확인해 넘긴 것:
- 배정된 사정인에게 그 건의 상태와 예정일만 보여 주는 것은 허용된다(보안팀·법무). 가입자 개인정보·내부 심사 메모·다음 단계는 사정인 화면으로 나가면 안 된다. 새로 저장하는 개인정보는 없어야 한다.
- 사정인 로그인 세션에는 사정인 번호가 실려 있고, 사정인 세션과 고객 세션이 구분된다(포털 팀).
- claims-core 는 읽기만 한다.
설계하며 발견한 것:
- 허용 목록이 이제 둘이다 — 하나의 상수로는 두 청중을 못 맞춘다. `build_response` 의 필드 인자를 필수로 만들어, 목록을 고르지 않는 호출이 성립하지 못하게 한다.
- R7(캐시 우회)과 0002 R5(TTL 캐시)는 같은 상류를 두 정책으로 읽는다. 사정인 경로는 하루 40통 규모라 조회 1건당 상류 1건이어도 절대량이 작지만, 초당 50건 한도의 정본은 아직 답이 없다 — F1.
- 판정을 상류 조회보다 앞에 둔다(R2·R3·R4의 「상류 호출 0」). 없는 번호·남의 세션으로 상류 예산을 태우지 못하게 하는 것은 0002·0006 이 이미 세운 규칙이다.
- 사정인 이름은 원장에 있어도 읽지 않는다. 판정에 쓰면 동명이인이 남의 건을 보고, 응답에 실으면 R5 위반이다.
## Open questions from intent
- 사정인에게 상태·예정일을 보여 주는 것이 개인정보 측면에서 괜찮은가 → **answered**: 허용된다 — 상태와 예정일만, 가입자 개인정보·내부 메모·다음 단계 금지, 새로 저장하는 개인정보 금지 (보안팀·법무, 제품 오너 전달 2026-09-09). R5·R8 이 받는다. 남은 결은 F2(「상태」의 값 집합)와 F3(감사).
- 포털 사정인 세션이 어느 사정인인지 가리키는가 → **answered**: 세션에 사정인 번호가 실려 있고 사정인/고객 세션이 구분된다, 기존 인증 그대로 (포털 팀). R1·R3 이 받는다. 키 이름 확정은 F7.
- 「예정일」이 원장 값인가 계산 값인가 → **carried forward** (claims-core 팀). 설계 가정: 원장의 `due_date` 를 그대로 보여 주고 계산하지 않는다 — 0002 spec 과 같은 가정이다. 「계산해야 한다」가 답이면 spec 변경이다.
- 초당 50건 제한이 이 경로에도 걸리는가 → **carried forward** (claims-core 팀). 이 spec 은 수치를 지어내지 않는다. R7 이 캐시를 쓰지 않으므로 이 경로의 상류 호출은 조회 수와 1:1 이다 — 한도가 확인되기 전까지 F1 의 결정이 열려 있다.
## Flagged concerns
- **F1 (충돌 — 둘 다는 못 맞춘다) 「이관 즉시 안 보임」 vs TTL 캐시.** intent 0008 은 이관 순간부터 안 보이기를 요구하고, 0002 R5 는 초당 50건을 지키려고 원장 레코드를 60초 캐시한다. 캐시를 그대로 쓰면 이관된 옛 사정인이 최대 60초 더 그 건을 보고, 새 사정인은 최대 60초 동안 `not_found` 를 본다 — 낡은 화면이 아니라 낡은 **권한**이다. 이 spec 은 accepted intent 의 제약을 지키는 쪽(R7, 캐시 우회)을 골랐고, 그 대가로 사정인 조회는 상류와 1:1 이 된다. 되돌리려면(캐시 사용 + 60초 창 용인) 결정이 필요하다: 클레임 운영팀장(60초 노출을 받는가) · 보안팀(권한 판정을 캐시해도 되는가) · claims-core 팀(1:1 호출을 받는가). **제품 오너가 먼저 볼 자리.**
- **F2 (허가의 범위가 값까지 닿지 않았다) 「상태」에 무엇이 들어 있는지 아무도 열거하지 않았다.** 허용 목록은 필드 **이름**을 막지 값을 막지 못한다. 원장 표본의 내부 메모가 「재심사 대상 — 내부 검토중」인 것을 보면 내부 어휘가 존재하고, `status` 값이 「특별조사 의뢰」류를 담게 되면 법무가 허용한 「상태」의 범위를 넘는다. 필요한 것: `status` 의 값 집합이 닫혀 있는지(claims-core 팀), 그 집합 전체가 외부 사정인에게 나가도 되는지(법무·보안팀). 답이 「열려 있다」면 사정인용 상태 어휘를 따로 정하는 것이 spec 변경으로 들어온다.
- **F3 (규칙의 문면과 취지가 갈린다) 감사 로그.** secure-api-review ③ 은 상태를 바꾸는 엔드포인트에만 감사를 요구하므로 읽기 전용인 이 경로는 문면상 대상이 아니다. 그런데 여기서 처음으로 **외부 제3자**가 고객 청구 정보를 보고, 그 열람이 아무 데도 남지 않는다. 반대로 「사정인 A-xxxx 가 청구 C-xxxx 를 몇 시에 봤다」를 남기면 「새로 저장하는 개인정보 없음」과 부딪힌다. 이 spec 은 R8 로 남기지 않는 쪽에 서 있다 — 제약을 문면대로 지킨 것이지 판단한 것이 아니다. 결정: 보안팀, 법무 개인정보 담당.
- **F4 (0002 F3 그대로 미해결) 인증의 정본.** secure-api-review ① 은 「모든 엔드포인트는 게이트웨이 JWT」라고 하고, intent 와 제품 오너는 「기존 포털 세션 그대로」라고 한다. 포털이 JWT 를 세션으로 바꿔 주는 것인지 둘이 다른 층인지가 아직 문서에 없다. 이 spec 은 0002 와 같이 세션 객체만 본다. 결정: 포털 팀, 보안팀.
- **F5 (제약 둘이 같이 성립하지 않을 수 있다) 종결 뒤에도 보임 vs 배정 칸.** 「종결된 건은 종결 뒤에도 보인다」는 종결 후에도 원장의 「담당 사정인」 칸이 그 사정인을 가리키고 있어야 성립한다. 종결·정산 처리에서 칸을 비우거나 다른 값으로 바꾸는 절차가 있으면, R6 의 판정이 그 순간 사정인을 잘라 낸다. 확인 필요: claims-core 팀(종결 시 칸이 유지되는가), 클레임 운영팀장(정산 기간에 얼마나 오래 보여야 하는가).
- **F6 (적용할 기준이 없다) 브랜드·UX.** 착수 지시는 「brand guidelines · UX standards 에 맞게」를 말하지만 `.claude/skills/` 에 있는 것은 capture-intent · design-spec · plan · secure-api-review 넷뿐이다 — 브랜드·UX 기준 스킬이 이 저장소에 없다. 이 spec 은 핸들러까지만 다루고 화면을 Out of scope 로 뒀으므로 지금은 공백이 문제가 되지 않지만, 사정인 화면을 만드는 사슬에서는 검토할 기준이 없는 채로 시작하게 된다. 결정: 제품 오너(기준 스킬을 만들지, 화면을 계속 범위 밖에 둘지).
- **F7 (계약의 이름) 「담당 사정인」 칸의 모양과 세션 키 이름.** 이 spec 은 원장 레코드의 `adjuster_id`(사정인 번호)와 세션의 `role`·`adjuster_id` 를 이름으로 못 박았다. 실제 원장이 이름과 번호를 한 문자열(예: `"홍길동/A-3391"`)로 들고 있다면 파싱이 생기고 그것은 설계 변경이다 — 파싱 규칙이 곧 인증 규칙이 되기 때문이다. 확인 필요: claims-core 팀(칸이 한 필드인가 두 필드인가), 포털 팀(세션 키 이름).
## Out of scope
배정 건 목록 화면 · 포털 프론트엔드(사정인 화면의 문구·표시·접근성) · 청구 서류 열람과 업로드 · `next_step` 을 사정인에게 보여 주는 일 · 고객 자가조회 경로의 동작 변경(0002) · 상담사 대리 조회 · 상태 변경 알림 · claims-core 쪽 변경(읽기만 한다) · 실제 HTTP 서버·라우터 배선(핸들러 함수까지) · 사정인 계정 발급과 권한 관리.
## Acceptance criteria
- AC1 → R1 사정인 세션(`adjuster_id` 가 원장의 배정과 일치)으로 조회하면 키 집합이 정확히 {claim_id, status, due_date} 이고 값이 비어 있지 않다. 판정에 쓰는 키 집합은 구현에서 임포트하지 않고 시험이 따로 적은 것이다.
- AC2 → R2 세션 `None` 이면 `{"error":"unauthenticated"}` 이고 상류 호출 수 0.
- AC3 → R3 고객 세션(`{"subscriber_id":"S-77"}`)·`role` 이 사정인이 아닌 세션·`adjuster_id` 가 없거나 `None`·`""` 인 세션은 모두 `{"error":"not_found"}` 이고 상류 호출 수 0.
- AC4 → R4 배정 안 된 건과 없는 건의 응답이 바이트 단위로 같다(`{"error":"not_found"}`). 형식이 틀린 번호(`"C-1001' OR 1=1 --"`, `"C-1001\n"`)는 `{"error":"invalid_claim_id"}` 이고 입력 문자열이 본문에 없으며 상류 호출 수 0.
- AC5 → R5 원장 레코드에 새 민감 필드를 심어도 응답 키 집합이 같고, `next_step` 의 값·가입자 이름·주민번호·계좌·내부 메모 문자열이 본문에 없다.
- AC6 → R6 원장의 `adjuster_id` 가 없거나 `None`·`""` 인 행은 같은 값의 세션으로도 `not_found` 이고, 사정인 **이름**만 일치하고 번호가 다른 세션도 `not_found` 다.
- AC7 → R7 조회 직후 원장의 배정을 다른 사정인으로 바꾸고 TTL(60초) 안에 다시 조회하면 옛 사정인은 `not_found`, 새 사정인은 세 필드를 받는다.
- AC8 → R8 사정인 경로를 한 번 조회해도 이 모듈이 남기는 기록이 없다(로그 호출 없음·감사 이벤트 없음) — 코드에 로깅 호출이 없다는 것으로 판정한다.
- AC9 → R9 `tests/test_claims_status.py`·`tests/test_claims_status_defect.py`·`tests/test_claims_status_format.py`·`tests/test_claims_status_incident.py` 가 한 줄도 고쳐지지 않은 채 그대로 통과한다.
