## Requirements
- R1 상담사 세션에 본인확인 표시가 있고 그 표시가 가리키는 가입자의 건이면, **고객 경로(0002)가 같은 건에 대해 내보내는 것과 바이트 단위로 같은 응답**이 돌아온다 — `claim_id`·`status`·`next_step`·`due_date` (클레임 운영팀장·법무: 상담사에게는 고객이 보는 값 그대로, 다음 단계 포함 / Problem: 상담사가 읽어 주는 말과 고객 화면의 말이 같아야 한다).
- R2 세션이 없으면 `unauthenticated` 만 돌아오고 상류 조회도 접근 기록도 일어나지 않는다 (Constraints: 기존 인증만).
- R3 상담사 세션이 아니면 — 고객 세션·사정인 세션·세션 종류가 없는 것 전부 — `not_found` 이고 상류 조회 0·기록 0 이다 (0008 R3 과 같은 규칙: 청중이 아닌 세션은 이 경로에서 아무것도 보지 못한다).
- R4 상담사 세션이지만 본인확인 표시가 없거나 만료됐으면 `verification_required` 이고 상류 조회 0·기록 0 이다 (보안팀·법무: 조회는 세션 표시가 있는 통화에서만 — 표시는 선행 조건이지 사후 확인이 아니다). 이 판정은 청구 번호를 보기 전에, 세션만으로 끝난다 — 그래서 원장의 어떤 것도 흘리지 않는다 (F5 에서 다시 든다).
- R5 소유 판정은 원장 레코드의 `subscriber_id` 와 세션의 **본인확인된 가입자 번호** 일치 하나다. 어느 한쪽이 비어 있으면(없음·`None`·`""`) 불일치다 — 「양쪽이 비면 일치」는 intent 0005 가 고친 결함이다. 확인된 고객의 건이 아닌 건과 없는 건은 바이트 단위로 같은 `not_found` 이고, 형식이 틀린 번호는 `invalid_claim_id` 이며 입력을 되비추지 않고 상류를 부르지 않는다 (0002 R4 · 0007 과 같은 규칙).
- R6 본인확인 표시는 확인 시각으로부터 30분이 지나면 만료다 — 콘솔이 세션에서 지우는 것과 **별개로** 이 핸들러가 한 번 더 본다. 확인 시각을 읽을 수 없거나(없음·형식 불일치·미래 시각) 30분을 넘겼으면 R4 로 닫는다 (콘솔 담당 팀: 통화 종료 또는 30분이면 표시가 지워진다 / 보안팀: 표시가 선행 조건이다). 「통화 종료」는 이 앱에서 볼 수 없으므로 그 갈래는 콘솔이 지우는 것에 의존한다.
- R7 응답에 나가는 필드는 **고객 경로와 같은 허용 목록 하나**(`response.RESPONSE_FIELDS`)다 — 상담사용 목록을 새로 만들지 않고 복사하지도 않는다. 목록이 하나라서 「고객이 보는 것과 똑같은 값」이 구조로 성립한다: 고객 목록을 넓히는 커밋이 상담사 화면도 같이 넓히고, 그것이 이 요구의 내용이다. 원장의 주민번호·계좌번호·가입자 이름·내부 심사 메모는 응답·오류 문구 어디에도 실리지 않고, 원장에 새 필드가 생겨도 응답은 넓어지지 않는다 (보안팀·법무).
- R8 값이 실제로 나간 조회는 접근 기록을 하나 남긴다 — **상담사 사번·고객 가입자 번호·청구 번호·시각 넷뿐**이다. `status`·`next_step`·`due_date` 와 가입자 이름·주민번호·계좌·내부 메모는 기록에 들어가지 않는다 (감사팀: 한 줄 = 누가·누구·어느 건·언제 / 보안팀·법무: 이 넷은 고객 개인정보가 아니라 접근 기록이라 「새 개인정보 저장 금지」와 충돌하지 않는다).
- R9 앞선 두 경로는 변하지 않는다. ① 0002 고객 자가조회와 0008 사정인 조회의 시험 파일 다섯이 한 줄도 고쳐지지 않은 채 그대로 통과한다. ② 사정인 접근 기록의 키 집합은 셋 그대로다(0008 R8) — 상담사 기록이 넷이라고 해서 사정인 기록이 넓어지지 않는다. ③ **상담사 세션을 0002 고객 경로에 넣으면 `not_found` 이고 기록이 0 이다** — 기록을 남기지 않는 조회 경로로 새는 것을 막는다(F1).
- R10 상류 조회는 고객 경로와 **같은 캐시**를 쓴다 — `fetch_claim(..., cached=True)`, TTL 60초 (claims-core 팀: 초당 50건은 전 경로 합산이고 하루 70통은 여유 안이다; 상담사 경로는 고객이 보는 것과 같아야 하니 같은 캐시를 써도 된다). 사정인 경로의 캐시 우회(0008 R7)는 이 경로의 규칙이 아니다 — 거기서 캐시를 우회한 이유는 배정이 **권한**이고 이관이 즉시여야 했기 때문이다(F6 에서 다시 든다).
## Design
새 패키지도 새 상수도 만들지 않는다. 청중이 셋이 됐지만 「하나여야 하는 것」은 계속 하나다 — 상류 문 `records.py`, 응답 문 `response.py`, 기록 문 `audit.py`. 이번에 새로 생기는 것은 라우트 파일 하나와 기록 함수 하나뿐이다.
- `agent_routes.py` (새 파일) — `/agent/claims/<claim_id>/status` 에 `get_agent_claim_status(claim_id, session, now=None, at=None)`. `routes.py` 의 `route` 데코레이터와 `CLAIM_ID_RE` 를 임포트해 쓴다(번호 형식 규칙은 0007 이 고친 `\A…\Z` 하나여야 한다 — 복사하지 않는다).
- `response.py` — **손대지 않는다.** 상담사 경로는 `RESPONSE_FIELDS` 를 그대로 임포트한다. 0008 이 `ADJUSTER_FIELDS` 를 새로 만든 것과 반대의 결정이고, 반대인 이유가 요구다: 사정인은 「덜 본다」였고 상담사는 「똑같이 본다」다. 상수를 하나 더 만들면 두 목록이 갈라질 수 있고, 갈라지는 순간 R1 이 깨진다.
- `audit.py` — `record_agent_access(agent_id, subscriber_id, claim_id, at)` 하나를 더한다. 기존 `record_access`(사정인용, 셋)는 **고치지 않는다**: 인자를 선택적으로 늘리면 0008 이 못 박은 세 키 집합이 흔들리고(R9②), 기본값을 둔 인자는 0008 Design 이 이미 배제한 모양이다. 새 함수도 같은 규율을 지킨다 — 스칼라 넷만 받고 원장 레코드를 받지 않으며, 시각은 UTC 벽시계를 인자로 받는다(`records.py` 의 `now` 는 캐시 만료용 단조 시계라 기록의 시각이 될 수 없다). 두 함수가 같은 `_ACCESS` 리스트에 쌓는다 — 줄의 모양이 둘이 되는 문제는 F3 이다.
- `records.py`·`routes.py` — 손대지 않는다. 상담사 경로는 `fetch_claim(claim_id, now=now, cached=True)` 로 부른다. 0008 이 `cached` 를 기본값 없는 필수 키워드로 만들어 둔 덕에, 이 경로도 정책을 호출부에서 **명시**한다.
- 판정 순서: 세션 없음 → `unauthenticated` · 상담사 세션 아님/사번 없음 → `not_found` · 본인확인 표시 없음·확인 시각 불량·30분 초과 → `verification_required` · 번호 형식 불일치 → `invalid_claim_id` · (여기까지 상류 호출 0 · 기록 0) → `fetch_claim(cached=True)` → 가입자 불일치·없는 건 → `not_found`(기록 0) → `build_response(record, RESPONSE_FIELDS)` → `record_agent_access(...)`. 기록은 값이 나가는 것이 확정된 뒤에 남긴다 — 「열람 기록」이므로 열람이 실제로 일어난 조회에만 붙는다(0008 F8① 과 같은 선택, 여기서는 F7).
- 세션 계약(콘솔 담당 팀 확인분을 이 spec 이 키 이름으로 옮긴 것): `{"role": "agent", "agent_id": "<사번>", "verified_subscriber_id": "<확인된 가입자 번호>", "verified_at": "<확인 시각, UTC ISO-8601>"}`. 확인 표시가 지워진 세션은 `verified_subscriber_id` 가 없거나 비어 있는 세션이다. **키 이름 `verified_subscriber_id` 는 이 설계의 안전장치다** — 확인된 가입자를 `subscriber_id` 키로 실으면 0002 핸들러가 상담사 세션을 고객 본인으로 보고 그대로 통과시켜, 접근 기록이 없는 조회 경로가 생긴다. 키를 가르면 그 경로가 문법으로 막히고 R9③ 이 그것을 잰다. 실제 키 이름은 콘솔 담당 팀이 확정할 자리다 — **F1**.
- 시계는 하나다. `at` 은 UTC ISO-8601 문자열이고 두 곳에 쓰인다: R6 의 만료 판정(세션의 `verified_at` 과 같은 형식으로 보고 뺀다)과 R8 의 기록 시각. 0008 이 `at` 을 ISO 문자열로 주입해 둔 모양을 그대로 잇는다 — 만료용으로 epoch 숫자를 따로 들이면 한 핸들러에 벽시계가 둘이 된다. 파싱이 실패하면(형식 불일치·타입 불일치) 닫는 쪽으로 판정한다(R6). `VERIFICATION_TTL_SECONDS = 1800` 은 `agent_routes.py` 의 상수다.
- 원장 표본에 행 둘을 더한다 — `C-3001`(가입자 `S-77`)·`C-3002`(가입자 `S-12`). 기존 행은 손대지 않는다: `C-1001`·`C-1002` 는 0002·0005·0006·0007 의 시험이, `C-2001`~`C-2003` 은 0008 의 시험이 전제를 잡고 있고, `C-1003`·`C-8888`·`C-9999` 는 「원장에 없다」를 시험이 단정하는 번호다(`tests/test_claims_status_incident.py:23` 은 `C-1003` 의 부재를 단정한다 — 이 번호는 못 쓴다). 새 행의 `status` 는 0008 R10 의 닫힌 다섯 값 안에서 고른다 — 안 그러면 0008 의 AC10 이 빨개진다.

secure-api-review 점검: ① 인증 — 익명 경로 없음. 상담사 콘솔의 기존 세션 없이는 아무 값도 나가지 않고 새 토큰·새 계정·새 권한을 만들지 않는다(콘솔 로그인은 이미 사번으로 있다). 다만 이 세션은 고객 포털이 아니라 **상담사 콘솔**에서 온다 — 스킬의 org note(「포털이 게이트웨이 JWT 를 검증해 세션으로 바꾼다; 세션만 읽는 코드는 ①을 충족한다」)는 「세션 계약 자체가 바뀌면 다시 들라」는 단서를 달고 있고, 이번이 그 경우다: **F8**. ② 입력 검증 — GET 이라 본문 없음, 경로 인자 `claim_id` 는 `C-<숫자>` 형식만 통과, 세션은 아는 키 넷만 읽고 모르는 키는 읽지 않는다, `verified_at` 은 형식이 맞지 않으면 값을 내주지 않는 쪽으로 닫는다. ③ 감사 — 상태를 바꾸지 않는 읽기 전용이지만 보안팀·법무·감사팀 결정으로 열람 기록을 남긴다(R8). 규칙 문면의 넷(actor·action·entity·timestamp)에 대해 이 기록은 actor=사번, entity=청구 번호, timestamp=시각이고 넷째로 **대상 고객**(가입자 번호)이 붙는다 — 감사팀이 「누구」를 한 줄의 요소로 지정했기 때문이다. action 은 이 경로에서 「조회」 하나뿐이라 필드로 두지 않는다(0008 과 같은 판단) — 그 선택이 사정인 줄과 상담사 줄을 구분 불가능하게 만드는 문제는 **F3**. ④ 데이터 분류 — pii(가입자 이름·주민번호·계좌)와 내부 심사 메모는 응답·오류 문구·접근 기록 어디에도 없다. 접근 기록에 들어가는 가입자 번호는 보안팀·법무가 「고객 개인정보가 아니라 접근 기록」으로 판정한 값이다(R8) — 이 spec 이 스스로 내린 분류가 아니다. `status` 의 값 집합은 0008 R10 이 닫아 둔 다섯이고, `next_step` 은 고객에게 이미 나가는 값이라 상담사에게도 나간다(클레임 운영팀장·법무).
## Constraints
intent 0009 에서 그대로 옮긴 것:
- 기존 인증만 쓴다 — 상담사 콘솔의 사번 로그인 그대로. 새 계정·새 로그인은 만들 일이 없다.
- 보여 주는 값은 고객이 포털에서 보는 것과 같은 것이다. 더 보이면 상담사가 그걸 읽어 주게 되고, 그게 사고다. 내부 청구 시스템 화면의 내부용 값은 이 화면에 오면 안 된다.
- 본인확인이 먼저다 — 콘솔의 「본인확인 완료」를 누르지 않은 통화에서는 보이지 않는다.
- 열람 기록이 남아야 한다 — 어느 상담사가 어느 고객 건을 언제 봤는지. 지금 청구 시스템 화면이 남기고 있으므로 새 화면도 같아야 한다.
- 청구 번호 목록은 본인확인 뒤 뜨는 고객 조회 화면에 이미 있다 — 새로 만들지 않는다. 상담사가 거기서 번호를 골라 넘어온다.
- 내부 청구 시스템 화면은 없어지지 않는다 — 다른 업무에 쓴다.
- 범위 밖: 고객 정보 수정 · 통화 녹음 · 본인확인 절차 자체 손질 · 청구 접수·수정 · 알림 · 목록 새로 만들기 · 사정인 위임 조회(0008) · 고객 포털 화면(0002).
제품 오너가 정책 소유자에게 확인해 넘긴 것(2026-09-09):
- 「본인확인 완료」를 누르면 상담사 콘솔 세션에 확인된 고객의 가입자 번호와 확인 시각이 실린다. 세션에는 상담사 사번도 있고, 세션 종류가 상담사 세션으로 구분된다. 「통화 종료」 또는 30분이면 그 고객 표시가 세션에서 지워진다(콘솔 담당 팀).
- 조회는 그 세션 표시가 **있는 통화에서만** 된다 — 사후 기록만으로는 부족하고 세션 표시가 선행 조건이다(보안팀·법무).
- 열람 기록은 상담사 사번·고객 가입자 번호·청구 번호·시각 넷이고, 고객 개인정보가 아니라 접근 기록이라 「새 개인정보 저장 금지」와 충돌하지 않는다(보안팀·법무). 원장의 주민번호·계좌·내부 메모는 상담 화면에 나가면 안 된다.
- 감사 기록 한 줄 = 누가(사번)·누구(가입자 번호)·어느 건·언제. 저장소는 기존 감사 로그 시스템이고 이 모듈의 범위 밖이다(감사팀; 0008 과 같은 방식).
- 상담사에게는 고객이 보는 값 **그대로** — 다음 단계 포함. 상담사는 고객을 대신해 읽어 주는 사람이라 사정인과 다르다(클레임 운영팀장·법무).
- `due_date` 는 원장 값이다 — 계산하지 않는다. 초당 50건은 전 경로 합산이고 하루 70통은 여유 안이며, 상담사 경로는 고객 경로와 같은 캐시를 써도 된다(claims-core 팀).
- claims-core 는 읽기만 한다.
설계하며 발견한 것:
- 「고객이 보는 것과 똑같은 값」은 상수를 **공유**해야 성립한다. 목록을 복사하면 두 벌이 되고, 두 벌은 언젠가 갈라진다. 그래서 이 사슬은 `response.py` 에 아무것도 더하지 않는다 — 0008 이 상수를 더한 것과 반대다.
- 확인된 가입자를 담는 세션 키가 0002 의 `subscriber_id` 와 **같으면** 기록 없는 조회 경로가 열린다(F1). 키를 가르는 것이 이 spec 의 유일한 방어이고, 그 방어는 코드가 아니라 콘솔 팀과의 계약에 있다.
- 접근 기록 함수를 늘리지 않고 **하나 더 만든다.** 인자를 선택적으로 늘리면 0008 이 못 박은 세 키가 흔들린다. 기록의 키 집합은 청중마다 닫혀 있어야 한다.
- 만료 판정과 기록 시각은 같은 벽시계를 쓴다. 캐시의 `now`(단조)와 섞으면 기록에 「부팅 후 12.3초」가 남고, 만료가 부팅 시각 기준이 된다.
- 상담사 경로는 **캐시된 레코드로 소유를 판정한다.** 0008 이 배정(권한)에 대해 하지 않기로 한 일이다. 제품 오너·claims-core 의 지시대로 두되, 가입자가 바뀌는 일이 있으면 60초 창이 생긴다는 것을 F6 으로 든다.
## Open questions from intent
일곱 개 모두 답이 왔다 — carried forward 는 0 이다.
- 「본인확인 완료」가 시스템에 무엇을 남기는가 → **answered**: 상담사 콘솔 세션에 확인된 고객의 가입자 번호와 확인 시각이 실리고, 통화 종료 또는 30분이면 지워진다 (콘솔 담당 팀, 제품 오너 전달 2026-09-09). R1·R4·R6 이 받는다. 남은 것은 **키 이름**이고 그것이 F1 이다.
- 사번 로그인이 고객 세션의 소유 판정을 무엇으로 대신하는가 → **answered**: 세션 종류로 상담사 세션이 구분되고, 판정에 쓰는 값은 세션에 실린 **본인확인된 가입자 번호**다 (콘솔 담당 팀·보안팀). R3·R5 가 받는다. 사번은 판정에 쓰지 않고 기록에만 쓴다 — 사번은 「누가 봤는가」이지 「무엇을 볼 수 있는가」가 아니다.
- 본인확인 없는 조회를 무엇이 막는가, 사후 기록으로 충분한가 → **answered**: 충분하지 않다 — 세션 표시가 선행 조건이다 (보안팀·법무). R4 가 받고, R6 이 만료까지 본다.
- 감사 기록 한 줄에 무엇이 들어가고 어디에 쌓이는가 → **answered**: 넷(사번·가입자 번호·청구 번호·시각), 저장소는 기존 감사 로그 시스템이고 이 모듈의 범위 밖이다 (감사팀). R8 이 받고 저장소는 Out of scope 다.
- 「다음 단계」를 상담사가 읽어 주어도 되는가 → **answered**: 된다 — 고객이 보는 값 그대로, 상담사는 대신 읽어 주는 사람이라 사정인과 다르다 (클레임 운영팀장·법무). R1·R7 이 받는다. 0008 이 사정인에게서 뺀 것과 반대 결정이고, 그래서 허용 목록도 반대로 **공유**한다.
- 「예정일」이 원장 값인가 계산 값인가 → **answered**: 원장 값이다 (claims-core 팀). 제품 오너 지적대로 이 답은 0008 spec 에서 이미 나왔다 — intent 0009 의 「두 번 답이 안 났다」는 잘못 적힌 것이고, 이 spec 이 그 자리를 정정한다(intent 파일은 고치지 않는다; 머지된 문서다).
- 초당 50건에 하루 70통이 얹히는가 → **answered**: 한도는 전 경로 합산이고 70통은 여유 안이다; 상담사 경로는 고객 경로와 같은 캐시를 써도 된다 (claims-core 팀). R10 이 받는다. 다시 볼 조건은 0008 과 같다 — 조회량이 자릿수로 늘 때(목록 화면·자동 폴링).
## Flagged concerns
제품 오너가 「충돌해서 만족시킬 수 없는 곳을 먼저」 요청했으므로 그 순서로 적는다. **F1 은 진행을 막는다** — 나머지 여덟은 막지 않는다.
- **F1 (충돌 · 진행 전 답이 필요) 상담사 세션이 0002 고객 경로로 들어가면 기록 없이 값이 나간다.** 보안팀·법무는 「세션 표시가 있는 통화에서만 + 열람 기록」을 요구하는데, 0002 의 고객 자가조회는 기록을 남기지 않는다(0008 R9 가 그렇게 못 박았다). 두 정책이 부딪히는 지점은 코드가 아니라 **세션의 키 이름 하나**다: 콘솔이 확인된 가입자를 `subscriber_id` 키로 싣는다면 `routes.get_claim_status` 가 그 세션을 고객 본인으로 판정해 네 필드를 그대로 내주고, 기록은 0 이다 — 이 사슬이 세우려는 통제를 우회하는 경로가 처음부터 열린 채로 생긴다. 이 spec 은 키를 `verified_subscriber_id` 로 가르는 것을 전제로 삼고 R9③ 으로 그것을 잰다. 콘솔이 이미 `subscriber_id` 로 싣고 있다면 선택지는 셋이고 전부 이 spec 밖의 결정이다: ① 콘솔이 키를 바꾼다, ② 0002 핸들러가 상담사 세션을 거부한다(0008 R9 의 「0002 는 변하지 않는다」를 뒤집는 일), ③ 고객 경로에도 접근 기록을 붙인다(별건의 사슬). 결정: 콘솔 담당 팀(실제 키 이름) · 보안팀 · 제품 오너.
- **F2 (요구끼리 부딪힘) 「고객이 듣는 말과 화면에 뜨는 말이 같다」 vs 60초 캐시.** intent 의 성공 문장은 동시성인데 TTL 캐시는 최대 60초 낡은 값을 준다. 같은 캐시를 쓰라는 claims-core 의 답이 이것을 완화한다(두 경로가 같은 스냅샷을 본다) — 그러나 없애지는 못한다: 통화 중 고객이 포털을 새로 고쳐 원장의 새 값을 보는 동안 상담사는 캐시의 옛 값을 읽어 줄 수 있다. 「지급완료」 직후 최대 60초가 그 자리다. 0002 F1 이 아직 닫히지 않은 채 이번 요구의 목적과 정면으로 닿았다. 결정: 클레임 운영팀장(60초가 맞는가) · 콜센터 운영팀장 박민서(통화 중 최대 60초 불일치를 감수하는가).
- **F3 (충돌) 감사 로그 한 줄이 두 모양이 된다.** 사정인 줄은 셋(0008 R8), 상담사 줄은 넷(R8). 같은 저장소에 쌓이면 소비자가 두 줄을 구분할 근거는 「어느 id 키가 있느냐」뿐이다. 종류를 나타내는 다섯째 필드를 넣으면 보안팀·법무가 못 박은 넷을 넘고, 안 넣으면 감사팀의 월간 추출이 키 모양에 의존한다. 이 spec 은 넷을 넘지 않는 쪽을 골랐다 — 필드를 늘리는 것은 결정이지 구현이 아니기 때문이다. 결정: 감사팀(구분이 필요한가) · 보안팀·법무(다섯째 필드 허용 여부).
- **F4 만료를 누가 소유하는가 · 확인 시각의 형식.** 콘솔이 30분에 지운다고 했는데 이 spec 은 앱에서 한 번 더 본다(R6). 이유는 0008 F1 의 교훈이다 — 권한 표시를 남이 지워 주기를 기다리지 않는다. 대가가 둘 있다: ① 두 시계가 어긋나면 29분대 조회가 `verification_required` 로 닫힐 수 있다. ② 확인 시각의 형식이 아직 미확정이라 이 spec 은 UTC ISO-8601 문자열로 가정하고 못 읽으면 닫는 쪽으로 판정한다 — 콘솔이 epoch 숫자나 지역 시각으로 싣는다면 변환은 콘솔·포털 경계에서 일어나야 하고 이 핸들러는 문자열 파싱을 늘리지 않는다. 결정: 콘솔 담당 팀(형식·시계·지우는 시점) · 보안팀(앱의 이중 확인을 유지할지).
- **F5 `verification_required` 를 별도 오류 코드로 두는 것.** 0008 은 청중이 아닌 세션을 `not_found` 로 합쳤다. 여기서 코드를 가른 이유는 둘이다: 이 판정은 청구 번호를 보기 전에 세션만으로 끝나므로 원장의 존재 여부를 흘리지 않고, 상담사가 화면에서 「본인확인부터 하세요」를 보는 것이 통화 시간을 줄인다(intent 의 목적). 그래도 오류 문구를 나누는 것은 정책이다 — 0002 F2 에서 법무가 잡고 있는 자리와 같은 종류다. 결정: 보안팀 · 법무.
- **F6 캐시된 레코드로 소유를 판정한다.** 0008 은 배정이 **권한**이라 캐시로 판정하지 않기로 했다(R7). 이 경로는 지시대로 `cached=True` 를 쓰므로, 청구 건의 가입자가 바뀌는 일(승계·법인 청구 정정·잘못 접수된 건의 이관)이 있다면 최대 60초 동안 낡은 소유로 판정한다. 0002 의 고객 경로도 같은 노출이지만 거기서는 읽는 사람이 본인이라 드러나지 않았다 — 상담사 경로에서는 **남**이 읽는다. 결정: claims-core 팀(청구 건의 가입자가 바뀌는가). 「바뀐다」면 R10 을 뒤집어 `cached=False` 로 가는 것이 답이고, 그때 초당 50건을 다시 본다.
- **F7 실패한 조회는 아무 데도 남지 않는다(0008 F8① 과 같은 자리).** 기록은 값이 나간 조회에만 붙으므로, 본인확인을 마친 상담사가 `C-<숫자>` 를 훑어도 `not_found` 만 돌아오고 기록은 0 이다. 사정인 경우와 다른 점은 범위다 — 훑기로 얻을 수 있는 것은 확인된 그 고객 한 명의 건뿐이고, 그 고객의 건은 어차피 볼 수 있다. 실패 시도까지 남기려면 그것은 「열람 기록」이 아니라 접근 시도 기록이고 결정이 다시 필요하다. 결정: 보안팀.
- **F8 콘솔 세션의 정본과 게이트웨이 JWT.** `secure-api-review` ①의 org note 는 「포털이 JWT 를 검증해 세션으로 바꾸므로 세션만 읽는 코드는 ①을 충족한다」로 두 번(0002 F3·0008 F4) 닫힌 자리지만, 그 note 는 「세션 계약 자체가 바뀌면 다시 들라」는 단서를 달고 있다. 이번 세션은 고객 포털이 아니라 **상담사 콘솔**에서 오고 키도 다르다 — 누가 콘솔의 토큰을 검증해 이 앱에 세션을 건네는가가 확인되지 않았다. 결정: 콘솔 담당 팀 · 보안팀.
- **F9 브랜드·UX 기준 스킬이 없다.** `/spec` 의 문면은 「브랜드 가이드·보안 정책·UX 기준에 맞춰라」인데 `.claude/skills/` 에 있는 것은 `capture-intent`·`design-spec`·`plan`·`secure-api-review` 넷뿐이다. 이 spec 은 보안만 스킬로 점검했고 **브랜드·UX 는 점검하지 않았다** — 맞출 기준이 레포에 없다. 상담 화면 자체가 Out of scope 인 것과 같은 결정(0008 F6)으로 두되, 화면을 만드는 사슬이 열릴 때는 기준부터 있어야 한다. 결정: 제품 오너.
## Out of scope
상담사 콘솔의 화면·문구·표시·접근성(프론트엔드 전부 — F9) · 본인확인 절차 자체(구두 대조·ARS 도입·「본인확인 완료」 버튼의 동작) · 콘솔 세션의 발급과 만료 처리(콘솔 팀 소유; 이 spec 은 세션을 읽기만 한다) · 청구 번호 목록 화면 · 고객 정보 수정 · 통화 녹음 · 청구 접수와 수정 · 상태 변경 알림 · 고객 자가조회 경로(0002)와 사정인 경로(0008)의 동작 변경 · 0002 spec 파일의 F1·F3 갱신 · intent 0009 의 「예정일」 문장 정정(머지된 문서다) · 접근 기록의 저장소와 보존 기간(`audit.record_agent_access` 까지) · claims-core 쪽 변경(읽기만 한다) · 실제 HTTP 서버·라우터 배선(핸들러 함수까지) · 상담사 계정과 권한 관리 · 통화 시간 측정(교환기 기록은 콜센터 운영팀이 센다).
## Acceptance criteria
- AC1 → R1 본인확인 표시가 있는 상담사 세션으로 그 가입자의 건을 조회한 응답이, 같은 건을 그 가입자의 고객 세션으로 0002 핸들러에서 조회한 응답과 **바이트 단위로 같다**. 키 집합은 정확히 {claim_id, status, next_step, due_date} 이고 값이 비어 있지 않다. 판정에 쓰는 키 집합은 구현에서 임포트하지 않고 시험이 따로 적은 것이다.
