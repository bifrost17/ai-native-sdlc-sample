# Spec: 후속 요구와 완료 조건에 설계·계획 갱신 연결
Upstream: intent.md@bdc1cbee49c1c26a00f65633c3d7d8417202c2fe. Status: draft.
사용자의 중요한 실패 지적과 기존 개선 반복 위임에 따라 root가 다음 단계 진행을 수락했다.

## Requirements
- R1 사용자 동작·범위·수용 기준 변화는 spec, 구현 파일·작업 순서·PR 범위·검증 변화는 plan에 반영한다.
  중요한 새 요구가 생겼는데 코드·시험·README만 바꾸고 완료를 보고하면 실패다.
- R2 후속 요청 진입점과 완료/리뷰에서 최신 합의·문서·diff·검증을 함께 대조한다. 영향 없는 문서를
  형식적으로 바꾸거나 이미 허용한 일상 구현 선택에 반복 승인을 요구하지 않는다.
- R3 spec 수락 판 S를 먼저 기록하고 plan의 Upstream을 S로 연결한다. 계획 개정·이유는 해당 구현
  커밋에 함께 담는다. 커밋을 HUMAN이 수행하면 AGENT가 정확한 인계와 문서 상태를 제공해야 한다.
- R4 기존 누락을 중요한 실패로 재분류한다. HUMAN의 문서 수정 촉구 후 복구는 보존하되 통과 근거로
  대체하지 않는다. 환경상 지침 제공이 확인되지 않으면 원인 판정을 유보한다.
- R5 새 세션 두 건에 작은 업무 변경을 전달해 개정·수락·동시 커밋과 기존 동작 회귀를 관측한다.

## Design
CLAUDE의 후속 요청/완료 지침, REVIEW, 기존 PROCESS·Git 정책 문구를 짧게 연결한다.
새 사용 후보를 원래 판에서 파생하고, 제작 main에는 데이터·결과·판정과 북극성 주석만 둔다.
실험은 PR1 통합 제품에 새 지침을 적용한 별도 clone에서 수행한다. 원래 JSON 변경 재현과
파일 출력이라는 다른 업무 변경을 사용하며 코딩이나 문서 수정 방법은 HUMAN 프롬프트로 주지 않는다.

## Constraints
정책 집행 코드·필수 스킬·추가 서비스 없음. 역할은 HUMAN=Codex, AGENT=Claude Code Sonnet·low.
실제 권한 분리·호스티드 CI·배포는 범위 밖. 단일 실행의 성공을 일반적인 신뢰도로 확대하지 않는다.

## Acceptance criteria
- AC1 → R1/R2/R3 지침 문서와 양식의 의미가 일치하며 수락 SHA의 순환이나 불필요한 전체 재승인이 없다.
- AC2 → R4 실제 지침 제공과 원래 실패를 구분해 기록하고 복구 사실로 초기 실패를 지우지 않는다.
- AC3 → R5 누락 지적 없는 업무 대화에서 필요한 문서 개정과 유효한 수락·구현 커밋 인계가 이뤄진다.
- AC4 → R1~R5 제품 기존/새 동작, 전체 흐름에 연결된 인계, 제작 검사와 독립 검증을 확인한다.
