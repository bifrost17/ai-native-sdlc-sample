# Spec: 우리 intent 양식과 작성 지침의 예시 기반 재설계
Upstream: intent.md@4f9fa6d. Status: draft.
사용자가 root 작성과 Astra·Fable 리뷰를 위임하여 이 제작 사슬은 draft 위에서 진행한다. 운영 승인으로 표시하지 않는다.

## Requirements
- R1. 요청자의 현재 상황·기회, 바라는 변화와 이유, 영향을 받는 대상, 확인된 제약과 미해결 질문을
  읽을 수 있다. 수치·시스템 이름·원인·질문 담당자를 임의로 만들지 않는다.
- R2. 요청자의 해결 제안은 제안으로 보존하고 그 밑의 목적을 묻는다. 확인된 필수 조건과 아직
  선택되지 않은 방법을 구별하며 intent 단계에서 기술 설계를 확정하지 않는다.
- R3. 작성 스킬은 필요한 질문과 조건별 상세를 돕고, 양식에는 다음 사람이 이해할 답을 남긴다.
  작은 작업에 없는 자료·정해진 질문 횟수·불필요한 별도 문서를 요구하지 않는다.
- R4. Codex root가 합성 사례의 입력·작성 결과, 대안, 최종 양식과 스킬을 작성한다. Astra와
  Claude Code CLI Fable은 같은 후보 파일을 읽어 독립적으로 검토하고 수정 권한은 받지 않는다.
- R5. 두 리뷰의 중요한 지적을 반영하고 같은 최종 후보에 대해 PASS를 받는다. 판정은 남은
  불확실성과 검사 범위를 기록하며 원래 대화 없이 문서를 이해하는 읽기 점검도 포함한다.
- R6. 기존 자동 intent 생성·하류 spec 인계·스킬 복사본 동일성·기본 검사가 회귀하지 않아야 한다.
  새로운 의미 검사기나 개별 문구를 고정하는 테스트는 만들지 않는다.

## Design
원본 Lesson 2와 대표 입력의 완성 예시를 먼저 대조한다. 다섯 핵심 구획 안에 필요한 내용을
자연스럽게 담는 안과 이유·근거·제안을 각각 분리한 안을 비교해 작성 부담이 작은 후보를 선정한다.
제목·Problem의 강한 해결책 금지와 무조건적인 수치/재현 요구를 완화하고, 지침에서 관측과 추정을
구분한다. 기존 5절이 실제 예시에 충분하면 그대로 사용하되 보존 자체를 목표로 삼지 않는다.

## Acceptance criteria
- AC1 → R1–R3: 기능·버그·불완전한 요청의 root 작성 예시가 주어진 입력을 왜곡·발명하지 않으며
  중요한 제안·제약·미확인 사항을 구분한다. 요청자가 고칠 수 있고 다음 단계가 이해할 수 있다.
- AC2 → R4–R5: 리뷰 요청·검토 파일 해시·실제 모델/추론·지적과 처리·최종 판정을 보존한다.
  한 리뷰어의 결과를 다른 리뷰어의 최초 판단에 주입하지 않는다. 통과를 요구하며 기준을 낮추지 않는다.
- AC3 → R6: make check, 기존 소비자의 인접 흐름, 독립 verifier의 계획 대조를 통과한다.
  테스트 fixture와 북극성 원문을 바꾸어 실패를 숨기지 않는다.

## Out of scope
spec·plan 양식 재설계, 전체 SDLC 실행 실험, 호스티드 PR 승인·배포 검증, 새 외부 skill 설치.
이번 부분 검토를 제품 구현 성공이나 조직 전체의 적용 성공으로 판정하지 않는다.
