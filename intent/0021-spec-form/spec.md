## Requirements
- R1. 북극성 Lesson 3의 요구·설계 통합, 관련 팀 정책 적용, intent와의 대조, 질문 처리와 사람의
  우려 해소를 지원한다. Lesson 4의 파일별 작업·순서·명령은 plan에 남긴다.
- R2. 변화·보존 계약·대표 성공/실패 기준과 중요한 설계 선택·이유·영향을 함께 읽을 수 있다.
  현재 사실, 확인된 요구, 제안·가정·예시를 구별한다. 자료와 성능 수치를 만들지 않는다.
- R3. 작은 기능·정밀한 버그·이행을 포함한 변경의 완성 예시를 root가 먼저 쓴다. 기존 구조도
  후보로 비교하고, 공통 핵심과 필요한 상세를 도출한다. 질문·판단 방법은 작성 스킬에 둔다.
- R4. intent의 질문과 설계 중 발견한 질문을 모두 처리하며, 답이 요구·설계를 바꾸는 중요한
  미결을 단순히 담당자 이름으로 덮어 plan에 넘기지 않는다. 중요한 결정 변경은 spec과 관련
  plan에 반영하고 원래 intent까지 바뀌었는지 확인한다.
- R5. Astra/ultra와 Claude Code CLI Fable/max가 같은 후보를 독립적으로 읽고 중요 지적을
  보고한다. root가 수정하고 같은 최종 판을 통과시킨다. 범위와 실행 한계도 남긴다.
- R6. 메타데이터·R/AC 참조·질문 이월·Flagged concerns·기존 정책 및 plan 소비자가 회귀하지
  않아야 한다. 기존 eval의 새 절 이름만 맞추며 질문 누락의 실패 기준과 정책 요구는 약화하지 않는다.
- R7. 제작용 원본과 사용판의 배포 경계를 구분한다. 사용판을 갱신하면 별도 파생 후보로 보존하며
  선택 스킬의 선택성과 References applied 표현을 유지한다. 제작 자산과 원시 리뷰를 제품에 넣지 않는다.

## Design
요구·수용 기준을 서로 연결하고, 선택 이유와 흐름은 Design 안에서 필요한 만큼 설명한다.
제약과 제외 범위를 한 곳에 두어 중복을 줄이며, Open questions는 출처와 관계없이 중요한
불확실성을 다룬다. Flagged concerns는 사람의 판단이 필요한 우려를 찾기 쉽게 유지한다.
문서 앞에는 핵심 변화·선택·남은 우려를 짧게 안내한다. 모든 상세 항목을 기본 절로 만들지 않는다.

현재 파일명·Upstream/Status·Skills applied와 R/AC 표식을 유지한다. 실제 사용판은 기존처럼
References applied를 사용한다. 관련 작성 스킬과 기존 eval 안내를 같이 고치고, 정책 플러그인과
plan 양식은 의미상 조정이 꼭 필요할 때만 수정한다. 별도 새 의미 검사기는 작성하지 않는다.

## Acceptance criteria
- AC1 → R1–R4: 세 유형의 예시와 중간 발견 전후 기록에서 요구·보존 계약·설계 선택·대표 검증·
  미결의 영향이 입력과 일치하고, 원래 대화가 없는 독자가 다음 판단을 설명한다.
- AC2 → R3,R5: 두 후보의 실제 정보 배치·중복·상세 확장·갱신을 비교한 근거, root의 선택 이유,
  같은 최종 파일 해시와 두 모델의 PASS가 남는다. 스타일만으로 검토 기준을 높이지 않는다.
- AC3 → R6,R7: 기존 검사와 독립 verifier, 적용 가능한 기존 semantic eval 또는 실제 부분 대화
  검토의 결과를 보존한다. 실행하지 못한 것은 통과로 쓰지 않는다. 사용판은 선택 스킬·참조 표현·
  제작 자료 제외와 원본 간 대응을 확인한다.

## Out of scope
plan 양식 재설계, 새 생산 프로그램·오케스트레이터·정책 엔진, 호스티드 PR 승인·merge·운영 배포,
플레이북 전체의 재평가. 부분 문서/대화 검토를 전체 개발 프로세스 성공률로 확대하지 않는다.
