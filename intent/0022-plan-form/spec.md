# Spec: 통합 가능한 실행 단위와 확인 방법을 연결하는 plan 양식
Upstream: intent.md@c89632f. Status: draft.
사용자의 양식 작성·반영 위임으로 draft에서 진행한다. 실제 제품 오너의 수락이나 PR merge를 뜻하지 않는다.

## Requirements
- R1. 북극성 L4의 변경 파일·순서·위험·증명을 유지하고, 실제 코드와 수락된 spec 판을 근거로
  대화를 보지 않은 독자가 구현할 수 있게 한다. 설계 계약을 plan에 새로 숨기거나 전부 복제하지 않는다.
- R2. 작은 작업은 짧게 작성한다. 여러 PR에서는 목적·선행 관계·범위·머지 뒤 main의 동작과 남은
  범위·검증을 연결한다. PR 크기는 응집성과 검증 가능성으로 판단하며 파일·작업 수로 강제하지 않는다.
- R3. 병렬 작업일 때만 worktree·파일 경계·공유 계약의 판·통합 책임과 공유 계획 갱신 조정을 설명한다.
  공유 파일 작업은 순차 실행한다. 종속 작업은 선행 main 통합 후 시작하는 기본과 stacked 예외를 따른다.
- R4. 위험한 단계의 중간 신호와 인접 회귀·최종 통합 검증을 계획한다. 예정 검사와 실행 결과를 구별한다.
  결함에는 재현 실패 확인·커밋 후 수정을 적용하고 이를 모든 종류의 변경 순서로 일반화하지 않는다.
- R5. 구현 발견에 따라 영향받는 plan·spec·intent만 갱신한다. 상위 판 수락과 하위 pin, 계획·이유의
  해당 구현과 같은 커밋을 지키며 작은 허용 선택마다 승인을 새로 요구하지 않는다.
- R6. root의 완성 예시와 두 배치 비교 후 Astra/ultra와 Claude Code CLI Fable/max의 독립 검토를
  받는다. 같은 최종 후보의 중요 지적을 해결한다. 실제 Sonnet 실행과 독립 verifier의 한계도 기록한다.
- R7. 사용판을 0021에서 별도 파생하고 양식·선택 스킬/예시만 전달한다. 기존 메타데이터와 네 절을
  유지하며 현재 verifier·REVIEW·lesson map의 범위/수락 해석을 맞춘다. 역사 자료·실험 원본·기존 검사 기준은 보존한다.

## Design
네 절을 공통 골격으로 유지한다. 작업은 구체적인 결과로 적고 필요한 경우 Order of work 안에
PR별 통합 설명과 병렬 인계를 둔다. Proof는 각 결과의 관측과 기준을 연결하며 중복은 참조로 줄인다.
양식에는 답을 남기고 작성 스킬에는 탐색·분할·질문·갱신 판단을 둔다. 상세 참조는 필요할 때만 읽는다.
F01 기능·B01 결함·F02 두 기능과 M01 합성 이행에 서로 다른 상세도를 사용한다. M01 경로·명령은
합성 실행 맥락을 별도로 선언하며 실제 코드 읽기·운영 시험으로 주장하지 않는다.

## Acceptance criteria
- AC1 → R1–R5: 예시마다 코드/입력의 근거, 작업 결과, 검증 기대값을 찾아 실행 판단을 설명할 수 있다.
  F02는 첫 목록 PR만으로 쓸 수 있고 요약은 선행 통합 뒤 이어진다. M01은 이행·복구와 통합 검증을 잃지 않는다.
- AC2 → R6: 두 배치 비교와 같은 최종 후보의 Astra·Fable PASS, 수정 내역·해시·모델 실행 기록을 남긴다.
- AC3 → R2,R4–R7: 사용판 파생의 실제 Sonnet 계획/인계와 구현 일부를 관찰한다. 새 대화 문맥, PR별
  통합 상태, 중간 계획 변경과 구현의 같은 커밋 여부를 실제 Git·시험으로 확인하고 미실행은 따로 쓴다.
- AC4 → R7: make check와 기존 검증, 독립 verifier, 전달 범위·문서 참조·북극성 원문 불변을 확인한다.

## Out of scope
실제 고객 제품, hosted PR·CI·운영 배포, 원격 push/merge, 전체 SDLC 성공률 주장, 새 production
검사 프로그램, 필수 스킬 설치, 모든 예시의 구현. 이번 변경은 선행 0021 완료판에 의존한 하나의 문서 PR 범위다.
