# Spec: spec 검토 범위와 계약 충분성
Upstream: intent.md@6087999. Status: draft.
작성·구현 허가: 프로젝트 오너의 2026-09-14 보완·OpenCode 실험 요청. 단계 진행 허가이며 실제 효과 판정은 별도다.
Skills applied: skill-creator, 시스템 제공 판(버전 미노출); 실제 읽어 기존 역할·선택성과 최소 보완에 적용.

## Requirements
- R1: spec 인계·중요 설계 개정에 기존 REVIEW/feedback/verifier의 설계 검토 범위를 연결한다.
- R2: 공유 계약 양쪽의 호환, 중요한 AC 장애 분기의 처리·복구, 다음 작업이 의존하는 미결정을 근거로 확인한다.
- R3: 설계만의 검토에는 없는 plan·구현·실행 결과를 요구하지 않는다. 구현 완료 fresh 검토와 두 TDD 판별은 보존한다.
- R4: 두 배포판과 제공 adapter·설치 안내를 일치시키고 실제 OpenCode 설치판의 읽기·결과를 검증한다.
- R5: 알려진 어려운 사례, 충분한 작은 문서와 정당한 이월을 평가해 중요한 문제만 최소 보완·재실험한다.

## Acceptance criteria
- AC1 → R1/R2: 인계 전 검토가 기존 흐름에서 발견 가능하며 계약/분기/이월 질문이 표현 형식 의무 없이 적용된다.
- AC2 → R3: 선택형 방식 선택과 기본형 test-first, 구현 완료 fresh verifier 의무를 유지한다. 혼합 작업의 실제 구현을 설계 예외로 처리하지 않는다.
- AC3 → R4: make check, 패키지 strict 검증, 제공 adapter patch 및 설치본 해시·참조 확인이 통과한다.
- AC4 → R5: 복잡한 원본의 공유 의미·독립 장애 공백을 근거와 함께 발견한다. 충분한 문서를 필수 그림·없는 plan·실행 증거 때문에 반려하지 않는다.
- AC5 → R4/R5: 실제 모델/variant·버전·스킬 설치/읽기·대화·브랜치·평가·한계를 보존한다. 실패와 HUMAN 복구는 최초 자발적 성공으로 바꾸지 않는다.

## Design
정본은 [보완 설계](../../docs/decisions/spec-validation-design/README.md)의 검토 방법과 자산 경계다.
이번 사용자 요청에 따라 행동 실험 대상만 Codex/Astra에서 OpenCode/Muse Spark 1.3/xhigh로 변경한다.
작은 spec은 짧은 기존 검토로 충분하며 중요한 공유 경계에는 역량 높은 새 문맥 검토를 우선 활용한다.
판정은 설계 준비·실제 실행·사람 수락을 구분한다. 현재 문제를 새 스킬이나 검사기로 해결하지 않는다.
실험 상세 입력·oracle은 실행 전 고정하며 HUMAN 원본과 에이전트 입력을 분리한다.

## Constraints and scope
활성 템플릿과 스킬 배포·실험 결과에 해당하는 제작 변경만 통합한다. 원본 제품 수정, 전체 SDLC 실행,
두 TDD 판 모두의 실제 제품 개발, 모든 CLI 행동의 통과로 확대하지 않는다. 제품 동작을 추가하지 않으므로 RED를 꾸미지 않는다.

## Open questions
현재 모델 가용성·호출/설치 경로는 실행 전 확인한다. 이용 불가라면 다른 모델로 조용히 대체하지 않는다.

## Flagged concerns
알려진 실패 사례의 재검출은 일반 탐지율을 증명하지 않는다. 충분한 대조 사례와 정당한 이월을 함께 평가한다.
새 기준을 직접 지정한 시험과 사용자 요청에서 자연 선택한 스킬·위임을 구분한다.
