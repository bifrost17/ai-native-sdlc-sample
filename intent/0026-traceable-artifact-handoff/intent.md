# Intent: 다음 세션이 이어받을 수 있는 요구·설계·계획
Author: 사용자 요청, Codex 정리. Status: draft.

## Problem
구현 중 중요한 결정을 바꾸고도 spec과 plan 갱신을 잊으면 다음 세션이 낡은 문서를 기준으로 작업한다.
문서에 링크가 있어도 어느 요구를 어떤 설계와 작업으로 구현하는지 찾기 어려우면 영향 확인 비용이 커진다.

## Proposed outcome
요구사항, 주요 설계 결정·컴포넌트, 구현 작업을 고정 번호로 연결한다. 실제 변경에서 영향을 받은
설계와 작업을 쉽게 찾고, 커밋·중단·인계·재개에서 현재 문서를 확인하도록 한다.
새 담당자가 이전 대화를 읽지 않아도 현재 합의·진행 상태·다음 작업을 이해할 수 있어야 한다.

## Affected users and systems
두 TDD 배포판의 제품 템플릿, 작성 스킬, 팀 feedback 스킬과 제공 검토자·설치 어댑터.

## Constraints
북극성 플레이북을 최우선으로 둔다. intent 양식과 요청자의 언어·제안·미결 질문을 유지하며,
FR/NFR 작성은 spec에서 시작한다. 모든 문서가 같은 내용을 반복하거나 항상 같이 바뀌어야 하는 것은 아니다.
기본형의 test-first와 선택형의 검증 방식 선택을 유지한다. 새 커밋 스킬·의미 판정 검사기·매 커밋
독립 리뷰는 만들지 않는다. 과거 번호와 실험 기록은 보존하고 현재 문서와 혼동하지 않는다.
템플릿은 대체로 잘 동작하는 수준이 목표이며 에이전트의 모든 실수를 막는 장치로 키우지 않는다.

## Open questions
없음. 사용자가 위 추적 구조의 설계·수정과 짧은 정책·기존 feedback 보강을 명시적으로 요청했다.
기존 제품 저장소와 개인 설치본의 갱신은 이번 소스 변경에 자동 포함하지 않는다.
