# Spec — 전수 이력 분석과 근거 있는 소수 개선

Status: draft
Upstream: intent.md@d5e2e7b, 사용자가 수락한 실행 계획.
Current change: 후속 사용자 지시에 따라 조사 결과의 보완을 단위별 수정·적대적 리뷰·지적 해결로 완료한다. 실제 개발 효과 AC04는 계속 유예한다.

## Requirements
- FR01: 조사 시작 시 접근 가능한 원격 refs·모든 PR·연결 이슈·커밋을 고정하고 개발건과 별칭을 연결한다.
- FR02: 모든 개발건의 의도→설계→계획→구현/시험→리뷰/수정→통합/후속 사건을 분석한다.
- FR03: 당시 지침·현재 배포 정본·미커밋 후보를 구분하고 원인과 증거 부족을 따로 기록한다.
- FR04: 현재에 남은 일반 문제만 우선 개선안으로 정리한다. 실제 개발의 전후 비교·다른 도구 실행은 별도 사용자 지시 후 진행한다.
- FR05: 사용자 기억의 네 가설을 사건 근거로 대조하고 실제 UI 설계·초기 통합·설계 단계 검증 방법을 원전 자료와 함께 조사한다.
- FR06: PR 본문과 커밋 메시지에 목적·실제 변경·검증판/한계·관련 설계/계획을 전달하는 간결한 정책과 양식을 제공한다.
- FR07: 새 배포판의 개발건은 changes/<NNNN>-<slug>/로 묶고 총괄 README에서 현재 상태·근거·다음 일을 찾게 한다. 과거 spec은 현재 정본으로 자동 승계하지 않는다.
- FR08: 보완을 여섯 책임 단위로 순차 완료하고 단위별 적대적 리뷰·수정 이유·대상판·한계를 전문으로 보존한다. 전체 패키지 정합성과 기존 동작은 마지막에 독립 검토한다.
- NFR01: 원제품·운영·전역 설치와 기존 WIP를 보존한다. 조사와 실험 공간은 제작 저장소 아래에 둔다.
- NFR02: 조사·리뷰 전문과 수집 출처 원문을 요약으로 대체하지 않고 파일에 보존한다. 대상판·해시·사람의 개입·실패·한계를 연결하며 최종 파일로 작성 순서를 추정하지 않는다.

## Design
### SP01 — 모집단과 증거 (FR01–03, NFR02)
현재 접근 가능한 GitHub main/branches/PR/issues와 그 연결 ancestry를 모집단으로 고정한다.
작업 식별은 intent 경로, PR head/title/body와 실제 변경 경로를 대조한다. 번호만으로 합치지 않는다.
번호 변경은 근거 있는 alias로 남기고, 다중 개발건 PR은 각 건에 연결하되 공통 사건을 중복 집계하지 않는다.
원본은 `.local/research/openwebagent-template-history/20261003/`에, 정리 자료는
`docs/research/openwebagent-template-history/`에 둔다. 인증·reasoning 원문은 공개 기록에 포함하지 않는다.
조사 전문은 연구 폴더에, 수집 원문과 에이전트의 공개 보고 응답 전문·바이트 스냅샷은 로컬 보관소에 둔다.
기존 Git mirror는 부분 clone이며 조사 중 lazy cache가 변할 수 있다. 처음의 pack manifest를 현재 온전한
제품 원문 보관 증명으로 사용하지 않고 후속 감사·관측 스냅샷을 별도 보존한다. 원문 부재·출력 잘림은 복원한 것으로 주장하지 않는다.

### SP02 — 심층 판정과 개선 승격 (FR02–04)
공통 여섯 평가축을 사용한다. 초기 0018/0021/0028로 방법을 교정하고 모든 개발건으로 진행한다.
의미 없는 반복은 제외 이유를 기록한다. 검토 완료·중요한 근거 부족·미검토를 구별한다.
원인은 template/skill/project policy/agent/tool-environment/evidence로 분류한다.
독립 사례의 반복 또는 중대한 단일 사례의 현재판 재현이 있는 문제만 수정 후보로 승격한다.
이미 해결된 문제는 기존 개선 검증 대상으로 돌린다. 필요한 로컬 대화 구간만 추가 조사한다.

### SP03 — 전후 비교와 반영 (FR04, NFR01–02)
현재판과 수정판에 같은 제품 시작판·입력·fixture·model/effort·권한·종료 기준을 적용한다.
두 사례×전후 네 실행과 다른 도구의 별도 사례 한 실행을 기본으로 한다. 초기 분석 밖의 사례를 포함한다.
개별 효과를 분리하지 못한 수정은 묶음 효과로 보고한다. 최대 9실행·수정 2차례·실행당 30분이다.
결과가 불명확하면 보류하며 통제를 더 늘리지 않는다. source 정본과 도구별 전달 의미를 함께 유지한다.
현재 미커밋 후보에서 이미 바뀐 지침은 원래 배포판과 구분해 어떤 판을 실험했는지 기록한다.

### SP04 — 추가 가설과 설계 방법 (FR05)
설계 부족과 정당한 발견을 구분한다. UI는 시안·실제 컴포넌트·사용 흐름·심미성/통일성의 기대와
사람 확인을 대조한다. 모듈 통합은 공유 인터페이스·대표 시퀀스·초기 연결 검증 여부를 읽는다.
검증은 설계에서 기대·방법·입력/환경·관측/증거·한계를 어떻게 정했고 구현 계획이 이를 실행으로
이어갔는지 확인한다. 검증 방법의 이름이나 테스트 수만으로 충분하다고 판단하지 않는다.
원전 조사로 접근의 효과와 한계를 검토하되 모든 UI 완성·모든 내부 인터페이스 선행 확정을 강제하지 않는다.

### SP06 — 실제 경계에 닿는 설계와 첫 인도 (FR04–05)
0003의 PR-H 최초 마운트, 0004의 실엔진 연결 뒤 재결함, 0018/0027의 가상 consumer와 실제 앱 차이를
근거로 기존 지침의 적용 판단을 명료하게 한다. 현행 0.1.8에 계약·관측 규칙 자체가 없었다고 주장하지 않는다.
spec의 중요한 AC/설계에는 독립 기대와 검증 경계·입력/환경·관측·가상화 한계를 연결하고 plan에서 실행한다.
UI 탐색은 불확실성에 맞춰 실제 기존 컴포넌트/앱 셸·대표 상태를 사용하며 시각 기준과 사람의 피드백을
보존한다. 정적 시안을 금지하거나 모든 화면을 제품 수준으로 선구현하지 않는다.
큰 plan은 이번 인도의 공유 의미와 대표 실패 순서를 읽고 위험한 실제 경계를 통과하는 작은 경로를
먼저 배치한다. 필요한 인프라로 미뤄야 하면 가상 경계와 실제 연결 시점·남은 위험을 밝힌다.
새 양식 패키지를 복제하지 않고 spec 양식·기존 design-depth/execution-depth·탐색 예시에서 설명한다.

## Acceptance criteria
- AC01: 원격 모집단·별칭·관계·버전별 기준과 원본 해시가 보존된다.
- AC02: 모든 접근 가능한 개발건에 사건 보고서가 있으며 미검토·증거 부족의 영향을 드러낸다.
- AC03: 원인과 현행판 잔여 문제가 독립 검토되고 얇은 수정 또는 정당한 보류로 연결된다.
- AC04 (후속 유예): 별도 실험 지시 후 실제 모델·설치·대화·Git·시험·회귀 근거로 전후 결과와 한계를 보존한다. 현재 부분 실행은 효과 입증으로 계산하지 않는다.
- AC05: 원제품·전역 설정·기존 WIP·역사를 보존하고 확인한 범위만 북극성에 추가한다.
- AC06: PR/커밋 양식과 changes 색인이 기존 작업/수락/실행 기록을 복제하지 않고 연결한다. 기존 채택 프로젝트의 intent 경로는 호환 참조로 유지하며 자동 이사하지 않는다.
- AC07: 각 단위의 중요한 리뷰 지적을 해결하거나 범위·근거 있는 보류로 남기며, 최종 source·참조·Claude/Codex 전달본과 기존 회귀 검사를 확인한다. 이 판정은 실제 개발 효과나 사람의 수락을 대신하지 않는다.

### SP07 — 단위별 완료와 검토 (FR08, AC07)
기존 묶음 후보 ec47695/74e1148과 원본 보고서를 보존하고 새 수정으로 완료한다. 순서는 검증 설계,
UI 설계, 초기 통합 계획, 개발건/현재 정본, PR·커밋/문서 갱신, 패키지/전체 회귀다. 한 단위를 고친 뒤
새 문맥의 적대적 검토자가 실제 입력·해당 source·필수 참조를 읽고 발견을 보고한다. root가 지적의 의미와
근거를 판단해 최소 수정하고 필요한 재검토를 마친 뒤 다음 단위로 진행한다. 형식·어휘 취향과 모든 상태
선확정 요구는 통과 조건으로 삼지 않는다. 리뷰 기록은 연구 폴더에, 전문 출력/해시는 .local에 보존한다.
단위별 리뷰는 문서·스킬의 적용 가능성을 평가하는 제작 검토다. 제품 구현 실험·자연 스킬 선택·효과 검증으로 세지 않는다.

### SP05 — 전달 기록과 개발건 정본 (FR06–07)
상위 changes는 기능·결함·유지보수를 포함한 개발건이며 plan의 개별 T와 구분한다. 번호와 내부
intent.md/spec.md/plan.md는 유지한다. 신규 제품 배포의 활성 경로만 바꾸고 maker 이력과 기존
채택 프로젝트는 이전 경로를 보존할 수 있다. 총괄 README의 행은 plan/PR의 현재 판에 연결한다.
과거 spec은 당시 결정의 근거다. 최신 코드와 설정·현행 정책·현재 적용할 수락된 계약을 대조하고
보존/대체 범위와 미확인 차이를 이번 spec에 기록한다. 최신 번호나 최종 파일이라는 이유로 승계하지 않는다.
PR은 최종 diff의 목적·동작·설계/계획 범위·실제로 실행한 검증과 미완료를 전달한다. 커밋은
짧은 type: subject와 필요한 이유·영향 문서·검증 본문을 쓰며 무관한 WIP를 포함하지 않는다.
새 자동 검사기·승인 단계·검증 상태 장부를 추가하지 않는다.

## Flagged concerns
윈도우 로컬 기록은 현재 원격 접근만으로 확보되지 않는다. 필요한 사건을 특정한 뒤 보충하며
확보하지 못한 경우 순서·설치·모델·사람 결정의 원인을 미확인으로 남긴다.
역사 모델과 환경을 복제하지 못하는 실행은 역사 자체의 재현이라고 부르지 않는다.
