# PR 크기 가이드

PR은 하나의 목적과 영향 범위를 이해하고, 검증하며, 문제 발생 시 대응할 수 있는 단위로 구성한다.
작고 응집된 변경을 기본으로 하되 줄 수나 파일 수의 고정 상한을 두지 않는다. AI가 작성하거나
리뷰해도 이 원칙은 같다. AI의 검토 능력과 실제 검증 근거에 따라 더 큰 변경을 함께 다룰 수 있다.

## 나누거나 함께 두는 판단

- 독립적으로 수락·사용·되돌릴 수 있는 변경, 서로 다른 목적의 기능과 큰 리팩터링은 분리할 이점이 크면 나눈다.
  먼저 끝난 부분의 검증과 사용자 피드백을 전체 기능 완료까지 미루지 않는다.
- 한 동작의 구현·관련 시험·사용 설명은 함께 둘 수 있다. 줄 수를 맞추려고 시험만 떼어 내거나,
  불필요한 임시 코드와 복잡한 의존 브랜치를 만들지 않는다.
- 대량 삭제, 확인 가능한 기계적 치환, 한 계약을 일관되게 바꾸는 작업은 큰 PR이 합리적일 수 있다.
  생성 코드·lockfile·fixture와 직접 작성한 동작 변경을 구분해 읽을 범위를 설명한다.
  LLM이 생성했다는 사실만으로 기계적 변환이라고 보지 않는다.
- 같은 PR에 넣으면 Git 변경은 함께 통합되지만 배포·데이터 변경까지 동시에 일어나는 것은 아니다.
  스키마·API·호출부를 바꿀 때는 실제 실행 중인 이전 버전과의 호환성과 복구 방법도 확인한다.

## 검토 가능한 근거

계획이나 PR 설명에 목적과 포함 범위, 중요한 의존성, 실행한 검증과 미확인 사항을 남긴다.
크거나 여러 영역에 걸친 PR이면 함께 둔 이유와 읽을 순서, 위험한 동작과 복구 방법을 짧게 보탠다.
사람은 의도·위험·검증의 충분성을 판단하고, AI 리뷰는 그 판단을 돕는다. AI가 문제를 지적하지
않았다는 사실을 결함 없음이나 승인으로 바꾸지 않는다.

검토 중 서로 다른 결정이 섞여 있거나 검증 범위를 설명하기 어렵다면 분할을 다시 검토한다.
큰 변경을 여러 에이전트가 나눠 읽었어도 경계 사이의 상호작용과 통합 후 회귀를 확인한다.
작은 PR 여러 개로 나눴어도 이 확인을 생략하지 않는다.

## 예시와 조정

| 변경 | 판단 예 |
|---|---|
| 알림 음소거 설정 + 그 시험 + 사용법 | 하나의 동작으로 함께 검토 |
| 알림 기능과 별개인 저장 형식 교체 | 목적·위험·복구가 달라 분리 |
| 여러 파일의 동일한 이름 변경 | 동작 불변 근거가 있으면 큰 묶음 허용 |
| 장기간 걸리는 새 서비스 | 먼저 검증·사용할 수 있는 결과부터 나누어 통합 |

에이전트 작업 단위와 PR 단위는 일대일일 필요가 없다. 팀은 리뷰·수정에 든 시간과 비용,
통합 후 결함·재작업·복구 경험을 보고 경계를 조정한다. 이 가이드를 위한 별도 점수표나
줄 수 차단 검사는 요구하지 않는다. 브랜치와 수락 절차는 [GitHub Flow 정책](GIT-WORKFLOW.md)을 따른다.
