+# Spec: 청구 번호 형식 검사는 문자열 끝까지 본다 (from intent 0007-claim-id-trailing-newline)
+Upstream: intent.md@6f45eea7f3e9db423353985078cd90a769965c73. Status: draft.
+Skills applied: secure-api-review (② 입력 검증만 해당), design-spec.
+## Requirements
+- R1 청구 번호는 문자열 **처음부터 끝까지** `C-<숫자>` 일 때만 형식에 맞는다. 끝에 개행이 붙은 `"C-1001\n"` 은 형식 불일치이고 `invalid_claim_id` 다 (Problem: `$` 가 끝 개행 앞에서 맞았다).
+- R2 형식이 맞지 않는 번호는 상류 claims-core 를 부르지 않는다 — 상류 호출 0 (Problem: 실제 1 · spec 0002 AC4).
+- R3 오류 문구는 0002 의 고정 셋 그대로이고 입력 문자열을 되비추지 않는다. 응답 필드는 넓어지지 않는다 (Constraints).

+## Design
+`routes.py` 의 `CLAIM_ID_RE` 상수 한 줄만 바꾼다: `r"^C-[0-9]+$"` → `r"\AC-[0-9]+\Z"`. `$` 는 문자열 끝 **또는 끝 개행 앞**에서 맞고, `\Z` 는 문자열 끝에서만 맞는다. 호출부(`CLAIM_ID_RE.match(claim_id)`)와 판정 순서, 오류 문구는 손대지 않는다.
+`re.fullmatch` 로 바꾸는 선택지도 같은 결과를 낸다. 앵커를 고른 이유는 두 가지다: 바뀌는 줄이 상수 하나라 호출부의 판정 순서(세션 → 형식 → 상류)를 건드리지 않고, 나중에 누가 `fullmatch` 를 `match`/`search` 로 되돌려도 앵커가 문자열에 남아 있어 결함이 되살아나지 않는다.
+입력을 `strip()` 해서 받아 주지 않는다 — 그것은 형식 규칙을 넓히는 결정이지 결함 수정이 아니다(intent Constraints, 아래 F1).
+secure-api-review: ② 입력 검증 — 경로 인자 `claim_id` 는 `C-<숫자>` 전체 일치만 통과하고, 통과하지 못한 입력은 원장·캐시 어느 쪽에도 닿지 않는다. ①③④ 는 이 변경으로 달라지지 않는다(인증 경로·감사·데이터 분류 불변, 응답에 새 값 없음).
+## Constraints
+- intent: 기존 인증만 · 새 개인정보 없음 · 응답 필드 불변 · 남의 건과 없는 건은 같은 `not_found` · 오류 문구에 입력 되비춤 없음 · 형식 규칙 `C-<숫자>` 자체는 그대로 · `tests/test_claims_status.py`·`tests/test_claims_status_defect.py`·`tests/test_claims_status_incident.py` 무편집 · 범위 밖(이슈 #25 세션 형식, 이슈 #26 미스 캐시·상류 예산).
+- 발견: 형식 검사는 이미 세션 검사 **뒤**, 상류 조회 **앞**에 있다 — 순서를 옮길 이유가 없다. 옮기면 0002 AC2(세션 `None` → 상류 0)와 얽힌다.
