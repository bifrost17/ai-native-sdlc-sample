# 필요한 실행 상세와 문서 갱신

판단 기준의 정본은 [GitHub Flow](../../../../docs/GIT-WORKFLOW.md), [PR 크기](../../../../docs/PR-SIZE.md),
[공개 제어](../../../../docs/RELEASE-CONTROL.md)다. 아래는 정책을 대체하지 않고 이 변경의 답을
계획에 옮기는 형식과 예다. 활성 배치에서는 해당 프로젝트의 docs/ 세 정책을 연결한다.

## 인도 지도와 작업 상세

큰 변경은 먼저 어떤 결과를 어떤 PR로 main에 넣는지 보여준 뒤, 맡아서 실행할 작업의 정보를 모은다.
작업은 T01처럼 안정 ID를 쓰고 소속 PR과 구분한다. 설계 정본 경로+SP/AC에서 결정의 의미를 읽고,
실제 함수·인터페이스·설정의 어디를 어떤 방법으로 바꿀지 연결한다. 디렉터리 이름이나 AC 범위만으로
방법을 대신하지 않는다. 입력·선행 결과·검증·Done과 다음 작업에 넘길 결과를 같은 자리에서 찾게 한다.
한 작업에서 `필수 spec 계약 → 파일 → 먼저 확인할 동작 시험/예상 실패 → 최소 연결 → 통과 관측`을 읽을 수 있게 한다.
기준 시험·전체 명령은 PR 안에서 공유하고, Proof는 AC/회귀/통합의 색인으로 쓴다. 기대값 전문을 두 군데 유지하지 않는다.
작업별 예: [F03](../../../../docs/sdlc-authoring/examples/F03/plan.md), 여러 정본/병렬 입력: [M01](../../../../docs/sdlc-authoring/examples/M01/plan.md), 화면/API: [W01](../../../../docs/sdlc-authoring/examples/W01/plan.md).

작업 하나가 몇 줄이면 충분한 F01/B01은 블록 제목을 반복하지 않아도 된다. 파일 수·작업 수·줄 수로 형식을 강제하지 않는다.
큰 plan은 인도 지도를 plan.md에 두고 필요한 작업 상세를 연결할 수 있다. 필수 읽기·정본 판·영향 갱신 범위에 포함한다.
다음 작업 전에 필요한 결정을 밝히고, 미해소 뒤 단계까지 실행 준비가 끝났다고 표시하지 않는다.

여러 PR: `목적/포함 | 선행 | 머지 후 main·일반/시험 상태 | 남은 범위/Proof`를 작성한다.
파일 수나 LOC를 맞추기보다 하나의 검토 가능한 결과로 code/test/docs를 묶는다.
준비 PR도 기존 동작을 보존하며 독립 검증 가능해야 한다. 종속 PR은 선행 main 통합 후 시작하는 것이 기본.
stacked가 필요하면 실제 base/의존을 쓰고 선행 merge 후 base와 남은 diff를 다시 검증한다.
장기 기능 통합 브랜치·하나의 거대 PR을 큰 계획의 자동 결과로 만들지 않는다.

병렬: `작업 | branch/worktree | 소유 파일 | 공유 계약 판 | 통합/문서 조정자`.
실제 이름은 시작 시 정하되 경계·입력·책임은 계획에 남긴다. 같은 파일 작업은 순차 조정한다.
공유 계약 변화는 spec 집합과 영향을 조정한 뒤 관련 구현 커밋에 문서도 포함한다.
개별 테스트 GREEN 이후 최신 main과 합친 전체 계약·데이터·사용 흐름을 검증한다.

공개 분리: spec의 같은 제어를 재사용하고 PR별 상태·설정 위치/값·반영 시점·공개/중단·담당·제거 조건을
작업 순서/Proof에 채운다. 예시 [F03](../../../../docs/sdlc-authoring/examples/F03/plan.md)의 phase별 기대가 다름을 참고한다.
일반 OFF에서도 배포 가능·기존 동작 유지가 필요하다. 기능 공개는 merge와 별도 결정일 수 있다.

운영: 실제 중지/전환/복구/재개 명령과 데이터 보존·대조를 확인한다. 미확인 입력은 담당·해결 시점을 쓰고
그 입력에 의존하는 단계만 기다린다. 코드 통합만으로 데이터 전환·권한·운영 리허설 성공을 주장하지 않는다.

## 구현 전 인계 준비

기존 계획 수락에서 첫 인도가 무엇이며 어떤 설계를 어떤 코드 연결·방법·검증으로 완성할지 확인한다.
중요 설계는 담당 작업, 근거가 있는 보존 동작 또는 명시한 후속 인도로 빠짐없이 연결한다.
거꾸로 새 중요한 동작·구조가 설계 정본 또는 허가된 개정에 근거하는지도 확인한다.
추적 표를 늘리기보다 작업과 Proof를 읽고, 대화를 모르는 사람이 첫 결과·방법·남은 일을 설명할 수 있는지 본다.
가장 위험한 단계와 버린 주요 대안·선택 이유를 Risks에 남긴다. 실질 대안이 없으면 만들지 않는다.

큰 계획이나 중요한 개정은 가능하면 역량 있는 새 검토자가 실제 입력·계획·필수 참조로 발견을 보고하게 한다.
구현 전에는 없는 코드 diff나 실행 성공을 요구하지 않는다. 작은 계획은 작성자 점검과 기존 엔지니어 검토로
다룰 수 있다. 검토 범위·발견/해결·이월·준비 한계를 기존 기록에 남기고, 실제 수락은 기존 담당자가 한다.
새 승인 단계·고정 검토자 수를 만들거나 이미 받은 허가를 다시 묻지 않는다.

다음 설계/인도 결정을 가르는 미정에는 질문·고정 제약·구별할 관찰·폐기/편입 조건을 갖춘 제한 탐색을 둘 수 있다.
학습 결과와 제품 인도를 구분하고, 미결에 의존하는 작업은 준비 완료로 보지 않는다.
독립적인 코드 작업에 필요 없는 운영 입력은 담당과 실제 필요 시점까지 이월할 수 있다.

## 영향받는 정본을 같은 구현 커밋에서 갱신
| 발견 | 변경할 정본 | 유지할 것 |
|---|---|---|
| 테스트/모듈 경로·작업 순서·PR 범위·증명 방법 변화 | plan과 이유 | 의미가 같은 spec |
| API/출력/오류/스키마·중요 설계/공개 계약 변화 | spec의 해당 정본·AC와 영향 plan, 이유 | 관계없는 정본 |
| 기존 계약을 그대로 확인하는 사례 추가/명백한 fixture 오타 수정 | 시험·실행/PR 근거, plan의 증명이 실제 달라지면 plan | 형식적 spec 편집 없음 |
| 요구/범위 자체 변화 | 관련 intent/spec/plan 및 필요한 사람 결정 | 허가된 범위 밖 임의 결정 없음 |

코드 결함은 합의한 계약에 맞게 고친다. 허용된 내부 선택과 설계 개정을 구분하며, T→SP→요구/AC와
intent 제약을 따라 영향 정본을 찾는다. plan-only 변경도 다음 의존 작업 전에 plan을 고친다.
설계 개정이면 해당 정본과 영향 plan을 다음 의존 구현/검증 전에 갱신하고 관련 구현 커밋에 함께 담는다.
이미 받은 허가를 재사용하며 문서만 갱신하는 인계에 가짜 코드 변경을 만들지 않는다.

문서 하나당 별도 PR을 요구하지 않는다. 초기 문서의 입력 판·단계 수락 기록과 최종 PR 통합은 구별한다.
기존 plan이 spec@A를 참조하는 상황에서 한 구현 커밋에 spec과 plan을 고치면 그 미래 SHA를 쓸 수 없다.
이때 기존 Upstream A를 보존하고 바로 아래에 `Current change: 이 커밋의 spec.md 및 선언된 설계 정본 개정과
함께 읽는다. 변경 이유: ...; 결정 기록: ...`처럼 현재 변경을 명시한다. 커밋 후 다음 갱신/인계에서
확정된 실제 SHA를 참조할 수 있다. 존재하지 않는 해시나 “승인됨” 표기로 해결하지 않는다.
리뷰는 이전 수락 판과 현재 diff·현재 연결 정본을 함께 대조한다. 사람의 새 판단이 필요한 변화는 기존
피드백/수락 절차로 처리하며 이미 허가된 내부 선택을 매번 다시 승인받지 않는다.

## 남은 일과 현재 요약

하위 작업만 계속 완료되고 같은 인도가 열려 있거나 선행 조건이 거듭 늘면 남은 일을 원래 Done과 대조한다.
필요 계약은 유지하고 근거 없는 확장은 걷어낸다. 응집된 인도를 나누거나 미정 질문의 탐색 범위를 제한한다.
시간이나 helper 수만으로 계획이 틀렸다고 판정하지 않는다. 상태 질문만 받았다면 새 작업·검토를 시작하지 않는다.

재계획·중단·인계 때 plan의 현재 요약에 실제 코드판/브랜치와 미커밋 범위, 입력/근거 판, 완료·미검증,
지금 닫을 인도, 선행 조건·다음 T를 남긴다. 이전 다음 작업을 현재 지시로 방치하거나 새 장부에 복제하지 않는다.
전체 출력·이전 판단·작성자는 기존 실행 기록과 Git에 보존한다. 재개 시 이 요약·연결 근거와 실제 Git 상태를
대조하고 차이·미해결 계약을 판단한 뒤 의존 작업을 잇는다. 일부 시험 통과가 후속 인도까지 증명하지는 않는다.

이 방식의 [구체 갱신 예](../../../../docs/sdlc-authoring/change-walkthrough.md)는 문서 diff 설계이며 제품 실행 기록이 아니다.
