‹이 설계를 어떤 순서로 제품에 넣는지 짧게 설명한다. spec 진입점·필수 정본·현재 코드/시험 맥락을 직접 연결한다.›
‹현재 요약: 첫 인도 결과·실제 입력/근거 판·완료/미검증·선행 조건·다음 작업.
재계획/인계 때 이 요약을 현재 상태로 고치고 상세 출력·이력은 기존 실행 기록을 연결한다.›

## Order of work
‹[GitHub Flow](../docs/GIT-WORKFLOW.md)·[PR 크기](../docs/PR-SIZE.md)·
[공개 제어](../docs/RELEASE-CONTROL.md)를 따른다. 아래에는 이 변경의 구체적인 답을 쓴다.›

‹한 PR이면 목적·머지 후 동작·남은 범위를 짧게 쓴다. 여러 PR이면 아래 표와 PR별 작업을 쓴다.›
| PR 목적·포함 범위 | 선행/병렬 조건 | 머지 후 main·일반/시험 노출 | 남은 범위·Proof |
|---|---|---|---|
| ‹기능·시험·설명이 응집된 범위› | ‹필요한 계약/PR; 독립이면 소유 경로› | ‹기존 동작·실행 가능한 부분·공개 상태› | ‹다음 인도·증명 참조› |

‹작으면 아래 내용을 몇 단계로 합친다. 따로 실행/인계할 작업은 PR 아래 이런 블록으로 모은다.
Files/Proof는 색인이고, 한 작업의 판단을 위해 여러 표를 재조립하게 하지 않는다.
[추적 규칙](../docs/sdlc-authoring/traceability.md)에 따라 독립 작업 T와 PR·Proof 번호를 구분한다.›

### T01 — ‹맡아서 끝낼 결과›
**PR:** ‹소속 PR 목적/식별자. 한 PR에 여러 T 가능›.
**Design basis:** ‹설계 정본 경로+SP와 관련 AC. 구현할 결정의 의미·보존 경계›.
**Input:** ‹실제 코드판/선행 결과·필요한 계약 판. 병렬이면 소유 경로·공유 계약·조정자›.
**Files:** ‹실제 코드 연결점, 먼저 쓸 시험 파일/사례, 설명 파일. new 구분›.
**Method:** ‹확인한 함수/인터페이스/설정의 어디를 어떤 방식·책임·순서로 바꾸는가.
SP의 의미를 실제 흐름에 연결한다. 경로·AC 번호만 나열하지 않는다›.

1. **Baseline:** ‹실제 명령·현재 결과와 근거. 기준 확인은 PR 내 공유 가능›.
2. **First test:** ‹입력/행동과 기대›를 먼저 작성하고 `‹명령›`을 실행한다.
   예상 RED는 ‹현재 동작과 기대의 차이›다. 이미 GREEN인 인접 회귀는 보존한다.
3. **Change:** ‹최소 구현의 위치·연결 방법›으로 통과시킨다. ‹다음 행동 시험·필요한 정리/통합 순서›.
4. **Done:** `‹해당 시험 명령/관측›`으로 ‹완료 결과·보존 계약›을 확인한다. ‹Proof 참조›.
   ‹이 결과가 PR의 무엇을 충족하고 다음 작업에 무엇을 넘기는지. 아직 미검증인 후속 결과›.

‹PR 끝: 최신 main과 합친 결과를 검증 → 검토/머지 → 통합 main 확인. 머지 후 동작/일반·시험 노출과
남은 일은 위 지도와 연결한다. 공개/전환이 있으면 같은 제어·설정 위치·담당·실행/중단·검증·제거 조건을 쓴다.›

## Risks
‹첫 인도·설계별 작업/보존 근거·실제 경로와 방법·검증·Done을 구현 전 기존 계획 수락에서 점검한다.
가장 위험한 단계와 검토한 주요 대안·선택 이유를 남긴다. 실질 대안이 없으면 만들지 않는다.›
| 깨질 동작·가장 위험한 단계 | 어떻게 발견하는가 | 대응/중지 조건 |
|---|---|---|
| ‹실질 위험› | ‹Proof/관측› | ‹선택 이유·안전한 대응› |

## Proof
| ID·AC/보존 동작 | 시험/작업의 정본 | 추가 검증·기대/한계 |
|---|---|---|
| P1 ‹AC› | ‹위 작업의 선행 시험·명령·완료 관측 링크› | ‹그 시험이 증명하지 못하는 것› |
| P2 ‹인접/통합› | ‹기존 시험·전체 명령/관측 위치› | ‹결합/main·전체 공개 단위에서 확인할 결과› |

‹이는 예정 증명이다. 실제 명령·판·출력/실패 이유는 기존 실행/PR 기록에 남긴다.
하위 작업의 완료만 늘고 같은 인도가 열려 있으면 남은 일을 원래 Done과 대조해 다시 계획한다.
경로·순서·PR 경계·검증만 바뀌면 다음 의존 작업 전에 plan을 고치고 관련 구현 커밋에 포함한다.
계약/중요 설계가 바뀌면 spec의 해당 정본과 영향 plan도 같은 순서로 갱신한다. 결함이면 계약에 맞게 구현을 고친다.
현재 요약·다음 작업을 갱신하고 이력은 보존한다. 문서만 인계하는 수정에 가짜 코드 변경을 만들지 않는다.
상세 절차는 저장소 루트의 examples/skills/plan/references/execution-depth.md를 따른다. 영향 없는 문서는 유지한다.
작성 안내·불필요한 블록은 지운다. 모든 RGR/구현 코드 전문·작업당 PR/승인은 요구하지 않는다.›
