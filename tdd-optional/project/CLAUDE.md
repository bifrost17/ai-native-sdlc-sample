# 프로젝트 작업 지침

## Commands

제품의 빌드·테스트·린트·실행 명령은 아직 정하지 않았다. `PROJECT-POLICY.md`의 검증 항목을 확인하고,
작업에서 실제 도구를 정하면 명령과 성공 기준을 함께 갱신한다. 존재하지 않는 명령을 실행하라고 하거나
명령을 실행하지 않은 채 통과했다고 보고하지 않는다.

## Conventions

- 변경의 문제와 의도를 `intent/<NNNN>-<slug>/intent.md`, 요구·설계를 `spec.md`, 구현 계획을
  `plan.md`로 이어 기록한다. 기존 건을 이어갈지와 번호·이름은 [변경 기록 규칙](intent/README.md)을,
  단계와 역할은 `docs/PROCESS.md`를 따른다.
- 현재 변경은 실제 diff에서 시작해 plan의 해당 작업(T) → spec의 설계 단위(SP) → 요구·수용 기준과
  intent 제약 순서로 의미를 대조한다. 문서가 바뀌었는지만 보지 않는다. 기존 문서는 기존 ID나
  경로·절 참조를 유지할 수 있으며, 모든 항목에 새 ID를 붙이는 일은 요구하지 않는다.
- 후속 요청·리뷰·구현 중 발견으로 합의한 동작·범위·수용 기준이 달라지면 해당 spec과 plan을 읽고,
  영향받는 문서를 다음 의존 시험·구현 주기 전에 현재화한다. TDD를 선택하지 않은 작업도 같은 순서다.
  갱신은 관련 구현과 같은 커밋에 담으며, 대화나 README의 설명만으로 설계·계획 갱신을 대신하지 않는다.
- 브랜치는 [GitHub Flow](docs/GIT-WORKFLOW.md), 변경 묶음은 [PR 크기 가이드](docs/PR-SIZE.md)를 따른다.
  최신 제품 `main`에서 작업하며 계획의 일부를 여러 PR로 통합할 수 있다.
- 산문은 의도를 제시한 사람의 언어로 쓴다. 양식의 영문 절 제목과 `Status:` 표기는 유지한다.
- 단계 수락은 대상 커밋과 사람의 결정·근거를 기록한다. 문서마다 PR을 만들 필요는 없다.
  구현의 최종 통합은 검증과 사람의 검토를 거친 PR 머지다. 책임자와 기록 위치는 `PROJECT-POLICY.md`에 둔다.
  파일의 `Status: draft.`를 직접 승인 표시로 바꾸지 않는다.
- 사람이 다음 단계를 미리 진행하도록 명시했다면, 무엇을 누가 왜 허용했는지 문서와 PR에 적는다.
  그 지시는 승인 기록을 대신하지 않는다.
- 새·변경 동작은 PROJECT-POLICY.md와 [검증 방식 선택](docs/TESTING-STRATEGY.md)에 따라 작업별
  TDD / 동작별 구현 후 테스트 / 기존 테스트 활용 / 혼합을 선택한다. 방식·이유·독립 기대의 근거와
  구현/검증 순서는 plan에, 실제 결과는 기존 실행 기록에 남긴다. non-TDD 자체에 별도 승인을 요구하지 않는다.
- 탐색은 질문·제약·직접 관찰과 폐기/편입 조건을 정한 허용 범위에서 진행한다. 학습 결과를 제품 완료로
  보고하지 않는다. 제품에 채택할 동작은 관련 spec·plan과 필요한 회귀·통합 검증으로 연결한다.
- 구현이 계획에서 벗어나면 `plan.md`와 이유를 해당 구현과 같은 커밋에 담는다.
  요구·설계 변경은 `docs/GIT-WORKFLOW.md`의 개정 절차를 따른다. 기존 검증을 약화해 문제를 숨기지 않는다.

## Architecture

`templates/`는 문서 양식, `intent/`는 제품 변경의 기록이다. 정책의 적용 범위와 책임자는
`PROJECT-POLICY.md`에서 확인한다. 정책이 충돌하거나 필요한 값이 없으면 결정자와 함께 우려로 남긴다.
제품 구조와 기술 선택은 해당 변경의 요구·설계에서 정한다. 팀이 선택한 스킬이나 도구가 있으면
관련 작업에 활용할 수 있다.

중요한 사용자 동작이 미정이면 제안한 가정과 확인된 결정을 구분하고, 질문이나 리뷰로 확인한다.
합의한 내용은 다음 단계가 읽을 문서에 남긴다. 사소한 구현 선택은 합의한 범위 안에서 판단한다.

## Verification

완료를 보고하기 전에 작업에서 정한 검증을 실행한다. 명령, 결과, 관측한 동작, 미실행 항목과 이유를
구분해 남긴다. 기존 동작에 미치는 영향도 확인한다. 리뷰는 `REVIEW.md`를 따르며, 사람의 승인과
실행 결과를 별개의 근거로 다룬다.
최신 합의·spec·plan·실제 diff와 검증 근거가 서로 맞는지 확인한다. 필요한 문서 갱신이 빠졌으면
작업은 미완료다. 갱신 문서와 수락·구현 커밋을 결과에 연결하고, 남은 결정이나 Git 작업을 구분한다.
중단·인계·재개는 `docs/PROCESS.md`의 현재 plan 요약과 실제 Git·근거를 대조한다. 단순 상태 질문만으로
구현이나 문서 개정을 시작하지 않는다.
기대값은 요구·정책·독립 입력에서 확인한다. 구현 출력·자체 시험 통과·새 문맥의 검토라는 사실만으로
정답이 보장되지 않는다. 직접 관찰도 실제 확인한 범위를 밝히고, 중요한 회귀에는 적절한 검증을 유지한다.

## Things to avoid

사용자가 제공하지 않은 정책 값·계정·성능 수치·검증 결과를 지어내지 않는다. 읽지 않은 자료를
적용했다고 쓰지 않는다. 도구가 할 수 있다는 이유만으로 배포·승인·머지를 수행하지 않는다.
