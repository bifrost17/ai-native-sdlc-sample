# PROJECT-POLICY — 프로젝트에서 정할 내용
Owner: 미정. Status: draft.

이 문서는 팀의 실제 결정으로 채운다. 값이 없으면 미정과 결정자를, 적용하지 않으면 이유를 적는다.
이 양식의 빈칸은 정책이 존재하거나 승인됐다는 뜻이 아니다.

## 역할과 인계

| 항목 | 결정 |
|---|---|
| 프로젝트 이름과 범위 | 미정 |
| 의도를 제시하고 확인할 사람 | 미정 |
| 의도와 요구·설계를 승인할 제품 책임자 | 미정 |
| 계획을 검토하고 구현을 맡을 엔지니어 | 미정 |
| 제품 구현계획의 인계 기준 | [구체성 기준](docs/PROCESS.md#구현계획의-구체성)에 따라 작성 대화 없이 현재 착수 범위를 구현·검증해 PR로 인도할 수 있는지 확인 |
| 코드 검토와 통합 책임자 | 미정 |
| 정책·운영·배포의 결정자 | 미정 |
| 브랜치 전략과 통합 대상 | GitHub Flow · `main` — [정책](docs/GIT-WORKFLOW.md) |
| PR 본문·커밋 메시지 | [전달 정책](docs/CHANGE-DELIVERY.md)과 기본 PR 양식. 프로젝트가 바꾸면 실제 형식·이유를 기록 |
| 머지 방식 | merge commit. 변경하려면 승인 원본 SHA 보존·대응 방식을 함께 기록 |
| 단계 수락과 최종 통합 | 단계는 대상 SHA와 사람의 결정 기록, 구현은 검증·리뷰 후 PR 머지 |
| 단계 수락·검증 기록을 남길 위치 | 미정 — 보존하는 PR 또는 대화·결정 기록 |

## 적용할 정책

| 항목 | 값·출처·판·결정자 |
|---|---|
| 용어·이름·표기·시간대 | 미정 |
| 민감 데이터·사용 범위·로그·보존 기간 | 미정 |
| 사용자 범위·외부 전송·준수할 규정 | 미정 |
| 인증·권한·역할 경계 | 미정 |
| 외부 의존성·사용 한도·실패 시 동작 | 미정 |
| 스키마·접근성·사용성 등 제품에 적용할 기준 | 미정 |

팀이 선택한 스킬이나 도구가 있으면 적용 범위와 출처를 함께 기록할 수 있다. 이 템플릿은 특정
스킬이나 도구를 요구하지 않는다.

## 검증과 운영

| 항목 | 실제 명령·방법·성공 기준 |
|---|---|
| 제품 실행과 빌드 | 미정 |
| 테스트·린트·관련 동작 확인 | 미정 |
| 새·변경 동작의 개발 방식 | 작업별로 TDD / 동작별 구현 후 테스트 / 기존 테스트 활용 / 혼합 중 적합한 방식을 선택한다. plan의 Order 또는 작업 블록에 방식·이유·독립된 기대·구현/검증 순서를 적는다. non-TDD 선택 자체에 별도 예외 승인을 요구하지 않는다. |
| 방식과 무관한 검증 기준 | 수락한 spec/AC·독립 입력에서 기대를 정하고 실제 출력에 맞춰 기대를 만들지 않는다. 모든 AC와 영향받는 기존 동작을 검증하고 회귀 근거를 보존한다. 기존 시험만으로 부족한 새 동작은 검증을 보강한다. 명령·코드판·결과·미실행/한계는 정한 위치에 남긴다. |
| 선택한 방식의 적용 | TDD는 의미 있는 실패를 관측한 뒤 최소 구현·재검증한다. 구현 후 테스트는 작은 동작마다 구현과 검증을 끝낸 뒤 다음 동작으로 간다. 기존 테스트 활용은 관련 AC의 실제 커버리지를 대조한다. 혼합은 작업별 경계를 명시한다. 이미 만족한 동작에 RED를 꾸미거나 사후 시험을 TDD 이력으로 소급하지 않는다. |
| 결함 진단과 계획 변경 | 버그 수정은 증상을 먼저 재현하는 진단을 권장하며 수동·임시 스크립트·자동 시험을 구분한다. 재현의 제약은 기록하고 의미 있는 회귀 보호를 남긴다. 실제 테스트 보호가 적용될 때는 그 범위를 따른다. 선택 방식/검증이 바뀌면 이유와 plan을 관련 구현 커밋에 담고, 계약·권한 변경은 기존 수락 절차를 따른다. |
| 탐색·직접 관찰 | UI·기술 탐색은 질문·제약·관찰 방법과 폐기/제품 편입 조건을 정한다. 자동 시험·브라우저·수동 확인은 증명할 동작에 맞게 선택한다. 학습 목표의 달성과 제품 완료를 구분하며, 편입할 동작은 관련 spec·plan과 필요한 회귀·통합 검증으로 연결한다. |
| 검증 근거를 남길 위치 | 미정 |
| CI와 필요한 검사·검토 | 미정 |
| 배포·기능 공개 권한, 설정 위치, 수락·중단 기록과 되돌리는 방법 | 미정 — [공개 제어](docs/RELEASE-CONTROL.md), 적용할 때 실제 값과 결정자를 기록 |
| 운영 지표·이상 징후·대응과 인계 | 미정 |

[검증 방식 선택 가이드](docs/TESTING-STRATEGY.md)로 plan의 판단을 구체화한다. 테스트 작성 순서와
검증 수단은 구분한다. 기존 기준을 읽고 영향을 확인하는 것은 모든 방식에 필요하지만, 새 자동 시험·
별도 에이전트·전체 검사 체계를 모든 작은 변경에 일괄 추가하지 않는다. 중요한 판단 근거와 실제 결과를
남기며, 팀이 선택한 독립 검토와 보호 통제는 그 적용 범위를 따른다.
플레이북의 버그 test-first·시험 동결 처방을 선택형에서 조정한 범위는
[가이드의 플레이북 적용 설명](docs/TESTING-STRATEGY.md#플레이북을-적용하는-범위)에 명시한다.
