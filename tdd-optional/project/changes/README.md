# 제품 개발건

새로 배포해 시작하는 제품은 기능·결함·유지보수 개발건을 `changes/<NNNN>-<slug>/`에 기록한다.
상위 개발건은 [plan 양식](../templates/plan.md)의 개별 작업(T)과 다르다. 한 개발건을 여러 작업·PR로
나눌 수 있다. 폴더 안의 `intent.md`, `spec.md`, `plan.md` 이름은 유지한다.
이미 `intent/<NNNN>-<slug>/`를 채택한 제품은 그 경로를 유지하며 새 규칙 때문에 이사할 필요가 없다.
그 제품의 후속 건도 실제 채택한 경로·참조를 먼저 확인한다.

## 현재 개발건

이 템플릿에는 실제 제품 개발건이 없다. 제품에서 개발건을 만들거나 중요한 범위를 바꾸거나 PR을
통합하거나 중단·인계할 때, 아래 표의 관련 행을 현재 기록에 맞춰 갱신한다. 각 행은 현재 plan과
대상 코드 판·관련 PR, 남은 범위와 다음 작업을 찾는 **색인**이다. 상세 시험 출력·과거 결정은
plan·PR·보존된 실행 기록을 연결하고 여기 복제하지 않는다.

| 개발건·목적 | 현재 상태 | 현재 plan 링크·대상 코드 판·PR 링크 | 남은 범위·다음 작업 |
|---|---|---|---|

상태는 `계획 중`, `진행 중`, `중단`, `부분 인도`, `완료`처럼 **확인된 사실**을 짧게 쓴다.
이는 필수 상태 목록이나 별도 승인 단계가 아니다. 일부 PR이 머지됐어도 합의한 전체 범위가
남았다면 완료로 적지 않는다. 완료는 전체 합의 범위의 실제 결과와 수락 근거를 확인해 기록한다.

## 폴더 배치

아래는 **경로 예시**이며 실제 개발건·수락 기록이 아니다.

```text
changes/
  README.md
  0001-request-export/
    intent.md
    spec.md
    plan.md
    design/                 # 필요한 상세 설계만; spec.md에서 연결
      api.md
  0002-fix-export-encoding/
    intent.md
    spec.md
    plan.md
```

문서는 [개발 절차](../docs/PROCESS.md)에 따라 단계별로 만든다. [templates/](../templates/)는 빈 양식이다.
spec.md는 설계의 진입점이며 필요한 상세 문서를 연결한다. 매 개발건에 design/이나 모든 파일을 미리 만들 필요는 없다.

## 번호와 이름

- `NNNN`은 제품 저장소 안의 개발건 번호다. 0001부터 시작해 최소 네 자리로 0을 채운다.
  현재 main과 알려진 진행 중 작업의 `changes/` 및 유지 중인 `intent/` 경로에서 쓰인 가장 큰 번호 다음을 사용한다.
  기존 번호를 유지하며 GitHub 이슈·PR 번호와 구별한다.
  번호를 재사용하지 않으며 병렬로 시작할 때는 작업을 조율하는 사람이 중복을 피하도록 배정한다.
  그래도 겹치면 이미 통합된 번호를 유지하고 나머지 건의 번호와 참조를 통합 전에 조정한다.
- `slug`는 목적을 짧게 나타내며 영문 소문자·숫자로 된 단어를 하이픈으로 연결한다. 예: `request-export`,
  `fix-export-encoding`, `upgrade-sqlite`. 기능·버그·유지보수에 같은 번호 체계를 쓰며 종류별 폴더나 접두사는 필수가 아니다.
- 문서의 `# Intent:` 제목과 본문은 요청자의 언어로 쓴다. 예: “CSV 내보내기에서 한글이 깨지는 문제 수정”.
  사용자가 자연어로 요청하면 에이전트가 기존 건과 범위를 확인해 번호·이름을 정하고 작업 안내에 경로를 밝힌다.
  이름을 정하려고 이미 합의한 요청을 다시 승인받지 않는다.
- 한번 공유한 폴더 경로는 가급적 유지한다. 범위가 조금 바뀌었다고 번호나 이름을 바꾸지 않는다.
  경로 변경이 필요하면 관련 링크·참조도 함께 고치고 이전 판은 Git 이력에 보존한다.

## 기존 개발건을 이어갈지 새로 만들지

대화 메시지·세션·브랜치·PR 하나가 개발건 하나라는 뜻은 아니다. **독립된 목표와 완료 범위**로 구분한다.
서로 독립적으로 수락·완료할 목표라면 같은 요청이어도 개발건을 나눈다. 여러 대화는 같은 개발건으로 이어질 수 있다.

| 요청 상황 | 기록할 위치 |
|---|---|
| 진행 중인 같은 목표의 구체화, 리뷰 수정, 구현 중 발견한 결함·계획 변경 | 기존 폴더의 영향받는 문서를 갱신한다. |
| 큰 개발건을 여러 작업·PR·에이전트로 나눠 실행 | 같은 폴더의 plan에 작업·의존성·PR 범위를 나눈다. 일부 PR 머지만으로 새 번호를 만들지 않는다. |
| 진행 중인 건과 별도로 수락·완료할 독립된 목표 | 새 번호의 폴더를 만들고 필요한 선행 관계를 연결한다. |
| 완료한 기능에 대한 추가 개발, 새로 접수한 결함·별도 유지보수 | 새 번호의 폴더에서 변경 이유·이번 범위와 이전 기능의 기준을 연결한다. |
| 같은 건의 상태 질문·설명 요청 | 새 폴더를 만들지 않는다. 답변 중 새 결정이 생기면 영향받는 문서에 반영한다. |
| 동작·설계·검증 계획을 바꾸지 않는 오탈자·링크 정리 | 해당 문서를 고치고 PR에 목적·확인 결과를 남긴다. 문서 세트를 새로 복제하지 않는다. |

“완료”는 그 개발건의 합의된 전체 범위에 대한 실제 완료·수락 기록으로 판단한다. 마지막 PR 번호,
`Status: draft.`나 단순 시험 통과만으로 판단하지 않는다. 재개한 미완료 작업은 기존 폴더를 이어 쓴다.
같은 기능이라는 이유만으로 앞으로의 모든 요구를 첫 폴더에 계속 붙이지 않는다.

## 후속 개발과 이전 설계 연결

새 intent의 Problem이나 Affected users and systems에 관련 개발건·이슈와 이번 변경 이유를 연결한다.
완료된 개발건의 당시 변경·결정 기록을 새 개발건의 진행 상태로 덮어쓰지 않는다.
새 spec을 쓸 때 과거 spec은 **당시 결정의 근거**로 읽는다. 그 문서의 번호가 크거나 당시 수락됐다는
이유만으로 현재 적용할 계약으로 승계하지 않는다. 현재 코드·설정, 현행 정책, 현재 적용할 수락된 계약을
대조한다. 새 spec에 이전 계약의 문서 경로·관련 절·기준 판과 보존·대체할 범위, 확인하지 못한 차이를 적는다.
예를 들어 0002는 0001의 CSV 계약을 참조하면서 인코딩 수정과 유지할 열·순서를 명시할 수 있다.
앞선 설계 전체를 복제하지 않아도 되지만, 새 spec과 선언된 참조만으로 이번 계약을 이해할 수 있어야 한다.
새 plan은 그 spec을 기준으로 실제 변경 파일·작업·검증과 이전 기능의 회귀를 연결한다.

현재도 사용하는 공통 설계 정본이 있으면 그것을 확인하고, 영향받는 파일은 함께 갱신해 새 spec에서 연결한다.
과거 기록을 보존한다는 이유로 현재 적용할 계약을 낡은 상태로 두지 않는다. 이전 수락 판과 근거는 Git에 보존하며,
같은 결정의 정본이 둘이 되지 않도록 새 spec에 대체하는 범위를 밝힌다. 번호가 더 크다는 사실만으로 계약을 덮어쓰지 않는다.
[GitHub Flow의 문서 개정 절차](../docs/GIT-WORKFLOW.md)를 따른다.

PR에도 개발건 폴더와 계획의 해당 범위를 적는다. 다른 건의 수락을 이번 변경의 수락으로 사용하지 않는다.
제품 개발과 전체 절차 실험은 각자의 통합 대상과 출발 커밋을 명시한다.
이 번호·폴더명과 총괄 표는 템플릿이 선택한 팀 규칙이며 별도 등록 도구나 이름 검사기를 요구하지 않는다.
