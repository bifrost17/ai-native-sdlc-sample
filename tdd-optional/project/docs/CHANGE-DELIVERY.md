# PR 본문과 커밋 메시지

PR과 커밋은 다음 담당자가 변경 목적·실제 범위·검증 한계를 이해할 수 있게 쓴다. 이 형식은 팀의
기본 정책이며 북극성이 정한 양식은 아니다. 산문은 요청자의 언어로 쓴다. 원문 출력은 기존 실행
기록에 두고 링크한다. 문서·코드가 같은 커밋에 있다는 사실만으로 작성 순서나 시험 성공을 증명하지 않는다.

## PR 본문

[기본 양식](../.github/pull_request_template.md)의 네 부분을 이번 diff에 맞춰 채운다.

- 목적과 결과: 사용자가 겪던 문제와 이제 가능한 동작. 의미 있는 before/after를 짧게 적는다.
- 범위와 설계: 개발건 폴더·plan의 이번 작업/인도와 관련 spec 정본, 실제 base·의존 PR을 연결한다.
  계약/계획이 바뀌면 무엇을 왜 개정했는지, 유지할 동작과 제외 범위를 필요한 만큼 적는다.
- 검증: 실제 대상 코드판(커밋 또는 기반 SHA+미커밋 범위), 방법·기대/관측 결과와 근거를 연결한다.
  미실행·실패·가상 환경의 한계를 밝힌다. 이전 PR의 통과나 수정 전 실행을 최신 결과로 쓰지 않는다.
- 남은 일과 인계: 이번 PR 후 남는 범위·위험·다음 작업. 배포/공개/사람의 수락이 별도라면 구분한다.

없는 의존성이나 위험을 만들어 칸을 채우지 않는다. 작은 오탈자 수정은 목적·변경과 확인 결과만으로
충분하다. 큰 설계와 시험 전문을 본문에 복제하지 않는다. 리뷰로 diff·동작·근거·남은 일이 바뀌면
본문도 최종 제출판에 맞춘다. 이전 실패와 사람의 결정은 Git·댓글·실행 기록에 보존한다.
PR 생성·검사 통과·에이전트 리뷰는 통합 승인이나 개발건 전체 완료와 같지 않다.

## 커밋 메시지

일반 작업 커밋 제목은 `type(scope): 변경 결과`로 쓴다. scope는 도움이 될 때만 사용한다.
type은 `feat`, `fix`, `docs`, `refactor`, `test`, `perf`, `build`, `ci`, `chore`, `revert` 중
변경 목적에 맞게 고른다. 예: `fix(settings): 저장 거절 후 입력과 재시도 동작을 유지한다`.
중요 호환성 파괴는 `!` 또는 `BREAKING CHANGE:`와 영향·이행 방법으로 명시한다.

의미 있는 동작·설계·계획 변경은 제목 다음 빈 줄 뒤에 이유, 관련 개발건/설계·작업, 실제 검증 또는
미실행 사유를 짧게 남긴다. 중요한 제한·데이터 전환/복구 영향이 있으면 함께 적는다. 관련 spec/plan
개정은 구현과 함께 담고 변경 이유를 연결한다. 모든 ID나 시험 출력을 복제할 필요는 없다.

```text
fix(settings): 저장 거절 후 다시 시도할 수 있게 한다

실패 뒤 남던 제출 잠금을 해제한다. 저장 성공 계약은 유지한다.
근거: changes/0002-settings-retry/plan.md T02와 spec.md SP01.
검증: <실제 실행 방법·결과·대상판 또는 보존 기록 링크>.
미확인: <있다면 남은 범위와 이유>.
```

예시는 형식 설명이며 실제 개발 결과가 아니다. 작은 오탈자는 제목만으로 목적과 변경이 충분하면
본문을 생략할 수 있다. Git/GitHub가 만든 merge/revert 형식은 허용하고, revert에는 대상·이유·
후속 영향을 남긴다. 과거 커밋을 이 형식에 맞추려고 재작성하지 않는다. 메시지 형식을 위해 commitlint·새 hook·
고정 글자 수·자동 버전 배포는 추가하지 않는다. staged 범위와 문서 정합성은 기존 Git 정책을 따른다.

팀이 선택한 문서 동기화 hook은 메시지 형식 검사와 별개다. 기존 세션의 문서 영향 판단과 실제 staged
범위/필수 동반 개정의 포함을 연결하며, 내용 정확성이나 검토 수행을 인증하지 않는다. 이미 채택했다면
현재 설치 안내에 따라 커밋 한 번의 확인 신호를 전달한다. hook 통과를 수락·통합·완료로 쓰지 않는다.
