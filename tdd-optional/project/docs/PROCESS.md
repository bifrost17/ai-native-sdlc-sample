# 제품 변경의 절차

새 개발건은 `changes/<NNNN>-<slug>/`에서 의도, 요구·설계, 구현 계획을 이어 간다. 기존 채택 제품의
`intent/` 경로는 유지할 수 있다. 문서는 각 단계의
책임자가 읽고 결정할 수 있도록 작성한다. 문서 형식과 승인 상태를 판정하는 자동 검사는 이 템플릿에
포함하지 않는다. 실제 코드와 동작의 검증 방법은 프로젝트가 정한다.

착수할 때 실제 채택한 색인·규칙으로 기존 개발건과 이번 목표를 확인한다. 새 템플릿의 기본은
[개발건 규칙](../changes/README.md)이며, 기존 `intent/` 제품은 기존 색인·경로를 사용한다.
색인이 없으면 현재 개발건·plan과 프로젝트 규칙을 먼저 확인한다. 경로 이사나 두 번째 색인을 요구하지 않는다.
진행 중인 같은 목표의 수정은 기존 문서를 갱신하고, 독립된 후속 개발·유지보수는 새 개발건으로 연결한다.
폴더 이름을 정하거나 PR을 나누는 일은 별도의 승인 단계가 아니다.

## 역할과 승인

의도를 제시한 사람은 문제와 기대 결과를 확인한다. 제품 책임자는 의도와 요구·설계를 검토한다.
엔지니어는 계획을 검토하고 구현·검증을 수행한다. 정책 충돌과 운영 결정은 해당 책임자가 판단한다.
역할을 맡은 사람과 기록 위치는 [PROJECT-POLICY.md](../PROJECT-POLICY.md)에 적는다.
브랜치·PR·통합은 [GitHub Flow 정책](GIT-WORKFLOW.md)을 따른다.

문서는 단계별 변경으로 커밋하고 담당 사람이 다음 단계에서 사용할 판을 수락한다. 대상 문서와
커밋 SHA·결정자·결정과 이유를 같은 Draft PR 또는 보존하는 대화·결정 기록에 남긴다.
문서마다 별도 PR을 만들 필요는 없다. 단계 수락과 구현 PR의 최종 통합은 구분하며,
최종 통합은 검증과 사람의 리뷰를 거친 PR 머지로 한다.
파일의 `Status: draft.`는 그대로 둔다.
초안에서 다음 단계를 시작하라는 명시적 지시가 있으면 지시자·범위·이유를 문서와 PR에 남긴다.
상위 저장소의 기본 브랜치 이름이나 파일의 상태 문자열만 보고 승인됐다고 추정하지 않는다.

## 단계별 인계

| 단계 | 입력과 할 일 | 산출·검토 |
|---|---|---|
| 의도 | 제안자와 문제, 사용자, 범위, 제약, 성공의 의미를 확인한다. 관측과 추정을 구분한다. | [intent 양식](../templates/intent.md). 제안자가 사실을 확인하고 제품 책임자가 검토한다. |
| 요구·설계 | 승인된 의도에서 관측 가능한 요구와 설계를 만든다. 현재 코드·설정·정책·적용할 수락 계약을 대조하고, 과거 spec의 보존·대체·미확인 범위를 적는다. | [spec 양식](../templates/spec.md). [리뷰 지침](../REVIEW.md)의 설계 정합성·충분성을 확인하고 우려와 결정자를 드러내어 제품 책임자에게 넘긴다. |
| 구현 계획 | 승인된 요구·설계에서 첫 인도 결과와 실제 구현 방법, 변경 파일, 작업 순서·선행 관계, 위험·대안, 검증·인계 근거를 정한다. [선택 가이드](TESTING-STRATEGY.md)로 방식·이유·기대의 출처와 실제 검증 순서를 구체화한다. | [plan 양식](../templates/plan.md). 현재 설계 정본과 사용할 판을 입력으로 다음 담당자가 첫 작업을 실행할 수 있는지 검토한다. 아직 없는 코드·시험은 요구하지 않으며 사람의 계획 수락은 별도로 기록한다. |
| 구현·검증 | 작업별로 선택한 방식에 따라 구현·검증한다. 결함은 수정 전 증상 재현을 권장하며 수동·임시 스크립트·자동 시험을 구분한다. 자동 시험 선작성을 모든 결함에 강제하지 않지만 해당 동작과 인접 동작의 회귀 근거는 남긴다. 이탈한 계획과 이유는 해당 구현과 같은 커밋에 담는다. | 코드 변경, 필요한 설계·계획 개정과 실행 근거. [리뷰 지침](../REVIEW.md)에 따라 검토한다. |
| 통합·운영 | 검토 결과를 처리하고 정해진 권한과 절차로 통합·배포한다. 운영 중 발견한 문제는 근거와 함께 다시 의도로 넘긴다. | 사람의 결정, 실행 결과, 미결 사항과 인계 대상. |

각 인계에서 확인할 내용은 “무엇이 달라졌는가, 어떤 근거가 있는가, 무엇이 미결이며 누가 결정하는가”다.
사용자 동작에 중요한 가정은 확인된 사실과 구분한다. 질문이나 리뷰에서 결정이 나면 해당 문서에
반영해 다음 단계가 대화를 추측하지 않도록 한다. 이미 합의한 결정을 다시 허가받을 필요는 없다.
중요한 후속 요구·설계 선택을 편입하기 전에 출처와 이유, 중요한 사실 전제, 현재 의도의 목적·제약에
미치는 영향을 대조한다. 제안·가정·채택 결정·관측을 구분하고, 위임 범위에서 명확한 선택은 진행한다.
중요한 충돌이나 전제 반증, 큰 재작업을 만드는 이유 불명은 구체 영향을 설명하고 빠진 결정만 묻는다.
같은 판의 현재 의도와 결정을 이미 확인했다면 그 문맥을 재사용한다. 중요한 선택의 이유와 의도 연결은
관련 spec에 남기고 영향받는 plan을 맞춘다. 실제 목적·제약·핵심 배경이 바뀌거나 잘못 기록됐다면
intent의 해당 산문부터 개정한다. 의도가 유지되는 변경에는 형식적인 intent 편집을 요구하지 않는다.
작은 선택이 누적되어 대상·성공의 의미·비용에 중요한 영향을 주면 기존 설계 인계에서 묶어 의도와 다시 대조한다.
정책이 충돌하면 양쪽 출처와 내용을 기록하고 임의로 한쪽을 승인하지 않는다. 적용할 자료를 확인할 수
없다면 확인하지 못한 범위와 이유를 적는다. 팀이 보유한 스킬과 도구는 필요한 작업에 선택해서 활용할 수 있다.

중단·인계할 때는 별도 상세 장부를 만들지 않고 현재 plan의 요약과 기존 실행 기록에 실제 대상 revision,
완료한 일과 미검증 범위, 남은 작업·의존성·다음 한 단계를 갱신한다. 재개할 때 그 내용과 현재 문서,
Git의 staged·unstaged·untracked 상태, 실행 근거를 대조한 뒤 의존 작업을 잇는다. 충돌하거나 빠진 결정은
드러내고 영향받는 후속 작업을 준비 완료로 단정하지 않는다. 강제 종료를 막았다고 주장하지 않으며,
단순 상태 질문은 이 개정·실행 사건을 시작하지 않는다.
개발건의 현재 상태·대상 판·다음 작업은 실제 채택한 색인의 관련 행에도 연결하되 plan과 시험 출력을
복제하지 않는다. 새 템플릿에서는 [총괄 표](../changes/README.md#현재-개발건)를 사용한다.

## 구현계획의 구체성

제품 구현 계획은 작성 대화를 보지 못한 담당자가 plan과 명시된 spec·설계 정본, 기존 코드를 읽고 현재 착수 범위를
구현·검증하여 해당 PR로 인도할 수 있어야 한다. 중요한 설계 결정을 추측하거나 다시 정하게 두지 않는다.
각 작업은 구현할 설계의 의미를 실제 파일·주요 변경 지점과 연결하고, 재사용·처리 방법과 보존 조건을
설명한다. 선행 입력·담당 범위·다음 작업에 넘길 결과, 독립된 기대와 검증 방법·완료 조건도 드러낸다.
파일 목록이나 spec 링크를 나열하는 것으로 구현 방법을 대신하지 않는다.

공유 인터페이스, 객체의 책임·수명, 상태 소유권·경합·트랜잭션처럼 다른 작업과 결과에 영향을 주는
설계는 spec의 해당 정본에서 결정하고 plan에서 연결한다. 모든 클래스·내부 메서드나 UML을 미리
확정할 필요는 없다. 중요한 계약과 다른 작업에 영향을 주지 않는 내부 분해는 구현 중 정할 수 있다.
판단 기준은 클래스 수나 분량이 아니라 구현에 필요한 결정의 충분성이다.

큰 변경은 전체 범위·주요 의존성·예정 PR 경계를 정한 뒤 착수할 작업부터 상세화할 수 있다.
후속 작업도 착수 전에는 같은 수준으로 구현 방법·검증·완료 조건을 구체화한다.
후속 작업의 미확인 사항에는 확인 방법, 영향을 받는 결정과 해결할 시점을 남긴다. 현재 작업에 필요한
공유 계약과 선행 결정을 후속 상세화로 미루지 않으며, 미결 사항의 영향을 받는 범위를 준비 완료로
표시하지 않는다. 작은 변경은 필요한 결정과 참조가 명확하면 짧게 쓴다. 계획의 중요한 가정·대안·위험은
기존 계획 검토에서 확인하며, 별도 승인 단계나 문서 형식 검사기를 추가하지 않는다.
별도로 허용된 탐색은 아래 “작업 크기에 맞추기”의 학습·폐기/편입 기준을 따른다.

## 검증 근거

검증은 실제 프로젝트에서 정한 명령과 관측 방법으로 한다. 실행한 명령·대상 판·결과·관측한 동작을
기록하고, 실행하지 못한 항목은 이유와 함께 분리한다. 테스트 실패를 숨기려고 기준을 완화하지 않는다.
독립 검토를 맡겼다면 검토 범위와 결과도 남긴다. 사람이 문서를 승인한 사실은 제품 동작을 검증한
사실을 대신하지 않으며, 검사 통과도 사람의 승인을 대신하지 않는다.
새 문맥의 검토도 같은 잘못된 요구 해석을 공유할 수 있다. 기대의 출처와 중요한 가정을 확인하고
관련 spec·plan·현재 diff·실제 결과를 대조한다. [검증 방식 선택](TESTING-STRATEGY.md)에서
자동 시험·기존 시험·브라우저·직접 관찰의 역할과 한계를 구분한다.

필요한 도구·자동화·CI·배포 환경이 없으면 필요한 자리와 담당자를 프로젝트 정책에 기록한다.
실행되지 않은 단계는 완료됐다고 보고하지 않는다.

## 작업 크기에 맞추기

범위가 불명확하면 필요한 조사로 이번 결과와 완료 기준을 먼저 정한다. UI·기술 탐색에 코드가 필요하면
허용된 질문·제약·관찰 방법·폐기/편입 조건 안에서 작은 시도를 한다. 이는 초기 계획 작성 중 제품 구현을
시작하는 것과 구분한다. 탐색으로 배운 내용은 관련 설계에 반영하고, 편입할 동작은 기존 수락과 제품
검증으로 연결한다. 폐기할 실험에 출시용 전체 절차를 요구하거나, 학습 성공을 제품 완료로 보고하지 않는다.

큰 변경은 계획에서
독립 작업·선행 관계·예정 PR 범위·통합 순서를 정한다. [PR 크기 가이드](PR-SIZE.md)에 따라
작업과 PR을 유연하게 묶고, 각 PR이 전체 계획의 어느 부분을 완료했는지 밝힌다.

작은 변경의 문서는 짧아도 된다. 중요한 결정·위험·검증·인계가 이해되면 충분하며, 모든 가이드를
기계적으로 재현하려 문서나 검사를 늘리지 않는다. 계획에는 핵심 변경과 검증을 실행할 수 있는
결정과 참조를 남기고, 이탈한 계획은 이유와 함께 해당 구현과 같은 커밋에 반영한다. 요구·설계 개정은
[GitHub Flow 정책](GIT-WORKFLOW.md)을 따른다. 팀의 스킬은 현재 단계에
적절한 것만 선택하고, 실제로 참고한 내용이 판단에 어떻게 쓰였는지 설명할 수 있으면 된다.
