# 검증 방식 선택과 실행

이 선택형은 **합의한 동작과 판정 근거를 먼저 정하고, 테스트 작성 순서는 작업에 맞게 선택**한다.
의도·요구·설계·계획·리뷰·운영의 흐름은 [PROCESS](PROCESS.md), 실제 역할과 도구는
[PROJECT-POLICY](../PROJECT-POLICY.md)를 따른다. 이 가이드는 plan의 판단을 돕는 자료이며
새 승인 단계나 작업마다 채울 별도 양식을 추가하지 않는다.

## 먼저 정할 것

- **바꿀 것과 보존할 것:** spec의 관련 요구·AC, 외부에서 관찰할 결과와 중요한 실패·금지 동작을 읽는다.
  기대 결과의 근거는 사람의 요구·정책·프로토콜·확인된 기준 데이터·독립 계산 등에서 가져온다.
  현재 코드의 출력은 관측한 사실이다. 그것만으로 새 요구사항의 정답을 결정하지 않는다.
- **아직 모르는 것:** 중요한 업무 동작이나 권한이 미정이면 결정자에게 확인한다. 조사가 필요한
  기술·UI 문제는 허용된 범위에서 짧게 탐색하고, 그 결과를 제품 설계로 채택할 때 관련 spec을 갱신한다.
- **확인할 수단:** 관련 기존 시험, 실행·빌드 명령, 실제 경계나 화면을 확인할 방법과 제약을 찾는다.
  검사 이름·커버리지 비율·통과 표시만 보지 말고 어떤 AC와 보존 동작을 판별하는지 확인한다.

이는 모든 세부 테스트 코드를 미리 작성하거나 모든 예제를 동결한다는 뜻이 아니다. 사전 기대도
잘못될 수 있다. 근거가 틀렸거나 요구가 바뀌면 영향받는 계약과 검증을 함께 고친다.

## 어떤 방식을 선택하는가

엔지니어와 에이전트는 이미 허용된 작업 범위에서 방식과 이유를 정해 plan의 Order 또는 작업 블록에
남긴다. 사용자가 방식을 지정했으면 그 범위에 적용한다. 지정하지 않았다면 현재 계약·불확실성·
기존 시험·실패 영향으로 판단한다. non-TDD를 선택했다는 사실만으로 추가 승인을 요청하지 않는다.
중요한 업무·정책 결정이 필요한 경우에는 기존 결정 절차를 따른다.

| 현재 작업의 조건 | 고려할 방식과 이유 | 여전히 확인할 것 |
|---|---|---|
| 작게 재현되는 버그, 명확한 계산·경계 계약 | TDD로 실패를 먼저 확인하면 고칠 동작이 선명해진다. 구현 후 검증을 선택할 수도 있다. | 재현이 가리키는 실제 원인, 독립된 기대와 인접 회귀 |
| 명세가 안정된 신규 동작, 직접 실행하며 구현하기 쉬운 연결 | TDD 또는 동작별 구현 후 테스트. 작은 동작을 확인한 뒤 다음 변경으로 진행한다. | 정상·경계·오류와 실제 외부 연결. 구현 출력을 정답으로 복사하지 않음 |
| 동작 보존 리팩터링 | 관련 기존 테스트를 먼저 확인하고 활용한다. 빈 관찰 지점에는 특성화·회귀 검사를 보강한다. | 보존할 현재 동작과 알려진 결함을 구분. 의미 없는 새 시험이나 인위적인 RED 불필요 |
| 배치·상호작용·기술 가능성이 미정인 UI나 spike | 질문과 제약을 정해 구현·브라우저 관찰을 짧게 반복한다. 이는 불확실성을 줄이는 작업이다. | 관찰한 것·남은 결정·폐기할 것. 채택할 동작의 AC와 필요한 회귀 검증 |
| 권한·민감 데이터·이행·복구처럼 실패 영향이 큰 변경 | 핵심 경계의 TDD를 고려하거나, 독립 기준을 갖춘 구현 후 검증·혼합을 선택한다. | 권한 행렬·불변 조건·부분 실패·복구를 실제 통합 경계에서 확인. 순서만으로 안전성을 판단하지 않음 |
| 서버 계약은 명확하지만 UI는 탐색 중인 변경 | 혼합. 작업별 방식과 연결 계약을 밝힌다. | 각각의 통과뿐 아니라 사용자 흐름 전체와 통합 판 |

이 표는 선택을 돕는 판단 예시다. 작업 종류만으로 방식을 자동 지정하거나 비용 우위를 보장하지 않는다.
기존 시험 활용은 새 테스트 작성 순서와 다른 축이다. 한 작업에서 기존 회귀를 재사용하면서
새 동작 일부는 TDD, 다른 일부는 구현 후 테스트로 검증할 수 있다.
탐색·직접 관찰은 검증 수단과 작업 목적을 설명한다. 시험을 새로 쓰지 않는 탐색을 네 방식 중 하나로
억지 분류할 필요는 없으며, 제품에 편입할 때 채택할 동작의 구현·검증 순서를 정한다.

## plan에 남길 최소한의 답

기존 [plan 양식](../templates/plan.md)의 네 절을 사용한다. 작은 작업은 아래 내용을 몇 문장으로 합친다.

1. **Files / Order:** 바뀌는 동작과 실제 파일, 선행 계약, 방식과 선택 이유, 구현·검증의 순서.
2. **Risks:** 가장 위험한 실패나 아직 미정인 조건, 그것을 알아낼 방법과 필요한 결정.
3. **Proof:** 관련 AC·보존 동작, 기대의 근거, 실행할 검사·브라우저 절차, 관측할 결과와 확인 한계.

구현 전에 무엇을 성공으로 볼지는 알아야 하지만, 시험의 내부 코드나 최종 파일 구조까지
미리 고정할 필요는 없다. 탐색 결과가 있어야 정할 수 있는 설계는 선행 조사와 후속 결정으로 표현한다.
중요한 미결 계약을 구현자가 알아서 정하도록 숨기거나, 예정 검사를 이미 통과한 것으로 쓰지 않는다.

## 작업 중 피드백

- **TDD:** 의미 있는 동작 시험 → 의도한 이유의 실패 → 최소 구현 → 같은 기대의 통과 → 필요한 정리와 회귀.
  잘못된 경로·fixture·환경 오류를 동작의 RED로 세지 않는다. 이미 통과하는 보존 동작은 그대로 검증한다.
- **구현 후 테스트:** 한 번에 확인 가능한 동작을 구현 → 그 동작의 검사 추가·실행 → 필요한 수정·회귀.
  다음 의존 작업으로 넘어가기 전에 현재 동작을 확인한다. 한 줄이나 함수마다 시험을 강제하지 않는다.
- **기존 시험 활용:** 바꾸기 전 관련 동작과 검사 범위를 확인 → 작은 변경 → 관련·인접 시험 실행.
  기존 시험이 새 계약을 다루지 않으면 보강한다. 새 테스트 파일이 없다는 사실만으로 무검증으로 판단하지 않는다.
- **UI·탐색:** 사용자 목표·제약·확인할 질문 → 작은 시도 → 실제 화면·행동 관찰 → 결과와 다음 결정.
  스크린샷만으로 상태 전환·키보드·권한·데이터 보존을 입증하지 않는다. 중요한 동작은 알맞은 실행으로 확인한다.

자동 시험은 반복 실행할 계약과 중요한 회귀를 보호하는 데 사용한다. 일회성 탐색이나 작은 가역 변경은
직접 확인이 더 적합할 수 있다. 어떤 동작을 어떤 방법으로 확인했는지와 남은 공백을 설명한다.
탐색의 성공은 질문에 답했다는 뜻이다. 제품 완료를 보고하려면 채택한 요구·설계와 필요한 제품 검증을 갖춘다.

## 구현과 테스트가 같은 오해를 공유하지 않도록

먼저 기대값의 출처와 의미를 확인하고, 검사 코드가 그 기대를 실제로 판별하는지 본다. 중요한 위험에
대해서는 독립 계산·신뢰할 수 있는 적합성 사례·실제 경계의 부정 사례·다른 관찰 방법 등을 골라 보강한다.
모든 작업에 이 방법들을 전부 요구하지 않는다. 서로 다른 모델이나 새 문맥이라는 사실도 정답을 보장하지 않는다.

별도 검증자는 spec·사람의 합의·독립 입력에서 기대를 먼저 파악한 뒤 현재 구현·시험·결과와 대조한다.
실제 연결을 검토하려면 구현도 읽어야 한다. 이는 코드를 보여주지 않고 요구사항만으로 테스트를 생성하는
실험과 다른 작업이다. 구현 비노출 테스트 생성이 도움이 되는 범위에서는 별도 문맥에 계약과 기준 입력을
주되, 생성된 시험도 검토하고 실제 실행한다. 최종 검토가 작업 중 피드백을 대신하지 않는다.

리뷰에서 테스트를 삭제·완화해 통과를 만든 변경과, 근거 있는 테스트 정정을 구분한다. 잘못된 fixture·
기대값은 근거와 영향받는 회귀를 제시해 고칠 수 있다. 계약이 달라지면 spec·plan과 필요한 사람의 결정을
함께 갱신한다. 실제 프로젝트가 보호한 시험·파일은 그 통제를 따르고 우회하지 않는다.

## 버그 수정과 전략 변경

가능하면 수정 전에 증상을 재현한다. 자동 시험·임시 스크립트·수동 재현·운영 로그는 각각 증명하는
범위가 다르다. 재현하지 못했다면 이유와 남은 불확실성을 남기고 수정 성공을 단정하지 않는다.
회귀 시험을 수정 뒤에 쓴 경우, 안전하고 실행 가능한 별도 기준 사본에서 같은 시험으로 원래 결함을
잡는지 확인할 수 있다. 이것은 시험의 판별력 확인이며 과거에 TDD를 했다는 증거가 아니다.
사용자 작업 트리를 되돌리거나 파괴적인 운영 동작을 재생하지 않는다. 기준 재생이 불가능하면
다른 독립 근거와 미확인 범위를 밝힌다.

계약이 바뀌거나, 재현·자동화의 제약을 알게 되거나, 기존 검사가 중요한 회귀를 놓치면 방식을 다시
판단한다. 이유·영향·새 검증 순서를 plan에 반영하고 관련 구현과 같은 커밋에 기록한다.
계약 변경은 기존 수락 절차를 따르며, 허용된 범위의 기술적 방식 변경 자체에 새 승인 단계를 만들지 않는다.
실패가 반복되면 같은 명령만 재실행하지 말고 기대·환경·구현·검사 중 무엇이 문제인지 확인한다.
정해진 실패 횟수나 시간만으로 자동 전환하지 않는다. 미해결 실패를 건너뛰어 완료로 바꾸지 않는다.

## 완료·통합·운영

완료 전에 정한 검사와 영향받는 회귀를 실제로 실행한다. 대상 코드판·명령·출력·중요 관찰과 한계를
기존 실행/PR 기록에 남긴다. `pass`, 실패, 미실행, 진행 중 검토를 구별한다. 다른 브랜치의 과거 통과로
현재 결합 결과를 대신하지 않는다. [REVIEW](../REVIEW.md)로 최신 spec·plan·diff·실행 근거를 대조한다.
독립 검토를 채택한 팀은 검토 결과를 기다리고 중요한 발견을 보완한다. 사람의 통합·공개 권한은 그대로다.

운영 결함은 재현·회귀 근거와 함께 다음 의도로 돌린다. 반복되는 에이전트의 오해는 관련 지침·예시를
고치고 그 동작을 별도로 평가한다. 제품 테스트와 에이전트 평가를 같은 성공률로 합치지 않는다.
효율을 비교할 때는 최종 검증·재작업까지의 시간과 알려진 비용을 보고, 중단·재시도·사람 검토의 누락을 밝힌다.
모든 변경에 별도 비용 장부나 평가 플랫폼을 요구하지 않는다.

## 플레이북을 적용하는 범위

AI-Native SDLC Playbook의 사람 중심 의도·설계·계획, 작업 중 피드백, 실행 근거와 최종 리뷰를 따른다.
플레이북의 feedback loop play는 버그 수정에서 실패 시험 선작성·실패 확인·시험 커밋·시험을 바꾸지 않는
수정을 명시하고, 수정 중 시험 편집 보호도 제시한다. **선택형은 이 구체적인 순서와 일괄 동결을 조정한 팀 정책**이다.
검증 약화 금지·독립 기대·회귀 보호는 유지하며 TDD 미선택을 원문과 같은 절차라고 보고하지 않는다.
원문의 해당 처방을 그대로 채택해야 하는 제품은 자기 정책과 실제 통제로 그 범위를 정한다.
이 문서만으로 그런 보호 도구가 설치되거나 기존 통제가 해제되지는 않는다.
