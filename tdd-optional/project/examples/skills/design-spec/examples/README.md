# 이전 최소 작성 예시

이 폴더의 기존 사례는 이전 판의 간결한 예시로 보존한다. 현행 양식을 채우는 구체적 깊이와 필수 입력은 [작성 예시 세트](../../../../docs/sdlc-authoring/README.md)를 먼저 참고한다. 기존 two-pr 사례는 각 PR이 독립적으로 쓸 수 있는 기능이며, 새 F03은 두 PR이 하나의 공개 단위인 경우다.

## 후속 선택을 편입할 때

[feature의 intent](feature/intent.md), [후속 답변](feature/context.md), [spec](feature/spec.md)을 함께 읽는다.
완료 건도 포함한다는 Q1 답변의 이유는 최근 완료 건까지 확인하려는 것이다. 담당자 목록을 좁혀 보는
목적과 읽기 전용 제약을 유지하므로 spec의 R1·AC1·필터 설계에 답을 반영한다. plan이 있으면 영향받는
구현·검증을 맞춘다. intent를 형식적으로 고치거나 이미 받은 답을 다시 묻지 않는다.

기존 배열 순회를 쓰는 설계도 담당자 선택 목적을 만족한다. context에는 저장소를 바꿀 규모나 성능
문제가 없으므로 기존 읽기·출력 경로를 유지한다. 이 이유는 spec의 Design에 남긴다. 별도 인덱스·DB·캐시를
추천하더라도 추천의 전제와 운영 비용을 대조한 뒤 채택하며, 채택 사실만으로 목적 일치를 설명하지 않는다.

다음 두 발언은 개정 경계를 설명하기 위한 가정이다. 실제 feature 요구·수락 기록에 추가하지 않는다.
“조회하면서 완료 처리도 하자”만 들었다면 조회가 파일을 바꾸지 않는 Constraints와 충돌한다.
완료 처리로 해결하려는 불편과 읽기 전용 제약을 바꿀 의사가 있는지, 빠진 결정을 확인한다.
그 선택은 미정으로 두고 독립된 설계 작업은 계속한다.

반면 요청자가 “확인만 하는 목적을 완료 처리까지로 바꾸고, 이 동작의 파일 변경을 허용하겠다”고
명확히 지시했다면 같은 결정을 다시 묻지 않는다. 기존 목적·제약과 바뀐 이유를 보존하며 intent의
해당 산문부터 개정하고 spec·plan을 맞춘다. 이유가 발언에 없고 해석에 따라 큰 재작업이 생기면
그 이유에 관한 빠진 결정만 확인한다. 이런 편입 전 대조는 작은 문구 수정이나 내부 함수 분해마다 반복하지 않는다.
