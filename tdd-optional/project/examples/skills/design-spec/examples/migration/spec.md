# Spec: 처리 결과를 보존하는 SQLite 전환과 보고서 호환
Upstream: intent.md@dbfd371. Status: draft.
작성 조건: root가 허용한 합성 예시 작성이다. 실제 서비스 수락·이행·성능 검증을 뜻하지 않는다.
References applied: intent.md와 context.md (합성 입력). 실제 팀 정책 검토를 실행한 예시는 아니다.

요청을 행 단위 트랜잭션으로 갱신해 다른 요청의 완료를 덮어쓰지 않는다. 서비스 중지 후 검증된
DB로 전환하고, 야간 보고서는 기존 조회 API로 옮긴다. 이행 뒤의 처리 결과까지 보존하는 복구가
전환 조건이다. API 밖 소비자 미확인은 후속 결정으로 해소됐으며 현재 중요한 미결 우려는 없다.

## Requirements
- R1. 서로 다른 요청의 동시 완료가 성공하면 두 결과가 모두 남는다. 같은 요청의 완료를 다시
  보내도 그 요청은 done이고 다른 필드·행을 바꾸지 않는다. 실패를 성공으로 응답하지 않는다.
- R2. 기존 ID·title·owner·status와 목록 순서를 유지한다. GET/완료 응답과 인증·권한·오류
  계약은 [context.md](context.md)에 주어진 기존 의미 그대로다. 권한 없는 완료는 저장소를 바꾸지 않는다.
- R3. 이행은 원본 JSON을 바꾸지 않고 모든 행의 유효성·유일 ID·허용 상태를 확인한다.
  지원하지 않는 형식 버전이나 필드도 값을 버리며 진행하지 않고 거부한다.
  실패·중단된 결과로 전환하지 않는다. 미완성 시도는 원본에서 다시 시작할 수 있다.
- R4. 전환 뒤 처리한 결과가 있으면 그 결과까지 포함해 복구한다. 오래된 원본으로 단순히
  돌아가지 않는다. 쓰기 여부가 불명확해도 쓰기 이후로 취급한다. 복구 데이터와 R1을 유지하는
  쓰기 경로가 검증되기 전에는 서비스를 중지하고 현 DB·복구 데이터를 보존한다.
- R5. 야간 보고서를 기존 GET /requests로 전환해 최신 처리 결과를 읽게 한다. 응답을 못 받으면
  보고서 실패로 알리며 옛 JSON을 현재 값처럼 대신 읽지 않는다. 기존 읽기 계정과 권한 범위만 쓴다.

## Acceptance criteria
다음은 plan이 구체적인 환경·시험·운영 확인으로 연결할 결과다. 아직 실행한 증거는 아니다.
- AC1 → R1: 서로 다른 두 요청을 겹쳐 완료하고 성공한 두 상태가 모두 남는지 확인한다.
  같은 요청의 재시도·응답 수신 실패 후 재조회에서도 다른 필드·행을 바꾸지 않는다.
- AC2 → R2: 같은 데이터로 이행 전후 조회 결과의 필드·값·순서를 비교한다. 정상 완료와
  미인증·권한 부족·없는 ID를 확인하고, 거부된 요청은 데이터가 같아야 한다.
- AC3 → R3: 유효 데이터 전체가 정확히 한 번 들어간다. 중복 ID·필수 필드 누락·잘못된 상태는
  전환을 막고 원본 바이트를 보존한다. 알 수 없는 버전·필드도 거부한다. 중간에 끊은 별도 시도
  후 원본에서 재실행해 누락·중복이 없다.
- AC4 → R1,R4: 전환 후 새로 완료한 행을 포함해 복구용 JSON을 내보내고, 별도 사본에서
  구버전 조회·완료 호환성을 확인한다. 원래 내보낸 복구 데이터는 이 시험으로 바꾸지 않는다.
  쓰기 여부 미확인도 내보내기 경로를 사용한다. 내보내기 실패·중단·검증 실패 또는 재개할
  쓰기 경로의 AC1 미충족 때는 서비스가 중지된 채 DB와 처리 결과가 남는다.
- AC5 → R1,R2: DB 쓰기 경합이 기존 대기 상한을 넘거나 I/O 작업이 실패하면 기존 503 형식이다.
  부분 갱신을 성공으로 알리지 않고, 이후 재조회·재시도에서 확정 상태를 확인할 수 있다.
- AC6 → R2,R5: 보고서를 API로 바꾼 뒤 저장소 전환 전·후에 같은 목록 의미와 신규 완료 반영을
  확인한다. API 오류 시 보고서 실패가 드러나고 옛 파일로 조용히 대체하지 않는다.

## Design

### 저장 경계와 선택
웹 → 기존 API 인증·권한 검사 → 저장소 어댑터 → SQLite라는 경계를 유지한다. 현재 JSON 전체
읽기·다시 쓰기를 대상 행의 상태 갱신으로 바꾼다. 목록은 별도의 원래 순서 값으로 정렬하고,
ID는 유일 키다. id/title/owner/status를 보존하며 null 담당자도 그대로 옮긴다.
스키마에는 형식 버전을 기록해 구버전 프로세스가 새 저장소를 잘못 여는 것을 막는다.

완료의 확인·갱신·결과 읽기는 한 짧은 트랜잭션에서 수행한다. 확인되지 않은 성공을 응답하지
않으며 오류 경로는 롤백·연결 정리를 거친다. 경합 대기는 기존 5초 상한 안에서 끝나고 실패는
기존 503으로 전달한다. 클라이언트는 응답을 놓치면 재조회할 수 있고 같은 완료의 재시도는 안전하다.
락·트랜잭션 전략의 실제 명령과 테스트 연결은 plan에서 구체화한다.

단일 호스트·운영 가능·중지 허용 조건에서 SQLite를 선택했다. JSON 파일 잠금도 가능하지만
전체 파일 갱신·내구성·오류 정리를 직접 유지해야 한다. 외부 DB는 현재 조건에서 새 서비스 운영
부담을 만든다. 이 선택이 모든 동시 쓰기를 무제한 수용한다는 뜻은 아니다. 단일 writer 경합은
위의 제한된 대기·실패 계약으로 다룬다.

### 이행·중단·복구
기존 서비스와 다른 직접 writer가 있다면 그것까지 멈춘 동안 원본을 보존하고 별도 새 DB를 만든다.
전체 입력 검증과 단일 이행 트랜잭션, 행·값·순서 대조가 끝난 뒤에만 서비스의 저장소 설정을
전환한다. 기존 DB가 있는 경로를 암묵적으로 덮어쓰지 않는다. 실패한 임시 시도는 활성 저장소와
구분하고, 원본과 새 임시 대상에서 재시작한다. 운영 담당이 전환·재개를 맡는다.

전환 후 쓰기가 없었음을 확인한 경우에만 보존된 원본을 복구 데이터로 쓸 수 있다. 쓰기 이후이거나
여부를 모르면 서비스를 멈추고 현재 DB의 일관된 전체 값을 별도 JSON으로 내보낸다. 기존
schema_version=1 형식·값·순서를 대조하고 구버전 읽기/완료는 별도 사본에서 검증한다.

이 데이터 검증만으로 결함 있는 구버전 writer를 재개하지 않는다. 운영 담당은 재개할 저장 경로가
R1을 유지함을 AC1로 확인한 뒤에만 쓰기를 연다. 이번 선택의 기본 복구 방향은 최신 데이터를
보존해 SQLite 경로를 복구하는 것이며, 기존 JSON writer의 무제한 동시 쓰기는 허용하지 않는다.
안전한 경로를 확보하지 못하면 중지를 유지한다. 구체적 복구 명령·운영 단계는 plan에서 정한다.
DB·기존 원본·검증 전 복구 데이터는 보존한다. DB 파일·journal을 임의로 복사/삭제해 복구한 것으로
취급하지 않는다. 디스크 자체 손실은 이번 전환 복구 범위 밖이며 백업 체계는 합성 입력에 주어지지 않았다.

### 뒤늦게 확인된 소비자
처음에는 Q1이 미확인이라 저장소 전환 설계를 인계하지 않았다. 보고서가 옛 JSON을 읽는다는
발견 뒤 업무 오너·운영 담당은 보고서를 기존 조회 API로 옮기기로 했다. 영구 JSON 미러나 이중
쓰기를 두면 현재 데이터가 둘로 나뉘므로 선택하지 않았다. 보고서의 기존 서비스 계정과 읽기 권한을
사용하고, 호환성 확인을 전환 조건에 포함한다. 그래서 R5·AC6가 같은 spec의 계약이다.

### 계획에 넘길 경계
공유 계약은 저장소 인터페이스, 목록 순서, 완료의 원자성, 기존 응답·권한과 이행/복구 조건이다.
구체적 스키마/함수 이름·파일별 소유·PR 순서는 plan에서 정한다. 저장소 어댑터와 보고서는
이 계약 아래 나눠 작업할 수 있지만, 최종 전환은 전체 데이터·API·보고서·복구의 통합 검증을 따른다.

## Constraints and scope
intent의 기존 필드·순서·정상 응답·인증/권한은 R2에 보존했다. 외부 서비스·계정을 추가하지 않고
중지 가능한 단일 호스트 안에서 이행한다. 데이터 보존은 R1,R3,R4의 전환·복구 기준으로 구체화했다.
보고서의 입력 경로 변경은 발견 후 이번 범위에 포함됐다. 롤링 배포·다중 호스트·ID 재발급·
영구 JSON 미러·새 권한 체계·성능 수치 개선 약속은 범위 밖이다.

## Open questions
- Q1 answered: 운영 담당이 보고서 하나의 직접 읽기와 직접 쓰기 소비자 없음을 확인했다.
  업무 오너·운영 담당의 API 전환 결정을 R5·Design·AC6에 반영했다.
- Q2 answered: 실패 시 원본 보존, 쓰기 이후의 최신 상태와 안전한 쓰기 경로가 필요하다.
  복구 설계 검토의 추가 결정을 R3,R4·AC4·Design에 반영했다.
- Q3 answered: 단일 호스트·SQLite 지원 로컬 저장소와 운영 담당 책임을 확인했다.
설계에서 새로 확인할 핵심 업무 결정은 현재 없다. 실제 경합·이행·복구 검증은 plan과 구현의
증거로 남겨야 하며, 미실행 검증을 이미 확인한 사실로 바꾸지 않는다.
