# 필요할 때 선택하는 설계 블록

설계 양식의 Design에 필요한 블록만 가져온다. 먼저 변경의 이유와 대표 흐름을 설명하고 상세 계약을 연결한다.
각 계약의 이름과 도식의 이름을 맞춘다. 아래는 선택할 형태이며 모든 항목·그림을 복사하라는 뜻이 아니다.
여섯 절은 spec 진입점에서 찾을 수 있게 하고 상세 정본은 여러 파일이어도 된다.

| 상황 | 남길 결정·표현 | 완성 예시 |
|---|---|---|
| 기존 흐름의 좁은 변화 | 정확 입력/출력·실패·삽입 위치. 짧은 표/문장으로 충분 | [F01](../../../../docs/sdlc-authoring/examples/F01/spec.md) |
| UI·통합 사용 흐름 | 실제 사용자 여정·빈/거부/실패 상태·기존 소비자 호환. 사용한 mock의 판과 구속 범위 | [W01 화면→API](../../../../docs/sdlc-authoring/examples/W01/spec.md) |
| API/공유 타입·객체 계약 | 입력/반환/오류·권한·호환·소유 관계. 관계가 복잡하면 클래스/컴포넌트 | [M01 architecture](../../../../docs/sdlc-authoring/examples/M01/design/architecture.md) |
| 순서·경합·재시도가 결과를 바꿈 | 전제/부작용 시점·실패 분기·멱등성. 시퀀스 | [M01 storage](../../../../docs/sdlc-authoring/examples/M01/design/storage.md) |
| PR별 준비/공개 상태가 다름 | 상태/허용/금지·제어·공개/중단·제거. 상태도 | [F03](../../../../docs/sdlc-authoring/examples/F03/spec.md) |
| 저장/실행 위치·운영 경계 변경 | 프로세스/설정/데이터·전환·복구 책임. 배포 뷰 | [M01](../../../../docs/sdlc-authoring/examples/M01/design/architecture.md) |
| 성능·외부 의존 | 알려진 부하/측정 근거·한도·운영 비용·허용할 성능 저하/실패. 근거 없으면 영향받는 결정을 미정으로 | 해당 제품의 실제 측정/제약 |

공개 제어는 [팀 정책](../../../../docs/RELEASE-CONTROL.md)의 신뢰할 시험 대상·직접 호출/부작용 경계·
설정 실패 기본값·구버전/복구를 함께 고려한다. 로컬 F03 예시가 실제 서버의 인증/권한 설계를 대신하지 않는다.

## 실행 가능한 UI와 검증 경계

기존 UI를 바꿀 때 비교할 실제 화면·공통 컴포넌트/스타일과 사람의 시각 기대를 확인한다. 상호작용이나
결합이 불확실하면 설계 중 실제 컴포넌트를 story·sandbox route·앱 셸에 최소 구현해 먼저 관찰할 수 있다.
정적 HTML은 배치 비교에 적합할 수 있지만 실제 앱의 전역 키 처리·겹침·초점·loading/error·권한 상태를
대신하지 않는다. 이번 위험에 닿는 상태를 고르고 스크린샷과 행동을 기준 화면·기대와 비교해 조정한다.
자료의 판·실행 위치·상태/데이터·채택한 결정·가상 연결·남은 검증을 인계한다. 초기 코드를 제품에
계속 쓸 수 있으나 실제 연결·품질·회귀를 확인해야 한다. 모든 화면 완성이나 특정 UI 도구를 요구하지 않는다.

## 중요한 AC의 검증 접근

중요한 AC/설계는 기대만 적지 말고 판별 가능한 검증 접근을 연결한다. 예를 들어 “저장 거절 시 기존 값 유지”는
독립 fixture의 이전 값, 실제 권한 거절을 통과하는 HTTP 호출, 응답과 저장소 재조회로 판별할 수 있다.
가짜 API 응답만 쓰는 컴포넌트 시험은 화면 상태의 근거이며 실제 권한/저장의 근거는 아니다.
실행할 환경·필요 입력·실패를 유도할 지점·관측할 효과와 가상화 한계를 spec에서 찾을 수 있게 하고,
plan에서 작업별 절차와 첫 실제 연결 시점으로 이어간다. 검증 방식 이름·시험 수만으로 충분성을 판단하지 않는다.
이 예시는 권한/저장 계약을 바꾸는 경우의 선택이다. F01처럼 출력 필터만 바꾸면 독립 입력과 정확한
stdout·종료 코드, 보존할 동작의 기존 시험으로 판별할 수 있다. 모든 변경에 HTTP·DB·별도 검증 표를 요구하지 않는다.
설계에서 기대/관측을 정한 것과 실제 시험으로 확인한 것을 구분한다. 실행해야 알 수 있는 환경·성능·
경합 결과는 필요한 관찰과 미확인 범위를 남기며 설계 검토만으로 통과했다고 기록하지 않는다.

## 설명과 계약을 잇는 형태

여러 경계를 바꾸면 `현재 문제 → 제약 → 선택과 감수할 점 → 대표 동작 → 정확한 계약`을 연결한다.
작은 변경이면 한 문단으로 충분하다. 예를 들어 F01은 다음 설명으로 흐름을 닫을 수 있다:

> 기존 list는 전체 요청을 같은 열/순서로 출력한다. 새 --owner는 JSON을 읽은 뒤 출력 직전에 정확히 일치하는
> 담당자만 남긴다. 기존 display와 show/complete를 재사용하므로 저장 형태와 완료 동작은 바뀌지 않는다.
> 완료된 요청도 포함하며, 결과가 없으면 빈 stdout과 rc0다. 데이터와 상세 입력은 F01의 R/AC를 따른다.

M01은 현재 JSON 전체 쓰기에서 생기는 유실, 행 트랜잭션과 보고서 소비자 전환을 먼저 설명한 뒤
[구성/흐름](../../../../docs/sdlc-authoring/examples/M01/design/architecture.md)과 [정확한 저장 계약](../../../../docs/sdlc-authoring/examples/M01/design/storage.md)을 읽게 한다.
W01은 [화면 상태와 대표 요청](../../../../docs/sdlc-authoring/examples/W01/spec.md)을 통해 권한·오류·공개 제어가 사용자 경험에 어떻게 연결되는지 보여준다.
새 다이어그램·용어집·대안 수를 강제하지 않는다. 비교할 선택이 있다면 그 제약에서 왜 골랐고 어떤 비용을 받아들이는지 쓴다.

## 공유 의미와 이월을 판단하는 예

공유 계약은 호출자와 수신자 양쪽에서 입력·허용/거부·결과를 따라간다. 두 구현자가 문장을 모두
지키면서도 호환되지 않는 결과를 만들 수 있다면 빠진 의미와 그 영향을 구체적으로 지적한다.
고정된 기존 정본을 참조해 보존하는 계약은 재기술하지 않아도 된다. 새로운 전달·변환 경계를 만들면
그 경계의 지원 동작별 의미를 별도로 확인하며, 공통 header나 대표 동작 하나로 나머지를 대신하지 않는다.
예를 들어 “중복 요청은 안전하게 처리”만으로는 재실행과 기존 결과 반환 중 무엇인지 알 수 없다.
동일 ID/같은 입력의 결과와 다른 입력의 거절을 정했다면 내부 Map/DB 선택·생성 manifest 파일은
뒤에 구체화할 수 있다. 모든 제품에 멱등성이나 schema 파일을 요구하는 예시는 아니다.

AC가 서버·작업자 재시작을 함께 약속한다면 각각에서 살아 있는 주체, 처리 권한, 상태/효과,
실패·불명 처리와 재개 조건이 이어지는지 확인한다. 서버 재시작의 복구 절이 작업자만 종료된
분기에도 적용되는지는 진입 조건으로 판단한다. “이전 실행이 끝날 때까지 차단”은 안전 규칙이며
누가 종료를 확인하고 다음 실행을 허용하는지까지 자동으로 정하지 않는다. 지원하지 않는 복구도
관찰 결과·수동 인계·범위를 정하면 유효한 결정이다. 중요한 분기만 보고 모든 상태 조합을 나열하지 않는다.

공유 의미·복구 선택처럼 다음 작업이 의존하는 미결은 영향·결정자·필요 시점과 인계 제한을 남긴다.
이미 결정한 계약 아래의 private method·배포 값과, 실행으로 확인할 성능·복구 성공은 구분한다.
후속 발견으로 계약이 바뀌면 해당 spec 정본과 영향 plan을 갱신한다. 작은 F01에는 기존 짧은 설명으로 충분하다.

## 도식의 작은 작성 형태
먼저 답할 질문을 고른다: 누가 호출하는가, 어디서 실패하는가, 어느 상태에 무엇이 허용되는가, 어디서 실행되는가.
문장/표만으로 모호하거나, 계약이 문장으로 충분해도 여러 경계의 관계와 대표 흐름을 한눈에 이해하는 데
도움이 될 때 Mermaid로 다음 요소를 선택한다. 완성 문법/렌더 결과는 위 예시와 검증 기록에 있다.
- 컴포넌트: `flowchart LR`, `A["실제 모듈·책임"] -->|"계약/데이터"| B["의존 모듈"]`.
- 시퀀스: `sequenceDiagram`, 실제 참여자와 호출/결과, 필요한 `alt` 실패 분기·효과 발생 시점.
- 클래스: `classDiagram`, 안정된 공개 메서드/속성과 의존·구현·소유 관계. 내부 메서드는 중요한 경우만.
- 상태: `stateDiagram-v2`, 상태별 허용/금지, 전이 이벤트·실패/중단을 표시.
- 배포: `flowchart`의 `subgraph`로 호스트/프로세스/신뢰 경계, 설정과 데이터 위치를 표시.

도식만으로 타입·오류/권한·동시성을 추측하게 하지 않는다. 표/문장과 역할을 나누되 같은 결정을
둘 다 다르게 정의하지 않는다. 다이어그램은 반드시 UML 형식일 필요가 없으며 클래스 그림 자체가
명확성을 높이지 않는 작은 변경에는 추가하지 않는다.

## 여러 설계 파일
예: spec.md는 FR/NFR(기존 R)/AC·요약·정본 목록, design/api.md는 API 계약, design/storage.md는 스키마/원자성.
주요 설계 단위의 SP는 그 결정을 소유한 파일에서 한 번 정의하고 관련 요구를 경로+ID로 연결한다.
spec 색인은 SP·소유 경로·필수 읽기를 안내한다. 컴포넌트 수와 SP 수를 맞추거나 모든 메서드에 ID를
붙일 필요는 없다. 이동·분할·폐기는 [추적 규칙](../../../../docs/sdlc-authoring/traceability.md)을 따른다.
spec.md에서 정확 상대 링크와 소유 결정/필수 읽기 범위를 제공한다. 같은 Git 판의 문서 집합으로
인계·리뷰한다. 외부 정본은 판/스냅샷과 접근 경로를 특정한다. plan은 그 집합의 필요한 절을 참조한다.
요약과 상세가 어긋나면 한쪽을 임의로 믿지 말고 정본을 확인해 고친다. 분리 후에도 중요한 결정 누락은 안 된다.
