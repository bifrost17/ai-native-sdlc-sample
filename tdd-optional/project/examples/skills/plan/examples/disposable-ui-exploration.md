# Plan: 제출 확인 UI 두 형태를 폐기 가능한 prototype으로 비교

가상 plan-only 예시이며 실제 제품 저장소·화면·사용자를 관찰한 기록이 아니다. 가상 입력은 다음과 같다.
요청 제출 직전 확인을 inline 영역과 modal 중 어떤 형태로 설계할지 미정이다. 고정된 제약은 키보드만으로
확인과 취소가 가능하고, 취소가 제출을 일으키지 않으며, 320px와 넓은 화면에서 주요 문구와 조작이 가려지지 않는 것이다.
서버 API·권한·데이터 계약은 이번 탐색에서 바꾸지 않는다. 실제 제품에 적용할 때에는 현재 intent/spec의 열린 질문,
허용된 탐색 범위, UI 정책과 실제 컴포넌트 경로를 먼저 확인한다.

## Files that change

- `spikes/request-confirmation.html` (new, 폐기 후보): 가상 데이터로 inline과 modal 확인 흐름을 전환해 보는 제품 비연결 prototype.

실제 `src/web/RequestForm.*`와 제품 route/build/import는 읽기 기준일 뿐 이 탐색에서 수정하지 않는다. 팀이 다른
격리 위치나 기존 Storybook을 사용한다면 실제 경로로 바꾸고 plan에 이유를 반영한다.

이 정적 탐색은 배치 비교용이다. 기존 앱의 키 처리·겹침·초점·상태 결합이 질문이라면 실제 컴포넌트와
앱 셸을 쓰는 격리 진입점이 더 적합하다. 그 경우 사용할 코드·상태/데이터·가상 API와 제품 편입 범위를
계획에 정하고, 실제 기준 화면과 비교해 사람의 시각 피드백을 남긴다. 모든 탐색을 HTML로 제한하지 않는다.

그 선택에서는 아래의 정적 예시 파일·순서·위험 범위를 실제 격리 경로에 맞게 바꾼다. 예를 들어 현재
제품의 기존 modal과 스타일을 sandbox에서 렌더하고 loading·error·초점 상태를 주입해 앱 셸과 비교할 수 있다.
읽기 기준의 `src/web/RequestForm.*`를 실제로 바꾸려면 그 파일과 범위를 plan에 명시한다. 현재 공개/데이터
정책에 따라 일반 사용자 노출과 실제 부작용을 제한한다. 어떤 코드는 폐기하고 어떤 코드는 제품에 편입할지
정하고, 편입할 때 해당 spec/AC와 실제 연결·회귀 Proof를 갖춘다. 아래의 제품 비연결 조건은 정적 예시의
탐색 경계이며 모든 UI 설계에 적용하는 금지 규칙이 아니다.

## Order of work

검증 방식: **UI 탐색과 직접 관찰**. 목적은 두 형태 중 하나를 이미 제품 계약으로 가정하는 것이 아니라,
고정 제약을 만족하는지와 남는 tradeoff를 확인해 설계 결정을 돕는 것이다. 자동 시험 선작성이나 RED는 요구하지 않는다.

1. 현재 제품에서 제출 직전 흐름, 키보드 순서, 사용 중인 dialog/inline pattern과 실제 브라우저 실행 방법을 확인한다.
   이 가상 예시에는 그 관찰 결과가 없으므로 baseline 통과를 주장하지 않는다.
2. 제품 코드에 연결하지 않은 prototype에 두 형태를 최소한으로 만든다. 실제 계정·API·저장소를 호출하지 않고,
   가상 데이터임을 표시한다. 디자인 시스템의 안정된 component가 확인되면 재사용하되 prototype이 새 정책을 정하지 않는다.
3. 320px와 넓은 viewport에서 Tab/Shift+Tab/Enter, modal의 Escape, 확인·취소와 초점 복귀를 직접 수행한다.
   각 형태가 고정 제약을 만족하는지, 문구·맥락·작은 화면에서 생기는 차이와 확인하지 못한 항목을 기록한다.
   스크린샷은 배치 근거일 뿐 키보드 전환이나 미제출 상태의 단독 증거로 쓰지 않는다.
4. 관찰이 질문에 답하면 **탐색 성공**이다. 선택하지 않은 prototype은 폐기한다. 어떤 형태를 제품에 채택하면
   관련 spec의 UI 동작·상태·AC를 갱신하고 수락된 판에서 실제 제품 파일, 검증 방식과 통합 Proof를 가진 계획으로 이어 간다.
   결정이 나지 않으면 두 prototype 중 하나를 임의로 제품에 넣거나 제품 완료로 보고하지 않는다.

## Risks

가상 화면은 실제 인증, 네트워크 실패, 중복 제출, 저장 결과나 제품 CSS 충돌을 증명하지 못한다. 한 사람이 두
viewport를 확인한 결과는 사용자 연구나 접근성 전체 감사도 아니다. prototype을 production import에 연결하거나 실제
데이터를 사용하면 폐기 가능한 경계를 잃으므로 중지하고 제품 변경의 spec/plan 범위로 다시 판단한다.

## Proof

탐색의 예정 근거는 사용한 prototype 판·브라우저/viewport, 각 키 입력과 관찰 결과, 두 형태의 제약 충족 여부,
남은 질문과 폐기/채택 결정이다. 아직 실행된 항목은 없다.

이 근거는 “어떤 형태를 채택할지 판단할 정보가 생겼다”까지만 뒷받침한다. 제품 완료에는 채택된 spec/AC,
실제 RequestForm 연결, 상태·키보드·오류·권한의 제품 검증과 영향받는 회귀, 최신 통합 판의 결과가 별도로 필요하다.
