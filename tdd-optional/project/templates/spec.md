# Spec: ‹이번에 만들거나 바꿀 것›
Upstream: intent.md@‹실제 사용한 판›. Status: draft.
Skills applied: ‹실제 읽고 적용한 팀 스킬·출처·확인 판, 없으면 none·확인 한계›.

‹현재 사용자가 겪는 문제와 이번 변화·선택을 연결한 짧은 설명. 확인한 현재 계약/입력은 링크한다.
사람이 판단할 중요한 미해결 우려가 있으면 먼저 밝힌다.›

## Requirements
| ID | 바뀔 동작 또는 유지할 계약 | 근거 |
|---|---|---|
| FR01 | ‹누가/어떤 조건에서 무엇을 할 수 있으며 무엇은 유지되는가› | ‹intent 문단·답변·정책·현재 계약의 경로/절› |
| NFR01 | ‹근거가 있는 품질·운영 제약. 해당 요구가 없으면 행 삭제› | ‹실제 제약/측정 근거. 없는 수치 생성 금지› |

‹새 spec의 기능/품질 요구는 FR/NFR로 구분한다. 기존 R/AC ID는 유지한다.
ID 범위·수명·정본 연결은 [추적 규칙](../docs/sdlc-authoring/traceability.md)을 따른다.
요구를 맞추려고 intent 산문을 요구 목록으로 바꾸거나 모든 요구를 intent에 역작성하지 않는다.›

| AC02 → ‹FR/NFR 또는 기존 R› | ‹중요한 실패 또는 인접 회귀 사례› | ‹구현과 독립적으로 알 수 있는 기대› |

## Design
‹아래 작성 면을 변경에 맞게 합치거나 나눈다. 작은 변경은 짧은 문단/표로 충분하다.
완성된 설명·계약·도식의 선택은 저장소 루트의 `examples/skills/design-spec/references/design-depth.md`를 참고한다.›

### Approach
‹현재 경계/흐름›에서 ‹문제의 원인›이 생긴다. ‹이어받은 제약› 때문에 ‹선택한 구조›로 바꾸고
‹기존 연결점/소비자›는 ‹보존할 방식›으로 유지한다.
‹실제 고려한 대안›도 가능하지만 ‹선택을 가른 이유›로 택하지 않았다. 대신 ‹운영/유지/성능 비용›을 감수한다.

### SP01 — ‹핵심 계약·결정 또는 컴포넌트 책임›
요구: ‹FR01, NFR01 또는 기존 R ID. 다른 정본이면 경로+ID›. 관련 관찰: ‹AC01/AC02›.
‹핵심 개념·책임·현재/목표 상태의 구분. 실제 확인한 코드/계약의 위치›.
1. ‹행위자›가 ‹대표 입력/행동›을 주면 ‹경계/모듈›이 ‹권한/전제›를 확인한다.
2. ‹호출·상태 변화와 효과가 확정되는 시점›. ‹결과를 바꾸는 실패/재시도 분기와 보존할 상태›.
3. ‹사용자/다음 소비자가 보는 결과›. ‹AC 또는 아래 정본 계약›으로 판정한다.

| 계약/정본 | 정확한 입력·출력·상태·실패 또는 읽을 절 |
|---|---|
| ‹인터페이스/데이터/설정의 실제 이름, 또는 상세 정본 링크› | ‹관련 타입·값·순서·권한·호환. 예시와 구속 계약 구별› |

‹공개를 나누면 저장소 루트의 `docs/RELEASE-CONTROL.md`를 이 변경의 공개 단위·제어 경계·
기본/시험 상태·공개/중단 조건으로 구체화한다. 그림은 모호한 관계·순서·경계를 설명할 때 선택한다.›

‹독립적으로 바꾸고 검토할 주요 설계 단위마다 SP를 부여한다. 작으면 위 블록 하나로 충분하다.
나누면 아래 색인에 ID·정본·필수 읽기를 연결하고, 각 SP의 정본에서 요구를 참조한다.
색인에 상세 계약이나 요구 관계를 중복 정의하지 않는다. 상세 파일에 여섯 절을 복제하지 않는다.›
| 설계 ID | 정본 경로 | 소유하는 결정·읽을 범위 |
|---|---|---|
| SP01 | 이 파일의 SP01 | ‹위 핵심 계약› |
| ‹SP02› | ‹예: design/storage.md 링크, 그 파일에서 정의할 ID› | ‹스키마/원자성·실패 계약, 구현·리뷰 시 함께 읽기› |
