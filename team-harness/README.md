# 팀 개발·독립 검토 진입점

`sdlc-claude`는 개발 Claude의 응답 뒤에 별도 Claude 검토를 실행한다. 중요한 누락을 발견하면
같은 개발 세션에 자동 피드백하며 한 사용자 턴에서 최대 두 번 보완한다. 마지막 보완도 다시 검토한다.
문서 의미는 모델이 판단한다. 파일이 수정됐다는 이유나 Markdown 모양만으로 통과시키지 않는다.

## 설치와 대화

Claude Code의 로그인과 Python 3가 있는 Mac에서 다음을 실행한다.

```bash
python3 team-harness/install.py
~/.local/bin/sdlc-claude --project /absolute/path/to/product \
  --chain intent/0001-your-change --base <기준-커밋>
```

프롬프트는 stdin으로 입력하고 EOF(Ctrl-D)로 끝낸다. 파일에 작성했다면 위 명령 뒤에
`< request.txt`를 붙일 수 있다. 응답 끝의 `Session:` 값을 다음 호출의 `--resume <UUID>`로 전달해
대화한다. 프로젝트·사슬·기준 커밋은 같은 값으로 유지한다. 원본 업무 요청·HUMAN 답변과 수락도
이 진입점으로 전달해야 검토자가 판단 근거로 읽을 수 있다.

현재 CLI의 고정 실행 조합은 개발 `sonnet --effort low`, 검토 `sonnet --effort medium`이다. 낮은 검토 추론에서 놓친
수락 판 참조를 같은 입력의 중간 추론에서 발견한 실험을 반영했다. 독립 검토는 도구 없는 별도 세션이다.
개발 AGENT는 파일 편집과 허용한 검증 명령을 수행하고 Git 변경·커밋·병합은 HUMAN이 맡는다.
기존 spec/plan 사슬이 있는 작은 작업에 적용하며, 초기 사슬 생성이나 범용 Claude 명령의 대체품은 아니다.

## 모델과 추론 선택

하네스의 목표는 모든 실수를 차단하는 것이 아니다. 개발자·하위 에이전트·독립 검토자에게 맡기는
일의 난도, 틀렸을 때의 영향, 판단의 불확실성에 맞춰 모델과 추론 수준을 선택한다.

- 일반적인 작은 구현·단순 확인은 비용과 시간을 고려한 가벼운 설정으로 시작한다.
- 복잡한 설계, 여러 문서의 합의·수락 판 대조, 보안·데이터 손상처럼 영향이 큰 변경의 판단은
  처음부터 더 역량 높은 모델과 높은 추론 수준을 사용한다. 실패할 때까지 낮은 설정을 고집하지 않는다.
- 오판이 반복되면 입력·맥락·근거가 충분한지 확인하고 모델이나 추론 수준을 높이거나 다른 검토자·
  사람에게 인계한다. 개별 오판을 모두 막으려고 프롬프트·절차·검사기를 계속 늘리지 않는다.

사용자의 비용·시간 한도를 존중하고 필요한 작업에 설정을 집중한다. 높은 모델도 실수할 수 있으므로
관련 시험·독립 검토·사람의 판단은 유지한다. 평가에서는 실제 실행 결함, 모델의 판단 실수, 사람이
결정할 사항을 구분하고 중요한 누락을 통과로 바꾸지 않는다.

위 원칙은 운영자의 선택 가이드다. 현재 CLI에는 모델 선택 옵션이나 자동 승격 기능이 없고,
0018에서 확인한 고정 조합을 사용한다. 그 조합이 작업에 부족하면 운영자가 더 높은 설정을 지원하는
실행 경로로 전환하거나 사람에게 인계한다. 현재 조합을 모든 작업의 권장값이나 상한으로 해석하지 않는다.

## 결과와 인계

| 결과 | 의미 | 종료 코드 |
|---|---|---|
| pass | 현재 요청과 실제 증거가 정합함 | 0 |
| wait | 사람의 업무 답변·수락이 필요한 정상 대기 | 0 |
| revise | 개발자가 보완할 구체적 결함. 자동 resume 후 재검토 | 아직 반환하지 않음 |
| unknown / 미해결 | 검토 오류·지원하지 않는 입력·오래된 결과·보완 상한 등 | 2 |

`wait`는 완료 판정이 아니다. 표시된 업무 결정을 한 뒤 `--resume`으로 답한다. rc2는 출력된
기록을 읽고 원인을 해결한 뒤 이어간다. 검토 실패를 통과로 바꾸는 우회 옵션은 없다.
실행당 timeout은 기본 180초이며 `--timeout <초>`로 조정한다. 큰 입력이나 binary가 포함되면
조용히 자르지 않고 인계한다. 제품 범위가 크면 검토 가능한 작업 단위로 나눈다.

## 적용 범위와 기록

- `~/.local/share/intent-sdlc-harness`에 실행 파일·검토 지침을, `~/.local/bin/sdlc-claude`에
  명령을 설치한다. PATH와 개인 Claude 설정 파일은 수정하지 않는다. 같은 설치 명령으로 갱신한다.
- 실행 기록은 `~/.local/state/intent-sdlc-harness/<session>/`에 남는다. 업무 대화·실행 도구 결과·
  검토 입력/결과·기준/현재 커밋·입력 digest·실제 모델·시간·CLI 표시 비용을 보존한다.
  숨겨진 추론은 제외한다. 기록에는 제품 코드와 업무 정보가 있으므로 팀 내부 자료로 취급한다.
- 원래 템플릿에 실행 도구나 필수 스킬을 복사하지 않는다. 현재 실행 프로필은 hooks·MCP와 지정한
  외부 플러그인을 끄며 제한된 도구로 실험한 프로필이다. 기존 조직 통제가 모두 적용됐다고 볼 수 없다.
- 일반 `claude` 직접 호출은 이 검토 경로를 거치지 않는다. 검토는 모델 판단이며 무오류를 보장하지
  않는다. HUMAN의 spec 수락·최종 코드 검토·PR 병합 책임과 조직의 권한 설정은 별개다.

설치 후 검증과 실제 자동 보완의 근거는 [0018 실험 기록](../docs/experiments/0018-team-harness.md)에 둔다.
